Presenter에서 유스케이스 인터페이스를 의존하는 이유

Clean Architecture · 22장 클린 아키텍처 · 2026-03-22

✦
핵심 답변
22장의 인터페이스는 두 종류이고, 존재 이유가 다르다. Output Boundary/Data Access Interface는 의존성 규칙을 지키기 위해 필수이고, Input Boundary는 유스케이스 교체 가능성이 있을 때만 의미 있다.

출발점: "UI 계층에서 UseCase에 의존하는 건 상관없잖아?"

맞다. Controller(저수준)→UseCase(고수준)는 이미 올바른 방향이다. 의존성 규칙을 위반하지 않는다. 그러면 왜 22장에서는 Input Boundary 인터페이스를 끼웠을까?

◉
Output Boundary — 이건 필수다

UseCase가 실행 결과를 Presenter에 전달해야 한다. 이때 UseCase가 Presenter를 직접 알면? 

// UseCase(고수준)가 Presenter(저수준)를 직접 의존 → 의존성 규칙 위반!
public class CreateOrderInteractor {
    private final OrderPresenter presenter; // 저수준 클래스를 직접 import

    public void execute(CreateOrderRequest request) {
        Order order = ...;
        presenter.present(order); // 고수준 → 저수준 의존
    }
}

고수준(UseCase)이 저수준(Presenter)을 직접 의존하게 된다. DB Gateway 케이스와 완전히 같은 문제다. 그래서 Output Boundary 인터페이스를 UseCase 계층에 두고, Presenter가 이를 구현하게 해서 방향을 역전시킨다. 이건 의존성 규칙을 지키기 위해 반드시 필요하다.

◈
Input Boundary — 이건 항상 필요한 건 아니다

Controller→UseCase는 이미 저수준→고수준이니까, 구체 클래스에 직접 의존해도 의존성 규칙 위반이 아니다. 

// 이것도 의존성 규칙상 문제없다
public class OrderController {
    private final CreateOrderInteractor useCase; // 구체 클래스 직접 의존

    public void createOrder(HttpRequest req) {
        useCase.execute(new CreateOrderRequest(...));
    }
}

그러면 22장에서 Input Boundary를 넣은 건 왜일까? 유스케이스 구현체를 교체할 가능성을 고려한 것이다. 

// 인터페이스가 있으면 구현체 교체가 가능
public interface CreateOrderInputBoundary {
    void execute(CreateOrderRequest request);
}

// 일반 주문
public class CreateOrderInteractor implements CreateOrderInputBoundary { ... }

// 프리미엄 주문 (다른 비즈니스 로직)
public class PremiumCreateOrderInteractor implements CreateOrderInputBoundary { ... }

이런 교체 가능성이 현실적으로 존재하면 Input Boundary는 의미가 있다. 하지만 구현체가 하나뿐이고 교체할 일이 없다면? 불필요한 간접 계층이고, 오버엔지니어링이다.

22장은 Clean Architecture의 "원칙의 완전한 형태"를 보여주는 교과서적 예시이지, "항상 이렇게 해야 한다"는 뜻이 아니다.

◆
정리
인터페이스 의존 방향 필수 여부 이유
Output Boundary
(UseCase → Presenter)		 고수준→저수준
방향 잘못됨		 필수 없으면 의존성 규칙 위반. 방향을 역전시켜야 한다.
Data Access Interface
(UseCase → DB)		 고수준→저수준
방향 잘못됨		 필수 Output Boundary와 같은 이유. 방향 역전이 필요하다.
Input Boundary
(Controller → UseCase)		 저수준→고수준
이미 올바름		 선택적 유스케이스 구현체 교체가 현실적일 때만 의미 있다. 구현체가 하나뿐이면 오버엔지니어링.
◆
시각화

빨간 인터페이스 = 없으면 고수준→저수준 의존이 되어 의존성 규칙 위반. 반드시 필요.
노란 인터페이스 = 방향은 이미 맞음. 유스케이스 구현체를 교체할 일이 있을 때만 의미 있고, 아니면 오버엔지니어링.
