쿠폰 발급에 Redis를 도입하고 맞닥뜨린 정합성 문제 (3)
2-phase Reservation과 pending 큐

보상이 실패할 수 있다는 걸 인정하고 나면, 남은 선택지는 "실패한 걸 나중에 주워 담을 수 있게 해놓기"다. 그 주워 담는 범위를 최대한 좁혀본다.

보상은 왜 약한가

1편에서 나왔던 구조를 다시 보자. 

try {
    Redis SADD
    Redis DECR
    DB INSERT
} catch (Exception e) {
    Redis INCR      // 보상
    Redis SREM      // 보상
    throw e;
}

얼핏 깔끔해 보이지만 이 구조는 보상이 무조건 실행된다는 가정에 기대고 있다. DB INSERT가 실패하는 원인이 서버 크래시라면 catch 블록 자체가 실행 안 된다. 네트워크가 끊겨도 보상 명령 자체를 Redis로 못 보낸다. 보상의 보상이 필요해지고, 그 보상의 보상도 필요하고... 끝이 없다.

완벽한 보상 트랜잭션은 불가능하다. 대신 "보상 실패한 건을 나중에 찾아낼 수 있는 장치"를 둘 수 있다.

"어디까지 진행됐지?"를 남겨두자

아이디어는 단순하다. Redis 작업을 하기 전에 "지금부터 이걸 하려고 한다"는 기록을 Redis 자체에 남긴다. 완료되면 그 기록을 지운다. 중간에 죽어서 기록이 지워지지 않았다면, 나중에 봤을 때 "얘는 어디선가 끊긴 놈이다"라는 단서가 된다.

이 "미확정 기록"을 담을 자리를 pending이라고 부르자. Redis Hash 하나면 충분하다. 

coupon:1:pending = {
    "5": "1713600000123",    // 유저 5가 1713600000123ms에 발급 시작함
    "7": "1713600000456",
    ...
}

그리고 발급 흐름을 이렇게 쪼갠다.

  1. Phase 1 (reserve) — 재고 차감 + 발급 기록 + pending에 "시작함" 표시
  2. DB INSERT
  3. Phase 2a (commit) — DB 성공 → pending에서 제거
  4. Phase 2b (revert) — DB 실패 → 재고/이력 원복 + pending에서 제거

정상 흐름이라면 pending은 거의 항상 비어있다. 들어왔다가 수십 ms 안에 빠져나가기 때문. pending에 남아있다는 건 "DB까지 끝냈는지 확인 안 된 건"이라는 뜻이다.

Lua 스크립트로 묶어야 하는 이유

Phase 1은 세 연산이다. 

SADD coupon:1:issued "5"         -- 중복 체크 + 기록
DECR coupon:1:stock              -- 재고 차감
HSET coupon:1:pending "5"    -- 미확정 표시

이걸 Java에서 그냥 순서대로 호출하면 어떻게 될까. 중간에 문제가 생길 여지가 꽤 많다.

  • SADD는 됐는데 DECR 직전에 서버가 죽으면 → 발급 기록은 남아있고 재고는 그대로
  • DECR이 -1을 돌려줘서 되돌리려고 INCR + SREM을 쳤는데 SREM 직전에 네트워크가 끊기면 → 발급 기록만 남은 채로 끝
  • DECR까진 됐는데 HSET 실패하면 → 제일 중요한 "미확정 표시"가 없어서, 이 건은 나중에 찾을 방법이 없다

마지막이 제일 치명적이다. Redis 상태가 바뀌었는데 pending 표시가 없으면, 나중에 "얘가 끊긴 건"인지 확인할 단서가 사라진다. 그러면 다시 전수 조사로 돌아가야 한다.

그래서 이 셋을 Lua 스크립트로 묶는다. Redis는 Lua 스크립트를 단일 명령처럼 실행한다. 중간에 다른 스레드가 끼어들 수도, 부분만 실행되고 끝날 수도 없다. 전부 되거나 전부 안 되거나. 

local added = redis.call('SADD', KEYS[1], ARGV[1])
if added == 0 then return -1 end   -- 이미 발급됨

local stock = redis.call('DECR', KEYS[2])
if stock < 0 then
    redis.call('SREM', KEYS[1], ARGV[1])  -- 보상도 Lua 안에서
    redis.call('INCR', KEYS[2])
    return -2                              -- 재고 없음
end

redis.call('HSET', KEYS[3], ARGV[1], ARGV[2])
return 1                                   -- OK

여기서 꼭 지켜지는 건 한 가지다. "Redis 상태가 바뀌었으면 pending에도 반드시 기록되어 있다." 이 불변식이 깨지지 않으면, 보상이 실패해도 나중에 pending을 뒤져서 정리할 수 있다.

revert도 Lua로 묶는다

DB INSERT가 실패했을 때 되돌리는 로직도 세 연산이다. 

local removed = redis.call('SREM', KEYS[1], ARGV[1])
if removed == 1 then
    redis.call('INCR', KEYS[2])
end
redis.call('HDEL', KEYS[3], ARGV[1])
return 1

중간에 끊기지 않도록 Lua로 묶어놨다. commit은 HDEL 하나뿐이라 Lua까지 갈 필요는 없다.

Java 쪽은 이렇게 단순해진다

@Transactional
public CouponIssue issueCoupon(Long userId, Long couponId) {
    // Phase 1
    ReserveResult result = reservationStore.reserve(couponId, userId);
    switch (result) {
        case ALREADY_ISSUED -> throw new CouponException("Already issued");
        case OUT_OF_STOCK   -> throw new CouponException("Out of stock");
    }

    try {
        User user = userRepository.findById(userId).orElseThrow(...);
        user.usePoint(coupon.getPointCost());
        CouponIssue issue = couponIssueRepository.save(new CouponIssue(user, coupon));

        // Phase 2a
        reservationStore.commit(couponId, userId);
        return issue;
    } catch (Exception e) {
        // Phase 2b
        reservationStore.revert(couponId, userId);
        throw e;
    }
}

pending이 지켜주는 것

이제 크래시 시나리오를 다시 보자.

Case A. DB INSERT 전 크래시

  • Redis: 재고 차감 + 발급 기록 + pending에 표시
  • DB: 기록 없음
  • 나중에 스케줄러가 pending을 봄 → DB 확인 → 없음 → revert 실행

Case B. DB INSERT 성공, commit 전 크래시

  • Redis: 재고 차감 + 발급 기록 + pending에 표시 (아직 있음)
  • DB: 기록 있음
  • 나중에 스케줄러가 pending을 봄 → DB 확인 → 있음 → commit 실행 (pending만 제거)

둘 다 pending에 흔적이 남아있다는 공통점 덕분에 자동으로 정리된다. 유저가 쿠폰을 받았는지 못 받았는지 DB를 정답지로 놓고 판단하는 게 핵심이다.

정합성 맞추는 범위가 확 좁혀졌다.
원래는 발급 이력 전체(수십만 건)를 뒤져야 했는데, 이제 pending에 남은 몇 건만 확인하면 된다. 이게 pending Hash를 따로 두는 진짜 이유다.
