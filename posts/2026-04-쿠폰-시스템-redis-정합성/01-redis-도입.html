전편 끝자락에서

전 시리즈의 최종 결과는 300 중 259 성공이었다. SELECT FOR UPDATE SKIP LOCKED로 락 경합을 우회하면서 거의 다 긁어왔지만, 나머지 41건은 끝까지 커넥션 풀이 버텨내질 못했다.

DB 쪽에서 쥐어짤 수 있는 건 다 쥐어짰다는 감이 왔다. 커넥션을 더 늘리면 DB가 먼저 나가떨어지고, 쿼리를 더 줄일 자리도 없었다. 다음 스텝은 DB를 덜 때리는 것이었다.

Redis로 뭘 옮길 건가

쿠폰 발급에서 제일 비싼 두 작업은 이거다.

  • 중복 발급 체크 — 같은 유저가 같은 쿠폰을 두 번 못 받게 막기
  • 재고 차감 — 동시에 여러 요청이 들어와도 수량을 정확히 맞추기

둘 다 DB 락이나 쿼리로 처리하고 있었다. Redis에는 이걸 훨씬 싸게 할 수 있는 명령이 있다.

SADD — 중복 체크 겸 기록

SADD coupon:1:issued "5" 한 방에 "유저 5가 쿠폰 1을 받았다"를 기록한다. Set이라서 이미 있으면 아무 일도 안 일어나고 0을 돌려주고, 없으면 추가하고 1을 돌려준다.

즉 "있는지 확인하고 없으면 추가하는 두 작업"이 하나로 묶여있다. DB로 하면 SELECT ... WHERE 해보고 INSERT하는 두 번이 필요하고, 그 사이에 다른 트랜잭션이 끼어드는 걸 막으려면 락도 걸어야 한다. Redis는 그냥 한 번이면 된다.

DECR — 재고 차감

DECR coupon:1:stock은 카운터를 1 내리고 결과값을 돌려준다. 결과가 -1이면 재고가 없는 것. 이 한 줄이 "재고 조회 + 차감 + 결과 판단"을 한 번에 처리한다.

핵심은 "원자적"이라는 점. 두 작업을 하나로 묶어야 할 때, DB는 락으로 막는데 Redis는 명령 자체가 한 덩어리다. 쓸 수 있으면 훨씬 싸다.

바꿔본 코드

기존 DB 기반 로직에서 중복 체크와 재고 차감만 Redis로 빼냈다. 발급 이력 INSERT는 DB에 그대로 남긴다 (영속성 있는 기록이 필요하니까). 

@Transactional
public CouponIssue issueCoupon(Long userId, Long couponId) {
    // 1. 중복 체크 + 발급 기록 (Redis SADD)
    boolean firstIssue = issueRedisStore.tryRecordIssue(couponId, userId);
    if (!firstIssue) throw new CouponException("Already issued");

    // 2. 재고 차감 (Redis DECR)
    boolean stockDecremented = stockRedisStore.tryDecrement(couponId);
    if (!stockDecremented) throw new CouponException("Out of stock");

    // 3. 포인트 차감 + 발급 이력 INSERT (DB)
    User user = userRepository.findById(userId).orElseThrow(...);
    user.usePoint(coupon.getPointCost());
    return couponIssueRepository.save(new CouponIssue(user, coupon));
}

User 락도 빠졌고 existsBy 쿼리도 빠졌다. DB로 가는 쿼리는 findById + save 두 번뿐이다. 300 동시 요청을 돌렸더니 결과가 이렇게 나왔다.

총 시간: 5071ms / 성공: 300 / 실패: 0
목표였던 15초의 3분의 1만에 다 들어왔다. 전편이 끝내 못 넘었던 41건도 사라졌다.

얼핏 보면 끝난 문제다. 부하 테스트 통과했고, DB 부담도 확 줄었다. 이제 배포하고 맛있는 저녁 먹으러 가면 되는 거 아닌가?

그런데 뭔가 찜찜하다

서비스에서 의외로 흔한 상황이 하나 있다. 배포 중 서버 재시작. 쿠팡이든 토스든 배포는 매일 돈다. 무중단 배포를 쓰더라도 트래픽이 몰릴 땐 인스턴스 하나가 어느 순간 내려간다.

이런 그림이다. 

1. Redis SADD "5" → 성공 (Set에 추가됨)
2. Redis DECR     → 성공 (재고 1 줄어듦)
3. DB INSERT      → 💥 서버가 여기서 죽음

이런 일이 벌어졌을 때 상태를 보면:

  • Redis에는 "유저 5가 쿠폰 받음"이라는 흔적이 남아있다
  • Redis의 재고는 1 줄어든 상태다
  • DB에는 아무 기록이 없다

유저 5 입장에서 어떻게 되냐면.

유저 화면: 쿠폰 받기 요청했는데 응답도 못 받고 에러만 떴다.
DB: CouponIssue 테이블에 아무것도 없음. 정말 안 받은 것.
재시도: 다시 요청 → Redis에 "이미 발급"으로 남아있어서 Already issued 에러.

유저는 쿠폰 못 받았는데 평생 막힌다. Redis와 DB가 손발이 안 맞는 채로 남아있고, 둘을 맞춰줄 사람이 없다. 재고도 1 빠진 채로 방치된다.

보상 트랜잭션은 임시방편이었다

처음엔 이걸 간단히 해결할 수 있을 줄 알았다. catch 블록에서 Redis 상태를 되돌리면 된다고 생각했다. 

try {
    // Redis 작업들
    // DB INSERT
} catch (Exception e) {
    // 보상
    stockRedisStore.increment(couponId);      // 재고 원복
    issueRedisStore.revertIssue(couponId, userId);  // Set에서 제거
    throw e;
}

이게 돌면 깔끔하다. 문제는 보상 코드 자체가 실패할 수 있다는 것. DB INSERT가 실패한 이유가 "서버가 죽어서"라면, catch 블록도 실행 안 된다. 네트워크가 끊겨서 보상 명령 자체를 Redis로 못 보낼 수도 있다.

"보상이 실패하면 어떡하지?"를 막으려면 "보상의 보상"이 필요한데, 그 보상의 보상도 실패할 수 있고, 이런 식으로 끝이 없다. 보상 트랜잭션은 잘 굴러갈 때만 깔끔한 방법이었다.

이게 단발성 문제가 아니라는 걸 깨달았을 때

처음엔 "아 배포할 때 조심하면 되겠네" 정도로 넘겼는데, 상황을 더 생각해보니 비슷한 문제가 여러 갈래로 터진다.

  • 서버 크래시 — 방금 본 케이스
  • Redis가 통째로 다운되면? 모든 요청이 실패한다. 앱 전면 장애.
  • Redis가 재시작하면? AOF를 켜놓아도 fsync 정책에 따라 최근 몇 초분은 유실될 수 있고, 파일이 깨지거나 인스턴스가 교체되면 아예 빈 상태로 올라온다. 중복 발급 + 재고 초과가 각각 터진다.
  • DB가 일시적으로 끊겼다가 복구되면? Redis 보상 로직 타이밍에 따라 상태가 제각각이 된다.
  • 이 모든 상황이 쌓이고 쌓이면 어느 순간 Redis 상태 ≠ DB 상태가 일상이 된다.

Redis를 도입해서 속도는 얻었는데, 정합성이라는 이름의 새 숙제가 생긴 것이다. DB 혼자였을 땐 트랜잭션이 지켜주던 걸, 이제 우리가 직접 관리해야 한다.

DB만 있을 땐 트랜잭션이 공짜였다. Redis가 껴들어오니 공짜가 아니다.
두 시스템 사이의 정합성은 우리가 설계해서 지켜줘야 한다. 이게 분산 시스템의 시작이다.
