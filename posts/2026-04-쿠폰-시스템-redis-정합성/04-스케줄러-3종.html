하나로 퉁치지 않는 이유

가장 나이브한 설계는 스케줄러 하나 만들어서 "주기적으로 전부 검사" 돌리는 거다. 근데 "전부 검사"는 비용이 크고, 트래픽이 도는 시간대엔 위험하다. 반대로 가벼운 것만 하면 놓치는 케이스가 생긴다.

그래서 다른 주기, 다른 비용, 다른 커버 범위의 스케줄러 세 개를 겹쳐놓는 게 맞다는 결론이 났다.

1) syncFromDb — DB를 기준으로 Redis 채우기

@Scheduled(fixedDelay = 60_000)
@Transactional(readOnly = true)
public void syncFromDb() {
    for (Coupon coupon : couponRepository.findAll()) {
        Long couponId = coupon.getId();
        List<Long> userIds = couponIssueRepository.findUserIdsByCouponId(couponId);
        userIds.forEach(userId -> issueRedisStore.tryRecordIssue(couponId, userId));
    }
}

역할: DB CouponIssue 전체를 읽어서 Redis Set에 SADD로 밀어넣는다.
주기: 60초.
비용: 매번 전체 조회라 DB 쪽 부담이 좀 있다. 대신 로직은 단순.

이 스케줄러가 해결하는 건 Redis 쪽이 비거나 일부 유실됐을 때다. AOF가 깨지거나 인스턴스가 교체돼서 Set이 비었다면, SADD는 멱등이라 다시 채워주면 그만이다. 이미 있으면 0 반환하고 넘어가니까 중복 걱정도 없다.

주의: 재고 카운터를 절대값으로 덮어씌우는 initStock은 여기 넣으면 안 된다. 운영 중에 DECR과 SET이 경쟁하면 재고가 엉뚱하게 틀어진다. 재고 복구는 재시작 직후 트래픽 받기 전에만 한다.

2) cleanupPending — 미확정 건 떨이

@Scheduled(fixedDelay = 30_000)
public void cleanupPending() {
    long now = System.currentTimeMillis();
    for (Coupon coupon : couponRepository.findAll()) {
        Map<Object, Object> pending = reservationStore.findAllPending(coupon.getId());
        for (var entry : pending.entrySet()) {
            Long userId = Long.parseLong(entry.getKey().toString());
            long timestamp = Long.parseLong(entry.getValue().toString());
            if (now - timestamp < 30_000) continue;  // 아직 처리 중일 수 있음

            if (couponIssueRepository.existsByUserIdAndCouponId(userId, coupon.getId())) {
                reservationStore.commit(coupon.getId(), userId);    // 지연 commit
            } else {
                reservationStore.revert(coupon.getId(), userId);    // 보상 못 한 것 revert
            }
        }
    }
}

역할: pending Hash에 30초 이상 남아있는 항목을 DB와 대조해서 정리.
주기: 30초.
비용: pending 자체가 작기 때문에 거의 공짜.

정상적일 땐 pending은 수십 ms 안에 들어왔다 나간다. 30초 이상 남아있다는 건 확실히 뭔가 끊긴 것이다. 이 스케줄러가 실제 일을 하는 경우는 드물고, 대부분은 빈 Hash만 보고 넘어간다. 장애 때만 바빠지는 구조다.

이 스케줄러 덕분에 1편에서 말한 "보상의 보상" 문제가 풀린다. 보상이 실패해도 pending에 남아있고, 30초 후 스케줄러가 와서 치워준다.

3) reverseSweep — SSCAN 전수 조사

public void reverseSweep() {
    for (Coupon coupon : couponRepository.findAll()) {
        List<Long> issuedInRedis = reservationStore.scanIssuedUserIds(coupon.getId(), 100);
        for (Long userId : issuedInRedis) {
            if (!couponIssueRepository.existsByUserIdAndCouponId(userId, coupon.getId())) {
                reservationStore.revert(coupon.getId(), userId);
            }
        }
    }
}

역할: Redis Set을 SSCAN으로 전부 순회하면서 DB에 없는 건 revert.
주기: 자동 실행 안 함. 운영자가 수동으로 실행.
비용: 발급 이력 전체를 훑는다. 트래픽 적은 시간에 돌려야 안전.

솔직히 이 스케줄러는 실무에선 거의 안 탄다. 위의 cleanupPending이 pending 흔적만 있으면 전부 정리해주기 때문이다. 이게 필요해지는 건 그 pending Hash마저 유실된 희귀 상황이다. Redis 인스턴스가 통째로 교체됐는데 AOF 스냅샷이 깨졌거나, 특정 키만 골라서 날아갔거나.

이런 건 보통 1년에 한 번 있을까 말까다. 자동 스케줄로 매시간 SSCAN 전수 조사 + DB 대조를 돌리면 얻는 거의 없고 비용만 꾸준히 나간다. 평소 안 타는 코드라 버그가 숨어있기도 쉽다.

"이상 징후가 감지됐을 때 운영자가 누르는 버튼"으로 두는 게 맞다.
어드민 엔드포인트로 빼놓고, 평소엔 잠자고 있다가 필요할 때만 깨운다. 
// @Scheduled 떼고 수동 호출 전용
@PostMapping("/admin/reconciliation/sweep")
public void triggerReverseSweep() {
    reconciliationScheduler.reverseSweep();
}

세 스케줄러의 포지션

이름 주기 커버 비용
syncFromDb 60초 Redis 유실 (Set) DB 전체 조회 (중)
cleanupPending 30초 보상 실패 / 미확정 pending만 (작음)
reverseSweep 수동 pending마저 유실 SSCAN 전수 (큼)

자주 터지는 문제는 싸고 빠르게 잡고, 드문 문제는 비싸더라도 확실히 잡는다. 각자 커버 범위가 다르기 때문에 셋을 겹쳐놓는 게 하나 크게 만드는 것보다 낫다.

재고 총합을 맞춰주는 스케줄러는 왜 없나

글 순서대로 보면 자연스럽게 떠오르는 질문이다. "DB totalQuantity - COUNT로 Redis 재고를 주기적으로 덮어씌워주면 되지 않나?" 처음엔 나도 그렇게 하려고 했다. 근데 운영 중에 재고 값을 절대값으로 덮어씌우는 건 위험하다. 

배치: DB COUNT → 50 → Redis SET "stock" 50
동시에 발급 요청: DECR → stock 49
배치가 계산하던 순간의 값으로 덮어씌우면 → stock 50 (방금 나간 발급 건이 증발)

DECR이랑 SET이 경쟁하면 재고가 오히려 틀어진다. 그래서 전용 스케줄러 대신 이벤트별로 그 자리에서 INCR 해주는 방식을 택했다.

상황 누가 INCR
Phase 1에서 재고 부족 Lua 스크립트 안에서 (reserve 실패 시)
Phase 2b revert Lua 스크립트 안에서
cleanupPending revert Lua 스크립트 호출
reverseSweep revert Lua 스크립트 호출

"재고가 감소했는데 취소된 경우"마다 그 자리에서 INCR로 원복한다. 총합을 맞추는 배치 없이도 자연히 수렴한다.

재고 값 자체가 유실된 경우(AOF 전체 유실 등)는 재시작 직후 트래픽 받기 전에 initStock으로 한 번 덮어씌우는 startup reconciliation으로 처리한다. 그땐 경쟁하는 요청이 없어서 안전하다.

한 가지 한계

이 스케줄러들은 전부 DB를 정답지로 두고 Redis를 맞추는 방향이다. 그래서 5편에서 볼 "Redis 자체가 죽었을 때"는 해결해주지 않는다. 그건 별도의 방어가 필요하다.

다음 편

5편에서는 Redis가 통째로 안 뜨는 상황을 다룬다. 처음엔 DB 폴백으로 버텨보려고 했는데, 파고들다 보니 오히려 깔끔하게 실패시키는 게 낫다는 결론에 도달했다. 왜 그랬는지, 완벽한 자동 복구라는 목표 자체가 왜 환상인지 정리하면서 시리즈를 마무리한다.
