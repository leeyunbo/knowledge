왜 분류부터 하는가

"Redis와 DB가 틀어질 수 있다"는 한 문장으로 두면 아무 대응도 못 한다. 비슷해 보이는 사고가 실은 서로 다른 원인에서 나오고, 각자 약한 포인트가 다르기 때문이다.

그래서 가능한 장애 상황을 네 갈래로 쪼개봤다. 원인이 다르면 해결도 달라진다는 걸 우선 눈으로 보자는 의도다.

네 가지 시나리오

1. 서버 크래시

우리 앱 프로세스가 죽는 경우. 배포할 때마다 생기는 상황이라 제일 흔하다. 

Redis SADD 성공 → Redis DECR 성공 → DB INSERT 중 서버 다운
  • Redis에는 "유저 5 발급함" + 재고 1 차감된 상태
  • DB에는 아무것도 없음
  • 유저 5는 쿠폰 못 받았는데 재요청 시 Already issued 에러

2. Redis 다운

Redis 프로세스 자체가 죽거나 메모리 초과로 연결이 안 되는 상황.

  • 발급 요청이 전부 Redis 연결 에러로 실패 → 앱 전면 장애
  • 재기동 후에도 AOF 유실 정도에 따라 재고/이력이 일부 또는 전체 날아감
  • 복구 안 하면 중복 발급, 재고 초과가 동시에 터진다

3. DB 다운

H2 / MySQL 접속이 일시적으로 끊기는 상황.

  • Redis 작업은 성공하는데 DB INSERT 실패
  • catch에서 Redis 보상 롤백 → 잘 굴러가면 여기서 끝
  • 문제는 보상 로직도 실패하는 경우. 그러면 서버 크래시랑 같은 상태로 남음

4. Redis-DB 정합성 틀어짐

위 1, 2, 3이 누적되면서 일상이 되는 상태. 단일 사건이 아니라 시간에 따라 쌓이는 문제다.

  • Redis Set엔 있는데 DB CouponIssue엔 없는 유저
  • DB엔 있는데 Redis Set엔 없는 유저 (역방향)
  • Redis 재고 카운터 ≠ DB 실제 발급 건수

빈도 × 심각도 × 난이도 매트릭스

네 개를 나란히 놓고 보면 우선순위가 보인다.

장애 빈도 심각도 난이도
1. 서버 크래시 높음 (배포마다) 중 중
2. Redis 다운 낮음 높음 (전면 장애) 높음
3. DB 다운 낮음 중 (보상 있음) 낮음
4. 정합성 틀어짐 중 (누적) 높음 중

1번과 4번이 사실 세트다

네 개를 따로 세워놓고 보면 각자 잡아야 할 것 같지만, 조금 들여다보면 1번과 4번은 원인과 결과다.

  • 서버 크래시(1)가 일어나면 Redis와 DB가 어긋남 → 누적되면 4번이 된다
  • 4번(정합성 맞추기)은 결국 1번 때문에 생긴 일들을 치우는 작업이다

그러니까 1번과 4번은 같은 설계로 같이 잡아야 한다. 1번을 막는 메커니즘과, 못 막은 것들을 사후에 정리하는 메커니즘이 한 쌍이다.

우선순위

순서를 정하면 이렇다.

  1. 1번 + 4번 — 빈도가 높고, 둘을 분리하면 엉망이 된다. 여기가 메인 이벤트.
  2. 3번 — 이미 보상 로직이 있고, 문제는 "보상의 실패"인데 이건 1번 대응과 겹친다. 같이 해결됨.
  3. 2번 — 터지면 큰일이지만 자주 안 나고, 난이도가 제일 높다. 마지막.
설계는 결국 이 두 축이다.
(A) 크래시가 나도 상태를 추적 가능한 구조로 만들기
(B) 이미 틀어진 것들을 주기적으로 맞춰주는 장치 추가

뒤에서 다룰 것

3편에서는 1번 + 4번을 한꺼번에 풀어주는 패턴을 본다. 핵심은 "발급 시작 → 진행 중 → 확정"이라는 3단 상태를 Redis 안에 직접 박아놓는 것. 이 설계 덕분에 크래시로 멈춘 건을 나중에 "얘는 어디까지 갔었지?"로 확인할 수 있다.

4편에선 주기적으로 돌면서 정리하는 세 종류의 스케줄러를 보고, 5편에선 Redis 자체가 죽었을 때 전면 장애를 막는 법을 다룬다.
