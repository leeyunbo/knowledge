죽는 순간이 가장 위험해요

서비스가 정상 동작할 때보다 종료될 때가 더 까다로워요. 배포·스케일 인·재시작이 매일 일어나는데, 그때마다 처리 중인 요청이 끊기면 사용자 입장에선 "주문 누르니까 에러"가 돼요. CI/CD 파이프라인이 빈번할수록 graceful shutdown 없는 서비스는 거의 항상 에러를 만들어요.

Graceful shutdown은 "곧 죽으니, 새 요청은 받지 말고 처리 중인 건 마무리하자"는 약속이에요. 정해진 시간 안에 in-flight 요청을 끝내고 깨끗이 종료해요.

OS 시그널과 JVM

리눅스가 프로세스에 종료를 요청하는 표준 방법은 시그널이에요. 종료 방식이 두 가지로 갈려요.

시그널의미JVM 동작
SIGTERM (15)정상 종료 요청shutdown hook 실행 후 종료
SIGKILL (9)강제 종료훅 없이 즉시 종료. 막을 수 없음
SIGINT (2)Ctrl+CSIGTERM과 비슷

Graceful shutdown이 가능한 건 SIGTERM뿐이에요. SIGKILL이 오면 프로세스는 바로 죽고, in-flight 요청은 그대로 끊겨요. 그래서 SIGTERM을 받았을 때 정해진 시간 안에 끝내는 게 핵심이에요.

K8s Pod 종료의 흐름

Kubernetes는 rolling update·scale down 시 Pod에 종료 신호를 보내요. 표준 흐름은 이래요.

  1. kubelet이 Pod에 SIGTERM을 보내요.
  2. 동시에 Pod를 Endpoints에서 제거해요. 새 트래픽이 안 와요.
  3. terminationGracePeriodSeconds(기본 30초)까지 기다려요.
  4. 그 시간이 지나도 살아 있으면 SIGKILL을 보내요.

여기가 핵심이에요. 우리가 처리할 시간은 보통 30초예요. 이 안에 끝나야 강제 종료를 피할 수 있어요.

피해야 할 사고 시나리오

1. 새 요청을 계속 받음

SIGTERM 받은 후에도 LB가 트래픽을 계속 보내요. K8s는 Endpoints 제거를 비동기로 처리해서 시간이 좀 걸려요. 그 사이 새 요청을 받으면 곧 죽을 우리 프로세스가 처리하다 끊겨요.

해결: K8s에는 preStop hook이 있어요. SIGTERM 직전에 잠깐 sleep을 두면 Endpoints 전파가 끝난 후 SIGTERM이 와요. 보통 5~10초 sleep을 둬요.

2. 처리 중인 요청을 끊음

SIGTERM 받자마자 서버 소켓을 닫으면 in-flight 요청이 끊겨요. 사용자가 받는 건 connection reset이에요. 결제·주문 같은 자리에서 발생하면 매우 위험해요.

해결: 새 요청은 거부(또는 다른 인스턴스로 라우팅 되게)하고, 진행 중인 요청은 완료까지 기다려요. Spring Boot의 shutdown: graceful이 이걸 자동으로 해 줘요.

3. 자원이 정리되지 않음

DB 커넥션 풀, 메시지 큐 컨슈머, 외부 API 호출 같은 자원이 정리되지 않으면 다음 인스턴스가 영향을 받아요. 분산 락이 안 풀려 있다면 잠시 후 다른 인스턴스가 그 락 때문에 멈춰요.

4. 메시지 컨슈머가 메시지를 잃음

Kafka 컨슈머가 메시지를 처리 중에 죽으면, 어디까지 처리됐는지에 따라 메시지가 유실되거나 중복돼요. graceful shutdown에서 컨슈머가 현재 메시지를 끝까지 처리하고 offset commit한 뒤 종료하도록 해야 해요.

Graceful Shutdown의 표준 순서

요약하면 다음 순서를 지켜야 해요.

  1. 새 요청 거부 준비: 헬스체크 readiness를 false로. LB가 트래픽을 안 보내게 해요.
  2. Endpoints 전파 대기: preStop sleep 또는 명시적 대기.
  3. 새 요청 차단: 서버 소켓의 accept를 멈춰요. 진행 중인 요청은 그대로 처리.
  4. In-flight 요청 완료 대기: 정해진 시간(보통 20~25초) 안에.
  5. 외부 자원 정리: DB 풀, Kafka 컨슈머, Redis 커넥션 닫기.
  6. JVM 정상 종료: shutdown hook 완료 후 exit.

이 순서를 어기면 어떤 자리가 새는지 다음 편에서 자세히 봐요.

Readiness Probe의 활용

K8s에는 두 가지 probe가 있어요. Liveness와 Readiness예요. Load Balancer 시리즈 2편에서 본 그 자리예요.

  • Liveness: 프로세스 살아 있나? 죽었으면 재시작.
  • Readiness: 트래픽 받을 준비 됐나? 아니면 Endpoints에서 제외.

Graceful shutdown에서 readiness를 false로 만들면 K8s가 LB에서 그 Pod를 빼요. SIGTERM이 오기 전에 미리 false를 만드는 패턴(예: /actuator/health/readiness의 fall-back)도 안전해요.

왜 한 번에 안 끝나는가

Graceful shutdown이 자주 실패하는 이유는 위 순서의 어느 한 자리가 빠져서예요. 예를 들어 이런 경우가 있어요.

  • JVM은 종료되는데 K8s Endpoints 전파가 늦어 LB가 잠시 죽은 인스턴스로 보내는 경우가 있어요.
  • Spring Boot의 graceful shutdown은 켜져 있는데 Kafka 컨슈머는 그대로 죽기도 해요.
  • DB 커넥션을 닫기 전에 in-flight 트랜잭션을 끝내지 못해서 데이터 불일치가 생겨요.

Graceful shutdown은 한 줄 설정이 아니라 전체 흐름 설계예요. 한 자리만 잘못돼도 효과가 없어져요.

면접에서 자주 나오는 자리

  • "Graceful shutdown이 왜 필요?": 배포·스케일 인 같은 정상 종료 시 in-flight 요청을 안전히 끝내고 새 요청은 차단하기 위해서예요. 안 하면 사용자가 connection reset 에러를 봐요.
  • "SIGTERM과 SIGKILL 차이?": SIGTERM은 정상 종료 요청이라 shutdown hook을 실행할 수 있어요. SIGKILL은 즉시 종료라 막을 수 없어요. K8s는 SIGTERM 후 30초 안에 끝나지 않으면 SIGKILL을 보내요.
  • "K8s에서 graceful shutdown 순서?": SIGTERM + Endpoints 제거가 동시에 일어나요. preStop hook의 sleep으로 Endpoints 전파를 기다린 뒤 SIGTERM이 오게 하는 게 안전해요.
  • "readiness probe의 역할?": 트래픽 받을 준비를 알려요. false로 만들면 LB가 즉시 트래픽을 다른 Pod로 보내요. Graceful shutdown 시작 신호로 활용해요.
