Richardson Maturity Model이 뭔가

Leonard Richardson이 제안한 REST 성숙도 모델이에요. 어떤 API가 REST의 원칙을 얼마나 많이 따르는지를 0~3단계로 분류해요. 0은 거의 안 따름, 3은 다 따름.

Level이름특징
0The Swamp of POX모든 요청을 POST 하나로. URL 하나.
1Resources자원마다 별도 URL
2HTTP Verbs+ GET/POST/PUT/DELETE 메서드 사용
3Hypermedia Controls+ HATEOAS (응답에 다음 액션 링크)

실무 API는 거의 다 Level 2에 머물러요. Level 3까지 가는 경우는 드물어요.

Level 0, 늪

HTTP를 전송 수단으로만 쓰고, 그 위에 자체 RPC 스타일 프로토콜을 얹어요. SOAP이 대표적이에요. 모든 요청이 POST로 가고, URL은 하나(/api), 요청 본문에 "어떤 메서드를 부를지"를 담아요. 

// Level 0 예시
POST /api
Content-Type: application/xml

<getOrder>
  <orderId>42</orderId>
</getOrder>

HTTP의 캐싱, 메서드 의미, 상태코드 같은 걸 거의 안 써요. HTTP를 그냥 "터널"로 쓴 셈이에요. JSON-RPC도 이 부류예요.

Level 1, 자원의 등장

자원마다 별도 URL을 부여해요. 하지만 메서드는 여전히 거의 POST. 

POST /orders/42/get
POST /orders/42/cancel
POST /users/100/getProfile

URL은 자원 중심으로 됐지만 동사가 URL에 박혀 있어요. HTTP 메서드의 의미를 안 써요. 캐시도 잘 못 활용해요(POST는 기본 캐시 안 됨).

Level 2, HTTP 메서드 활용

실무 API의 대부분이 여기에 있어요. URL은 자원, 메서드는 HTTP 표준 동사. 

GET    /orders/42         // 조회
PUT    /orders/42         // 전체 갱신
PATCH  /orders/42         // 부분 갱신
DELETE /orders/42         // 삭제
POST   /orders            // 생성

각 메서드는 정해진 의미를 가져요. GET은 안전(side-effect 없음), PUT·DELETE는 멱등(여러 번 호출해도 결과 같음), POST는 비멱등(매번 새 자원 생성). 상태코드도 표준 의미대로 써요(200, 201, 204, 404, 409, 500 등).

이 단계에서 HTTP의 캐싱, 안전성, 멱등성을 다 누릴 수 있어요. 실무에서 거의 모든 "REST API"가 이 단계예요. 그래서 사람들이 "Level 2 = REST"라고 부르기도 해요. 사실 Fielding 입장에서는 아직 진짜 REST가 아니지만요.

Level 3, HATEOAS

응답에 다음 액션의 링크가 포함돼야 진짜 REST예요. 클라이언트는 URI 패턴을 외우지 않고, 시작점 URL만 알고 거기서 받은 링크를 따라가요. 

GET /orders/42
{
  "id": 42,
  "status": "pending",
  "amount": 50000,
  "_links": {
    "self": { "href": "/orders/42" },
    "cancel": { "href": "/orders/42/cancel", "method": "POST" },
    "pay": { "href": "/orders/42/pay", "method": "POST" },
    "customer": { "href": "/users/100" }
  }
}

주문 상태가 pending일 때 cancel과 pay 링크가 보여요. 상태가 paid로 바뀌면 응답에 cancel 링크가 사라지고 refund 링크가 생기는 식이에요. 가능한 액션이 자원 상태에 따라 응답에서 동적으로 드러나요.

왜 Level 3까지 잘 안 가나

HATEOAS는 이론적으로 매력적이에요. 클라이언트가 URL 구조를 안 외워도 되고, 서버가 URL 구조를 자유롭게 바꿔도 클라이언트가 안 깨져요. 그런데 실무에서는 거의 안 써요.

  • 클라이언트 구현 부담: 응답을 받아서 링크를 파싱하고 그걸 따라가는 클라이언트 라이브러리가 필요해요. JSON 응답에서 키를 꺼내 쓰는 것보다 복잡.
  • 모바일 앱 현실: 모바일 앱은 한 번 빌드하면 한참 사용자 폰에 남아요. 서버가 URL을 바꿔도 옛 앱은 옛 URL로 가요. HATEOAS 이론대로면 서버 변경에 강해야 하는데, 실제로는 클라이언트가 URL을 캐시하거나 가정해요.
  • 응답 크기 증가: 매 응답마다 링크가 잔뜩 붙어 무거워져요.
  • 비즈니스 가치가 명확하지 않음: 노력 대비 얻는 게 명확하지 않아요. URL 패턴을 한 번 정하면 거의 안 바꾸는 게 현실이에요.

그래서 "REST는 사실 거의 아무도 안 한다"는 농담이 나와요. 표면적으로 Level 2고, Level 3 HATEOAS까지 가는 API는 극소수예요.

HAL과 JSON:API, HATEOAS의 표준

HATEOAS를 구현하려는 사람들을 위한 표준 포맷이 몇 가지 있어요.

  • HAL (Hypertext Application Language): _links와 _embedded 키로 링크와 임베디드 자원을 표현해요.
  • JSON:API: 더 엄격한 스펙이에요. data·attributes·relationships·links로 구조가 정해져 있어요.
  • Siren: 액션과 링크를 더 풍부하게 표현해요.

Spring HATEOAS 같은 라이브러리가 HAL 형식 생성을 도와줘요. 실무 적용 비용이 약간 더 들지만 일관성은 좋아져요.

실용적 결론

"진짜 REST"를 추구하는 게 늘 옳은 건 아니에요. 다음 자리에 따라 단계를 골라야 해요.

  • 일반 웹 API: Level 2면 충분해요. 표준 HTTP를 잘 따르고, 상태코드와 메서드 의미를 정확히 쓰면 그걸로 돼요.
  • 퍼블릭 API에 진화 여유 필요: Level 3을 검토해 봐요. URL 구조를 자유롭게 바꿀 수 있어요.
  • 고성능·내부 통신: REST 자체를 안 써도 돼요. gRPC, GraphQL을 검토해 봐요.

Fielding이 정의한 REST는 매우 깊은 아키텍처지만, 실무에서 그 전부를 다 따라가는 건 비용이 커요. 자기 상황에 맞는 단계를 의식적으로 고르는 게 더 중요해요.

다음 편

마지막 편에서는 REST의 비판과 대안을 봐요. JSON-RPC, gRPC, GraphQL이 REST의 어떤 한계를 풀려고 등장했는지, 그리고 어디에 어느 것이 맞는지를 정리해요.
