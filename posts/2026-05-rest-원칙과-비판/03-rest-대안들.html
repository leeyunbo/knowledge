REST가 못 푸는 자리들

REST는 잘 만든 스타일이지만 모든 자리에 맞지는 않아요. 실무에서 자주 부딪치는 한계가 몇 가지 있어요.

  • 여러 자원을 한 번에 가져오기: 화면 하나에 필요한 데이터가 5개 자원에 흩어져 있으면 5번 GET이 필요해요. 모바일 환경에서 RTT 5번은 비싸요. 이걸 "N+1 API 호출 문제"라고도 해요.
  • 오버패칭 / 언더패칭: GET /users/42가 50개 필드를 주는데 우리는 3개만 필요. 또는 3개만 주는데 우리가 더 필요. 둘 다 비효율.
  • RPC 스타일 동작: "주문 취소", "재시도", "재고 차감" 같은 동사적 동작이 REST 자원 모델에 잘 안 맞아요. POST /orders/42/cancel이 자원 중심이라기보다 동작 중심이에요.
  • 스트리밍·양방향: HTTP 요청-응답은 단방향이에요. 실시간 양방향 통신엔 안 맞아요.
  • 스키마 강제: REST에는 표준 스키마 형식이 없어요. OpenAPI를 따로 써야 하고, 타입 안전성이 약해요.

JSON-RPC, 가장 단순한 RPC

JSON-RPC는 REST 이전부터 있던 단순한 RPC 프로토콜이에요. 한 URL에 POST로 메서드 이름과 파라미터를 보내고 결과를 받아요. 

POST /api
{
  "jsonrpc": "2.0",
  "method": "cancelOrder",
  "params": { "orderId": 42 },
  "id": 1
}

Richardson Level 0의 모양이에요. URL 하나에 POST만 쓰는 동사 중심 구조예요. REST 관점에서는 안티패턴이지만 단순한 자리에서는 명료해요.

사용 자리는 거의 동작 중심 API예요. 블록체인 클라이언트, 게임 서버 백엔드, 일부 내부 도구에서 보여요.

gRPC, 강타입 RPC + 효율

Google이 만든 RPC 프레임워크예요. Protocol Buffers 스키마로 메시지를 정의하고, HTTP/2 위에서 효율적으로 전송해요. 

// .proto 파일
service OrderService {
  rpc GetOrder(GetOrderRequest) returns (Order);
  rpc CancelOrder(CancelOrderRequest) returns (CancelOrderResponse);
}

message GetOrderRequest {
  int64 order_id = 1;
}

message Order {
  int64 id = 1;
  string status = 2;
  int64 amount = 3;
}

스키마에서 클라이언트·서버 코드가 자동 생성돼요. 타입 안전, 컴파일 타임 검증, 빠른 직렬화(Protobuf 이진), HTTP/2의 스트리밍과 멀티플렉싱까지 다 얻을 수 있어요. 마이크로서비스 사이 내부 통신에 강점이에요.

gRPC의 장점

  • 성능: 이진 직렬화로 JSON보다 빠르고 작아요.
  • 타입 안전: .proto가 contract이고 양쪽이 같은 코드를 자동 생성해요.
  • 스트리밍: 클라이언트→서버, 서버→클라이언트, 양방향까지 4가지 모드를 지원해요.
  • 다국어 지원: Protobuf 컴파일러가 거의 모든 언어로 코드를 생성해요.

gRPC의 한계

  • 브라우저 직접 호출 불편: gRPC-Web이 있지만 프록시가 필요해요. 일반 웹 프론트엔드와 직접 통신은 거추장스러워요.
  • 디버깅 어려움: 이진 형식이라 tcpdump·curl로 못 봐요. 별도 도구가 필요해요.
  • 스키마 진화 신중: 필드 번호를 재사용하면 안 돼요. 호환성 규칙을 따로 익혀야 해요.

어디에 쓰나

서비스 메시 내부, 마이크로서비스 사이 통신에 거의 표준이에요. Netflix, Google, Uber 같은 대형 서비스의 내부 백엔드 통신은 gRPC를 써요. 외부 공개 API에는 잘 안 써요(브라우저 호환성 문제).

GraphQL, 클라이언트가 필요한 만큼만

Facebook이 만든 쿼리 언어예요. 클라이언트가 원하는 필드를 명시해서 요청하고, 서버는 정확히 그것만 줘요. 오버패칭과 N+1 API 호출 문제를 한 번에 풀어요. 

// 한 번 요청에 여러 자원 가져오기
POST /graphql
{
  user(id: 42) {
    name
    email
    orders(last: 5) {
      id
      amount
      product {
        name
      }
    }
  }
}

// 응답
{
  "data": {
    "user": {
      "name": "Alice",
      "email": "a@example.com",
      "orders": [
        { "id": 100, "amount": 50000, "product": { "name": "키보드" } },
        ...
      ]
    }
  }
}

GraphQL의 장점

  • 정확히 필요한 데이터만: 오버패칭·언더패칭을 둘 다 풀어요.
  • 한 요청에 여러 자원: 모바일·SPA에서 RTT를 아껴요.
  • 강타입 스키마: 자동 문서화와 타입 안전을 같이 얻어요.
  • 버저닝 회피: 필드 추가는 클라이언트에 영향이 없어요. deprecated 표시로 점진적으로 제거해요.

GraphQL의 한계

  • 캐싱이 어려움: 모든 요청이 POST이고 쿼리 본문이 매번 다르니 HTTP 캐시를 못 써요. 클라이언트·CDN 캐싱은 별도 라이브러리(Apollo)로.
  • N+1 쿼리 문제: 쿼리 한 번에 여러 자원을 가져오는 건 좋은데, 서버 구현에서 각 자원마다 DB 쿼리가 따로 나면 N+1이 생겨요. DataLoader 같은 배치 라이브러리로 풀어요.
  • 복잡한 쿼리의 DOS 위험: 클라이언트가 깊은 중첩 쿼리를 보내면 서버가 죽을 수 있어요. depth 제한·복잡도 제한 필요.
  • 러닝 커브: REST보다 학습 비용이 높아요. 스키마 설계, resolver, N+1 회피까지 익힐 게 많아요.

어디에 쓰나

복잡한 데이터를 다양한 모양으로 조회해야 하는 자리에 강해요. SPA, 모바일 앱이 백엔드와 통신하는 자리. GitHub API, Shopify, Airbnb가 GraphQL을 외부 공개로 운영해요.

실무 선택 기준

  • 외부 공개 API, 표준 웹 클라이언트: REST. 학습 곡선 낮고 도구가 많아요.
  • 마이크로서비스 내부 통신: gRPC. 성능과 타입 안전.
  • SPA·모바일 클라이언트, 복잡한 데이터 모델: GraphQL. 오버패칭 회피.
  • 특정 동작 중심 API: REST의 동작 자원으로 먼저 시도해 봐요. 안 맞으면 JSON-RPC로 가요.

여러 개를 같이 쓰는 것도 흔해요. 외부 공개는 REST/GraphQL, 내부 서비스 통신은 gRPC. 한 회사 안에 둘 다 있는 게 자연스러워요.

면접에서 자주 나오는 자리

  • "REST가 뭔가요? 진짜로?": 6가지 제약. Stateless, Uniform Interface, HATEOAS 등.
  • "Level 3 HATEOAS를 안 쓰는 이유?": 클라이언트 구현 부담이 크고, 모바일 호환성이 떨어지고, 비즈니스 가치가 명확하지 않아요.
  • "gRPC와 REST 차이?": 직렬화가 JSON 대 Protobuf, 전송이 HTTP/2, 스키마가 강제, 스트리밍을 지원한다는 점이 달라요.
  • "GraphQL의 N+1은?": 쿼리 한 번에 여러 자원을 받는데 서버가 각 자원마다 DB 쿼리를 날리면 N+1이 생겨요. DataLoader로 배치해서 풀어요.
  • "REST에 PATCH와 PUT 차이?": PUT은 자원 전체 교체(멱등), PATCH는 부분 갱신.

시리즈 마무리

1편에서는 Fielding이 정의한 REST의 6가지 제약을 봤어요. 2편에서는 Richardson Maturity Model로 실무 API의 위치(Level 2)와 Level 3 HATEOAS가 잘 안 가는 이유를 봤어요. 3편에서는 REST의 한계와 대안 셋(JSON-RPC, gRPC, GraphQL), 그리고 실무 선택 기준을 정리했어요.

"RESTful API"라는 표현을 들으면, 그게 진짜 REST의 6가지 제약을 다 만족하는지는 따져볼 가치가 있어요. 거의 다 Level 2고 그게 자연스럽다는 사실을 알면, 다른 도구를 고려할 때도 편견 없이 보게 돼요.
