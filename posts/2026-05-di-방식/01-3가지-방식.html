의존성 주입의 의미

한 클래스가 다른 클래스를 사용해야 할 때, 그 의존을 누가 만들어 주느냐의 문제. 전통적으로는 본인이 직접 new로 만들었지만 그러면 결합도가 높아 테스트와 교체가 어려워진다. Spring은 이 책임을 컨테이너가 떠안고 빈을 만들어 주입한다 — Inversion of Control.

그 주입의 통로가 어디인지에 따라 세 방식으로 나뉜다. 생성자, 세터, 필드. 기능적으로는 모두 같은 결과를 만들지만 코드의 형태와 안전성이 달라진다.

1. 생성자 주입 (Constructor Injection)

@Service
public class OrderService {

    private final UserRepository userRepository;
    private final PaymentClient paymentClient;

    public OrderService(UserRepository userRepository, PaymentClient paymentClient) {
        this.userRepository = userRepository;
        this.paymentClient = paymentClient;
    }
}

가장 권장되는 방식. 의존성을 생성자 매개변수로 받고 final 필드에 저장한다. Spring 4.3 이후로 생성자가 하나뿐이면 @Autowired는 생략 가능. Lombok의 @RequiredArgsConstructor를 쓰면 final 필드용 생성자가 자동 생성된다. 

@Service
@RequiredArgsConstructor
public class OrderService {
    private final UserRepository userRepository;
    private final PaymentClient paymentClient;
}

동작 흐름

Spring이 빈을 만들 때 의존성 그래프를 분석해 필요한 빈을 먼저 준비한 뒤 생성자에 넘긴다. OrderService를 만들기 위해 UserRepository와 PaymentClient가 필요하다는 걸 컨테이너가 인식하고, 둘을 먼저 생성/준비한 후 OrderService 생성자를 호출한다.

생성자가 끝나는 시점에 모든 final 필드가 채워져 있다 — 객체가 처음부터 완전한 상태. 이 특성이 다음 편에서 다룰 여러 장점의 근거가 된다.

2. 세터 주입 (Setter Injection)

@Service
public class OrderService {

    private UserRepository userRepository;
    private PaymentClient paymentClient;

    @Autowired
    public void setUserRepository(UserRepository userRepository) {
        this.userRepository = userRepository;
    }

    @Autowired
    public void setPaymentClient(PaymentClient paymentClient) {
        this.paymentClient = paymentClient;
    }
}

기본 생성자로 빈을 만든 뒤 setter를 호출해 의존성을 주입. 필드에 final을 붙일 수 없고, 객체 생성과 의존성 채워지는 시점이 분리된다.

동작 흐름

빈 생성 단계는 다음과 같다 (Bean 생명주기 시리즈에서 본 그것).

  1. 기본 생성자로 객체 생성
  2. BeanPostProcessor가 @Autowired가 붙은 setter들을 모두 호출해 의존성 주입
  3. 초기화 콜백 (@PostConstruct 등) 실행

1번과 2번 사이에는 객체가 존재하지만 의존성이 비어있는 상태가 일시적으로 존재한다. 이 짧은 윈도우가 잠재적인 위험 — 생성자에서 의존성을 사용하려 하면 NPE.

적합한 용도 — 옵셔널 의존성

세터 주입의 진짜 자리는 옵셔널 의존성. 항상 필요한 건 아니지만 환경에 따라 들어올 수도 있는 빈. 

@Service
public class OrderService {

    private MetricsCollector metricsCollector;

    @Autowired(required = false)
    public void setMetricsCollector(MetricsCollector metricsCollector) {
        this.metricsCollector = metricsCollector;
    }
}

required = false로 두면 그 빈이 컨테이너에 없어도 에러 없이 넘어간다. 반대로 생성자 주입은 모든 매개변수가 반드시 있어야 객체가 만들어지므로 옵셔널을 표현하기 어렵다.

3. 필드 주입 (Field Injection)

@Service
public class OrderService {

    @Autowired
    private UserRepository userRepository;

    @Autowired
    private PaymentClient paymentClient;
}

가장 간결한 형태. 필드에 직접 @Autowired를 붙이고 끝. 생성자도 setter도 작성하지 않는다.

동작 흐름

Spring이 reflection으로 private 필드에 직접 값을 꽂는다. 필드의 접근 제어자를 setAccessible(true)로 풀고 Field.set으로 값 대입. 외부에서 강제로 필드를 건드리는 방식.

왜 권장되지 않는가

짧고 편하지만 다음 편에서 본격적으로 다룰 여러 단점이 있다. 핵심만 짚으면.

  • final 사용 불가 — 의존성이 immutable하지 않다
  • 의존성 명시성 약함 — 클래스 외부에서 의존 관계를 보기 어렵다
  • 테스트가 까다롭다 — Spring 컨텍스트 없이 단위 테스트하려면 reflection 또는 스프링 도구 필요
  • 순환 참조가 늦게 발견된다 — 런타임에야 드러남

IntelliJ가 필드 주입에 경고 메시지를 띄우는 것도 이 이유들 때문. Spring 공식 가이드도 생성자 주입을 권장한다.

혼합 사용 — 가능하지만 권장 X

@Service
public class OrderService {

    private final UserRepository userRepository;   // 생성자

    @Autowired
    private PaymentClient paymentClient;           // 필드

    public OrderService(UserRepository userRepository) {
        this.userRepository = userRepository;
    }
}

기술적으로 가능하지만 의존성을 어디서 받는지 일관성이 없어 가독성이 떨어진다. 한 클래스 안에서는 한 방식으로 통일하는 게 권장.

면접 단골 질문

Q. DI의 세 방식은?

생성자 주입, 세터 주입, 필드 주입. Spring이 빈을 만들고 의존성을 채우는 통로의 차이. 생성자는 객체 생성 시점에 매개변수로, 세터는 setter 메서드로, 필드는 reflection으로 직접 필드에 꽂는다. Spring 공식 가이드와 IntelliJ 모두 생성자 주입을 권장.

Q. 필드 주입이 권장되지 않는 이유?

final 사용 불가, 단위 테스트 시 reflection 필요, 의존성 명시성 부족, 순환 참조가 런타임에야 발견되는 점 등. 짧고 편하다는 게 유일한 장점이지만 그 대가가 너무 커서 모범 사례에서는 피한다. Spring 4.3 + Lombok @RequiredArgsConstructor 조합이면 생성자 주입도 그만큼 짧게 쓸 수 있다.

Q. 세터 주입은 언제 쓰나?

옵셔널 의존성. 항상 필요한 건 아니지만 환경에 따라 들어올 수 있는 빈. @Autowired(required = false)로 두면 그 빈이 없어도 에러 없이 넘어간다. 또는 의존성을 런타임에 교체해야 하는 특수한 경우 (드물지만).

Q. 생성자가 둘 이상이면 어떻게 되나?

Spring은 어느 생성자를 쓸지 모르므로 명시적으로 @Autowired가 붙은 생성자를 사용한다. @Autowired 없는 다중 생성자면 컨테이너 시작 시점에 에러. 생성자가 하나뿐이면 Spring 4.3+에서 @Autowired 생략 가능.

한 줄 정리

DI는 생성자 / 세터 / 필드 세 통로로 들어온다. 생성자는 객체를 처음부터 완전하게 만드는 강한 보장, 세터는 옵셔널 의존성을 표현하는 유연한 도구, 필드는 가장 짧지만 안전성을 잃는 지름길. 현대 Spring 코드의 표준은 final + 생성자 주입.

다음 편은 왜 생성자 주입을 권장하는가의 이유들. final 보장, 순환 참조 조기 발견, 테스트 용이성, 그리고 빠지기 쉬운 함정까지.
