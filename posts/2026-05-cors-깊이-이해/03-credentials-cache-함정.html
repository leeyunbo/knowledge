Credentials, Cache, Vary — 운영에서 만나는 함정

쿠키를 같이 보내려면, CDN 캐시가 끼어있다면, 여러 origin을 허용하려면. 정상 시나리오 너머의 운영 함정들.

CORS 깊이 이해
  1. Same-Origin Policy의 진짜 의미
  2. Preflight (OPTIONS) — 왜 한 번 더 왔다 갔다 하는가

쿠키가 안 가요

프론트가 백엔드에 호출하는데 세션 쿠키가 자동으로 안 실린다. 분명히 같은 회사의 도메인끼리고, 사용자는 로그인했는데 매 호출마다 401.

원인: cross-origin 요청은 기본적으로 쿠키를 자동 첨부하지 않는다. 1편에서 본 SOP의 일부다. 인증된 쿠키가 다른 origin으로 자동으로 흘러가면 CSRF 공격 시나리오가 만들어지니, 브라우저가 자기가 막는다.

쿠키를 같이 보내려면 클라이언트와 서버 양쪽이 명시적으로 허용해야 한다. 이게 credentials 영역이다.

credentials 모드 — 클라이언트 측

fetch API의 credentials 옵션은 세 가지 값을 갖는다. 

fetch(url, { credentials: "omit" })         // 기본값. 쿠키 안 보냄
fetch(url, { credentials: "same-origin" })  // 같은 origin이면 쿠키 보냄
fetch(url, { credentials: "include" })      // 모든 요청에 쿠키 보냄 (cross-origin 포함)

기본값이 omit인 게 핵심 함정. 명시적으로 include를 안 적어주면 cross-origin 요청에 쿠키가 안 실린다. 

// 쿠키가 안 가는 코드 (자주 만남)
fetch("https://api.example.com/me")

// 쿠키 같이 보내는 코드
fetch("https://api.example.com/me", { credentials: "include" })

axios도 비슷하다. 

axios.get("https://api.example.com/me", {
    withCredentials: true   // ← 명시 필요
})

Access-Control-Allow-Credentials — 서버 측

클라이언트가 credentials: include로 보내도 서버가 받을 의사를 명시해야 한다. 

HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Credentials: true
Set-Cookie: session=...; HttpOnly; Secure; SameSite=None

서버 응답에 Access-Control-Allow-Credentials: true가 있어야 브라우저가 그 응답의 쿠키를 저장하고, 이후 요청에 포함한다.

함정 1 — Allow-Credentials와 wildcard 충돌

이게 가장 자주 만나는 함정이다. 

잘못된 응답:
  Access-Control-Allow-Origin: *
  Access-Control-Allow-Credentials: true

→ 브라우저: 둘이 동시에 있으면 거부. 응답 차단.

credentials를 허용하려면 Allow-Origin이 구체 origin이어야 한다. wildcard(*)와 같이 못 쓴다. 이유는 보안. 인증 쿠키가 흘러가는 응답을 모든 origin에 허용하면 그 자체가 CSRF 시나리오를 다시 만든다. 

해결: 구체 origin을 응답에 명시

  Access-Control-Allow-Origin: https://app.example.com
  Access-Control-Allow-Credentials: true

함정 2 — 여러 origin을 허용하고 싶을 때

한 백엔드를 여러 프론트에서 호출하는 경우. 예: https://app.example.com과 https://admin.example.com 둘 다 허용하고 싶다.

Wildcard는 못 쓴다(credentials와 충돌). 그렇다고 한 응답에 origin을 두 개 적을 수도 없다. Access-Control-Allow-Origin은 단일 값만 허용. 

잘못된 응답:
  Access-Control-Allow-Origin: https://app.example.com, https://admin.example.com
                                                       ↑ 콤마 구분 안 됨

해법 — 요청 Origin을 echo하기

서버가 요청의 Origin 헤더를 받고, 허용 목록에 있는지 확인한 후 그 origin을 응답에 그대로 실어준다. 

// 의사 코드
String requestOrigin = request.getHeader("Origin");
Set<String> allowedOrigins = Set.of(
    "https://app.example.com",
    "https://admin.example.com"
);

if (allowedOrigins.contains(requestOrigin)) {
    response.setHeader("Access-Control-Allow-Origin", requestOrigin);
    response.setHeader("Access-Control-Allow-Credentials", "true");
    response.setHeader("Vary", "Origin");   // 캐시 분리, 후술
}

핵심은 화이트리스트 검증 후 echo다. 그냥 무조건 echo하면 보안 위험이 된다(다음 함정).

함정 3 — Origin 무조건 echo의 보안 위험

귀찮다고 검증 없이 그냥 echo하면 어떻게 될까. 

// 위험한 코드
String requestOrigin = request.getHeader("Origin");
response.setHeader("Access-Control-Allow-Origin", requestOrigin);  // ❌
response.setHeader("Access-Control-Allow-Credentials", "true");

이러면 모든 origin을 허용하게 되는 것과 같다. attacker.com에서 호출이 와도 그 origin을 그대로 echo하니 credentials 포함 응답이 흘러간다. 1편에서 본 CSRF 위협이 다시 가능해진다.

반드시 화이트리스트 검증을 거친 후 echo해야 한다. 또는 정규식으로 패턴 검증(*.example.com처럼). 이 검증이 빠지면 wildcard와 같은 보안 수준으로 떨어진다.

함정 4 — CDN 캐시와 Vary 헤더

CDN(CloudFront, Akamai 등)이 앞단에 끼어있는 경우. API 응답을 캐시하는 CDN이라면 CORS와 까다롭게 상호작용한다. 

시나리오:
1. https://app.example.com 사용자가 API 호출
2. CDN이 응답을 캐시:
   Access-Control-Allow-Origin: https://app.example.com

3. https://admin.example.com 사용자가 같은 API 호출
4. CDN이 캐시된 응답을 그대로 줌:
   Access-Control-Allow-Origin: https://app.example.com   ← 잘못됨!

5. 두 번째 사용자의 브라우저: origin 불일치로 차단

해법: Vary: Origin 헤더를 응답에 실어준다. 

HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://app.example.com
Vary: Origin                                          ← 캐시 분리 신호

Vary: Origin은 CDN과 브라우저 캐시에게 "이 응답은 Origin 헤더 값에 따라 다르니 origin별로 따로 캐시해라"고 알려준다.

이 헤더 없으면 CDN이 한 origin의 응답을 다른 origin 사용자에게 줘버려서 위 시나리오가 발생한다. 여러 origin 허용하면서 CDN 끼는 환경이라면 Vary: Origin 거의 필수다.

함정 5 — Spring Security와 CORS의 순서

Spring Boot 환경에서 흔한 실수. Spring Security가 CORS 처리 전에 인증 체크를 해버리면 OPTIONS preflight가 401로 떨어진다. 

잘못된 흐름:
1. 브라우저: OPTIONS /api/foo (인증 헤더 없음 — preflight는 헤더 없이 옴)
2. Spring Security: 인증 안 됨 → 401
3. 브라우저: preflight 실패로 판단, 본 요청 안 보냄

OPTIONS preflight는 인증을 면제해야 한다. Spring Security 설정에서 명시적으로 풀어줘야 한다. 

@Bean
public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    http
        .cors(Customizer.withDefaults())              // CORS 활성화
        .authorizeHttpRequests(auth -> auth
            .requestMatchers(HttpMethod.OPTIONS, "/**").permitAll()  // ← OPTIONS 허용
            .anyRequest().authenticated()
        );
    return http.build();
}

@Bean
public CorsConfigurationSource corsConfigurationSource() {
    CorsConfiguration config = new CorsConfiguration();
    config.setAllowedOrigins(List.of("https://app.example.com"));
    config.setAllowedMethods(List.of("GET", "POST", "PUT", "DELETE"));
    config.setAllowedHeaders(List.of("*"));
    config.setAllowCredentials(true);
    config.setMaxAge(3600L);

    UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
    source.registerCorsConfiguration("/**", config);
    return source;
}

cors(Customizer.withDefaults())가 CORS 필터를 Security 체인 앞쪽에 끼워준다. 그래서 OPTIONS는 인증 검사 전에 처리되고 정상 응답된다. 본 요청은 그 다음 단계에서 인증 검사.

실전 디버깅 체크리스트

CORS 에러를 만났을 때 순서대로 확인할 것. 

1. 네트워크 탭에 OPTIONS가 보이는가?
   - 안 보임 → simple request로 본 요청만 갔음
   - 200/204 → preflight OK, 다음 본 요청 단계
   - 4xx/5xx → preflight 실패. 서버 OPTIONS 핸들러 확인

2. OPTIONS 응답의 헤더 확인:
   - Access-Control-Allow-Origin: 요청 origin과 일치?
   - Access-Control-Allow-Methods: 본 요청 메서드 포함?
   - Access-Control-Allow-Headers: 본 요청 헤더 모두 포함?

3. 본 요청 응답의 헤더 확인:
   - Access-Control-Allow-Origin: 또 있어야 함 (preflight에만 있는 게 아님)
   - credentials 쓰면: Access-Control-Allow-Credentials: true

4. Credentials 관련:
   - 클라이언트: credentials: "include" 명시?
   - 서버: Allow-Credentials: true?
   - 서버: Allow-Origin이 구체 origin? (* 아닌가?)

5. 여러 origin 허용한다면:
   - Vary: Origin 응답에 있나? (CDN 환경이면 필수)

6. Spring Security 환경:
   - OPTIONS가 permitAll로 풀려있나?
   - CorsConfigurationSource 빈 등록됐나?

Spring의 @CrossOrigin 간단 사용

간단한 케이스라면 컨트롤러에 어노테이션 한 줄로 끝. 

@RestController
@RequestMapping("/api")
@CrossOrigin(
    origins = "https://app.example.com",
    methods = { RequestMethod.GET, RequestMethod.POST },
    allowedHeaders = "*",
    allowCredentials = "true",
    maxAge = 3600
)
public class FooController {
    // ...
}

이러면 Spring이 알아서 CORS 헤더를 응답에 실어준다. 단, 글로벌 정책은 위에서 본 CorsConfigurationSource 빈으로 가는 게 일관성 측면에서 낫다.

시리즈 정리

1편: Same-Origin Policy의 진짜 의미
     - SOP는 브라우저가 강제하는 사용자 보호 정책
     - origin = scheme + host + port
     - CSRF 방지가 목적
     - 서버는 SOP를 모름 (curl/서버-to-서버는 영향 없음)
     - CORS는 SOP의 예외 허용 메커니즘
     - Simple request vs Preflight request 분류

2편: Preflight (OPTIONS) — 왜 한 번 더 왔다 갔다 하는가
     - 부수효과 있는 요청은 미리 권한 확인
     - Preflight 트리거 조건 (메서드, Content-Type, custom 헤더)
     - OPTIONS 요청/응답의 헤더
     - Access-Control-Max-Age로 캐시 (Chrome 7200, Firefox 86400)
     - 흔한 실패 시나리오

3편: Credentials, Cache, Vary — 운영에서 만나는 함정
     - cross-origin은 기본적으로 쿠키 안 보냄
     - credentials: "include" + Allow-Credentials: true
     - wildcard와 credentials 동시 사용 불가
     - 여러 origin 허용은 화이트리스트 echo로
     - origin 무조건 echo는 보안 위험
     - CDN과 Vary: Origin
     - Spring Security와 CORS 순서

CORS는 처음 만났을 때 이상한 정책처럼 느껴진다. 서버는 잘 응답했는데 브라우저가 못 읽게 막는 게 직관적이지 않다. 그러나 그 뒤엔 인터넷 보안의 가장 기본적인 가정이 있다. "다른 사이트의 JS가 우리 사용자의 인증으로 우리 API를 마음대로 부를 수 있어선 안 된다."

CORS는 그 보호를 유지하면서도 정당한 cross-origin 호출을 가능하게 하는 명시적 허락 시스템이다. 운영 환경에선 함정이 많지만, 본질만 알면 디버깅이 명확해진다. SOP가 무엇이고, 누가 강제하고, 서버는 무엇을 보내야 하는가 — 이 셋이 출발점이다.
