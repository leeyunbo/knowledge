Same-Origin Policy의 진짜 의미

curl로는 잘 되는데 브라우저에선 막힌다. 왜 브라우저만 막고, 그 정책의 진짜 목적은 무엇인가.

curl로는 되는데 브라우저에선 막힌다

개발 중 흔히 만나는 시나리오. 

$ curl https://api.kakao.com/v1/foo
{ "result": "ok", ... }                 ← 잘 됨

브라우저에서 같은 URL을 fetch:
  fetch("https://api.kakao.com/v1/foo")
   → 네트워크 탭엔 호출 갔다 옴, 응답도 200 OK
   → 그런데 JS는 응답을 못 읽음
   → 콘솔: "blocked by CORS policy"

여기서 헷갈리는 점. 호출은 분명히 갔고 응답도 왔다. 서버는 정상 처리했다. 그런데 브라우저가 그 응답을 우리 JS에 전달하지 않는다. 왜?

답: Same-Origin Policy(SOP). 브라우저가 JavaScript의 동작을 스스로 막고 있는 것이다. 이게 CORS의 출발점이다.

Origin이라는 단위

SOP를 이해하려면 먼저 origin이 뭔지 알아야 한다. 

origin = scheme + host + port

https://example.com         → origin: https://example.com (port 443 묵시적)
http://example.com          → origin: http://example.com (port 80) — 다른 origin!
https://example.com:8080    → origin: https://example.com:8080 — 또 다른 origin
https://api.example.com     → origin: https://api.example.com — 또 다른 origin
                              (sub도메인이 달라도 다른 origin)

셋 중 하나라도 다르면 다른 origin이다. https://example.com과 http://example.com이 다르고, example.com과 www.example.com이 다르고, 포트가 달라도 다르다. 정의가 매우 엄격하다.

Same-Origin Policy — 브라우저가 스스로 만든 룰

핵심 규칙은 단순하다.

JavaScript가 자기 origin과 다른 origin의 응답을 읽으려면 그 origin이 명시적으로 허락해야 한다. 

[brower at https://myapp.com]
   │ JS: fetch("https://api.kakao.com/...")
   ▼
[api.kakao.com]
   ◀── 응답 (200 OK + body)
   │
브라우저가 응답을 받음. 그런데:
  - 응답에 Access-Control-Allow-Origin 헤더가 있고
  - 그 값이 https://myapp.com 이거나 *
  → 브라우저가 응답을 JS에 전달

  - 위 헤더가 없거나 우리 origin 안 적혀있음
  → 브라우저가 응답을 막아버림 (JS는 못 읽음)

중요한 점: 호출 자체는 막지 않는다. 브라우저는 요청을 보내고 응답도 받아온다. 그 다음 응답에 권한이 있는지 확인하고, 없으면 그 응답을 JS에 전달하지 않는다.

그래서 서버 입장에선 요청을 정상 처리한 것처럼 보이고, (만약 그게 GET이 아니라 POST 같은 요청이라면) DB에 데이터까지 들어갔을 수 있다. 응답만 못 읽을 뿐.

왜 이런 정책이 필요한가 — CSRF의 위협

SOP가 없다고 가정해보자. 어떤 일이 가능해질까. 

1. 사용자가 은행 사이트 (https://mybank.com)에 로그인
   → 브라우저가 mybank.com의 세션 쿠키를 저장

2. 사용자가 다른 사이트 (https://attacker.com)를 방문
   → 그 사이트의 JS 코드:
       fetch("https://mybank.com/transfer", {
         method: "POST",
         body: JSON.stringify({ to: "attacker", amount: 1000000 })
       })
       .then(res => res.json())
       .then(data => sendToAttacker(data))

3. SOP가 없다면:
   → 브라우저가 mybank.com 세션 쿠키를 자동 첨부 (쿠키는 도메인 기반)
   → 은행 서버는 정상 사용자 요청으로 인식
   → 송금 처리됨
   → 응답까지 attacker에게 전달
   → 인증 토큰이나 잔액 같은 정보도 다 노출

SOP가 없으면 인터넷의 모든 사이트가 사용자를 사칭해서 다른 사이트의 API를 마음대로 호출할 수 있다. 쿠키 기반 인증은 도메인 단위로 자동 첨부되니, 사용자가 로그인한 어떤 사이트든 attacker가 자기 사이트에서 호출 가능해진다.

SOP는 이 위협을 막기 위해 등장했다. "다른 origin의 응답은 명시적 허락 없이 못 본다"는 룰로 attacker가 응답 데이터를 훔치는 걸 차단한다. (요청 자체를 막진 않으니 CSRF 자체가 완전히 막히진 않지만, 데이터 유출의 일부 시나리오는 차단된다)

그래서 서버는 SOP를 모른다

이 점이 가장 헷갈리는 부분이다. SOP는 100% 브라우저가 강제하는 정책이다. 서버는 누가 호출했는지, 그게 어느 origin에서 왔는지 알지 못한다(요청 헤더로 받지 않으면). 

curl https://api.kakao.com/...    → SOP 영향 없음. 정상 응답
node fetch ...                    → SOP 영향 없음. 정상 응답
Postman으로 호출                   → SOP 영향 없음. 정상 응답
서버-to-서버 호출                  → SOP 영향 없음. 정상 응답

브라우저 JS의 fetch                → SOP 적용. 응답 차단 가능

SOP는 브라우저가 사용자 보호를 위해 자기가 강제하는 룰이다. 서버는 이 룰의 존재 자체를 모를 수 있다. 이게 백엔드 개발자가 처음 CORS를 만났을 때 헷갈리는 핵심 이유다. "내 서버는 잘 응답했는데 왜 안 된다고 하지?"

CORS — SOP의 예외 허용 메커니즘

SOP가 너무 엄격하면 정작 정당한 cross-origin 호출도 막힌다. 예: 우리 회사의 프론트(https://app.example.com)에서 우리 회사의 API(https://api.example.com)를 호출하는 것. 이건 합법적이고 필요한 호출이지만 origin이 다르니 SOP는 막는다.

그래서 표준이 만든 게 CORS(Cross-Origin Resource Sharing)다. 서버가 응답에 특정 헤더를 실어 보내면 그 헤더를 보고 브라우저가 SOP의 예외를 허용한다. 

HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://app.example.com
Content-Type: application/json

{ ... }

서버가 "https://app.example.com origin에서 오는 요청은 응답을 보여줘도 돼"라고 명시. 브라우저가 이 헤더를 보고 자기 origin이랑 일치하면 응답을 JS에 전달.

핵심 헤더 셋

응답 헤더
─────────────────────────────────────────────
Access-Control-Allow-Origin
  - 어느 origin에서 오는 요청에 응답을 허용할지
  - 구체 origin 명시: https://app.example.com
  - 모두 허용: *  (단, credentials와 함께 못 씀, 3편에서 다룸)

Access-Control-Allow-Methods
  - 어떤 HTTP 메서드를 허용할지 (GET, POST, PUT, DELETE 등)
  - Preflight 응답에 주로 등장

Access-Control-Allow-Headers
  - 클라이언트가 보낼 수 있는 custom 헤더 목록
  - Authorization, X-Custom-Header 같은 것
  - Preflight 응답에 등장

Simple Request — 추가 검증 없이 곧장 가는 호출

모든 cross-origin 요청이 똑같이 처리되는 건 아니다. 가장 단순한 형태의 요청은 simple request로 분류되어 브라우저가 추가 절차 없이 그냥 본 요청을 보내고 응답 헤더만 확인한다.

Simple request 조건 (Fetch standard 정의): 

1. 메서드는 GET, HEAD, POST 중 하나
2. 헤더는 자동 설정 헤더 + 다음 안전 헤더만 허용:
   Accept, Accept-Language, Content-Language,
   Content-Type, Range
3. Content-Type을 명시한다면 다음 셋 중 하나만:
   - application/x-www-form-urlencoded
   - multipart/form-data
   - text/plain
4. XMLHttpRequestUpload에 이벤트 리스너 없음
5. 요청 body에 ReadableStream 없음

여기 한 가지라도 어긋나면 simple request가 아니고, 브라우저가 본 요청 보내기 전에 preflight request(OPTIONS)를 먼저 보낸다.

현실에서 거의 모든 API 호출이 preflight를 트리거한다. API 호출에 흔히 쓰는 Content-Type: application/json이 이미 simple request 조건을 벗어난다. custom 헤더(Authorization 등)를 쓰면 또 벗어난다. PUT, DELETE, PATCH 메서드도 simple이 아니다.

그래서 백엔드 개발자가 만나는 CORS는 거의 항상 preflight 얘기다. 이게 다음 편의 주제다.

이 편의 한 줄 정리

SOP는 브라우저가 사용자 보호를 위해 자기가 강제하는 정책이다. 다른 origin의 응답을 JS가 읽으려면 그 origin이 명시적으로 허락해야 한다. 서버는 이 정책을 모르고, curl이나 서버-to-서버 호출엔 적용되지 않는다.

CORS는 SOP의 예외 허용 메커니즘이다. 서버가 Access-Control-Allow-Origin 같은 헤더를 응답에 실으면 브라우저가 그걸 보고 예외를 허용한다.

단, 단순한 요청만 그냥 보낸다. JSON content-type이나 custom 헤더가 끼면 브라우저가 본 요청 전에 "preflight" OPTIONS 요청으로 먼저 권한 확인을 한다. 왜 그걸 하는지, 그게 어떻게 생겼는지가 다음 편이다.
