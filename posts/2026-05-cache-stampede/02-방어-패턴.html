Cache Stampede 방어 패턴

5가지 표준 방어 패턴. 각각의 장단점과 적합한 자리를 정리해봐요.

방어 패턴 1 — Lock

가장 직관적인 답. cache miss 시 lock을 잡고 첫 요청만 DB 조회. 나머지는 대기 또는 stale 반환. 

public User getUser(Long id) {
    String key = "user:" + id;
    User cached = redis.get(key);
    if (cached != null) return cached;

    String lockKey = key + ":lock";
    boolean acquired = redis.setIfAbsent(lockKey, "1", Duration.ofSeconds(10));

    if (!acquired) {
        // 다른 요청이 이미 처리 중
        Thread.sleep(50);
        return getUser(id);   // 재시도
    }

    try {
        User user = userRepository.findById(id);
        redis.set(key, user, Duration.ofMinutes(5));
        return user;
    } finally {
        redis.delete(lockKey);
    }
}

장점과 단점

  • 장점: DB 호출 정확히 한 번, 단순한 의도
  • 단점: 락 보유자 다운 시 다른 요청 모두 대기, 락 시스템 필요, 분산 락 함정 그대로
  • 적합: 트래픽이 매우 높지 않은 critical 캐시

방어 패턴 2 — Probabilistic Early Expiration

더 영리한 답. TTL이 만료되기 전부터 일부 요청만 미리 캐시를 갱신해요. 확률적으로 일찍 만료된 것처럼 처리해서 stampede를 분산. 

public User getUser(Long id) {
    String key = "user:" + id;
    CachedItem item = redis.get(key);
    if (item == null) {
        return loadAndCache(id);   // miss
    }

    // 만료가 가까울수록 미리 갱신할 확률 증가
    long now = System.currentTimeMillis();
    long expiresAt = item.getExpiresAt();
    long ttl = expiresAt - now;
    long beta = 1000;   // 갱신 시작 윈도우 (ms)

    double prob = -beta * Math.log(Math.random());
    if (prob > ttl) {
        return loadAndCache(id);   // 일찍 갱신
    }

    return item.getValue();
}

XFetch 알고리즘이라 불리는 패턴이에요. 만료 직전 일부 요청만 갱신하니 동시 cache miss 폭주가 자연스럽게 분산.

장점과 단점

  • 장점: 락 없이 분산, 갱신이 점진적으로 일어남
  • 단점: 구현 약간 복잡, 갱신 비용이 약간 늘어남
  • 적합: 인기 키, 갱신 비용이 크지 않은 데이터

방어 패턴 3 — Refresh Ahead

만료 전에 백그라운드 잡으로 미리 갱신. 사용자 요청은 항상 cache hit. 

@Scheduled(fixedRate = 60_000)   // 1분마다
public void refreshHotKeys() {
    List<Long> hotUserIds = identifyHotKeys();
    for (Long id : hotUserIds) {
        User user = userRepository.findById(id);
        redis.set("user:" + id, user, Duration.ofMinutes(10));
    }
}

장점과 단점

  • 장점: 사용자 요청 latency 일정, stampede 발생 안 함
  • 단점: hot key 식별 필요, 안 인기 키도 갱신될 수 있음 (낭비)
  • 적합: 핵심 콘텐츠, hot key가 명확한 경우

방어 패턴 4 — TTL Jitter

모든 키의 TTL이 같은 시점에 만료되지 않도록 jitter(랜덤 오차)를 추가. 

public void cacheWithJitter(String key, Object value) {
    long baseTtl = 300;   // 5분
    long jitter = ThreadLocalRandom.current().nextLong(60);   // 0~60초
    long actualTtl = baseTtl + jitter;

    redis.set(key, value, Duration.ofSeconds(actualTtl));
}

같은 시각에 채워진 1000개 키들이 5~6분 사이로 분산되어 만료. 한 시점에 100개씩만 만료되어 부하 분산.

장점과 단점

  • 장점: 매우 단순, 추가 인프라 불필요
  • 단점: 한 키 만료의 stampede는 못 막음 (여러 키 만료의 동기화만 풀림)
  • 적합: 모든 캐싱 환경의 default. 항상 켜두는 게 좋음

방어 패턴 5 — Stale-While-Revalidate

만료된 캐시를 일단 반환하면서 백그라운드로 새로 가져와 갱신. 사용자는 stale data를 보지만 빠른 응답 받음. 

public User getUser(Long id) {
    String key = "user:" + id;
    CachedItem item = redis.get(key);

    if (item == null) {
        return loadAndCache(id);   // 진짜 miss
    }

    if (item.isStale()) {
        // 백그라운드로 갱신 시작
        scheduler.execute(() -> loadAndCache(id));
    }

    return item.getValue();   // stale도 일단 반환
}

HTTP의 Cache-Control: stale-while-revalidate와 같은 패턴이에요. 사용자 응답 latency 일정, 단 stale 윈도우 동안 옛 데이터 표시.

장점과 단점

  • 장점: latency 일정, stampede 자연스럽게 방어
  • 단점: stale 데이터 표시 (잠시), 일관성 약함
  • 적합: 약간의 stale을 허용할 수 있는 자원 (제품 카탈로그, 콘텐츠)

실무 조합 — 다층 방어

한 패턴만으로 모든 stampede를 막기 어려워요. 보통 여러 패턴을 조합해요.

일반 추천 조합

  1. TTL Jitter: 모든 캐시에 default로 적용
  2. Probabilistic Early Expiration 또는 Stale-While-Revalidate: 인기 키 처리
  3. Refresh Ahead: 핵심 hot key 미리 갱신
  4. Lock: critical하고 정확한 데이터에 backup으로

외부 도구 활용

Caffeine, Hazelcast 같은 캐시 라이브러리가 일부 패턴을 자동 제공해요. 

// Caffeine의 refreshAfterWrite — Refresh Ahead 자동
LoadingCache<Long, User> cache = Caffeine.newBuilder()
    .expireAfterWrite(Duration.ofMinutes(10))
    .refreshAfterWrite(Duration.ofMinutes(5))   // 5분 후 백그라운드 갱신
    .maximumSize(10000)
    .build(this::loadUser);

장애 대비 — Cache 다운 시 fallback

cache 자체가 다운되면 모든 요청이 cache miss로 DB로 폭주. 이걸 막는 패턴도 필요해요.

Circuit Breaker

캐시 호출에 circuit breaker 적용. 캐시 fail이 누적되면 일정 시간 캐시 호출 자체를 차단하고 직접 DB로. DB 부하가 동시 폭주하지 않도록 단계적 처리.

Local Cache Fallback

Redis 다운 시 in-memory fallback cache 사용. 일시적 stale은 허용. 

public User getUser(Long id) {
    try {
        return redisCache.get(id);
    } catch (RedisException e) {
        return localFallbackCache.get(id);   // Caffeine 로컬 캐시
    }
}

Rate Limiting

DB로 가는 요청 수에 직접 제한. 초당 N개만 허용, 나머지는 fail-fast. stampede 자체를 막진 않지만 DB 보호 효과.

실전 시나리오 — 한정 세일

이커머스의 한정 세일 페이지. 인기 상품 정보가 캐시에 있고 5분 TTL. 세일 시작 시간에 트래픽 spike + 캐시 만료가 겹치면 stampede.

적용 패턴 조합

  1. 제품 정보 캐시에 TTL Jitter (5~6분 분산)
  2. 핵심 hot 제품은 Refresh Ahead로 1분마다 백그라운드 갱신
  3. 그 외 제품은 Stale-While-Revalidate로 stale 허용
  4. DB 호출에 circuit breaker로 폭주 차단
  5. 관리자가 hot key 모니터링 후 미리 warming

이런 다층 방어가 큰 트래픽에서 안정성을 만들어요.

흔한 실수

1. TTL을 매우 길게 설정

stampede 무서워서 TTL을 12시간 같이 설정. stale 데이터 위험 커지고, 실제 변경된 데이터를 사용자가 못 봐요. TTL을 늘리는 게 답이 아니에요. 만료 시 부하를 분산하는 패턴 적용이 답.

2. 락만 의존

모든 stampede를 lock 한 패턴으로 막으려는 시도. 락 시스템(Redis 등)이 hot spot 되어 자체 부하 발생. 또 락 보유자가 죽으면 다른 모든 요청 대기 → 다른 형태의 정지. 여러 패턴 조합이 필요해요.

3. Stale-While-Revalidate를 critical 데이터에

금융 잔액 같은 데이터에 SWR 적용하면 사용자가 옛 잔액 보고 잘못된 결정 가능. stale 허용 가능한 데이터에만 적용해야 해요.

면접 단골 질문

Q. Cache Stampede를 어떻게 막아요?

5가지 패턴을 조합해서 막아요. TTL Jitter는 항상 켜두고(만료 시점 분산), 인기 키는 Probabilistic Early Expiration(미리 갱신)이나 Stale-While-Revalidate(stale 반환 + 백그라운드 갱신). 핵심 hot key는 Refresh Ahead(백그라운드 잡으로 주기 갱신). critical 데이터에는 Lock으로 정확한 한 번 조회 보장. 그리고 캐시 다운 시 circuit breaker로 DB 보호도 함께.

Q. Probabilistic Early Expiration이 뭐예요?

TTL이 만료되기 전부터 일부 요청만 확률적으로 미리 갱신하는 패턴이에요. 만료가 가까울수록 갱신 확률이 높아져요. 분산 갱신으로 stampede 자연스럽게 막아요. XFetch 알고리즘이라 불리는데, 락 없이 처리할 수 있어 Lock 패턴보다 운영 단순해요.

Q. Stale-While-Revalidate는 언제 쓰면 안 되나요?

정확성이 critical한 데이터에는 부적합해요. 금융 잔액, 결제 상태, 재고 정확성 같은 자리. stale 데이터를 잠시 보여주는 게 비즈니스적으로 받아들일 수 있는 자원에만 써요. 제품 카탈로그, 콘텐츠 메타데이터, 통계 같은 게 적합해요.

Q. TTL을 길게 늘리면 stampede가 안 생기나요?

오히려 stampede 자체는 줄어들지만 만료 시점에 한 번 발생하는 stampede의 규모가 더 커져요. 긴 시간 누적된 핫 키일수록 만료 순간 더 많은 요청이 몰리거든요. 또 stale 데이터 위험 증가하는 부작용. TTL을 늘리는 게 아니라 분산 패턴을 적용하는 게 답이에요.

한 줄 정리

Cache Stampede는 5가지 패턴(Lock, Probabilistic Early Expiration, Refresh Ahead, TTL Jitter, Stale-While-Revalidate) 조합으로 막아요. TTL Jitter는 default로 항상, 인기 키는 SWR이나 Probabilistic, hot key는 Refresh Ahead, critical은 Lock. 캐시 다운 fallback도 함께 설계하는 게 운영 안정성의 핵심이에요.
