함정 — 메모리 누수, 스레드풀 상극

ThreadLocal이 가지는 두 큰 위험. 명시적 정리 없이 쓰면 메모리가 새고, 스레드풀과 결합하면 데이터가 다음 사용자에게 새어나간다.

함정 1 — 메모리 누수

1편에서 봤던 비대칭 — 키(ThreadLocal 인스턴스)는 WeakReference, 값은 strong reference. 이 설계가 어떻게 누수를 만드는지 단계로 따라가본다.

일반적인 시나리오

public class HeavyContext {
    private static final ThreadLocal<byte[]> cache =
        ThreadLocal.withInitial(() -> new byte[1024 * 1024]);  // 1MB

    public static byte[] get() { return cache.get(); }
}

// 어딘가에서
HeavyContext.get();   // 현재 스레드의 ThreadLocalMap에 1MB 값 저장

한 스레드에서 get()이 호출되면 그 스레드의 ThreadLocalMap에 1MB 배열이 저장된다. 그 배열을 가리키는 strong reference가 ThreadLocalMap의 Entry.value에 들어간 셈.

ThreadLocal 인스턴스가 GC된 후

Static이 아니거나 클래스가 unload되어 ThreadLocal 인스턴스 자체가 GC 대상이 되었다고 하자. 키는 WeakReference라 자동으로 정리된다. 하지만 Entry 자체와 그 안의 value는 strong reference라 그대로 남는다. 

ThreadLocalMap의 Entry:

Before GC:
  key: WeakRef(ThreadLocal 인스턴스) → strong → ThreadLocal 객체
  value: 1MB byte[]

After ThreadLocal 인스턴스 GC:
  key: WeakRef(null)            ← 키는 정리됨
  value: 1MB byte[]             ← 값은 여전히 살아있음 (누수)

이 상태가 ThreadLocal 누수. 키는 사라졌으니 누구도 이 값에 접근할 수 없는데 ThreadLocalMap의 Entry가 여전히 들고 있어 GC 대상이 되지 않는다. Thread 객체가 살아있는 동안(스레드풀이라면 거의 영원) 그 1MB가 메모리에 박혀있다.

JDK가 시도하는 정리

JDK는 ThreadLocalMap의 set/remove/rehash가 일어날 때 stale entry(키가 null인 Entry)를 일부 청소한다. 하지만 이 청소는 best-effort일 뿐 보장되지 않는다. 명시적으로 remove()를 호출하지 않으면 누수가 그대로 남을 수 있다.

방어 — 명시적 remove

public void process() {
    HeavyContext.get();
    try {
        // 실제 작업
    } finally {
        cache.remove();   // 반드시 finally에서 정리
    }
}

set과 remove를 try-finally로 묶는 패턴이 정석. 예외가 발생해도 remove가 보장되어 누수가 발생하지 않는다. ThreadLocal을 "쓰면 반드시 정리한다"는 디시플린이 누수 방지의 핵심.

함정 2 — 스레드풀과의 상극

이게 더 위험하다. ThreadLocal과 스레드풀이 만나면 데이터 오염과 누수가 동시에 발생할 수 있다.

시나리오

웹 서버에서 사용자 인증 정보를 ThreadLocal에 저장한다고 하자. 일반적인 패턴이다. 

public class UserContext {
    private static final ThreadLocal<User> current = new ThreadLocal<>();
    public static void set(User u) { current.set(u); }
    public static User get() { return current.get(); }
}

@RestController
public class OrderController {
    @PostMapping("/orders")
    public Order create(@RequestBody OrderRequest req) {
        User user = authService.authenticate(req.getToken());
        UserContext.set(user);   // ★ set만 하고 remove 안 함
        return orderService.create(req);
    }
}

발생하는 일

웹 서버가 ThreadPool 위에서 동작하므로 같은 스레드가 여러 요청을 처리한다. 요청 1에서 Alice가 인증되고 ThreadLocal에 Alice가 set된다. 요청 처리 끝났는데 remove 안 함. 그 스레드가 풀로 돌아가 다음 요청 2를 받는다. 요청 2가 인증을 안 했거나 다른 사용자라면 어떻게 될까.

  • Best case — 요청 2도 set을 호출해 Alice를 새 사용자로 덮어씀. 다행히 정상.
  • Worst case — 요청 2가 인증을 안 하는 endpoint면 set이 없음 → ThreadLocal엔 여전히 Alice의 정보 → 다른 사용자가 Alice인 척 보일 수 있음. 보안 사고.
  • 또 다른 worst case — 스레드가 다른 인증 키로 set했지만 일부 필드가 옛 값 그대로 — 데이터 오염.

이게 단순한 메모리 누수보다 훨씬 위험한 시나리오. 한 사용자의 정보가 다른 사용자에게 새어나가는 보안 결함. 실제로 운영 환경에서 종종 일어나는 사고.

방어 — 항상 try-finally + remove

@Component
public class UserContextFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        try {
            User user = authenticate(req);
            UserContext.set(user);
            chain.doFilter(req, res);
        } finally {
            UserContext.clear();   // ★ 무조건 정리
        }
    }
}

요청 시작 지점(Filter, Interceptor)에서 set, 끝나는 지점에서 무조건 clear/remove. 요청 처리 도중 예외가 나도 finally가 보장하니 안전. 이 패턴이 Spring Security의 SecurityContextHolder, MDC, 트랜잭션 매니저 모두 사용하는 방식.

함정 3 — 스레드 누수와 결합된 메모리 폭증

웹 서버는 보통 200개 정도 thread pool을 유지한다. 각 스레드의 ThreadLocalMap에 큰 값이 누수되면 200개 × 큰 값 = 상당한 메모리. 요청마다 ThreadLocal에 무거운 객체를 넣고 정리 안 하면 시간이 지날수록 메모리가 차오른다.

더 나쁜 시나리오는 ThreadLocal에 Connection이나 Stream 같은 자원이 들어간 경우. GC도 안 되고, 자원 소진(connection pool 고갈, file handle 소진)도 일으킨다. 실무에서 "GC 후에도 메모리가 안 줄어든다"는 증상의 흔한 원인.

InheritableThreadLocal의 한계

ThreadLocal의 변형인 InheritableThreadLocal은 자식 스레드가 부모 스레드의 값을 상속받게 한다. 새 Thread를 만들 때 부모의 ThreadLocalMap을 자식에게 복사. 

public class TraceContext {
    private static final InheritableThreadLocal<String> traceId = new InheritableThreadLocal<>();
}

// 부모 스레드
TraceContext.traceId.set("abc-123");
new Thread(() -> {
    System.out.println(TraceContext.traceId.get());  // "abc-123" 출력 (상속)
}).start();

스레드풀과 만나면 깨진다

InheritableThreadLocal은 "새 스레드를 만드는 시점"에 한 번만 부모 값을 복사한다. ThreadPoolExecutor의 worker 스레드는 한 번 만들어진 후 여러 작업을 재사용하므로, 처음 worker가 생성될 때(보통 첫 submit 시점)의 부모 값만 복사되고 이후엔 갱신되지 않는다.

  • worker 스레드가 처음 만들어지는 시점의 submitter 값이 그 worker에 박힘
  • 이후 다른 스레드가 새 traceId로 set한 뒤 작업을 submit해도 worker는 옛 값 그대로
  • 요청마다 traceId가 바뀌어야 하는데 풀 worker는 첫 값에 묶여 있음 — 의도와 다른 동작

이 한계로 InheritableThreadLocal은 스레드풀 환경에서 사실상 쓸모없다. 많은 분산 트레이싱 라이브러리가 이 함정을 만난다.

해결 시도 — TransmittableThreadLocal

Alibaba가 만든 라이브러리로 InheritableThreadLocal의 풀 환경 한계를 푼 구현. ExecutorService를 wrapping해서 작업 submit 시점에 부모의 ThreadLocal 값을 자식 스레드로 전달. 

// 의존성: com.alibaba:transmittable-thread-local

TransmittableThreadLocal<String> traceId = new TransmittableThreadLocal<>();

ExecutorService executor = TtlExecutors.getTtlExecutorService(
    Executors.newFixedThreadPool(10));

traceId.set("abc-123");
executor.submit(() -> {
    System.out.println(traceId.get());  // "abc-123" 정상 전달
});

별도 라이브러리 의존성이 필요하지만 풀 환경에서 ThreadLocal 전달이 필요하면 사실상의 표준. Sleuth/Brave 같은 분산 트레이싱 라이브러리가 내부적으로 이 패턴을 사용한다.

대안 — Virtual Thread

Java 21+에서는 Virtual Thread가 ThreadLocal의 많은 함정을 자연스럽게 해결한다. Virtual Thread는 매 작업마다 새로 만들고 끝나면 사라지는 가벼운 스레드라 "다음 사용자에게 데이터가 새는" 풀 함정이 발생하지 않는다.

또한 Java 21+의 ScopedValue가 ThreadLocal의 더 안전한 대안으로 도입되었다 (preview). 스코프 안에서만 유효하고 자동으로 정리되어, ThreadLocal의 명시적 remove 부담을 없앤다. 단, 아직 정식 안정화 단계는 아니라 신중히 도입.

실무 체크리스트

  1. ThreadLocal에 값을 set하면 반드시 try-finally의 finally에서 remove한다
  2. 웹 서버에서 요청 시작 지점(Filter)에서 set, 끝 지점에서 clear가 표준
  3. 큰 객체(MB 단위)를 ThreadLocal에 넣지 않는다 — 누수 시 영향이 크다
  4. ThreadLocal에 Connection, InputStream 같은 자원을 넣지 않는다
  5. 스레드풀 환경에서 InheritableThreadLocal은 쓰지 않는다 — 의도대로 동작 안 함
  6. 분산 트레이싱이나 컨텍스트 전파가 필요하면 TransmittableThreadLocal 또는 그 위 라이브러리 사용
  7. 가능하면 매개변수 전달이 더 명시적이고 안전 — ThreadLocal은 신중히
  8. Java 21+에선 ScopedValue를 검토

모니터링 — 누수 감지

ThreadLocal 누수는 일반 GC 로그로는 보이지 않는다. Heap dump를 떠서 분석해야 한다. 

jcmd <pid> GC.heap_dump /tmp/heap.hprof
# Eclipse MAT, VisualVM 등으로 분석

MAT(Memory Analyzer Tool) 같은 도구로 Thread 객체의 ThreadLocalMap을 들여다보면 어떤 ThreadLocal이 어떤 값을 들고 있는지 보인다. 크고 오래된 값이 의심스러우면 그 ThreadLocal의 정리 로직을 확인.

면접 단골 질문

Q. ThreadLocal 누수가 왜 발생하나?

ThreadLocalMap의 키는 WeakReference, 값은 strong reference. ThreadLocal 인스턴스가 GC되면 키는 정리되지만 값은 strong이라 그대로 남는다. Thread가 살아있는 동안 그 값도 살아있어 회수 불가 — 이게 누수. 명시적 remove가 유일한 방어.

Q. 스레드풀과 ThreadLocal이 왜 위험?

풀의 스레드는 여러 요청을 처리하며 재사용된다. 한 요청에서 set한 ThreadLocal 값을 정리하지 않으면 다음 요청이 그 값을 본다. 인증 정보 같은 민감한 데이터면 사용자 정보 유출 사고. 모든 요청의 시작/끝에서 set/clear를 반드시 페어링해야 한다.

Q. InheritableThreadLocal이 풀에서 안 되는 이유?

InheritableThreadLocal은 "새 스레드 생성 시점"에 부모 값을 복사한다. ThreadPoolExecutor는 스레드를 미리 만들어두고 재사용하므로, 나중에 작업을 submit할 때 부모 값이 자식 스레드로 전달되지 않는다. 작업 submit 시점에 전달이 필요하면 TransmittableThreadLocal 같은 라이브러리 필요.

Q. 실무에서 ThreadLocal 사용 패턴은?

요청 시작 지점(Filter, Interceptor)에서 set, 끝 지점에서 try-finally의 finally에서 clear. Spring Security의 SecurityContextHolder, SLF4J의 MDC가 모두 이 패턴. set과 clear를 페어링하지 않으면 누수와 데이터 오염 위험이 누적된다.

한 줄 정리

ThreadLocal의 두 큰 함정은 메모리 누수와 스레드풀 환경의 데이터 오염. 누수의 원인은 키(WeakRef)와 값(strong)의 비대칭. 풀 함정의 원인은 스레드 재사용. 방어는 단 하나 — set과 remove를 try-finally로 페어링. InheritableThreadLocal은 풀에서 동작 안 하므로 TransmittableThreadLocal 또는 ScopedValue를 검토.

ThreadLocal 시리즈는 여기까지. 다음은 Deadlock — 동시성의 또 다른 고전 함정.
