ThreadLocal의 정체

스레드마다 자기만의 값을 가지는 변수. 편리한 추상화이지만 그 아래 자료구조를 알아야 다음 편의 함정이 보인다.

풀려는 문제

여러 스레드가 같은 객체를 공유하면 동기화가 필요하다. synchronized, volatile, Atomic 등 동시성 도구의 출발점. 그런데 어떤 데이터는 처음부터 스레드별로 따로 관리되면 동기화가 필요 없어진다. 예를 들어 SimpleDateFormat은 thread-safe하지 않아 공유하면 깨지지만, 스레드마다 자기 인스턴스를 가지면 안전하다.

이 패턴을 자바 표준으로 추상화한 게 java.lang.ThreadLocal. 한 변수처럼 보이지만 각 스레드가 자기 인스턴스의 값을 따로 갖는 구조.

기본 사용

public class DateFormatter {

    private static final ThreadLocal<SimpleDateFormat> formatter =
        ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd"));

    public static String format(Date date) {
        return formatter.get().format(date);
    }
}

한 줄로 동기화 문제를 푼다. 스레드 A가 get()을 호출하면 A 전용 SimpleDateFormat이, 스레드 B가 호출하면 B 전용 인스턴스가 반환된다. 서로 다른 인스턴스라 같은 코드를 동시 실행해도 깨지지 않는다.

내부 구조 — Thread 객체에 매달린 자료구조

ThreadLocal이 어떻게 스레드별 분리를 달성하는가. 이름과 달리 ThreadLocal 인스턴스 자체가 값을 들고 있는 게 아니라, 각 Thread 객체 안에 ThreadLocalMap이라는 해시 자료구조가 있고 거기 키로 ThreadLocal 인스턴스, 값으로 그 스레드의 값이 저장된다.

핵심 포인트

  • 값은 Thread 객체 안에 저장 — 그 스레드만 자기 값을 본다
  • 키는 ThreadLocal 인스턴스 자체
  • 스레드가 살아있는 동안 그 스레드의 ThreadLocalMap도 살아있음
  • 스레드가 종료되면 해당 ThreadLocalMap도 GC 대상

이 구조 덕에 같은 ThreadLocal 변수에 대해 스레드마다 다른 값이 자연스럽게 분리된다. 단, 키-값이 Thread 안에 저장된다는 사실이 다음 편 누수 함정의 출발점.

주요 메서드

ThreadLocal<String> tl = new ThreadLocal<>();

tl.set("hello");      // 현재 스레드의 값 설정
String v = tl.get();  // 현재 스레드의 값 조회
tl.remove();          // 현재 스레드의 값 제거 (핵심)

ThreadLocal<String> withDefault = ThreadLocal.withInitial(() -> "default");
withDefault.get();    // 처음 호출 시 "default" 자동 설정 후 반환

withInitial

ThreadLocal.withInitial은 처음 get()이 호출될 때 자동으로 초기값을 만드는 패턴. set()을 명시적으로 안 해도 되어 코드가 짧아진다. 람다는 각 스레드의 첫 호출 시점에 그 스레드 컨텍스트에서 실행됨.

remove의 중요성

뒤에서 다시 강조하지만 미리 짚어둔다. remove()는 단순한 청소 메서드가 아니라 ThreadLocal 사용 시 가장 중요한 메서드. 메모리 누수와 스레드풀 함정의 핵심 방어선. "set은 항상 try-finally 안에 두고 finally에서 remove"가 안전한 패턴.

실무에서 자주 쓰이는 자리

1. SecurityContext / 인증 정보

public class UserContext {
    private static final ThreadLocal<User> current = new ThreadLocal<>();

    public static void set(User user) { current.set(user); }
    public static User get() { return current.get(); }
    public static void clear() { current.remove(); }
}

요청 처리 시작 지점(예: Servlet Filter)에서 인증된 User를 set하고, 요청 처리 중 어디서든 UserContext.get()으로 현재 사용자에 접근. 요청 처리 끝나면 clear로 정리. Spring Security의 SecurityContextHolder가 정확히 이 패턴.

2. 트랜잭션 컨텍스트

Spring의 TransactionSynchronizationManager는 ThreadLocal로 현재 트랜잭션 정보(Connection, 커밋/롤백 후크 등)를 관리한다. @Transactional이 있는 메서드 호출 시작 시 트랜잭션 정보를 ThreadLocal에 set, 그 안의 모든 코드가 같은 Connection을 공유하고, 메서드 끝나면 정리.

3. 로깅 컨텍스트 (MDC)

@Component
public class RequestIdFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        String requestId = UUID.randomUUID().toString();
        MDC.put("requestId", requestId);
        try {
            chain.doFilter(req, res);
        } finally {
            MDC.clear();
        }
    }
}

SLF4J/Logback의 MDC(Mapped Diagnostic Context)도 내부적으로 ThreadLocal 기반. 요청 시작 시 requestId 같은 키를 MDC에 넣으면 그 요청 처리 중 모든 로그에 자동 포함되어 분산 로그에서 한 요청의 흐름을 추적 가능.

4. Thread-unsafe 객체의 스레드별 분리

처음 예시인 SimpleDateFormat이 대표적. NumberFormat, Random(Java 7 이전), 일부 라이브러리의 객체. 단, 모던 자바는 ThreadLocalRandom 같은 thread-safe 대안을 제공하므로 직접 ThreadLocal로 감쌀 일이 줄었다. DateTimeFormatter는 thread-safe해서 ThreadLocal이 불필요.

왜 ThreadLocal이 메서드 매개변수보다 나을 때가 있는가

정직한 답은 "거의 없다"다. 매개변수로 전달하는 게 항상 더 명시적이고 안전. 그러나 다음 경우에 ThreadLocal이 합리적인 선택지가 된다.

  • 크로스컷팅 관심사 — 인증 정보, 트랜잭션, 로깅처럼 모든 메서드가 잠재적으로 필요할 수 있는 정보. 매번 매개변수로 받으면 시그니처가 폭발
  • 프레임워크 통합 — Spring, Servlet, Hibernate 같은 프레임워크가 이미 ThreadLocal 기반인 경우
  • 레거시 코드 — 매개변수 변경이 어려운 깊은 호출 체인에 정보를 주입해야 할 때

이 외 일반적인 데이터 전달은 매개변수가 옳다. ThreadLocal을 "전역 변수"처럼 쓰면 코드 추적이 어려워지고 다음 편의 함정에 걸린다.

구현 디테일 — 키의 WeakReference

ThreadLocalMap의 키(ThreadLocal 인스턴스 참조)는 WeakReference로 저장된다. 값은 strong reference. 이 비대칭이 다음 편 누수 함정의 핵심. 

// java.lang.ThreadLocal의 내부 구조 (간략화)
static class ThreadLocalMap {
    static class Entry extends WeakReference<ThreadLocal<?>> {
        Object value;
        Entry(ThreadLocal<?> k, Object v) {
            super(k);  // 키는 WeakReference
            value = v;  // 값은 strong reference
        }
    }
    Entry[] table;
}

이 비대칭 설계 의도는 ThreadLocal 인스턴스 자체가 GC된 경우 키는 자동으로 사라지게 하기 위함. 하지만 값은 여전히 strong reference라 명시적 remove 없이는 메모리에 남는다. 이게 다음 편의 출발점.

면접 단골 질문

Q. ThreadLocal이 어떻게 스레드별 분리를 달성?

ThreadLocal 인스턴스 자체에 값이 저장되는 게 아니라, 각 Thread 객체가 자기 ThreadLocalMap을 가지고 그 안에 키로 ThreadLocal, 값으로 그 스레드의 값을 저장한다. 그 스레드만 자기 Thread 객체에 접근하므로 자연스럽게 분리되며 동기화도 필요 없다.

Q. ThreadLocal의 용도는?

크로스컷팅 컨텍스트(인증 정보, 트랜잭션, 로깅 MDC), thread-unsafe 객체의 스레드별 분리. Spring의 SecurityContextHolder, TransactionSynchronizationManager, SLF4J의 MDC가 모두 ThreadLocal 기반. 일반 데이터 전달은 매개변수가 더 명시적이라 ThreadLocal은 신중히 사용.

Q. ThreadLocal에서 키와 값의 참조 관계는?

ThreadLocalMap의 Entry는 키(ThreadLocal 인스턴스)를 WeakReference로, 값을 strong reference로 가진다. ThreadLocal 인스턴스가 GC되면 키는 자동으로 사라지지만 값은 strong reference라 그대로 남는다. 이 비대칭이 메모리 누수의 원인 — 다음 편 주제.

Q. withInitial과 set의 차이?

withInitial은 ThreadLocal 생성 시 초기값 공급자(Supplier)를 등록. 처음 get() 호출 시점에 자동으로 람다가 실행되어 초기값 설정. set은 명시적으로 값을 넣는 메서드. 일반적으로 withInitial로 ThreadLocal을 만들고, 필요 시 set으로 변경하는 패턴이 깔끔.

한 줄 정리

ThreadLocal은 스레드마다 자기 값을 가지는 변수. 내부적으로 각 Thread 객체의 ThreadLocalMap에 키-값 형태로 저장된다. 크로스컷팅 정보(인증, 트랜잭션, 로깅)에 적합하고, Spring과 SLF4J가 광범위하게 사용. 단, 키는 WeakReference이고 값은 strong reference라는 비대칭이 다음 편 누수 함정의 출발점.
