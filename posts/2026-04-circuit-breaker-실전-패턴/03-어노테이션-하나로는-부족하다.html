기본 설정이 놓치는 것들

CircuitBreaker를 처음 붙이면 보통 이렇게 끝낸다.

@CircuitBreaker(name = "kakaoApi", fallbackMethod = "fallback")
public String send(String message) {
    return kakaoApi.send(message);
}

private String fallback(String message, Throwable t) {
    return "발송 실패 처리";
}

동작은 한다. 그런데 이 상태로 프로덕션에 올리면 세 가지 문제가 숨어있다.

  • 비즈니스 예외도 CircuitBreaker가 실패로 카운트한다
  • fallback에서 어떤 이유로 실패했는지 알 수 없다
  • CircuitBreaker가 OPEN됐을 때 아무도 모른다

문제 1: 비즈니스 예외도 실패로 카운트된다

카카오 API에서 발생하는 예외는 두 종류다.

인프라 예외: 서버 연결 실패, 타임아웃. 외부 시스템이 불안정하다는 신호다. CircuitBreaker가 실패로 카운트해야 맞다.

비즈니스 예외: 수신 거부, 발송 한도 초과. 서버는 살아있고 정상 응답을 준 것이다. CircuitBreaker가 카운트하면 안 된다.

기본 설정에서는 두 예외를 구분하지 않는다. 수신 거부 사용자가 몰려서 KakaoBizException이 쏟아지면 CircuitBreaker가 OPEN되어 정상 사용자 발송까지 막힌다.

설정으로 분리한다.

resilience4j:
  circuitbreaker:
    instances:
      kakaoApi:
        record-exceptions:
          - com.example.KakaoNetworkException   # 이건 실패로 카운트
        ignore-exceptions:
          - com.example.KakaoBizException       # 이건 카운트 제외

실험해보면 확연하다. KakaoBizException을 7번 던져도 bufferedCalls=0, CircuitBreaker는 CLOSED 상태 그대로다.

주의: ignoreExceptions는 CircuitBreaker 상태에만 영향이 없다. 예외 자체는 콜러에게 그대로 전파된다. 비즈니스 예외 처리는 서비스 레이어에서 별도로 해야 한다.

문제 2: 왜 실패했는지 fallback에서 알 수 없다

fallback이 하나면 어떤 이유로 실패했는지 구분이 안 된다. 네트워크 오류라면 DLQ에 적재해서 나중에 재처리해야 하고, CircuitBreaker가 OPEN 상태라면 대체 IDC로 라우팅해야 한다. 같은 "발송 실패"지만 대응이 완전히 다르다.

fallback 메서드는 예외 타입별로 오버로딩할 수 있다. Resilience4j는 가장 구체적인 타입부터 매칭한다. 

// 네트워크 오류 → DLQ 적재 (나중에 재처리)
private String sendFallback(String message, KakaoNetworkException e) {
    log.error("[FALLBACK] 네트워크 오류. DLQ 적재: {}", message);
    return "DLQ 적재 완료";
}

// CircuitBreaker OPEN → 대체 IDC 라우팅
private String sendFallback(String message, CallNotPermittedException e) {
    log.warn("[FALLBACK] CircuitBreaker 차단 중. 대체 IDC 시도");
    return "대체 IDC 발송 시도";
}

// 최후 보루
private String sendFallback(String message, Throwable t) {
    log.error("[FALLBACK] 알 수 없는 오류: {}", t.toString());
    return "관리자 확인 필요";
}

문제 3: CircuitBreaker가 OPEN됐을 때 아무도 모른다

CircuitBreaker가 OPEN되면 fallback이 조용히 처리한다. 로그를 뒤지기 전까지는 장애가 난 줄도 모른다. 프로덕션에서는 OPEN 순간 온콜 알림이 가야 한다.

getEventPublisher()로 상태 전이를 구독한다.

@PostConstruct
public void subscribe() {
    CircuitBreaker circuitBreaker = registry.circuitBreaker("kakaoApi");

    circuitBreaker.getEventPublisher().onStateTransition(event -> {
        CircuitBreaker.State toState = event.getStateTransition().getToState();

        if (toState == CircuitBreaker.State.OPEN) {
            log.error("!!! CircuitBreaker OPEN — 온콜 알림 발송 필요 !!!");
            // alertService.sendCritical("kakaoApi CircuitBreaker OPEN");
        }
        if (toState == CircuitBreaker.State.CLOSED) {
            log.info("CircuitBreaker CLOSED — 정상 복구");
            // alertService.sendResolved("kakaoApi CircuitBreaker CLOSED");
        }
    });

    // OPEN 직전 경고 (실패율 임계값 초과 시점)
    circuitBreaker.getEventPublisher().onFailureRateExceeded(event ->
        log.warn("실패율 임계값 초과: {}%", event.getFailureRate())
    );
}

구독할 수 있는 이벤트는 4가지다.

  • onStateTransition: 상태 전이 전부. 가장 중요.
  • onFailureRateExceeded: 실패율 임계값 초과 직후. OPEN 직전 경고.
  • onSlowCallRateExceeded: 느린 호출 임계값 초과.
  • onCallNotPermitted: OPEN 중 차단된 호출. 메트릭 카운팅용.

실전에서는 여기서 Prometheus Counter를 올리거나 PagerDuty 에스컬레이션을 건다. 상태 전이 이벤트 없이는 CircuitBreaker가 조용히 동작해서 오히려 더 위험하다.

다음 편에서는 @Retry와 @Bulkhead를 함께 쓸 때 왜 순서가 중요한지 다룬다.
