Saga가 푸는 문제

주문 → 결제 → 재고차감을 분산 환경에서 처리한다고 해봐요. 2PC는 비싸고 가용성을 해쳐요. 그렇다고 일관성을 완전히 포기할 순 없어요.

Saga 패턴의 발상은 단순해요. 각 서비스가 자기 로컬 트랜잭션만 처리하고, 그 결과를 다음 서비스에 전달해요. 만약 중간에 실패하면, 이전 단계들의 효과를 보상 트랜잭션으로 되돌려요.

Shipping에서 실패하면 Inventory 복구, Payment 환불, Order 취소 순으로 보상해요. 각 단계가 자기 로컬 트랜잭션이라 한 단계 실패가 전체를 멈추지 않아요. ACID처럼 깔끔하지 않지만 결과적으로 일관성을 회복해요.

두 가지 구현 방식

방식특징장단점
Choreography각 서비스가 이벤트를 발행·구독단순·자율 / 흐름 추적 어려움
Orchestration중앙 오케스트레이터가 순서 조율흐름 명확 / 단일 진입점 의존

Choreography (코레오그래피)

중앙 지휘자 없이 각 서비스가 이벤트를 통해 자율적으로 움직여요. 무대 안무처럼 각자 자기 역할을 알고 있어요. 

// OrderService
@Transactional
public void createOrder(Order order) {
    orderRepo.save(order);
    eventBus.publish(new OrderCreated(order.getId()));
}

// PaymentService: OrderCreated 구독
@EventListener
public void on(OrderCreated event) {
    try {
        paymentRepo.charge(event.userId, event.amount);
        eventBus.publish(new PaymentCharged(event.orderId));
    } catch (Exception e) {
        eventBus.publish(new PaymentFailed(event.orderId));
    }
}

// InventoryService: PaymentCharged 구독
@EventListener
public void on(PaymentCharged event) {
    try {
        inventoryRepo.decrease(event.productId, event.quantity);
        eventBus.publish(new InventoryReserved(event.orderId));
    } catch (Exception e) {
        // 실패. 보상 이벤트 발행
        eventBus.publish(new InventoryFailed(event.orderId));
    }
}

// OrderService: PaymentFailed/InventoryFailed 구독해서 보상
@EventListener
public void on(PaymentFailed event) {
    orderRepo.cancel(event.orderId);
}

각 서비스가 자기에게 관련된 이벤트를 듣고 자기 일을 하고 다음 이벤트를 발행해요. 보상 흐름도 같은 메커니즘이에요.

Choreography의 강점

  • 탈중앙: 단일 장애점이 없어요. 한 서비스가 죽어도 다른 서비스가 자기 큐의 이벤트를 처리해요.
  • 자율성: 각 팀이 자기 서비스에 자기 로직만 두면 돼요. 외부 의존이 적어요.
  • 느슨한 결합: 서비스가 이벤트만 알면 돼요. 누가 발행하는지, 누가 구독하는지 몰라요.

Choreography의 한계

  • 흐름 추적 어려움: 전체 트랜잭션 흐름이 코드 한 자리에 없어요. 디버깅 시 여러 서비스 로그를 모아야 해요.
  • 순환 의존 위험: 이벤트를 잘못 짜면 A→B→A 무한 루프에 빠져요.
  • 새 단계 추가 비용: 흐름 변경 시 여러 서비스를 동시에 수정해야 해요.

Orchestration (오케스트레이션)

중앙 오케스트레이터(Saga 코디네이터)가 흐름을 명령으로 지휘해요. 각 서비스는 명령을 받고 결과를 회신해요. 

// OrderSagaOrchestrator
public void execute(OrderSaga saga) {
    try {
        // 1. 주문 생성
        orderService.create(saga.order);

        // 2. 결제 청구
        paymentService.charge(saga.userId, saga.amount);

        // 3. 재고 차감
        inventoryService.decrease(saga.productId, saga.quantity);

        // 성공
        saga.markComplete();

    } catch (Exception e) {
        // 보상 (역순으로 호출)
        if (saga.passed("payment")) {
            paymentService.refund(saga.userId, saga.amount);
        }
        if (saga.passed("order")) {
            orderService.cancel(saga.orderId);
        }
        saga.markFailed();
    }
}

실제 운영에서는 상태 머신을 영속화해야 해요. 오케스트레이터가 중간에 죽어도 saga를 재개할 수 있도록. Camunda, Conductor, Temporal 같은 워크플로우 엔진이 이 자리를 위한 거예요.

Orchestration의 강점

  • 흐름 명확: saga 코드 한 자리에 전체 흐름. 읽기 쉬움.
  • 변경 단순: 흐름 변경은 saga 코드만 수정.
  • 관찰성: 각 saga 인스턴스의 진행 상태를 한 자리에서 추적.

Orchestration의 한계

  • 중앙화: 오케스트레이터가 단일 장애점이 돼요. 영속화와 고가용성이 필요해요.
  • 서비스 결합: 오케스트레이터가 모든 서비스 API를 알아야 해요.
  • 비대화 위험: 흐름이 많아지면 오케스트레이터가 "분산 모놀리스"가 될 수 있어요.

보상 트랜잭션 설계

Saga에서 가장 중요한 자리예요. 보상이 잘 짜여 있지 않으면 일관성 회복이 안 돼요.

1. 보상은 idempotent해야

네트워크 재시도나 중복 호출이 가능해요. 보상 트랜잭션을 두 번 호출해도 안전해야 해요. 예: refund(orderId, amount)는 이미 환불됐으면 그냥 무시(no-op)하는 게 안전.

2. 보상은 항상 가능해야

어떤 동작은 되돌릴 수 없어요. 외부에 이메일을 보냈으면 그걸 못 되돌려요. 보상이 불가능한 단계는 saga의 마지막에 두거나, "취소 이메일"을 보내는 식으로 대체 보상을 두세요.

3. 의미 있는 보상

Inventory를 차감했다가 보상으로 복구할 때, 그 사이 같은 상품이 매진됐을 수 있어요. 보상의 의미가 "원상복귀"가 아닐 수도 있어요. 비즈니스 관점에서 어떤 상태가 맞는지를 정의해야 해요.

실패 시나리오와 대응

  • 중간 단계 실패: 보상으로 복구해요. 일관성을 회복해요.
  • 보상 자체 실패: 재시도. 그래도 안 되면 인간 개입(dead letter queue, 알람).
  • 이벤트 유실: 메시지 브로커의 at-least-once 보장 + idempotent 처리.
  • 이벤트 중복: idempotent 처리로 같은 결과를 보장해요.
  • 이벤트 순서 뒤바뀜: 순서 의존 로직 회피, 또는 timestamp·version 검증.

Choreography vs Orchestration, 무엇을 골라야 하나

도메인의 복잡도에 따라 갈려요.

  • 3~5 단계 단순 흐름: Choreography. 이벤트 한두 개로 자연스럽게.
  • 5단계 이상, 분기 많음, 재시도 정책 복잡: Orchestration. 흐름을 한 자리에서 통제.
  • 여러 도메인이 한 흐름에 얽혀 있음: Orchestration. 책임 명확.
  • 각 단계가 독립적, 결합 최소화 목표: Choreography.
