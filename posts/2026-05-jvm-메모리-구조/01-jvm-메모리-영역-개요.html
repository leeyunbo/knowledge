전체 그림

JVM이 실행될 때 운영체제로부터 받는 메모리는 크게 세 종류로 나뉜다. 모든 스레드가 공유하는 영역, 스레드마다 따로 가지는 영역, 그리고 JVM 바깥의 native 메모리.

JVM Spec이 정의하는 5개 영역

Java Virtual Machine Specification (JVMS §2.5) 은 JVM 실행 시점에 존재하는 런타임 데이터 영역을 5개로 정의한다. Direct Memory는 spec에 없고 NIO 등이 사용하는 native 영역이다.

영역 스코프 용도 OOM 시 메시지
Heap 공유 객체와 배열 Java heap space
Method Area 공유 클래스 메타데이터, 상수 풀 Metaspace
JVM Stack 스레드별 메서드 호출 프레임 StackOverflowError
PC Register 스레드별 현재 실행 중인 JVM 명령어 주소 —
Native Method Stack 스레드별 JNI를 통한 native 코드 호출 StackOverflowError

Heap — 객체가 사는 곳

new로 만든 모든 객체와 배열이 들어가는 자리. 모든 스레드가 공유하기 때문에 동시성 이슈도 여기서 시작된다. GC가 도는 영역도 Heap이다. 

User user = new User("Alice");
int[] arr = new int[100];
String s = "hello";

위 세 줄에서 만들어진 User 인스턴스, int[] 배열, String 객체 모두 Heap에 자리 잡는다. 참조 변수(user, arr, s) 자체는 Stack에 살지만 가리키는 대상은 모두 Heap에 있다.

HotSpot JVM의 Heap은 다시 Young Generation과 Old Generation으로 나뉘고, Young은 Eden + Survivor 둘로 또 나뉜다. 이 세부 구조는 GC 동작과 직결되며 다음 편의 주제다.

Method Area / Metaspace — 클래스의 청사진

JVMS가 정의한 이름은 "Method Area"인데 HotSpot의 구현체는 Java 8부터 Metaspace로 불린다. 이 안에는 클래스 하나하나의 청사진이 들어간다. 필드와 메서드 목록, 상속 관계, 메서드의 바이트코드, 런타임 상수 풀, 어노테이션 정보까지 그 클래스를 실행에 옮기기 위해 필요한 메타데이터가 모여 있다.

JIT가 컴파일한 native 코드는 Metaspace가 아닌 별도의 Code Cache 영역에 저장된다. 기본 크기는 240MB 정도이고 가득 차면 JIT 최적화가 멈춰 성능이 점진적으로 떨어진다. -XX:ReservedCodeCacheSize로 조정.

Java 7까지는 PermGen(Permanent Generation)이라는 이름으로 Heap 안에 있었지만 Java 8에서 Heap 밖 native 메모리로 옮겨가며 Metaspace로 개명됐다. 크기가 동적으로 늘어날 수 있어 PermGen 시절 자주 보던 OutOfMemoryError: PermGen space가 기본적으로 사라졌다.

JVM Stack — 메서드 호출의 자리

스레드가 만들어질 때 함께 만들어지는 자기만의 스택. 메서드 하나가 호출될 때마다 스택 프레임(frame)이 push되고, 메서드가 끝나면 pop된다. 프레임 하나에는 그 메서드의 로컬 변수 배열, 연산용 피연산자 스택, 그리고 메서드가 속한 클래스의 런타임 상수 풀 참조가 함께 묶여 들어간다. 

void outer() {
    int x = 10;
    inner(x);
}

void inner(int n) {
    int y = n * 2;
}

outer()가 호출되면 outer의 프레임이 push되고 로컬 변수 x가 그 안에 자리 잡는다. 그 안에서 inner(x)를 호출하면 inner의 프레임이 또 push되고 n, y가 들어간다. inner가 리턴하면 inner 프레임이 pop되어 사라진다.

깊은 재귀나 무한 재귀로 프레임이 너무 많이 쌓이면 StackOverflowError가 발생한다. 스택 크기는 -Xss 옵션으로 조정할 수 있다 (기본 512KB ~ 1MB, 플랫폼별).

PC Register — 현재 어디 줄을 읽고 있는지

각 스레드가 "지금 실행 중인 JVM 명령어"의 주소를 보관하는 작은 레지스터. 스레드가 자바 메서드를 실행 중이면 그 메서드의 바이트코드 주소를 가리키고, native 메서드를 실행 중이면 정의되지 않은(undefined) 값이다.

OS의 컨텍스트 스위칭이 일어나도 각 스레드가 자기 PC Register를 가지고 있어 중단된 위치를 정확히 복원할 수 있다. 크기는 매우 작아 OOM 같은 문제가 발생하지 않는 영역.

Native Method Stack — JNI를 위한 별도 스택

C나 C++로 작성된 native 메서드를 호출할 때 사용되는 스택. JVM Stack과 별개로 존재해서 Java 코드와 native 코드의 호출 경로가 섞이지 않는다. HotSpot은 실제로는 둘을 통합 관리하지만 JVMS 모델상으로는 분리되어 있다.

JNI를 직접 쓸 일은 적지만 JDK 내부의 많은 부분(File I/O, Socket, 암호화 등)이 native 메서드를 호출하므로 모든 자바 프로그램에서 이 영역이 사용되고 있다.

Direct Memory — JVM Spec 바깥의 손님

JVM Spec이 정의하지 않는 영역이지만 NIO가 도입된 이후 실무에서 매우 중요해졌다. ByteBuffer.allocateDirect()로 할당하면 JVM 힙이 아닌 native 메모리에 버퍼가 만들어진다. 

ByteBuffer heapBuffer = ByteBuffer.allocate(1024);          // Heap
ByteBuffer directBuffer = ByteBuffer.allocateDirect(1024);  // Off-heap

왜 Heap 밖에 두는가? OS의 I/O 함수가 Java 힙의 객체를 직접 읽고 쓸 수 없기 때문. Heap 안의 ByteBuffer로 read/write하면 JVM이 native 버퍼로 한 번 복사한 뒤 OS에 전달한다. Direct Memory를 쓰면 그 복사가 사라져 I/O 성능이 좋아진다.

단점은 GC 대상이 아니라 -Xmx의 한도와 무관하게 메모리를 잡아먹는다는 점. -XX:MaxDirectMemorySize로 한도를 두지 않으면 OS 메모리 전체를 잠식할 수 있다. 4편에서 자세히 다룬다.

OOM 메시지로 영역 식별

운영 중 OOM이 떴을 때 어떤 영역이 부족한지는 메시지로 구분한다. 어느 영역인지 알아야 처방이 다르다.

OOM 메시지 영역 주요 원인
Java heap space Heap 객체 누수, 너무 큰 컬렉션
GC overhead limit exceeded Heap GC가 시간만 쓰고 메모리 회수 거의 못함
Metaspace Metaspace 클래스 로더 누수, 동적 클래스 생성 폭주
Direct buffer memory Direct Memory NIO 버퍼 누수, MaxDirectMemorySize 부족
unable to create new native thread Native 스레드 너무 많이 생성, ulimit 도달
StackOverflowError JVM Stack 깊은 재귀, 무한 재귀

면접 단골 질문

Q. JVM 메모리 영역을 설명하라

Heap, Method Area(Metaspace), JVM Stack, PC Register, Native Method Stack 5개가 JVMS 정의 영역. 실무에서는 Direct Memory도 함께 본다. Heap과 Metaspace는 모든 스레드 공유, 나머지 셋은 스레드별로 따로 가진다.

Q. PermGen이 Metaspace로 바뀐 이유?

PermGen은 Heap 안의 고정 크기 영역이라 동적 클래스 로딩이 많은 환경에서 OutOfMemoryError: PermGen space가 흔했다. Java 8에서 Heap 밖 native 메모리로 옮겨 동적으로 늘어날 수 있게 만들고 Metaspace로 개명했다. 한도는 -XX:MaxMetaspaceSize로 명시 가능, 명시 안 하면 가용 native 메모리만큼.

Q. 객체와 참조 변수는 어디에 저장되나?

객체 자체는 Heap에. 그 객체를 가리키는 참조 변수가 메서드 안의 로컬 변수면 JVM Stack의 프레임에, 다른 객체의 필드면 그 객체와 함께 Heap에, static 필드면 클래스 객체와 함께 Metaspace에 위치한다.

Q. Direct Memory는 GC 대상인가?

GC 대상이 아니다. Heap이 아닌 native 메모리에 있기 때문에 -Xmx와 무관하게 잡아먹는다. DirectByteBuffer를 가리키는 Java 참조가 GC되면 그제서야 Cleaner 매커니즘으로 native 메모리가 해제된다. 참조가 살아있는 동안은 계속 점유되므로 누수 위험이 크다.

한 줄 정리

JVM은 자바 프로세스가 잡은 메모리를 Heap, Metaspace, JVM Stack, PC Register, Native Method Stack 5개로 나누고 NIO 등이 쓰는 Direct Memory를 native 메모리에서 별도로 사용한다. 공유되는 영역(Heap, Metaspace)에서는 동시성과 GC가 중요하고, 스레드별 영역(Stack 등)은 호출/실행 흐름을 추적한다.

가장 많은 질문이 쏟아지는 곳은 Heap이다. 다음 편은 Heap 안으로 들어가서 Young Generation의 Eden과 Survivor, Old Generation, TLAB 같은 디테일을 본다.
