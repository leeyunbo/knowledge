스레드별로 따로인 이유

스레드 하나가 메서드 A를 실행하다가 컨텍스트 스위칭으로 멈추고, 다른 스레드가 메서드 B를 실행한다고 하자. B가 끝난 뒤 다시 A가 재개되려면 A가 멈춘 지점, 그 시점의 로컬 변수, 호출 스택이 모두 보존되어 있어야 한다.

이 세 가지 정보가 스레드마다 별도로 보관되어야 하는 이유. 공유 영역(Heap, Metaspace)은 동시 접근 보호가 필요하지만, 스레드별 영역은 본인만 쓰니 동기화가 필요 없다.

JVM Stack — 메서드 호출의 자리

스레드가 만들어질 때 함께 생성되는 자기만의 스택. 메서드가 호출될 때마다 스택 프레임(frame)이 push되고, 메서드가 종료되면 pop된다. 마지막 메서드의 프레임만 active이며, 그 위에 새 프레임이 쌓이거나 끝나서 사라지는 구조.

스택 프레임의 구성

한 프레임은 세 부분으로 이뤄져 있다 (JVMS §2.6). 로컬 변수와 매개변수가 저장되는 Local Variables 배열, JVM 명령어가 연산할 때 사용하는 Operand Stack, 그리고 메서드가 속한 클래스의 런타임 상수 풀 참조 같은 부가 정보를 담은 Frame Data.

예제로 보는 프레임 흐름

int outer() {
    int x = 10;
    int y = inner(x);
    return x + y;
}

int inner(int n) {
    int z = n * 2;
    return z;
}

① outer가 호출되면 outer 프레임이 만들어지고 x = 10이 기록된다.
② inner(x) 호출 시 inner 프레임이 push되고 n = 10으로 매개변수가 복사된다. inner 안의 로컬 변수 z도 그 프레임에 자리 잡는다.
③ inner가 리턴하면 inner 프레임은 pop되어 사라지고, 리턴값이 outer의 y에 들어간다.

참조 변수와 객체의 자리

void method() {
    User user = new User("Alice");
}

User 객체는 Heap에 만들어진다. 그 객체를 가리키는 참조 변수 user는 method의 스택 프레임 안 Local Variables 배열에 저장된다. 메서드가 끝나면 user 변수는 사라지고, 그 객체를 가리키는 다른 참조가 없으면 Heap의 객체는 GC 대상이 된다.

StackOverflowError

스택 크기가 한정되어 있으니 프레임이 너무 많이 쌓이면 터진다. 

void recursive() {
    recursive();
}

recursive();   // StackOverflowError

호출 깊이가 수만 정도까지 가면 발생. 정확한 한계는 스택 크기와 프레임당 메모리 사용량(로컬 변수 수 등)에 따라 다르다. 기본 스택 크기는 플랫폼마다 다르며 보통 512KB~1MB. -Xss 옵션으로 조정한다 (예: -Xss2m).

꼬리 재귀 최적화(TCO)는 자바에 없으므로 깊은 재귀는 항상 위험. 깊이가 클 수 있는 알고리즘은 명시적 스택(Deque)으로 변환하는 게 안전.

PC Register — 다음에 읽을 명령어 주소

각 스레드가 가지는 작은 레지스터로, 현재 실행 중인 JVM 명령어의 주소를 보관한다. OS 수준의 PC(Program Counter)와 비슷한 개념의 JVM 버전. 스레드가 자바 메서드를 실행 중이면 그 메서드의 바이트코드 주소를 가리키고, native 메서드를 실행 중이면 정의되지 않은 값이 들어가 있다. 컨텍스트 스위칭이 일어나도 각 스레드가 자기 PC Register를 들고 있으니 중단된 위치를 정확히 복원할 수 있다.

크기가 매우 작아 OOM 같은 문제가 발생하지 않는 영역. 개발자가 직접 다룰 일도 거의 없지만 "스레드가 어떻게 실행 위치를 기억하는가"의 답이 여기 있다.

Native Method Stack — JNI 호출용 별도 스택

C나 C++로 작성된 native 메서드를 호출할 때 사용되는 스택. JVM Stack과 별개로 존재해 자바 호출 흐름과 native 호출 흐름이 모델상 분리된다. 

public class FileInputStream {
    private native int read0() throws IOException;
}

native 키워드가 붙은 메서드를 호출하면 JVM Stack에서 Native Method Stack으로 흐름이 넘어간다. OS의 read 시스템 콜, 암호화 라이브러리, 그래픽 라이브러리 등 자바가 아닌 코드가 거의 모두 이 경로를 탄다.

HotSpot은 실제로는 JVM Stack과 Native Method Stack을 통합 관리하지만 JVMS 모델상으로는 분리되어 있다. 여기서도 깊은 호출은 StackOverflowError를 일으킬 수 있다.

스레드 생성 비용 — 잊기 쉬운 부분

새 스레드 하나를 만들 때 JVM Stack과 Native Method Stack이 함께 만들어진다. 기본 1MB짜리 스택을 두 종류 잡으니 스레드 하나당 수 MB가 native 메모리에서 잡힌다.

그래서 스레드를 무제한으로 만들려고 하면 OS의 가상 메모리 한계 또는 ulimit에 부딪쳐 OutOfMemoryError: unable to create new native thread가 발생한다. 이는 Heap 부족이 아니라 OS 수준 제약. -Xmx를 늘려도 해결되지 않는다.

해결 방향

  • 새 스레드를 만들지 말고 ThreadPool로 재사용
  • I/O 위주 워크로드는 Reactive 또는 Java 21+의 Virtual Thread로
  • OS 한도(ulimit -u, /proc/sys/kernel/threads-max)와 애플리케이션 한도를 같은 선에서 점검

Virtual Thread (Java 21+)

기존의 OS 스레드가 가진 두꺼운 스택의 부담을 줄이기 위해 Java 21에서 정식화된 가상 스레드. 자바 레벨의 가벼운 스레드가 OS 스레드 위에 multiplex되며, 스택은 동적으로 늘어나는 segment 형태로 Heap에 저장된다.

Virtual Thread는 수만 개를 만들어도 OS 스레드를 그만큼 잡지 않는다. 전통적인 Thread는 OS 스레드 1:1 매핑이라 1만 개를 만들면 1만 개의 OS 스레드가 만들어지는 것과 대조적. 별도 시리즈에서 깊게 다룰 주제.

면접 단골 질문

Q. 스택은 왜 스레드마다 따로 가지나?

스레드 각자가 독립적인 호출 흐름을 가지기 때문. 메서드 호출 시점의 로컬 변수와 매개변수, 돌아갈 위치 등을 자기만의 공간에 보관해야 다른 스레드와 섞이지 않는다. 공유 영역과 달리 동기화가 필요 없다는 부수 효과도 있다.

Q. 객체와 참조 변수는 각각 어디에?

객체(인스턴스, 배열)는 항상 Heap에. 그 객체를 가리키는 참조 변수가 메서드의 로컬 변수면 JVM Stack의 프레임에, 다른 객체의 필드면 그 객체와 함께 Heap에, static 필드면 클래스 객체와 함께 Metaspace에 위치한다.

Q. StackOverflowError와 OutOfMemoryError의 차이?

StackOverflowError는 한 스레드의 JVM Stack이 너무 깊어졌을 때 (보통 무한 재귀). OutOfMemoryError는 Heap, Metaspace, Direct Memory, Native Thread 등 영역의 메모리가 부족할 때. 전자는 알고리즘 문제, 후자는 메모리 또는 누수 문제로 접근하면 된다.

Q. unable to create new native thread는 왜 뜨나?

새 스레드를 만들 때 native 메모리에서 스택을 잡지 못해 발생. Heap 부족과 무관하다. 원인은 보통 스레드 폭주(ThreadPool 미사용), OS의 ulimit 한계, 너무 큰 -Xss로 스택 하나당 비용이 높을 때.

한 줄 정리

스레드별 영역은 셋. JVM Stack은 메서드 호출 프레임, PC Register는 다음 실행 명령어 주소, Native Method Stack은 JNI 경로의 호출 스택. 모두 스레드 생성 시 함께 만들어지고 종료 시 함께 사라진다.

스레드 수가 많아지면 이 영역들이 native 메모리를 점점 잡아먹어 OS 한계에 부딪친다. ThreadPool, Reactive, Virtual Thread 같은 패턴이 이 문제를 풀려는 시도. 마지막 편은 Off-heap — NIO와 Direct Memory가 만드는 또 다른 메모리 영역.
