Off-heap — Direct Memory와 NIO

JVM Spec 바깥의 메모리 영역. NIO 도입 후 실무에서 매우 중요해졌고 GC가 닿지 않아 누수 위험이 가장 큰 자리.

Off-heap이란

Heap, Metaspace, Stack 같은 JVM이 관리하는 영역과 별개로, 자바 코드가 사용하지만 JVM 힙 밖의 native 메모리에 존재하는 영역을 통틀어 off-heap이라 한다. 대표적인 것이 NIO의 Direct Memory.

off-heap은 JVMS가 정의하지 않는다. 따라서 -Xmx가 정한 최대 Heap 크기와 무관하게 잡히고, GC가 자동으로 회수해주지 않는다. 개발자가 라이프사이클을 명확히 이해해야 누수 없이 사용 가능.

왜 off-heap이 필요한가 — I/O 복사 비용

OS의 read/write 같은 native 함수는 자기가 관리하는 메모리 주소만 인자로 받을 수 있다. 그런데 자바 Heap의 객체는 GC가 위치를 마음대로 옮길 수 있어 안정된 주소를 보장 못 한다. 그래서 Heap의 ByteBuffer로 I/O를 하려면 JVM이 한 번의 우회를 거쳐야 한다.

  1. JVM이 Heap 안의 ByteBuffer 데이터를 native 임시 버퍼로 복사
  2. 그 native 버퍼 주소를 OS 함수에 넘김
  3. OS가 read/write를 실제 수행
  4. read의 경우 native 버퍼 → Heap 버퍼로 다시 복사

매번 한 번의 추가 복사가 발생하는 셈. 큰 데이터(파일 전송, 네트워크 버퍼 등)에서는 무시할 수 없는 비용이다. Direct ByteBuffer를 쓰면 처음부터 native 메모리에 버퍼를 두므로 이 복사가 사라진다.

DirectByteBuffer의 동작

ByteBuffer heap = ByteBuffer.allocate(1024);          // Heap
ByteBuffer direct = ByteBuffer.allocateDirect(1024);  // Off-heap

direct.putInt(0xCAFEBABE);
direct.flip();
fileChannel.write(direct);   // 복사 없이 바로 OS로

allocateDirect는 native 메모리를 malloc으로 잡고 그 주소를 DirectByteBuffer라는 작은 자바 객체가 들고 있는 형태. 자바 객체 자체는 Heap에 살지만 데이터는 off-heap에 있다.

DirectByteBuffer는 어떻게 native 메모리를 해제하나

Java 객체가 GC되면 native 메모리도 함께 해제되어야 한다. DirectByteBuffer는 생성 시점에 Cleaner(내부적으로 PhantomReference 기반)를 함께 등록해두고, 객체가 GC 대상이 되는 순간 Cleaner의 clean()이 호출되어 native 메모리를 free한다. 정리하면 native 메모리 해제는 참조하는 자바 객체가 GC되어야 일어나는 셈.

여기서 함정이 하나 생긴다. 자바 객체에 GC 압박이 약하면 native 메모리가 오래 잡혀 있을 수 있다는 것. Heap은 여유 있어 보이는데 native 메모리만 부족한 상황이 발생할 수 있다. 명시적으로 비우려면 Java 9+에서 cleaner.clean()을 호출하는 방법이 있다. Unsafe를 통한 수동 해제도 가능하지만 권장되지 않는다 (Java 8까지는 sun.misc.Unsafe, Java 9+부터는 jdk.internal.misc.Unsafe로 모듈 캡슐화).

MaxDirectMemorySize

Direct Memory의 한도를 명시하는 옵션. 미지정 시 OpenJDK는 내부적으로 Runtime.maxMemory() 근사치를 사용 — 실질적으로 -Xmx 수준. 한도를 넘으면 OutOfMemoryError: Direct buffer memory가 발생한다. 

java -Xmx2g -XX:MaxDirectMemorySize=512m MyApp

한도 설정 없이 두면 -Xmx만큼 잡을 수 있어 OS 메모리의 두 배까지 잡아먹는 셈이 된다. 명시적으로 한도를 두는 게 안전.

Memory-Mapped File — 파일을 메모리처럼

NIO의 또 다른 off-heap 사용처. FileChannel.map으로 파일을 메모리 주소에 매핑한다. OS의 mmap 시스템 콜을 활용. 

FileChannel ch = FileChannel.open(path, READ, WRITE);
MappedByteBuffer mb = ch.map(FileChannel.MapMode.READ_WRITE, 0, ch.size());

mb.putLong(0, 12345L);   // 파일 첫 8바이트에 직접 기록

OS는 매핑된 영역을 페이지 단위로 lazy하게 메모리에 올리고, 다른 페이지가 필요할 때 디스크와 swap한다. GB 단위 큰 파일도 일부만 메모리에 두고 처리할 수 있어 DB, 검색엔진, 메시지 큐 등이 활용.

장점과 함정

  • 장점: 큰 파일을 read/write 시스템 콜 없이 메모리 접근 속도로 다룸
  • 함정 1: GC와 무관하게 OS 페이지 캐시 사용. top에서 RES가 크게 보임
  • 함정 2: MappedByteBuffer도 Cleaner 기반 해제. 명시적 unmap이 어려움
  • 함정 3: 파일이 작으면 mmap 오버헤드가 일반 read보다 클 수 있음 (보통 수 MB 이상에서 이득)

Native Memory Tracking (NMT)

off-heap을 비롯한 JVM 외부 메모리를 추적하는 도구. 기본 비활성화이며 옵션을 켜야 동작. 

java -XX:NativeMemoryTracking=summary MyApp
jcmd <pid> VM.native_memory summary

출력에 Heap, Class(Metaspace), Thread, Code, GC 등 영역별 reserved/committed 값이 나온다. Direct Memory는 별도로 보이지 않고 "Other" 영역에 합산되거나 NIO 사용량을 코드 수준에서 추적해야 한다. BufferPoolMXBean으로 자바 레벨 모니터링도 가능. 

import java.lang.management.ManagementFactory;
import java.lang.management.BufferPoolMXBean;

for (BufferPoolMXBean pool : ManagementFactory.getPlatformMXBeans(BufferPoolMXBean.class)) {
    System.out.println(pool.getName() + " count=" + pool.getCount()
        + " mem=" + pool.getMemoryUsed());
}
// direct count=12 mem=131072
// mapped count=2 mem=4194304

off-heap 누수의 흔한 시나리오

시나리오 1 — DirectByteBuffer를 캐시에 쌓음

요청마다 큰 Direct ByteBuffer를 만들고 캐시에 넣어두면 자바 객체 참조가 살아있어 GC 못 함. Heap은 여유 있어 보이지만 native 메모리는 계속 차오름. 결국 OutOfMemoryError: Direct buffer memory.

시나리오 2 — JNI 라이브러리의 native 누수

JNI를 통해 호출한 C 라이브러리가 자체적으로 native 메모리를 잡고 free하지 않으면 JVM은 그 사실을 알지 못한다. 자바 코드는 멀쩡한데 OS에서 보면 RSS가 끝없이 늘어남. NMT, valgrind, jemalloc heap profile 등으로 추적해야 한다.

시나리오 3 — Netty의 PooledByteBufAllocator

고성능 네트워크 라이브러리는 ByteBuffer를 풀에 모아둠. 풀의 한도와 누수 감지 옵션을 모르면 off-heap을 무한히 점유. -Dio.netty.leakDetection.level=PARANOID 같은 옵션이 도움.

면접 단골 질문

Q. Direct Memory와 Heap의 차이?

Heap은 JVM이 관리하는 메모리 영역으로 GC 대상이고 -Xmx 한도 안에 있다. Direct Memory는 JVM 힙 밖의 native 메모리로 GC가 자동 회수하지 않으며, OS와의 I/O 시 복사 없이 직접 사용 가능해 NIO에서 활용한다.

Q. DirectByteBuffer의 native 메모리는 언제 해제되나?

참조하는 자바 객체(DirectByteBuffer)가 GC될 때 Cleaner 메커니즘으로 해제. 즉 GC 압박이 약하면 native 메모리가 오래 잡혀 있을 수 있다. 명시적 해제는 Java 9+의 cleaner.clean() 또는 Unsafe 사용으로 가능하나 권장되지 않음.

Q. -Xmx를 충분히 줬는데 왜 OOM이 나나?

OOM의 종류를 봐야 한다. Direct buffer memory 메시지면 Direct Memory 부족으로 -XX:MaxDirectMemorySize를 늘려야 한다. Metaspace면 클래스 누수 의심. unable to create new native thread면 OS 한계. -Xmx는 Heap 한도일 뿐이라 다른 영역 OOM은 별도 처방이 필요.

Q. Memory-Mapped File을 언제 쓰나?

GB 단위 큰 파일을 일부만 효율적으로 다루어야 할 때. OS의 페이지 캐시를 활용하므로 random access가 많은 워크로드(DB 인덱스, 로그 파일 검색)에 적합. 작은 파일에는 일반 read/write가 더 빠를 수 있다.

한 줄 정리

off-heap = JVM 힙 밖의 native 메모리. Direct ByteBuffer와 MappedByteBuffer가 대표 사용처. GC가 자동 회수하지 않아 누수 위험이 가장 크고, -Xmx와 별개로 OS 메모리를 잡아먹는다. NIO 기반 라이브러리(Netty, Kafka 클라이언트 등)를 쓰면 무의식적으로 사용하게 되므로 한도와 모니터링이 필수.

JVM 메모리 시리즈는 여기까지. 다음은 동시성으로 돌아가서 volatile과 JMM의 happens-before 규칙으로 들어간다.
