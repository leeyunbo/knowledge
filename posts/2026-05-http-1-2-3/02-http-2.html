HTTP/2 — 멀티플렉싱과 HPACK

한 연결에서 여러 요청을 동시에. 텍스트에서 바이너리로. HTTP/2가 1.1의 한계를 어떻게 깼는지 봐요.

HTTP/2의 출발

2015년 RFC 7540으로 표준화됐어요. 출발점은 구글의 SPDY 프로토콜이고, 그게 HTTP/2로 IETF에 흡수됐어요. 목표는 단순했어요. HTTP/1.1의 의미를 그대로 두면서 전송 효율을 올리자는 거였어요.

그래서 HTTP의 메서드, 헤더, 상태코드, URL 같은 의미는 모두 동일해요. 바뀐 건 wire 위에 데이터가 어떻게 흐르는지, 그 부분만이에요. 개발자 입장에서는 거의 투명하게 1.1에서 2로 갈 수 있어요.

핵심 변화 4가지

HTTP/2를 정의하는 핵심 개선이 네 가지 있어요.

  1. 바이너리 프레이밍 (Binary Framing)
  2. 멀티플렉싱 (Multiplexing)
  3. HPACK 헤더 압축
  4. 서버 푸시 (Server Push)

하나씩 봐볼게요.

1. 바이너리 프레이밍

HTTP/1.1은 텍스트 기반이에요. GET /index.html\r\n 같은 줄을 직접 파싱해야 해요. 공백, 줄바꿈, 대소문자 같은 미묘한 처리에 취약하고, 파싱 자체도 효율적이지 않아요.

HTTP/2는 통신 단위를 프레임이라는 바이너리 단위로 바꿨어요. 프레임 헤더는 정확히 9바이트, 그 뒤에 페이로드가 따라와요. 

+-----------------------------------------------+
|                 Length (24)                   |
+---------------+---------------+---------------+
|   Type (8)    |   Flags (8)   |
+-+-------------+---------------+-------------------------------+
|R|                 Stream Identifier (31)                      |
+=+=============================================================+
|                   Frame Payload (0...)                      ...
+---------------------------------------------------------------+

주요 프레임 타입

  • HEADERS: 요청/응답 헤더 (HPACK 압축)
  • DATA: 응답 본문, 요청 body
  • SETTINGS: 연결 파라미터 협상
  • WINDOW_UPDATE: 흐름 제어
  • RST_STREAM: 스트림 강제 종료
  • GOAWAY: 연결 종료 신호
  • PING: 연결 살아있는지 확인

프레임을 단위로 통신하니 다음에 볼 멀티플렉싱이 가능해져요.

2. 멀티플렉싱 — 핵심 중의 핵심

가장 큰 변화예요. 한 TCP 연결에서 여러 요청과 응답이 동시에 흐를 수 있어요. 어떻게 가능한가? 각 요청과 응답이 독립적인 스트림(Stream)이라는 가상 채널로 분리되거든요.

스트림과 프레임의 관계

  • 한 TCP 연결 안에 여러 스트림이 동시에 존재
  • 각 스트림은 고유한 ID를 가짐
  • 요청 하나, 응답 하나가 한 스트림
  • 프레임마다 자기가 속한 stream ID가 적혀 있어요

그래서 클라이언트와 서버 모두 프레임이 도착하면 그 ID로 어느 스트림 데이터인지 즉시 알 수 있어요.

HOL blocking 일부 해결

HTTP 레벨에서는 head-of-line blocking이 사라졌어요. 한 요청의 응답이 늦어도 다른 요청들은 그것과 무관하게 진행돼요. 1편에서 본 1.1의 가장 큰 문제가 풀린 거예요.

단, TCP 레벨의 HOL blocking은 여전히 남아 있어요. 이건 HTTP/3에서 해결되는 부분이라 다음 편에서 자세히.

3. HPACK 헤더 압축

HTTP/1.1 요청은 헤더가 자주 비대해요. 쿠키, User-Agent, Accept 헤더만 모아도 수 KB. 그런데 같은 클라이언트가 같은 사이트로 보내는 요청들은 헤더가 거의 동일해요. 매번 같은 정보를 반복 전송하는 건 낭비예요.

HTTP/2의 HPACK은 이 낭비를 줄이는 헤더 전용 압축 알고리즘이에요. 두 가지 기법을 결합해요.

정적 테이블

자주 쓰이는 헤더 이름과 값 조합 61개가 미리 인덱스로 정의돼 있어요. 예를 들어 :method = GET은 인덱스 2번. 그래서 GET 요청은 헤더 한 줄을 한 바이트로 표현할 수 있어요.

동적 테이블

연결 동안 사용된 헤더를 동적으로 인덱스에 추가해요. 첫 요청에서 User-Agent: Mozilla/5.0...이 나오면 인덱스 62번에 등록. 다음 요청에선 같은 헤더가 인덱스 한 바이트로 표현돼요.

Huffman 코딩

새로 보내는 값은 Huffman 코딩으로 비트 단위로 압축해요. ASCII 문자별로 빈도 기반 가변 길이 코드. UTF-8 영어 텍스트 기준 약 25% 압축 효과.

왜 gzip이 아니고 HPACK?

gzip 같은 일반 압축은 HTTP/1.1에서 응답 본문에 쓰여요. 이걸 헤더에도 쓰면 안 되나? 안 돼요. CRIME, BREACH 같은 공격이 가능했어요. 압축 비율을 관찰해서 비밀 정보(쿠키 토큰 등)를 추측하는 사이드채널 공격이에요.

HPACK은 처음부터 이 공격에 안전하도록 설계됐어요. Huffman 코딩은 정적이고, 동적 테이블은 헤더 이름 단위라 비밀 값 비교가 안 돼요.

4. 서버 푸시

클라이언트가 요청하기 전에 서버가 자원을 미리 보내는 메커니즘이에요. 예를 들어 index.html 요청이 들어오면 서버는 그 페이지가 style.css도 필요할 거라고 예측해서 함께 푸시. 클라이언트는 HTML을 파싱하고 CSS 요청을 보내기 전에 이미 받아놓은 셈이에요.

실무에서 잘 안 쓰여요

이론적으로는 멋진데 현실에서는 잘 동작하지 않았어요.

  • 클라이언트 캐시에 이미 있는 자원도 서버가 푸시해서 트래픽 낭비
  • 클라이언트가 어떤 자원을 가지고 있는지 서버가 정확히 알기 어려움
  • 실측에서 성능 향상이 미미하거나 오히려 손해
  • 크롬은 2022년에 서버 푸시 지원을 deprecate

대안으로 103 Early Hints + preload 헤더 패턴이 부상하고 있어요. 서버가 "이 자원을 먼저 받아두라"고 힌트만 주고 클라이언트가 결정하게 하는 방식이라 더 안전해요.

HTTP/2의 또 다른 디테일

스트림 우선순위

클라이언트가 어느 자원이 더 중요한지 서버에 알릴 수 있어요. 예를 들어 CSS는 우선순위 높게, 광고 이미지는 낮게. 서버가 우선순위에 따라 프레임을 어떻게 섞을지 결정해요.

흐름 제어

연결과 스트림 단위로 윈도우 기반 흐름 제어가 있어요. 한 스트림이 데이터를 너무 빨리 보내서 받는 쪽이 처리 못하는 상황을 막아요. TCP의 흐름 제어와 비슷한 개념인데 HTTP 레벨에서 또 한 번 적용돼요.

보안

기술적으로 HTTP/2는 평문(h2c)도 정의돼 있지만, 모든 브라우저가 TLS 위에서만 HTTP/2를 지원해요. 그래서 실무에선 HTTPS == HTTP/2 위에서 가능 같은 인식이 자리잡았어요. ALPN 확장으로 TLS handshake 중 HTTP 버전을 협상해요.

HTTP/2의 한계 — TCP HOL blocking

HTTP/2가 HTTP 레벨의 HOL blocking은 풀었지만, 더 아래층의 TCP 자체의 HOL blocking은 여전히 남았어요. TCP는 데이터를 순서대로 전달해야 하기 때문에, 패킷 하나가 유실되면 그 뒤 패킷이 도착해도 응용 계층에 전달하지 않아요. 재전송으로 그 패킷이 채워질 때까지 모두 기다려요.

HTTP/2가 한 연결로 멀티플렉싱하니까 이 효과가 더 두드러져요. 한 스트림의 패킷이 유실되면 무관한 다른 스트림의 데이터까지 모두 막혀요. 연결을 여러 개 두는 1.1보다 오히려 못한 상황이 생길 수도 있어요.

이게 HTTP/3가 풀려는 핵심 문제예요. TCP 자체를 버리고 UDP 위에 새 프로토콜을 올린 이유죠. 다음 편에서 자세히 봐요.

면접 단골 질문

Q. HTTP/2가 1.1과 가장 다른 점은요?

멀티플렉싱이에요. 1.1은 한 연결에서 한 번에 한 요청만 처리할 수 있었지만, HTTP/2는 한 연결 안에 여러 스트림을 두고 요청·응답을 동시에 흐르게 해요. 각 프레임에 stream ID가 붙어 있어서 어떤 요청에 속한 데이터인지 구분할 수 있고요.

Q. HPACK이 뭔가요?

HTTP/2의 헤더 압축 알고리즘이에요. 정적 테이블(자주 쓰이는 헤더 61개), 동적 테이블(연결 동안 학습된 헤더), Huffman 코딩 셋을 결합해서 헤더 크기를 크게 줄여요. 같은 클라이언트의 반복 요청에서 헤더가 거의 무료에 가까워져요. gzip 같은 일반 압축으로는 CRIME/BREACH 사이드채널 공격이 가능해서 안전한 전용 알고리즘이 필요했어요.

Q. HTTP/2의 서버 푸시가 왜 잘 안 쓰여요?

이론적으론 좋은데 실무에서 효과가 미미했어요. 클라이언트가 이미 캐시에 가진 자원도 서버가 푸시해서 트래픽 낭비, 서버가 클라이언트 상황을 정확히 알기 어려운 한계 때문이에요. 크롬은 2022년에 서버 푸시 지원을 deprecate했고, 대안으로 103 Early Hints + preload 패턴이 부상 중이에요.

Q. HTTP/2도 HOL blocking이 있나요?

HTTP 레벨은 해결됐지만 TCP 레벨은 여전해요. TCP는 패킷 순서대로만 전달하기 때문에, 한 패킷이 유실되면 그 뒤 모두 막혀요. HTTP/2가 멀티플렉싱으로 한 연결에 여러 스트림을 묶으니, 한 스트림 패킷 유실이 다른 스트림까지 막는 부작용이 있어요. 이걸 풀려고 HTTP/3가 TCP 대신 UDP 기반 QUIC를 사용해요.

한 줄 정리

HTTP/2는 한 연결 안에 여러 스트림을 두는 멀티플렉싱으로 1.1의 head-of-line blocking을 풀었어요. 바이너리 프레이밍으로 효율적 파싱, HPACK으로 헤더 압축, 서버 푸시(거의 안 쓰임)까지. 단, TCP 레벨 HOL blocking은 여전히 남아서 한 패킷 유실이 무관한 스트림까지 막을 수 있어요.

다음 편에서는 이 한계를 풀려고 TCP를 버린 HTTP/3와 그 기반 프로토콜 QUIC를 살펴봐요.
