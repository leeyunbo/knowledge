데드락이 아닌 막힘

Deadlock은 모든 스레드가 멈춰서 못 움직이는 거예요. 그런데 멈추지 않는데도 일이 안 진행되는 자리가 있어요. Livelock과 Starvation이에요. 이름은 비슷하지만 원인과 해결책이 달라요.

Livelock, 영원한 양보

두 스레드가 서로 양보하느라 진짜 일을 못 해요. 좁은 복도에서 두 사람이 서로 비켜 주려고 좌우로 움직이다가 결국 못 지나가는 상황을 떠올리면 돼요. 

// Livelock 예시 (의도적 단순화)
class Spoon {
    private Diner owner;

    void setOwner(Diner d) { this.owner = d; }
}

class Diner {
    boolean isHungry = true;
    String name;

    void eat(Diner spouse, Spoon spoon) {
        while (isHungry) {
            if (spoon.owner != this) {
                Thread.sleep(1);
                continue;
            }
            if (spouse.isHungry) {
                spoon.setOwner(spouse);  // 양보
                continue;
            }
            // 먹기...
        }
    }
}

두 다이너가 서로에게 스푼을 양보해요. 둘 다 hungry라 둘 다 양보만 해요. CPU는 계속 돌지만 진전이 없어요.

해결책

  • 무작위 backoff: 양보 후 다시 시도하기 전 무작위 시간만큼 쉬어요. 두 스레드가 다른 타이밍에 다시 시도하니 한쪽이 먼저 잡아요. (Retry/Backoff 시리즈의 jitter와 같은 발상.)
  • 우선순위 도입: ID가 작은 쪽이 먼저 가는 식의 단순 우선순위.
  • 책임 분리: 양보 대신 큐를 두고 먼저 도착한 순서대로 처리.

Starvation, 굶는 스레드

특정 스레드가 우선순위 경쟁에서 계속 밀려서 자원을 받지 못해요. 시스템은 정상 동작하는데 그 스레드만 일을 못 해요.

흔한 자리

  • 비공정 락: synchronized나 기본 ReentrantLock은 unfair. 운 나쁜 스레드가 계속 밀릴 수 있어요.
  • PriorityBlockingQueue: 낮은 우선순위 항목이 영원히 처리되지 않을 수 있어요.
  • 스레드 우선순위 차이: Thread.setPriority가 OS 스케줄러에 영향을 주면 낮은 우선순위 스레드가 굶어요.
  • 리더 선출 후 잡 분배 불균등: 분산 시스템에서 리더가 특정 노드에 작업을 계속 몰아주는 자리.

해결책

  • 공정성 옵션: new ReentrantLock(true)나 ArrayBlockingQueue(n, true)로 FIFO를 강제.
  • Aging: 오래 대기한 항목의 우선순위를 점점 올려요. PriorityBlockingQueue의 starvation 방어.
  • 모니터링: 평균 대기 시간과 P99·P999를 같이 봐서 outlier를 잡아요.

Livelock vs Starvation vs Deadlock

현상스레드 상태CPU 사용
Deadlock완전 멈춤 (서로 기다림)거의 0
Livelock활발히 움직이는데 진전 없음높음
Starvation일부 스레드만 진전 없음다른 스레드는 정상

CPU 사용량과 영향 범위로 구분해요. Deadlock은 멈춤, Livelock은 헛도는 활동, Starvation은 특정 스레드의 굶주림이에요.

진단

  • Thread dump: BLOCKED·WAITING이 많으면 Deadlock 의심. RUNNABLE이 많은데 진전이 없으면 Livelock 의심.
  • 대기 시간 분포: P50은 정상인데 P99·P999가 폭증이면 starvation 가능성.
  • 락 경합 측정: jstack이나 JFR로 락 hold time을 봐요.

면접에서 자주 나오는 자리

  • "Deadlock과 Livelock 차이?": Deadlock은 멈춤, Livelock은 헛돌아요. Livelock은 CPU를 계속 쓰지만 일이 진전되지 않는 거예요.
  • "Starvation 방어?": 공정성 옵션, aging, 모니터링이에요. ReentrantLock(true)나 ArrayBlockingQueue의 fair=true로 FIFO를 강제할 수 있어요.
  • "Livelock 해결?": 무작위 backoff로 타이밍을 깨거나, 단순 우선순위로 한쪽이 먼저 가게 해요.
