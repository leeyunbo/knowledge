CSRF가 뭔가

Cross-Site Request Forgery. 피해자가 이미 로그인된 상태에서, 공격자의 사이트가 피해자의 브라우저로 하여금 우리 사이트로 의도 외 요청을 보내게 만드는 공격이에요.

시나리오는 이래요.

  1. 사용자가 은행 사이트에 로그인해요. 세션 쿠키가 브라우저에 저장돼요.
  2. 사용자가 같은 브라우저로 공격자가 만든 함정 사이트에 방문해요.
  3. 그 사이트에 숨겨진 <img src="https://bank.com/transfer?to=attacker&amount=1000000"> 같은 태그가 있어요.
  4. 브라우저가 이미지 로드를 위해 GET 요청을 보내요. 이때 bank.com 세션 쿠키가 자동으로 첨부돼요.
  5. 은행 서버는 정상 사용자의 요청으로 보고 송금 처리를 해요.

핵심 메커니즘은 브라우저가 요청에 자동으로 쿠키를 첨부한다는 거예요. 그 요청이 어느 사이트에서 시작됐는지를 따지지 않아요.

XSS와의 차이

관점XSSCSRF
공격 위치우리 사이트 안에서 스크립트 실행다른 사이트가 우리 사이트로 요청
훔치는 것쿠키·토큰·데이터피해자의 권한 (요청 행위 자체)
필요한 것입력 검증 실패인증된 세션 + 외부 요청 가능
방어 방향출력 escape, CSP, HttpOnlySameSite 쿠키, CSRF 토큰, Origin 검증

XSS는 "남의 스크립트가 우리 페이지에서 실행". CSRF는 "남의 페이지가 우리 서버에 요청". 막는 방법도 완전히 달라요.

왜 GET 요청도 위험한가

GET 요청은 안전(safe)해야 한다는 게 HTTP 원칙이에요. side-effect가 없어야 해요. 그런데 종종 GET이 상태를 바꾸는 자리가 있어요. /delete?id=42 같은 자리. CSRF의 표적이 되기 쉽거든요.

방어의 첫 단추는 상태 변경 동작은 절대 GET으로 노출하지 않기예요. POST, PUT, DELETE만 써요. GET은 그저 조회만.

SameSite 쿠키: 가장 강력한 방어

최근 브라우저 표준으로 가장 효과적인 방어예요. 쿠키에 SameSite 속성을 두면 브라우저가 cross-site 요청에 쿠키를 안 붙여요. 

// 응답 헤더
Set-Cookie: sessionId=abc; HttpOnly; Secure; SameSite=Lax
값동작
Strictcross-site 요청에 쿠키 첨부 안 함. 다른 사이트에서 우리 링크 클릭으로 들어와도 로그아웃 상태.
Laxtop-level GET 탐색(링크 클릭)은 OK, POST나 iframe·이미지 요청은 차단. 균형 잡힌 기본값.
None모든 cross-site 요청에 첨부. Secure 필수.

Chrome은 명시 안 하면 자동으로 Lax로 처리해요. 다른 브라우저도 따라가는 추세. SameSite=Lax 하나로 대부분의 CSRF가 막혀요.

주의: SameSite는 브라우저 의존이에요. 옛 브라우저나 모바일 webview에서는 동작이 다를 수 있어요. 그래서 추가 방어가 필요.

CSRF Token: 전통적 방어

서버가 무작위 토큰을 생성해서 폼에 숨겨두고, 폼 제출 시 그 토큰이 같이 와야만 처리. 공격자 사이트는 그 토큰을 모르니까 위조 못 함. 

// 폼에 토큰 삽입
<form action="/transfer" method="POST">
  <input type="hidden" name="_csrf" value="random-token-abc123">
  <input type="text" name="amount">
  <button>Send</button>
</form>
// 서버에서 검증
String sessionToken = (String) session.getAttribute("_csrf");
String formToken = request.getParameter("_csrf");
if (!sessionToken.equals(formToken)) {
    throw new ForbiddenException("CSRF token mismatch");
}

토큰을 세션에 저장하고 폼 제출 시 비교. 토큰이 일치해야 요청 처리. Spring Security가 기본으로 켜둬요(CsrfTokenRepository).

Double Submit Cookie 패턴

세션을 안 쓰는 stateless API에서 CSRF 방어가 필요할 때 쓰는 패턴이에요. 토큰을 쿠키와 헤더 양쪽에 두고 비교.

  1. 서버가 응답에 Set-Cookie: csrfToken=xyz를 설정해요 (HttpOnly 아님).
  2. 클라이언트 JS가 그 쿠키를 읽어 다음 요청의 X-CSRF-Token 헤더에 같이 보내요.
  3. 서버는 쿠키의 토큰과 헤더의 토큰을 비교해요. 같아야 통과해요.

공격자가 cross-site에서 요청을 보내면 쿠키는 자동 첨부되지만, 다른 사이트는 그 쿠키 값을 읽을 수 없어요(same-origin policy). 헤더에 같은 값을 넣을 방법이 없어 검증 실패. CSRF 차단.

Origin과 Referer 헤더 검증

요청의 Origin이나 Referer 헤더를 확인해서 우리 도메인에서 시작된 요청만 받는 방식이에요. 보조적 방어로 좋아요. 

String origin = request.getHeader("Origin");
if (!isAllowed(origin)) {
    throw new ForbiddenException("invalid origin");
}

주의: Referer는 사용자가 끄거나 프록시가 제거할 수 있어요. Origin이 더 신뢰할 만함. 단독 방어로는 부족하고 SameSite·토큰과 함께 써야 해요.

API에서의 CSRF: 토큰 인증이면 자동 해결?

REST API가 Authorization: Bearer ... 같은 헤더 기반 토큰 인증을 쓰면 CSRF가 자동으로 막혀요. 브라우저가 cross-site 요청에 자동으로 Authorization 헤더를 첨부하지 않기 때문이에요(쿠키와 달리).

단, 토큰을 쿠키에 저장하는 경우는 CSRF에 취약해요. localStorage에 저장하면 안전하지만, 그건 XSS에 취약해요. 트레이드오프가 있어요.

표준 방어 체크리스트

  1. 모든 상태 변경 동작은 POST/PUT/DELETE.
  2. 세션 쿠키에 SameSite=Lax 또는 Strict.
  3. 세션 쿠키에 HttpOnly + Secure.
  4. Spring Security 같은 프레임워크의 CSRF 토큰 기능 활용.
  5. Stateless API는 헤더 기반 토큰 인증 또는 double-submit.
  6. Origin/Referer 헤더 추가 검증.

면접 자주 나오는 자리

  • "CSRF가 뭔가요?": 피해자의 인증된 세션을 이용해 다른 사이트가 우리 서버로 요청을 보내게 하는 공격.
  • "XSS와 차이는?": XSS는 우리 사이트에서 남의 스크립트 실행, CSRF는 다른 사이트가 우리 서버로 요청.
  • "어떻게 막나요?": SameSite 쿠키 + CSRF 토큰 + Origin 검증. 다층 방어.
  • "REST API에서도 필요한가요?": 쿠키 기반 인증이면 필요. 헤더 기반 토큰이면 자동 방어.
  • "Double Submit Cookie가 뭐예요?": 토큰을 쿠키와 헤더에 둘 다 두고 비교. stateless 환경에서 CSRF 방어.

세 공격은 OWASP Top 10의 단골이에요. 막는 방법이 다 다르고, 한 가지 방어로 다 막히지 않아요. 다층 방어와 표준 도구(Spring Security, OWASP 라이브러리) 사용이 정답이에요.
