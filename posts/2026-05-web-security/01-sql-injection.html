SQL Injection이 뭔가

사용자 입력이 SQL 쿼리에 그대로 끼어 들어가서, 입력이 데이터가 아니라 코드의 일부로 해석되는 사고예요. 1998년부터 알려졌고, OWASP Top 10에 거의 매번 등장해요.

단순한 예예요. 로그인 폼에서 username과 password를 받아 SQL을 만든다고 해봐요. 

// 위험한 코드
String sql = "SELECT * FROM users WHERE username = '" + username +
             "' AND password = '" + password + "'";
stmt.execute(sql);

사용자가 username에 admin' --을 넣으면 쿼리가 이렇게 돼요. 

SELECT * FROM users WHERE username = 'admin' --' AND password = '...'

--는 SQL 주석이라 뒤가 다 무시돼요. 비밀번호 검증 없이 admin으로 로그인이 돼요. 더 끔찍한 변형도 가능해요. '; DROP TABLE users; -- 같은 입력이 들어오면 테이블 자체가 사라져요.

왜 이게 가능한가

원인은 단순해요. 데이터와 코드의 경계가 무너졌기 때문이에요. 사용자 입력은 데이터로만 쓰여야 하는데, 문자열 연결로 SQL을 만들면 입력 안의 따옴표·세미콜론이 코드 기호로 해석돼요.

해결은 두 영역을 명확히 분리하는 거예요. 입력은 절대로 코드가 될 수 없도록.

Prepared Statement: 표준 방어

SQL과 데이터를 별도 채널로 보내는 게 prepared statement예요. 쿼리에 ? 자리표시자를 두고, 값은 별도 인자로 넘겨요. 

// 안전한 코드
PreparedStatement ps = conn.prepareStatement(
    "SELECT * FROM users WHERE username = ? AND password = ?"
);
ps.setString(1, username);
ps.setString(2, password);
ps.executeQuery();

중요한 차이는 SQL 파싱이 입력을 받기 전에 끝난다는 거예요. ? 자리에 무슨 값이 들어와도 그건 데이터로만 처리돼요. '; DROP TABLE이 와도 그게 통째로 username 값으로 비교될 뿐, SQL 명령으로 실행되지 않아요.

거의 모든 SQL 데이터베이스가 prepared statement를 지원해요. Java의 JDBC, Python의 PEP 249, Node.js의 mysql2, Go의 database/sql 모두 표준이에요. 예외 없이 항상 써야 해요.

ORM을 쓰면 안전한가

대체로 안전해요. JPA, Hibernate, MyBatis, Eloquent, Django ORM 같은 도구는 내부적으로 prepared statement를 써요. 그러나 함정이 있어요.

1. Native Query / Raw SQL

// 위험한 JPA 사용: 문자열 연결
String jpql = "SELECT u FROM User u WHERE u.name = '" + name + "'";
em.createQuery(jpql);

// 안전한 사용: 파라미터 바인딩
String jpql = "SELECT u FROM User u WHERE u.name = :name";
em.createQuery(jpql).setParameter("name", name);

Native query를 문자열 연결로 만들면 ORM 안에서도 SQL Injection이 가능해요. JPA의 @Query, MyBatis의 ${}(문자열 치환, 위험)과 #{}(파라미터 바인딩, 안전)의 차이를 외워두세요.

2. Order By / Column Name 동적 결정

prepared statement는 컬럼 이름이나 ORDER BY 절을 바인딩 못 해요. 정렬 컬럼을 사용자 입력으로 받으면 위험해져요. 

// 위험한 코드
String sortBy = request.getParameter("sortBy");   // 사용자 입력
String sql = "SELECT * FROM users ORDER BY " + sortBy;

방어는 화이트리스트예요. 허용된 컬럼 이름만 통과시켜요. 

Set<String> allowedColumns = Set.of("id", "name", "created_at");
if (!allowedColumns.contains(sortBy)) {
    throw new BadRequestException("invalid sort");
}
String sql = "SELECT * FROM users ORDER BY " + sortBy;

3. LIKE 와일드카드

LIKE 검색의 와일드카드(%, _)는 SQL Injection은 아니지만 비슷한 자리예요. 사용자 입력이 %로만 이루어지면 모든 데이터가 매치돼요. DoS 위험이거나 의도 외 데이터 노출. 이스케이프하거나 길이를 제한해야 해요.

2차 SQL Injection (Stored)

보통 SQL Injection은 입력이 즉시 쿼리에 들어가는 형태예요. 2차 공격은 다르게 동작해요.

  1. 공격자가 회원가입 시 username에 '; DROP TABLE을 넣어요. 회원가입 쿼리는 prepared statement라 안전해요. 이 문자열이 그대로 DB에 저장돼요.
  2. 나중에 관리자 화면에서 사용자 이름을 가져와 다른 쿼리에 끼워 넣을 때, 그 자리에서 prepared statement를 안 쓰면 그때 공격이 실행돼요.

방어는 똑같아요. 모든 SQL 생성 자리에서 예외 없이 prepared statement. "DB에서 가져온 값이라 안전하다"는 가정이 무너지는 자리예요.

Blind SQL Injection

공격자가 결과를 직접 볼 수 없는 환경이라도 공격이 가능해요. 응답의 미세한 차이나 응답 시간으로 정보를 빼내는 거예요.

  • Boolean-based: AND 1=1이면 정상, AND 1=2면 오류. 차이를 보고 한 비트씩 정보를 빼내요.
  • Time-based: AND SLEEP(5) 같은 함수로 응답이 5초 지연되면 조건이 참인 걸 알 수 있어요.

방어는 같아요. prepared statement면 둘 다 막혀요.

운영 단계의 추가 방어

코드 수준 방어가 1순위지만, 다층 방어가 안전해요.

  • 최소 권한 원칙: 애플리케이션 DB 계정이 DROP, ALTER 같은 위험한 권한을 못 가지게. 읽기 전용 계정과 쓰기 계정 분리.
  • WAF (Web Application Firewall): 의심스러운 패턴을 차단. 우회 가능하지만 한 겹 더.
  • 로깅과 알람: 비정상 쿼리 패턴 감지. SQL 에러 빈도 모니터링.
  • 코드 리뷰 / 정적 분석: SonarQube, Snyk 같은 도구가 위험한 패턴을 잡아줘요.

면접 단골 질문

  • "SQL Injection이 뭔가요?": 사용자 입력이 SQL 코드로 해석돼서 의도 외 동작이 일어나요.
  • "어떻게 막나요?": Prepared statement를 써요. 동적 컬럼·정렬은 화이트리스트로 막아요.
  • "ORM을 쓰면 안전한가요?": 대체로 안전해요. 다만 native query, 동적 컬럼 자리는 여전히 위험해요.
  • "Blind SQL Injection이 뭐예요?": 결과를 못 보는 상황에서 응답 차이·시간으로 정보를 빼내는 공격이에요.
