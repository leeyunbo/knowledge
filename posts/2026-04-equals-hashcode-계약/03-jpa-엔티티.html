JPA 엔티티의 equals와 hashCode, Lombok @Data가 위험한 이유

엔티티에 무심코 @Data 붙이는 순간 깔리는 세 가지 함정. ID 기반 해시도, 가변 필드도, Hibernate 프록시도 다 같은 곳에서 깨진다.

흔한 패턴, 그리고 깨지는 순간

Spring Boot + JPA 프로젝트에서 엔티티는 보통 이렇게 시작한다. Lombok이 보일러플레이트를 줄여주니까 자연스럽게 @Data를 붙인다. 

@Entity
@Data
@NoArgsConstructor
public class User {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;
    private int age;

    @OneToMany(mappedBy = "user", fetch = FetchType.LAZY)
    private List<Order> orders;
}

이 코드는 컴파일도 되고, 일반 단위 테스트도 통과한다. 그런데 @Data는 @EqualsAndHashCode를 포함하고, 그 디폴트가 모든 필드를 사용해서 equals/hashCode를 만든다. 이게 JPA 엔티티에선 폭탄이 된다.

함정 1 — 영속화 전후의 ID 변화

@GeneratedValue(strategy = IDENTITY)를 쓰면 id는 save() 전엔 null, save() 후엔 DB가 발급한 값으로 바뀐다. 모든 필드를 쓰는 hashCode는 id도 포함하니까 그 한 번의 변화로 같은 객체의 hashCode가 달라진다. 

User user = new User();
user.setName("yunbok");
user.setAge(30);
// user.id == null

Set<User> cache = new HashSet<>();
cache.add(user);                  // null 기반 해시로 저장

userRepository.save(user);
// user.id == 42 로 변경됨

cache.contains(user);             // false
// 같은 인스턴스인데 못 찾는다

이게 2편에서 본 "규칙 1 위반 — 같은 객체에서 호출마다 다른 해시"의 현실 버전이다. 코드를 보면 hashCode를 직접 깬 곳이 없는데, DB가 ID를 발급하는 순간 객체 상태가 바뀌면서 자연스럽게 깨진다.

Vlad Mihalcea가 이 문제를 정리하면서 결론낸 내용이 핵심이다.

the consistency guarantee breaks if we implemented the equals and hashCode based on the identifier just like for assigned identifiers

(직접 부여한 식별자와 똑같은 방식으로 자동 생성 식별자에 대해 equals/hashCode를 구현하면, 일관성 보장이 깨진다)

함정 2 — Lazy 컬렉션이 끌려 나온다

@Data가 만든 equals/hashCode는 모든 필드를 건드린다. 위 예시의 orders처럼 @OneToMany(LAZY)로 매핑된 컬렉션도 예외가 아니다. equals나 hashCode를 호출하는 순간 Hibernate가 그 컬렉션을 로드하려고 SQL을 날린다. 

// 엔티티 하나의 hashCode 호출이
user.hashCode();
// → orders 필드 접근
// → SELECT * FROM orders WHERE user_id = ? 추가 발생

HashSet에 엔티티 1000개를 넣었다? 1000개의 추가 SELECT가 트리거된다. 더 나쁜 건 트랜잭션이 닫힌 상태에서 호출하면 LazyInitializationException이 터진다. 서비스 레이어 밖에서 무심코 equals 한 번 부른 게 예외로 돌아온다.

함정 3 — Hibernate 프록시와 getClass()

Lombok @EqualsAndHashCode의 디폴트는 타입 비교에 getClass()를 쓴다 (정확히 같은 클래스인지 확인). 그런데 Hibernate는 Lazy 연관 관계를 가져올 때 엔티티를 프록시 서브클래스로 감싼다. 그 프록시는 원래 엔티티 클래스가 아니다. 자식 클래스다. 

User user = userRepository.findById(1L).get();
User userProxy = order.getUser();   // Lazy로 끌려온 프록시

user.getClass();                    // class User
userProxy.getClass();               // class User$HibernateProxy$abc123

user.equals(userProxy);             // false!
// 같은 DB row를 가리키는 객체인데도

그래서 getClass()가 아니라 instanceof를 써야 한다. 이건 Lombok의 onlyExplicitlyIncluded 설정으로 우회할 수 있긴 하지만, 그 자체로 "엔티티에 @Data 그냥 붙이면 안 된다"는 신호다.

그럼 어떻게 짜야 하나

정답은 한 줄이다. @Data를 엔티티에 쓰지 않는다. @Getter, @NoArgsConstructor 정도만 쓰고 equals/hashCode는 직접 짠다. 짜는 방식은 비즈니스 키 유무에 따라 갈린다.

비즈니스 키가 있을 때 (가장 좋은 케이스)

이메일, 사용자 핸들, 주문번호처럼 변하지 않으면서 유일한 자연 키가 있으면 그걸 쓴다. 

@Override
public boolean equals(Object o) {
    if (this == o) return true;
    if (!(o instanceof User u)) return false;
    return email.equals(u.email);
}

@Override
public int hashCode() {
    return email.hashCode();
}

비즈니스 키는 영속화 전에도 정해져 있고, 한 번 정해지면 안 바뀐다. 1편/2편의 모든 계약을 자연스럽게 만족한다.

비즈니스 키가 없을 때 (자동 생성 ID만 있을 때)

Vlad Mihalcea가 제시한 패턴이 가장 안전하다 — equals는 ID로 비교하되 둘 다 non-null일 때만 같다고 보고, hashCode는 클래스 단위 상수로 고정한다. 

@Override
public boolean equals(Object o) {
    if (this == o) return true;
    if (!(o instanceof User u)) return false;
    return id != null && id.equals(u.id);
}

@Override
public int hashCode() {
    return getClass().hashCode();
}

핵심은 hashCode가 객체 상태와 무관하게 항상 같은 값을 돌려준다는 것. ID가 null이든 아니든, 영속화 전이든 후든 같다. 그래서 2편 규칙 1(consistent)을 자동으로 지킨다.

이러면 같은 클래스의 모든 엔티티가 한 버킷에 몰리는 것 아니냐 싶지만, 하나의 HashSet이나 HashMap에 같은 엔티티 종류만 백 만 개 넣고 쓰는 OLTP 시나리오는 현실적으로 잘 없다. 한 트랜잭션 안에서 다루는 컬렉션 크기를 생각하면 이 트레이드오프가 합리적이다.

JPA 엔티티에 한정한 핵심

순수 자바 객체에선 1편/2편 규칙만 지키면 충분했다. JPA 엔티티는 거기에 두 가지 추가 제약이 붙는다.

  • 객체 상태가 영속화 도중 바뀐다는 점 — ID, 연관 컬렉션 모두 시점에 따라 달라진다
  • 프록시가 끼어든다는 점 — 비교 방식과 lazy 트리거를 의식해야 한다

Lombok @Data는 이 두 제약을 전혀 모르는 채 equals/hashCode를 만든다. 그래서 위험하다. 엔티티에선 그냥 직접 짜는 게 결과적으로 안전하고 명확하다.

이걸로 equals/hashCode 시리즈는 마친다. 순수 객체 → 계약 → JPA 엔티티 순서로 봤는데, 공통 메시지는 하나다. 해시 기반 자료구조에 들어갈 객체는, 한 번 결정된 해시가 객체 수명 동안 변하지 않아야 한다. 이 규칙을 지키지 못하는 객체를 키로 쓰면 어디선가 조용히 깨진다.
