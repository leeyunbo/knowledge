왜 쉬는 시간이 필요한가

외부 서버가 일시적 과부하예요. 모든 클라이언트가 즉시 재시도하면 그 서버는 더 빨리 죽어요. 쉬는 시간을 주면 서버가 회복할 기회가 생겨요. 이 "쉬는 시간"을 backoff라고 해요.

Backoff는 단순히 sleep 거는 게 아니에요. 어떻게 분포시키느냐가 시스템 전체 회복에 결정적이에요. 잘못 설계하면 클라이언트들이 동기화돼서 동시에 재시도하는 "thundering herd"가 일어나요.

Fixed Delay

가장 단순한 전략이에요. 매번 같은 시간 대기해요. 

long delay = 1000;  // 1초
for (int i = 0; i < 3; i++) {
    try {
        return api.call();
    } catch (Exception e) {
        Thread.sleep(delay);
    }
}

장점

  • 구현이 단순하고 직관적이에요.
  • 예측 가능한 응답 시간을 가져요.

한계

  • 모든 클라이언트가 같은 간격으로 재시도해요. 동기화된 herd가 만들어져요.
  • 큰 장애에는 너무 자주 시도해서 부하를 더해요.

Exponential Backoff

대기 시간이 재시도 횟수에 따라 지수적으로 늘어나요. 1초, 2초, 4초, 8초, 16초처럼요. 

long base = 1000;
for (int i = 0; i < 5; i++) {
    try {
        return api.call();
    } catch (Exception e) {
        long delay = base * (1L << i);  // 1s, 2s, 4s, 8s, 16s
        Thread.sleep(Math.min(delay, 30_000));  // 상한 두기
    }
}

장점

  • 초반엔 빠르게 시도하고, 계속 실패하면 점점 부담을 줄여요.
  • 긴 장애도 너무 자주 시도하지 않아 회복 기회를 줘요.

한계

  • 여러 클라이언트가 같은 시각에 첫 호출이 실패했다면, 1초·2초·4초도 모두 같은 시각에 재시도해요. 여전히 동기화된 부하가 발생해요.
  • 상한(cap)이 없으면 한 번 실패가 길어지면 매우 오래 기다려요.

Jitter, 동기화를 깨는 무작위

Exponential의 herd 문제를 해결하는 핵심 기법이에요. 대기 시간에 무작위 요소를 더해 클라이언트들이 다른 시각에 재시도하게 만들어요.

Full Jitter (AWS 권장)

long base = 1000;
Random random = new Random();

for (int i = 0; i < 5; i++) {
    try {
        return api.call();
    } catch (Exception e) {
        long cap = Math.min(base * (1L << i), 30_000);
        long delay = random.nextLong(cap);  // [0, cap)
        Thread.sleep(delay);
    }
}

대기 시간이 [0, exponential cap) 사이의 균등 분포예요. 동기화가 완벽히 깨져요. AWS의 Architecture Blog가 시뮬레이션으로 "가장 효과적"이라고 결론 내린 전략이에요.

Equal Jitter

long cap = Math.min(base * (1L << i), 30_000);
long delay = cap / 2 + random.nextLong(cap / 2);

대기 시간의 절반은 exponential, 나머지 절반은 jitter예요. Full jitter보다 분산이 작아서, 보통 약간 낮은 성능이지만 더 예측 가능해요.

Decorrelated Jitter

long base = 1000;
long cap = 30_000;
long sleep = base;

for (int i = 0; i < 5; i++) {
    try {
        return api.call();
    } catch (Exception e) {
        sleep = Math.min(cap, random.nextLong(base, sleep * 3));
        Thread.sleep(sleep);
    }
}

이전 대기 시간이 다음 계산에 영향을 줘요. 클라이언트마다 다른 궤적을 그려서 동기화가 더 깨져요. Full jitter와 비슷하거나 약간 더 좋은 성능이에요. AWS Architecture Blog의 후속 글에서 권장돼요.

네 가지 전략 비교

전략특성적합한 자리
Fixed단순, herd 위험 큼저빈도, 단일 클라이언트
Exponential점진 백오프, 동기화 가능적은 클라이언트 환경
Full Jitter완전 무작위, herd 거의 없음일반 추천 (AWS 권장)
Decorrelated Jitter이전 값과 상관, 분포 좋음대규모 클러스터

실무 추천. 보통 클라이언트가 많고 동시에 실패하는 자리라면 Full Jitter 또는 Decorrelated Jitter예요. 단일 인스턴스 또는 동시 호출이 적은 자리라면 Exponential도 충분해요. Fixed는 거의 안 써요.

Retry-After 헤더 존중

429 Too Many Requests나 503 Service Unavailable 응답에 Retry-After 헤더가 있으면 서버가 명시적으로 "이만큼 기다려 줘"라고 알려주는 거예요. backoff 계산을 무시하고 서버의 지시를 따라야 해요. 

HTTP/1.1 429 Too Many Requests
Retry-After: 30

Retry-After는 두 형식이 있어요. 초 단위 정수이거나 HTTP 날짜예요. 두 경우 모두 파싱해야 해요. 임의로 backoff 계산을 적용하면 서버는 더 빨리 죽어요.

최대 횟수와 총 시간

Backoff 전략을 정해도 끝 조건이 없으면 영원히 재시도해요. 두 가지 끝 조건을 같이 둬요.

  • Max Attempts: 최대 횟수 (보통 3~5).
  • Max Total Time: 총 시간 한계 (보통 30초~1분).

둘 중 먼저 도달한 쪽에서 멈춰요. 사용자 요청 흐름은 보통 30초 안에 끝나야 하니, total time이 사실상 결정적이에요. 백그라운드 작업은 더 긴 한계를 가져요.

회복 후 갑작스러운 herd

Backoff가 잘 동작해도 위험 자리가 있어요. 장애 서버가 회복한 직후 모든 클라이언트의 재시도가 한꺼번에 몰려요. 평소보다 5~10배 부하가 짧게 몰려서 서버가 다시 죽기도 해요.

Decorrelated Jitter나 Full Jitter는 이 회복 후 herd도 어느 정도 분산시켜요. 추가 보완책으로 circuit breaker가 회복 시 트래픽을 단계적으로 흘려주는 half-open 패턴을 같이 써요.

실측 비교 (AWS Architecture Blog)

AWS는 백오프 전략을 시뮬레이션해서 발표했어요. 100 클라이언트가 동시에 호출하는 시나리오를 보면 결과가 갈렸어요.

  • Exponential without jitter는 첫 호출 100번이 동시에 몰리고, 다음 라운드도 거의 동기화돼서 herd가 반복돼요.
  • Full Jitter는 호출이 시간 축에 고르게 분포해요. 서버 부하가 평탄해져요.
  • Decorrelated Jitter는 Full Jitter와 비슷하거나 약간 더 좋아요. 평균 완료 시간도 조금 더 빨라요.

실측 결과 "exponential + full jitter" 또는 "decorrelated jitter"가 가장 효과적이에요. 단순 exponential은 거의 항상 herd를 만들어요.

라이브러리 기본 동작

라이브러리기본 backoff
Spring RetryFixed (1초). Exponential·Jitter 별도 설정.
Resilience4jExponential + Random Wait 가능
AWS SDKEqual Jitter (기본), Full Jitter도 선택 가능

기본값에 만족하지 말고 설정을 확인해요. 특히 Spring Retry의 기본 fixed는 herd 위험이 있어요. Exponential + Random Wait로 바꾸는 게 좋아요.

면접에서 자주 나오는 자리

  • "Exponential backoff가 뭐예요?": 재시도 간격을 지수적으로 늘리는 전략이에요. 1초, 2초, 4초, 8초처럼요.
  • "Jitter는 왜 필요?": 여러 클라이언트가 동시에 실패했을 때 동기화된 재시도를 분산시켜요. 서버 회복 기회를 더 줘요.
  • "AWS가 권장하는 백오프는?": Full Jitter 또는 Decorrelated Jitter예요. 시뮬레이션 결과 단순 exponential보다 훨씬 좋다고 보고됐어요.
  • "Retry-After 헤더는?": 서버가 "이만큼 기다려 달라"는 명시적 신호예요. backoff 계산보다 우선이에요.
  • "백오프 상한이 왜 필요?": 한 번 실패가 길어지면 다음 재시도가 너무 늦어져요. 보통 30초~1분으로 상한을 둬요.
