Resilience4j Retry 적용

자바 생태계의 표준 라이브러리예요. Spring Boot와 잘 통합되고, 백오프·jitter·예외 필터링을 다 설정할 수 있어요. 

RetryConfig config = RetryConfig.custom()
    .maxAttempts(3)
    .waitDuration(Duration.ofMillis(500))
    .retryExceptions(IOException.class, TimeoutException.class)
    .ignoreExceptions(BusinessException.class)
    .intervalFunction(IntervalFunction.ofExponentialRandomBackoff(
        500, 2.0, 0.5))  // base 500ms, multiplier 2, jitter 0.5
    .build();

Retry retry = Retry.of("paymentApi", config);

Supplier<Payment> decorated = Retry.decorateSupplier(retry,
    () -> paymentApi.charge(orderId, amount));

Payment result = decorated.get();

핵심 옵션은 다음과 같아요.

  • maxAttempts: 최대 시도 횟수예요 (첫 호출 포함).
  • retryExceptions: 재시도할 예외 화이트리스트예요.
  • ignoreExceptions: 절대 재시도하지 않을 예외 블랙리스트예요.
  • intervalFunction: backoff 함수예요. exponential random이 권장 기본값이에요.

Spring Boot 통합

resilience4j:
  retry:
    instances:
      paymentApi:
        max-attempts: 3
        wait-duration: 500ms
        enable-exponential-backoff: true
        exponential-backoff-multiplier: 2
        enable-randomized-wait: true
        randomized-wait-factor: 0.5
        retry-exceptions:
          - java.io.IOException
        ignore-exceptions:
          - com.example.BusinessException
@Retry(name = "paymentApi", fallbackMethod = "fallback")
public Payment charge(Order order) {
    return paymentApi.charge(order.getId(), order.getAmount());
}

private Payment fallback(Order order, Exception e) {
    // 모든 재시도 실패 후
    return Payment.failed(order);
}

애노테이션 한 줄로 끝나서 깔끔해요. 단, AOP 기반이라 self-invocation 함정이 있어요. @Transactional 시리즈에서 다룬 그 자리예요. 같은 클래스 내부 호출은 적용 안 돼요.

Retry Storm

재시도가 시스템을 더 망가뜨리는 자리가 있어요. Retry storm이에요. 호출 체인의 모든 레이어에서 각자 재시도를 하면 부하가 곱셈으로 늘어나요.

곱셈 효과

서비스 A → B → C 호출 체인이 있어요. 각 레이어가 3번씩 재시도하면 C가 받는 총 호출은 3×3×3 = 27배예요. C가 일시적으로 느려졌을 뿐인데 27배 부하를 받아서 진짜로 죽어요.

방어책

  • 레이어 중 한 곳만 재시도: 보통 가장 바깥 쪽(사용자에 가까운 쪽)에서만 재시도. 나머지는 즉시 실패를 전파해요.
  • 재시도 헤더 전파: X-Retry-Attempt 같은 헤더로 안쪽 레이어가 "이건 이미 재시도된 요청"임을 알아채고 다시 재시도하지 않도록 해요.
  • Retry budget: 단위 시간당 재시도 비율을 제한해요. 다음 자리에서 자세히.

Retry Budget

Envoy·gRPC에서 쓰는 패턴이에요. "전체 요청 중 N%만 재시도 허용"이라는 제한을 둬요. 평상시엔 거의 영향 없지만, 큰 장애 시 폭주를 막아요. 

retry_policy:
  retry_budget:
    budget_percent: 20.0   # 전체 요청의 20%까지만 재시도
    min_retry_concurrency: 3

요청 100개 중 20개까지만 재시도 가능해요. 80%가 실패하는 상황이면 재시도가 부분적으로만 일어나서 부하가 폭주하지 않아요. 정상 트래픽일 때는 영향이 없어요.

Circuit Breaker와의 조합

Retry와 Circuit Breaker는 서로 보완 관계예요. 일시적 실패엔 retry, 영구적·반복 장애엔 circuit breaker가 잡아 줘요.

순서

  1. 일반 호출 → 성공.
  2. 일시적 실패 → retry 몇 번 → 성공.
  3. 계속 실패 → circuit breaker가 open → 모든 호출 즉시 실패.
  4. 일정 시간 후 → half-open → 일부 트래픽을 흘려서 회복을 확인해요.
  5. 회복되면 closed로 돌아가요.
resilience4j:
  circuitbreaker:
    instances:
      paymentApi:
        failure-rate-threshold: 50
        wait-duration-in-open-state: 30s
        permitted-number-of-calls-in-half-open-state: 3
  retry:
    instances:
      paymentApi:
        max-attempts: 3
        wait-duration: 500ms

Resilience4j는 두 패턴을 같은 인스턴스 이름으로 묶어 쓸 수 있어요. 호출 → retry → circuit breaker 순서로 적용돼요.

Timeout과의 조합

Timeout 없는 retry는 위험해요. 호출이 영원히 안 끝나면 재시도 자체가 의미 없어요. 보통 다음과 같이 묶어요.

  • 단일 호출 timeout: 한 번의 호출이 최대 얼마나 기다릴지. 예: 2초.
  • 총 retry timeout: 모든 재시도 포함 최대 시간. 예: 30초.
// 한 호출은 2초 timeout, 전체는 30초까지 retry
TimeLimiterConfig timeLimiter = TimeLimiterConfig.custom()
    .timeoutDuration(Duration.ofSeconds(2))
    .build();

RetryConfig retry = RetryConfig.custom()
    .maxAttempts(5)
    .waitDuration(Duration.ofSeconds(1))
    .build();

// 데코레이터 체인으로 합성
Supplier<Payment> decorated =
    Decorators.ofSupplier(() -> paymentApi.charge(...))
        .withRetry(Retry.of("payment", retry))
        .withTimeLimiter(TimeLimiter.of("payment", timeLimiter))
        .decorate();

Timeout 시리즈에서 더 자세히 다룰 자리예요. Retry와 timeout이 같이 있어야 안전한 재시도가 완성돼요.

실무에서 자주 만나는 버그

1. 비동기 재시도의 컨텍스트 손실

CompletableFuture·Reactor 같은 비동기 흐름에서 재시도하면 ThreadLocal·MDC가 사라져요. 로깅에 traceId가 안 나오거나 트랜잭션이 깨질 수 있어요. 비동기 재시도 라이브러리가 컨텍스트를 전파하는지 확인해야 해요.

2. 재시도 중 인증 토큰 만료

첫 호출에서 토큰 만료로 401이 나서 재시도해요. 그런데 두 번째도 같은 만료 토큰이라 또 401이에요. 401은 재시도 대상에서 빼고, 토큰 갱신 후 새로 호출해야 해요.

3. 비멱등 호출의 무자비한 재시도

1편의 결제 예시예요. idempotency key 없이 비멱등 호출을 재시도하면 중복 처리 사고로 직결돼요. 비멱등 호출은 retry 정책에서 명시적으로 빼거나, idempotency key를 함께 보내야 안전해요.

4. 빠른 재시도와 느린 클라이언트 사이드 timeout

단일 호출 timeout이 30초인데 backoff 사이의 재시도 간격이 1초·2초·4초면 결국 한 사이클이 30초+1+30+2+30+4 = 97초까지 걸려요. 사용자는 30초만 기다리도록 설계됐는데 백엔드는 97초 걸려요. 총 timeout과 단일 timeout, 재시도 횟수를 같이 계산해야 해요.

관측성 (Observability)

재시도는 잠재적 사고 신호예요. 다음 지표를 같이 봐요.

  • 재시도 횟수: 평소보다 늘면 외부 의존이 흔들리는 신호.
  • 최종 실패 비율: 재시도 후에도 실패한 비율. 회복력 지표.
  • 재시도별 지연 분포: backoff가 의도대로 동작하는지.
  • Circuit breaker 상태: 한 번씩 open되는지, 자주 open되는지.

Resilience4j는 Micrometer 메트릭을 노출해요. resilience4j_retry_calls_total, resilience4j_retry_max_retries_exceeded 같은 지표예요. Grafana 대시보드와 알람을 걸어 두면 장애 초기 신호를 빠르게 잡아요.

면접에서 자주 나오는 자리

  • "Retry storm이 뭐예요?": 호출 체인의 여러 레이어가 각자 재시도해서 부하가 곱셈으로 늘어나는 현상이에요. 한 레이어가 흔들리면 다른 레이어가 27배 부하를 줘요.
  • "방어법은?": 가장 바깥 레이어에서만 재시도, retry budget으로 비율 제한, X-Retry 헤더 전파로 안쪽 레이어가 재시도 안 하도록.
  • "Retry와 Circuit Breaker의 차이?": Retry는 일시적 실패에, Circuit Breaker는 반복적·영구적 장애에 대응해요. 보통 같이 써요.
  • "Resilience4j의 Retry는 어떻게?": 애노테이션 @Retry와 yaml 설정으로 maxAttempts·waitDuration·backoff 종류를 잡아요. AOP 기반이라 self-invocation은 안 돼요.
  • "비동기 재시도에서 주의?": ThreadLocal·MDC 컨텍스트 전파를 확인해요. 또 timeout과 같이 둬야 무한 대기를 막아요.

시리즈 마무리

1편에서 재시도 안전 조건(멱등성, 일시적 실패만 재시도)과 안티패턴을 봤어요. 2편에서 Fixed·Exponential·Full Jitter·Decorrelated Jitter 같은 backoff 전략과 AWS가 권장하는 jitter 기반 패턴을 정리했어요. 3편에서는 Resilience4j 실무 적용, retry storm 방어, retry budget, circuit breaker·timeout과의 조합을 다뤘어요.

핵심은 단순해요. 재시도는 안전 조건과 backoff 전략, 그리고 다른 패턴과의 조합으로 완성돼요. 하나만 쓰면 사고를 키워요. 멱등성·circuit breaker·timeout·retry가 같이 쌓일 때 진짜 회복력 있는 시스템이 만들어져요.
