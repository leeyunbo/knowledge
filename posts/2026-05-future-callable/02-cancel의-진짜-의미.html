cancel은 무엇을 하나

future.cancel(mayInterruptIfRunning)의 동작은 작업이 어느 단계냐에 따라 달라요. 세 가지 경우가 있어요.

  1. 아직 시작 안 함 (큐에서 대기 중): 그냥 큐에서 제거돼요. 작업 자체는 실행되지 않고, 항상 성공해요.
  2. 이미 끝남: 아무 일도 안 일어나고 false를 반환해요.
  3. 실행 중: mayInterruptIfRunning에 따라 다름. 이게 핵심이에요.

mayInterruptIfRunning = false

실행 중인 작업에는 아무 영향도 주지 않아요. 그저 Future를 "취소된 것으로 마킹"만 해요. 작업은 계속 돌고, 끝나도 결과는 버려져요. 

Future<String> f = es.submit(() -> heavyWork());
// ... 시간이 지남 ...
f.cancel(false);   // 작업은 계속 돌고 있음, 결과만 버림

이게 유용한 자리는 "결과는 더 이상 필요 없지만 작업을 굳이 멈출 필요는 없는" 경우예요. 예를 들어 검색 결과를 받는 도중 사용자가 페이지를 떠났을 때. 작업이 끝까지 돌게 두고 결과만 무시하면 충분한 자리.

mayInterruptIfRunning = true

실행 중인 스레드에 Thread.interrupt()를 호출해요. 인터럽트 시그널을 보내는 거예요. 그리고 Future를 취소 상태로 마킹해요. 

Future<String> f = es.submit(() -> heavyWork());
// ... 시간이 지남 ...
f.cancel(true);   // 인터럽트 보냄, 결과 버림

주의할 점이 있어요. 인터럽트는 부탁일 뿐이에요. 받는 쪽 작업 코드가 인터럽트를 처리해 줘야 진짜로 멈춰요. 안 그러면 인터럽트 플래그만 set되고 작업은 계속 돌아요.

인터럽트가 안 듣는 작업

다음 코드는 cancel(true)를 받아도 안 멈춰요. 

// cancel을 받아도 멈추지 않는 작업
Callable<Long> task = () -> {
    long sum = 0;
    for (long i = 0; i < Long.MAX_VALUE; i++) {
        sum += i * i;
    }
    return sum;
};

계산 루프는 인터럽트 플래그를 확인하는 코드가 없어요. cancel(true)로 인터럽트 시그널이 와도 그냥 무시당해요. 작업이 끝까지 돌아요.

반대로 다음은 cancel을 잘 받아들여요. 

// cancel을 받으면 멈추는 작업
Callable<Long> task = () -> {
    long sum = 0;
    for (long i = 0; i < Long.MAX_VALUE; i++) {
        if (Thread.currentThread().isInterrupted()) {
            throw new InterruptedException();
        }
        sum += i * i;
    }
    return sum;
};

isInterrupted()를 주기적으로 체크해요. true면 예외를 던져서 빠져나와요. 이게 cancel-가능한 작업의 표준 패턴이에요.

블로킹 호출은 인터럽트에 자동 반응

손으로 isInterrupted를 체크하지 않아도 인터럽트에 자동 반응하는 호출들이 있어요. 자바 표준의 블로킹 메서드들이에요.

  • Thread.sleep
  • Object.wait, Condition.await
  • Lock.lockInterruptibly
  • BlockingQueue.put, BlockingQueue.take
  • Future.get
  • CountDownLatch.await

이런 메서드들은 인터럽트를 받으면 즉시 InterruptedException을 던져요. 그래서 sleep을 자주 부르는 작업은 cancel에 잘 반응해요. 

// 이런 작업은 cancel(true)에 잘 반응함
Callable<Void> pollTask = () -> {
    while (true) {
        String item = queue.take();   // 블로킹. 인터럽트되면 InterruptedException
        process(item);
    }
};

I/O는 그대로 안 풀려요

애매한 자리가 있어요. 표준 InputStream.read, 소켓 읽기 같은 I/O 블로킹은 일반적인 인터럽트로 안 풀려요. 인터럽트 플래그만 set되고 read는 계속 막혀 있어요.

자바 NIO의 InterruptibleChannel은 인터럽트에 반응해요. Closeable 인터페이스의 close()를 외부에서 호출하면 read가 풀려요. 이런 자리에선 작업 코드를 짤 때 인터럽트 신호를 받으면 채널을 닫는 try-catch를 직접 두르는 게 표준이에요. 

// I/O 작업에서 cancel 가능하게 만들기
Callable<String> readTask = () -> {
    InputStream in = connection.getInputStream();
    Thread t = Thread.currentThread();

    // 인터럽트 들으면 채널 닫는 별도 로직
    // (Spring의 RestTemplate이나 OkHttp 같은 라이브러리는 자체적으로 이걸 처리)

    try {
        return readAllBytes(in);
    } catch (IOException e) {
        if (t.isInterrupted()) {
            throw new InterruptedException();
        }
        throw e;
    }
};

실무에서는 외부 호출 라이브러리(HttpClient, OkHttp, JDBC 드라이버 등)가 인터럽트를 어떻게 처리하는지 확인해 두는 게 좋아요. 라이브러리마다 인터럽트 대응이 다 달라요.

취소 가능한 작업의 패턴

지금까지 본 걸 한 번에 정리하면 이래요. cancel에 잘 반응하는 작업을 짤 때 신경 쓸 부분.

  1. 장시간 루프는 isInterrupted()를 주기적으로 체크. 보통 매 반복 또는 100~1000회마다.
  2. 블로킹 호출은 InterruptedException이 던져지면 그걸 위로 던지거나 작업 종료 처리.
  3. InterruptedException catch 시에는 Thread.currentThread().interrupt()로 상태 복원.
  4. I/O 블로킹이 있으면 자체적으로 채널을 닫는 메커니즘 필요. 라이브러리 동작 확인.
  5. 리소스 해제는 try-finally 안에서. 인터럽트로 빠져나갈 때도 정리되도록.

cancel 결과를 어떻게 확인하나

cancel의 반환값은 단순해요. true는 "취소 시도 가능했음", false는 "이미 끝났거나 취소 못 함"이에요. 그런데 true가 작업이 실제로 멈췄다는 보장은 아니에요. mayInterruptIfRunning=true로 인터럽트를 보냈을 뿐, 작업이 응답할지는 작업 코드 책임이에요.

진짜 끝났는지 확인하려면 그 Future에 get을 호출해서 CancellationException이 잡히는지 보거나, isDone()이 true인지 확인해야 해요. 

future.cancel(true);

// 작업이 실제로 정리될 때까지 기다리려면
try {
    future.get(1, TimeUnit.SECONDS);
} catch (CancellationException e) {
    log.info("정상적으로 취소됨");
} catch (TimeoutException e) {
    log.warn("취소 요청 후에도 작업이 안 끝남. 라이브러리 인터럽트 응답을 확인하세요");
} catch (Exception e) {
    // ...
}

한 줄 요약

  • cancel(false): 결과만 버림. 작업은 그대로 돔.
  • cancel(true): 인터럽트 보냄. 작업이 받아주면 멈춤.
  • 장시간 루프는 isInterrupted() 체크. 블로킹 호출은 InterruptedException 처리.
  • I/O는 자동으로 안 풀려요. 채널 close 메커니즘 필요.
  • cancel 후 정말 멈췄는지는 별도 확인해야 해요.
