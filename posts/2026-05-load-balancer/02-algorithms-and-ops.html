분산 알고리즘 종류

Load Balancer가 여러 백엔드 중 어느 서버로 보낼지 결정하는 방법이에요. 자리에 따라 다른 알고리즘이 맞아요.

1. Round Robin

단순히 순서대로 보내요. A → B → C → A → B → C로 모든 서버에 균등하게 분산되고, 가장 단순한 기본값이에요.

서버 사양이 같고 각 요청 처리 시간이 비슷한 환경에 잘 맞아요. API 서버처럼 균질한 워크로드가 대표적이에요.

한 요청이 오래 걸리는데 다음 요청도 계속 같은 서버로 가면 부하가 불균형해져요. 짧은 요청과 긴 요청이 섞이면 잘 맞지 않아요.

2. Least Connections (또는 Least Requests)

현재 연결 수가 가장 적은 서버로 우선 보내요. 부하 균형을 동적으로 잡아요.

요청 처리 시간 차이가 큰 환경에 잘 맞아요. 어떤 서버가 무거운 요청을 처리 중이면 다른 서버로 자동으로 분산돼요.

연결 수만 보기 때문에 실제 부하(CPU, 메모리)와 다를 수 있어요. 활성 연결은 적은데 CPU가 100%인 서버가 그런 경우예요.

3. IP Hash

클라이언트 IP를 해시 함수에 넣어 항상 같은 서버로 보내요. 같은 사용자가 항상 같은 서버를 보게 돼요.

서버에 세션을 두는 stateful 시스템이나 캐시 적중률을 높이고 싶을 때 잘 맞아요.

NAT 뒤 사용자가 모두 같은 IP로 보여서 한 서버에 몰려요. 회사·학교·통신사 NAT의 함정이에요.

4. Weighted Round Robin / Weighted Least Connections

서버마다 가중치를 둬서 더 큰 서버에 더 많이 분산해요. 서버 사양이 다른 환경에서 유용해요. 

# nginx 예시
upstream backend {
    server srv1.example.com weight=5;   # 50% 트래픽
    server srv2.example.com weight=3;   # 30%
    server srv3.example.com weight=2;   # 20%
}

점진적 카나리 배포에도 활용해요. 새 버전 서버에 가중치 1로 시작해서 점점 늘려가요.

5. Random

무작위로 골라요. 의외로 잘 작동해요. 큰 클러스터에서 부하가 자연스럽게 균등해져요.

6. Power of Two Choices

무작위로 두 서버를 골라 그중 부하가 적은 쪽으로 보내요. Round Robin과 Least Connections의 중간이에요. 단순한데 효과가 좋아서 많은 LB가 기본값으로 채택해요. Envoy의 기본 분산 알고리즘이에요.

헬스체크 (Health Check)

LB가 죽은 서버로 트래픽을 보내면 사용자가 에러를 받아요. 죽은 서버를 빨리 발견하고 분산 풀에서 빼야 해요. 이게 헬스체크예요.

Active Health Check

LB가 주기적으로(보통 1~10초) 각 서버에 헬스체크 요청을 보내요. 응답이 200이면 정상, 아니면 비정상. 

# nginx 예시
upstream backend {
    server srv1 max_fails=3 fail_timeout=30s;
    server srv2 max_fails=3 fail_timeout=30s;
}
# max_fails: 30초 내 3번 실패하면 죽은 걸로 간주
# fail_timeout: 30초 동안 트래픽 안 보냄

헬스체크 엔드포인트는 가벼워야 해요. /health가 일반적이에요. DB·외부 의존을 다 검사하면 LB의 헬스체크 부담이 커져요.

헬스체크의 두 단계: Liveness vs Readiness

  • Liveness: "프로세스가 살아 있나?" 죽으면 재시작 필요.
  • Readiness: "트래픽 받을 준비가 됐나?" 시작 직후, 또는 일시적 과부하 상태면 false.

LB는 보통 Readiness를 봐요. Kubernetes의 자동 재시작은 Liveness를 봐요. 두 개를 잘 나눠야 의도대로 동작해요.

Passive Health Check

실제 요청의 결과로 판단해요. 연속 N번 5xx 응답이면 그 서버를 잠깐 빼는 식이에요. Active만큼 정확하진 않지만 추가 부하가 없어요.

Sticky Session (세션 어피니티)

같은 사용자의 요청을 같은 서버로 보내는 패턴이에요. 서버에 세션을 두는 stateful 시스템에서 필요해요.

두 가지 방법

  • IP 기반 (L4): IP Hash 방식이고, 단순하지만 NAT 문제가 있어요.
  • 쿠키 기반 (L7): LB가 응답에 Set-Cookie: lb=server1 같은 쿠키를 심고, 다음 요청에서 그 쿠키를 보고 같은 서버로 라우팅해요.

Sticky Session의 함정

  • 스케일링 어려움: 사용자가 한 서버에 묶여 있어서 서버를 추가해도 기존 세션은 이동하지 않고, 부하 분산 효과가 줄어요.
  • 장애 시 세션 유실: 그 서버가 죽으면 세션도 사라져요. 다른 서버는 그 세션을 몰라요.
  • 롤링 배포 까다로움: 배포할 때 세션을 가진 서버를 어떻게 처리할지 신경 써야 해요.

현대적 접근은 sticky session 피하기예요. 세션을 외부 저장소(Redis)에 두고 stateless로 가요. 그러면 어느 서버로 보내도 같은 결과를 받아요. LB는 단순 분산만 해요.

LB 자체의 가용성

LB가 단일 장애점이면 의미가 없어요. LB 자체도 이중화해야 해요.

Active-Passive (HA)

LB 두 대 중 하나만 활성이고 나머지는 대기예요. 활성 LB가 죽으면 Virtual IP를 대기 LB로 옮겨요. Keepalived + VRRP가 표준이에요.

Active-Active

두 대 다 동시에 트래픽을 처리해요. DNS 라운드 로빈이나 ECMP로 클라이언트가 둘 중 아무 데나 보내요. 더 효율적이지만 설정이 복잡해요.

클라우드 환경

AWS ALB·NLB, GCP Load Balancer 같은 매니지드 LB는 알아서 다중 AZ에 분산돼서 자체 가용성을 확보해요. 운영팀이 신경 쓰지 않아도 돼요. 클라우드의 장점이에요.

리버스 프록시와의 차이

"Reverse Proxy"와 "Load Balancer"는 거의 같은 의미로 쓰여요. nginx 같은 도구는 둘 다 가능해요. 정확한 차이를 보면 이렇게 나뉘어요.

  • Reverse Proxy: 클라이언트로부터의 요청을 받아 백엔드로 전달하는 중간 계층이에요. 백엔드가 한 서버일 수도 있어요.
  • Load Balancer: 여러 백엔드에 트래픽을 분산해요. Reverse Proxy의 일종이에요.

실무에서는 거의 혼용해요. nginx 한 대가 reverse proxy 역할과 load balancer 역할을 동시에 하는 게 일반적이에요.

면접에서 자주 나오는 자리

  • "L4와 L7 LB 차이?": L4는 IP·포트 수준이고 L7은 HTTP 수준이에요. L4가 빠르고 L7이 라우팅이 풍부해요.
  • "Sticky session이 뭐예요?": 같은 사용자를 같은 서버로 보내는 패턴이에요. 세션을 외부화해서 피하는 게 현대적이에요.
  • "Liveness와 Readiness 차이?": Liveness는 프로세스 생존, Readiness는 트래픽 받을 준비를 보는 거예요. K8s에서 별도로 검사해요.
  • "LB도 죽으면 어떻게 하나요?": 이중화해요. Active-Passive(Keepalived/VRRP)나 클라우드 매니지드로 가요.
  • "TLS는 어디서 풀어요?": 보통 L7 LB에서 풀어요. 내부 트래픽이 평문이 되니 mTLS나 re-encryption을 같이 고려해요.

시리즈 마무리

1편에서는 L4와 L7의 차이, 두 계층의 트레이드오프, 실무에서 두 계층을 같이 쓰는 패턴, TLS 종단 위치 결정을 봤어요. 2편에서는 6가지 분산 알고리즘과 선택 기준, Active/Passive 헬스체크, sticky session의 함정, LB 자체 가용성 확보 방법을 정리했어요.

실무에서는 거의 다 매니지드 LB(AWS ALB/NLB, GCP)를 써서 직접 설정할 일이 줄었어요. 그래도 동작 원리와 트레이드오프를 알면 어떤 자리에 어떤 LB를 쓰고, 어떤 알고리즘을 골라야 할지가 명확해져요.
