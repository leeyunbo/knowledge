Load Balancer가 푸는 문제

단일 서버가 모든 요청을 처리하면 한계가 있어요. CPU·메모리·네트워크 어느 자리든 한계에 부딪쳐요. 여러 서버에 트래픽을 나눠 보내고, 하나가 죽으면 자동으로 다른 서버로 보내는 게 Load Balancer의 역할이에요.

Load Balancer는 어느 OSI 계층에서 동작하느냐로 크게 두 가지로 나뉘어요. L4(전송 계층)와 L7(애플리케이션 계층)이에요. 이 차이가 가시성·성능·기능의 거의 모든 트레이드오프를 만들어요.

OSI 모델 복기

계층이름예시 프로토콜
L7ApplicationHTTP, gRPC, WebSocket
L6PresentationTLS
L5SessionNetBIOS
L4TransportTCP, UDP
L3NetworkIP

L4는 IP·포트 수준이에요. L7은 HTTP 헤더·URL·메서드를 다 들여다볼 수 있어요.

L4 Load Balancer

TCP/UDP 패킷 수준에서 분산해요. 출발 IP·포트와 목적지 IP·포트를 보고 적절한 백엔드 서버로 전달해요.

요청의 내용(HTTP 본문, URL)을 안 봐요. 그냥 TCP 연결을 그대로 한 서버로 보내고, 그 후 모든 패킷은 같은 서버로 흘러요. 빠르고 단순한 발상이에요.

L4의 장점

  • 빠름: 패킷 검사가 적어서 라인 속도에 가까운 처리량이 나와요.
  • 단순함: 프로토콜에 무관해서 HTTP뿐 아니라 어떤 TCP·UDP 트래픽도 분산할 수 있어요.
  • 저비용: CPU 사용량이 낮아서 같은 하드웨어로 더 많은 트래픽을 처리해요.
  • SSL 종단 안 함: 암호화된 트래픽을 그대로 패스해서 인증서를 따로 관리하지 않아도 돼요.

L4의 한계

  • 가시성 부족: HTTP 헤더·URL을 볼 수 없어서 "이 URL은 A 서버로, 저 URL은 B 서버로" 같은 분기를 할 수 없어요.
  • 세션 어피니티가 IP 기반: 같은 클라이언트 IP는 같은 서버로 보낼 수 있지만, 회사 사용자가 NAT 뒤에 있으면 모두 같은 IP로 보여서 한 서버에 몰려요.
  • L7 기능 부재: 쿠키 기반 라우팅, 헤더 변환, 압축, 캐싱, WAF 같은 기능이 없어요.

대표 구현

  • HAProxy (mode tcp): L4·L7 둘 다 가능하고 광범위하게 써요.
  • nginx stream: nginx의 stream 모듈로 TCP·UDP를 분산해요.
  • AWS NLB (Network Load Balancer): 클라우드 L4로 ms 단위 지연이에요.
  • IPVS / LVS: 리눅스 커널 수준 L4 분산이고 매우 빨라요.

L7 Load Balancer

HTTP 요청 수준에서 분산해요. URL·헤더·메서드·쿠키를 다 들여다보고 라우팅을 결정해요.

L7이 가능한 라우팅 예시예요.

  • GET /api/users/... → user-service 풀
  • GET /api/orders/... → order-service 풀
  • GET /static/... → CDN 또는 static-server
  • Cookie: experiment=B → 새 버전 서버 (A/B 테스트)
  • Accept: image/webp → WebP 변환 서버

L7의 장점

  • 높은 가시성: HTTP의 모든 정보를 다룰 수 있어서 라우팅 규칙이 풍부해요.
  • 경로 기반 라우팅: 같은 도메인 안에서 URL에 따라 다른 서비스로 보낼 수 있어서 MSA 환경의 핵심이에요.
  • WAF·인증·압축·캐싱: HTTP 레벨의 다양한 처리를 LB가 담당해서 백엔드 부담이 줄어요.
  • 세션 어피니티 정교화: 쿠키 기반으로 NAT 문제를 피할 수 있어요.
  • SSL 종단 (TLS termination): LB가 HTTPS를 풀어서 내부는 HTTP로 통신하고, 인증서를 한 자리에서 관리해요.

L7의 한계

  • 느림: HTTP 파싱·헤더 검사 비용이 있어서 L4보다 수십 ms 정도 더 걸릴 수 있어요.
  • CPU 부하 큼: HTTPS 종단까지 하면 암호화·복호화 부담이 있어서 같은 하드웨어로 처리할 수 있는 트래픽이 적어요.
  • 프로토콜 의존: HTTP 전용이라 TCP의 다른 프로토콜은 다룰 수 없어요.

대표 구현

  • nginx: 가장 광범위하게 쓰고, 정적 파일 서빙·리버스 프록시·캐싱을 해요.
  • HAProxy (mode http): L7 라우팅과 헬스체크가 강력해요.
  • Envoy: 서비스 메시(Istio, Linkerd)의 기반이고, gRPC·HTTP/2·HTTP/3을 모두 지원해요.
  • AWS ALB (Application Load Balancer): 클라우드 L7이에요.
  • API Gateway: L7 LB에 인증·rate limit·변환을 더했어요. Kong, Spring Cloud Gateway, AWS API Gateway가 있어요.

실무에서는 둘 다 같이 써요

현대 시스템은 보통 L4 + L7 조합이에요. 외부 트래픽이 L4로 먼저 들어와서 여러 L7 인스턴스로 분산되고, 각 L7이 다시 백엔드 서비스로 라우팅해요. 두 계층의 강점을 같이 가져요.

L4가 처리량을, L7이 라우팅 정교함을 담당해요. 클라우드 환경의 표준 패턴이에요. AWS면 NLB → ALB → ECS로 가고, 온프레미스면 LVS → nginx → 백엔드로 가요.

TLS 종단 위치 결정

실무에서 자주 헷갈리는 자리예요. TLS를 어디서 풀지가 중요한 결정이에요.

방식설명장단점
TLS PassthroughL4가 암호화된 TCP를 그대로 백엔드로인증서 LB에 없음 / L7 기능 못 씀
TLS TerminationL7이 HTTPS 풀어 백엔드는 HTTPL7 기능 모두 가능 / 내부 트래픽 평문
TLS Re-encryptionL7이 풀고 다시 백엔드로 HTTPS완전 암호화 / 비용 두 배

많은 경우 TLS Termination이 일반적이에요. 내부 망을 신뢰할 수 있다고 가정해요. 금융처럼 내부도 의심해야 하는 자리는 Re-encryption이나 mTLS를 써요.
