분산 캐시

캐시도 한 노드로는 부족해요. 여러 노드에 분산하는 메커니즘과 그에 따른 트레이드오프를 봐요.

왜 분산이 필요한가요

단일 캐시 노드의 한계는 명확해요.

  • 메모리 한계 — 한 서버 RAM이 한정적 (보통 수백 GB)
  • 처리량 한계 — 한 노드의 RPS 처리 한계
  • 가용성 — 한 노드 다운 시 모든 캐시 손실
  • 네트워크 latency — 다른 region에 모든 클라이언트가 접근 시 느림

그래서 캐시도 결국 분산해야 해요. 두 가지 차원이 있어요. Partitioning(데이터 분산)과 Replication(복제).

Partitioning — 데이터 분산

전체 데이터셋을 여러 노드에 나눠 저장. 각 노드가 일부 키만 담당. 용량과 처리량이 노드 수에 비례해 늘어나요.

가장 단순한 — modulo hash

node_index = hash(key) % N (전체 노드 수)

단순하지만 큰 함정이 있어요. 노드를 추가하거나 제거하면 거의 모든 키의 매핑이 바뀌어요. 전체 캐시가 무효화되어 DB로 폭주하는 cache stampede 위험.

Consistent Hashing — 표준 패턴

이 함정을 푸는 알고리즘이에요. 1997년 MIT가 제안했고 모던 분산 시스템의 표준이 됐어요.

  1. 해시 공간을 0 ~ 2^32-1 같은 큰 ring으로 표현
  2. 각 노드를 hash로 ring 위 한 점에 배치
  3. 키도 hash로 ring 위 한 점에 배치
  4. 키는 자기 위치에서 시계방향으로 가장 가까운 노드에 저장

장점

노드 추가/제거 시 영향 범위가 작아요. 한 노드를 추가하면 그 노드 위치의 인접 키들만 새 노드로 이동. 전체의 1/N만 재배치돼요. 다른 키들은 그대로 매핑 유지.

단점과 보완 — Virtual Node

노드를 ring 위에 그냥 놓으면 분포가 균일하지 않을 수 있어요. 한 노드가 큰 영역, 다른 노드가 작은 영역을 담당. 부하 불균형 발생.

해결은 한 물리 노드를 여러 가상 노드(virtual node, vnode)로 ring에 배치. 보통 100~1000개. 분포가 통계적으로 더 균일해져서 부하가 골고루 분산.

Redis Cluster의 분산

Redis는 자체 분산 메커니즘이 있어요. Consistent hashing이 아닌 hash slot 방식.

Hash Slot

  • 전체 키 공간을 16384개의 슬롯으로 나눔
  • 키의 CRC16 해시를 16384로 나눈 나머지로 슬롯 결정
  • 각 슬롯이 어느 노드에 할당되는지는 클러스터가 관리
  • 노드 추가/제거 시 슬롯 단위로 재할당
slot = CRC16(key) % 16384

Hash Tag로 같은 슬롯 강제

여러 키를 같은 슬롯에 두려면 hash tag를 사용해요. 중괄호로 감싼 부분이 hash 계산에 사용돼요. 

{user:123}:profile     → slot 같음
{user:123}:settings    → slot 같음
{user:123}:notifications → slot 같음

# 모두 같은 슬롯이라 한 노드에서 atomic 트랜잭션 가능

Lua 스크립트, MULTI/EXEC, 분산 락 같이 여러 키를 atomic하게 다뤄야 할 때 필수예요. slot이 다르면 cross-slot 작업 불가.

Replication — 복제

한 노드에만 데이터를 두면 그 노드 다운 시 데이터 손실. Replication으로 같은 데이터를 여러 노드에 둬요.

Master-Replica

한 master가 쓰기 받고, 여러 replica가 master의 변경을 비동기로 따라가는 구조. 가장 흔한 패턴.

  • 쓰기는 항상 master로
  • 읽기는 master 또는 replica 어디든 가능
  • master 다운 시 replica 중 하나를 새 master로 promotion (failover)
  • 비동기 복제라 master 다운 시 일부 데이터 손실 가능

Multi-Master

여러 master가 모두 쓰기를 받고 서로 동기화. 이론적으로 가능하지만 충돌 해결이 어려워서 캐시 환경에선 잘 안 써요. DynamoDB Global Tables 같은 일부 시스템에서 사용.

Sharding + Replication 조합

실무에서는 두 차원을 함께 써요. Sharding으로 데이터를 나누고, 각 shard마다 replication. 

전체 키
  ├── Shard 1 (Master + 2 Replica)
  ├── Shard 2 (Master + 2 Replica)
  ├── Shard 3 (Master + 2 Replica)
  └── Shard N (Master + 2 Replica)

Redis Cluster의 표준 구성. Master 3 + Replica 3이 최소 권장 구성이에요.

분산 캐시의 일관성 함정

Master-Replica 비동기 복제

분산 락 시리즈에서 본 함정. master에 쓴 데이터가 replica에 전파되기 전 master 다운. replica가 새 master로 promotion되면 그 쓰기는 사라짐.

해결

  • WAIT 명령어 — 일정 수의 replica에 전파될 때까지 대기 (Redis)
  • min-replicas-to-write 설정 — 일정 수 replica가 살아있어야만 쓰기 허용
  • Synchronous replication — 매우 비싼 비용

캐시는 일반적으로 손실 허용이라 비동기 복제로 충분. critical 데이터는 캐시에 두지 않는 게 답.

분산 캐시의 운영 패턴

Cache Warming

새 노드 추가 또는 캐시 비우기 후 cold cache 상태에서 모든 요청이 DB로 몰림. warming 작업으로 미리 자주 쓰이는 데이터를 캐시에 채워두는 패턴.

Cache Pre-warming

Deployment 직전에 새 인스턴스의 로컬 캐시를 채우는 작업. 첫 요청부터 캐시 hit.

Hot Key 모니터링

소수의 키가 트래픽 대부분을 받는 hot key 패턴. 그 키가 위치한 노드만 부하 집중. 모니터링으로 hot key 발견 시 대응.

  • 해당 키를 여러 노드에 복제 (랜덤 routing)
  • 로컬 cache로 분산
  • 키 자체를 분할 (counter:user:123 → counter:user:123:shard:0~9)

모니터링 메트릭

  • cache hit ratio (높을수록 좋음, 90%+ 권장)
  • memory usage 노드별
  • QPS (queries per second) 노드별
  • P99 latency
  • eviction rate (메모리 부족으로 키가 쫓겨나는 빈도)

면접 단골 질문

Q. modulo hash와 consistent hashing의 차이는요?

modulo는 단순하지만 노드 추가/제거 시 거의 모든 키의 매핑이 바뀌어요. 전체 캐시 무효화로 DB 폭주 위험. consistent hashing은 노드를 hash ring에 배치해서, 추가/제거 시 인접 노드의 일부 키만 재배치돼요. 영향이 1/N로 작아서 모던 분산 시스템의 표준이에요.

Q. Redis Cluster의 hash slot이 뭔가요?

Redis는 consistent hashing이 아닌 16384개 hash slot으로 키를 분산해요. 키의 CRC16을 16384로 나눈 나머지가 슬롯 번호. 슬롯이 어느 노드에 할당되는지는 클러스터가 관리. 노드 추가/제거 시 슬롯 단위로 재할당. 여러 키를 같은 슬롯에 두려면 hash tag를 사용해요.

Q. Hash Tag는 언제 쓰나요?

여러 키를 한 노드에서 atomic하게 다뤄야 할 때 써요. {user:123}:profile처럼 중괄호 안의 부분이 hash 계산에 사용되어, 중괄호 안이 같은 키들은 같은 슬롯에 위치. Lua 스크립트, MULTI/EXEC, 분산 락 같은 cross-key 작업에 필수. 단, hot spot 만들 위험 있어 신중히 사용.

Q. Master-Replica 비동기 복제의 함정은요?

master에 쓴 데이터가 replica에 전파되기 전 master가 다운되면 그 쓰기가 사라질 수 있어요. 새 master로 promotion된 replica는 그 데이터를 모르거든요. 캐시는 보통 손실 허용이라 비동기 복제로 충분하지만, 락 같은 critical 데이터엔 위험해요. Redlock이나 ZooKeeper 같은 강한 일관성 시스템 검토가 필요해요.

한 줄 정리

분산 캐시는 partitioning과 replication 두 차원이 있어요. Partitioning은 consistent hashing 또는 hash slot으로, replication은 master-replica가 표준. 비동기 복제로 인한 일시적 손실 가능성이 있지만 캐시 특성상 받아들일 수 있어요. Hot key 모니터링과 warming 같은 운영 패턴이 분산 캐시의 안정성을 좌우해요.
