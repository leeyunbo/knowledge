푸는 문제

"여러 작업이 모두 끝나야 다음 단계로 넘어가는" 자리예요. 5개 외부 API 호출이 모두 끝나야 결과를 합치거나, 초기화 5단계가 모두 완료돼야 서버를 시작하는 자리예요. CountDownLatch가 가장 단순한 도구예요.

기본 사용

CountDownLatch latch = new CountDownLatch(5);  // 5번 줄어들면 0

for (int i = 0; i < 5; i++) {
    executor.submit(() -> {
        try {
            doWork();
        } finally {
            latch.countDown();  // 카운터 -1
        }
    });
}

latch.await();  // 0이 될 때까지 대기
System.out.println("모두 끝남");

주요 메소드

메소드의미
countDown()카운터를 1 감소. 0 이하가 되면 무시.
await()0이 될 때까지 대기.
await(t, unit)timeout 안에서 대기. 0이면 true.
getCount()현재 카운터. 디버깅·관측 용도.

일회용

CountDownLatch는 한 번 0이 되면 끝이에요. 다시 N으로 리셋할 수 없어요. 재사용이 필요하면 다음 시리즈의 CyclicBarrier를 써요.

흔한 자리

1. Fan-out / Fan-in

여러 호출을 동시에 보내고 결과를 모아요. CompletableFuture.allOf로 더 깔끔하게 할 수 있지만, 동시성 라이브러리만 쓸 수 있는 환경에선 latch가 유용해요.

2. 초기화 대기

서버 시작 시 여러 구성 요소가 초기화되길 기다려요. main 스레드가 await에서 멈추고, 각 초기화 코드가 끝날 때 countDown.

3. 테스트

멀티스레드 테스트에서 "모든 스레드가 끝날 때까지 대기"를 표현해요. JUnit과 같이 자주 써요.

흔한 실수

1. countDown을 try-finally 밖에 두기

// 위험
executor.submit(() -> {
    doWork();         // 예외 시 countDown이 안 됨
    latch.countDown();
});

// 안전
executor.submit(() -> {
    try {
        doWork();
    } finally {
        latch.countDown();
    }
});

예외가 나면 countDown이 안 돼서 main이 영원히 await에 갇혀요. 항상 finally에 둬요.

2. 카운터 잘못 계산

N을 잘못 잡으면 영원히 대기하거나 너무 빨리 풀려요. 작업 수와 카운터가 정확히 일치해야 해요.

3. await에 timeout 없음

무한 await는 위험해요. 어떤 작업이 죽으면 main도 같이 멈춰요. await(timeout)으로 안전망을 둬요.

면접에서 자주 나오는 자리

  • "CountDownLatch와 CyclicBarrier 차이?": Latch는 일회용. 0이 되면 끝. Barrier는 N명이 모이면 풀리고 다시 모일 수 있어요.
  • "countDown을 어디에?": try-finally의 finally예요. 예외가 나도 카운터가 줄어들어야 해요.
  • "CompletableFuture와 비교?": Future가 풍부한 API와 조합 가능. Latch는 단순하지만 결과 수집은 별도 처리가 필요해요. 새 코드는 보통 CompletableFuture가 더 깨끗해요.
