Reverse Proxy와 무엇이 다른가

API Gateway는 사실 Reverse Proxy의 확장이에요. 모든 API Gateway는 reverse proxy 기능을 포함해요. 거기에 API 운영에 특화된 기능을 더 얹은 거예요. 경계가 흐릿하지만 보통 다음 기능 중 다수를 갖추면 "Gateway"라고 불러요.

핵심 기능 1: 인증·인가

마이크로서비스 환경에서 각 서비스가 인증을 따로 구현하면 코드 중복과 정책 불일치가 일어나요. Gateway가 단일 진입점에서 검증하면 백엔드는 비즈니스 로직에만 집중해요.

흔한 패턴

  • API Key: 헤더의 키를 화이트리스트와 비교. 단순하지만 회전·폐기가 어려워요.
  • JWT 검증: 토큰의 서명과 만료를 확인해요. 사용자 정보를 백엔드에 헤더로 전달해요.
  • OAuth 2.0 / OIDC: Gateway가 IdP와 연동해 토큰을 받아 검증해요. 사용자 정보를 백엔드에 전달해요.
  • mTLS: 서비스 간 통신에서 양방향 인증을 해요. 내부 메시 환경에서 써요.
# Kong JWT 플러그인 예시
plugins:
- name: jwt
  config:
    secret_is_base64: false
    key_claim_name: iss
    claims_to_verify:
    - exp

핵심 기능 2: Rate Limit과 Quota

Rate Limiting 시리즈에서 본 그 자리예요. Gateway는 사용자별·API key별·엔드포인트별로 차등 정책을 적용해요. 무엇보다 한 곳에서 관리되니 정책 일관성이 보장돼요. 

# Kong rate-limiting
plugins:
- name: rate-limiting
  config:
    minute: 100
    hour: 10000
    policy: redis
    redis_host: redis.example.com

특히 SaaS API 운영에선 quota가 필수예요. Free tier는 분당 100번, Pro tier는 1000번 같은 차등을 Gateway에서 처리해요. 백엔드는 quota 검사 부담이 없어요.

핵심 기능 3: Request·Response Transformation

외부 API 스펙과 내부 서비스 스펙이 다를 수 있어요. Gateway가 중간에서 변환해요.

흔한 변환 자리

  • 외부엔 REST, 내부는 gRPC인 환경. Gateway가 중간에서 변환해요.
  • 구버전 API 응답 형식을 그대로 유지하면서 새 백엔드를 쓰는 자리예요.
  • 외부에 보여줄 필요 없는 내부 필드를 응답에서 제거해요.
  • 헤더 변환·재작성을 해요. Authorization을 검증한 뒤 X-User-Id로 백엔드에 전달해요.
# Kong request-transformer
plugins:
- name: request-transformer
  config:
    add:
      headers:
      - X-Internal-Service:gateway
    remove:
      headers:
      - Authorization

핵심 기능 4: API 버저닝·카나리

외부에는 /api/v1/orders가 안정적으로 유지돼야 해요. 내부에선 새 버전을 점진적으로 배포하고 싶어요. Gateway에서 트래픽을 비율로 나눠요. 

# Spring Cloud Gateway 가중치 라우팅
spring:
  cloud:
    gateway:
      routes:
      - id: orders-v1
        uri: lb://orders-service-v1
        predicates:
        - Path=/api/orders/**
        - Weight=group1, 80
      - id: orders-v2
        uri: lb://orders-service-v2
        predicates:
        - Path=/api/orders/**
        - Weight=group1, 20

카나리 배포·A/B 테스트·블루그린이 모두 Gateway 한 자리에서 제어돼요. 점진적으로 100%로 올려 가는 방식이 안전해요.

BFF 패턴 (Backend for Frontend)

Gateway의 변종 패턴이에요. 클라이언트 종류(웹, 모바일 앱, 외부 파트너)에 따라 다른 응답 형식과 다른 데이터 조합이 필요할 때 써요.

왜 필요한가

  • 모바일은 데이터 사용량 제약이 있어 응답을 작게 받고 싶어요. 웹은 화면이 크니 더 많은 정보가 필요해요.
  • 한 화면을 그리는데 5개 마이크로서비스에 호출해야 하는 자리. 클라이언트가 5번 호출하면 모바일 네트워크에선 느려요. BFF가 한 번에 모아 줘요.
  • 외부 파트너에겐 일부 필드를 숨겨야 해요. BFF가 필터링해요.

주의 자리

BFF가 늘어나면 코드 중복이 늘어요. 공통 로직(인증, 로깅)은 라이브러리로 빼고, 각 BFF는 클라이언트별 변환에만 집중해야 해요. BFF가 너무 두꺼워지면 마이크로서비스 분리 효과가 사라져요.

관측성 (Observability)

Gateway는 모든 요청이 지나가는 자리라 관측성에 최적이에요. API 단위로 다음 지표를 수집해요.

  • API별 호출 수 (RPS).
  • API별 응답 시간 분포 (P50, P95, P99).
  • API별 에러율 (4xx, 5xx 비율).
  • 사용자·API key별 사용량.
  • 각 API의 quota 사용 비율.

분산 트레이싱(OpenTelemetry, Zipkin)도 Gateway에서 trace ID를 생성하는 게 일반적이에요. 같은 trace ID가 모든 백엔드에 전파돼 한 요청의 전체 흐름을 추적할 수 있어요.

Gateway 안티패턴: 비즈니스 로직 끼워 넣기

Gateway가 워낙 강력해서 비즈니스 로직까지 거기에 두는 유혹이 있어요. "주문 생성 시 사용자 등급 확인"을 gateway에서 하는 식이에요. 위험해요.

  • Gateway가 한 곳의 변경에 자주 영향받아요. 배포 부담이 커져요.
  • 비즈니스 규칙이 코드 두 곳(백엔드와 gateway)에 흩어져 디버깅이 어려워져요.
  • Gateway 자체가 가용성의 단일 장애점이 돼요.

Gateway에는 횡단 관심사(cross-cutting concerns)만 두세요. 인증, rate limit, 로깅, 라우팅, 변환이에요. 도메인 로직은 백엔드에 있어야 해요.

Gateway 자체의 가용성

Gateway가 죽으면 모든 API가 죽어요. 단일 장애점이 되지 않게 다음을 신경 써요.

  • 여러 인스턴스로 수평 확장해요. 보통 Active-Active로 구성해요.
  • 앞단에 Load Balancer를 둬서 gateway 자체를 분산해요.
  • 설정 변경 시 무중단 reload를 지원해야 해요. nginx의 nginx -s reload, Envoy의 hot restart가 그 예예요.
  • 관측성 알람을 강하게 걸어요. Gateway가 5xx를 내면 즉시 알람이 가야 해요.

면접에서 자주 나오는 자리

  • "Reverse Proxy와 API Gateway 차이?": Gateway는 Reverse Proxy + API 운영 기능(인증·rate limit·변환·버저닝)이에요. 경계는 흐릿하고 점진적으로 더해 가는 거예요.
  • "BFF가 뭐예요?": 클라이언트 종류별로 별도 Gateway를 두는 패턴이에요. 웹·모바일·파트너가 각각 다른 BFF를 쓰고, BFF가 각 클라이언트에 맞춰 데이터를 조합해 줘요.
  • "Gateway에 비즈니스 로직을 넣어도 돼요?": 안 돼요. 횡단 관심사(인증·rate limit·로깅·변환)만 두고, 도메인 로직은 백엔드에 둬야 해요. 안 그러면 배포 부담과 디버깅 어려움이 커져요.
  • "Gateway가 죽으면?": 모든 API가 죽어요. 여러 인스턴스로 수평 확장, 앞단 LB, 무중단 reload, 강한 알람으로 가용성을 보장해야 해요.
