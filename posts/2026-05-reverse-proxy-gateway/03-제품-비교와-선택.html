nginx

HTTP 서버이자 reverse proxy의 사실상 표준이에요. C로 만들어 빠르고 메모리도 가벼워요. 정적 파일 서빙, reverse proxy, 기본 LB까지 한 자리에서 처리해요.

장점

  • 성능이 압도적이에요. 단일 인스턴스로 10만 RPS도 가능해요.
  • 설정이 직관적이에요. nginx.conf 하나면 돼요.
  • 커뮤니티가 크고 자료가 풍부해요.

한계

  • 동적 설정이 약해요. 백엔드 추가·제거 시 reload가 필요해요.
  • 인증·JWT 같은 고급 기능은 nginx-plus(유료)나 OpenResty(Lua 확장)가 필요해요.
  • 관측성이 기본만 있어요. Prometheus exporter 별도 설치.

잘 맞는 자리

단순한 reverse proxy, 정적 파일 서빙, 기본 로드 밸런싱이면 nginx면 충분해요. 가장 많이 쓰이는 이유가 있어요.

HAProxy

L4·L7 모두 강력한 로드 밸런서예요. 헬스체크와 세션 sticky에 강하고, 통계 페이지가 풍부해요. nginx와 자주 비교되는 자리예요.

  • L4 모드(mode tcp)에선 매우 빨라요. 데이터베이스·Redis 같은 TCP 프록시에 잘 맞아요.
  • nginx보다 LB 정책이 더 다양해요. roundrobin, leastconn, source, uri 등.
  • 정적 파일 서빙은 못해요. 순수 LB·proxy 전용이에요.

Envoy

서비스 메시(Istio, Linkerd)의 데이터 플레인이고 Edge proxy로도 쓰여요. 가장 강력한 기능과 가장 가파른 학습 곡선을 가져요.

특징

  • 완전 동적 설정. xDS API로 런타임에 라우팅·백엔드를 갱신해요.
  • HTTP/2·gRPC·HTTP/3을 1급 시민으로 지원해요.
  • 관측성이 탁월. Prometheus 메트릭, distributed tracing, access log가 풍부해요.
  • 설정이 매우 자세해요. YAML이 길어지는 게 단점이에요.

잘 맞는 자리

마이크로서비스 환경, gRPC 트래픽, 강한 관측성이 필요한 자리예요. Kubernetes의 ingress 또는 서비스 메시의 사이드카로 광범위하게 쓰여요.

Kong

nginx + Lua(OpenResty) 기반 API Gateway예요. 플러그인 생태계가 가장 풍부해요. JWT, OAuth, rate limit, request transformer 등을 플러그인으로 끼워 넣어요.

특징

  • 플러그인이 100여 개예요. 인증·관측성·변환을 거의 다 지원해요.
  • 관리 UI(Kong Manager), 개발자 포털(Kong Dev Portal)이 있어요.
  • 설정은 DB 모드(Postgres·Cassandra)와 DB-less 모드로 나뉘어요. 운영 방식이 달라요.
  • nginx 위에 얹은 거라 nginx의 빠른 성능을 그대로 가져가요.

잘 맞는 자리

외부 API를 다루는 SaaS, 파트너 통합이 많은 환경, 인증·rate limit 같은 정책을 한 곳에서 통합 관리하고 싶을 때예요.

Spring Cloud Gateway

JVM 기반 API Gateway예요. Spring Boot 코드로 작성하고, Project Reactor 위에 만들어졌어요. Spring 생태계와 자연스럽게 통합돼요.

장점

  • Spring 코드와 같은 언어·도구로 작성해요. 디버깅·테스트가 편해요.
  • Spring Cloud의 service discovery(Eureka)와 자동으로 통합돼요.
  • 커스텀 필터를 자바·코틀린으로 작성해요. 비표준 변환이 쉬워요.

한계

  • JVM이라 메모리·CPU 부담이 nginx·Envoy보다 커요.
  • 처리량이 nginx의 절반 정도예요. 매우 큰 규모엔 부적합해요.
  • Netflix Zuul처럼 단종 위험이 있는 자리이긴 해요. Spring Cloud 의존이 커요.

잘 맞는 자리

Spring Boot 기반 마이크로서비스, JVM 팀이 운영하는 자리예요. 별도 nginx·Kong 운영 부담 없이 JVM으로 통일하고 싶을 때 좋아요.

AWS API Gateway

매니지드 서비스예요. 인프라 운영 부담이 0이에요. AWS Lambda·Cognito와 깊게 통합돼요.

장점

  • 운영 부담이 거의 없어요. 자동으로 확장되고 가용성도 챙겨 줘요.
  • AWS Cognito로 인증, IAM으로 인가, CloudWatch로 관측성을 가져가요.
  • WebSocket, REST, HTTP API를 모두 지원해요. HTTP API는 더 싸고 빨라요.

한계

  • 비용이 단점이에요. 호출당 과금이 있어 대량 트래픽엔 비싸요.
  • AWS lock-in이 있어요. 다른 클라우드로 옮기기 어려워요.
  • 비표준 변환·복잡한 라우팅은 제한적이에요. 단순 패턴만 가능해요.
  • Cold start와 latency가 인스턴스 기반보다 살짝 높아요.

Traefik

Kubernetes·Docker 환경에 특화된 reverse proxy·gateway예요. 컨테이너가 시작·종료되면 자동으로 라우팅 설정이 갱신돼요.

  • K8s ingress와 Docker label로 자동 디스커버리를 해요.
  • Let's Encrypt 자동 인증서 발급·갱신이 기본으로 내장돼 있어요.
  • 설정이 단순해요. YAML이나 라벨로 짧게 작성해요.
  • 대규모 트래픽엔 nginx·Envoy보다 처리량이 낮아요.

배포 패턴

1. Edge에 단일 Gateway

외부 트래픽이 들어오는 가장 바깥에 Gateway 하나. 모든 인증·rate limit·라우팅이 여기서 일어나요. 가장 단순하고 운영도 쉬워요. 작은 규모엔 충분해요.

2. Edge Gateway + 내부 Service Mesh

Edge는 Kong/AWS API Gateway 같은 외부 노출용으로 두고, 내부 서비스 간 통신은 Envoy 사이드카로 처리해요. 외부와 내부 트래픽의 책임이 분리돼요. 대규모 마이크로서비스에서 일반적이에요.

3. 클라이언트별 BFF + 내부 Gateway

각 클라이언트(웹, 모바일, 파트너)마다 별도 BFF. BFF 뒤에 공통 internal gateway가 있어요. 외부 진입점이 클라이언트 종류에 따라 갈리지만, 내부 라우팅·정책은 통합돼요.

운영 실수

1. 설정 reload 누락

nginx 설정을 바꿨는데 reload를 안 하면 새 설정이 안 적용돼요. CI/CD에 항상 nginx -t(검증) 후 reload를 포함시켜요.

2. 인증서 만료

자동 갱신이 안 돼서 인증서가 만료되면 모든 HTTPS가 죽어요. Let's Encrypt 사용 시 cert-manager·certbot의 자동 갱신을 확인해요. 만료 30일 전 알람.

3. Gateway 한 곳에 모든 변경

Gateway가 강력해서 거기에 모든 변경(라우팅·헤더·rate limit 정책)을 모으는 유혹이 있어요. 자주 변경되면 Gateway 자체의 변경 부담이 커지고, 한 실수가 모든 API에 영향을 줘요. 변경 정책과 테스트가 필수예요.

4. WebSocket / SSE 누락

Gateway가 WebSocket을 모르거나 SSE(Server-Sent Events)의 long-lived connection을 지원 안 하면 클라이언트가 끊겨요. 사용 전에 반드시 검증해요.

5. 헬스체크 엔드포인트 보호

Gateway는 자기 헬스체크 엔드포인트를 노출해서 LB가 검사하게 해요. 그런데 이 엔드포인트가 외부에서도 접근되면 정보 노출이에요. 내부망에서만 접근 가능하도록 분리해요.

관측성 통합

Gateway는 관측성의 첫 진입점이에요. 다음 도구를 같이 연결해요.

  • Prometheus + Grafana: RPS, latency, error rate를 API 단위로.
  • 분산 트레이싱: Gateway에서 trace ID 생성, 백엔드까지 전파. OpenTelemetry가 표준.
  • 중앙 로깅: ELK·Loki로 access log 수집. trace ID로 한 요청의 흐름을 연결.
  • 알람: 4xx 비율 급증, 5xx 발생, P99 폭증 같은 신호.

면접에서 자주 나오는 자리

  • "nginx와 Kong 차이?": Kong은 nginx 위에 Lua로 API Gateway 기능을 얹은 거예요. nginx보다 무겁지만 플러그인이 풍부해요.
  • "Envoy는 언제 써요?": 서비스 메시, gRPC, 강한 관측성이 필요할 때예요. Istio·Linkerd의 데이터 플레인이고 Edge proxy로도 가능해요.
  • "Spring Cloud Gateway의 한계?": JVM 기반이라 메모리·CPU 부담이 nginx·Envoy보다 커요. 처리량도 절반 정도예요. Spring 통합이 강점이지만 매우 큰 규모엔 부적합해요.
  • "AWS API Gateway가 좋은 자리?": 운영 부담을 줄이고 싶고 AWS Lambda 기반이면 좋아요. 단점은 비용과 lock-in이에요.
  • "Gateway의 단일 장애점 우려?": 여러 인스턴스로 수평 확장하고 앞단 LB를 두세요. 무중단 reload, 강한 알람, 카나리 배포로 변경 위험도 낮춰요.

시리즈 마무리

1편에서 Forward Proxy와 Reverse Proxy의 차이, Reverse Proxy의 6가지 역할(단일 진입점·보안·LB·SSL termination·캐싱·정적 서빙)을 봤어요. 2편에서 API Gateway가 reverse proxy에 인증·rate limit·변환·버저닝·BFF를 더한 layer라는 걸 정리했고요. 3편에서는 nginx·HAProxy·Envoy·Kong·Spring Cloud Gateway·AWS API Gateway·Traefik의 강점과 선택 매트릭스를 다뤘어요.

핵심은 단순해요. 요구가 늘어나는 만큼 Gateway가 두꺼워져요. 단순한 자리는 nginx면 충분하고, 외부 API 운영이 본격화되면 Kong이나 매니지드 Gateway로 가요. 비즈니스 로직은 백엔드에 두고, Gateway엔 횡단 관심사만 둬야 시스템이 깨끗하게 유지돼요.
