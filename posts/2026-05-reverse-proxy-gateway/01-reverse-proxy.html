Forward Proxy vs Reverse Proxy

같은 "프록시"라는 단어를 써서 헷갈리지만, 두 가지는 정반대 자리예요. 누구의 대리인이냐가 다르다고 생각하면 쉬워요.

구분Forward ProxyReverse Proxy
위치클라이언트 쪽서버 쪽
대리하는 쪽클라이언트서버
주된 자리회사 인터넷 차단·캐싱, VPN로드 밸런싱, SSL termination, 캐싱
대표 예Squid, 회사 프록시nginx, HAProxy, Envoy

Reverse Proxy가 풀어 주는 문제

Reverse Proxy 없이 서버를 직접 노출하면 여러 문제가 생겨요. Reverse Proxy는 그 사이를 막아 주는 layer가 돼요.

1. 단일 진입점

내부에 서비스가 여러 개여도 외부에서는 하나의 IP·도메인만 봐요. 내부 구조가 바뀌어도 외부 클라이언트는 영향을 안 받아요.

2. 보안

실제 서버의 IP가 노출되지 않아요. 공격자가 내부 서버를 직접 못 때려요. WAF·rate limit·인증을 한 자리에서 검사하니 보안 정책이 일관돼요.

3. 부하 분산

여러 백엔드 서버로 요청을 나눠요. Load Balancer 시리즈에서 자세히 본 그 자리예요. 한 서버가 죽어도 다른 서버로 우회해요.

4. SSL Termination

HTTPS를 풀어서 내부 망에서는 HTTP로 통신해요. 내부 서버는 인증서 관리에서 자유로워요.

5. 캐싱

자주 요청되는 응답을 메모리·디스크에 보관해요. 백엔드까지 안 가도 응답해서 성능이 올라가요. nginx의 proxy_cache가 대표예요.

6. 압축·정적 파일 서빙

gzip·brotli 압축을 reverse proxy가 처리하면 백엔드 부담이 줄어요. 정적 파일(이미지, JS, CSS)은 nginx가 직접 서빙하면 백엔드를 거치지 않고 빠르게 응답해요.

가장 단순한 nginx 설정

server {
    listen 443 ssl;
    server_name api.example.com;

    ssl_certificate     /etc/ssl/cert.pem;
    ssl_certificate_key /etc/ssl/key.pem;

    location / {
        proxy_pass http://backend:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

HTTPS를 받아 풀고, 내부 백엔드(backend:8080)에 HTTP로 전달해요. 클라이언트 정보를 헤더로 백엔드에 전달해요. 30줄 미만으로 기본 reverse proxy가 완성돼요.

X-Forwarded-* 헤더의 의미

Reverse Proxy를 거치면 백엔드 입장에서 모든 요청이 reverse proxy IP로 보여요. 진짜 클라이언트 정보는 헤더로 전달해야 해요.

헤더의미
X-Forwarded-For원본 클라이언트 IP (체인이면 쉼표 분리)
X-Forwarded-Proto원본 프로토콜 (http / https)
X-Forwarded-Host원본 Host 헤더
X-Real-IPnginx 특화. 직전 hop의 IP
ForwardedRFC 7239 표준. 위 헤더의 통합본

X-Forwarded-For 신뢰 자리

클라이언트가 직접 보낸 X-Forwarded-For는 신뢰하면 안 돼요. 누구나 가짜 IP를 헤더에 넣을 수 있어요. Reverse Proxy가 받은 직후 자기가 덮어쓰는 것만 믿을 수 있어요. 

# 잘못된 설정: 클라이언트 헤더를 그대로 전달
proxy_set_header X-Forwarded-For $http_x_forwarded_for;

# 올바른 설정: proxy가 알아서 체인을 만듦
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

캐싱의 효과

Reverse Proxy 캐싱은 단순한 변경이지만 성능에 큰 영향을 줘요. 백엔드 응답 시간이 200ms인 API를 nginx가 1초 캐시하면, 같은 요청이 1초 안에 10번 와도 백엔드는 1번만 호출돼요. 

proxy_cache_path /var/cache/nginx levels=1:2
    keys_zone=api_cache:10m max_size=1g inactive=60m;

location /api/products {
    proxy_cache api_cache;
    proxy_cache_valid 200 1m;
    proxy_cache_key "$request_method$request_uri";
    proxy_pass http://backend;
}

캐시 무효화

캐시의 가장 어려운 자리예요. 데이터가 변경됐는데 캐시가 오래된 응답을 주면 사용자가 잘못된 정보를 봐요. Cache-Control 헤더를 백엔드가 잘 설정해야 하고, 변경 시 명시적 무효화(proxy_cache_purge) 또는 짧은 TTL을 두어 자연 만료를 노려요.

SSL Termination의 옵션

Load Balancer 시리즈 1편에서도 다룬 자리지만 다시 정리해요.

  • Passthrough: Reverse Proxy가 TLS를 안 풀고 그대로 백엔드로 보내요. L4처럼 동작하고 L7 기능은 안 돼요.
  • Termination: Reverse Proxy가 풀어서 내부는 HTTP로 통신해요. 가장 흔한 패턴이고 내부망을 신뢰한다는 전제예요.
  • Re-encryption: Reverse Proxy가 풀고 다시 HTTPS로 백엔드에 전달해요. 내부도 암호화되지만 비용은 두 배예요.
  • mTLS: 백엔드와 양방향 인증서를 써요. 서비스 메시 환경에서 일반적이에요.

대부분 Termination이 일반적이에요. 결제·의료 같은 critical은 Re-encryption이나 mTLS를 써요.

실무에서 자주 만나는 함정

1. 호스트 헤더 누락

proxy_pass 만 하고 proxy_set_header Host를 안 하면, 백엔드가 받는 Host가 nginx의 upstream 이름이 돼요. 백엔드가 Host 기반 라우팅을 하면 깨져요. 거의 항상 같이 두는 게 안전해요.

2. WebSocket이 끊김

WebSocket은 HTTP upgrade로 시작하지만 그 후엔 일반 TCP처럼 양방향이에요. Reverse Proxy가 이 protocol upgrade를 알지 못하면 끊겨요. 

location /ws {
    proxy_pass http://backend;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_read_timeout 86400;   # 긴 연결 유지
}

3. HTTP/2와 백엔드 사이

외부엔 HTTP/2지만 백엔드와는 HTTP/1.1로 통신하는 게 일반적이에요. 백엔드도 HTTP/2를 원하면 proxy_http_version이나 nginx의 grpc_pass 같은 별도 설정이 필요해요.

4. Upload size limit

nginx의 기본 client_max_body_size는 1MB예요. 큰 파일 업로드가 413 Request Entity Too Large로 실패하면 이 설정이에요. 명시적으로 키워야 해요.

5. Slow client buffer

nginx는 기본적으로 클라이언트 응답을 메모리·디스크에 버퍼링해요. proxy_buffering off로 끄지 않으면 백엔드는 응답을 빠르게 끝내지만 사용자에게 전달은 느릴 수 있어요. 스트리밍 응답에선 보통 끄는 게 맞아요.

면접에서 자주 나오는 자리

  • "Forward와 Reverse Proxy 차이?": Forward는 클라이언트 쪽에서 클라이언트를 대리하고, Reverse는 서버 쪽에서 서버를 대리해요. 회사 인터넷 프록시는 forward, nginx의 reverse proxy 설정은 reverse예요.
  • "Reverse Proxy의 주요 역할?": 단일 진입점, 보안, 부하 분산, SSL termination, 캐싱, 압축·정적 서빙이에요. 보통 한 nginx가 여러 역할을 같이 해요.
  • "X-Forwarded-For는 어떻게 신뢰?": 클라이언트가 직접 보낸 값은 못 믿어요. 신뢰할 수 있는 가장 안쪽 proxy가 추가한 값까지만 믿어요. nginx면 $proxy_add_x_forwarded_for를 써요.
  • "Reverse Proxy 캐싱의 효과?": 같은 응답을 메모리에 보관해 백엔드까지 안 가도 응답해요. 트래픽이 많은 자리에서 응답 시간과 백엔드 부담을 크게 줄여요. 무효화 정책이 중요해요.
