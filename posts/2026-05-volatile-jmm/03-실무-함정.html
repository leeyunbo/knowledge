고전 문제 — Double-Checked Locking

싱글턴을 lazy하게 만들면서 락 비용을 최소화하려는 패턴. 1990년대 C++ 시절부터 유명했고, 자바에서도 반복적으로 쓰이며 함정도 반복됐다.

잘못된 DCL — Java 5 이전

class Singleton {
    private static Singleton instance;

    public static Singleton getInstance() {
        if (instance == null) {
            synchronized (Singleton.class) {
                if (instance == null) {
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}

의도는 명확하다. 첫 호출 때만 락을 잡고 인스턴스를 만들고, 이후엔 락 없이 빠르게 읽는다. 그런데 Java 5 이전엔 이 코드가 깨졌다. 이유는 객체 생성 과정의 재정렬 때문.

instance = new Singleton()은 단일 연산이 아니라 세 단계로 분해될 수 있다.

  1. 메모리 할당
  2. 생성자 호출 (필드 초기화)
  3. instance 변수에 참조 대입

컴파일러나 CPU가 1 → 3 → 2 순서로 재정렬할 수 있고, 이때 다른 스레드가 첫 번째 if (instance == null) 검사에서 참조는 있지만 생성자가 끝나지 않은 상태의 객체를 보게 된다. 반쯤 만들어진 객체를 사용하면 어떤 일이 일어날지 정의되지 않음.

올바른 DCL — Java 5+ with volatile

class Singleton {
    private static volatile Singleton instance;

    public static Singleton getInstance() {
        if (instance == null) {
            synchronized (Singleton.class) {
                if (instance == null) {
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}

volatile이 한 글자 추가됐다. 이제 instance에 대한 쓰기가 volatile write가 되고, 그 이전의 모든 작업(생성자 안의 필드 초기화)이 다른 스레드의 volatile read에서 모두 보인다 — 2편의 happens-before 규칙. 재정렬도 차단되니 반쯤 만들어진 객체를 보는 일이 사라진다.

그러나 실무에선 더 단순한 방법이 있다 — 정적 내부 클래스

class Singleton {
    private Singleton() {}

    private static class Holder {
        private static final Singleton INSTANCE = new Singleton();
    }

    public static Singleton getInstance() {
        return Holder.INSTANCE;
    }
}

JVM의 클래스 로딩 메커니즘이 클래스 초기화의 thread-safety를 보장한다. Holder 클래스는 getInstance()가 처음 호출될 때 비로소 로드되고 INSTANCE가 초기화된다. DCL의 미묘한 함정 없이 동일한 lazy 초기화 + thread-safety를 얻는다. 권장 패턴.

volatile vs AtomicXXX

1편에서 본 volatile int count의 한계 — read-modify-write가 깨진다는 것 — 의 답이 AtomicXXX 시리즈. j.u.c.atomic 패키지의 클래스들은 CAS(Compare-And-Swap) 명령어를 활용해 단일 변수의 read-modify-write를 원자적으로 처리한다. 

class Counter {
    private final AtomicInteger count = new AtomicInteger(0);

    public void increment() {
        count.incrementAndGet();
    }

    public int get() {
        return count.get();
    }
}

CAS의 동작

CAS는 "값이 X면 Y로 바꾼다"는 작업을 CPU 명령어 한 번으로 원자적으로 수행한다. incrementAndGet은 내부적으로 다음 루프를 돈다.

  1. 현재 값 V를 읽음
  2. 새 값 V+1을 계산
  3. CAS(V, V+1) — 메모리가 여전히 V면 V+1로 바꾸고 성공 반환, 그 사이 누가 바꿨으면 실패 반환
  4. 실패면 다시 1번부터

락 없이 동시성 안전을 달성. 경쟁이 적으면 매우 빠르고 (한 번에 성공), 경쟁이 많으면 retry가 누적되며 점점 느려진다. 극심한 경쟁에서는 락 기반(synchronized, ReentrantLock)이 더 빠를 수도 있다.

volatile vs AtomicInteger 정리

단순 대입과 읽기만 있다면 volatile, 누적/계산이 필요하다면 AtomicXXX. 이 둘로도 부족한 복합 연산이라면 synchronized나 ReentrantLock으로.

volatile이 적절한 자리

volatile을 쓰는 게 옳은 시나리오들.

1. Boolean flag로 종료/상태 신호

class Worker {
    private volatile boolean running = true;

    public void run() {
        while (running) {
            // 작업
        }
    }

    public void stop() {
        running = false;
    }
}

가장 흔한 volatile 사용처. 한 스레드가 set하고 다른 스레드가 read하는 단순 구조. synchronized보다 가볍고 의도가 명확.

2. 한 번 발행되고 여러 번 읽히는 immutable 참조

class ConfigHolder {
    private volatile Config config;

    public void update(Config newConfig) {
        this.config = newConfig;
    }

    public Config get() {
        return config;
    }
}

설정값을 hot-reload할 때 자주 쓰이는 패턴. Config 자체는 immutable로 두고 참조만 volatile로 교체하면 모든 스레드가 안전하게 새 설정을 본다.

3. DCL의 instance 필드

위에서 본 그 시나리오. lazy 초기화 + 락 최소화 패턴에서 instance 필드에 volatile을 붙이면 정확성 보장. 단, 정적 내부 클래스 패턴이 더 간결하니 새 코드라면 그쪽을 선택.

4. State machine의 현재 상태

단일 변수가 상태를 표현하고 set/get만 일어나는 경우. 상태 전이가 복합 조건이라면 AtomicReference나 락이 필요하다.

volatile이 부적절한 자리

1. 카운터, 누적 합

앞서 여러 번 본 count++ 함정. volatile은 1번 안 되고, AtomicInteger 또는 LongAdder가 답이다. (LongAdder는 경쟁이 매우 심한 환경에서 AtomicLong보다 빠른 옵션 — 별도 시리즈 주제.)

2. 여러 변수의 일관성

// 잘못된 패턴
class Range {
    private volatile int min;
    private volatile int max;

    public void set(int newMin, int newMax) {
        this.min = newMin;
        this.max = newMax;
    }
}

min과 max를 함께 갱신해야 하는데, 두 volatile write 사이에 다른 스레드가 끼어들면 새 min과 옛 max를 보는 inconsistent 상태가 가능하다. 이런 케이스는 synchronized나 락으로 묶거나, 두 값을 하나의 immutable 객체로 만들고 그 참조를 volatile로 둬야 한다. 

// 올바른 패턴
class Range {
    private record Pair(int min, int max) {}
    private volatile Pair pair;

    public void set(int newMin, int newMax) {
        this.pair = new Pair(newMin, newMax);
    }

    public int min() { return pair.min(); }
    public int max() { return pair.max(); }
}

3. Compound check-then-act

// 잘못된 패턴
class LazyInit {
    private volatile boolean initialized = false;

    public void initIfNeeded() {
        if (!initialized) {
            // 다른 스레드가 동시에 여기 진입할 수 있음
            doInit();
            initialized = true;
        }
    }
}

"값을 보고 행동한다"는 패턴. volatile이 가시성은 보장하지만 check와 act 사이의 원자성은 못 보장한다. 여러 스레드가 동시에 !initialized를 읽고 모두 doInit을 호출할 수 있다. synchronized나 AtomicBoolean의 compareAndSet으로 해결.

의사결정 흐름

어떤 동기화 도구를 쓸지 고를 때 다음 순서로 판단하면 대부분의 경우에 답이 나온다.

  1. 변수가 immutable로 만들 수 있나? — 가능하면 final + 그냥 공유. 동기화 불필요.
  2. 한 스레드만 쓰고 여러 스레드가 읽나? — volatile.
  3. 여러 스레드가 단일 변수에 read-modify-write? — AtomicXXX.
  4. 여러 변수의 묶음 갱신이 필요? — synchronized 또는 ReentrantLock.
  5. 복잡한 조건/대기/통지가 필요? — Lock + Condition, 또는 BlockingQueue/Latch/Semaphore 같은 고수준 도구.

가장 가벼운 도구부터 시도하고 보장이 부족할 때만 무거운 쪽으로 넘어가는 게 원칙.

면접 단골 질문

Q. Double-Checked Locking이 깨진 이유와 해결?

객체 생성이 단일 연산이 아니라 [메모리 할당 → 생성자 호출 → 참조 대입] 세 단계로 분해되고, 이게 재정렬되면 다른 스레드가 반쯤 만들어진 객체를 볼 수 있다. Java 5+에선 instance 필드에 volatile을 붙여 재정렬을 막고 happens-before 보장. 더 단순한 대안은 정적 내부 클래스 패턴 (Holder pattern).

Q. volatile과 AtomicInteger의 차이?

volatile은 가시성과 순서만 보장하고 원자성은 단순 read/write에만 적용. count++ 같은 복합 연산은 깨진다. AtomicInteger는 CAS로 read-modify-write를 원자적으로 수행한다. 단순 대입엔 volatile이 가볍고, 누적/카운터 같은 연산엔 AtomicInteger가 답.

Q. 여러 변수에 모두 volatile을 붙이면 안전한가?

아니다. 각 변수의 가시성은 보장되지만 두 변수 쓰기 사이에 다른 스레드가 끼어들 수 있어 inconsistent 상태가 가능하다. 여러 변수의 일관성이 필요하면 synchronized로 묶거나, 관련 값들을 하나의 immutable 객체로 만들고 그 참조를 volatile로 두는 패턴이 안전.

Q. CAS는 어떻게 동작하고 어떤 한계?

"값이 X면 Y로 바꾼다"를 CPU 명령어 한 번으로 원자적으로 처리. 락 없이 race를 풀 수 있어 가볍다. 한계는 ABA 문제 (값이 X → Y → X로 돌아오면 변경을 감지 못함, AtomicStampedReference로 해결), 그리고 경쟁이 극심하면 retry가 누적되며 락 기반보다 느려질 수 있다는 것. 별도 시리즈에서 CAS와 lock-free 알고리즘 deep dive.

한 줄 정리

volatile은 가벼운 동기화 도구. flag, 단순 read/write, immutable 참조 교체에 적합. read-modify-write는 AtomicXXX, 복합 연산은 synchronized나 락으로. DCL 패턴은 volatile + double check로 정확하지만 정적 내부 클래스가 더 간결하다. 가장 가벼운 도구부터 시도하고 보장이 부족할 때만 무거운 쪽으로 — 이게 동시성 도구 선택의 원칙.
