Rate Limiting이 푸는 문제

서비스가 받을 수 있는 요청 수에는 한계가 있어요. 한 사용자가 초당 1000번 호출하거나, 한 IP가 폭발적으로 트래픽을 쏟아 부으면 다른 정상 사용자가 영향을 받아요. Rate limiting은 "단위 시간당 N번까지"라는 제한을 두어 서비스를 보호해요.

공격이 아니어도 필요해요. 외부 API의 quota를 지키기 위해, 무거운 작업의 동시성을 제한하기 위해, 그리고 비용을 관리하기 위해 어디서나 써요.

네 가지 대표 알고리즘

알고리즘핵심 아이디어버스트
Token Bucket버킷에 토큰이 쌓이고, 요청당 하나씩 소비허용
Leaky Bucket버킷에서 일정 속도로 요청이 새어 나감불허 (평활)
Fixed Window시간 구간마다 카운터 리셋경계 폭주
Sliding Window이동 시간 창의 요청 수 추적매끄러움

이 편은 "버킷" 두 종류를, 다음 편은 "윈도우" 두 종류를 다뤄요. 이 두 묶음이 거의 모든 rate limiting의 기초예요.

Token Bucket

가장 흔히 쓰는 알고리즘이에요. 버킷에 토큰이 일정 속도로 채워져요. 요청이 오면 토큰을 하나 소비해요. 토큰이 없으면 거부해요.

동작 원리

  • 버킷의 최대 용량: capacity (예: 10).
  • 토큰 충전 속도: refill rate (예: 초당 5개).
  • 요청이 오면 토큰 1개를 소비해요. 토큰이 있으면 허용하고, 없으면 거부해요.

버스트 처리

Token Bucket의 특징이에요. 버킷이 가득 차 있을 때 갑자기 요청이 몰리면 capacity 만큼 한꺼번에 받아 줘요. 평균 속도(refill rate)는 지키지만 짧은 폭주를 허용해요.

예: capacity 10, refill rate 5/sec. 30초 동안 아무 요청 없이 대기하면 버킷에 10개가 가득. 그 순간 한꺼번에 10개 요청이 오면 모두 통과. 그 후 1초에 5개씩만 통과해요.

의사 코드

class TokenBucket {
    private final int capacity;
    private final double refillRate;  // tokens per second
    private double tokens;
    private long lastRefillTime;

    public synchronized boolean tryConsume() {
        refill();
        if (tokens >= 1) {
            tokens--;
            return true;
        }
        return false;
    }

    private void refill() {
        long now = System.nanoTime();
        double elapsedSec = (now - lastRefillTime) / 1e9;
        tokens = Math.min(capacity, tokens + elapsedSec * refillRate);
        lastRefillTime = now;
    }
}

실무에서는 직접 구현하기보다 Bucket4j 같은 라이브러리를 써요. 분산 환경 처리도 다 들어 있어요.

잘 맞는 자리

  • 외부 API quota를 지킬 때 잘 맞아요. 평균 1000번을 지키면서 짧은 폭주는 받아 주는 자리예요.
  • 일반 API rate limit에 좋아요. 정상 사용자의 짧은 폭주는 허용하고 학대성 사용만 차단해요.
  • 네트워크 트래픽 셰이핑에도 써요.

Leaky Bucket

버킷에서 요청이 일정 속도로 새어 나가는 모델이에요. 도착하는 요청은 버킷 안에 줄을 서고, 일정 속도로 처리돼요. 버킷이 가득 차면 새 요청은 거부예요.

동작 원리

  • 버킷 용량: capacity (예: 10).
  • 처리 속도: leak rate (예: 초당 5개).
  • 요청은 큐에 쌓여요. 큐가 가득 차면 거부해요.

버스트 처리

Token Bucket과 정반대예요. 폭주가 와도 큐가 쌓일 뿐 처리 속도는 leak rate 그대로예요. 짧은 폭주가 평활화되어 흘러나가요.

네트워크의 traffic shaping에서 유래한 알고리즘이라, 대역폭처럼 "정확히 일정한 속도"를 보장해야 하는 자리에 맞아요.

의사 코드

class LeakyBucket {
    private final int capacity;
    private final double leakRate;  // requests per second
    private final Queue<Request> queue;

    public synchronized boolean tryEnqueue(Request r) {
        leak();
        if (queue.size() < capacity) {
            queue.offer(r);
            return true;
        }
        return false;
    }

    private void leak() {
        long now = System.nanoTime();
        double elapsedSec = (now - lastLeakTime) / 1e9;
        int toLeak = (int)(elapsedSec * leakRate);
        for (int i = 0; i < toLeak && !queue.isEmpty(); i++) {
            process(queue.poll());
        }
        lastLeakTime = now;
    }
}

잘 맞는 자리

  • 외부 시스템 호출을 평활화할 때 써요. "초당 정확히 5번"을 지켜야 하는 외부 API에 잘 맞아요.
  • 네트워크 대역폭을 제어해요. 패킷 단위 traffic shaping에서 유래했어요.
  • 비동기 작업 큐로도 써요. 백엔드가 처리할 수 있는 속도로 자연스럽게 throttle해요.

분산 환경의 구현

단일 서버의 메모리 카운터로는 안 돼요. 여러 인스턴스가 같은 사용자의 요청을 처리하니, 카운터를 공유해야 해요. 보통 Redis를 써요.

Redis 기반 Token Bucket

-- KEYS[1]: bucket key
-- ARGV[1]: capacity
-- ARGV[2]: refill rate (tokens/sec)
-- ARGV[3]: now (ms)

local data = redis.call('HMGET', KEYS[1], 'tokens', 'last')
local tokens = tonumber(data[1]) or tonumber(ARGV[1])
local last = tonumber(data[2]) or tonumber(ARGV[3])

local now = tonumber(ARGV[3])
local elapsed = (now - last) / 1000
local refill = elapsed * tonumber(ARGV[2])
tokens = math.min(tonumber(ARGV[1]), tokens + refill)

if tokens >= 1 then
    tokens = tokens - 1
    redis.call('HMSET', KEYS[1], 'tokens', tokens, 'last', now)
    return 1
else
    redis.call('HMSET', KEYS[1], 'tokens', tokens, 'last', now)
    return 0
end

Lua 스크립트로 만들면 Redis가 원자적으로 실행해 줘요. race condition 없이 분산 token bucket이 동작해요. Bucket4j 같은 라이브러리도 내부적으로 비슷한 패턴을 써요.

면접에서 자주 나오는 자리

  • "Token Bucket과 Leaky Bucket 차이?": 둘 다 capacity와 속도가 있지만, Token Bucket은 burst를 허용하고 Leaky Bucket은 평활화해요. 보호 목적에 따라 선택이 갈려요.
  • "어느 게 더 흔히 쓰여요?": API rate limit에는 Token Bucket이 일반적이에요. AWS·GitHub·Stripe 같은 회사가 다 token bucket이에요. 네트워크 셰이핑은 leaky bucket이 많아요.
  • "분산 환경에서 구현은?": Redis + Lua 스크립트로 원자적으로 카운터를 갱신해요. Bucket4j나 Resilience4j 같은 라이브러리는 이 패턴을 추상화해 줘요.
  • "Burst를 허용하면 위험하지 않나요?": capacity로 상한이 정해져 있어서 무한 burst가 아니에요. 평균은 refill rate로 제한되니 long-term 부하는 leaky와 같아요.
