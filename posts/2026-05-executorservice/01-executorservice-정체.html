Thread 직접 다루기의 문제

스레드를 처음 배울 때는 new Thread(runnable).start() 패턴이 익숙해요. 작동은 해요. 그런데 실무에서는 거의 안 써요. 이유가 몇 가지 있어요.

  • 스레드 생성 비용: OS 스레드 하나 만드는 게 가볍지 않아요. 스택 메모리(보통 1MB) 할당, 커널 자료구조 등록, 스케줄러 등록까지. 작업 한 번에 한 개씩 만들면 작업 비용보다 스레드 비용이 커지는 자리가 생겨요.
  • 관리의 부재: 만든 스레드의 수명, 종료 시점, 예외 처리를 누가 책임지나요? 손으로 직접 join을 부르고 try-catch를 두르는 코드는 금방 지저분해져요.
  • 병렬도 제어가 어려움: "동시에 최대 N개만 실행"이라는 요구를 손으로 구현하려면 세마포어 같은 도구가 또 필요해요.
  • 결과 받기가 불편함: Runnable은 반환값이 없어요. 작업 결과를 받으려면 공유 변수를 통하는 패턴이 등장하는데, 그것도 동기화 코드가 따라붙어요.

이걸 다 푸는 게 자바의 Executor 계층이에요. "스레드를 직접 만들지 말고 ExecutorService에 작업만 던지자"는 발상이에요.

Executor 계층

작은 인터페이스 셋이에요. 위에서 아래로 점점 기능이 늘어나요.

인터페이스핵심 메서드역할
Executorexecute(Runnable)가장 단순. 작업 던지기만
ExecutorServicesubmit, shutdown, invokeAll생명주기 + 결과 수신 + 종료
ScheduledExecutorServiceschedule, scheduleAtFixedRate지연·주기 실행

실무에서 변수 타입은 거의 항상 ExecutorService예요. Executor는 너무 단순하고, ScheduledExecutorService는 주기 작업 전용이거든요.

Runnable vs Callable

ExecutorService에 던질 수 있는 작업의 형태는 두 가지예요. 

// Runnable: 반환값 없음, checked exception 없음
Runnable task = () -> {
    log.info("doing work");
};

// Callable: 반환값 있음, checked exception 던질 수 있음
Callable<String> query = () -> {
    return fetchFromDb();   // SQLException 던져도 OK
};

차이는 두 가지예요. Callable은 결과를 반환하고, checked exception을 던질 수 있어요. Runnable은 둘 다 못 해요.

"결과가 필요하면 Callable, 필요 없으면 Runnable"이 기본 가이드예요. 결과는 필요 없는데 checked exception을 던지고 싶다면? Callable에 Void 반환 타입을 쓰면 돼요(Callable<Void>).

execute vs submit

작업을 던지는 메서드도 두 가지예요. 차이가 작아 보이지만 중요한 자리가 있어요. 

ExecutorService es = ...;

// execute: Executor 인터페이스 메서드. Runnable만. 결과 없음
es.execute(() -> doWork());

// submit: ExecutorService 메서드. Runnable/Callable 둘 다. Future 반환
Future<?> f1 = es.submit(() -> doWork());        // Runnable
Future<String> f2 = es.submit(() -> fetchData()); // Callable

표면적으로는 "submit이 Future를 주니까 submit 쓰면 된다"로 끝날 수 있는데, 한 가지 함정이 있어요. execute로 던진 작업의 예외는 ThreadFactory의 UncaughtExceptionHandler로 가요. 즉 콘솔이나 로그에 stack trace가 떠요.

반면 submit으로 던진 작업의 예외는 Future 안에 갇혀요. future.get()을 부르지 않으면 예외가 어디로도 안 가요. 작업이 조용히 실패해도 모를 수 있어요. 

// 위험한 패턴. 예외가 사라짐
es.submit(() -> {
    throw new RuntimeException("뭔가 잘못됨");
});
// future를 안 받았고 get도 안 부름 → 예외가 어디에도 안 보임

결과를 안 쓸 거면 execute가 안전해요. 또는 submit을 쓰되 반드시 future.get()이나 future.exceptionally(...)로 결과/예외를 받아야 해요. 백그라운드 작업이 묵묵히 실패하는 자리를 막으려면 이걸 신경 써야 해요.

Executors 팩토리의 함정

ExecutorService를 만드는 가장 흔한 방법이 Executors 정적 팩토리예요. 그런데 이 팩토리의 표준 메서드들이 운영 환경에서는 위험해요. 

// 흔하게 쓰는 형태들
ExecutorService a = Executors.newFixedThreadPool(10);
ExecutorService b = Executors.newCachedThreadPool();
ExecutorService c = Executors.newSingleThreadExecutor();

세 개 모두 함정이 있어요. 정리하면 이래요.

팩토리내부 큐최대 스레드위험
newFixedThreadPool무한 LinkedBlockingQueue고정큐가 무한대로 쌓여 OOM
newCachedThreadPoolSynchronousQueue (즉시 넘김)Integer.MAX_VALUE스레드 무한 생성. CPU/메모리 폭주
newSingleThreadExecutor무한 LinkedBlockingQueue1 (고정)fixedThreadPool과 같은 OOM 위험

실무에서 안전한 패턴은 ThreadPoolExecutor를 직접 생성하는 거예요. 큐 크기와 최대 스레드 수를 명시적으로 정하면 둘 다 막혀요. 

// 안전한 패턴
ThreadPoolExecutor es = new ThreadPoolExecutor(
    10,                                   // corePoolSize
    20,                                   // maximumPoolSize
    60L, TimeUnit.SECONDS,                // keepAlive (max - core)
    new ArrayBlockingQueue<>(100),        // 큐 크기 명시 (무한 X)
    new ThreadFactoryBuilder()
        .setNameFormat("worker-%d")
        .build(),
    new ThreadPoolExecutor.AbortPolicy()  // 거부 시 RejectedExecutionException
);

ThreadPoolExecutor 7인자는 ThreadPoolExecutor 시리즈에서 자세히 봤어요. 핵심만 다시 짚으면, 큐는 유한 크기로 두고 최대 스레드 수도 명시적으로 잡고 거부 정책도 의도적으로 선택해야 해요. Executors 팩토리는 편하지만 운영 환경에 못 들어가는 옵션이에요.

그래서 어떻게 쓰나

기본 사용 흐름을 한 번에 정리하면 이래요. 

// 1. ExecutorService 생성 (운영에서는 ThreadPoolExecutor 직접 구성)
ExecutorService es = Executors.newFixedThreadPool(10);   // 개발/예시용

// 2. 작업 던지기
Future<String> future = es.submit(() -> fetchData());

// 3. 결과 받기 (블로킹)
String result = future.get();
// 또는 타임아웃과 함께
String result2 = future.get(5, TimeUnit.SECONDS);

// 4. 종료 (다음 편에서 자세히)
es.shutdown();
es.awaitTermination(30, TimeUnit.SECONDS);

생성 → 작업 던지기 → 결과 받기 → 종료. 이 흐름이 ExecutorService의 표준 사용법이에요.

다음 편

종료 단계는 단순해 보이지만 graceful shutdown은 의외로 함정이 많아요. shutdown과 shutdownNow의 차이, awaitTermination의 의미, 인터럽트 처리, 그리고 운영에서 ExecutorService를 만들 때 따라붙는 ThreadFactory 커스텀까지 다음 편에서 정리해요.
