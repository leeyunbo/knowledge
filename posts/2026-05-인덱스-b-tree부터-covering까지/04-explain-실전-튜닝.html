EXPLAIN — 옵티마이저의 결정을 보는 창

EXPLAIN은 쿼리를 실제로 실행하지 않고 옵티마이저가 어떤 계획으로 실행할지를 보여주는 명령이다. 

EXPLAIN SELECT * FROM orders WHERE user_id = 100;

+----+-------------+--------+------+---------------+---------+---------+-------+------+-------+
| id | select_type | table  | type | possible_keys | key     | key_len | ref   | rows | Extra |
+----+-------------+--------+------+---------------+---------+---------+-------+------+-------+
|  1 | SIMPLE      | orders | ref  | idx_user_id   | idx_user_id | 4   | const|   45 |       |
+----+-------------+--------+------+---------------+---------+---------+-------+------+-------+

이 출력의 모든 컬럼이 다 의미가 있지만, 처음 볼 때는 핵심 4개부터 본다. type, key, rows, Extra.

1. type — 데이터 접근 방식

가장 먼저 봐야 할 건 type. 좋은 순서대로 나열하면 이렇다. 

const   ─ PK 또는 unique 인덱스로 단일 행 매칭. 최고 성능
eq_ref  ─ JOIN에서 한쪽 테이블의 PK 또는 unique 인덱스 매칭
ref     ─ 일반 인덱스로 매칭 (PK 아님). 매우 좋음
range   ─ 인덱스 범위 검색 (BETWEEN, >, <)
index   ─ 인덱스 풀스캔 (인덱스 전체를 처음부터 끝까지)
ALL     ─ 테이블 풀스캔. 가장 비효율적

ALL이 보이면 풀스캔이라는 신호. 가장 먼저 의심해야 할 대상이다. 단 2편에서 봤듯, 옵티마이저가 의도적으로 풀스캔을 선택한 경우라면 오히려 그게 빠를 수 있다. 결과 행 수가 테이블의 20~30%를 넘으면 그렇다.

index도 풀스캔이지만 인덱스만 스캔하니 ALL보단 가벼움. 커버링 인덱스 작동 시 이 type이 자주 보인다.

2. key — 실제 사용된 인덱스

possible_keys  ─ 옵티마이저가 고려한 인덱스 후보들
key            ─ 실제로 선택된 인덱스

key가 NULL이면 인덱스를 안 탔다는 뜻. possible_keys에 후보가 있는데 key가 NULL이면 옵티마이저가 인덱스를 안 쓰는 게 더 빠르다고 판단한 경우다. 이게 "인덱스 걸었는데 안 타요"의 흔한 원인.

3. rows — 검사할 예상 행 수

이 쿼리가 실제 검사할 거라고 옵티마이저가 추정하는 행 수. 적을수록 좋다. 

rows: 45        ← 좋음 (45행만 검사)
rows: 1000000   ← 나쁨 (백만 행 검사 = 사실상 풀스캔에 가까움)

단, 이건 통계 기반 추정치다. 실제와 다를 수 있다. 통계가 오래되어 정확하지 않으면 옵티마이저가 잘못된 선택을 할 수 있다. 그럴 땐 ANALYZE TABLE 테이블명으로 통계를 갱신하면 옵티마이저 결정이 바뀐다.

4. Extra — 가장 정보 많음

Extra 컬럼에 다양한 메타정보가 표시된다. 자주 보이는 것들.

좋은 신호

Using index
  → 커버링 인덱스 작동. Back to Table 없음. 매우 좋음.

Using index condition
  → Index Condition Pushdown 작동.
    인덱스 단계에서 추가 필터링이 일어나 Back to Table 횟수 감소.

Backward index scan
  → ORDER BY DESC를 인덱스 역순으로 처리. 별도 정렬 없음.

주의 신호

Using where
  → WHERE 조건이 인덱스 단계 후 메모리에서 추가 필터링.
    꼭 나쁜 건 아니지만 결과 비율 낮으면 비효율적.

Using filesort
  → ORDER BY가 인덱스 정렬을 활용 못 해서 별도 정렬 발생.
    데이터 많으면 디스크 정렬까지 가서 매우 느려짐. 튜닝 대상.

Using temporary
  → GROUP BY나 DISTINCT가 임시 테이블 생성.
    메모리에 안 맞으면 디스크 임시 테이블로 떨어져서 매우 느림.
    Using filesort와 같이 뜨면 큰 위험 신호.

위험 신호 조합

Using filesort + Using temporary
→ GROUP BY 또는 ORDER BY 쿼리가 무거움. 즉시 튜닝 대상.

Using where + rows: 백만 이상
→ 인덱스 효과가 거의 없음. 인덱스 자체를 재설계할 시점.

실전 시나리오 — 1억 건 주문 테이블 튜닝

가상 시나리오 하나로 단계적 진단/튜닝 흐름을 보자. 

테이블: orders (1억 건)
  id            BIGINT PK
  user_id       BIGINT
  status        VARCHAR(20)   -- PENDING, PAID, SHIPPED, DELIVERED, CANCELLED
  store_id      BIGINT
  product_id    BIGINT
  amount        DECIMAL
  created_at    DATETIME
  updated_at    DATETIME

기존 인덱스: PK (id), idx_user_id (user_id)

문제 쿼리:
  SELECT * FROM orders
  WHERE user_id = ? AND status = ?
  ORDER BY created_at DESC
  LIMIT 10;

증상: 평균 응답 시간 3~5초.

1단계 — 현황 파악

EXPLAIN SELECT * FROM orders
WHERE user_id = 12345 AND status = 'PAID'
ORDER BY created_at DESC LIMIT 10;

+------+--------+---------------+--------------+---------+------+--------+--------------------+
| type | key    | possible_keys | key_len      | ref     | rows | Extra                       |
+------+--------+---------------+--------------+---------+------+--------+--------------------+
| ref  | idx_user_id | idx_user_id | 8     | const   | 50000| Using where; Using filesort |
+------+--------+---------------+--------------+---------+------+--------+--------------------+

분석:
  - type: ref ─ user_id 인덱스 사용. OK.
  - rows: 50000 ─ user_id로 5만 행 매칭됨. 너무 많음.
  - Using where ─ status 조건이 인덱스 후 메모리 필터링.
  - Using filesort ─ ORDER BY created_at DESC가 별도 정렬됨.
    5만 행을 메모리/디스크에서 정렬한 후 LIMIT 10. 비효율적.

진단: user_id로 5만 행 가져오고 그중 status 필터링한 다음 5만 행을 created_at으로 정렬한다. 정렬 비용이 압도적이다.

2단계 — 복합 인덱스 설계

앞 편의 원칙들을 적용한다. 

대안 1: (user_id, status)
  → user_id, status 조건은 좁힘
  → 그러나 ORDER BY created_at은 여전히 filesort

대안 2: (user_id, status, created_at)
  → user_id, status로 좁히고 그 안에서 created_at 정렬은
    인덱스 순서 그대로 활용 (filesort 제거)
  → ORDER BY ... DESC면 backward index scan으로 처리됨

→ 대안 2 채택
CREATE INDEX idx_user_status_created
ON orders (user_id, status, created_at);

3단계 — 결과 확인

EXPLAIN (다시)

+------+----------------------------+------+------+----------------------+
| type | key                        | rows | Extra                       |
+------+----------------------------+------+------+----------------------+
| ref  | idx_user_status_created    |   45 | Backward index scan         |
+------+----------------------------+------+------+----------------------+

개선:
  - rows: 50000 → 45 (1100배 감소)
  - Using filesort 제거
  - Backward index scan ─ DESC 정렬을 인덱스 역순으로 처리
  - 응답 시간: 3~5초 → 10ms 미만

4단계 — 커버링 인덱스 검토

여기까지도 충분히 빠른데, 더 짜내려면 커버링 인덱스로 갈 수 있다. 

현재 쿼리: SELECT * FROM orders WHERE ...
→ 모든 컬럼 필요. 보조 인덱스로 부족.
→ Back to Table 발생 (45행만 가져오니 비용은 작음)

만약 자주 호출되는 컬럼이 한정적이면:

  자주 쓰는 화면 쿼리:
    SELECT id, amount, created_at FROM orders WHERE user_id = ? AND status = ?
    ORDER BY created_at DESC LIMIT 10

  → 인덱스를 (user_id, status, created_at, amount)로 확장
  → 커버링 인덱스 작동, Back to Table 제거

단, 커버링을 위해 컬럼을 너무 많이 인덱스에 넣으면 인덱스가 비대해진다. 쓰기 비용도 증가. 실측해보고 충분히 자주 호출되는 쿼리만 적용.

5단계 — 트레이드오프 점검

새 인덱스 추가의 비용을 평가한다. 

orders 테이블의 INSERT/UPDATE 빈도:
  - INSERT: 초당 100건
  - UPDATE: 초당 50건 (status 변경 등)

추가 인덱스 1개의 영향:
  - INSERT 비용: 인덱스 1개 갱신 추가 (~5% 증가)
  - UPDATE 비용: status 컬럼이 인덱스에 포함되어 있어
    status 변경 시 인덱스 항목 이동 (다소 큼)

판단:
  - 읽기 쿼리가 압도적으로 많다 (1초당 1000+회)
  - 5% 쓰기 비용 증가는 감내 가능
  - 새 인덱스 채택

EXPLAIN 외의 진단 도구

EXPLAIN ANALYZE (MySQL 8.0+)

EXPLAIN ANALYZE SELECT ...

→ EXPLAIN의 추정치가 아니라 실제 쿼리를 실행하면서
  각 단계의 실행 시간, 처리한 행 수를 측정해서 보여줌
→ 추정치 vs 실측치의 차이로 통계 정확도도 확인 가능

SHOW PROFILE (deprecated, 그래도 유용)

SET profiling = 1;
SELECT ... ;
SHOW PROFILE;

→ 쿼리의 각 단계(파싱, 실행, 송신 등)별 시간 측정
→ 단순한 진단에 빠름

Performance Schema

-- 가장 느린 쿼리 TOP 10
SELECT digest_text, count_star, avg_timer_wait/1000000000 as avg_ms
FROM performance_schema.events_statements_summary_by_digest
ORDER BY avg_timer_wait DESC
LIMIT 10;

-- 자주 실행되는 쿼리 TOP 10
SELECT digest_text, count_star, sum_rows_examined
FROM performance_schema.events_statements_summary_by_digest
ORDER BY count_star DESC
LIMIT 10;

어디서 시간이 많이 쓰이는지, 어디서 자주 호출되는지를 한눈에 본다. 튜닝 대상 쿼리 우선순위를 정할 때 출발점.

Slow Query Log

# my.cnf
slow_query_log = 1
slow_query_log_file = /var/log/mysql/slow.log
long_query_time = 1   # 1초 이상 걸린 쿼리 기록

1초 이상 걸린 쿼리를 모두 로그로 남김. mysqldumpslow나 pt-query-digest로 분석.

튜닝 후에도 항상 해야 할 일

운영 모니터링

인덱스 추가가 의도대로 작동하는지 운영 대시보드에서 확인. 평균 응답 시간, p99 latency, slow query 수 등이 개선되는지.

인덱스 사용 통계 정기 점검

-- 인덱스별 사용 횟수
SELECT object_schema, object_name, index_name, count_read
FROM performance_schema.table_io_waits_summary_by_index_usage
WHERE object_schema = 'your_db'
ORDER BY count_read DESC;

-- 안 쓰이는 인덱스
SELECT * FROM sys.schema_unused_indexes;

시간이 지나면서 쿼리 패턴이 바뀐다. 어떤 인덱스는 더 이상 안 쓰이고, 어떤 인덱스는 새로 필요해진다. 분기에 한 번 정도 정리.

면접 답변 시뮬레이션

시리즈 마무리로, "1억 건 테이블의 느린 쿼리 어떻게 튜닝하시나요?" 질문에 답할 때 흐름. 

1. 단계적으로 접근하겠습니다.

2. 1단계, 현황 파악
   - EXPLAIN으로 현재 실행 계획 확인
   - type이 ALL인지, key가 NULL인지, rows가 큰지
   - Extra에 Using filesort, Using temporary가 있는지

3. 2단계, 복합 인덱스 설계
   - 등호 조건은 앞에, 범위/정렬 조건은 뒤에
   - 카디널리티 높은 컬럼 앞에
   - ORDER BY를 인덱스 정렬로 처리할 수 있게

4. 3단계, 커버링 인덱스 검토
   - 자주 함께 조회되는 컬럼을 인덱스에 포함
   - Back to Table 제거

5. 4단계, 검증
   - 다시 EXPLAIN 확인
   - type: ref, Extra: Using index 또는 Backward index scan 보이는지
   - 실제 쿼리 시간 측정

6. 5단계, 트레이드오프 점검
   - 인덱스 추가로 INSERT/UPDATE 비용 증가는?
   - 그 테이블의 쓰기 빈도와 비교해서 운영 영향 평가

7. 6단계, 운영 모니터링
   - 배포 후 응답 시간, slow query 수 변화 추적
   - 안 쓰이는 인덱스 정기 정리

이 흐름이 자연스럽게 나오면 면접관이 인덱스에 대한 깊이를 인정한다. 단순히 "인덱스 걸겠어요"가 아니라 "어떤 인덱스를, 왜, 어떻게 검증하고, 어떤 비용을 감내하는지"까지가 시니어의 답이다.

시리즈 정리

1편: 인덱스가 왜 빠른가 — B+Tree의 정체
     - 정렬돼있어 O(log N) 이진 탐색
     - 디스크 페이지에 키 많이 담아 트리 높이 낮춤 (1억 건 3~4 레벨)
     - 리프끼리 Linked List로 범위 검색까지 빠름
     - Hash가 안 되는 이유 (범위, 정렬, prefix 활용 불가)

2편: 클러스터드 vs 보조 — Back to Table과 커버링 인덱스
     - InnoDB의 두 종류 인덱스
     - PK 짧게 잡는 이유 (모든 보조 인덱스에 PK 복사)
     - Back to Table과 커버링 인덱스
     - Random I/O vs Sequential I/O가 만드는 풀스캔 선택
     - Buffer Pool이 디스크 I/O를 메모리로 흡수

3편: 복합 인덱스 운영 — Left-most Prefix와 카디널리티
     - 인덱스의 정렬 방식과 Left-most Prefix Rule
     - 컬럼 순서 결정 원칙 셋 (등호/범위, 카디널리티, 실제 쿼리)
     - 안 타게 만드는 5가지 패턴
     - JPA 환경의 흔한 함정

4편: EXPLAIN으로 진단하기 — 1억 건 테이블 튜닝
     - type/key/rows/Extra의 의미
     - 좋은 신호와 위험 신호
     - 단계적 튜닝 시나리오 (현황 파악 → 인덱스 → 커버링 → 검증)
     - EXPLAIN ANALYZE, Performance Schema, Slow Query Log
     - 인덱스 사용 통계 정기 점검

인덱스는 RDBMS 성능의 토대다. 이 위에 트랜잭션, 락, 격리 수준, MVCC 같은 다른 주제들이 얹힌다. 그 모든 것이 결국 "인덱스가 잘 작동하는 환경"에서 의미를 갖는다.

외부 API 호출 코드 한 줄이 어떤 단계를 거치는지 그릴 수 있게 됐듯, 쿼리 한 줄이 어떤 인덱스를 어떻게 타고 어떤 페이지를 읽는지 그릴 수 있으면 데이터 레이어의 시야가 한 단계 올라간다. 평소 안 보이던 함정들이 미리 보이기 시작한다.
