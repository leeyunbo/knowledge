풀 크기를 결정하는 두 변수

스레드 수를 결정하는 출발점은 작업의 성격을 두 축으로 나누는 것. CPU를 얼마나 쓰는가, 그리고 I/O 대기에 얼마나 시간을 쓰는가. 이 비율이 적정 스레드 수를 결정한다.

CPU bound 작업

작업 시간 대부분을 CPU가 일하는 데 쓰는 작업. 이미지 처리, 암호화, 데이터 압축, 복잡한 계산. 여러 스레드가 동시에 같은 코어에서 경쟁해도 처리량이 늘지 않는다 — 코어는 한 시점에 한 스레드만 실행.

CPU bound 워크로드에 스레드를 너무 많이 두면 컨텍스트 스위칭 비용이 처리량을 깎아먹는다. OS 스케줄러가 빈번하게 스레드를 갈아끼우면서 캐시가 무효화되고, 정작 일은 못 한다. 그래서 최적 스레드 수는 CPU 코어 수에 가깝다. 

CPU 코어 수: N

권장 스레드 수: N + 1
또는 N (정확히 코어 수)

+1은 한 스레드가 가끔 발생하는 짧은 I/O(예: page fault, GC)로 잠시 멈출 때 다른 스레드가 그 코어를 채워 사용률을 100%에 가깝게 유지하기 위함. Doug Lea의 java.util.concurrent 설계에서 자주 언급되는 휴리스틱.

I/O bound 작업

작업 시간 대부분을 외부 시스템 응답을 기다리는 데 쓰는 작업. DB 쿼리, HTTP 요청, 파일 I/O, 메시지 큐 송수신. 스레드가 응답을 기다리는 동안 CPU는 놀고 있으니 그 사이 다른 스레드가 일할 수 있다.

여러 스레드를 두면 동시에 여러 외부 시스템에 요청을 보내고 그 동안 CPU는 다른 스레드의 응답 처리에 쓸 수 있다. 그래서 적정 스레드 수가 CPU 코어 수보다 훨씬 많다.

Brian Goetz 공식

"Java Concurrency in Practice" (Brian Goetz et al., 2006)에서 제시된 공식. I/O bound 작업의 적정 스레드 수를 계산하는 출발점. 

N_threads = N_cpu × U_cpu × (1 + W/C)

N_cpu : CPU 코어 수
U_cpu : 목표 CPU 사용률 (0.0 ~ 1.0)
W     : 평균 대기(Wait) 시간
C     : 평균 컴퓨팅(Compute) 시간
W/C   : 대기 시간 / 컴퓨팅 시간 비율

예시 — 일반 웹 서버

가정: 코어 8개, CPU 사용률 목표 80%, 한 요청당 컴퓨팅 5ms + DB 대기 50ms (대부분 I/O 기다림). 

N = 8 × 0.8 × (1 + 50/5)
  = 6.4 × 11
  ≈ 70 스레드

CPU 코어 8개 환경에서 적정 스레드 수가 70개로 계산된다. I/O 대기 시간이 컴퓨팅 시간의 10배라 그만큼 더 많은 스레드를 둘 수 있다는 것. 이런 분석 없이 코어 수만큼만 스레드를 두면 처리량이 1/10 수준에 그친다.

Little's Law로 검증

큐 이론의 기본 정리. 안정 상태에서 시스템 안에 머무르는 평균 작업 수는 유입률과 평균 체류 시간의 곱. 

L = λ × W

L : 시스템 안의 평균 작업 수
λ : 작업 도착률 (요청/초)
W : 한 작업의 평균 처리 시간 (초)

예시

서비스가 초당 1000 요청을 받고, 한 요청 처리에 평균 50ms 걸린다고 하면 시스템 안에 머무르는 평균 작업 수는 50. 즉 동시에 50개의 작업이 진행 중이어야 하므로 최소 50개 스레드가 필요하다. 

λ = 1000 req/sec
W = 0.05 sec
L = 1000 × 0.05 = 50

→ 동시 처리 작업 50개 → 최소 스레드 50개

여기서 "동시 처리"가 핵심. 모든 작업이 매 순간 CPU를 쓴다는 게 아니라 시작했지만 아직 끝나지 않은 작업의 수. I/O 대기 중인 것도 포함. 그래서 Little's Law는 I/O 비중이 높을수록 더 많은 스레드를 요구한다.

두 공식의 관계

Brian Goetz 공식은 작업의 W/C 비율로 사이징을, Little's Law는 처리량과 시간으로 사이징을 한다. 출발점은 다르지만 본질은 같은 시스템을 다른 각도에서 보는 것.

실무에서는 둘을 함께 사용하는 게 자연스럽다. Goetz 공식으로 1차 추정을 하고, 측정된 throughput과 latency로 Little's Law 검증을 통해 확정. 그 결과를 corePoolSize와 maximumPoolSize의 출발점으로 삼는다.

실무에서 자주 쓰이는 휴리스틱

이론적 공식을 매번 적용하기는 부담스러우니 자주 쓰이는 시작점들이 있다.

워크로드core 추정max 추정설명
순수 CPU 계산 코어 수 코어 수 스레드를 더 둬도 처리량 안 늘어남
가벼운 I/O (캐시, 로컬 DB) 코어 × 2 코어 × 4 약간의 대기 흡수

이 표는 출발점일 뿐. 실제 사이즈는 부하 테스트와 모니터링으로 검증해야 한다. 무엇보다 중요한 건 추측이 아닌 측정 — APM이나 GC/스레드 메트릭을 보면서 단계적으로 조정.

Tomcat의 기본값과 함정

Spring Boot 내장 Tomcat의 기본 thread 설정. 

server:
  tomcat:
    threads:
      max: 200
      min-spare: 10
    accept-count: 100
    max-connections: 8192

기본 max 스레드가 200개. 일반적인 웹 부하에 충분하지만, 느린 외부 API 호출이 많으면 200개도 빨리 차서 backpressure가 발생한다. 반대로 코어 수가 적은 작은 인스턴스에서는 200개도 너무 많을 수 있다.

중요한 건 코어 수에 비례해 늘리는 게 아니라 작업 성격에 맞춰 측정 후 조정하는 것. 외부 API에 1초씩 걸리는 워크로드면 200개가 작을 수도 있고, 순수 CPU 계산이라면 코어 수의 2배로 충분.

모니터링 — 사이징의 검증 도구

숫자를 정한 뒤에는 반드시 측정으로 검증한다. 봐야 할 메트릭들.

  • Active 스레드 수 — 평균과 최대. core에 머무는지 max까지 가는지
  • Queue 크기 — 평균과 max 도달 빈도. 자주 가득 차면 max를 늘릴 신호
  • RejectedExecution 발생 빈도 — 0이어야 정상. 발생하면 풀이 부족하다는 신호
  • 처리량 (RPS) — 풀 사이즈 변경 후 처리량이 어떻게 변하는지
  • 응답 시간 p99 — 풀 사이즈 변경이 사용자 응답에 어떤 영향
  • CPU 사용률 — 너무 낮으면 풀이 작거나 큐에 쌓이고 있는 것
  • 스레드 수가 메모리에 미치는 영향 — 스레드 하나당 native 메모리 부담

Spring Boot Actuator는 /actuator/metrics에서 이 메트릭을 노출한다. Prometheus + Grafana 또는 Datadog 같은 APM으로 시각화하면 풀의 동작을 한눈에 볼 수 있다.

Virtual Thread와의 관계

Java 21에서 정식화된 Virtual Thread는 풀 사이징 패러다임을 일부 무력화한다. 가벼운 가상 스레드를 만들기에 비용이 거의 없어, "스레드를 아껴 쓴다"는 전제 자체가 약해진다. I/O bound 워크로드에서는 매 요청마다 새 Virtual Thread를 만드는 게 합리적인 패턴이 된다.

단, CPU bound 작업은 여전히 코어 수에 묶여 있고, 기존 ThreadPoolExecutor 기반 코드는 갑자기 사라지지 않는다. 한동안은 두 모델이 공존하며 작업 성격에 맞춰 선택하는 시대. Virtual Thread는 별도 시리즈에서 깊게.

면접 단골 질문

Q. 풀 크기를 어떻게 정하나?

작업의 CPU vs I/O 성격을 먼저 파악. CPU bound면 코어 수 + 1, I/O bound면 Brian Goetz 공식 N×U×(1+W/C). 그 추정을 Little's Law(L = λ × W)로 검증. 그 다음 부하 테스트와 모니터링으로 조정해 확정. 정답은 없고 측정 기반의 반복 조정이 핵심.

Q. CPU bound와 I/O bound의 차이?

CPU bound는 작업 시간 대부분을 CPU가 일하는 데 쓰는 작업 — 계산, 압축 등. 스레드 많아도 처리량 안 늘어남. I/O bound는 외부 응답 대기에 시간을 많이 쓰는 작업 — DB, HTTP, 파일. 스레드를 많이 둘수록 동시 진행이 가능해 처리량 증가. 두 종류 작업이 섞여 있다면 풀을 분리하는 것도 검토.

Q. Little's Law는?

L = λ × W. 시스템 안 평균 작업 수는 도착률 × 평균 처리 시간. 예: 초당 1000 요청, 한 요청 50ms면 동시 50개 작업 → 최소 50 스레드. 큐 이론의 기본 정리이며 풀 사이징의 검증 도구.

Q. 풀이 부족하다는 건 어떤 신호?

큐가 자주 가득 차거나 RejectedExecution이 발생, 응답 시간 p99가 갑자기 튀거나, Active 스레드 수가 max에 자주 도달하는 패턴. APM으로 monitoring하면 이런 신호를 추적 가능. 일시적 spike면 backpressure(CallerRunsPolicy 등)로 흡수, 지속적이면 사이즈 확대 또는 인스턴스 scale-out.

한 줄 정리

풀 사이징의 출발점은 CPU bound인지 I/O bound인지 구분. CPU bound는 코어 수 + 1, I/O bound는 W/C 비율로 늘려간다. Brian Goetz 공식과 Little's Law로 추정하고 부하 테스트와 모니터링으로 검증. 정답은 없고 측정 기반의 반복 조정이 본질.
