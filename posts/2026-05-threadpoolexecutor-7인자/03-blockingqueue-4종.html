큐는 풀 동작의 분기점

1편에서 본 것처럼 작업이 들어오면 풀은 corePoolSize를 채운 뒤 큐에 적재하고, 큐가 가득 차야 maximum까지 확장한다. 큐가 가득 차는 시점이 곧 풀이 max로 확장하는 트리거. 큐의 종류가 이 트리거를 언제, 어떻게 만들지 결정한다.

4가지 BlockingQueue

Java가 기본 제공하는 ThreadPoolExecutor용 큐는 크게 네 종류.

큐저장 공간특성풀 동작
SynchronousQueue 0개 저장 안 함. 생산자/소비자 바로 연결 매번 max로 확장 시도
LinkedBlockingQueue (무한) Integer.MAX_VALUE 사실상 무한대 max 의미 없음, 큐만 자람
LinkedBlockingQueue (유한) 지정 크기 유한 큐 큐 차면 max 확장
ArrayBlockingQueue 고정 크기 배열 유한, 배열 기반 큐 차면 max 확장
PriorityBlockingQueue 무한 우선순위 정렬 max 의미 없음
DelayQueue 무한 지연 후 처리 스케줄러 용도

1. SynchronousQueue — 저장하지 않는 큐

이름에 큐가 붙어있지만 정확히는 큐가 아니다. 용량이 0이라 어떤 작업도 저장하지 않고, 생산자(submit)와 소비자(스레드) 사이의 직접 핸드오프 역할만 한다. 

new ThreadPoolExecutor(
    0, Integer.MAX_VALUE,
    60, TimeUnit.SECONDS,
    new SynchronousQueue<>()
);

풀 동작

작업이 들어오면 받는 스레드가 즉시 있어야 한다. 받을 스레드가 없으면 큐에 넣지 못하고 거부. 1편의 흐름에서 "큐가 거부 → max로 확장" 단계가 매번 발동되므로, 사실상 모든 작업이 새 스레드 생성을 시도하게 된다.

이 동작이 Executors.newCachedThreadPool()의 핵심. maximum이 Integer.MAX_VALUE라 사실상 무제한 스레드 생성이 가능하고, 작업이 끝나 idle 상태가 된 스레드는 keepAliveTime 후 종료되어 풀이 자동 축소.

적합한 케이스

  • 작업이 짧고 자주 들어오는 환경 (스레드 재사용이 잦음)
  • backlog를 만들지 않고 즉시 처리 또는 거부하는 정책

위험

maximumPoolSize 제한이 없으면 부하 spike 때 스레드가 무제한 생성되어 OS 자원 고갈. 반드시 maximumPoolSize를 합리적인 값으로 제한해야 한다. newCachedThreadPool은 이 제한이 없어 4편에서 다룰 함정의 한 사례.

2. LinkedBlockingQueue — 가장 흔한 선택

연결 리스트 기반의 큐. 생성자에 용량을 지정 안 하면 사실상 무한(Integer.MAX_VALUE), 지정하면 그 크기까지만 받는다.

무한 LinkedBlockingQueue의 함정

new ThreadPoolExecutor(
    10, 100,
    60, TimeUnit.SECONDS,
    new LinkedBlockingQueue<>()    // 용량 미지정 → 무한
);

이 풀은 어떻게 동작할까. core 10이 다 차면 큐에 쌓이는데, 큐가 무한이라 절대 가득 차지 않는다. 1편의 흐름에서 "큐 거부 → max 확장" 단계가 영원히 발동하지 않으므로 maximum 100은 사실상 무의미. 풀은 영원히 corePoolSize 10에 머무르고, 부하가 많아지면 큐만 무한정 자라 OOM.

Executors.newFixedThreadPool과 newSingleThreadExecutor가 정확히 이 함정. 이름은 안전해 보이지만 무한 큐 때문에 OOM 위험이 내재.

유한 LinkedBlockingQueue

new ThreadPoolExecutor(
    10, 100,
    60, TimeUnit.SECONDS,
    new LinkedBlockingQueue<>(500)   // 용량 500
);

용량을 지정하면 큐가 가득 찰 수 있어 max까지 확장이 정상 동작. 위 예시는 평소 10 스레드, 큐 500개까지 쌓이고, 그래도 부족하면 100 스레드까지 확장. 모두 다 차면 reject. 가장 무난한 패턴.

특성

  • 연결 리스트라 동적으로 크기 변경, 메모리 효율적
  • put/take용 락이 분리되어 있어 동시성 좋음 (head와 tail 별도 잠금)
  • 높은 throughput

3. ArrayBlockingQueue — 고정 크기 배열

new ThreadPoolExecutor(
    10, 100,
    60, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(500)
);

특성

  • 고정 크기 원형 버퍼 (배열 기반)
  • put과 take가 같은 락을 공유 → LinkedBlockingQueue보다 동시성 약간 낮음
  • 메모리 사전 할당 (배열 크기만큼)
  • 예측 가능한 메모리 사용량

LinkedBlockingQueue (유한)와의 차이

기능은 거의 같다. 둘 다 유한 큐이고 풀 동작은 동일. 미세한 차이가 있다 — Linked는 동시성 처리가 더 좋고 노드를 동적으로 만들지만, Array는 고정 메모리 풋프린트가 보장됨. 대부분의 실무에선 LinkedBlockingQueue(유한)가 흔한 선택. ArrayBlockingQueue는 메모리 예측이 critical한 환경에 적합.

4. PriorityBlockingQueue — 우선순위 큐

작업에 우선순위를 두고 그 순서로 처리하는 큐. Comparator 또는 Comparable로 우선순위 정의. 용량은 사실상 무한(자동 확장), 정렬된 순서로 take. 

PriorityBlockingQueue<Runnable> queue = new PriorityBlockingQueue<>(
    11,
    Comparator.comparingInt(r -> ((PriorityTask) r).priority())
);

new ThreadPoolExecutor(
    10, 10,    // core == max (큐가 무한이라 어차피 max 확장 안 됨)
    0, TimeUnit.MILLISECONDS,
    queue
);

특성과 함정

우선순위 정렬을 위해 heap 자료구조를 사용 — 한 번의 take에 O(log n). 무한 큐라 max 확장이 트리거되지 않으므로 max는 사실상 의미 없다. 또한 작업이 단순한 Runnable이라면 우선순위를 어떻게 매길지 별도로 설계해야 한다.

잘못 쓰면 starvation 위험. 우선순위가 낮은 작업이 영원히 처리되지 않을 수 있다. 반드시 fairness 또는 timeout 정책을 함께 설계해야 한다.

큐 선택 가이드

상황권장 큐이유
일반 웹/API 서버 유한 LinkedBlockingQueue backlog 흡수 + max 확장 트리거 정상 동작
짧은 작업의 burst 처리 SynchronousQueue + max 제한 즉시 처리 또는 거부, backlog 만들지 않음
메모리 예측 critical ArrayBlockingQueue 고정 메모리 풋프린트 보장
긴 작업 + 우선순위 차이 큼 PriorityBlockingQueue 중요 작업 우선 처리, starvation 대책 필수
지연 처리 작업 DelayQueue 예약 실행, ScheduledThreadPoolExecutor 기반

큐 크기를 정하는 법

유한 큐를 쓸 때 크기는 어떻게 정하나. Brian Goetz 공식과 Little's Law의 연장.

  1. 평균 부하 기준 throughput과 latency 측정
  2. 그 부하에서 동시 처리 작업 수 = corePoolSize 정도면 큐는 비어있어야 함
  3. spike를 감안해 큐 크기를 corePoolSize의 1~10배 사이에서 시작
  4. 모니터링하며 큐가 평소 거의 비어있는지, spike에 흡수되는지 확인

큐를 너무 크게 두면 max 확장이 안 일어나서 응답 시간만 길어진다 (큐에서 대기 시간). 너무 작으면 spike에 reject가 자주 발생. 중간점을 찾는 것이 튜닝의 본체.

면접 단골 질문

Q. SynchronousQueue가 큐인가?

이름은 큐이지만 용량이 0이라 어떤 작업도 저장하지 않는다. 생산자와 소비자의 직접 핸드오프 역할만. 큐가 거부하면 max로 확장하는 ThreadPool 흐름과 결합되어, newCachedThreadPool 같은 동작 — 받을 스레드 없으면 새 스레드 생성 — 을 만든다.

Q. 무한 LinkedBlockingQueue의 위험?

큐가 절대 가득 차지 않으니 max 확장 트리거가 발동하지 않는다. 풀은 영원히 corePoolSize에 머물고 큐만 무한정 자라 OOM. Executors.newFixedThreadPool, newSingleThreadExecutor가 이 함정에 빠진다. 유한 큐를 명시적으로 두는 게 안전.

Q. PriorityBlockingQueue의 함정?

무한 큐라 max 확장 안 됨, 우선순위 낮은 작업의 starvation 위험, take가 O(log n)이라 high-throughput 워크로드엔 부적합. 우선순위가 정말 필요한 특수한 케이스에만 쓰고, 그 경우에도 fairness/timeout 대책 함께 설계.

Q. ArrayBlockingQueue와 LinkedBlockingQueue 중 무엇?

기능적으로 거의 같지만 Linked가 동시성 처리에 약간 유리 (head/tail 락 분리). Array는 고정 메모리 풋프린트가 보장되어 메모리 예측이 critical한 환경에 적합. 대부분 일반 워크로드에선 유한 LinkedBlockingQueue가 무난한 선택.

한 줄 정리

BlockingQueue의 종류가 풀 동작을 결정한다. SynchronousQueue는 즉시 처리 또는 거부, 무한 LinkedBlockingQueue는 max 확장 무력화 + OOM 위험, 유한 LinkedBlockingQueue/ArrayBlockingQueue는 정상적인 backlog + 확장 동작. PriorityBlockingQueue는 우선순위가 필요한 특수 케이스용.
