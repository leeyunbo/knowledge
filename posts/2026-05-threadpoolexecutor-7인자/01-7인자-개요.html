ThreadPoolExecutor 7인자 개요

작업이 들어왔을 때 풀이 어떻게 행동할지 결정하는 7개의 인자. 그 인자들이 만들어내는 한 가지 기본 흐름을 먼저 머릿속에 박아두는 것이 출발점.

왜 ThreadPool인가

매 작업마다 새 스레드를 만드는 건 비싸다. JVM 메모리 시리즈에서 본 것처럼 스레드 하나에 native 메모리 1MB 이상이 잡히고, OS 수준에서 스레드 생성/소멸도 무거운 작업. 많은 짧은 작업이 들어오는 워크로드(웹 서버 요청 처리 등)에서 매번 스레드를 만들면 그 비용만으로 시스템이 무너진다.

ThreadPool은 미리 만든 스레드들을 재사용하는 패턴. 작업이 들어오면 노는 스레드에 할당하고, 작업이 끝나면 그 스레드는 다시 풀로 돌아가 다음 작업을 기다린다. 스레드 생성/소멸 비용을 분산하고, 동시 실행 스레드 수에 상한을 두어 자원 폭주를 막는다.

ThreadPoolExecutor의 7가지 인자

Java 5에서 도입된 java.util.concurrent.ThreadPoolExecutor의 가장 일반적인 생성자가 받는 7개의 인자. 

public ThreadPoolExecutor(
    int corePoolSize,
    int maximumPoolSize,
    long keepAliveTime,
    TimeUnit unit,
    BlockingQueue<Runnable> workQueue,
    ThreadFactory threadFactory,
    RejectedExecutionHandler handler
)

이 일곱 인자가 풀의 모든 행동을 결정한다. 하나씩 짚어본다.

인자의미주요 영향
corePoolSize 유지하는 기본 스레드 수 가만히 있어도 살아있는 스레드 수의 하한
maximumPoolSize 최대 스레드 수 풀이 동시에 가질 수 있는 스레드 수의 상한
keepAliveTime 유휴 스레드 생존 시간 core 초과 스레드가 노는 동안 살아있는 시간
unit keepAliveTime 단위 TimeUnit.SECONDS 등
workQueue 대기 작업 큐 풀이 모두 바쁠 때 작업이 들어가는 자리
threadFactory 스레드 생성 방법 이름, 우선순위, daemon 여부 등 커스터마이징
handler 거부 정책 풀과 큐가 모두 가득 찼을 때 어떻게 할지

작업이 들어왔을 때의 흐름

가장 중요한 그림. 인자들의 의미는 이 흐름을 알아야 비로소 이해된다. ThreadPoolExecutor는 새 작업을 받으면 다음 순서로 처리한다.

흐름 정리

  1. 현재 스레드 수가 corePoolSize 미만이면 새 스레드를 만들어 실행
  2. core가 다 찼으면 workQueue에 넣어 대기
  3. 큐가 거부하면(가득 찼다는 의미) 스레드 수가 maximumPoolSize 미만일 때 새 스레드 생성
  4. maximum까지 다 차서 새로 만들 수도 없으면 RejectedExecutionHandler 호출

가장 자주 오해되는 부분 — 큐가 maximum 확장의 트리거

많은 사람이 "스레드가 부족하면 maximum까지 늘어난다"고 막연히 생각한다. 실제로는 그렇지 않다. 큐가 가득 차야 maximum까지 확장된다. 큐에 자리가 있으면 풀은 corePoolSize에 머무른다.

이 미묘한 동작이 다음 편들의 주제와 연결된다. 큐의 종류에 따라 풀이 사실상 어떻게 동작할지 결정되고, 잘못된 큐 선택은 처리량 저하나 OOM 같은 실무 함정으로 이어진다. 예를 들어 무한 LinkedBlockingQueue를 쓰면 큐가 절대 가득 차지 않으니 maximumPoolSize는 사실상 의미 없는 숫자가 되고, 풀은 영원히 corePoolSize에 머무른다.

인자별 디테일

corePoolSize와 maximumPoolSize

core는 항상 살아있는 스레드의 하한, max는 살 수 있는 스레드의 상한. 기본 동작에서 core 스레드들은 idle해도 죽지 않는다. 예외적으로 allowCoreThreadTimeOut(true)를 호출하면 core 스레드도 keepAliveTime 후 종료될 수 있다.

keepAliveTime

core를 초과해 만들어진 스레드가 작업 없이 노는 동안 살아있는 시간. 이 시간 동안 작업이 들어오지 않으면 그 스레드는 종료되어 풀에서 사라진다. 순간적인 부하 spike에 maximum까지 늘렸다가 부하가 가라앉으면 자연스럽게 core로 돌아오는 메커니즘.

workQueue

BlockingQueue<Runnable>. 풀이 모두 바쁠 때 작업이 들어가는 대기실. 종류 선택이 풀의 동작 특성을 크게 바꾼다 — 3편의 주제.

threadFactory

새 스레드를 만들 때 호출되는 팩토리. 스레드 이름, 우선순위, daemon 여부, UncaughtExceptionHandler 등을 설정. 운영에서 가장 중요한 건 이름. 의미 없는 이름이면 thread dump를 봐도 어느 풀의 스레드인지 알기 어렵다. 

ThreadFactory factory = new ThreadFactoryBuilder()
    .setNameFormat("order-worker-%d")
    .setDaemon(true)
    .setUncaughtExceptionHandler((t, e) -> log.error("Worker error", e))
    .build();

handler (RejectedExecutionHandler)

풀과 큐가 모두 가득 차서 더 받을 수 없을 때 호출되는 콜백. 기본 4가지 정책이 제공되며 직접 구현도 가능. 4편에서 자세히.

예시 — 흔한 설정 한 줄로 보기

ThreadPoolExecutor executor = new ThreadPoolExecutor(
    10,                                  // core
    50,                                  // max
    60, TimeUnit.SECONDS,                // keepAlive
    new ArrayBlockingQueue<>(100),       // 유한 큐
    new ThreadFactoryBuilder()
        .setNameFormat("worker-%d").build(),
    new ThreadPoolExecutor.CallerRunsPolicy()  // 거부 시 호출자가 실행
);

이 풀은 평소 10개 스레드로 처리하다가 큐(100개)가 가득 차면 50개까지 늘어난다. 50개로도 부족하면 호출자 스레드가 직접 작업을 실행해 backpressure를 만든다. 유휴 스레드는 60초 후 정리되어 평상시 부하로 돌아간다.

면접 단골 질문

Q. ThreadPoolExecutor의 7가지 인자는?

corePoolSize, maximumPoolSize, keepAliveTime, unit, workQueue, threadFactory, handler. 기본 스레드 수, 최대 스레드 수, 유휴 생존 시간과 단위, 대기 큐, 스레드 생성 방법, 거부 정책. 이 일곱이 풀의 모든 행동을 결정한다.

Q. 작업 처리 흐름은?

① core 미달 → 새 스레드 생성. ② core 다 차면 큐에 적재. ③ 큐 가득 차면 max까지 새 스레드 생성. ④ max도 다 차면 RejectedExecutionHandler 호출. 핵심은 큐가 가득 차야 max까지 확장된다는 것 — 큐에 자리 있으면 풀은 core에 머문다.

Q. 무한 큐를 쓰면 어떻게 되나?

큐가 절대 가득 차지 않으니 maximumPoolSize는 사실상 의미 없다. 풀은 영원히 corePoolSize에 머무르고, 부하가 늘어나면 큐에 작업이 무한정 쌓여 OOM 위험. Executors.newFixedThreadPool과 newSingleThreadExecutor가 이 함정에 빠진다.

Q. allowCoreThreadTimeOut의 효과?

기본 동작은 core 스레드가 idle해도 죽지 않는다. 이 옵션을 켜면 core 스레드도 keepAliveTime 후 종료 가능. 가끔만 부하가 들어오는 풀에서 평상시 자원을 아낄 수 있다. 단, 매 부하마다 스레드 생성 비용이 다시 들어가므로 응답 시간 sensitive한 곳엔 부적합.

한 줄 정리

ThreadPoolExecutor의 7인자가 풀의 모든 행동을 결정한다. 작업 흐름은 core → queue → max → reject 순으로 진행되고, 가장 자주 오해되는 부분은 "큐가 가득 차야 max까지 확장된다"는 점. 이 흐름을 머리에 박은 뒤에야 풀 사이징과 큐 선택의 의미가 보인다.
