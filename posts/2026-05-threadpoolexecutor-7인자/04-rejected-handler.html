RejectedExecutionHandler와 Executors 함정

풀과 큐가 모두 가득 찼을 때의 마지막 방어선. 그리고 가장 흔한 함정인 Executors 팩토리 메서드의 본체.

거부의 의미

1편에서 본 흐름의 마지막 단계. 풀의 스레드가 max까지 차고 큐도 가득 차면 더 이상 새 작업을 받을 수 없다. 이 시점에 호출되는 콜백이 RejectedExecutionHandler. 시스템이 자기 한계를 인정하고 어떻게 대응할지 결정하는 자리.

거부 자체가 나쁜 게 아니다. 무한정 작업을 받아 OOM을 일으키는 것보다 명확한 거부와 backpressure가 시스템 안정성에 훨씬 좋다. 어떤 거부 정책을 쓸지가 시스템 동작의 성격을 결정.

기본 제공되는 4가지 정책

ThreadPoolExecutor 안에 정적 inner class로 정의되어 있다.

1. AbortPolicy — 예외 던지기 (기본)

new ThreadPoolExecutor.AbortPolicy()   // 기본값

가장 단순한 정책. 거부된 작업에 대해 RejectedExecutionException을 던진다. 호출자는 이 예외를 받아 어떻게 대응할지 자기 코드에서 결정해야 한다. 명시적이고 예측 가능하지만 호출자가 처리하지 않으면 런타임 에러로 흘러간다.

2. CallerRunsPolicy — 호출자가 직접 실행

new ThreadPoolExecutor.CallerRunsPolicy()

거부된 작업을 풀 대신 submit을 호출한 스레드가 직접 실행한다. 예외 없이 처리되지만, 호출자 스레드(보통 웹 서버의 요청 처리 스레드)가 그 시간 동안 작업에 묶여 새 요청을 받지 못한다.

왜 좋은가 — 자연스러운 backpressure

호출자가 묶이면 다음 요청 처리도 자연히 늦어진다. 이건 부정적 효과 같지만 사실 시스템 안정성에 큰 도움. 새 요청 유입 속도가 자동으로 느려져 풀의 부담이 줄어든다. backlog가 통제 불가하게 자라는 대신 호출자에게로 부담이 거꾸로 전파되는 셈.

이 패턴이 분산 시스템의 backpressure 핵심. 외부 API 호출에서 본 sliding window나 Token Bucket 같은 개념의 micro 버전. 웹 서버에서 가장 자주 추천되는 정책 중 하나.

3. DiscardPolicy — 조용히 버리기

new ThreadPoolExecutor.DiscardPolicy()

거부된 작업을 그냥 버린다. 예외도 없고 로그도 없음. 작업 손실이 허용되는 환경에서만 사용 — 메트릭 수집, 일부 로그, 분석용 이벤트 등. 비즈니스 로직에는 절대 쓰지 말 것 — 작업이 사라진 사실을 아무도 모르는 위험한 정책.

4. DiscardOldestPolicy — 가장 오래된 것 버리고 새 작업 큐에

new ThreadPoolExecutor.DiscardOldestPolicy()

큐의 head(가장 오래된 작업)를 버리고 새 작업을 큐에 넣는다. "최신 작업을 우선시"하는 의미. 실시간성이 중요한 워크로드 — 예: 가장 최근 시세만 의미 있는 트레이딩 시스템 — 에 적합. PriorityBlockingQueue와 함께 쓰면 의도하지 않은 동작이 나오므로 주의.

커스텀 핸들러

기본 4가지로 부족하면 직접 구현. RejectedExecutionHandler 인터페이스의 한 메서드만 구현하면 된다. 

RejectedExecutionHandler handler = (task, executor) -> {
    log.warn("Task rejected, queueSize={}, activeCount={}",
        executor.getQueue().size(),
        executor.getActiveCount());
    metrics.incrementCounter("pool.rejected");

    if (executor.isShutdown()) {
        throw new RejectedExecutionException("Pool is shutdown");
    }

    try {
        if (!executor.getQueue().offer(task, 100, TimeUnit.MILLISECONDS)) {
            throw new RejectedExecutionException("Queue still full after waiting");
        }
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
    }
};

위 예시는 거부 시 메트릭 카운터 증가 + 짧게 큐를 다시 시도해보는 패턴. 실무에서는 보통 메트릭 + 로그 + 적절한 backpressure를 조합한 커스텀 핸들러가 필요.

정책 선택 가이드

워크로드권장 정책이유
일반 웹 서버 CallerRunsPolicy backpressure 자연 발생, 안정성 좋음
중요 비즈니스 작업 AbortPolicy + 명시적 처리 거부를 호출자가 인지하고 대응
실시간 데이터 (시세 등) DiscardOldestPolicy 최신 데이터만 의미 있을 때

커스텀 요구사항 직접 구현 메트릭 + 로그 + 특수 로직

Executors 팩토리의 함정

Java가 제공하는 java.util.concurrent.Executors 클래스는 ThreadPoolExecutor의 흔한 설정을 한 줄로 만들어주는 팩토리 메서드 모음. 이름이 안전해 보이지만 대부분 함정이 숨어 있어 실무에서 직접 사용은 권장되지 않는다.

newFixedThreadPool(n)

// 내부 구현
public static ExecutorService newFixedThreadPool(int nThreads) {
    return new ThreadPoolExecutor(
        nThreads, nThreads,
        0L, TimeUnit.MILLISECONDS,
        new LinkedBlockingQueue<Runnable>()    // ★ 무한 큐
    );
}

고정된 n개 스레드의 풀. 이름은 "fixed"라 안전해 보이지만 큐가 무한 LinkedBlockingQueue. 3편에서 본 함정 — 큐가 가득 차지 않으니 max 확장 트리거 안 됨, 큐만 무한정 자라 OOM. 부하가 처리 능력을 초과하면 메모리에 작업이 쌓이다 결국 터진다.

newSingleThreadExecutor()

public static ExecutorService newSingleThreadExecutor() {
    return new FinalizableDelegatedExecutorService(
        new ThreadPoolExecutor(
            1, 1,
            0L, TimeUnit.MILLISECONDS,
            new LinkedBlockingQueue<Runnable>()    // ★ 무한 큐
        )
    );
}

단일 스레드 풀. 같은 함정 — 무한 큐. 순차 처리가 보장되지만 큐 폭발 위험.

newCachedThreadPool()

public static ExecutorService newCachedThreadPool() {
    return new ThreadPoolExecutor(
        0, Integer.MAX_VALUE,                  // ★ max 무제한
        60L, TimeUnit.SECONDS,
        new SynchronousQueue<Runnable>()
    );
}

작업이 들어오면 idle 스레드를 재사용하고 없으면 새로 만든다. maximum이 Integer.MAX_VALUE라 사실상 무제한. 짧은 작업 부하엔 효율적이지만 부하 spike 때 스레드가 무제한 생성되어 OS 자원 고갈. OutOfMemoryError: unable to create new native thread가 흔한 결과.

newScheduledThreadPool(n)

public static ScheduledExecutorService newScheduledThreadPool(int corePoolSize) {
    return new ScheduledThreadPoolExecutor(corePoolSize);
}

ScheduledThreadPoolExecutor는 max가 Integer.MAX_VALUE이지만 큐가 DelayQueue (무한)이라 max 확장이 트리거되지 않음. 사실상 corePoolSize 고정. 예약 작업이 늘어나면 DelayQueue가 커지므로 OOM 위험은 있지만 newCachedThreadPool 정도는 아님. 그래도 직접 ThreadPoolExecutor를 쓰는 게 권장.

왜 Executors가 위험한가 — 한눈에

팩토리함정증상
newFixedThreadPool 무한 LinkedBlockingQueue OutOfMemoryError: Java heap (큐 폭증)
newSingleThreadExecutor 무한 LinkedBlockingQueue 동일
newCachedThreadPool max = Integer.MAX_VALUE OutOfMemoryError: unable to create native thread
newScheduledThreadPool DelayQueue 무한 스케줄링 작업 누적 시 메모리

Goetz, Brian 등이 "Java Concurrency in Practice"에서 Executors 팩토리 사용을 신중히 하라고 권고했고, IntelliJ Inspector도 이 메서드 사용에 경고를 띄운다.

권장 패턴 — 직접 ThreadPoolExecutor 생성

@Bean
public ExecutorService orderExecutor() {
    return new ThreadPoolExecutor(
        10,                                  // core
        50,                                  // max
        60, TimeUnit.SECONDS,                // keepAlive
        new LinkedBlockingQueue<>(500),      // 유한 큐
        new ThreadFactoryBuilder()
            .setNameFormat("order-worker-%d")
            .setDaemon(false)
            .setUncaughtExceptionHandler(this::onUncaught)
            .build(),
        new ThreadPoolExecutor.CallerRunsPolicy()
    );
}

모든 7인자를 명시한다. 큐는 유한, 핸들러는 backpressure 정책, ThreadFactory는 의미 있는 이름과 예외 처리. 이게 운영 환경의 표준 패턴.

Spring의 추상화

Spring은 ThreadPoolTaskExecutor로 ThreadPoolExecutor를 감싼 추상화를 제공. 설정이 더 직관적이고 Bean으로 관리가 쉽다. 

@Bean
public ThreadPoolTaskExecutor orderExecutor() {
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    executor.setCorePoolSize(10);
    executor.setMaxPoolSize(50);
    executor.setQueueCapacity(500);
    executor.setKeepAliveSeconds(60);
    executor.setThreadNamePrefix("order-worker-");
    executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
    executor.initialize();
    return executor;
}

내부적으로 ThreadPoolExecutor를 만들므로 동작은 동일. Spring 환경에서는 이 패턴이 자연스럽다.

Graceful Shutdown

애플리케이션 종료 시 풀의 진행 중 작업이 완료되도록 기다리는 패턴. 그렇지 않으면 처리 도중 데이터 손실 위험. 

@PreDestroy
public void shutdown() throws InterruptedException {
    executor.shutdown();
    if (!executor.awaitTermination(30, TimeUnit.SECONDS)) {
        executor.shutdownNow();
        if (!executor.awaitTermination(10, TimeUnit.SECONDS)) {
            log.warn("Pool did not terminate cleanly");
        }
    }
}

shutdown()은 새 작업을 거부하고 진행 중인 것은 끝나도록 둠. awaitTermination으로 완료 대기. 타임아웃 후엔 shutdownNow로 강제 종료 시도. 이 패턴이 안전한 종료의 표준.

면접 단골 질문

Q. RejectedExecutionHandler 4종의 차이?

AbortPolicy(기본): 예외 던지기. CallerRunsPolicy: 호출자가 직접 실행 → 자연스러운 backpressure. DiscardPolicy: 조용히 버림 (위험). DiscardOldestPolicy: 큐의 가장 오래된 것 버리고 새 작업 큐에. 웹 서버 일반 권장은 CallerRunsPolicy, 비즈니스 critical은 AbortPolicy + 명시적 처리.

Q. Executors 팩토리가 왜 위험한가?

newFixedThreadPool, newSingleThreadExecutor는 무한 LinkedBlockingQueue를 써서 큐 폭증 OOM. newCachedThreadPool은 max가 Integer.MAX_VALUE라 스레드 무제한 생성 — native thread OOM. 모두 부하 spike 때 시스템을 무너뜨릴 수 있어, 직접 ThreadPoolExecutor 또는 ThreadPoolTaskExecutor를 쓰는 게 권장.

Q. CallerRunsPolicy가 backpressure를 만드는 이유?

거부된 작업을 호출자(보통 요청 처리 스레드)가 직접 실행해야 한다. 그 시간 동안 호출자는 새 요청을 받지 못해 자연스럽게 유입 속도가 줄어든다. 시스템이 자기 한계 안에서 안정적으로 동작하도록 부담이 거꾸로 전파되는 셈. 웹 서버 일반 권장 패턴.

Q. Graceful Shutdown은 어떻게?

@PreDestroy 또는 SIGTERM 핸들러에서 shutdown() → awaitTermination(timeout) → 타임아웃 후 shutdownNow(). 이 패턴으로 진행 중 작업을 마무리할 시간을 주고 한도를 넘으면 강제 종료. Spring의 setWaitForTasksToCompleteOnShutdown과 setAwaitTerminationSeconds로 자동화 가능.

한 줄 정리

RejectedExecutionHandler는 풀과 큐가 가득 찼을 때의 마지막 방어선. 웹 서버 일반은 CallerRunsPolicy로 backpressure를, critical 작업은 AbortPolicy + 명시 처리, 데이터 손실 허용은 Discard 계열. Executors 팩토리는 안전해 보이지만 대부분 함정이 있어, 직접 ThreadPoolExecutor를 만드는 게 권장. Graceful Shutdown으로 종료 시 데이터 손실을 막는 것까지가 풀 운영의 표준.

ThreadPoolExecutor 시리즈는 여기까지. 다음은 동시성의 고전 함정 — ThreadLocal.
