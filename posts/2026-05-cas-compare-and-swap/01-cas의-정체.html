락이 비싼 이유부터

여러 스레드가 같은 값을 동시에 바꿀 때 가장 먼저 떠오르는 도구가 synchronized예요. 안전하긴 한데 비용이 있어요. 락을 잡는 동안 다른 스레드는 대기하고, 경합이 심해지면 OS 수준 컨텍스트 스위칭까지 발생해요.

그런데 사실 카운터 하나 증가시키는 정도의 작업에 락은 좀 과해요. 그래서 등장한 게 락 없이 원자적으로 값을 바꾸는 방법, CAS예요.

CAS가 하는 일

CAS는 Compare And Swap의 약자예요. 한 줄로 표현하면 이래요.

"메모리의 어느 위치 값이 A라면, 그 값을 B로 바꿔. 아니면 아무것도 하지 마."

핵심은 이 비교와 교체가 원자적으로 일어난다는 거예요. 다른 스레드가 끼어들 수 없는 단일 연산이라는 뜻이에요. CPU 명령어 하나가 이걸 보장하기 때문에 락 없이도 안전한 갱신이 가능해요.

CPU 명령어 수준

CAS는 그냥 추상적인 개념이 아니라 실제 CPU 명령어로 구현돼요.

  • x86: CMPXCHG 명령어 (LOCK 접두사로 원자성 보장)
  • ARM: LDREX + STREX 한 쌍 (load-link / store-conditional 방식)
  • RISC-V: LR/SC 한 쌍

이름과 형태는 다르지만 셋 다 같은 일을 해요. 짧고 빠르며, 락이 필요 없어요.

자바에서 CAS 만나기

자바 개발자가 CAS를 직접 다루는 자리는 AtomicInteger, AtomicLong 같은 java.util.concurrent.atomic 패키지의 클래스예요. 

AtomicInteger counter = new AtomicInteger(0);

// 단일 CAS 호출
boolean success = counter.compareAndSet(0, 1);
// 메모리가 0이면 1로 바꾸고 true, 아니면 false

// CAS 기반의 increment
int newValue = counter.incrementAndGet();

incrementAndGet 안에서 일어나는 일

incrementAndGet()은 단순해 보이지만 내부에서 CAS를 반복해요. 

public final int incrementAndGet() {
    int oldValue, newValue;
    do {
        oldValue = get();             // 현재 값 읽기
        newValue = oldValue + 1;      // 새 값 계산
    } while (!compareAndSet(oldValue, newValue));   // CAS 실패하면 재시도
    return newValue;
}

이 패턴이 흔히 말하는 spin loop예요. 다른 스레드가 같은 값을 먼저 바꿔서 CAS가 실패하면, 새로 읽고 다시 계산해서 다시 시도해요. 누가 결국 한 번은 성공하니까 작업은 진행되고, 실패한 쪽만 잠깐 더 도는 셈이에요.

CAS의 장점

왜 락 대신 CAS를 쓰는지, 정리하면 이래요.

  • 락 비용 없음: OS 수준 mutex 호출이 없어요. 컨텍스트 스위칭도 없고요
  • 경합이 적을 때 매우 빠름: 한 번에 성공하면 거의 무료에 가까워요
  • 데드락 위험 없음: 락을 안 잡으니 순환 대기 자체가 불가능해요
  • 인터럽트 안전: 락이 걸려있지 않으니 어떤 스레드가 죽어도 다른 스레드를 막지 않아요

CAS의 단점

만능은 아니에요. 뒤집으면 이런 단점이 보여요.

  • 경합이 심하면 효율 떨어짐: spin loop가 retry를 반복해서 CPU만 태워요
  • 단일 변수에만 효과적: 여러 변수의 일관성을 한 번에 보장하기 어려워요
  • ABA 문제: 값이 A에서 B로 갔다가 다시 A로 돌아오면 변경을 감지 못해요 (다음 편 주제)
  • spin이 길어지면 오히려 손해: 락보다 느려질 수도 있어요

경합이 심할 때의 대안

AtomicLong이 경합이 심하면 spin loop가 지옥이 될 수 있어요. 그래서 자바 8에서 LongAdder가 등장했어요. 

LongAdder counter = new LongAdder();
counter.increment();   // 내부적으로 여러 cell에 분산해 갱신
long total = counter.sum();   // 합산할 때만 모음

핵심 아이디어는 단순해요. 모든 스레드가 같은 메모리 위치를 두고 다투지 말고, 여러 cell에 나눠서 갱신하다가 합계가 필요할 때만 모으자는 거예요. 경합이 분산되니 spin loop가 거의 발생하지 않아요.

상황적합한 도구
경합 적은 카운터 AtomicLong
경합 심한 카운터 (트래픽 메트릭, 통계) LongAdder
현재 값을 자주 읽어야 함 AtomicLong (sum이 비교적 비싸요)
값을 거의 안 읽고 누적만 LongAdder

CAS가 살아 있는 자리

자바의 동시성 도구 거의 전부가 CAS 위에 서 있다고 봐도 돼요.

  • ConcurrentHashMap의 버킷별 락 회피 갱신
  • AtomicReference로 만드는 lock-free 자료구조 (Stack, Queue)
  • ReentrantLock 내부의 큐 처리 (AQS, AbstractQueuedSynchronizer)
  • CompletableFuture의 상태 전이
  • CountDownLatch, Semaphore의 카운터 갱신

j.u.c 패키지를 만든 Doug Lea가 CAS 없이는 거의 모든 클래스를 다시 짜야 한다고 말한 적이 있는데, 과장이 아니에요.

면접 단골 질문

Q. CAS가 뭔가요?

Compare And Swap의 약자예요. 메모리 어느 위치의 값이 기대값과 같으면 새 값으로 바꾸고, 다르면 아무것도 안 해요. 이 비교와 교체가 CPU 명령어 한 번으로 원자적으로 일어나서, 락 없이도 동시성 안전한 갱신이 가능해요.

Q. 왜 락 대신 CAS를 쓰나요?

OS 수준 락은 컨텍스트 스위칭 비용이 있어요. 카운터 한 번 증가시키는 작업에 그 비용을 치르는 건 과해요. CAS는 CPU 명령어 한 번이라 매우 빠르고, 락이 없으니 데드락 위험도 없어요. 대신 경합이 심하면 spin loop가 비효율적이라는 단점이 있어요.

Q. AtomicLong과 LongAdder의 차이는요?

AtomicLong은 단일 메모리 위치를 CAS로 갱신해요. 경합 적을 때 가장 빠르지만, 경합 심하면 spin loop가 늘어나요. LongAdder는 여러 cell에 나눠 갱신하다가 합계가 필요할 때만 모아요. 경합 분산이 핵심이라 메트릭/카운터에 적합해요.

Q. CAS의 한계는요?

단일 변수에만 효과적이고, 여러 변수의 일관성을 한 번에 보장하긴 어려워요. 경합이 심하면 spin loop 비용이 누적돼서 락보다 느려질 수도 있어요. 그리고 ABA 문제가 있는데, 다음 편에서 자세히 봐요.

한 줄 정리

CAS는 락 없이 원자적 갱신을 가능하게 하는 CPU 명령어예요. AtomicInteger같은 클래스가 이걸 spin loop로 활용해서 동시성 안전한 카운터를 제공해요. j.u.c의 거의 모든 클래스가 CAS 위에 서 있다고 봐도 좋아요. 단, 경합이 심하면 비효율적이고 다음 편에서 볼 ABA 문제도 있어요.
