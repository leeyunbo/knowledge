ABA 문제가 뭔가요

이름 그대로 값이 A에서 B로 갔다가 다시 A로 돌아오는 상황이에요. CAS는 "현재 값이 A냐?"만 확인하기 때문에, 그 사이에 다른 스레드가 값을 바꿨다가 되돌려놨어도 알아차릴 수 없어요.

시나리오

간단한 예시로 따라가볼게요. 

AtomicReference<Integer> ref = new AtomicReference<>(10);

// 스레드 1
Integer expected = ref.get();   // 10 읽기
// ... 잠깐 다른 일을 함

// 그 사이 스레드 2와 3이
ref.compareAndSet(10, 20);      // 10 → 20
ref.compareAndSet(20, 10);      // 20 → 10 (다시 원래대로)

// 스레드 1이 돌아와서
ref.compareAndSet(expected, 30); // 현재 값 10 == 기대값 10 → 성공!

스레드 1 입장에서는 "내가 본 값이 그대로 있네, 안 바뀌었구나"라고 판단해요. 그런데 사실 그 사이 두 번이나 바뀌었다 돌아온 거죠. 이걸 모르고 진행하면 미묘한 버그가 생길 수 있어요.

왜 문제가 되나요

단순한 정수 카운터라면 ABA가 별 문제 안 돼요. 결국 같은 값이니까요. 진짜 문제는 참조형 자료구조에서 일어나요.

유명한 사례 — 락프리 스택

class LockFreeStack<T> {
    private final AtomicReference<Node<T>> head = new AtomicReference<>();

    public void push(T value) {
        Node<T> newHead = new Node<>(value);
        Node<T> oldHead;
        do {
            oldHead = head.get();
            newHead.next = oldHead;
        } while (!head.compareAndSet(oldHead, newHead));
    }

    public T pop() {
        Node<T> oldHead, newHead;
        do {
            oldHead = head.get();
            if (oldHead == null) return null;
            newHead = oldHead.next;
        } while (!head.compareAndSet(oldHead, newHead));
        return oldHead.value;
    }
}

평범한 락프리 스택이에요. 그런데 여기에 ABA 함정이 숨어 있어요.

ABA가 만드는 결함 시나리오

스택에 노드 A, B, C가 쌓여 있다고 해볼게요. head → A → B → C 순서예요.

  1. 스레드 1이 pop() 시작. oldHead = A, newHead = B로 읽음
  2. 스레드 1이 잠깐 멈춤 (스케줄링)
  3. 스레드 2가 빠르게 pop() 두 번 실행: A 제거, B 제거
  4. 스레드 2가 push(A): A를 다시 head로 넣음. 이제 head → A → C
  5. 스레드 1이 깨어나 CAS 실행: head == A 맞으니까 성공으로 처리됨
  6. head가 newHead(=B)로 바뀜. 그런데 B는 이미 스택에서 빠진 노드

결과적으로 head가 사라진 노드 B를 가리키는 깨진 상태가 돼요. 스택 구조 자체가 망가져서 다음 작업부터 잘못된 결과가 나와요. C 노드가 갑자기 사라지는 거예요.

해결 — 버전 스탬프 붙이기

아이디어는 단순해요. 값만 비교하지 말고 값 + 버전을 함께 비교하는 거예요. 값을 바꿀 때마다 버전을 1씩 증가시키면, 값이 같아도 버전이 다르면 변경을 감지할 수 있어요.

AtomicStampedReference

자바가 이 패턴을 위한 클래스를 제공해요. 

AtomicStampedReference<Integer> ref = new AtomicStampedReference<>(10, 0);

int[] stampHolder = new int[1];
Integer value = ref.get(stampHolder);
int currentStamp = stampHolder[0];

// 값과 stamp 둘 다 일치해야 성공
boolean success = ref.compareAndSet(
    value,           // 기대 값
    20,              // 새 값
    currentStamp,    // 기대 stamp
    currentStamp + 1 // 새 stamp
);

값을 바꿀 때마다 stamp(버전)도 함께 증가시켜요. A → B → A로 돌아왔어도 stamp는 0 → 1 → 2로 올라가니까, 스레드 1이 갖고 있던 stamp 0과 다른 걸 보고 변경을 감지할 수 있어요.

그림으로

AtomicMarkableReference

비슷한 클래스가 하나 더 있어요. AtomicMarkableReference는 stamp 대신 boolean 플래그를 붙여요. "삭제 표시" 같은 단순한 상태 변화를 표현할 때 쓰여요. 

AtomicMarkableReference<Node> ref = new AtomicMarkableReference<>(node, false);

// 노드를 "삭제 예정"으로 표시
ref.attemptMark(node, true);

// 마킹된 노드는 다른 스레드가 보고 처리
boolean[] markHolder = new boolean[1];
Node current = ref.get(markHolder);
if (markHolder[0]) {
    // 삭제 처리
}

락프리 LinkedList 같은 자료구조에서 노드 삭제를 두 단계로 처리할 때 자주 쓰여요. 버전 자체는 필요 없고 "지워질 예정" 같은 단순 상태만 필요한 경우에 stamp보다 가벼워요.

둘 중 무엇을 쓸지

상황적합한 도구
참조 자료구조의 ABA 방지 AtomicStampedReference
스택, 큐 같은 락프리 자료구조 AtomicStampedReference
"삭제 예정" 같은 단순 상태 표시 AtomicMarkableReference
2단계 노드 제거 (logical delete + physical remove) AtomicMarkableReference
단일 정수 카운터 그냥 AtomicLong (ABA 무관)

실무에서 ABA를 만나기 어려운 이유

이론적으로는 무서운 문제처럼 들리지만, 실무에서 ABA로 인한 실제 사고는 생각보다 드물어요. 이유가 있어요.

  • 대부분의 동시성 코드는 j.u.c의 검증된 클래스 (ConcurrentHashMap, BlockingQueue 등)를 써요
  • 이 클래스들은 내부에서 이미 ABA를 적절히 처리해뒀어요
  • 락프리 자료구조를 직접 만드는 자리가 일반 애플리케이션에는 거의 없어요
  • 단순 카운터/플래그 같은 경우는 ABA가 발생해도 의미적 문제가 없어요

그래도 AtomicReference로 직접 락프리 자료구조를 만들거나, 참조형 값을 CAS로 갱신하는 코드를 짤 일이 있다면 ABA를 의식해야 해요. AtomicStampedReference가 그럴 때를 위한 도구예요.

면접 단골 질문

Q. ABA 문제가 뭔가요?

값이 A에서 B로 바뀌었다가 다시 A로 돌아왔을 때, CAS는 "현재 값이 A냐?"만 확인하기 때문에 변경을 감지하지 못하는 문제예요. 단순 카운터라면 의미상 문제 없지만, 참조형 자료구조에서는 사라진 노드를 가리키는 깨진 상태가 만들어질 수 있어요.

Q. ABA를 어떻게 해결하나요?

값에 버전 스탬프를 함께 붙여요. 자바의 AtomicStampedReference가 이 패턴을 제공해요. 값과 stamp를 둘 다 비교하기 때문에, 값이 같아도 stamp가 다르면 변경됐다고 판단해서 CAS가 실패해요.

Q. 실무에서 ABA를 자주 만나나요?

드물어요. 대부분의 동시성 코드는 j.u.c의 검증된 클래스를 사용하고, 그 안에서 이미 처리돼 있어요. 락프리 자료구조를 직접 구현할 때만 의식하면 돼요. 단순 카운터나 boolean flag면 ABA가 의미상 문제가 안 돼요.

Q. AtomicMarkableReference와 AtomicStampedReference의 차이는요?

AtomicStampedReference는 정수 stamp(버전)를 함께 다뤄요. ABA 방지가 주 용도예요. AtomicMarkableReference는 boolean 플래그를 함께 다뤄요. "삭제 예정" 같은 단순 상태 표시에 적합하고, 락프리 LinkedList의 2단계 삭제에서 자주 쓰여요.

한 줄 정리

ABA 문제는 값이 잠깐 바뀌었다 돌아온 사이의 변경을 CAS가 감지 못하는 사각지대예요. 참조형 자료구조에서 깨진 상태를 만들 수 있고, AtomicStampedReference의 버전 스탬프로 해결해요. j.u.c 클래스를 쓰면 거의 마주치지 않지만, 직접 락프리 자료구조를 만들 때는 반드시 의식해야 해요.
