모놀리스가 뭔가

하나의 코드베이스, 하나의 빌드 산출물, 하나의 배포 단위. 모든 비즈니스 도메인(사용자, 주문, 결제, 알림 등)이 한 애플리케이션 안에 모여 있는 게 모놀리스예요.

"모놀리스 = 나쁜 것"이라는 인식이 한때 있었어요. 지금은 다시 바뀌었어요. 시작 단계에서 모놀리스가 거의 항상 정답이라는 게 업계 합의예요. Shopify, Basecamp, GitHub, Stack Overflow 같은 대형 서비스도 모놀리스로 한참 운영했고, 일부는 여전히 모놀리스예요.

모놀리스의 장점

관점이점
개발 속도한 IDE, 한 저장소, 한 빌드. 인지 비용 최소
배포한 산출물을 한 번 배포. 단순
트랜잭션같은 DB에 단일 ACID 트랜잭션
호출인메모리 함수 호출. 빠르고 안정적
디버깅전체 스택 트레이스. 한 프로세스에서 추적
리팩토링IDE가 전체 영향 범위 자동 추적
운영인스턴스 하나 띄우면 끝

이 장점들이 거대해요. 작은 팀과 작은 시스템에서는 거의 모든 자리에서 모놀리스가 빠르고 안전해요. 의식적으로 "모놀리스로 시작한다"는 결정이 좋은 출발점인 이유예요.

모놀리스의 한계가 드러나는 자리

모놀리스도 영원한 답은 아니에요. 시스템과 팀이 커지면 다음 자리에서 한계가 드러나요.

1. 스케일 단위가 거칠다

사용자 검색 기능만 부하가 큰데, 모놀리스는 그 부분만 스케일할 수 없어요. 전체 애플리케이션을 통째로 더 띄워야 해요. CPU 코어와 메모리를 효율적으로 못 써요.

특정 API가 CPU 집약적이고 다른 API는 I/O 집약적이라면, 둘이 같은 프로세스 안에 있으면 자원 튜닝이 어려워요. JVM 힙 설정, 스레드풀, 캐시 크기를 하나로 통합해야 하니까.

2. 빌드와 배포 시간

코드가 커질수록 빌드가 느려져요. 한 글자 고치는 데 빌드 10분, 배포 30분이 걸리면 개발 속도가 떨어져요. CI도 점점 무거워져요. 한 명이 코드를 머지하면 다른 모두가 기다려요.

3. 기술 다양성 부재

모놀리스는 보통 단일 언어·프레임워크예요. 새 기능에 다른 언어가 더 맞아도 도입이 어려워요. 머신러닝 모델 서빙에 Python이 더 좋은데 Java 모놀리스 안에서는 끼워 넣기 어색해요.

4. 팀 자율성과 Conway's Law

Conway's Law는 "시스템은 그걸 만든 조직의 의사소통 구조를 닮아간다"는 관찰이에요. 팀이 100명인데 모놀리스 하나면 100명이 같은 코드베이스에서 끊임없이 충돌해요. 머지 충돌, 인터페이스 합의, 릴리스 일정 조율이 모두 비용이 돼요.

팀을 작게 나눠 자율적으로 움직이게 하려면, 시스템도 그렇게 나눠지는 게 자연스러워요. 이게 MSA로 가는 가장 강한 동기예요.

5. 장애 격리 부족

한 모듈에서 메모리 누수가 나면 프로세스 전체가 죽어요. 한 라이브러리에 보안 취약점이 있으면 전체 시스템이 노출돼요. 한 기능의 장애가 전체 시스템 다운으로 이어지기 쉬워요.

6. 진화의 마찰

같은 비즈니스 모델 안에서도 어떤 영역은 빠르게 진화하고 어떤 영역은 안정적이어야 해요. 결제는 느리고 안정적으로, 추천은 빠르게 실험하면서. 모놀리스는 두 영역을 같은 배포 주기로 묶어요. 결제 변경이 무서워서 추천 배포 빈도가 떨어지는 식이에요.

그런데 이 한계가 진짜 나타나는 시점은?

중요한 점은 위 한계들이 시스템과 팀이 충분히 커진 이후에야 본격적으로 나타난다는 거예요. 작은 팀, 작은 시스템에서는 위 단점들이 거의 안 보여요. 빌드는 빠르고, 머지 충돌도 적고, 한 사람이 전체 코드를 머릿속에 담을 수 있어요.

그래서 "처음부터 MSA로 가야 한다"는 조언은 거의 항상 틀려요. 큰 시스템이 직면한 문제를 작은 시스템이 미리 떠안는 셈이에요. 분산 시스템의 비용은 큰데 얻는 게 별로 없어요.

모놀리스 안에서 잘 나누기 (Modular Monolith)

모놀리스의 한계가 코드 결합에서 오는 경우가 많아요. 결제 모듈이 사용자 모듈의 내부 함수를 직접 호출하고, 데이터베이스 테이블도 자유롭게 JOIN하면 두 모듈은 사실상 분리 안 된 거예요. 한쪽 변경이 다른 쪽을 깨요.

Modular Monolith는 하나의 배포 단위 안에서 모듈 사이 경계를 엄격하게 지키는 패턴이에요. 각 모듈은 명시적 인터페이스를 통해서만 통신하고, 자기 데이터는 자기만 직접 접근해요. 다른 모듈의 데이터가 필요하면 그 모듈의 공개 API를 호출해요.

이게 잘 돼 있으면 MSA로 분리하기도 쉬워요. 모듈 경계가 이미 서비스 경계의 후보가 돼 있으니까. 반대로 잘 안 돼 있는 모놀리스를 MSA로 쪼개려고 하면 비용이 폭발해요. 그래서 "분리는 깨끗한 모놀리스에서 시작한다"가 정설이에요.

모놀리스가 답인 자리

  • 스타트업 초기: 빠른 진화가 가장 중요한 시기. 분산 시스템 비용은 비싸요.
  • 팀이 10~20명 이하: Two-pizza team 한두 개 규모. 모놀리스로 충분.
  • 도메인이 안정적: 비즈니스 모델이 거의 안 바뀌면 굳이 쪼갤 이유 없음.
  • 강한 일관성이 필수: 금융, 의료 같은 자리. 분산 트랜잭션은 비싸요.
  • 인프라 운영 역량이 부족: Kubernetes, 서비스 메시 운영 인력이 없으면 MSA는 부담만 더 큼.

다음 편

다음 편에서는 MSA로 갈 때 따라오는 비용을 봐요. 네트워크 호출의 비용, 분산 트랜잭션의 어려움, 디버깅과 관찰성의 복잡도, 그리고 Conway's Law가 어떻게 작동하는지를 정리해요.
