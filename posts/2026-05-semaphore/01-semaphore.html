푸는 문제

"동시에 N개까지만 자원에 접근 가능"한 제약을 표현해요. DB 커넥션 풀의 한도, 외부 API의 동시 호출 제한, 무거운 작업의 병렬 수 제한 같은 자리예요. Semaphore는 permit이라는 가상의 토큰을 가지고 있고, 작업이 시작할 때 acquire, 끝날 때 release해요.

기본 사용

Semaphore sem = new Semaphore(3);  // 동시에 3개

executor.submit(() -> {
    sem.acquire();
    try {
        callExternalApi();
    } finally {
        sem.release();
    }
});

주요 메소드

메소드의미
acquire()permit 1개 확보. 없으면 블록.
acquire(n)permit n개 동시 확보.
tryAcquire()즉시 시도. 없으면 false.
tryAcquire(t, unit)timeout 안에 시도.
release()permit 1개 반환.
availablePermits()남은 permit 수.

공정성 옵션

생성자의 두 번째 인자가 fair예요. 

Semaphore sem = new Semaphore(3, true);  // FIFO
  • true: 대기 순서대로 깨어나요. starvation 방지.
  • false (기본): 임의 순서. 처리량 우선.

흔한 자리

1. 자원 풀 제한

DB 커넥션·HTTP 클라이언트 같은 자원의 동시 사용 수를 제한해요. acquire-release를 try-finally로 둘러싸요.

2. Rate Limiting 토대

Rate Limiting 시리즈의 Token Bucket이 사실 Semaphore와 비슷한 발상이에요. permit을 일정 속도로 다시 보충하면 그게 token bucket이에요.

3. 동시 실행 작업 수 제한

무거운 작업을 동시에 너무 많이 실행하면 OOM이 와요. Semaphore로 동시 실행 수를 5~10개로 제한해요.

4. Mutex 흉내

Semaphore(1)이면 mutex처럼 동작해요. 다만 ReentrantLock이 더 풍부한 API와 reentrant 보장을 주니, mutex 용도면 ReentrantLock이 정석이에요.

흔한 실수

1. release 누락

acquire 후 예외가 나면 release가 안 돼요. permit이 영원히 소비된 상태로 남아요. 항상 try-finally에 release를 둬요.

2. permit 수 잘못 잡기

너무 적으면 처리량이 부족하고, 너무 많으면 자원 보호가 의미 없어요. 외부 자원의 실제 한도와 P99 latency를 기준으로 잡아요.

3. acquire를 인터럽트 무시

acquire는 InterruptedException을 던져요. shutdown 신호로 받아 처리해야 해요. 무시하고 잡아 던지면 graceful shutdown이 깨져요.

Semaphore vs Lock vs BlockingQueue

도구제어 대상
Lock동시 1개만 (mutex)
Semaphore동시 N개까지 (permit)
BlockingQueue큐 길이를 통한 자연 백프레셔

"동시 N개"가 핵심이면 Semaphore. 그 외 N개의 작업 흐름 자체를 큐로 다루면 BlockingQueue가 더 자연스러워요.

면접에서 자주 나오는 자리

  • "Semaphore와 Lock 차이?": Lock은 동시 1개 (mutex). Semaphore는 동시 N개. Semaphore(1)이 mutex처럼 동작은 하지만 reentrant 보장이 없어서 같은 용도면 ReentrantLock이 정석이에요.
  • "DB 커넥션 풀이 내부에 Semaphore?": 비슷한 발상이지만 HikariCP는 Semaphore를 직접 쓰지 않고 자체 큐와 락을 써요. 개념적으론 같아요.
  • "Rate Limiting과 관계?": Semaphore에 일정 속도로 release를 추가하면 Token Bucket이 돼요. Rate Limiter 라이브러리들은 이 발상 위에 만들어졌어요.
