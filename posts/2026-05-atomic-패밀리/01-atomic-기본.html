Atomic이 뭘 푸나

단일 변수를 여러 스레드가 동시에 갱신하는 자리. 가장 흔한 게 카운터예요. 

private int counter = 0;

public void increment() {
    counter++;   // 안전하지 않음
}

counter++는 한 줄로 보이지만 실제로는 읽기 → 1 더하기 → 쓰기, 세 단계예요. 다른 스레드가 사이에 끼어들면 값이 덮어쓰여요. synchronized로 감싸면 안전한데, 카운터 하나 증가시키려고 락을 잡는 건 과해요.

java.util.concurrent.atomic 패키지가 이 자리를 위한 거예요. CAS(이전 편 참조)를 직접 부르지 않고, 그 위에 만들어진 깔끔한 래퍼를 씁니다. 

private AtomicInteger counter = new AtomicInteger(0);

public void increment() {
    counter.incrementAndGet();   // 안전. 락 없음
}

패밀리 구성

종류는 단순해요. 어떤 타입을 원자적으로 다룰지에 따라 클래스가 갈려요.

클래스다루는 값대표 사용
AtomicIntegerint카운터, 시퀀스 번호
AtomicLonglong큰 값 카운터, 통계
AtomicBooleanboolean한 번만 실행 플래그, 종료 신호
AtomicReference<T>임의 객체 참조구성 객체 통째 교체, 락 없는 자료구조
AtomicIntegerArrayint[]배열 원소를 원자적으로
AtomicReferenceArrayT[]배열 원소(참조)를 원자적으로

실무에서 자주 보는 건 위 네 개예요. 배열 버전은 자료구조 직접 만들 때 가끔 등장합니다.

가장 자주 쓰는 메서드

AtomicInteger를 예로 봐요. 다른 타입도 거의 같은 메서드 시그니처를 가져요. 

AtomicInteger a = new AtomicInteger(0);

// 단순 갱신
a.set(10);                  // 그냥 대입 (volatile write 효과)
int v = a.get();            // 읽기

// 원자 증감
int after  = a.incrementAndGet();   // ++a, 갱신 후 값
int before = a.getAndIncrement();   // a++, 갱신 전 값
a.addAndGet(5);                     // a += 5, 갱신 후 값
a.getAndAdd(5);                     // a += 5, 갱신 전 값

// CAS
boolean ok = a.compareAndSet(10, 20);   // 현재 값이 10이면 20으로 교체

incrementAndGet vs getAndIncrement이 헷갈리면 자바 컨벤션을 기억하면 돼요. "AndGet"이 뒤에 오면 그 동작 후의 값을 반환, "GetAnd~"가 앞에 오면 그 동작 전의 값을 반환이에요.

updateAndGet: 람다로 임의 변환

Atomic이 빛나는 자리 중 하나가 updateAndGet과 accumulateAndGet이에요. 람다로 임의 변환 함수를 줄 수 있어요. 

AtomicInteger a = new AtomicInteger(10);

// 현재 값을 두 배로
a.updateAndGet(x -> x * 2);   // 20

// 현재 값에 인자를 합쳐서 변환 (Math.max 같은)
a.accumulateAndGet(50, Math::max);   // 50

// 음수면 0으로 클램프
a.updateAndGet(x -> Math.max(0, x));

내부 구현은 사실 단순한 CAS 루프예요. "현재 값 읽기 → 함수 적용 → CAS 시도 → 실패하면 처음부터 다시"가 반복돼요. 직접 짤 수 있는 패턴인데 표준 메서드로 깔끔히 정리돼 있어서 안 짜는 게 낫습니다.

주의할 점 하나. 람다 안에서 부작용을 일으키면 안 돼요. CAS가 실패해서 람다가 여러 번 호출될 수 있거든요. 람다는 순수 함수여야 합니다.

AtomicReference: 객체 참조의 원자 교체

AtomicReference는 임의 객체 참조를 원자적으로 다뤄요. 가장 흔한 패턴은 구성 객체 통째 교체예요. 

class Config {
    final String url;
    final int timeout;
    // 불변(immutable) 객체

    Config(String url, int timeout) {
        this.url = url;
        this.timeout = timeout;
    }
}

class ConfigService {
    private final AtomicReference<Config> ref = new AtomicReference<>(initial);

    public Config get() { return ref.get(); }

    public void reload(Config next) {
        ref.set(next);   // 통째 원자 교체
    }
}

설정 객체를 불변으로 만들고 갱신할 때 통째로 새 객체를 만들어 참조만 바꿔치기해요. 이렇게 하면 읽기 쪽은 락이 전혀 필요 없어요. 그냥 ref.get()으로 받아서 쓰면 됩니다. 그 객체는 변하지 않으니까 안전해요.

이 패턴이 락 없는 자료구조의 토대이기도 해요. 자료구조의 어떤 노드를 통째로 바꿀 때 AtomicReference의 CAS로 교체합니다.

AtomicBoolean: "한 번만"의 패턴

AtomicBoolean은 의외로 카운터보다 자주 봐요. "여러 스레드 중 한 명만 실행"하는 자리에 딱 맞아요. 

class ShutdownHook {
    private final AtomicBoolean shutdown = new AtomicBoolean(false);

    public void shutdown() {
        if (shutdown.compareAndSet(false, true)) {
            // 정확히 한 번만 실행
            cleanup();
        }
        // 두 번째 호출부터는 cleanup 안 함
    }
}

compareAndSet(false, true)가 한 번 성공하면 그다음부터는 다 false를 반환해요. 첫 호출자만 정리 작업을 하고 나머지는 그냥 통과하는 패턴이에요. shutdown, startup, initialize 류의 메서드에 자주 등장합니다.

volatile만으로 안 되는 이유

"그냥 volatile int로 쓰면 안 되나" 싶을 수 있어요. volatile은 읽기와 쓰기 각각의 가시성을 보장하지, "읽고 더해서 쓰기" 같은 복합 연산을 원자적으로 만들지 못해요. 

private volatile int counter = 0;

public void increment() {
    counter++;   // 여전히 안전하지 않음 (3단계 사이에 끼어들기 가능)
}

AtomicInteger는 내부에 volatile int value를 가지고 있어요. 가시성은 volatile이 보장하고, 원자성은 CAS가 보장합니다. 둘 다 필요한 자리에 AtomicInteger가 답이에요.

다음 편

여기까지가 가장 많이 쓰이는 4개의 Atomic이에요. 한 가지 약점이 있어요. 경합이 매우 심한 자리(여러 스레드가 같은 카운터를 동시에 두드리는)에서는 CAS 실패가 많아져서 성능이 나빠지거든요. 이걸 풀기 위해 등장한 LongAdder를 다음 편에서 봅니다.
