왜 필요한가요

시나리오 하나. 사용자가 결제 버튼을 눌렀어요. 클라이언트가 서버로 결제 요청을 보냈고, 서버는 결제를 처리했어요. 그런데 응답이 클라이언트에 도착하기 전에 네트워크가 끊어졌어요.

클라이언트는 응답을 못 받으니 timeout 처리. 사용자에게 "오류가 발생했습니다, 다시 시도해주세요" 보여줘요. 사용자가 다시 결제 버튼을 누르면? 같은 결제가 두 번 처리되는 사고가 발생해요.

이런 상황이 일어나는 자리

  • 네트워크 timeout으로 클라이언트가 재시도
  • 로드밸런서가 같은 요청을 다른 인스턴스로 재라우팅
  • 메시지 큐가 최소 한 번 이상 전달 보장으로 같은 메시지 두 번 전달
  • 사용자가 더블 클릭, 새로고침 등으로 같은 요청 반복
  • 모바일 앱이 네트워크 불안정해서 자동 재시도

단순히 사용자 실수로 보기엔 빈도가 너무 높아요. 어떤 분산 시스템에서도 일어나는 자연스러운 현상이에요. 그래서 비멱등 작업(결제, 주문, 메시지 발송 같은)을 안전하게 만드는 메커니즘이 필요해요. 그게 Idempotency Key예요.

아이디어

핵심 아이디어를 한 줄로 표현하면 이래요. 같은 요청에 같은 키를 붙여서, 서버가 키로 중복을 식별하게 하자.

클라이언트가 요청마다 unique한 key를 생성. HTTP 헤더로 함께 전송. 서버는 그 키와 결과를 저장해두고, 같은 키로 다시 들어오면 처리하지 않고 저장된 결과만 반환. 여러 번 요청해도 결과가 동일하니 중복 처리 방지. 

POST /payments
Idempotency-Key: 7c9f6b4d-e1a2-4321-bc3d-1234567890ab
Content-Type: application/json

{
  "amount": 10000,
  "currency": "KRW",
  "method": "card"
}

이 패턴을 Stripe가 표준화해서 결제 API의 사실상 표준이 됐어요. Toss, PayPal, Square 등 거의 모든 결제 PG가 이 방식을 채택.

HTTP 메서드의 멱등성과 다른 거예요

헷갈리지 말아야 할 부분. HTTP 메서드의 멱등성과 Idempotency Key는 다른 개념이에요.

HTTP 메서드 멱등성Idempotency Key
주체 HTTP 메서드 자체 특정 요청의 식별자
적용 RFC가 정의한 동작 서비스 측 메커니즘
예시 GET, PUT, DELETE 멱등 POST를 멱등하게 만듦
관계 POST는 본질적으로 비멱등 POST를 멱등하게 만드는 도구

HTTP 표준상 POST는 비멱등이에요. 같은 POST를 두 번 보내면 같은 자원이 두 개 만들어질 수 있어요. Idempotency Key는 이 본질적 비멱등성을 서비스 레벨에서 풀어주는 도구예요. POST에 키를 붙여 멱등하게 만드는 거죠.

분산 락과의 차이

앞 시리즈에서 본 분산 락과도 다른 개념이에요. 둘 다 동시성을 다루지만 접근이 달라요.

분산 락

  • 여러 클라이언트의 동시 진입을 막음
  • 한 시점에 한 클라이언트만 작업 진행
  • 락 보유 시간 동안 다른 클라이언트는 대기
  • 적합: 여러 단계 작업의 mutex

Idempotency Key

  • 같은 요청의 중복을 식별
  • 중복 요청은 처리하지 않고 저장된 결과 반환
  • 대기 없이 빠르게 응답
  • 적합: 단일 작업의 중복 방지

Idempotency Key가 더 단순하고 효율적이에요. 분산 락의 함정(TTL, GC pause, 시계 drift 등)이 모두 무관. DB의 unique constraint가 race condition을 자연스럽게 막아주거든요. 가능하면 분산 락보다 Idempotency Key를 먼저 검토하는 게 좋아요.

흐름

흐름 정리

  1. 클라이언트가 요청에 unique key 첨부
  2. 서버는 키로 저장소 조회
  3. 처음 보는 키면: 작업 처리, 결과 저장
  4. 같은 키 다시 오면: 처리 안 하고 저장된 결과 반환

단순해 보이지만 동시 요청 처리에서 미묘함이 있어요. 두 요청이 거의 동시에 들어오면 둘 다 "키 없음" 판단하고 둘 다 처리할 수 있거든요. 그래서 atomic insert + unique constraint가 핵심이에요. 다음 편에서.

키 생성 — 누가 만드나요

키는 누가 만들어야 할까요? 클라이언트? 서버? 답은 명확해요. 클라이언트가 만들어야 해요.

서버가 만들면 의미가 없어요. 클라이언트가 같은 요청을 두 번 보낼 때 둘 다 다른 키를 받게 되어 중복 식별 불가. 클라이언트가 "이 사용자 행위는 한 번"이라고 판단해 키를 만들고, 재시도 시 같은 키 사용해야 해요.

클라이언트가 키를 만드는 시점

  • 버튼 누른 시점: 사용자 한 번의 의도가 시작되는 시점
  • 화면 진입 시점: 결제 화면 진입할 때 미리 만들어둠
  • 주문 ID 사용: 주문 생성 시점에 만든 ID를 그대로 idempotency key로

가장 흔한 건 결제 화면 진입 시점에 미리 키를 만들어 form에 hidden으로 넣어두는 패턴. 사용자가 더블 클릭하든 새로고침하든 같은 키가 사용되니 중복이 자연스럽게 막혀요.

키 형식

UUID v4가 가장 흔한 선택. 충돌 가능성이 사실상 0이에요. 

7c9f6b4d-e1a2-4321-bc3d-1234567890ab
b1234567-89ab-cdef-0123-456789abcdef

또는 비즈니스 의미가 있는 ID와 결합. order-12345-attempt-1 같은 형식. 단, 클라이언트가 attempt를 증가시킬 가능성이 있다면 안 좋아요. 같은 요청에 다른 키를 만드는 셈.

저장소

키와 결과를 어디에 저장할지가 중요한 결정이에요.

저장소장점단점
Redis (TTL 24시간) 빠름, TTL 자동, 캐시처럼 사용 Redis 다운 시 보호 깨짐
RDB (idempotency_key 테이블) 강한 일관성, ACID 느림, DB 부하
Redis + RDB 이중화 빠름 + 안전 구현 복잡
NoSQL (DynamoDB 등) scale-out 좋음 운영 비용

금융, 결제처럼 critical한 시스템은 RDB의 unique constraint가 가장 안전. 일반 시스템은 Redis로 충분한 경우가 많아요.

TTL — 얼마나 보관해야 하나요

저장된 키와 결과를 영원히 보관할 수는 없어요. 저장소 부하가 누적되니까요. TTL을 둬야 해요.

TTL 결정 기준

  • 같은 요청이 재시도될 시간 윈도우
  • 비즈니스 정책 (결제 같은 경우 며칠 보관 권장)
  • 저장소 비용

일반적 권장

  • Stripe: 24시간
  • Toss: 5분~24시간 (API에 따라 다름)
  • 일반 API: 1시간 ~ 24시간

24시간이 가장 흔한 선택. 이 정도면 거의 모든 재시도 케이스가 커버되고, 사용자가 하루 이상 후 다시 시도하면 다른 의도로 봐야 한다는 가정.

"같은 요청"의 정의

한 가지 미묘한 부분. 같은 키로 들어왔는데 요청 본문이 다르면 어떻게 해야 할까요? 

첫 요청:
POST /payments
Idempotency-Key: ABC
{ "amount": 10000 }

두 번째 요청:
POST /payments
Idempotency-Key: ABC      ← 같은 키
{ "amount": 50000 }       ← 다른 본문

이건 클라이언트의 잘못이에요. 같은 키는 같은 요청에 써야 해요. 서버는 어떻게 대응할지 정책을 세워야 해요. Stripe의 정책은 명확해요.

  • 같은 키 + 같은 요청: 저장된 결과 반환
  • 같은 키 + 다른 요청: 422 Unprocessable Entity 에러

이 검증을 위해 키와 함께 요청 본문의 hash도 저장해두는 패턴이 일반적이에요.

장점 정리

  • 단순함: 분산 락보다 구현 단순, 함정 적음
  • 빠름: 재시도 시 처리 안 하고 저장된 결과 반환
  • 안전: DB unique constraint가 race를 막음
  • 확장 가능: 외부 저장소(Redis, RDB) 사용으로 분산 환경 대응
  • 표준: Stripe 같은 큰 서비스의 표준 패턴

한계

  • 저장소 의존: Redis/RDB 다운 시 보호 깨짐. fallback 정책 필요
  • 저장 비용: 키와 결과 저장 공간 누적
  • TTL 후엔 보호 없음: 만료 후 같은 키 재사용 시 또 처리됨
  • 여러 단계 작업엔 부적합: 단일 atomic 작업에만 효과적
  • 클라이언트 책임: 키 생성과 재사용을 클라이언트가 정확히 해야 함

면접 단골 질문

Q. Idempotency Key가 왜 필요한가요?

네트워크 timeout이나 클라이언트 재시도로 같은 요청이 두 번 처리되는 걸 막기 위해서예요. 결제, 주문 같은 비멱등 작업에서 중복 처리는 큰 사고로 이어져요. 클라이언트가 unique key를 생성해 요청에 첨부하면, 서버는 그 키로 중복을 식별해 처리 안 하고 저장된 결과를 반환해요. Stripe 같은 결제 PG가 사실상 표준화한 패턴이에요.

Q. HTTP의 PUT은 멱등이라는데 왜 Idempotency Key가 또 필요해요?

HTTP 메서드 멱등성과 Idempotency Key는 다른 개념이에요. PUT은 RFC가 정의한 의미상 멱등이지만 그건 "여러 번 호출해도 결과 상태가 같다"는 약속일 뿐. POST 같은 비멱등 메서드를 멱등하게 만드는 게 Idempotency Key의 목적이에요. 또 PUT도 실제 구현이 멱등하지 않으면 보호가 필요해서, critical 작업에는 PUT/DELETE에도 키를 권장해요.

Q. 키는 누가 만들어야 하나요?

클라이언트가 만들어야 해요. 서버가 만들면 같은 요청을 두 번 보낼 때 둘 다 다른 키를 받게 되어 중복 식별 불가. 클라이언트가 "이 사용자 행위는 한 번"이라고 판단해 키를 만들고, 재시도 시 같은 키 사용해야 해요. UUID v4가 가장 흔하고, 결제 화면 진입 시점에 미리 만들어 form에 hidden으로 넣어두는 패턴이 일반적이에요.

Q. 분산 락과 Idempotency Key 중 무엇을 쓰나요?

한 번의 atomic 작업에는 Idempotency Key가 더 단순하고 안전해요. DB의 unique constraint가 race를 자동으로 막아주고, 분산 락의 함정(TTL, GC pause 등)이 무관해져요. 분산 락은 여러 단계 작업의 mutex가 필요할 때나 외부 시스템과 인터랙션이 있을 때 써요. 단순 중복 방지면 Idempotency Key가 거의 항상 더 좋아요.

한 줄 정리

Idempotency Key는 클라이언트가 unique 키를 요청에 첨부해서 서버가 중복을 식별하게 하는 패턴이에요. 비멱등 작업(결제, 주문)을 안전하게 만드는 표준 도구. 분산 락보다 단순하고 안전해서 가능하면 먼저 검토할 가치가 있어요. Stripe, Toss 같은 결제 PG의 사실상 표준이고, RDB unique constraint 또는 Redis 기반으로 구현해요.

다음 편에서는 실제 구현 패턴과 함정을 봐요. atomic insert, race condition, 동시 요청 처리 같은 디테일이에요.
