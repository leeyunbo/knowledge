synchronized의 wait/notify 다시보기

synchronized 모니터를 잡은 스레드는 같은 모니터의 wait()를 부를 수 있어요. 그러면 락을 풀고 대기 큐에 들어가요. 다른 스레드가 같은 모니터의 notify() 또는 notifyAll()을 호출하면 대기 중이던 스레드 하나(또는 전부)가 깨어나서 다시 락을 잡으려고 합니다. 

synchronized (lock) {
    while (queue.isEmpty()) {
        lock.wait();        // 락 풀고 대기
    }
    return queue.poll();
}

여기서 while로 감싸는 이유는 깨어났을 때 조건이 여전히 만족 안 될 수 있어서예요. notifyAll로 여러 스레드가 깨어나면 그중 한 명만 큐 아이템을 가져가고 나머지는 다시 자야 하니까. if로 쓰면 spurious wakeup(가짜 깨어남)이나 경쟁에서 깨진 가정 때문에 버그가 나요.

그런데 synchronized 모니터에는 대기 큐가 딱 하나예요. 큐가 비어서 기다리는 스레드(consumer)와 큐가 가득 차서 기다리는 스레드(producer)가 같은 대기 큐에 섞여요. notifyAll을 부르면 둘 다 깨어나는데, 한쪽은 깨어나봤자 조건이 안 맞아 다시 자요. 비효율적이에요.

Condition이 푸는 문제

ReentrantLock은 newCondition()으로 같은 락에 여러 개의 독립적인 대기 큐를 만들 수 있어요. 각 Condition이 자기 큐를 가져요. 

ReentrantLock lock = new ReentrantLock();
Condition notEmpty = lock.newCondition();   // 큐가 빌 때 기다리는 자리
Condition notFull  = lock.newCondition();   // 큐가 찰 때 기다리는 자리

consumer는 notEmpty에서 자고, producer는 notFull에서 자요. producer가 아이템을 넣으면 notEmpty.signal()만 부르면 됩니다. consumer만 깨어나요. producer는 안 깨어나서 컨텍스트 스위치 비용을 안 써요.

BlockingQueue를 직접 만들어 보기

Condition이 어떤 모양으로 쓰이는지 가장 잘 보여주는 예가 BlockingQueue 구현이에요. 자바 표준의 ArrayBlockingQueue 내부도 정확히 이 패턴입니다. 

public class SimpleBlockingQueue<T> {
    private final Object[] items;
    private int head, tail, count;
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notEmpty = lock.newCondition();
    private final Condition notFull  = lock.newCondition();

    public SimpleBlockingQueue(int capacity) {
        this.items = new Object[capacity];
    }

    public void put(T x) throws InterruptedException {
        lock.lock();
        try {
            while (count == items.length) {
                notFull.await();        // 큐 가득 참. 빌 때까지 대기
            }
            items[tail] = x;
            tail = (tail + 1) % items.length;
            count++;
            notEmpty.signal();          // 비었다가 차게 됐으니 consumer 깨우기
        } finally {
            lock.unlock();
        }
    }

    @SuppressWarnings("unchecked")
    public T take() throws InterruptedException {
        lock.lock();
        try {
            while (count == 0) {
                notEmpty.await();       // 큐 빔. 찰 때까지 대기
            }
            T x = (T) items[head];
            items[head] = null;
            head = (head + 1) % items.length;
            count--;
            notFull.signal();           // 가득찼다가 빈 자리 생겼으니 producer 깨우기
        } finally {
            lock.unlock();
        }
    }
}

100줄도 안 되는 코드에 일반적인 BlockingQueue의 핵심이 다 있어요. producer가 put하고 notEmpty.signal()을 부르면 consumer만 깨어나요. consumer가 take하고 notFull.signal()을 부르면 producer만 깨어납니다. 양쪽이 서로 헷갈리지 않아요.

await의 의미: wait와 같지만 더 명확

condition.await()는 synchronized의 lock.wait()와 거의 같은 의미예요. 락을 풀고, 자기 Condition의 대기 큐에 들어가고, signal을 받으면 다시 락을 잡고 깨어나요.

하나 다른 게 있어요. wait는 정해진 모니터 객체에 직접 부르는 거라(obj.wait()) 어떤 모니터의 대기 큐에 들어가는지가 호출 형태로 드러나지 않아요. Condition은 notEmpty.await()처럼 변수명에서 의도가 보입니다. "어떤 조건을 기다리는 거냐"가 코드를 읽기만 해도 보여요.

await의 변형도 있어요. wait처럼.

  • await(): 깨어날 때까지 영원히 대기
  • await(time, unit): 시간 안에 못 깨어나면 false 반환
  • awaitNanos(long): 나노초 단위 정밀 타임아웃
  • awaitUninterruptibly(): 인터럽트 무시

signal vs signalAll

signal()은 그 Condition 큐에서 기다리는 스레드 한 명만 깨워요. signalAll()은 전부 깨워요.

Condition을 잘 나눠 쓰면 보통 signal() 하나로 충분해요. 위 BlockingQueue 예에서도 produce 한 번에 consumer 한 명만 깨우면 됩니다. signalAll()까지 갈 필요가 없어요.

반면 synchronized의 notify()는 위험해요. 단일 대기 큐에 다양한 조건의 스레드가 섞여 있으니까, 깨어난 스레드가 자기 조건 안 맞아서 다시 자면 다른 스레드도 못 깨어나는 자리가 생겨요(이걸 missed signal이라고 해요). 그래서 synchronized에선 안전을 위해 notifyAll()이 권장돼요. Condition은 큐가 잘 나뉘어 있으니 signal() 하나가 안전합니다.

주의: 락을 잡은 채로 await

await()를 부르기 전에 락을 반드시 잡고 있어야 해요. 락을 안 잡고 부르면 IllegalMonitorStateException이 터집니다. wait/notify와 똑같은 규칙이에요.

await가 락을 풀고 자고, 깨어나면 다시 락을 잡아요. 사용자 코드 입장에서는 await 호출 전후로 항상 락이 잡혀 있다고 보면 돼요. 그래서 BlockingQueue 코드의 try/finally가 await 위 아래로 다 살아 있는 거예요.
