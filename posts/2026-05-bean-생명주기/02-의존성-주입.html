주입의 세 가지 방식

의존성 주입은 Spring의 핵심 기능이다. 그런데 같은 결과를 만드는 방법이 셋으로 나뉜다. 각자 일어나는 시점이 다르다. 

1. 생성자 주입 (Constructor Injection)
   public class UserService {
       private final UserRepository repo;
       public UserService(UserRepository repo) { this.repo = repo; }
   }

2. 세터 주입 (Setter Injection)
   public class UserService {
       private UserRepository repo;
       @Autowired
       public void setRepo(UserRepository repo) { this.repo = repo; }
   }

3. 필드 주입 (Field Injection)
   public class UserService {
       @Autowired
       private UserRepository repo;
   }

코드만 보면 셋 다 같은 결과 같지만, 실제 동작과 권장 정도가 크게 다르다.

생성자 주입 — 인스턴스화와 동시에

가장 권장되는 방식. 1편에서 잠깐 봤듯, 인스턴스화 단계에서 의존성도 같이 해결된다. 

1. Spring이 UserService 인스턴스화하려 함
2. 생성자 시그니처 봄: UserService(UserRepository)
3. UserRepository 빈을 먼저 찾거나 만듦 (재귀 해결)
4. UserService(repo) 호출
5. 생성 완료. repo 필드는 final이라 한 번 주입 후 변경 불가.

장점

1. 불변성 보장
   - final로 선언 가능
   - 한 번 주입된 의존성은 변경 안 됨
   - 멀티스레드 환경에서 안전

2. 생성 시점에 의존성이 모두 갖춰짐
   - 인스턴스가 만들어진 직후부터 사용 가능
   - "의존성 없는 채로 사용" 같은 함정 X

3. 필수 의존성을 명확히 표현
   - 생성자 시그니처가 곧 의존성 명세서
   - "이 빈은 이것들이 있어야 만들어진다"가 직관적

4. 테스트 용이
   - 단순 new UserService(mockRepo)로 테스트 가능
   - Spring 컨텍스트 없이도 단위 테스트 OK

5. 순환 참조를 컴파일 타임에 강제 차단
   - 순환 참조면 인스턴스화 자체가 불가능

Lombok과의 조합

@Service
@RequiredArgsConstructor   // final 필드 자동으로 생성자 생성
public class UserService {
    private final UserRepository repo;
    private final EventPublisher publisher;
}

→ Lombok이 컴파일 타임에 생성자 추가
→ Spring 4.3+부터 생성자 1개면 @Autowired 생략 가능
→ 코드 간결 + 생성자 주입의 장점 유지

현재 Spring 커뮤니티에서 사실상 표준 패턴. 모든 의존성을 생성자 주입 + Lombok @RequiredArgsConstructor.

세터 주입 — 인스턴스화 후

생성자가 먼저 호출되어 객체가 만들어진 다음, 세터를 호출해서 의존성 주입. 

1. UserService() 빈 생성자 호출 → 객체 생성. repo는 null.
2. Spring이 setRepo(repo) 호출 → 의존성 주입.
3. 빈이 사용 가능 상태가 됨.

특징과 한계

장점:
  - 의존성을 "선택적"으로 표현 가능 (필수 아닌 의존성)
  - 순환 참조를 우회할 수 있음 (다음 섹션에서)
  - 객체가 만들어진 후 의존성을 바꿀 수 있음 (테스트 등)

단점:
  - 객체가 만들어진 직후엔 의존성이 null
  - "의존성이 다 주입됐는지" 코드만 봐선 모름 (선택적이니까)
  - final 사용 불가 → 불변성 보장 X

생성자 주입이 가능한 케이스에선 거의 안 쓴다. 필수 의존성을 세터로 주입하는 건 위험. "주입 안 된 채로 사용"이 가능해진다.

필드 주입 — 가장 간단해 보이지만 가장 안 좋은

@Service
public class UserService {
    @Autowired
    private UserRepository repo;
}

코드는 가장 짧다. 하지만 권장 안 하는 패턴이다. 이유: 

1. 단위 테스트 어려움
   - new UserService()로 만들면 repo가 null
   - Reflection으로 강제 주입하거나 Spring 컨텍스트 띄워야 함
   - 단순 단위 테스트에 무거운 환경 필요

2. final 사용 불가
   - 불변성 보장 X
   - 멀티스레드 안전성 약화

3. 의존성이 코드에서 잘 안 보임
   - 어노테이션 산재
   - 클래스가 무엇에 의존하는지 한눈에 안 들어옴

4. 너무 쉬워서 의존성 폭발을 못 막음
   - 필드만 추가하면 되니 의존성이 5개, 10개로 늘어나기 쉬움
   - 생성자 주입이라면 인자가 너무 많아져 자연스럽게 리팩토링 신호

이런 이유로 IntelliJ나 Spring 공식 문서에서도 필드 주입을 권장하지 않는다. 레거시 코드에선 자주 보이지만 새 코드에선 안 쓰는 게 정답.

주입 방식 비교 한 표

                        생성자        세터          필드
─────────────────────  ──────────    ──────────    ──────────
주입 시점              인스턴스화     인스턴스화 후  인스턴스화 후
final 가능             ✅            ❌            ❌
필수 vs 선택           필수           선택 가능      필수 (보통)
단위 테스트 용이성     ✅            ✅            ❌
순환 참조 처리         차단 (예외)    가능          가능
의존성 명시성          높음           중간           낮음
권장도                 ★★★          ★              ☆

순환 참조 — 가장 흔한 문제

두 빈이 서로를 참조하면 어떻게 될까. 

@Service
public class A {
    public A(B b) { ... }
}

@Service
public class B {
    public B(A a) { ... }
}

→ Spring 동작:
  1. A를 만들려면 B가 필요
  2. B를 만들려면 A가 필요
  3. A를 만들려면 B가 필요 ... (무한 루프)

→ Spring이 감지하고 BeanCurrentlyInCreationException 던짐
→ 애플리케이션이 시작 자체를 못 함

생성자 주입의 큰 장점. 순환 참조를 시작 시점에 강제 발견한다. 런타임에 복잡한 버그로 만나는 게 아니라 빌드/시작 시점에 명확한 에러.

옛날엔 세터 주입으로 우회 가능했다

@Service
public class A {
    private B b;
    @Autowired
    public void setB(B b) { this.b = b; }
}

@Service
public class B {
    private A a;
    @Autowired
    public void setA(A a) { this.a = a; }
}

Spring 동작 (Spring Boot 2.5 이하):
  1. A 인스턴스화 (생성자 호출, 의존성 없음)
  2. B 인스턴스화 (생성자 호출, 의존성 없음)
  3. A.setB(b) 호출
  4. B.setA(a) 호출
  → 둘 다 만들어짐. 동작.

세터 주입은 "객체 생성"과 "의존성 주입"이 분리되니 순환 참조라도 우회할 수 있다. 일단 둘 다 만들고 그 후 의존성을 채우는 식.

Spring Boot 2.6의 변화 — 순환 참조 기본 차단

Spring Boot 2.6 (2021년 11월) 부터 정책이 바뀌었다. 순환 참조가 기본적으로 금지된다. 

Spring Boot 2.6+ 동작:
  세터 주입 순환 참조도 기본 차단
  애플리케이션 시작 실패 + 명확한 에러 메시지

복원하려면:
  application.yml
    spring:
      main:
        allow-circular-references: true

  → 옛 동작으로 돌아감 (세터 주입 순환 참조 허용)

공식 release notes 그대로: "Circular references between beans are now prohibited by default. If your application fails to start due to a BeanCurrentlyInCreationException you are strongly encouraged to update your configuration to break the dependency cycle."

이 변경의 의미: 순환 참조는 코드 냄새다. 우회하지 말고 리팩토링해라. Spring 팀이 명시적으로 권장하는 방향.

순환 참조 진짜 해결법 — 리팩토링

allow-circular-references=true로 우회하는 건 일시적 처방이다. 근본 해결은 리팩토링.

패턴 1: 공통 의존성 추출

Before:
  A → B
  B → A    (순환)

After:
  A → C
  B → C    (공통 의존성 C로 분리)

A와 B가 서로 호출하던 로직을 C로 옮기고
A, B는 각자 C를 의존하게 함.

패턴 2: 이벤트 기반

Before:
  A.doSomething() → B.notify()
  B.process() → A.callback()    (순환)

After:
  A → ApplicationEventPublisher
  A.doSomething() → publish event
  B는 EventListener로 그 이벤트 받음
  B.process() → publish another event
  A는 그 이벤트의 EventListener

A와 B가 직접 의존 안 함. 이벤트로 느슨하게 결합.

패턴 3: @Lazy로 프록시 주입

@Service
public class A {
    private final B b;
    public A(@Lazy B b) { this.b = b; }   // ★ @Lazy
}

→ Spring이 B의 진짜 인스턴스 대신 프록시를 주입
→ A는 일단 만들어짐
→ A.b.someMethod() 첫 호출 시 그제서야 진짜 B 인스턴스화

이게 가능한 이유:
  프록시는 인터페이스 기반이라 생성 시점엔 빈 껍데기
  실제 메서드 호출 시점에 진짜 빈을 찾아 위임

@Lazy는 응급 처치로 쓸 수 있지만 권장은 아니다. 순환 참조 자체를 없애는 게 좋다.

Aware 인터페이스 — 의존성이 아닌 또 다른 주입

의존성 주입과 비슷하지만 약간 다른 메커니즘. Aware 인터페이스를 구현하면 Spring 컨테이너 자체에 대한 정보를 받을 수 있다. 

@Component
public class MyBean implements ApplicationContextAware {
    private ApplicationContext ctx;

    @Override
    public void setApplicationContext(ApplicationContext ctx) {
        this.ctx = ctx;
    }
}

→ 의존성 주입이 끝난 직후, Spring이 setApplicationContext(ctx) 호출
→ 빈이 ApplicationContext에 대한 참조를 갖게 됨

주요 Aware 인터페이스: 

BeanNameAware           — 자기 빈 이름 받음
BeanFactoryAware        — BeanFactory 받음
ApplicationContextAware — ApplicationContext 받음
EnvironmentAware        — Environment(설정) 받음
ResourceLoaderAware     — 리소스 로더 받음

이걸 직접 쓰는 일은 드물다. 보통 Spring이 알아서 주입해주니까. 그러나 가끔 ApplicationContext를 빈에서 직접 다뤄야 할 때 (예: 동적으로 빈을 가져오기) 유용하다.

의존성 주입의 시점 정리

1. BeanDefinition 등록 (1편)
2. 인스턴스화 (1편)
   → 생성자 주입은 여기서 일어남
3. 프로퍼티 주입 (이 편)
   → 세터 / 필드 주입은 여기서 일어남
4. Aware 콜백 (이 편)
5. BeanPostProcessor.before (3편)
6. 초기화 콜백 (3편)
7. BeanPostProcessor.after (3편)
8. 사용
9. 소멸 (4편)

한 줄 정리

생성자 주입: 인스턴스화와 동시에. 권장. final 가능. 순환 참조 차단.
세터 주입:  인스턴스화 후. 선택적 의존성. 순환 참조 우회 가능 (옛 Spring).
필드 주입:  인스턴스화 후. 코드 짧지만 권장 안 함.

Spring Boot 2.6+: 순환 참조 기본 차단.
근본 해결은 우회가 아닌 리팩토링.

다음 편에서는 의존성 주입과 Aware 콜백 직후 일어나는 일을 본다. BeanPostProcessor의 before/after, @PostConstruct, InitializingBean.afterPropertiesSet, 그리고 AOP 프록시가 정확히 어디서 만들어지는지.
