Bean이 만들어지기까지 — 등록부터 인스턴스화

@Component 어노테이션 한 줄 뒤에 일어나는 일. BeanDefinition이 ApplicationContext에 등록되고 인스턴스가 만들어지는 흐름.

Bean 하나가 만들어지기까지 거치는 단계

Spring 애플리케이션에서 @Component 또는 @Bean 한 줄을 적었을 때 그 객체가 사용 가능해지기까지 거치는 단계는 의외로 많다. 전체 흐름을 먼저 그려보자. 

1. BeanDefinition 등록
   - @Component, @Bean 등을 스캔해서 메타데이터로 등록

2. 인스턴스화 (Instantiation)
   - 생성자를 호출해 객체 생성

3. 의존성 주입 (Population)
   - 프로퍼티에 다른 빈 주입

4. Aware 인터페이스 콜백
   - BeanNameAware, ApplicationContextAware 등

5. BeanPostProcessor.postProcessBeforeInitialization
   - 초기화 전 후처리 (AOP 프록시도 여기서)

6. 초기화 콜백
   - @PostConstruct → InitializingBean.afterPropertiesSet → @Bean(initMethod)

7. BeanPostProcessor.postProcessAfterInitialization
   - 초기화 후 후처리

8. 사용 (Bean 준비 완료)

9. 소멸 (컨테이너 종료 시)
   - @PreDestroy → DisposableBean.destroy → @Bean(destroyMethod)

이 9단계를 한 번에 이해하려고 하면 머리가 복잡해진다. 이번 편은 1~2단계, 즉 BeanDefinition 등록과 인스턴스화까지를 본다. 나머지는 다음 편들에서 차례로.

BeanDefinition — Bean의 설계도

Spring이 객체를 직접 만드는 게 아니다. 먼저 그 객체를 어떻게 만들어야 하는지에 대한 메타데이터를 등록한다. 이게 BeanDefinition이다. 

BeanDefinition이 들고 있는 정보:
  - className           — 어떤 클래스의 인스턴스인가
  - scope               — singleton / prototype / request 등
  - lazyInit            — 즉시 생성 vs 지연 생성
  - dependsOn           — 다른 어떤 빈에 의존하는가
  - constructorArgs     — 생성자에 넘길 인자
  - propertyValues      — 세터로 주입할 값
  - factoryMethod       — @Bean 메서드 정보 등
  - initMethodName      — 초기화 메서드
  - destroyMethodName   — 소멸 메서드
  ...

BeanDefinition은 빈의 설계도다. 이 설계도가 BeanFactory에 등록되고, 나중에 실제 인스턴스를 만들 때 참조된다. 이 분리가 중요한 이유: 등록과 생성 시점이 다르다. 모든 BeanDefinition이 먼저 다 등록되고, 그 후에 필요한 것부터 인스턴스화된다.

BeanDefinition은 어디서 만들어지나

크게 세 갈래로 만들어진다.

1. 컴포넌트 스캔

@Component
public class UserService { ... }

@SpringBootApplication  // = @ComponentScan + 기타
public class App { ... }

→ Spring이 패키지 트리를 스캔하면서
   @Component, @Service, @Repository, @Controller가 붙은 클래스를 찾음
→ 각 클래스마다 BeanDefinition 생성하여 등록

2. @Configuration 클래스의 @Bean 메서드

@Configuration
public class AppConfig {
    @Bean
    public DataSource dataSource() {
        return new HikariDataSource();
    }
}

→ AppConfig 자체가 한 빈으로 등록 (BeanDefinition 1개)
→ 그 안의 @Bean 메서드도 별도 BeanDefinition으로 등록
   factoryMethod=dataSource로 표시
→ 나중에 dataSource 빈 만들 때 AppConfig의 dataSource() 메서드 호출

3. XML 설정 (옛 방식)

<bean id="userService" class="com.example.UserService" />

→ XML 파서가 읽어 BeanDefinition 생성

요즘은 거의 안 쓰지만 레거시 시스템엔 남아있다.

등록 직후 — 아직 인스턴스는 없음

여기서 중요한 점. 모든 BeanDefinition이 등록된 시점엔 아직 어떤 객체도 만들어지지 않았다. 설계도만 모인 상태. 이 단계에서 BeanFactoryPostProcessor가 동작해서 BeanDefinition을 수정할 수 있다. 

@Component
public class CustomBeanFactoryPostProcessor
        implements BeanFactoryPostProcessor {
    @Override
    public void postProcessBeanFactory(ConfigurableListableBeanFactory factory) {
        BeanDefinition def = factory.getBeanDefinition("userService");
        // BeanDefinition 자체를 수정
        // 예: 다른 클래스로 교체, scope 변경, 프로퍼티 추가 등
    }
}

이 시점은 인스턴스가 만들어지기 전이라 "빈을 어떻게 만들지" 자체를 바꿀 수 있다. BeanPostProcessor와 이름이 비슷하지만 동작 시점이 완전히 다르다. BeanFactoryPostProcessor는 인스턴스 만들기 전, BeanPostProcessor는 인스턴스 만든 후.

인스턴스화 (Instantiation)

이제 진짜로 객체가 만들어진다. Spring이 getBean() 호출을 받으면 (또는 즉시 초기화 빈이라면 컨테이너 시작 시점에) BeanDefinition을 보고 인스턴스를 생성한다.

1. 생성자 호출

가장 단순한 케이스:

@Component
public class UserService {
    public UserService() { ... }
}

Spring 동작:
  1. UserService.class.getDeclaredConstructor().newInstance()
  2. 객체 생성됨. 단, 의존성은 아직 주입 안 됨

2. 생성자 주입이 있다면

@Component
public class UserService {
    private final UserRepository repo;

    public UserService(UserRepository repo) {
        this.repo = repo;
    }
}

Spring 동작:
  1. UserRepository 빈을 먼저 찾거나 만든다 (재귀)
  2. UserService 생성자 호출 시 그 인스턴스를 인자로 전달
  3. UserService 생성됨. repo는 이미 주입된 상태.

생성자 주입은 인스턴스화 단계에서 의존성도 같이 해결된다. 이게 다음 편(의존성 주입)에서 다시 본다. 다른 주입 방식과 차이가 있음.

3. @Bean 메서드 호출

@Configuration
public class AppConfig {
    @Bean
    public DataSource dataSource() {
        return DataSourceBuilder.create().url(...).build();
    }
}

Spring 동작:
  1. AppConfig 빈 자체를 먼저 만듦 (생성자 호출)
  2. dataSource() 메서드 호출
  3. 반환된 객체를 dataSource 빈으로 등록

@Bean 메서드 안의 코드는 우리가 직접 작성한 객체 생성 로직. Spring은 그 결과만 빈으로 받아서 관리한다.

FactoryBean — 또 다른 생성 방식

가끔 Spring이 직접 객체를 만드는 게 아니라 "공장 객체"를 거쳐 만드는 경우도 있다. 

public class MyFactoryBean implements FactoryBean<Database> {
    @Override
    public Database getObject() {
        // 복잡한 생성 로직
        return new Database(...);
    }
    @Override
    public Class<?> getObjectType() { return Database.class; }
}

@Component
public class MyFactoryBean { ... }

→ Spring이 @Component를 보고 MyFactoryBean을 빈으로 등록
→ 그러나 다른 곳에서 @Autowired Database로 주입받으면
   MyFactoryBean.getObject()를 호출해서 진짜 Database를 받아 줌

FactoryBean은 "복잡한 생성 로직이 필요한 빈"을 만들 때 쓴다. 요즘은 @Bean 메서드로 거의 대체되지만 Spring 내부의 일부 빈은 여전히 FactoryBean으로 만들어진다.

인스턴스화 직후 — 아직 사용 가능 아님

생성자가 호출되어 객체가 메모리에 만들어졌다고 빈이 다 준비된 건 아니다. 이 시점에는: 

아직 안 끝난 것:
  - 세터/필드 의존성 주입
  - Aware 인터페이스 콜백
  - BeanPostProcessor.postProcessBeforeInitialization
  - @PostConstruct / afterPropertiesSet / initMethod
  - postProcessAfterInitialization

이 단계들을 모두 거쳐야 빈이 "준비 완료" 상태가 된다.

그래서 생성자 안에서 다른 빈을 사용하려고 하면 위험하다. 생성자 시점엔 같은 빈의 의존성도 아직 주입 안 됐을 수 있다. 초기화 로직은 생성자가 아니라 @PostConstruct에 두는 게 정석. 이건 3편에서 자세히.

Singleton vs Prototype의 차이가 시작되는 곳

BeanDefinition의 scope 속성에 따라 인스턴스화 시점과 횟수가 달라진다. 

@Component  // 기본값 singleton
public class UserService { ... }

@Component
@Scope("prototype")
public class CommandHandler { ... }

Singleton (기본)

- 컨테이너 시작 시점에 한 번 인스턴스화 (lazyInit이 false면)
- 이후 모든 요청에 같은 인스턴스 반환
- 컨테이너가 그 인스턴스를 자체 캐시에 들고 있음
- 컨테이너 종료 시 한 번 소멸

Prototype

- 매 getBean() 호출마다 새 인스턴스
- 컨테이너가 인스턴스를 들고 있지 않음 (만들어 주고 손 뗌)
- 의존성 주입과 초기화 콜백은 매번 일어남
- 소멸 시점은 Spring이 관리 안 함 (사용자 책임)

Prototype은 매번 새 객체라 메모리 부담이 있고 소멸도 직접 관리해야 해서 거의 안 쓴다. 정말 필요한 케이스(예: stateful command 객체)에만 한정.

Lazy Initialization

Singleton이라도 즉시 안 만들고 처음 필요할 때 만들 수 있다. 

@Component
@Lazy
public class HeavyService { ... }

→ 컨테이너 시작 시 인스턴스화 안 함
→ 처음 누군가 이 빈을 요청할 때 그제서야 인스턴스화
→ 시작 시간 단축. 단, 그 빈을 처음 쓸 때 약간 느림.

Spring Boot에서는 spring.main.lazy-initialization=true로 전체 빈을 lazy로 바꿀 수도 있다. 시작 시간이 중요한 환경(테스트, 개발)에 유용.

한 줄 정리

1. @Component / @Bean 어노테이션을 보고 BeanDefinition을 등록 (메타데이터)
2. BeanFactoryPostProcessor가 BeanDefinition을 수정할 기회를 가짐
3. 그 다음에 인스턴스화 (생성자 호출)
4. 인스턴스화 직후엔 아직 빈이 사용 가능하지 않음 — 의존성 주입과 초기화 콜백이 남음

설계도(BeanDefinition)와 실제 객체(인스턴스)가 분리되어 있다는 게 핵심.
이 분리가 Spring의 유연성의 출발점.

다음 편에서는 인스턴스화 직후 일어나는 의존성 주입을 본다. 생성자 주입, 세터 주입, 필드 주입의 차이. 그리고 그 시점에 발생할 수 있는 순환 참조 문제와 Spring Boot 2.6에서 바뀐 정책.
