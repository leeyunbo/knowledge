분산 락의 필요와 함정

여러 서버가 같은 자원을 다툴 때 필요한 도구. 단일 서버 락과 뭐가 다르고, 어떤 함정이 있는지부터 봐요.

왜 분산 락이 필요한가요

단일 서버에서는 synchronized나 ReentrantLock으로 동시성을 처리할 수 있어요. 한 JVM 안의 여러 스레드를 조정하는 건 자바 동시성 도구로 충분.

그런데 서버가 여러 대로 scale-out되면 사정이 달라져요. 한 서버의 synchronized는 다른 서버 스레드를 막을 수 없어요. 여러 서버의 인스턴스가 동시에 같은 자원을 다투는 상황이 생기는데, JVM 락은 이 상황을 풀지 못해요.

흔한 시나리오

  • 여러 서버 인스턴스가 같은 사용자의 결제를 처리하려 할 때 (이중 결제 방지)
  • 여러 인스턴스가 같은 작업을 스케줄러로 실행하려 할 때 (한 번만 실행 보장)
  • 한정 수량 상품 재고 관리 (초과 판매 방지)
  • 리더 선출 — 여러 인스턴스 중 하나만 특정 작업 수행
  • 같은 외부 자원을 여러 서비스가 동시 수정하려 할 때

이런 자리들이 모두 여러 서버 인스턴스가 보는 외부 락 시스템이 필요해요. 그게 분산 락의 자리예요.

구현 후보들

분산 락을 만드는 방법은 여러 가지예요. 대표적인 후보들을 봐볼게요.

도구특징난이도
DB 기반 락 SELECT FOR UPDATE, UNIQUE 인덱스 활용 쉬움
Redis SETNX, Redisson 라이브러리 중간
ZooKeeper ephemeral znode, Curator 라이브러리 중간
etcd Raft 기반, 강한 일관성 중간

DB 기반 락 — 가장 단순

이미 사용 중인 RDB가 있다면 가장 단순한 옵션이에요. 

SELECT * FROM resource WHERE id = ? FOR UPDATE;
-- 트랜잭션 끝날 때까지 다른 세션은 대기

또는 UNIQUE 인덱스를 활용해 lock row를 INSERT 하는 방식. 

INSERT INTO distributed_lock (key, holder, expires_at)
VALUES ('order-lock-123', 'instance-A', NOW() + INTERVAL 30 SECOND);
-- 같은 key로 동시 INSERT는 한 트랜잭션만 성공

장점과 한계

  • 장점: 추가 인프라 불필요, 트랜잭션 안전성, ACID 보장
  • 단점: DB 부하 증가, 락 대기로 connection 점유, latency 큼
  • 적합: 트래픽 적은 시스템, 결제처럼 정확성이 critical한 자리

Redis — 가장 흔한 선택

높은 throughput과 낮은 latency가 필요할 때 가장 많이 쓰여요. SETNX(SET if Not Exists) 명령어가 핵심 도구예요. 

SET lock-key value NX EX 30
# NX: 키가 없을 때만 설정
# EX 30: 30초 후 자동 삭제 (TTL)

한 클라이언트만 SETNX에 성공하고 나머지는 실패. 성공한 클라이언트가 락 보유자. 단순하고 빠르지만 함정이 있어요. 다음 편에서 자세히.

ZooKeeper / etcd — 강한 일관성

분산 합의 알고리즘 기반이라 가장 안전하지만 운영 복잡도가 큼. ZooKeeper는 Zab, etcd는 Raft 알고리즘 사용. 둘 다 majority 노드의 합의로 모든 변경이 일관성 보장.

  • 장점: 가장 안전, ephemeral node로 장애 자동 정리
  • 단점: 운영 복잡도, 추가 인프라 비용, throughput 제한
  • 적합: 정확성이 매우 critical한 자리, 리더 선출, 구성 관리

분산 락의 본질적 어려움

단일 노드 락(synchronized)과 분산 락의 가장 큰 차이는 실패 가능성이에요. 단일 노드에서는 락 자체가 실패할 일이 거의 없어요. JVM 안의 자료구조 한 번 갱신이니까요.

분산 락은 다양한 실패가 가능해요.

  • 네트워크 지연으로 락 해제가 늦게 도착
  • 락 보유 클라이언트가 GC pause로 멈춤
  • 락 보유 클라이언트가 갑자기 죽음
  • 락 시스템(Redis 등) 자체가 장애
  • 네트워크 분단으로 일부 노드가 격리

이 모든 가능성에 대비해야 분산 락이 안전해요. 단순히 SETNX 한 번 하면 끝나는 게 아니에요. 그래서 분산 락 구현은 의외로 깊은 주제고, "Redlock 논쟁" 같은 학계 논쟁까지 있어요.

자주 빠지는 함정 5가지

함정 1 — TTL 없는 락

가장 흔한 실수. SETNX로 락을 잡고 finally에서 DEL로 해제. 그런데 클라이언트가 갑자기 죽으면? DEL이 호출 안 되고, 락이 영영 풀리지 않아요. 다른 모든 클라이언트가 영원히 대기.

반드시 TTL을 설정해야 해요. 클라이언트가 죽어도 일정 시간 후 자동 해제. 

SET lock-key value NX EX 30   # 30초 TTL

함정 2 — TTL이 너무 짧음

반대로 TTL이 작업 시간보다 짧으면 작업 도중에 락이 풀려요. 그러면 다른 클라이언트가 락을 잡고 같은 작업을 시작. 두 클라이언트가 동시에 같은 자원을 수정하는 race condition 발생.

작업 예상 시간보다 충분히 길게 TTL 설정. 또는 작업 진행 중 TTL을 연장하는 패턴(watchdog) 사용. Redisson 같은 라이브러리가 자동으로 처리해줘요.

함정 3 — 다른 클라이언트의 락 해제

A가 락을 잡고 작업 중인데 TTL이 지나 자동 해제됐어요. B가 락을 잡고 자기 작업 시작. 그 사이 A가 작업을 끝내고 DEL 호출. B의 락이 풀려버려요.

해결은 락 값에 unique ID를 두는 거예요. SETNX 시 random UUID를 값으로 저장. DEL 전에 값이 자기 UUID와 일치하는지 확인. 일치할 때만 DEL. 

# Lua 스크립트로 atomic 처리
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end

GET 후 DEL을 따로 하면 둘 사이에 다른 클라이언트가 락을 잡을 수 있어 안전 못 함. 반드시 Lua 스크립트로 atomic하게.

함정 4 — GC pause로 인한 race

이게 가장 미묘한 함정이에요. 자바의 stop-the-world GC pause가 길어질 수 있어요. 30초 GC도 가능.

시나리오를 그려볼게요.

  1. A가 락 획득 (TTL 30초)
  2. A가 작업 시작
  3. A에서 30초 GC pause 발생
  4. 그 사이 TTL 만료, 락 자동 해제
  5. B가 락 획득, 작업 시작
  6. A의 GC pause 끝남. A는 자기가 락을 갖고 있다고 생각하고 작업 계속
  7. A와 B가 동시에 같은 자원 수정 → race condition

A 입장에서는 자기 락이 풀린 줄 모르고 작업을 마무리해요. 이걸 막으려면 fencing token 같은 추가 안전장치가 필요해요. 다음 편에서.

함정 5 — Redis Master 장애 + Failover

Redis가 master + replica 구성일 때. master에 락을 SET. master가 곧바로 죽음. Redis는 비동기 복제라 replica에 아직 그 락이 전파되지 않은 상태. Failover로 replica가 새 master가 되면 락이 사라져요. A는 자기가 락 가졌다고 생각하지만 새 master에는 락 없음. B가 SETNX 성공해서 락 획득. A와 B가 동시에 락 보유 → race condition.

이 함정을 풀려고 등장한 게 Redlock 알고리즘이에요. 단, 그것도 논쟁이 있어요. 마지막 편에서.

안전한 분산 락의 요건

위 함정들을 풀려면 분산 락이 다음 성질을 모두 갖춰야 해요.

  • Mutual Exclusion: 한 시점에 한 클라이언트만 락 보유
  • Deadlock-Free: TTL 등으로 무한 대기 방지
  • Fault-Tolerance: 락 시스템 일부 노드 장애에도 동작
  • Safety: 어떤 경우에도 두 클라이언트가 동시에 락을 가지면 안 됨
  • Liveness: 결국에는 누군가 락을 획득해 작업이 진행됨

이 다섯 성질을 모두 만족시키는 게 어려워요. 특히 Safety와 Liveness는 분산 시스템에서 본질적 트레이드오프. 그래서 단순한 SETNX만으로 안전한 분산 락을 만드는 건 불가능에 가깝고, 추가 메커니즘이 필요해요.

Idempotency가 더 좋은 답일 수도 있어요

분산 락을 쓰기 전에 한 번 더 생각해볼 가치가 있는 게 있어요. 많은 경우 분산 락 대신 idempotent한 작업으로 만드는 것이 더 안전하고 단순해요.

예시 — 결제 처리

분산 락 접근:

  1. 주문 ID로 락 획득
  2. 이 주문이 이미 결제됐는지 확인
  3. 결제 처리
  4. 락 해제

Idempotency 접근:

  1. idempotency key를 unique 인덱스로 INSERT (이미 있으면 실패)
  2. INSERT 성공한 클라이언트만 결제 처리

두 번째 접근이 더 단순하고 안전해요. DB의 unique 제약이 race condition을 자동으로 막아줘요. 분산 락의 함정들도 모두 무관해져요.

분산 락이 정말 필요한 경우는 여러 단계 작업이 묶여야 하거나 외부 시스템과 인터랙션이 있을 때예요. 단순 한 번의 atomic 작업이면 idempotency가 더 좋아요.

분산 락 vs 다른 패턴

패턴적합 시나리오
분산 락 여러 단계 작업의 mutex, 외부 시스템과 인터랙션
Idempotency Key 한 번의 atomic 작업, race condition 방지
Optimistic Lock 경합 적은 자원, version 기반 충돌 감지
SAGA 긴 시간 분산 트랜잭션
Event Sourcing 상태 자체가 이벤트의 누적

분산 락이 만능이 아니에요. 각 패턴의 적합한 자리가 따로 있어요. 새 시스템 설계 시 분산 락 외 다른 패턴이 더 좋지 않은지 먼저 검토하는 게 좋아요.

면접 단골 질문

Q. 분산 락이 왜 필요한가요?

서버가 여러 대로 scale-out된 환경에서는 한 JVM의 synchronized로 다른 서버 인스턴스를 막을 수 없어요. 여러 서버가 같은 자원을 다투는 상황(이중 결제, 한정 재고, 스케줄러 중복 실행 등)을 풀려면 외부에 공유 락 시스템이 필요해요. 그게 분산 락의 자리예요.

Q. 분산 락 구현 시 가장 흔한 함정은요?

TTL 관련 함정이 가장 흔해요. TTL 없이 락 잡으면 클라이언트 장애 시 락이 영영 안 풀려요. TTL이 작업 시간보다 짧으면 작업 도중 락이 풀려서 race condition. 또 다른 함정은 락 값에 unique ID 안 두면 A의 늦은 DEL이 B의 락을 풀어버리는 문제예요. 모두 atomic Lua 스크립트와 unique token으로 풀어요.

Q. GC pause로 인한 race는 어떻게 풀어요?

단순히 락 보유자만 검증하는 건 부족해요. fencing token이라는 추가 메커니즘이 필요해요. 락 획득 시 monotonically increasing token을 받아서 자원 수정 시 함께 보내요. 자원 서버는 이전에 받은 token보다 큰 token만 수락. 옛 token으로 오는 요청은 거부. 이래야 GC pause 사이 두 클라이언트가 동시에 락을 가지는 상황에서도 안전해요. 다음 편에서 자세히.

Q. 분산 락 대신 다른 패턴이 좋은 경우?

한 번의 atomic 작업이라면 Idempotency Key가 더 좋아요. DB의 unique 제약이 race condition을 자동으로 막아줘요. 분산 락의 모든 함정이 무관해지고 구현도 단순해요. 분산 락은 여러 단계 작업의 mutex가 필요하거나 외부 시스템 인터랙션이 있을 때 정말 필요한 경우에만 써요.

한 줄 정리

분산 락은 여러 서버 인스턴스가 같은 자원을 다투는 상황을 푸는 도구예요. DB, Redis, ZooKeeper, etcd 등으로 구현할 수 있어요. 단, TTL 설정, unique token, atomic 해제, GC pause 대비 같은 함정들이 있어 단순한 구현은 위험해요. 많은 경우 Idempotency Key 같은 더 단순한 패턴이 더 안전한 답이 될 수 있어요.
