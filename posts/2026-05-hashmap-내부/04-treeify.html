왜 Java 8에 추가되었나

Java 7까지: 충돌 처리는 링크드 리스트만
  → 같은 버킷에 n개 충돌하면 get/put이 O(n)

문제:
  1. 잘 만든 hashCode면 거의 안 발생
  2. 버그 있는 hashCode (모두 같은 값 반환): 모든 엔트리가 한 버킷
  3. 악의적 입력 (HashDoS 공격): 의도적으로 같은 hash 만든 키들

Java 8 추가:
  한 버킷의 길이가 임계값 넘으면 Red-Black Tree로 전환
  최악 O(log n)으로 떨어뜨림
  → HashDoS 공격 영향 완화
  → 버그 hashCode가 있어도 견딜 수 있음
  → "방어적 자료구조"로 진화

Treeify의 두 임계값

static final int TREEIFY_THRESHOLD = 8;        // 한 버킷 8개 → 트리화
static final int UNTREEIFY_THRESHOLD = 6;      // 트리에서 6개 이하 → 리스트 복귀
static final int MIN_TREEIFY_CAPACITY = 64;    // 테이블 자체가 64 미만이면 트리화 대신 resize

왜 8과 6 (이력 차)

오실레이션(oscillation) 방지:
  만약 임계값이 같다면 (예: 둘 다 7):
    7개 → 트리화
    1개 빼면 6개 → 리스트로 복귀
    1개 추가 → 7개 → 다시 트리화
    ...
    경계에서 변환이 반복 발생 → 비용 폭증

  히스테리시스(hysteresis) 적용:
    들어갈 때 8, 나올 때 6 → 경계에서 안정성

왜 8이라는 숫자:
  좋은 hashCode면 한 버킷에 8개 이상 충돌할 확률은 매우 낮음 (통계상 0.00000006)
  실제로 트리화는 거의 일어나지 않음
  일어났다면 진짜 문제 상황 (버그 hashCode 또는 악의적 입력)

→ 트리화는 "정상 상황의 최적화"가 아니라 "비정상 상황의 안전망"

왜 MIN_TREEIFY_CAPACITY = 64

한 버킷에 8개가 충돌했다 = 두 가지 가능성:
  ① 테이블이 너무 작아 충돌이 많음 → resize하면 분산됨
  ② 테이블은 충분히 크지만 진짜로 hash가 같은 키들 → 트리화가 답

판단:
  table.length < 64 이면 ① → resize로 해결 시도
  table.length >= 64 이면 ② → 트리화

→ 작은 테이블이라 단순히 충돌이 많은 거라면 resize가 더 좋은 해법
→ 64 이상에서도 충돌 8 이상이면 hash 자체의 문제로 판단 → 트리화

TreeNode 구조 — Red-Black Tree

static final class TreeNode<K,V> extends LinkedHashMap.Entry<K,V> {
    TreeNode<K,V> parent;
    TreeNode<K,V> left;
    TreeNode<K,V> right;
    TreeNode<K,V> prev;     // 트리화 전 리스트 순서 보존
    boolean red;            // RB-Tree의 색
    ...
}

TreeNode는 일반 Node를 상속하며 트리 포인터(parent/left/right)와 RB-Tree 색을 추가. prev는 untreeify 시 리스트로 빠르게 복귀하기 위한 양방향 링크.

왜 Red-Black Tree인가

요구사항:
  - 최악 O(log n) 보장
  - 삽입/삭제 비용도 합리적
  - 균형 유지 비용이 너무 크면 안 됨

후보들:
  AVL Tree: 균형 더 빡빡 → 검색 약간 빠름, 삽입/삭제 회전 많음
  Red-Black Tree: 균형 약간 느슨 → 검색 살짝 느림, 삽입/삭제 회전 적음
  Splay Tree: 평균 O(log n)이지만 최악 O(n) → 안전망 목적에 부적합

선택: Red-Black Tree
  HashMap의 트리 사용은 "비정상 상황의 안전망"
  → 자주 일어나지 않음
  → 일어났을 때 삽입/삭제도 자주 발생
  → 회전 비용이 적은 RB-Tree가 적합

같은 이유로 TreeMap, java.util.TreeSet도 Red-Black Tree 사용

트리에서 비교 기준 — hash + comparable + 동등성

BST는 "어느 쪽이 더 큰가"를 정해야 함
  HashMap의 키는 임의의 객체 → 비교 기준이 없을 수 있음

해결 단계:
  1. 두 노드의 hash 값으로 먼저 비교
     - 다르면 hash 작은 쪽이 왼쪽
     - 같으면 다음 단계

  2. key가 Comparable이면 compareTo로 비교
     - 다르면 그 결과로 좌/우 결정
     - 같으면(0) 다음 단계

  3. tieBreakOrder — 객체 식별 해시(System.identityHashCode)로 비교
     - 일관된 순서를 강제로 만들어 트리 구조 유지

→ 어떤 객체든 트리 안에 일관된 위치를 가질 수 있도록 보장

Untreeify — 트리에서 리스트로 복귀

언제: 트리의 노드 수가 6 이하로 떨어졌을 때 (UNTREEIFY_THRESHOLD)
  - remove 후
  - resize 시 그 버킷이 두 그룹으로 분할되면서 양쪽 다 작아지는 경우

방법:
  TreeNode의 prev 포인터를 따라가며 일반 Node로 변환
  table[index]에 다시 link 형태로 채우기

목적:
  트리 구조 유지 비용보다 짧은 리스트가 더 효율적
  6개 정도면 순회가 트리 탐색만큼 빠름

실측으로 보는 트리화의 영향

일반 케이스 (정상 hashCode, capacity 16, 100 entries):
  load factor 0.75 도달 전에 resize → capacity 두 배씩 확장
  최종적으로 capacity ~256
  체인 길이 평균 0~1개 → get/put 모두 O(1)
  트리화 거의 일어나지 않음

악성 케이스 (모두 hash=42, 100 entries):
  모두 한 버킷에 들어감
  capacity 64 도달 후 8번째 entry부터 트리화
  100 entries 다 들어가면 한 버킷에 RB-Tree 100개 노드
  get/put: O(log 100) ≈ 7번 비교

  Java 7 (트리 없음) 비교:
    같은 상황에서 get/put: O(100) = 100번 비교
    14배 차이

HashDoS와 트리화의 관계

HashDoS 공격:
  공격자가 많은 양의 키를 보내며 모두 같은 hash가 되도록 조작
  서버의 HashMap에 강제 충돌 → 모든 작업 O(n) → CPU 폭증

Java 8 트리화의 효과:
  같은 상황에서 작업 O(log n)으로 떨어짐
  CPU 부담 크게 완화 (단, 0이 되지는 않음)

추가 방어:
  Spring의 일부 자료구조: 키 종류 화이트리스트
  Tomcat: 폼 파라미터 개수 제한 (maxParameterCount)
  Servlet 4: 같은 종류 공격 일반 대응

  → 트리화는 application 측 안전망, 외곽 방어와 함께 가야 완전

면접 단골 질문

Q. Java 8에서 HashMap이 어떻게 바뀌었나?

한 버킷의 충돌이 8개를 넘으면 링크드 리스트가 Red-Black Tree로 변환되도록 추가됨. 최악 시간 복잡도가 O(n)에서 O(log n)으로 개선. HashDoS 공격에 대한 방어 효과.

Q. 트리화 임계값이 8과 6으로 다른 이유?

오실레이션 방지(히스테리시스). 같은 임계값이면 경계에서 트리↔리스트 변환이 반복되면서 비용이 폭증. 들어갈 때 8, 나올 때 6으로 차이를 두면 안정성이 확보됨.

Q. 왜 AVL Tree가 아니라 Red-Black Tree인가?

HashMap의 트리는 "비정상 상황의 안전망"이라 삽입/삭제도 자주 일어남. AVL은 검색에 더 빠르지만 균형 유지 비용이 큼. RB-Tree는 회전이 적어 삽입/삭제가 가벼움. TreeMap, TreeSet도 같은 이유로 RB-Tree 채택.

Q. capacity가 64 미만일 때 트리화 대신 resize하는 이유?

한 버킷에 8개가 몰린 게 테이블이 작아서일 수도 있고 진짜 hash가 같아서일 수도 있음. 작은 테이블이면 resize로 분산이 더 좋은 해법. 64 이상에서도 충돌 8개라면 hash 자체 문제로 판단해 트리화.

한 줄 정리

Treeify (Java 8+):
  한 버킷 충돌 8개 + capacity 64 이상 → Red-Black Tree로 전환
  6 이하로 떨어지면 → 리스트로 복귀 (히스테리시스)

목적:
  악성 hashCode / HashDoS 공격에 대한 안전망
  최악 O(n) → O(log n)

선택:
  RB-Tree 채택 — 균형이 빡빡하지 않아 삽입/삭제 가벼움
