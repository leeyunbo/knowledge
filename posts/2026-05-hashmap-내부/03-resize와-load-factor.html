Resize와 Load Factor

데이터가 늘면 테이블이 가득 차고 충돌이 폭증한다. HashMap이 자동으로 테이블을 두 배로 늘리는 메커니즘과 그 비용.

Load Factor의 의미

load factor: 채워진 정도를 나타내는 비율
  load factor = size / capacity

  size: 현재 저장된 엔트리 수
  capacity: table.length

기본값: 0.75
  capacity 16 × 0.75 = 12 → 12개 차면 resize
  capacity 32 × 0.75 = 24 → 24개 차면 resize
  ...

threshold: 다음 resize 임계값
  threshold = capacity × loadFactor
  size > threshold이면 resize 호출

핵심: HashMap은 결코 가득 차지 않는다. 75%만 채워져도 "충돌 위험이 커진다"고 판단해서 미리 두 배로 늘린다.

왜 0.75인가

너무 낮으면 (예: 0.25):
  - 자주 resize 발생 → 비용 증가
  - 메모리 낭비 (배열의 75%가 빈 공간)
  - 단, 충돌은 적어 get/put 빠름

너무 높으면 (예: 0.95):
  - resize 드물어 메모리 효율적
  - 그러나 충돌 폭증 → 체인 길어짐 → get/put 느림

0.75:
  - 메모리 효율과 시간 효율의 균형점
  - 푸아송 분포 분석에서 충돌 빈도가 합리적인 지점
  - JDK 소스 주석에 "compromise between time and space costs"
  - "예외적인 상황 외엔 바꾸지 마라" 권고

OpenJDK HashMap javadoc에 명시된 트레이드오프. 0.75는 모든 일반 상황에 충분히 좋고, 바꾸려면 명확한 측정 근거가 있어야 함.

Resize의 흐름

1. 새 테이블 생성: newCap = oldCap × 2
2. 새 threshold 계산: newThr = oldThr × 2
3. 기존 테이블의 모든 Node를 새 테이블로 재배치
4. 기존 테이블 GC

핵심 비용: 3번 — 모든 엔트리를 다시 인덱스 계산해서 옮겨야 함
시간 복잡도: O(n)
빈도: 평균적으로 n번 put할 때 log(n)번 정도 (capacity가 두 배씩)
amortized: O(1)에 분산

핵심 트릭 — 인덱스 분할

가장 흥미로운 부분. capacity가 두 배가 되면 모든 엔트리를 단순히 새 위치 계산해서 옮기는 게 아니라 두 곳 중 하나로만 갈 수 있다. 

capacity가 16 → 32로 늘 때:

기존 인덱스: hash & 15  (= hash & 0b01111, 하위 4비트)
새 인덱스:   hash & 31  (= hash & 0b11111, 하위 5비트)

새 인덱스가 기존보다 한 비트(상위 1비트)만 더 봄.
그 한 비트의 값에 따라:
  - 0이면: 새 인덱스 == 기존 인덱스
  - 1이면: 새 인덱스 == 기존 인덱스 + 16 (= oldCap)

즉, 한 버킷의 엔트리들은 두 그룹으로 분할:
  ① "low 그룹": 새 테이블의 같은 인덱스에 그대로
  ② "high 그룹": 새 테이블의 인덱스 + oldCap 위치로

코드로 보는 분할 — Java 8+ resize

// java.util.HashMap.resize (요약)
Node<K,V> loHead = null, loTail = null;   // low 그룹 체인
Node<K,V> hiHead = null, hiTail = null;   // high 그룹 체인

Node<K,V> e;
do {
    Node<K,V> next = e.next;

    if ((e.hash & oldCap) == 0) {
        // 추가된 비트가 0 → low 그룹
        if (loTail == null) loHead = e;
        else loTail.next = e;
        loTail = e;
    } else {
        // 추가된 비트가 1 → high 그룹
        if (hiTail == null) hiHead = e;
        else hiTail.next = e;
        hiTail = e;
    }
} while ((e = next) != null);

// 새 테이블에 두 체인 배치
if (loTail != null) {
    loTail.next = null;
    newTab[j] = loHead;             // 같은 인덱스
}
if (hiTail != null) {
    hiTail.next = null;
    newTab[j + oldCap] = hiHead;    // 인덱스 + oldCap
}

핵심: e.hash & oldCap 한 번의 비트 연산으로 어디로 갈지 결정. rehash(다시 hash 함수 호출)할 필요 없이 기존 hash로 충분.

왜 이게 가능한가 — capacity가 2의 제곱이라서

oldCap = 16 = 0b10000
oldCap - 1 = 15 = 0b01111
newCap - 1 = 31 = 0b11111

→ newCap의 mask는 oldCap의 mask보다 정확히 1비트(추가된 상위 비트) 더 봄
→ 그 비트는 oldCap 자체의 비트와 일치 (0b10000)
→ hash & oldCap == 0인지 확인하면 그 비트가 0인지 1인지 즉시 알 수 있음

만약 capacity가 2의 제곱이 아니었다면:
  - mask가 비트 패턴이 아니라 임의의 값
  - 인덱스 분할 트릭 불가능
  - 모든 엔트리에 대해 hash & (newCap - 1) 다시 계산해야 함

→ "capacity는 2의 제곱"이라는 약속이 resize를 빠르게 만드는 핵심

분할 그림

before resize (capacity=16):
  table[3]: Node{hash=0b...0011}     → 0b011 & 0b1111 = 3
            Node{hash=0b...10011}    → 0b10011 & 0b1111 = 3 (충돌!)
            Node{hash=0b...0011}     → 3
            Node{hash=0b...10011}    → 3 (충돌)

after resize (capacity=32):
  새 mask = 0b11111

  Node{hash=0b...0011}    & 0b10000 = 0   → low 그룹 → table[3]
  Node{hash=0b...10011}   & 0b10000 = 1   → high 그룹 → table[19]
  Node{hash=0b...0011}    & 0b10000 = 0   → low 그룹 → table[3]
  Node{hash=0b...10011}   & 0b10000 = 1   → high 그룹 → table[19]

→ 한 버킷에 몰려있던 4개가 두 버킷으로 깔끔히 분할
→ 충돌이 줄고 평균 체인 길이 감소

Resize의 비용과 영향

비용:
  1. 새 배열 할당 (capacity의 두 배 크기)
  2. 모든 Node를 새 자리로 이동 (O(n))
  3. GC가 곧 옛 배열 회수 (메모리 일시적 두 배)

영향:
  put 한 번이 O(n)이 될 수 있음 (resize 트리거 시)
  → amortized 분석으론 O(1)이지만 즉각적인 latency spike
  → 응답 시간 SLA가 빡빡한 시스템에선 문제

회피:
  초기 capacity를 충분히 잡아 두기
    new HashMap<>(expectedSize / 0.75 + 1)

  예: 1만 개 저장 예정
    new HashMap<>(1334)   // 1만 / 0.75 + 1
    → Hibernate가 1334 이상의 가장 가까운 2의 제곱 = 2048로 capacity 설정
    → resize가 거의 일어나지 않음

capacity 초기화의 함정

new HashMap<>(expectedSize)

→ 흔한 실수. 이건 "초기 capacity"이지 "수용 가능한 엔트리 수"가 아님

예:
  new HashMap<>(1000)
  - capacity = 1024 (가장 가까운 2의 제곱)
  - threshold = 1024 × 0.75 = 768
  - 768개부터 resize 시작 → 1000개 다 넣기 전에 한 번 더 늘어남

올바른 사용:
  expectedSize / loadFactor + 1
  → 1000 / 0.75 + 1 = 1334
  → capacity = 2048
  → threshold = 1536 → 1000개 넣어도 resize 없음

Java 19+ (JEP 446):
  HashMap.newHashMap(expectedSize)
  → 알아서 적절한 capacity 계산
  → 권장

Hashtable / ConcurrentHashMap의 resize

Hashtable:
  - capacity가 2의 제곱이 아닐 수 있음 (소수 권장)
  - resize 시 모든 엔트리에 대해 인덱스 다시 계산 (% 사용)
  - 인덱스 분할 트릭 못 씀
  - resize 동안 모든 작업 블록 (synchronized 메서드)

ConcurrentHashMap:
  - capacity는 2의 제곱 (HashMap과 동일)
  - resize 동안에도 다른 스레드가 읽기/쓰기 가능
  - "transfer" 단계에서 여러 스레드가 분할 협력
  - 매우 정교한 동시성 제어 (별도 시리즈에서 깊이)

면접 단골 질문

Q. Load Factor가 왜 0.75인가?

시간 효율과 공간 효율의 균형점. 더 낮으면 메모리 낭비 + 잦은 resize, 더 높으면 충돌 폭증. 푸아송 분포 분석상 충돌 빈도가 합리적인 지점이라 OpenJDK가 권장 기본값으로 채택.

Q. Resize 시 모든 엔트리를 다시 hash해야 하나?

아니다. capacity가 2의 제곱이라는 약속 덕에 hash & oldCap 한 번의 비트 연산으로 어디로 갈지 결정. 같은 인덱스에 그대로 두거나 인덱스 + oldCap에 두 그룹으로 분할. rehash 호출 불필요.

Q. expectedSize가 1만 개일 때 HashMap을 어떻게 만드나?

new HashMap<>(1334) 또는 Java 19+의 HashMap.newHashMap(10_000). 단순히 new HashMap<>(10_000)으로 만들면 threshold가 7500이라 도중에 resize가 한 번 일어남.

Q. Resize의 시간 복잡도가 amortized O(1)인 이유?

개별 resize는 O(n)이지만, n번 put 동안 capacity가 log(n)번 두 배로 늘어남. 각 resize는 직전 크기의 엔트리만 옮기므로 총 비용은 n + n/2 + n/4 + ... = 2n = O(n). n번의 put에 분산하면 평균 O(1).

한 줄 정리

HashMap은 size > capacity × 0.75일 때 자동으로 capacity를 두 배로 확장.

resize의 핵심 트릭:
  capacity가 2의 제곱이라 hash & oldCap 한 번으로 분할 가능.
  엔트리는 같은 인덱스에 그대로 또는 인덱스 + oldCap으로 깔끔히 두 그룹.

영향:
  put 하나가 O(n)이 될 수 있음 (latency spike)
  expectedSize 알면 미리 capacity 충분히 주는 게 안전.
