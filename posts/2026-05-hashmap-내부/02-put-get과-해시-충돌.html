put의 전체 흐름

map.put(key, value)
  ↓
1. hash = hash(key)  // 1편의 보정된 해시 (h ^ h>>>16)
  ↓
2. index = hash & (table.length - 1)  // 버킷 위치
  ↓
3. table[index] 확인:
   ① null이면 → 새 Node 생성해서 그 자리에 넣기 (충돌 없음)
   ② Node가 있으면 → 충돌 처리 진입
  ↓
4. 충돌 처리:
   기존 Node부터 순회하며 같은 key를 찾는다
   - equals로 비교
   - 같은 key면 value만 덮어쓰기
   - 끝까지 못 찾으면 리스트 끝에 새 Node 추가
  ↓
5. size++ → load factor 체크 → 필요하면 resize (3편 주제)
  ↓
6. (Java 8+) 한 버킷의 길이가 너무 길어지면 트리 변환 (4편 주제)

코드로 보는 putVal 핵심

// java.util.HashMap.putVal (요약)
final V putVal(int hash, K key, V value, ...) {
    Node<K,V>[] tab; Node<K,V> p; int n, i;

    // 테이블 초기화 (lazy)
    if ((tab = table) == null || (n = tab.length) == 0)
        n = (tab = resize()).length;

    // 1. 인덱스 계산 후 빈 자리면 즉시 삽입
    if ((p = tab[i = (n - 1) & hash]) == null)
        tab[i] = newNode(hash, key, value, null);
    else {
        // 2. 충돌 — 기존 Node가 있는 경우
        Node<K,V> e; K k;

        // 첫 노드가 같은 key인지
        if (p.hash == hash &&
            ((k = p.key) == key || (key != null && key.equals(k))))
            e = p;
        else if (p instanceof TreeNode)
            // 이미 트리화된 버킷이면 트리에서 처리 (4편)
            e = ((TreeNode<K,V>)p).putTreeVal(this, tab, hash, key, value);
        else {
            // 리스트 순회
            for (int binCount = 0; ; ++binCount) {
                if ((e = p.next) == null) {
                    // 끝까지 같은 key 없음 → 새로 추가
                    p.next = newNode(hash, key, value, null);
                    if (binCount >= TREEIFY_THRESHOLD - 1)
                        treeifyBin(tab, hash);   // 8개 넘으면 트리화
                    break;
                }
                if (e.hash == hash &&
                    ((k = e.key) == key || (key != null && key.equals(k))))
                    break;   // 같은 key 발견
                p = e;
            }
        }

        // 같은 key가 있었으면 value 덮어쓰기
        if (e != null) {
            V oldValue = e.value;
            e.value = value;
            return oldValue;
        }
    }

    if (++size > threshold)
        resize();   // 임계값 넘으면 확장
    return null;
}

get의 흐름

map.get(key)
  ↓
1. hash = hash(key)
  ↓
2. index = hash & (table.length - 1)
  ↓
3. table[index]가 null이면 → null 반환
  ↓
4. 첫 Node 검사:
   - hash 같고 equals 같으면 → 그 Node의 value 반환
  ↓
5. next가 있으면 순회 (또는 트리면 트리 탐색)
   - 같은 key 찾을 때까지
   - 끝까지 못 찾으면 null 반환

핵심 — hash 비교가 먼저

if (e.hash == hash &&
    ((k = e.key) == key || (key != null && key.equals(k))))

순서:
  ① e.hash == hash : int 비교 (매우 빠름)
  ② k == key : 참조 동일성 (매우 빠름)
  ③ key.equals(k) : 사용자 정의 (느릴 수 있음)

→ 거의 다른 key는 ①에서 걸러짐
→ ②로 동일 객체 fast path
→ ③은 정말 같은 hash인 경우에만

그래서 hashCode가 분포 좋아야 ① 조건이 효과적으로 걸러주고, 분포 나쁘면 ③(equals)이 자주 호출되어 느려진다. equals/hashCode 시리즈에서 짚은 "hashCode 분포의 중요성"이 여기서 구체화.

해시 충돌 — 같은 인덱스, 다른 key

충돌의 정의:
  서로 다른 key A, B가
  hash(A) & (length-1) == hash(B) & (length-1)
  인덱스로 같은 버킷에 떨어지는 것

이유:
  hashCode 자체가 같음 (드뭄)
  hashCode는 다른데 하위 비트가 같음 (흔함, 1편의 인덱스 계산에서 본 그것)

해결 (Java 7까지): 분리 연결법(Separate Chaining)
  같은 버킷에 들어온 노드들을 링크드 리스트로 연결
  table[i] → Node1 → Node2 → Node3 → null

해결 (Java 8+):
  체인 길이가 8 이상 + 테이블 크기 64 이상이면 Red-Black Tree로 전환 (4편)
  그렇지 않으면 여전히 링크드 리스트

충돌이 여러 개인 버킷의 그림

가정:
  HashMap, capacity=16
  put("a", 1) — hash("a") & 15 == 1
  put("b", 2) — hash("b") & 15 == 5
  put("c", 3) — hash("c") & 15 == 1   // ★ "a"와 충돌
  put("d", 4) — hash("d") & 15 == 1   // ★ 또 충돌
  put("e", 5) — hash("e") & 15 == 5   // ★ "b"와 충돌

table:
  [0] null
  [1] Node{a,1} → Node{c,3} → Node{d,4} → null
  [2] null
  [3] null
  [4] null
  [5] Node{b,2} → Node{e,5} → null
  [6] null
  ...

get("d"):
  index = 1 → table[1] 찾기
  Node{a,1} → equals 비교 → "d" 아님 → 다음
  Node{c,3} → equals → "d" 아님 → 다음
  Node{d,4} → equals → 같음 → value 4 반환

충돌이 많을 때의 비용

이상적 (load factor 0.75 이하 + 분포 좋음):
  대부분 버킷의 체인 길이 0 또는 1
  get 평균: O(1)

극단적 (모든 key가 같은 버킷에 충돌):
  버킷 하나의 체인 길이 = n
  get 최악: O(n) — Java 7까지
  get 최악: O(log n) — Java 8+ (트리 변환)

극단적 케이스가 발생할 가능성:
  - 사용자가 정의한 hashCode가 항상 같은 값 (버그)
  - 악의적 입력이 일부러 같은 hash가 되도록 만든 키 ★ 보안 이슈

  ★ HashDoS 공격:
  - 공격자가 같은 hash가 되는 문자열 수만 개를 보냄
  - 모두 한 버킷에 충돌 → get/put이 O(n)
  - 서버 CPU 폭증 → DoS
  - 2011년 ~2012년 Tomcat, Jetty 등 다수 웹 서버 영향
  - Java 8의 트리 변환은 이 공격에 대한 방어책 중 하나

같은 key를 여러 번 put

map.put("a", 1);
map.put("a", 2);
map.put("a", 3);

map.get("a") → 3
map.size() → 1

putVal에서 같은 key를 발견하면 value만 덮어쓴다 (Node 교체 X). 그래서 size는 안 늘어남. put의 반환값은 이전 value (없으면 null).

putIfAbsent와의 차이

map.putIfAbsent("a", 100);
  - 같은 key가 이미 있으면 그 value 반환, 덮어쓰지 않음
  - 없으면 put과 동일하게 동작

map.compute("a", (k, v) -> v == null ? 1 : v + 1);
  - key의 현재 value를 받아 새 value 계산해서 저장
  - 카운트 누적 패턴에 자주 쓰임

null key — 특별 케이스

HashMap.hash:
  static final int hash(Object key) {
      int h;
      return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
  }

→ null key의 hash는 항상 0
→ index = 0 & (length-1) = 0
→ table[0]에 저장됨

특징:
  HashMap은 null key를 허용 (단 1개)
  Hashtable, ConcurrentHashMap은 null key 금지 (NullPointerException)

면접 단골 질문

Q. HashMap에서 hash 충돌이 일어나면 어떻게 처리하나?

분리 연결법(Separate Chaining). 같은 버킷에 들어온 엔트리를 링크드 리스트로 연결하고, get 시 그 리스트를 순회하면서 hash + equals로 같은 key를 찾는다. Java 8+에선 체인이 길어지면 Red-Black Tree로 전환.

Q. put 과정에서 같은 key를 다시 넣으면?

기존 Node의 value만 덮어쓰고 size는 변하지 않음. 반환값은 이전 value(없으면 null). put은 항상 "한 key에 한 value"를 보장.

Q. HashDoS 공격을 들어봤나?

모든 key의 hash가 같아지도록 입력을 만들어 한 버킷에 강제 충돌시키는 공격. 모든 작업이 O(n)으로 떨어져 서버 CPU를 폭증시킴. Java 8의 트리 변환이 부분적 방어책.

Q. HashMap은 null key를 허용하나?

허용. null key의 hash는 0으로 처리되어 table[0]에 저장. 반면 Hashtable, ConcurrentHashMap은 null key를 NullPointerException으로 거부.

한 줄 정리

put: hash → index → 빈 자리면 즉시 삽입, 충돌이면 체인/트리에 연결
get: hash → index → 첫 Node hash 비교 fast path → 다르면 체인/트리 탐색

충돌 처리:
  Java 7까지: 링크드 리스트만
  Java 8+: 길어지면 Red-Black Tree로 전환 (HashDoS 방어 + 최악 O(log n))
