왜 "Authorization Code"인가요

OAuth 2.0에는 여러 Flow가 있는데, Authorization Code Flow가 가장 표준이고 가장 안전해요. 이름의 출처는 흐름 중간에 등장하는 Authorization Code라는 짧은 임시 코드예요.

핵심 아이디어를 한 줄로 표현하면 이래요. 토큰을 두 단계로 나눠 발급해서, 사용자 브라우저에는 절대 진짜 토큰이 노출되지 않게 해요. 왜 이렇게 복잡하게 하는지는 흐름을 따라가면서 이해해봐요.

전체 흐름

단계별 디테일

① 사용자가 로그인 클릭

앱 화면에 "구글로 로그인" 같은 버튼을 누르는 거예요. 단순한 출발이에요.

② Auth Server로 redirect

앱이 사용자 브라우저를 Auth Server의 authorize 엔드포인트로 보내요. 

GET /authorize?
    response_type=code
    &client_id=printify-me-app
    &redirect_uri=https://printifyme.com/callback
    &scope=read:photos
    &state=xyz789

Host: accounts.google.com

쿼리 파라미터 5개가 핵심이에요.

  • response_type=code: "Authorization Code Flow를 쓸게요"라는 표시
  • client_id: 미리 등록한 앱의 ID
  • redirect_uri: 처리 끝나면 사용자를 이 URL로 돌려보내라
  • scope: 요청하는 권한 범위
  • state: CSRF 방어용 랜덤 값. 7단계에서 검증됨

③ 사용자 로그인 + 동의

Auth Server에서 사용자가 비밀번호를 입력해 로그인하고, 권한 동의 화면을 봐요. "PrintifyMe가 다음 권한을 요청합니다: 사진 읽기"

여기서 핵심은 비밀번호가 Auth Server에만 노출된다는 거예요. Client인 PrintifyMe는 이 단계에 관여하지 않아요. 비밀번호를 절대 보지 못해요.

④ Auth code로 redirect

사용자가 동의하면 Auth Server가 사용자를 client의 redirect_uri로 보내요. 쿼리 파라미터에 짧은 임시 코드(authorization code)를 붙여서요. 

HTTP/1.1 302 Found
Location: https://printifyme.com/callback?code=ABC123&state=xyz789

이 코드는 매우 짧게 유효해요. 보통 10분 이하, 한 번 쓰면 끝. Client에 진짜 Access Token을 직접 주지 않고 이런 임시 코드를 주는 게 핵심이에요.

⑤ Browser가 Client에 도달

Browser가 redirect를 따라 Client(printifyme.com/callback)에 도착해요. Client는 쿼리에서 code와 state를 추출해요. state가 ②에서 보낸 값과 일치하는지 먼저 확인. 일치 안 하면 CSRF 의심으로 즉시 거부.

⑥ Code → Token 교환 (서버↔서버)

여기가 핵심 차별점이에요. Client의 백엔드가 Auth Server의 token 엔드포인트를 호출해 Access Token으로 교환해요. 

POST /token HTTP/1.1
Host: accounts.google.com
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code
&code=ABC123
&redirect_uri=https://printifyme.com/callback
&client_id=printify-me-app
&client_secret=very-secret-key

이 요청에는 client_secret이 들어가요. Client가 발급 시 받아둔 비밀 키예요. 이건 절대 브라우저나 사용자에게 노출되지 않아요. 백엔드 서버에서만 안전하게 보관돼요.

⑦ Access Token 발급

Auth Server가 검증 통과하면 토큰을 응답해요. 

{
  "access_token": "ya29.a0Aa4xrXM...",
  "token_type": "Bearer",
  "expires_in": 3600,
  "refresh_token": "1//05BgFtBfVjf...",
  "scope": "read:photos"
}

이 토큰은 Client 백엔드에 저장돼요. 사용자 브라우저는 절대 이 토큰을 보지 못해요. 이후 Client는 사용자별 세션에 토큰을 연결해두고, API 호출에 사용해요.

왜 이렇게 두 단계인가요

가장 자주 받는 질문이에요. 그냥 ④에서 Auth Server가 토큰을 직접 주면 안 될까요? 답은 명확해요. 토큰이 브라우저 URL이나 히스토리에 노출되면 위험하기 때문이에요.

토큰을 URL에 두면 생기는 문제

  • 브라우저 히스토리에 영구 저장돼요
  • Referer 헤더로 다른 사이트에 노출될 수 있어요
  • 웹 서버 access log에 그대로 기록돼요
  • 중간 프록시가 캐싱할 수 있어요
  • 브라우저 확장 프로그램이 읽을 수 있어요

Authorization Code Flow는 임시 코드만 URL에 노출시키고, 진짜 Access Token은 백엔드끼리의 통신으로만 주고받아요. 코드 자체가 노출되더라도 client_secret 없이는 교환이 안 되니까 안전해요. 또 코드는 한 번 쓰면 끝이라 reuse도 안 돼요.

state 파라미터 — CSRF 방어

②에서 본 state는 단순한 옵션이 아니에요. CSRF 공격을 막는 핵심 방어선이에요.

공격 시나리오 (state 없이)

  1. 공격자가 자기 계정으로 OAuth Flow를 시작해 callback URL을 받음
  2. 그 callback URL을 피해자에게 보냄 (이메일, 메시지 등)
  3. 피해자가 클릭하면 공격자의 코드가 피해자 client에 도착
  4. 코드 교환 후 피해자 client가 공격자 계정의 Access Token을 발급받음
  5. 피해자가 모르고 공격자 계정으로 로그인된 상태가 됨 → 공격자가 그 계정에 데이터를 심어둘 수 있음

state로 막기

②에서 client가 랜덤한 state 값을 만들어 세션에 저장하고 보내요. ④에서 Auth Server가 같은 state를 callback URL에 포함시켜 돌려줘요. ⑤에서 client가 받은 state와 세션의 state를 비교해서 일치하지 않으면 거부.

공격자가 만든 callback URL의 state는 피해자 세션의 state와 다르니 검증 실패. 공격이 차단돼요. state는 OAuth 구현의 필수예요.

refresh_token 사용

Access Token이 만료되면 client는 Refresh Token으로 새 Access Token을 받아요. 

POST /token HTTP/1.1
Host: accounts.google.com
Content-Type: application/x-www-form-urlencoded

grant_type=refresh_token
&refresh_token=1//05BgFtBfVjf...
&client_id=printify-me-app
&client_secret=very-secret-key

응답으로 새 Access Token이 와요. 가끔 새 Refresh Token도 함께 와서, 옛 Refresh Token이 무효화되기도 해요(Token Rotation). 사용자는 이 모든 과정을 알아채지 못해요. 자동 갱신이라.

주요 파라미터 정리

파라미터의미필수 여부
response_type Flow 종류 (code, token 등) 필수
client_id 등록된 앱 ID 필수
redirect_uri 처리 후 redirect할 URL 필수 (등록된 URL이어야 함)
scope 요청하는 권한 범위 대부분 필요
state CSRF 방어용 랜덤 강력 권장 (사실상 필수)
code_challenge / code_verifier PKCE용 (3편) 모바일/SPA에 필수
nonce OIDC ID Token replay 방어 OIDC 사용 시 필수

redirect_uri의 보안

redirect_uri는 매우 민감한 파라미터예요. 잘못 다루면 토큰 탈취 공격이 가능해요.

등록된 URI만 허용

Auth Server는 client 등록 시 미리 redirect_uri를 받아둬요. 요청에서 그 URI와 정확히 일치하지 않으면 거부. 문자열 비교가 엄격해야 해요. https://app.com/callback과 https://app.com/callback/은 다른 거.

Open Redirect 회피

redirect_uri가 와일드카드 패턴이거나 검증이 약하면 공격자가 자기 도메인을 redirect_uri로 지정할 수 있어요. 그러면 피해자의 코드가 공격자 도메인으로 전송돼요. 정확한 문자열 일치, 또는 매우 제한된 prefix 매칭만 허용해야 해요.

흔한 실수

1. state 안 씀

위에서 본 CSRF 공격에 노출돼요. 라이브러리 쓰면 자동인 경우가 많지만 직접 구현하면 빠뜨리기 쉬워요.

2. client_secret 노출

모바일 앱이나 SPA에 client_secret을 넣으면 사실상 공개돼요. 디컴파일이나 브라우저 개발자 도구로 누구나 볼 수 있어요. 이런 환경에서는 client_secret을 쓰지 않는 PKCE를 써야 해요. 3편 주제.

3. 코드 재사용

Authorization Code는 한 번만 써야 해요. 두 번째 사용 시 Auth Server가 원래 발급한 토큰까지 무효화하는 게 일반적. 가끔 백엔드 버그로 코드를 두 번 호출하면 사용자가 갑자기 로그아웃되는 사고가 발생.

4. Token을 URL에 노출

서버 응답으로 받은 Access Token을 client가 사용자 브라우저로 redirect할 때 URL에 넣으면 안 돼요. Authorization Code Flow의 모든 노력이 헛수고가 되는 셈. Token은 백엔드에 보관하고 사용자 세션과 연결.

보안 요건 정리

  • 모든 통신을 HTTPS로 (HTTP는 절대 안 됨)
  • state 파라미터로 CSRF 방어
  • redirect_uri 정확한 문자열 일치 검증
  • client_secret을 백엔드에만 보관
  • Access Token도 백엔드에 보관, 사용자 세션과 연결
  • Authorization Code는 한 번만 사용
  • OIDC 사용 시 nonce도 검증
  • 모바일/SPA에는 PKCE 사용 (3편)

면접 단골 질문

Q. Authorization Code Flow가 왜 두 단계로 토큰을 교환하나요?

토큰을 사용자 브라우저에 노출시키지 않기 위해서예요. ④에서 Auth Server가 직접 토큰을 주면 그게 URL이나 히스토리, Referer 헤더, access log에 노출될 수 있어요. 그래서 임시 코드만 URL에 두고, 코드를 client 백엔드에서 토큰으로 교환해요. 이때 client_secret을 함께 보내서 코드가 탈취됐어도 교환이 안 되게 만들어요.

Q. state 파라미터는 왜 필요한가요?

CSRF 공격을 막기 위해서예요. 공격자가 자기 코드가 들어있는 callback URL을 피해자에게 보내고, 피해자가 모르고 공격자 계정으로 로그인되게 하는 공격이 가능해요. state는 client가 랜덤하게 만들어 세션에 저장하고 보내는 값이에요. callback에서 받은 state가 세션의 state와 일치하지 않으면 거부. 공격자가 만든 callback의 state는 피해자 세션과 다르니 차단돼요.

Q. redirect_uri는 왜 미리 등록해야 하나요?

Open Redirect 공격을 막기 위해서예요. 검증이 약하면 공격자가 자기 도메인을 redirect_uri로 지정해서 피해자의 인증 코드를 자기 서버로 빼돌릴 수 있어요. Auth Server는 client 등록 시 redirect_uri를 받아두고, 요청 시 정확히 일치하는지 확인해서 등록 안 된 URL은 거부해요.

Q. Authorization Code가 한 번만 쓰이는 이유?

한 번만 쓰는 게 원칙이에요. 두 번째 사용을 감지하면 Auth Server가 그 코드로 발급된 토큰까지 모두 무효화하는 게 일반적이에요. 이렇게 하면 코드가 탈취돼서 공격자와 정상 client 둘 다 교환을 시도해도, 한 쪽만 성공하고 나머지는 차단돼요. 정상 client가 갑자기 로그아웃되더라도 보안이 우선이라는 정책이에요.

한 줄 정리

Authorization Code Flow는 토큰을 두 단계로 교환해서 사용자 브라우저에 진짜 토큰이 노출되지 않게 해요. 짧은 임시 코드만 URL에 두고, 코드 → 토큰 교환은 client 백엔드와 Auth Server 사이의 직접 통신으로 처리. state로 CSRF 방어, redirect_uri 검증으로 Open Redirect 방어가 핵심 보안 메커니즘. OAuth 2.0의 가장 표준이고 안전한 흐름이에요.

다음 편에서는 다른 Flow들 (Implicit, Client Credentials, Device Code) 그리고 모바일/SPA에 필수인 PKCE를 봐요.
