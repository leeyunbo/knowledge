OAuth 2.0의 빈 자리 — "사용자가 누구지?"

1편에서 말한 부분을 다시 짚어요. OAuth 2.0은 인가(Authorization) 프로토콜이에요. Access Token으로 무엇을 할 수 있는지는 알려주지만, 그 토큰이 어떤 사용자의 것인지는 직접 알려주지 않아요.

그런데 "구글로 로그인" 같은 기능에서는 사용자 신원이 핵심이에요. 토큰만 받고 끝나는 게 아니라 "누가 로그인했는지"를 알아야 해요. 이 빈 자리를 채우려고 OAuth 2.0 위에 인증 표준을 얹은 게 OpenID Connect (OIDC)예요.

OIDC가 추가한 것

OIDC는 OAuth 2.0과 거의 같은 흐름이에요. 엔드포인트, 파라미터, Flow까지 동일. 핵심 차이는 두 가지예요.

  • ID Token: 사용자 신원을 담은 JWT가 추가로 발급돼요
  • UserInfo 엔드포인트: 사용자 프로필을 조회할 수 있는 표준 API

그리고 scope에 openid가 들어가야 OIDC로 인식돼요. 이 한 단어가 OIDC 활성화 스위치예요. 

GET /authorize?
    response_type=code
    &client_id=...
    &redirect_uri=...
    &scope=openid profile email      ← openid 포함

ID Token — JWT 형식의 신원 증명

OIDC의 가장 큰 추가물이에요. JWT 형식의 토큰으로 사용자 신원 정보가 담겨 있어요. 토큰 교환 시 Access Token과 함께 ID Token도 응답에 들어와요. 

{
  "access_token": "ya29.a0Aa4xrXM...",
  "id_token": "eyJhbGciOiJSUzI1NiIs...",
  "refresh_token": "1//05BgFtBfVjf...",
  "token_type": "Bearer",
  "expires_in": 3600
}

ID Token의 내용

JWT라 base64로 디코딩하면 사용자 정보가 보여요. 

{
  "iss": "https://accounts.google.com",
  "sub": "1234567890",
  "aud": "printify-me-app",
  "exp": 1699999999,
  "iat": 1699996399,
  "nonce": "n-0S6_WzA2Mj",
  "email": "alice@example.com",
  "email_verified": true,
  "name": "Alice Kim",
  "picture": "https://example.com/photo.jpg"
}

표준 클레임

  • iss: 발급자 (Auth Server URL)
  • sub: 사용자 고유 ID (이 발급자 안에서 유니크)
  • aud: 이 토큰이 사용될 client_id
  • exp: 만료 시각
  • iat: 발급 시각
  • nonce: 인증 요청에 보낸 nonce. replay 공격 방어

이 외에 scope에 따라 email, name, picture, profile 같은 사용자 정보 클레임이 추가돼요.

ID Token vs Access Token — 헷갈리지 마세요

가장 자주 헷갈리는 부분이에요. 둘은 완전히 다른 용도예요.

측면ID TokenAccess Token
용도 사용자 신원 증명 API 자원 접근 권한
대상 (audience) Client (받은 앱) Resource Server (자원 서버)
형식 JWT (구조화) opaque 또는 JWT (표준 X)
검증 위치 Client가 직접 검증 Resource Server가 검증
API 호출에 사용? 안 됨 사용

흔한 실수

ID Token을 API 호출의 Bearer Token으로 사용하는 경우가 있어요. 잘못된 사용법이에요. ID Token은 client(앱)에게 사용자가 누구인지 알려주는 용도지, 자원 서버에 보내는 토큰이 아니에요. API 호출엔 Access Token을 써야 해요.

ID Token 검증

Client가 ID Token을 받으면 반드시 검증해야 해요. JWT 시리즈에서 다룬 검증 단계가 그대로 적용돼요.

  1. Signature 검증: Auth Server의 공개키로 서명 검증 (보통 RS256)
  2. iss 확인: 신뢰하는 발급자가 맞는지
  3. aud 확인: 내 client_id와 일치하는지
  4. exp 확인: 만료되지 않았는지
  5. nonce 확인: 내가 보낸 nonce와 일치하는지 (replay 방어)

이 검증을 빼먹으면 위조된 ID Token을 그대로 신뢰하게 돼요. 절대 생략하지 말아야 해요. 대부분 라이브러리(Spring Security, Auth0 SDK, Auth.js 등)가 자동으로 처리해주지만, 직접 구현 시 반드시 의식해야 해요.

UserInfo 엔드포인트

ID Token에 모든 사용자 정보를 다 담을 수 있지만, 토큰이 너무 커지는 걸 피하려고 별도 엔드포인트가 있어요. 

GET /userinfo
Authorization: Bearer ya29.a0Aa4xrXM...
{
  "sub": "1234567890",
  "name": "Alice Kim",
  "given_name": "Alice",
  "family_name": "Kim",
  "email": "alice@example.com",
  "picture": "https://example.com/photo.jpg",
  "locale": "ko-KR"
}

ID Token에 핵심 정보(sub, email)만 담고, 더 자세한 프로필은 필요할 때 UserInfo 엔드포인트로 조회하는 게 일반적이에요.

Refresh Token Rotation — 보안 강화

1편에서 Refresh Token이 보안 자산이라고 했어요. 탈취되면 공격자가 계속 새 Access Token을 만들 수 있으니까요. 이걸 강화하는 패턴이 Refresh Token Rotation이에요.

핵심 아이디어

Refresh Token 사용 시마다 새 Refresh Token을 함께 발급하고, 옛 Refresh Token은 즉시 무효화해요. 그래서 한 Refresh Token은 평생 한 번만 사용 가능. 

처음 발급: A, RT1
RT1로 갱신 1회: B, RT2 (RT1 무효)
RT2로 갱신 2회: C, RT3 (RT2 무효)
...

탈취 감지

공격자가 RT1을 탈취해서 사용했다고 해볼게요. Auth Server는 RT2를 발급하고 RT1을 무효화해요. 나중에 정상 사용자가 RT1으로 갱신을 시도하면 거부돼요. 이 시점에 Auth Server는 "이 사용자의 토큰이 탈취된 것 같다"고 감지하고, 그 사용자의 모든 토큰을 무효화하는 강력한 대응을 할 수 있어요.

OAuth 2.0 Security BCP에서 SPA, 모바일에 Token Rotation을 권장해요. Auth0, Okta 같은 주요 IdP가 기본 지원.

Logout — 의외로 복잡한 부분

OAuth 2.0 자체는 logout을 정의하지 않았어요. OIDC가 별도 표준으로 추가했어요.

RP-Initiated Logout

Relying Party(client)가 logout을 시작하는 방식이에요. 

GET /endsession?
    id_token_hint=eyJhbGciOiJSUzI1NiIs...
    &post_logout_redirect_uri=https://app.com/logged-out
    &state=xyz

Auth Server가 사용자 세션을 종료하고, post_logout_redirect_uri로 redirect해요. 단, 클라이언트 측 토큰 폐기는 별도예요. Access Token이 만료될 때까지 살아있을 수 있어요.

Front-Channel / Back-Channel Logout

한 Auth Server에 여러 client가 연결된 SSO 환경에서 한 client logout이 다른 client에도 전파돼야 할 때 사용.

  • Front-Channel: 브라우저가 보이지 않는 iframe으로 각 client에 logout 신호 전달
  • Back-Channel: Auth Server가 직접 각 client의 백엔드에 logout 알림 (HTTP POST)

둘 다 한계가 있어서 SSO logout은 여전히 까다로운 영역이에요. 많은 시스템이 일관된 logout보다는 "토큰 만료를 기다린다"는 정책으로 운영해요.

Spring Security와 OAuth/OIDC

Spring Security가 OAuth 2.0과 OIDC를 표준으로 지원해요. yaml 한 줄로 시작 가능. 

spring:
  security:
    oauth2:
      client:
        registration:
          google:
            client-id: ${GOOGLE_CLIENT_ID}
            client-secret: ${GOOGLE_CLIENT_SECRET}
            scope:
              - openid
              - email
              - profile
        provider:
          google:
            issuer-uri: https://accounts.google.com

그리고 Spring Security 설정에서 OAuth2 로그인 활성화. 

@Configuration
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/", "/login").permitAll()
                .anyRequest().authenticated()
            )
            .oauth2Login();
        return http.build();
    }
}

이 설정으로 /oauth2/authorization/google에 접근하면 자동으로 구글 OAuth Flow가 시작돼요. 토큰 교환, ID Token 검증, 사용자 세션 생성까지 Spring이 모두 처리. PKCE도 기본 활성화돼 있어요. 매우 편해요.

실무 시나리오 1 — 소셜 로그인

가장 흔한 사용처. 사용자가 구글/카카오/네이버로 로그인하는 기능.

흐름 정리

  1. 사용자가 "구글로 로그인" 클릭
  2. Authorization Code Flow + PKCE로 진행
  3. Auth Server에서 ID Token 받음
  4. ID Token 검증 후 sub(고유 ID)로 사용자 식별
  5. 처음 로그인이면 회원가입, 이미 있으면 로그인 처리
  6. 자체 세션 또는 자체 JWT 발급해 사용자 인증 유지

마지막 단계가 중요해요. OIDC ID Token을 그대로 세션 토큰으로 쓰지 말고, 자체 토큰을 발급하는 게 좋아요. OIDC ID Token은 사용자 신원 증명용이지 세션 관리용이 아니에요.

실무 시나리오 2 — API 인증

모바일 앱이 백엔드 API에 인증된 요청을 보내는 경우.

흐름

  1. 앱이 자체 백엔드의 OAuth 서버(또는 Auth0/Cognito)에서 토큰 발급받음
  2. Authorization Code + PKCE 사용
  3. Access Token을 Keychain/Keystore에 안전하게 저장
  4. API 호출마다 Authorization: Bearer 헤더로 토큰 전송
  5. 토큰 만료 시 Refresh Token으로 자동 갱신 (Rotation 권장)

실무 시나리오 3 — 마이크로서비스

여러 서비스가 같은 사용자의 토큰을 공유해야 할 때.

패턴

  • 한 Auth Server (Keycloak, Cognito, Auth0)가 토큰 발급
  • 각 서비스는 Resource Server 역할
  • 토큰을 JWT로 발급하면 각 서비스가 공개키로 직접 검증 가능 (RS256)
  • opaque 토큰이면 Auth Server의 introspection 엔드포인트 호출 (느림)
  • JWT 검증 결과는 짧게 캐싱해도 OK

흔한 실수 정리

  1. ID Token을 API 호출에 사용: Access Token을 써야 해요
  2. ID Token 검증 생략: 위조 토큰을 그대로 신뢰하게 됨
  3. nonce 검증 생략: replay 공격에 노출
  4. localStorage에 토큰 저장: XSS 위험. 메모리 또는 HttpOnly 쿠키 권장
  5. HTTPS 안 쓰는 환경에서 OAuth: 절대 안 됨. 토큰이 평문으로 노출
  6. scope를 과도하게 요청: 사용자 거부율 높아짐. 최소 권한 원칙
  7. state 검증 생략: CSRF 공격 가능
  8. redirect_uri 검증 약하게: Open Redirect로 토큰 탈취 위험

면접 단골 질문

Q. OAuth 2.0과 OIDC의 차이는요?

OAuth 2.0은 인가(Authorization) 프로토콜이에요. "이 토큰으로 무엇을 할 수 있는가"를 알려주지 "사용자가 누구인가"는 알려주지 않아요. OIDC는 OAuth 2.0 위에 인증(Authentication)을 얹은 표준이에요. ID Token이라는 JWT를 추가로 발급해서 사용자 신원을 증명해요. scope에 openid가 들어가면 OIDC로 동작해요. "구글로 로그인"이 OIDC 기반이에요.

Q. ID Token과 Access Token을 어떻게 다르게 사용하나요?

ID Token은 client(앱)가 사용자 신원을 확인하는 용도예요. JWT라 client가 직접 검증해서 sub, email 같은 정보를 추출. Access Token은 Resource Server(API)에 자원 요청할 때 Authorization: Bearer 헤더로 보내는 용도예요. ID Token을 API 호출에 쓰는 건 잘못된 사용법. 반대도 마찬가지예요.

Q. Refresh Token Rotation이 왜 안전한가요?

한 Refresh Token이 평생 한 번만 사용되니, 탈취된 토큰의 영향이 제한돼요. 공격자가 토큰을 탈취해 사용하면 그 토큰은 무효가 되고 새 토큰이 발급돼요. 정상 사용자가 옛 토큰으로 갱신을 시도하면 거부되니, Auth Server는 탈취를 즉시 감지하고 모든 토큰을 무효화하는 강력한 대응이 가능해요. 탈취 자체를 시그널로 활용하는 패턴이에요.

Q. nonce는 왜 필요한가요?

ID Token replay 공격을 막기 위해서예요. client가 인증 요청에 nonce를 포함해 보내요. Auth Server는 그 nonce를 ID Token의 클레임으로 넣어 응답. Client가 ID Token 검증 시 nonce가 자기가 보낸 값과 일치하는지 확인해요. 공격자가 다른 사용자의 ID Token을 가로채 자기 client에 주입하려 해도 nonce가 일치하지 않으니 검증 실패.

한 줄 정리

OIDC는 OAuth 2.0 위에 인증을 얹은 표준이에요. ID Token이라는 JWT로 사용자 신원을 증명해요. ID Token과 Access Token은 다른 용도라 헷갈리지 말아야 하고, 항상 검증을 거쳐야 해요. 실무에서 Spring Security 같은 라이브러리가 표준 흐름을 자동 처리해주지만, PKCE / nonce / state / Refresh Token Rotation 같은 보안 메커니즘을 의식하는 게 안전한 운영의 핵심이에요.

OAuth/OIDC 시리즈는 여기까지예요.
