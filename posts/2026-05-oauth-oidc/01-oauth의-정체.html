OAuth 2.0의 정체

"구글로 로그인" 같은 기능 뒤에 있는 표준. 비밀번호 없이 권한을 위임하는 메커니즘이 뭔지부터 봐요.

풀려는 문제 — 비밀번호 없이 권한 위임

OAuth 2.0이 풀려는 문제를 한 시나리오로 시작해볼게요. 내가 어떤 사진 인쇄 서비스(예: PrintifyMe)를 쓰려고 해요. 이 서비스는 내 구글 드라이브의 사진을 가져와 인쇄해줘요.

어떻게 가져오게 할까요? 가장 단순한 방법은 내 구글 비밀번호를 PrintifyMe에 알려주는 거예요. 그런데 이건 위험해요.

  • PrintifyMe가 내 비밀번호로 구글의 모든 기능을 마음대로 사용할 수 있어요
  • 비밀번호를 바꾸려면 PrintifyMe에서도 다시 입력해야 해요
  • PrintifyMe의 보안이 뚫리면 내 구글 비밀번호도 함께 유출돼요
  • 나중에 권한을 회수하려면 비밀번호를 바꿔야 해요

OAuth 2.0이 풀려는 문제가 이거예요. 비밀번호를 알려주지 않고 특정 권한만 안전하게 위임하는 방법이요. 내가 PrintifyMe에 "내 구글 드라이브의 사진을 읽을 권한"만 주고, 다른 권한이나 비밀번호는 노출하지 않는 거죠.

4가지 역할

OAuth 2.0은 시스템을 4가지 역할로 나눠요. 위 시나리오에 대입하면 명확해져요.

역할설명예시
Resource Owner 자원의 실제 주인. 보통 사용자 나 (내 구글 드라이브 소유)
Client 자원에 접근하려는 애플리케이션 PrintifyMe
Resource Server 자원을 보관하고 제공하는 서버 구글 드라이브 API
Authorization Server 권한을 발급해주는 서버 구글 OAuth 서버

큰 서비스(구글, 페이스북, 카카오)는 Resource Server와 Authorization Server를 별도로 운영해요. 작은 서비스는 한 시스템이 둘 다 처리할 수도 있고요.

큰 그림 — Access Token이 핵심

OAuth 2.0의 모든 흐름은 결국 Access Token이라는 짧은 문자열을 발급받는 과정이에요. 이 토큰은 "이 클라이언트가 이 사용자의 이런 권한으로 자원에 접근할 수 있다"는 증명서 같은 거예요.

흐름 정리

  1. Client가 사용자에게 권한 위임을 요청
  2. 사용자가 Auth Server에서 동의하고 비밀번호 입력 (이때만!)
  3. Auth Server가 Client에게 Access Token 발급
  4. Client는 그 Token으로 Resource Server에 자원 요청
  5. Resource Server가 Token 검증 후 자원 반환

핵심은 비밀번호가 Client(PrintifyMe)에 절대 노출되지 않는다는 거예요. 비밀번호는 사용자가 Auth Server에 직접 입력하고, 그 결과물인 Token만 Client가 받아요.

Access Token의 성격

Token은 어떻게 동작할까요? 몇 가지 중요한 성질이 있어요.

  • 제한된 권한 (scope): "사진 읽기"만 허용, "삭제"는 안 됨 같은 식으로 권한 범위 명시
  • 유효 기간: 보통 짧음 (1시간 정도). 만료되면 새로 발급받아야 해요
  • 회수 가능: 사용자가 동의 철회하면 Token 즉시 무효
  • 대체 가능: Client가 손상되어도 그 Token만 폐기하면 됨. 비밀번호 안 바꿔도 됨

이 성질들이 비밀번호를 직접 주는 것에 비해 OAuth가 가지는 큰 장점이에요. 권한이 작고, 짧고, 통제 가능해요.

Scope — 권한의 범위

Token이 가지는 권한을 표현하는 게 scope예요. 사용자가 동의하는 시점에 어떤 권한을 줄지 결정돼요. 

scope=read:photos write:photos profile email

공백으로 구분된 문자열이에요. Authorization Server마다 정의된 scope가 달라요.

  • 구글: https://www.googleapis.com/auth/drive.readonly 같은 URL 형태
  • GitHub: repo, user, read:org 같은 짧은 이름
  • OpenID Connect: openid, profile, email 같은 표준 scope

사용자 동의 화면에서 "이 앱이 다음 권한을 요청합니다"로 보이는 게 scope의 표현이에요. 개발자는 진짜 필요한 최소 권한만 요청하는 게 좋아요. 너무 많은 권한 요청은 사용자가 거부할 가능성이 높아요.

Refresh Token — 재발급용

Access Token은 짧게 유효해요(보통 1시간). 만료되면 어떻게 새 Token을 받을까요? 매번 사용자가 다시 로그인하라고 할 수는 없잖아요.

그래서 Refresh Token이라는 별도 토큰을 함께 발급해요. 이건 더 길게 유효(보통 7일~30일 또는 만료 없음)하고, Access Token이 만료되면 이걸로 새 Access Token을 받아요. 

POST /oauth/token
Content-Type: application/x-www-form-urlencoded

grant_type=refresh_token
&refresh_token=def...
&client_id=...
&client_secret=...

Auth Server가 Refresh Token을 검증하고 새 Access Token(과 가끔 새 Refresh Token)을 반환해요. 사용자는 이 과정을 알아채지 못해요. 자동으로 갱신되니까요.

단, Refresh Token도 보안 자산이에요. 탈취되면 공격자가 계속 새 Access Token을 만들 수 있어요. 그래서 안전하게 보관해야 하고, 모바일 앱 같은 환경에선 Token Rotation 같은 추가 보호가 필요해요. 이건 4편에서 자세히.

OAuth 1.0과 뭐가 달라요

OAuth 2.0이 나오기 전에 OAuth 1.0이 있었어요. 둘은 거의 다른 프로토콜이라고 봐도 돼요.

측면OAuth 1.0OAuth 2.0
서명 HMAC 서명 필수 HTTPS 의존, 서명 선택
복잡도 높음 (서명 계산 복잡) 낮음 (HTTPS만 있으면 됨)
Flow 종류 1가지 여러 가지 (Authorization Code, Implicit, Client Credentials, ...)
모바일/SPA 지원 어려움 적합한 Flow 제공
현재 위치 레거시 표준

OAuth 2.0이 단순함과 유연성을 챙긴 대신 보안의 일부를 HTTPS에 의존해요. 그래서 OAuth 2.0은 항상 HTTPS 환경에서만 안전하게 동작해요. 평문 HTTP에서 OAuth 2.0을 쓰면 토큰이 그대로 노출돼요.

"Authentication"이 아니에요

한 가지 헷갈리는 부분이 있어요. OAuth 2.0은 인증(Authentication)이 아니라 인가(Authorization) 프로토콜이에요.

  • 인증: "당신이 누구인지" 확인 (로그인)
  • 인가: "당신이 무엇을 할 수 있는지" 결정 (권한)

OAuth 2.0이 알려주는 건 "이 Token으로 이런 작업을 할 수 있다"이지 "이 Token의 사용자가 누구다"가 아니에요. "구글로 로그인"처럼 사용자 신원도 알아야 하는 경우엔 OAuth 2.0 위에 추가 표준이 필요해요. 그게 OpenID Connect (OIDC)예요. 4편의 주제.

OAuth가 필요한 자리

어떤 상황에서 OAuth 2.0을 쓰는지 정리하면 이래요.

  • 3rd-party 앱이 사용자 데이터에 접근: PrintifyMe가 구글 드라이브 사진 사용
  • SSO (Single Sign-On): 한 번 로그인으로 여러 서비스 사용
  • 모바일 앱과 백엔드 API 인증: 모바일 앱이 백엔드 API에 접근하는 표준
  • 마이크로서비스 간 인증: 서비스끼리 서로 권한 확인
  • "소셜 로그인": 구글/페이스북/카카오 로그인 (OIDC와 결합)

현대 웹/모바일 인증의 사실상 표준이에요. 직접 인증 시스템 만들기 전에 OAuth 2.0과 OIDC 기반 솔루션을 먼저 검토하는 게 일반적.

면접 단골 질문

Q. OAuth 2.0이 풀려는 문제가 뭔가요?

비밀번호를 노출하지 않고 특정 권한만 안전하게 위임하는 거예요. 예를 들어 사진 인쇄 앱이 내 구글 드라이브의 사진을 가져오게 하고 싶은데, 구글 비밀번호를 알려주는 건 위험해요. OAuth는 사용자가 직접 구글에서 동의한 뒤, "사진 읽기" 같은 제한된 권한의 Access Token만 발급받아 앱에 전달해요. 비밀번호는 절대 앱에 노출되지 않아요.

Q. OAuth의 4가지 역할은요?

Resource Owner(자원 주인, 보통 사용자), Client(접근하려는 앱), Resource Server(자원 서버), Authorization Server(권한 발급 서버)예요. 큰 서비스는 Resource Server와 Auth Server를 별도로 운영하고, 작은 서비스는 한 시스템이 둘 다 처리해요.

Q. Access Token과 Refresh Token의 차이는요?

Access Token은 자원 접근에 직접 쓰는 토큰이에요. 짧게 유효(보통 1시간). Refresh Token은 Access Token이 만료되면 새 Access Token을 받기 위한 도구예요. 길게 유효(7일~30일). Access Token은 자주 노출되니 짧게, Refresh Token은 안전하게 보관하면서 자주 안 보냄. 이 분리가 보안과 사용성의 균형을 만들어요.

Q. OAuth 2.0이 인증(Authentication)인가요?

엄밀히는 아니에요. OAuth 2.0은 인가(Authorization) 프로토콜이에요. "이 Token으로 무엇을 할 수 있는가"를 알려주지 "이 Token의 사용자가 누구인가"는 직접 알려주지 않아요. 사용자 신원을 알려면 OpenID Connect(OIDC)를 OAuth 2.0 위에 얹어 써요. "구글로 로그인" 같은 기능이 OIDC 기반이에요.

한 줄 정리

OAuth 2.0은 비밀번호 없이 권한을 위임하는 표준이에요. Resource Owner, Client, Resource Server, Authorization Server 4가지 역할로 나누고, 사용자 동의를 거쳐 짧게 유효한 Access Token을 발급해요. Refresh Token으로 자동 갱신하고, scope로 권한 범위를 제한해요. 현대 웹/모바일 인증의 사실상 표준이지만, 인증 자체가 아닌 인가 프로토콜이라는 점을 의식해야 해요.
