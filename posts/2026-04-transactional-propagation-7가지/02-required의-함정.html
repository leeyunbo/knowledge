REQUIRED — 가장 흔하지만 가장 위험한 디폴트

예외를 catch했는데 왜 UnexpectedRollbackException이 터지는가. REQUIRED의 logical/physical 구분이 만든 가장 유명한 함정.

Series
@Transactional Propagation 7가지
  1. Propagation이 왜 있는가
  2. REQUIRED — 가장 흔하지만 가장 위험한 디폴트
  3. REQUIRES_NEW — 진짜 새 트랜잭션의 함정
  4. 나머지 5가지와 선택 가이드

왜 REQUIRED가 디폴트인가

@Transactional에 propagation을 명시하지 않으면 REQUIRED다. Propagation enum의 Javadoc은 한 줄로 정의한다.

"Support a current transaction, create a new one if none exists."

(현재 트랜잭션을 지원하고, 없으면 새로 만든다.)

외부 tx 있으면 합류, 없으면 새로 시작. 가장 무난한 동작이라 디폴트가 됐다. 대부분의 비즈니스 로직은 "이 작업은 호출자의 트랜잭션에 묶여야 한다"가 자연스럽다.

그런데 REQUIRED의 "합류"가 정확히 무엇이고, 그 안에서 무슨 일이 일어나는지 모른 채로 쓰면 가장 유명한 함정에 걸린다.

합류 = 같은 physical, 다른 logical

1편에서 잠깐 본 physical/logical 구분을 다시 꺼낸다. REQUIRED가 외부 tx에 합류할 때 일어나는 일은: 

placeOrder() 호출
  ├─ TX1 시작 (physical transaction)
  │  └─ logical scope L1 (placeOrder의 @Transactional 범위)
  │
  ├─ paymentService.charge() 호출 (REQUIRED)
  │  └─ logical scope L2 (charge의 @Transactional 범위)
  │     ↓
  │     L2는 새 physical을 만들지 않고 TX1에 합류
  │     L2는 자신만의 rollback-only 플래그를 가짐

물리적으로는 트랜잭션이 하나(TX1)다. BEGIN ~ COMMIT 한 사이클. 하지만 Spring은 각 @Transactional 메서드마다 logical scope를 만들고 그 안에 rollback-only 플래그를 둔다.

왜 이런 구조인가? 다음 절을 보면 이유가 드러난다.

rollback-only 마킹 메커니즘

Spring 공식 문서가 기본 rollback 규칙을 정의한 부분:

"In its default configuration, the Spring Framework's transaction infrastructure code marks a transaction for rollback only in the case of runtime, unchecked exceptions."

(기본 설정에서, Spring은 runtime/unchecked 예외에 한해 트랜잭션을 rollback 대상으로 마킹한다.)

이 "마킹"이 정확히 무엇인가:

@Transactional 메서드 호출
  → TransactionInterceptor가 메서드 실행을 감쌈
  → 메서드 안에서 RuntimeException 던져짐
  → Interceptor가 예외 catch
  → 현재 logical scope에 rollback-only 플래그 set
  → 예외 그대로 다시 throw

그래서 외부에서 그 예외를 잡지 않으면 트랜잭션이 롤백된다. 여기까지는 직관에 맞다.

문제는 외부에서 그 예외를 잡았을 때 일어난다.

catch했는데 UnexpectedRollbackException

가장 자주 보이는 코드 패턴이다. 

@Service
public class OrderService {

    @Transactional
    public Order placeOrder(OrderRequest request) {
        Order order = orderRepository.save(...);
        try {
            paymentService.charge(order);   // REQUIRED, 합류
        } catch (PaymentFailedException e) {
            // 결제 실패해도 주문은 PENDING으로 남기자
            order.markAsPending();
            return order;
        }
        return order;
    }
}

의도는 명확하다. 결제가 실패해도 주문 자체는 살리고 PENDING 상태로 두자는 것.

그런데 실행하면 UnexpectedRollbackException이 터진다. 분명 catch했는데도. 왜?

Spring 공식 문서의 한 줄 설명:

"However, in the case where an inner transaction scope sets the rollback-only marker, the outer transaction has not decided on the rollback itself, so the rollback (silently triggered by the inner transaction scope) is unexpected. A corresponding UnexpectedRollbackException is thrown at that point."

(내부 트랜잭션 scope가 rollback-only 마커를 설정한 경우, 외부 트랜잭션은 롤백을 결정하지 않았으므로, 내부 scope가 조용히 트리거한 롤백은 예상치 못한 상황이다. 이 시점에 UnexpectedRollbackException이 던져진다.)

벌어진 일을 단계별로 보면: 

1. placeOrder() 시작 → TX1 시작
2. charge()에서 PaymentFailedException 던짐
3. charge()의 logical scope L2가 TX1을 rollback-only로 마크
   (charge의 @Transactional이 RuntimeException을 보고 마킹)
4. 예외가 placeOrder()로 propagate
5. placeOrder()의 catch가 예외 잡음
6. placeOrder() 정상 종료, return order
7. Spring이 TX1을 commit하려고 함
   → rollback-only 마크 발견
   → "어? commit 요청 받았는데 rollback-only네"
   → UnexpectedRollbackException 던짐

핵심: logical scope의 rollback-only 마크는 catch로는 풀 수 없다. 내부에서 마크된 순간 그 트랜잭션은 끝났다. 외부가 catch해도 마크는 그대로다.

왜 이렇게 설계됐을까

이 동작이 의아하게 느껴질 수 있다. 그냥 catch했으니 commit해주면 안 되나? 답은 "안 된다, 더 위험하니까"다.

만약 logical scope L2가 마크한 rollback을 외부 catch가 무시할 수 있다면, charge가 한 작업의 일부만 commit되는 상황이 생긴다. charge는 자기 입장에서 "이 작업은 롤백돼야 한다"고 판단했는데, 외부가 그 판단을 무시하고 commit해버리면 charge가 본 부분 작업이 남아있게 된다. 트랜잭션의 원자성이 깨진다.

그래서 Spring은 더 안전한 쪽을 택했다. 한번 마크되면 무조건 롤백, 외부에 명시적으로 알린다는 정책.

그럼 어떻게 풀어야 하나

"결제 실패해도 주문은 살리고 싶다"는 요구가 진짜라면, 트랜잭션 분리가 답이다. charge를 REQUIRES_NEW로 두면 charge의 롤백이 외부 트랜잭션에 영향을 주지 않는다. 

@Service
public class PaymentService {

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void charge(Order order) {
        ...
    }
}

이러면 charge의 트랜잭션이 자체적으로 롤백되고, 외부 placeOrder의 트랜잭션은 영향 없다. catch도 의도대로 동작한다.

단, REQUIRES_NEW에는 또 다른 함정이 있다. 다음 편에서 본다.

정리

  • REQUIRED는 외부 tx에 합류한다 — 같은 physical, 다른 logical
  • RuntimeException이 내부 logical에서 던져지면 physical tx 전체에 rollback-only 마킹
  • 마킹은 catch로 풀 수 없다 — 외부 commit 시도 시 UnexpectedRollbackException
  • "내부 작업은 실패해도 외부는 살리고 싶다"면 REQUIRES_NEW로 분리해야 함

다음 편

다음 편에서는 REQUIRES_NEW를 본다. "진짜 새 트랜잭션"이라는 이름답게, 외부 tx와 완전히 독립된 새 connection을 쓴다. 그런데 그 독립성이 DB 락과 만나면 자기 자신을 데드락에 빠뜨릴 수 있다.
