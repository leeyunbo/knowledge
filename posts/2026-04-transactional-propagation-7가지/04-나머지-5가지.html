나머지 5가지와 선택 가이드

NESTED, SUPPORTS, NOT_SUPPORTED, NEVER, MANDATORY. 7가지 중 실무에서 진짜 필요한 건 몇 개일까.

Series
@Transactional Propagation 7가지
  1. Propagation이 왜 있는가
  2. REQUIRED — 가장 흔하지만 가장 위험한 디폴트
  3. REQUIRES_NEW — 진짜 새 트랜잭션의 함정
  4. 나머지 5가지와 선택 가이드

NESTED — savepoint 기반의 부분 롤백

공식 문서는 NESTED를 이렇게 정의한다.

"PROPAGATION_NESTED uses a single physical transaction with multiple savepoints that it can roll back to. Such partial rollbacks let an inner transaction scope trigger a rollback for its scope, with the outer transaction being able to continue the physical transaction despite some operations having been rolled back."

(NESTED는 하나의 physical transaction 안에서 여러 savepoint를 사용해 그 지점까지 롤백할 수 있게 한다. 이런 부분 롤백 덕분에 내부 scope가 자기 영역의 작업만 롤백시키고, 외부 트랜잭션은 일부 작업이 롤백된 상태로도 physical transaction을 계속 진행할 수 있다.)

REQUIRED와 REQUIRES_NEW의 중간 지점이다:

  • physical은 외부 tx와 공유 (REQUIRES_NEW처럼 새 connection 안 씀)
  • 그런데 내부 작업만 따로 롤백 가능 (REQUIRED와 다른 점)
  • JDBC Connection.setSavepoint() 메커니즘으로 구현
outerMethod() (REQUIRED, TX1)
  ├─ INSERT row1
  ├─ innerMethod() (NESTED)
  │  ├─ Savepoint sp1 생성
  │  ├─ INSERT row2
  │  └─ 예외 발생
  │     └─ Savepoint sp1로 롤백 (row2만 사라짐)
  ├─ INSERT row3       ← 계속 진행 가능
  └─ commit            ← row1, row3은 살아남음

제약: JDBC 기반 트랜잭션 매니저에서만 동작한다. 공식 Javadoc 경고:

"Actual creation of a nested transaction will only work on specific transaction managers. Out of the box, this only applies to the JDBC DataSourceTransactionManager."

(실제 nested 트랜잭션 생성은 특정 transaction manager에서만 동작한다. 기본 제공으로는 JDBC DataSourceTransactionManager에서만.)

JPA를 쓰는 환경(JpaTransactionManager)에선 동작하지 않는다. 쓰려면 transaction manager를 직접 다뤄야 해서 실제로 보기 드물다.

SUPPORTS — 있으면 합류, 없으면 non-tx

공식 정의:

"Support a current transaction, execute non-transactionally if none exists."

(현재 트랜잭션이 있으면 지원하고, 없으면 트랜잭션 없이 실행한다.)

외부 tx 유무에 따라 동작이 달라지는 "기회주의적" 옵션. 단순 조회 메서드를 만들 때 호출자가 트랜잭션 안에 있으면 그걸 따르고, 아니면 그냥 실행하는 식의 유연성이 필요할 때 쓴다.

그런데 Javadoc에는 미묘한 함정 한 줄이 더 있다.

"For transaction managers with transaction synchronization, SUPPORTS is slightly different from no transaction at all, as it defines a transaction scope that synchronization will apply for. As a consequence, the same resources (JDBC Connection, Hibernate Session, etc) will be shared for the entire specified scope."

(트랜잭션 동기화를 지원하는 transaction manager에선, SUPPORTS는 트랜잭션 없는 상태와 약간 다르다. 동기화가 적용될 scope를 정의하기 때문에, 같은 자원(JDBC Connection, Hibernate Session 등)이 그 scope 내내 공유된다.)

즉 외부 tx가 없을 때도 "non-transactional이지만 connection은 공유되는" 상태가 된다. 미묘한 동작이라 어설프게 쓰면 헷갈린다. 실무에선 거의 안 쓰인다.

NOT_SUPPORTED — 트랜잭션 밖에서 실행

공식 정의:

"Execute non-transactionally, suspend the current transaction if one exists."

(트랜잭션 없이 실행하고, 외부 트랜잭션이 있으면 일시 중단한다.)

"이 작업은 트랜잭션 밖에서 돌아야 한다"고 명시할 때 쓴다. REQUIRES_NEW와 비슷하게 외부 tx를 suspend하지만, 새 트랜잭션을 만들지는 않는다는 차이.

쓰임새:

  • 트랜잭션 비용을 피하고 싶은 무거운 read-only 작업
  • 트랜잭션 안에서 실행되면 안 되는 외부 시스템 호출 (예: 메시지 발송, 외부 API)

단, REQUIRES_NEW와 같은 suspend 메커니즘을 쓰므로 외부 tx의 connection이 보관된다. Connection 부담은 동일.

MANDATORY — 외부 tx 없으면 예외

공식 정의:

"Support a current transaction, throw an exception if none exists."

(현재 트랜잭션이 있으면 지원하고, 없으면 예외를 던진다.)

"이 메서드는 반드시 외부 tx 안에서 호출되어야 한다"는 강제. 호출자에게 "당신이 트랜잭션을 시작했어야 한다"고 명시적으로 알리는 효과.

쓰임새: 라이브러리/프레임워크 내부 메서드에서, 호출자가 트랜잭션 컨텍스트 준비를 잊었을 때 즉시 실패시키고 싶을 때. 비즈니스 코드에선 잘 안 보인다.

NEVER — 외부 tx 있으면 예외

공식 정의:

"Execute non-transactionally, throw an exception if a transaction exists."

(트랜잭션 없이 실행하고, 트랜잭션이 존재하면 예외를 던진다.)

MANDATORY의 반대. "이 메서드는 트랜잭션 안에서 호출되면 안 된다"는 강제.

쓰임새: 트랜잭션 안에서 실행되면 정합성이 깨지거나 의도와 다른 동작을 하는 작업을 보호할 때. 실무에서 거의 보기 드물다.

실무에선 몇 개나 쓰는가

7가지를 다 알아야 면접 답변이 되지만, 실제 쓰임새는 솔직히 편차가 크다. 

REQUIRED       ★★★★★ — 디폴트, 거의 모든 케이스
REQUIRES_NEW   ★★☆☆☆ — 감사 로그/이력 등 분리 필요할 때
NESTED         ★☆☆☆☆ — JDBC 한정, 거의 안 씀
SUPPORTS       ★☆☆☆☆ — 미묘한 동작, 잘 안 씀
NOT_SUPPORTED  ★☆☆☆☆ — 트랜잭션 회피 케이스 한정
MANDATORY      ★☆☆☆☆ — 라이브러리 내부 강제용
NEVER          ☆☆☆☆☆ — 거의 보기 드뭄

현실적으로 90% 이상은 REQUIRED, 가끔 REQUIRES_NEW. 나머지 5개는 존재를 알아두는 정도면 충분하다.

선택 의사결정

어떤 상황에서 어떤 propagation을 쓸지 정리하면: 

이 메서드는 외부 tx에 합류해도 되는가?
  ├─ 예 → REQUIRED (디폴트)
  │       └─ 일부만 롤백 가능해야 하면 → NESTED (JDBC만)
  │
  └─ 아니, 분리되어야 함
     ├─ 항상 새 tx여야 함 → REQUIRES_NEW
     │   └─ 같은 row를 건드리는가? → 그러면 self-deadlock 위험,
     │      애초에 분리 자체를 재고
     │
     ├─ tx 자체가 필요 없는 작업 → NOT_SUPPORTED
     │
     ├─ 호출자가 외부 tx를 가지고 있어야만 함 → MANDATORY
     │
     └─ 호출자가 외부 tx 안에서 부르면 안 됨 → NEVER

실무 가이드:

  1. 일단 propagation 명시하지 말고 디폴트(REQUIRED)로 시작
  2. "내부 작업이 실패해도 외부는 살리고 싶다" 같은 명확한 요구가 생기면 그제야 REQUIRES_NEW 검토
  3. REQUIRES_NEW 검토할 땐 락 충돌 / connection pool 사이즈 / 진짜 독립이 필요한지 체크
  4. 나머지 5개는 정말로 그 동작이 필요할 때만

시리즈 정리

4편을 통해 본 핵심 정리:

  • 1편 — Propagation은 메서드 호출 중첩 시 트랜잭션을 어떻게 처리할지의 답. 7가지는 두 축(외부 tx 있을 때 / 없을 때)의 조합.
  • 2편 — REQUIRED는 logical/physical을 구분하기 때문에 catch해도 UnexpectedRollbackException이 터질 수 있음. 한번 마크된 rollback-only는 풀 수 없다.
  • 3편 — REQUIRES_NEW는 진짜 새 connection을 쓰지만, DB 락 라이프사이클이 Spring tx와 다르다는 점을 모르면 self-deadlock에 빠진다.
  • 4편 — NESTED는 JDBC 한정의 부분 롤백, SUPPORTS/NOT_SUPPORTED는 트랜잭션 유연성, MANDATORY/NEVER는 호출 컨텍스트 강제. 실무에선 REQUIRED 90%, REQUIRES_NEW 가끔, 나머지는 드물다.

Propagation은 알면 알수록 "디폴트로 두는 게 안전하다"는 결론에 가까워진다. 분리해야 할 명확한 이유가 있을 때만 손대는 것이 가장 안전한 사용법이다.
