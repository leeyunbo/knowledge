Propagation이 왜 있는가

@Transactional 두 개가 만났을 때 무슨 일이 생기나. 그리고 Spring이 7가지 답을 준비한 이유.

Series
@Transactional Propagation 7가지
  1. Propagation이 왜 있는가
  2. REQUIRED — 가장 흔하지만 가장 위험한 디폴트
  3. REQUIRES_NEW — 진짜 새 트랜잭션의 함정
  4. 나머지 5가지와 선택 가이드

트랜잭션은 메서드 단위가 아니다

@Transactional을 메서드에 붙이면 그 메서드는 트랜잭션 안에서 돈다. 여기까지는 다들 안다. 

@Transactional
public Order placeOrder(OrderRequest request) {
    Order order = orderRepository.save(...);
    paymentService.charge(order);
    return order;
}

placeOrder가 시작되면 트랜잭션이 열리고, 정상 종료되면 커밋, 예외가 던져지면 롤백. 단순하다.

문제는 paymentService.charge() 안에도 @Transactional이 있을 때 생긴다. 

@Service
public class PaymentService {

    @Transactional
    public void charge(Order order) {
        Payment payment = paymentRepository.save(...);
        externalGatewayClient.charge(...);
    }
}

placeOrder의 트랜잭션과 charge의 트랜잭션, 이 둘은 같은 트랜잭션인가, 다른 트랜잭션인가?

합쳐야 할 때, 분리해야 할 때

같은 트랜잭션이라면:

  • charge에서 예외가 나면 placeOrder가 했던 INSERT까지 같이 롤백
  • 둘이 한 단위로 묶인다. 깔끔하다.

다른 트랜잭션이라면:

  • charge는 자체 트랜잭션을 가지고, 끝나면 즉시 커밋
  • 그 후 placeOrder에서 무슨 일이 생겨도 charge의 결과는 살아있음
  • 결제는 성공했는데 주문은 실패하는 상황이 발생할 수 있음

비즈니스 요구에 따라 답이 다르다. 트랜잭션을 합쳐야 할 때도 있고, 분리해야 할 때도 있다. 예를 들어 감사 로그(audit log)는 본 작업이 롤백돼도 남기고 싶을 때가 많다. 그럼 audit는 분리된 트랜잭션이어야 한다.

그래서 Spring이 7가지 옵션을 만들었다

@Transactional(propagation = ...)로 이 동작을 지정한다. 7가지를 한 줄씩 정리하면: 

REQUIRED      외부 tx 있으면 합류, 없으면 새로 (디폴트)
REQUIRES_NEW  항상 새 tx, 외부 tx는 일시 중단
NESTED        외부 tx 안에 savepoint, 없으면 REQUIRED처럼
SUPPORTS      외부 tx 있으면 합류, 없으면 tx 없이
NOT_SUPPORTED 외부 tx 있으면 중단, 없으면 tx 없이
MANDATORY     외부 tx 있으면 합류, 없으면 예외
NEVER         외부 tx 있으면 예외, 없으면 tx 없이

7가지가 많아 보이지만, 모두 같은 두 가지 질문에 다른 조합으로 답할 뿐이다.

핵심 축은 두 개

각 propagation은 결국 두 질문에 답한다.

1) 외부 트랜잭션이 있을 때 어떻게 하나?

  • 합류한다 — REQUIRED, SUPPORTS, MANDATORY
  • 새로 만든다 — REQUIRES_NEW
  • savepoint를 만든다 — NESTED
  • 일시 중단한다 — NOT_SUPPORTED
  • 예외를 던진다 — NEVER

2) 외부 트랜잭션이 없을 때 어떻게 하나?

  • 새로 만든다 — REQUIRED, REQUIRES_NEW, NESTED
  • 트랜잭션 없이 실행한다 — SUPPORTS, NOT_SUPPORTED, NEVER
  • 예외를 던진다 — MANDATORY

이 두 축을 머리에 넣어두면 7가지가 외워지는 게 아니라 유도된다. 외부 tx에 대한 동작 5가지 × 외부 tx 없을 때 동작 3가지 중에서 의미 있는 조합을 추린 것이 7가지다.

physical transaction vs logical transaction

Spring 공식 문서는 의도적으로 두 개념을 구분한다. 이 구분이 다음 편의 핵심 함정과 직결되니 미리 잡아두자.

"Each such logical transaction scope can determine rollback-only status individually, with an outer transaction scope being logically independent from the inner transaction scope. In the case of standard PROPAGATION_REQUIRED behavior, all these scopes are mapped to the same physical transaction."

(각 logical transaction scope는 rollback-only 상태를 독립적으로 결정할 수 있고, 외부 scope는 내부 scope로부터 logical하게 독립적이다. REQUIRED의 경우 이 모든 scope가 같은 physical transaction에 매핑된다.)

풀어 쓰면:

  • Physical transaction — 진짜 DB 트랜잭션. BEGIN ~ COMMIT/ROLLBACK 한 사이클.
  • Logical transaction — @Transactional이 붙은 메서드 하나의 범위. 자신만의 rollback-only 플래그를 가짐.

REQUIRED로 합류하면 logical은 따로지만 physical은 하나다. REQUIRES_NEW면 logical도 physical도 새로 만든다.

이 구분이 왜 중요한가? 다음 편의 핵심 함정, "REQUIRED인데 catch했더니 UnexpectedRollbackException이 터지는" 현상이 바로 logical과 physical이 다르게 동작해서 생기는 일이다.

다음 편

다음 편에서는 디폴트인 REQUIRED를 깊게 본다. 합류 메커니즘, rollback-only 마킹, 그리고 catch했는데도 트랜잭션이 죽는 함정.
