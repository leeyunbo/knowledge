HTTP는 stateless다

HTTP의 가장 근본적인 설계 결정은 stateless. 매 요청이 독립적이며, 서버는 이전 요청을 기억해두지 않는다. RFC 9110 §3.4에서 "HTTP is a stateless protocol"이라고 명시되어 있다.

이 설계가 가지는 장점은 분명하다. 서버가 클라이언트의 상태를 들고 있지 않으니 어느 서버 인스턴스가 요청을 처리해도 같은 결과가 나온다. 이게 HTTP가 인터넷 규모로 확장 가능하게 만든 결정적 요인.

그런데 인증은 상태를 요구한다

현실 서비스는 stateless하지 않다. 사용자가 한 번 로그인했으면 그 다음 요청부터는 매번 ID/비밀번호를 다시 입력하지 않아도 본인임을 증명할 수 있어야 한다. 이건 명백히 "이 사용자가 누구인지"를 어딘가가 기억해야 한다는 요구.

stateless 프로토콜 위에서 stateful한 요구를 어떻게 풀 것인가. 이게 모든 웹 인증 메커니즘이 답하려는 같은 질문이다.

매 요청마다 신원 증명

답은 단순하다. 매 요청마다 클라이언트가 자기 신원을 증명하면 된다. 한 번 로그인 후 발급받은 무언가를 매 요청에 같이 보내고, 서버가 그걸 검증해 사용자를 식별. 이 "무언가"가 무엇인가에 따라 인증 방식이 갈린다.

방식 요청에 담는 것 서버가 하는 일
Basic 인증 매번 ID/비밀번호 (Base64) 매번 비밀번호 검증
Session 쿠키 Session ID 저장소에서 ID 조회 → 사용자 매핑
JWT (Bearer) 서명된 토큰 서명 검증 → 토큰 안의 클레임 사용
API Key 발급받은 키 키 검증 + 권한 매핑
OAuth 2.0 / OIDC Access Token 토큰 검증 (자체 서명 또는 인증 서버 조회)

가장 원시적인 게 Basic 인증 — 매 요청에 비밀번호 자체를 보낸다. 비밀번호가 자주 노출될 위험이 큰 만큼 보안적으로 약하고, 현대 웹에서 거의 쓰이지 않는다. 현실에서는 Session과 JWT가 가장 많이 쓰이는 두 패러다임. 이 시리즈의 주제.

두 가지 패러다임 — 어디에 상태를 둘 것인가

Session과 JWT는 결국 "stateful 정보를 어디에 둘 것인가"의 답이 다른 두 방식.

서버에 둔다 — Session

서버 측 저장소에 사용자 정보를 보관하고, 클라이언트에는 그 위치를 가리키는 짧은 키(Session ID)만 준다. 매 요청마다 클라이언트가 키를 보내고, 서버는 키로 저장소를 조회해 사용자를 알아낸다.

서버 측 상태가 권위적인 진실. 로그아웃이나 권한 변경이 즉각 반영되고, 클라이언트는 가벼운 키만 들고 있으면 된다. 단점은 서버가 상태를 들고 있어야 한다는 것 — 분산 환경에서 추가 작업이 필요.

토큰 자체에 둔다 — JWT

모든 사용자 정보를 토큰 안에 인코딩하고 서명을 붙여 발급한다. 매 요청마다 클라이언트가 그 토큰을 보내고, 서버는 서명만 검증하면 토큰 안의 정보를 그대로 신뢰할 수 있다.

서버는 어떤 상태도 저장할 필요가 없다 — stateless 그 자체. 단점은 토큰이 발급된 후엔 서버가 그 내용을 즉시 무효화하기 어렵다는 것. 이 미묘함이 4편의 주제.

인증과 인가의 구분

용어 혼동이 자주 일어나는 부분. 두 단어가 영어로도 비슷하다 (Authentication vs Authorization).

  • 인증 (Authentication) — 사용자가 "누구인가"를 확인. 로그인, 신원 증명.
  • 인가 (Authorization) — 그 사용자가 "무엇을 할 수 있는가"를 결정. 권한 부여.

Session과 JWT는 1차적으로 인증의 도구지만 토큰/세션에 권한 정보를 함께 담아 인가까지 처리하는 게 일반적. 예를 들어 JWT의 클레임에 "role: admin"을 넣으면 그 토큰을 가진 사용자가 admin임을 같이 알 수 있다.

HTTP의 어디에 담아 보내나

신원을 매 요청마다 보낸다고 했는데, HTTP의 어디에 담는가. 기본적으로 두 자리가 표준이다.

Cookie 헤더 (Session 위주)

GET /api/orders HTTP/1.1
Host: example.com
Cookie: JSESSIONID=abc123def456; theme=dark

쿠키는 브라우저가 자동으로 같은 도메인 요청에 첨부해주는 헤더. Session ID를 쿠키에 두면 브라우저가 자동으로 보내고, JavaScript에서 따로 신경 쓸 필요 없다. HttpOnly 플래그로 JavaScript 접근을 막을 수 있어 XSS 공격에서 토큰 탈취를 줄일 수 있다.

Authorization 헤더 (Bearer 토큰)

GET /api/orders HTTP/1.1
Host: example.com
Authorization: Bearer eyJhbGciOiJIUzI1NiIs...

모바일 앱이나 SPA에서 자주 쓰이는 방식. Authorization: Bearer <token> 형식이 표준. 쿠키와 달리 클라이언트 코드가 명시적으로 헤더를 붙여야 한다. JavaScript가 토큰을 다룰 수 있어야 하므로 보통 localStorage 또는 메모리에 저장 (XSS 노출 위험 존재).

두 자리의 차이

측면CookieAuthorization Bearer
전송브라우저 자동클라이언트 명시적
저장브라우저 쿠키 저장소localStorage / 메모리 / 보안 storage
JavaScript 접근HttpOnly로 차단 가능늘 가능 (XSS 위험)
CSRF 위험높음 (자동 첨부)낮음 (명시적)
CORS 처리credentials: include 필요일반 헤더로 가능
주 사용처전통 웹, SessionSPA, 모바일, JWT

어느 자리가 더 안전한지는 단순하지 않다. Cookie + HttpOnly + SameSite는 XSS에 강하고 CSRF 방어 추가 필요. Bearer 토큰은 CSRF엔 무관하지만 XSS로 토큰이 탈취되기 쉽다. 트레이드오프 관계.

이 시리즈가 풀어갈 질문들

면접 단골 질문

Q. HTTP가 stateless인데 왜 로그인이 유지되나?

HTTP 자체는 stateless이지만 매 요청마다 클라이언트가 자기 신원을 증명할 수 있는 무언가를 보낸다. Session ID 쿠키, JWT, API Key 등이 그 역할. 서버는 매 요청을 독립적으로 처리하지만, 클라이언트가 들고 다니는 토큰으로 사용자를 식별.

Q. 인증과 인가의 차이?

인증(Authentication)은 사용자가 누구인지 확인하는 과정 — 로그인, 신원 증명. 인가(Authorization)는 인증된 사용자가 무엇을 할 수 있는지 결정 — 권한 부여, 접근 제어. 영어로도 비슷해 헷갈리기 쉽지만 별개의 단계.

Q. Cookie와 Authorization 헤더 중 무엇이 더 안전?

단순 비교는 어렵다. Cookie + HttpOnly + Secure + SameSite는 XSS에 강하지만 CSRF 방어 별도 필요. Authorization Bearer는 CSRF엔 무관하지만 JavaScript에서 접근 가능하므로 XSS로 탈취되기 쉽다. 어떤 위협이 더 큰지에 따라 선택. 일반적으로 전통 웹은 Cookie + Session, SPA/모바일은 Bearer + JWT.

Q. 분산 환경에서 인증의 어려움은?

Session 방식은 서버가 상태를 들고 있어 여러 인스턴스 간 공유 또는 sticky session이 필요. JWT 방식은 토큰 자체에 정보가 담겨 stateless라 분산이 쉽지만, 즉시 무효화가 어렵다. 이 트레이드오프가 다음 편들의 핵심 주제.

한 줄 정리

HTTP는 stateless이지만 인증은 상태를 요구한다. 그 상태를 어디에 둘지가 인증 방식의 분기점. 서버에 두면 Session, 토큰 자체에 두면 JWT. 매 요청마다 클라이언트가 신원을 증명하는 것이 공통 패턴이고, Cookie와 Authorization Bearer가 그 통로의 두 표준.
