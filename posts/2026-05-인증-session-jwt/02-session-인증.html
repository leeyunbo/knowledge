Session 인증의 흐름

전통적인 Session 인증은 단순한 두 단계 흐름으로 동작한다. 로그인 시점에 서버가 세션을 만들고, 이후 요청마다 클라이언트가 그 세션을 가리키는 짧은 ID를 함께 보내는 식.

단계별 동작

  1. 클라이언트가 ID/비밀번호로 로그인 요청
  2. 서버가 사용자 검증 후 새 Session 객체 생성, 저장소에 저장
  3. 응답에 Set-Cookie: JSESSIONID=... 헤더 포함
  4. 이후 요청부터 브라우저가 자동으로 같은 쿠키 첨부
  5. 서버가 쿠키의 ID로 저장소 조회해 사용자 정보 획득
  6. 그 정보로 요청 처리 후 응답

Session 객체에는 보통 사용자 ID, 권한, 마지막 활동 시각, 사용자 환경설정 같은 정보가 들어간다. 저장소는 메모리, DB, 또는 Redis 같은 캐시.

Session ID의 보안 요건

Session ID는 사용자를 대신하는 인증 토큰이므로 다음 요건을 만족해야 한다.

  • 예측 불가 — 충분한 엔트로피를 가진 무작위 값. 보통 128bit 이상.
  • 만료 — 일정 시간 후 또는 일정 비활성 시간 후 자동 무효화.
  • HttpOnly — JavaScript에서 접근 불가 (XSS로 탈취 방지).
  • Secure — HTTPS 통신에서만 전송 (네트워크 도청 방지).
  • SameSite — Cross-site 요청에 첨부되지 않음 (CSRF 방어).

Spring Boot는 기본 설정으로 이 대부분을 적용한다. server.servlet.session.cookie 하위 설정으로 명시 가능.

Spring에서의 Session

@PostMapping("/login")
public String login(@RequestParam String id, @RequestParam String password,
                    HttpSession session) {
    User user = authService.authenticate(id, password);
    session.setAttribute("user", user);
    return "redirect:/home";
}

@GetMapping("/api/me")
public User me(HttpSession session) {
    return (User) session.getAttribute("user");
}

HttpSession 추상화로 Spring이 세션 처리를 감춘다. setAttribute로 데이터 저장하고 getAttribute로 꺼낸다. 쿠키 발급, ID 생성, 저장소 관리는 모두 자동.

분산 환경의 도전 — 서버가 여러 대일 때

로컬 메모리에 세션을 저장하는 단일 서버 시절엔 위 패턴이 단순했다. 하지만 트래픽이 늘어 여러 서버 인스턴스로 scale-out하면 문제가 생긴다.

한 서버에 로그인했는데 다음 요청이 LB에 의해 다른 서버로 라우팅되면, 그 서버는 해당 Session ID를 모르므로 인증 실패. 사용자가 갑자기 로그아웃당한 것처럼 보인다.

분산 환경의 해법 세 가지

1. Sticky Session — 같은 사용자는 같은 서버로

Load Balancer가 클라이언트 IP나 쿠키 기반으로 같은 사용자의 요청을 항상 같은 서버에 라우팅. LB의 hash 또는 cookie-based persistence 기능을 사용.

장점은 단순함. 기존 로컬 메모리 세션 코드를 거의 그대로 두고 LB 설정만 바꾸면 된다. 단점은 부하 분산이 비효율적이고 (특정 서버에 트래픽 집중 가능), 서버 한 대가 다운되면 그 서버의 모든 사용자가 로그아웃당한다. 확장성 면에서 한계가 분명한 임시 해결책에 가깝다.

2. Session Clustering — 서버 간 세션 동기화

모든 서버가 자기 메모리에 모든 세션을 들고 있고, 변경이 일어나면 다른 서버로 복제. 전통적으로 Tomcat의 DeltaManager나 Hazelcast, Apache Ignite 같은 분산 캐시가 사용됐다.

어느 서버가 요청을 받든 세션을 알 수 있다는 게 장점. 하지만 동기화 트래픽이 서버 수에 따라 제곱으로 늘어 확장성이 나쁘다. 서버 수가 많아지면 동기화 비용이 본업을 방해할 정도가 된다. 현대에서 거의 쓰이지 않는 방식.

3. 외부 저장소 — Redis 등

가장 흔히 쓰이는 현대적 답안. 모든 서버가 외부의 Redis(또는 다른 빠른 저장소)에 세션을 저장하고 조회. Spring Session 라이브러리가 이 패턴을 추상화해준다. 

spring:
  session:
    store-type: redis
  data:
    redis:
      host: redis.internal
      port: 6379

이 한 줄 설정으로 HttpSession의 모든 동작이 Redis에 저장된다. 애플리케이션 코드는 그대로, 인프라만 바꾸는 셈. 서버 인스턴스가 늘어도 모두 같은 Redis를 보면 되니 확장성 좋고, 서버 한 대가 죽어도 사용자가 영향받지 않는다.

단점은 Redis가 추가 의존성이 된다는 것. Redis 다운 시 인증 자체가 마비되므로 HA 구성과 모니터링이 필수. 매 요청마다 Redis 조회가 일어나 latency도 약간 추가된다.

Session의 비용 — 트레이드오프

Session 인증의 본질적 비용은 "서버가 상태를 들고 있어야 한다"는 데서 온다.

  • 저장소 비용 — 동시 접속 사용자 수만큼 메모리 또는 Redis 키.
  • 조회 비용 — 매 요청마다 저장소 조회. Redis 0.1~1ms 수준이지만 0은 아니다.
  • 분산 복잡도 — 위에서 본 sticky / clustering / 외부 저장소 중 하나를 선택해야 함.
  • 스케일 한계 — Redis 한 대가 처리할 수 있는 RPS에 한계. 더 늘리려면 Redis 클러스터 등.

반대로 얻는 것은 강력한 통제력. 로그아웃이 즉시 반영되고, 권한 변경이 즉시 다음 요청에 적용되며, 세션 무효화가 단순하다. 이게 다음 편들에서 볼 JWT의 약점이다.

면접 단골 질문

Q. Session 인증의 동작 흐름?

로그인 시 서버가 사용자 정보를 저장소에 저장하고 그 ID를 쿠키로 응답. 이후 요청마다 브라우저가 쿠키를 자동 첨부하고, 서버는 ID로 저장소를 조회해 사용자 식별. 서버 측에 상태가 있다는 게 핵심.

Q. Session 쿠키의 보안 옵션?

HttpOnly (JavaScript 접근 차단), Secure (HTTPS 전용), SameSite (CSRF 방어). 이 셋을 모두 적용하는 게 표준. Spring Boot 기본 설정에서 대부분 자동 적용.

Q. Sticky Session의 한계?

부하가 균일하게 분산되지 않고, 서버 한 대가 다운되면 그 서버의 사용자들이 모두 로그아웃당한다. 서버 수가 많아지면 한 서버에 과부하가 몰릴 수도. 임시 해결책 정도로 쓰이고 본격 분산엔 부적합.

Q. Spring Session + Redis 패턴은?

Spring Session 라이브러리가 HttpSession의 동작을 Redis로 위임하도록 만든 것. 애플리케이션 코드는 기존과 동일하고 인프라만 외부화한 셈. 확장성과 가용성이 좋아 현대 분산 환경의 표준 답안. 단, Redis 다운 시 인증 마비되므로 HA 구성이 필수.

한 줄 정리

Session 인증은 서버가 상태를 들고 있는 전통적 방식. 단일 서버에서는 단순하지만 분산 환경으로 가면 추가 작업이 필요. 현대 표준은 외부 저장소(Redis) + Spring Session 같은 추상화로 stateless에 가깝게 운영. 강력한 통제력이 장점이고, 저장소 의존이 단점.

다음 편은 정반대 방향 — 토큰 자체에 정보를 넣어 서버를 stateless로 만드는 JWT의 구조.
