Session vs JWT + Refresh Token

두 방식의 정확한 비교와 의사결정 가이드. 그리고 둘의 단점을 균형 잡는 Refresh Token 패턴까지.

의사결정 가이드

어느 쪽을 쓸지는 서비스의 특성과 요구사항에 따라 갈린다. 결정에 도움이 되는 기준들.

Session이 적합한 경우

  • 전통 웹 애플리케이션 (서버 렌더링 위주)
  • 로그아웃이나 권한 변경의 즉시성이 중요
  • 관리자 도구 등 보안이 매우 중요한 환경
  • 토큰 크기를 작게 유지하고 싶을 때
  • 이미 Redis 인프라가 있고 추가 부담이 적을 때

JWT가 적합한 경우

  • SPA, 모바일 앱과의 API 통신
  • 여러 마이크로서비스가 같은 인증을 공유
  • OAuth 2.0 / OIDC 표준을 따라야 할 때
  • 외부 저장소를 두기 어려운 환경 (서버리스 등)
  • 인증 서버와 자원 서버가 분리되어 있을 때 (RS256으로 공개 키 검증)

혼합 패턴

실무에서 자주 쓰이는 절충안. 같은 서비스 안에서도 통로별로 다른 방식을 쓴다.

  • 웹 페이지 (서버 렌더링) — Session 쿠키
  • API (SPA, 모바일) — JWT Bearer
  • 둘 다 같은 사용자 DB를 공유하므로 인증의 진실은 한 곳

Refresh Token 패턴 — JWT 함정의 균형

4편에서 본 JWT의 무효화 어려움을 완화하는 표준 패턴. 짧은 만료의 Access Token과 긴 만료의 Refresh Token을 분리해 사용한다.

두 토큰의 역할

측면Access TokenRefresh Token
용도매 API 요청에 사용새 Access Token 발급용
만료5~15분 (짧게)7일~30일 (길게)
사용 빈도매 요청Access Token 만료 시에만
저장 위치메모리 또는 localStorageHttpOnly Secure 쿠키 권장
JWT 형태JWT (클레임 포함)JWT 또는 단순 식별자
탈취 영향짧은 시간만 유효큰 영향 (재발급 가능)

흐름

  1. 로그인 시 서버가 Access(짧음) + Refresh(긺) 두 토큰 발급
  2. 클라이언트는 매 API 요청에 Access 토큰 사용
  3. Access 만료되면 Refresh 토큰으로 /refresh 호출
  4. 서버가 Refresh 검증 후 새 Access 토큰 발급
  5. 로그아웃 시 Refresh 토큰을 서버에서 폐기 → 더 이상 갱신 불가

왜 이 패턴이 균형을 잡나

  • Access 탈취 영향 최소화 — 15분 안에 자연 만료
  • 매 요청마다 Refresh를 보내지 않으므로 노출 빈도 낮음
  • Refresh를 서버 저장소에 두면 즉시 무효화 가능 → 사실상 로그아웃 강제 가능
  • 사용자는 7~30일 동안 자동 로그인 유지 — UX 좋음

순수 JWT의 stateless 매력이 일부 사라지지만(Refresh를 저장소에 두므로) 그 대가로 무효화 가능성을 얻는다. 매 요청은 stateless 검증, 가끔의 갱신만 서버 조회 — 합리적 균형.

Refresh Token Rotation

더 강한 보안을 위한 진화 패턴. Refresh를 한 번 쓰면 새 Refresh를 함께 발급하고 옛 Refresh는 무효. 

처음 발급:  Access1 + Refresh1
갱신 1회:   Access2 + Refresh2  (Refresh1 무효)
갱신 2회:   Access3 + Refresh3  (Refresh2 무효)
...

왜 회전이 안전한가

Refresh가 탈취되어 공격자가 갱신 시도를 하면, 정상 사용자가 다음 갱신을 할 때 옛 Refresh가 이미 무효라 갱신 실패. 이 시점에 "내 Refresh가 누군가에게 탈취되었다"는 신호가 명확히 드러난다. 서버가 그 시점에 모든 토큰 폐기 등 강한 대응 가능.

OAuth 2.0의 Refresh Token Rotation 권장 사항이고, Auth0/Okta 같은 IdP가 기본 제공. 단, 동시 요청에서 미묘한 race condition이 있어 짧은 grace period(예: 30초)를 두는 게 일반적.

Refresh Token의 보호

Refresh가 Access보다 더 중요한 보안 자산이다. 다음 보호 수단을 모두 적용한다.

  • HttpOnly + Secure + SameSite Cookie — JavaScript 접근 차단, HTTPS 전용, CSRF 방어
  • 서버 측 저장 — Redis 등에 Refresh의 jti를 저장. 폐기 시 즉시 제거
  • Rotation — 위에서 본 회전 패턴
  • 이상 감지 — IP 변경, User-Agent 변경 등에 대해 추가 인증 요구
  • 로그아웃 시 즉시 폐기 — Access는 자연 만료를 기다리지만 Refresh는 즉시 무효화

실무 선택 가이드

상황별 실용적 답을 정리.

상황권장
전통 웹 (서버 렌더링) Session + Redis
SPA + Spring Boot 단일 백엔드 Session 또는 JWT (Access + Refresh) 둘 다 무난
모바일 앱 + REST API JWT (Access + Refresh)
마이크로서비스 (여러 자원 서버) JWT RS256 (인증 서버 발급, 자원 서버 공개 키 검증)
관리자 도구 (보안 critical) Session + 짧은 만료

서버리스 (Lambda 등) JWT (저장소 의존 최소화)

두 방식 모두 잘하는 것

어느 쪽을 선택하든 인증의 기본기는 동일하다.

  • HTTPS 필수 — HTTP에서는 토큰이 그대로 노출됨
  • 비밀번호는 강력한 해시(bcrypt, Argon2)로 저장
  • Brute-force 방어 (rate limiting, CAPTCHA)
  • 로그인 실패 횟수 제한과 임계 시 계정 잠금
  • 비밀번호 변경 시 모든 토큰/세션 무효화
  • 로그아웃 시 토큰/세션 즉시 폐기
  • 중요 작업(결제, 비밀번호 변경)에 추가 인증(2FA, 비밀번호 재확인)

이런 기본을 무시하고 토큰 방식만 잘 골라봐야 의미가 없다. 반대로 기본기를 잘 갖추면 Session이든 JWT든 합리적으로 운영 가능.

면접 단골 질문

Q. Session과 JWT 중 무엇을 쓸까?

상황에 따라. 전통 웹과 즉시 무효화가 중요하면 Session, SPA/모바일/마이크로서비스 환경이면 JWT. 단일 서비스 SPA + Spring Boot면 어느 쪽이든 무난. OAuth/SSO 표준이 필요하면 JWT가 사실상 강제. 절대적 답은 없고 트레이드오프 이해가 핵심.

Q. Refresh Token이 왜 필요한가?

JWT 무효화 어려움을 완화하기 위해. Access Token을 짧게 두면 탈취 영향이 짧은 시간으로 제한되고, 긴 Refresh Token으로 갱신해 사용자는 자동 로그인 유지. Refresh를 서버에 저장하면 즉시 무효화도 가능. 보안과 UX의 균형.

Q. Refresh Token Rotation의 장점?

Refresh를 한 번 쓰면 새 Refresh를 발급하고 옛 것을 무효화. 탈취된 Refresh를 공격자가 사용하면 정상 사용자가 다음 갱신할 때 옛 토큰이 이미 무효라 갱신 실패 — 탈취 자체를 감지하는 신호. OAuth 2.0 권장 사항이고 Auth0 등 IdP가 기본 제공.

Q. Access Token은 어디에 저장?

정답은 없지만 트레이드오프가 있다. 메모리(JS 변수)는 새로고침 시 사라져 안전하지만 UX 손해. localStorage는 편리하지만 XSS로 탈취 가능. HttpOnly 쿠키는 XSS에 강하지만 CSRF 방어 추가 필요. 가장 보수적인 답은 Access는 메모리, Refresh는 HttpOnly 쿠키.

한 줄 정리

Session은 서버 측 상태로 강한 통제를 얻고, JWT는 stateless로 분산 친화성을 얻는다. 어느 쪽을 쓸지는 서비스 특성에 달렸지만, JWT를 쓴다면 Refresh Token 패턴이 사실상 표준. Access는 짧게 + Refresh는 긴 만료 + Rotation + HttpOnly 쿠키 보호 — 이 조합이 모던 인증의 표준 형태.
