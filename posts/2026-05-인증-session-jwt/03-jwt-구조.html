JWT의 구조

세 부분으로 분할된 토큰. Base64로 인코딩된 메타데이터와 클레임, 그리고 그것이 위조되지 않았음을 증명하는 서명. 그 안을 정확히 들여다본다.

JWT는 무엇인가

JSON Web Token. RFC 7519에 명세된 토큰 형식. 서버가 클라이언트에 발급한 정보를 클라이언트가 보관하고 매 요청에 보내며, 서버는 그 토큰의 서명만 검증해 내용을 신뢰할 수 있는 구조.

핵심 성질은 self-contained. 토큰 자체에 사용자 정보가 들어 있고 서명으로 위조 방지가 보장되므로, 서버가 별도의 저장소를 두지 않아도 된다. 이게 Session과의 가장 큰 차이.

세 부분으로 나뉜 토큰

JWT는 점(.)으로 구분된 세 부분으로 구성된다. 

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0IiwibmFtZSI6IkFsaWNlIiwiZXhwIjoxNzM5OTk5OTk5fQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c

이걸 점으로 자르면 세 토막이 나온다.

  1. Header — 토큰의 메타데이터 (서명 알고리즘 등)
  2. Payload — 실제 데이터 (claims)
  3. Signature — 위조 방지를 위한 서명

앞 두 부분은 Base64URL로 인코딩된 JSON. 누구나 디코딩해 내용을 볼 수 있다. 마지막 서명만 비밀 키로 만들어진 서명이라 위조가 어렵다.

Header

{
  "alg": "HS256",
  "typ": "JWT"
}

서명에 사용된 알고리즘(alg)과 토큰 타입(typ)을 명시. HS256은 HMAC-SHA256, RS256은 RSA-SHA256, ES256은 ECDSA. JSON을 그대로 Base64URL로 인코딩한 것이 첫 번째 토막.

Payload — 클레임의 모음

토큰이 담고 있는 정보의 본체. JSON 객체이며 각 필드를 "claim"이라고 부른다. RFC 7519는 표준 클레임을 정의하지만, 사용자 정의 클레임도 자유롭게 추가할 수 있다. 

{
  "sub": "1234567890",
  "name": "Alice",
  "role": "admin",
  "iat": 1739900000,
  "exp": 1739999999,
  "iss": "auth.example.com"
}

표준 클레임 (RFC 7519)

자주 쓰이는 표준 클레임들. 모두 3글자로 짧게 정의된 것이 특징 (토큰 크기 절약).

클레임이름의미
issIssuer토큰 발급자 (예: 인증 서버 URL)
subSubject토큰의 주체 (보통 사용자 ID)
audAudience토큰의 대상 (어떤 서비스에서 쓸 토큰인지)
expExpiration만료 시각 (Unix timestamp)
nbfNot Before이 시각 이전엔 무효 (지연 활성화)
iatIssued At발급 시각
jtiJWT ID토큰 고유 식별자 (재사용 방지에 사용)

사용자 정의 클레임

표준 클레임 외에 자유롭게 추가 가능. 일반적으로 사용자 ID, 역할, 권한, 이메일 등을 넣는다. 

{
  "sub": "1234",
  "email": "alice@example.com",
  "role": "admin",
  "permissions": ["read:orders", "write:orders"],
  "exp": 1739999999
}

단, 클레임이 많아질수록 토큰 크기가 커진다. 매 요청마다 토큰이 함께 전송되므로 너무 크면 네트워크 부담. 또한 Payload는 누구나 디코딩할 수 있으니 비밀번호 같은 민감 정보는 절대 넣지 않는다.

Signature — 위조 방지의 핵심

JWT의 진짜 핵심. Header와 Payload가 위조되지 않았음을 보장하는 부분. 서명 계산 방법은 alg에 따라 다르지만 기본 형태는 다음과 같다. 

signature = HMAC-SHA256(
  base64url(header) + "." + base64url(payload),
  secret
)

서버는 비밀 키를 알고 있어야 같은 서명을 다시 만들 수 있다. 누군가 Header나 Payload를 수정하면 서명이 달라지므로 서버가 즉시 위조를 감지할 수 있다. 비밀 키 없이는 정상 서명을 만들 수 없는 게 보안의 토대.

대칭 키 vs 비대칭 키

구분HS256 (HMAC)RS256 (RSA)
키 종류대칭 (비밀 키 1개)비대칭 (비밀 키 + 공개 키)
서명 가능자비밀 키 가진 모두비밀 키 가진 사람만
검증 가능자비밀 키 가진 모두공개 키 가진 모두 (제한 없음)
키 배포비밀이라 어려움공개 키 자유롭게 배포
속도빠름느림 (RSA 연산)
적합 케이스단일 서비스 내부인증 서버 + 여러 자원 서버

단일 서비스가 자기 토큰을 발급하고 검증하면 HS256이 단순하고 빠르다. OAuth/OIDC처럼 인증 서버와 자원 서버가 분리된 환경에서는 RS256이 적합 — 자원 서버는 공개 키만 가지고 검증할 수 있다.

전체 구조 그림

JWT는 암호화가 아니다

가장 자주 오해되는 부분. JWT는 암호화가 아니라 서명이다. Header와 Payload는 단순히 Base64URL로 인코딩된 JSON일 뿐, 누구나 디코딩해 볼 수 있다. 서명이 보장하는 것은 "위조되지 않았음"이지 "비밀임"이 아니다.

따라서 비밀번호, 신용카드 번호, 주민번호 같은 민감 정보를 Payload에 넣으면 안 된다. 이런 정보가 필요하면 별도로 암호화된 채널로 다루거나, JWE(JSON Web Encryption)를 사용 (이건 흔하지 않음). 평범한 JWT는 인증/인가 정보 정도만 담는 게 맞다.

Spring Security에서 JWT 발급

@Service
public class JwtService {

    private final SecretKey key;

    public JwtService(@Value("${jwt.secret}") String secret) {
        this.key = Keys.hmacShaKeyFor(secret.getBytes());
    }

    public String issue(User user) {
        return Jwts.builder()
            .subject(String.valueOf(user.getId()))
            .claim("role", user.getRole())
            .issuedAt(new Date())
            .expiration(new Date(System.currentTimeMillis() + 3600_000))
            .signWith(key)
            .compact();
    }

    public Claims parse(String token) {
        return Jwts.parser()
            .verifyWith(key)
            .build()
            .parseSignedClaims(token)
            .getPayload();
    }
}

jjwt 라이브러리 기준 코드. 발급은 builder 패턴으로 클레임을 채우고 서명. 검증은 같은 키로 parser를 만들어 서명 일치를 확인하고 클레임을 추출. 서명이 일치하지 않거나 만료(exp)가 지났으면 예외가 발생한다.

JWT 검증의 흐름

서버가 토큰을 받았을 때 무엇을 해야 하는가. 정확한 검증 순서는 다음과 같다.

  1. 토큰 형식 확인 — 점으로 구분된 세 부분이 맞는지
  2. Header 디코딩 — alg 확인 (지원하는 알고리즘인지, none 등 위험한 값 거부)
  3. Signature 검증 — 같은 키로 다시 만든 서명과 일치하는지
  4. Expiration 확인 — exp가 현재 시각보다 큰지 (만료 안 됐는지)
  5. iss, aud 등 다른 클레임 정책 확인 (선택)
  6. 모두 통과하면 클레임을 신뢰하고 사용자 식별

Spring Security나 jjwt 같은 라이브러리는 이 검증을 모두 자동으로 처리한다. 개발자는 적절히 설정만 하면 된다. 단, 라이브러리 버전이 옛날이거나 잘못된 옵션을 쓰면 4편에서 볼 함정에 걸릴 수 있다.

면접 단골 질문

Q. JWT의 세 부분은?

Header, Payload, Signature. 점(.)으로 구분되며 모두 Base64URL 인코딩. Header는 알고리즘 등 메타데이터, Payload는 클레임(사용자 정보), Signature는 위조 방지를 위한 서명. 앞 두 부분은 누구나 디코딩 가능하고, 서명만 비밀 키로 검증된다.

Q. JWT는 암호화되어 있나?

아니다. 서명만 되어 있고 내용은 Base64URL로 단순 인코딩된 JSON. 누구나 디코딩해 클레임을 볼 수 있다. 서명이 보장하는 건 "위조되지 않았음"이지 "비밀임"이 아니다. 민감 정보를 Payload에 넣으면 안 되는 이유.

Q. HS256과 RS256의 차이?

HS256은 대칭 키 HMAC. 단일 비밀 키로 서명/검증 모두 가능. 단일 서비스 내부에 적합. RS256은 비대칭 키 RSA. 비밀 키로 서명, 공개 키로 검증. 인증 서버가 발급하고 여러 자원 서버가 공개 키로 검증하는 구조에 적합 — OAuth/OIDC 표준.

Q. exp 클레임이 없으면?

토큰이 영원히 유효해진다. 한 번 발급된 토큰을 무효화할 방법이 없으므로 보안상 매우 위험. 반드시 exp를 설정하고, 추가로 짧은 만료 + Refresh Token 패턴을 쓰는 게 표준 (5편 주제).

한 줄 정리

JWT는 Header.Payload.Signature 세 부분으로 된 self-contained 토큰. 앞 두 부분은 Base64URL 인코딩된 JSON이고 누구나 볼 수 있다. 서명만 비밀 키로 위조 방지를 보장. 비밀번호 같은 민감 정보는 Payload에 넣지 않는다 — 암호화가 아닌 서명이기 때문. 단일 서비스엔 HS256, OAuth 같은 분산 환경엔 RS256이 적합.

다음 편은 JWT의 함정들 — 토큰 무효화의 어려움, alg=none 같은 보안 공격, 그리고 토큰 크기 문제.
