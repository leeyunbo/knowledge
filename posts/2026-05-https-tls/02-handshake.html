왜 handshake가 필요한가

TLS 통신이 시작되려면 양쪽이 합의해야 할 게 많아요.

  • 어떤 TLS 버전을 쓸지
  • 어떤 암호 알고리즘 모음(cipher suite)을 쓸지
  • 서버를 어떻게 인증할지 (인증서 검증)
  • 대칭키 암호화에 쓸 공통 비밀 키를 어떻게 만들지 (ECDHE)
  • 각 사이드의 ephemeral 키 교환

이걸 다 하는 게 handshake예요. TLS 1.2는 보통 2-RTT, TLS 1.3은 1-RTT로 줄였어요. 0-RTT 재연결도 가능해요.

TLS 1.3의 1-RTT handshake

TLS 1.3 기준으로 흐름을 보면 이래요.

단계별로 정리하면 이래요.

  1. ClientHello: 클라이언트가 자기가 지원하는 TLS 버전, cipher suite 목록, 자기 ECDHE 공개 키 후보(key share), SNI(어느 도메인에 접속하는지) 등을 보내요.
  2. ServerHello: 서버가 cipher suite를 골라서 회신하고, 자기 ECDHE 공개 키를 보내요. 같은 메시지에 Certificate(서버 인증서)와 그 인증서의 비밀 키로 서명한 CertificateVerify, 마지막으로 Finished까지 묶어 보내요.
  3. Client → Finished: 클라이언트가 서버 인증서를 검증하고, 자기 쪽 ECDHE 비밀 키를 사용해 공통 비밀(master secret)을 계산해요. ChangeCipherSpec(이제 암호화 통신 시작)과 Finished를 보내요.
  4. 이제 양쪽이 같은 공통 비밀을 가졌고, 대칭키 암호화로 Application Data(HTTP 요청/응답)를 주고받아요.

포인트는 클라이언트가 ClientHello에 key share를 미리 포함해 보낸다는 거예요. 서버는 그걸 받자마자 자기 ECDHE 키와 합쳐서 공통 비밀을 만들 수 있어요. 그래서 별도 키 교환 라운드가 필요 없고 1-RTT로 끝나요.

TLS 1.2의 2-RTT

TLS 1.2는 cipher suite 협상과 키 교환이 분리돼 있었어요.

  1. ClientHello: 지원 버전·cipher suite 목록. (key share 없음)
  2. ServerHello + Certificate + ServerKeyExchange + ServerHelloDone: 서버가 cipher suite 고름, 인증서 보냄, 자기 ECDHE 공개 키 보냄.
  3. ClientKeyExchange + ChangeCipherSpec + Finished: 클라이언트가 자기 ECDHE 공개 키 보냄, 암호화 시작.
  4. ServerFinished: 서버가 마지막 확인.

실제 데이터를 보내려면 ClientHello → ServerHelloDone(1 RTT) → ClientFinished/ServerFinished(2 RTT) 다음이에요. RTT가 100ms면 200ms를 그냥 handshake에 써요. TLS 1.3은 이걸 절반으로 줄였어요.

0-RTT: 재연결 때 데이터까지 같이

TLS 1.3은 한 번 연결한 적 있는 서버에는 0-RTT로 재연결할 수 있어요. PSK(pre-shared key)를 이전 세션에서 받아두고, 다음 연결의 ClientHello에 PSK로 암호화한 초기 데이터(early data)를 함께 보내요. 서버는 첫 패킷에서 PSK를 확인하면 즉시 응답을 시작해요.

RTT가 0이라는 건 첫 패킷에 HTTP 요청까지 같이 실어 보낼 수 있다는 의미예요. 모바일에서 사이트 재방문 속도가 눈에 띄게 빨라지는 이유 중 하나예요.

다만 0-RTT 데이터는 재전송 공격에 취약해요. 도청자가 그 패킷을 그대로 다시 보내면 서버는 또 처리해요. 그래서 멱등 요청(GET 같은)만 0-RTT로 보내고, 결제 같은 비멱등 요청은 풀 handshake 뒤에 보내는 게 표준이에요.

Cipher Suite 읽는 법

cipher suite 이름은 처음 보면 외계어 같아요. TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256 같은 거. 분해하면 이래요.

위치역할예시
TLS_프로토콜 식별TLS
키 교환공통 비밀 만드는 방법ECDHE, RSA, DH
인증서 종류서버 인증 알고리즘RSA, ECDSA
WITH_구분자WITH
대칭키 알고리즘본문 암호화AES_128_GCM, CHACHA20_POLY1305
해시handshake 메시지 무결성SHA256, SHA384

TLS 1.3에서는 더 간단해졌어요. cipher suite가 키 교환·인증서 부분과 분리돼서 TLS_AES_128_GCM_SHA256처럼 5개만 남아요. 키 교환과 서명은 별도로 협상해요.

SNI: 가상호스팅의 필수 조각

한 IP에 여러 도메인이 호스팅되는 경우(거의 모든 클라우드 환경) 서버는 클라이언트가 어느 도메인의 인증서를 원하는지 알아야 해요. ClientHello에 평문으로 SNI(Server Name Indication)가 들어가요. "지금 api.example.com으로 접속하는 거야"를 알려주는 거예요.

SNI는 평문이라 도청자가 어떤 도메인에 접속 중인지 알 수 있어요. 프라이버시 문제. ESNI나 ECH(Encrypted Client Hello)로 이걸 암호화하는 표준이 진행 중이에요.
