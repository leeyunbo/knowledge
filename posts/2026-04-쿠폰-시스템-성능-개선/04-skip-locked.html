SKIP LOCKED이 뭘까?

SELECT ... FOR UPDATE는 조회한 행에 쓰기 락을 걸어두는 구문이다. 근데 여기 옵션을 두 개 더 붙일 수 있다.

구문동작
FOR UPDATE 락이 걸린 행이면 대기한다 (기본 동작)
FOR UPDATE NOWAIT 락이 걸려 있으면 즉시 예외
FOR UPDATE SKIP LOCKED 락이 걸린 행은 건너뛰고 다음 행을 찾는다

우리가 원하던 게 정확히 이거였다. 락이 걸린 앞쪽 행은 버리고 다음 AVAILABLE 행을 가져가는 동작.

SKIP LOCKED 동작
스레드 A → 1번 행 잡음
스레드 B → 1번 잠겨있으니 skip, 2번 행 잡음
스레드 C → 1, 2 skip, 3번 행 잡음
...
대기 없음. 각자 다른 행을 바로 들고간다.

쿼리 바꾸기

문제는 UPDATE ... FOR UPDATE SKIP LOCKED는 문법 오류다. FOR UPDATE는 SELECT 전용 구문이기 때문이다.

그래서 두 단계로 분리했다.

  1. SELECT ... FOR UPDATE SKIP LOCKED로 AVAILABLE 행 하나 확보하고 락 건다
  2. 그 행의 status를 TAKEN으로 바꾼다 (dirty checking으로 UPDATE)
public interface CouponStockRepository extends JpaRepository<CouponStock, Long> {

    @Query(value = "SELECT * FROM coupon_stock " +
                   "WHERE coupon_id = :couponId AND status = 'AVAILABLE' " +
                   "LIMIT 1 FOR UPDATE SKIP LOCKED",
           nativeQuery = true)
    Optional<CouponStock> findAvailableStock(@Param("couponId") Long couponId);
}

서비스 쪽은 이렇게. 

CouponStock stock = couponStockRepository.findAvailableStock(couponId)
    .orElseThrow(() -> new CouponException("Out of stock"));
stock.taken();  // dirty checking으로 UPDATE가 커밋 시점에 반영됨

CouponStock 엔티티에 상태 전이 메서드만 추가. 

public void taken() {
    this.status = StockStatus.TAKEN;
}

테스트 결과

총 시간: 5690ms / 성공: 259 / 실패: 41
70 → 259. 15초 제한을 다 쓰던 테스트가 5.7초 만에 끝난다. 처리량 3배 이상 증가.

진짜 어이없었다. 한 줄 바꾼 건데 판이 뒤집혔다.

왜 이렇게 극적으로 바뀌는가

앞선 편들이 전부 직렬화 지점 하나를 붙들고 있었다. 쿼리를 줄이고 캐시를 넣어봤자 쿠폰 UPDATE가 한 줄로 서 있으면 소용없는 구조였다.

SKIP LOCKED는 이 직렬화를 원천적으로 없앤다. 스레드들이 서로 다른 행을 가져가니까 기다릴 일이 없다. 실제로 병렬이다. 암달의 법칙에서 말하는 "직렬 구간 자체를 없애는" 해결이다.

실무에서 어디 쓰이나

SKIP LOCKED를 찾아보니 실무에서 생각보다 많이 쓰이는 패턴이었다. 대표적인 게 작업 큐(Job Queue). 

-- 워커 여러 대가 "처리할 작업 하나 가져와"
SELECT * FROM jobs WHERE status = 'PENDING'
LIMIT 1 FOR UPDATE SKIP LOCKED

워커 10대가 동시에 이 쿼리를 날려도 각자 다른 작업을 가져간다. 대기 없이, 중복 없이. DB를 메시지 큐 비슷하게 쓰는 패턴이다.

지원 DB는 이렇다.

  • PostgreSQL 9.5+
  • MySQL 8.0+ (5.7에는 없음)
  • Oracle
  • H2 2.1+

41개는 왜 실패했나

259개는 성공했는데 41개는 실패했다. 목표는 300건 전부였으니 아직 목표 미달이다. 로그 찍어보니 역시 커넥션 타임아웃. 트랜잭션 안에 남아있는 다른 쿼리들(user 락, existsBy, save, dirty checking)이 차지하는 시간이 누적되면서 뒤쪽 스레드들이 3초 안에 커넥션을 못 얻은 거였다.

300개 전부 통과시키려면 user 락 제거나 트랜잭션 분리 같은 추가 작업이 필요하다. 근데 거기서부터는 이 시스템의 근본적인 설계를 바꾸는 영역으로 들어간다. 오늘은 여기까지.

정리

쿼리 한 줄로 성능이 5배 뛴다는 건, 거꾸로 말하면 잘못된 쿼리 한 줄이 5배의 손해를 만들고 있었다는 뜻이기도 하다.

UPDATE ... LIMIT 1로 Lock Sharding을 하려고 했던 2편 구현은 "행을 쪼갰으니 당연히 잘 되겠지"라는 가정에 기대고 있었다. 실제로는 쿼리 실행 방식이 직렬화 경로를 타고 있었다. DB가 쿼리를 어떻게 실행하는가를 알아야 한다는 교훈.

마지막 편에서는 이 시리즈에서 얻은 것들을 CS 관점으로 정리한다.
