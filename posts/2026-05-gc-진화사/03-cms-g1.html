Concurrent가 들어왔다 — CMS

Concurrent Mark Sweep. 2002년 Java 1.4에서 도입돼 Java 8까지 latency 중시 환경의 표준이었던 GC. 핵심 아이디어는 Old GC의 일부 단계를 application 스레드와 동시에(concurrent) 진행하는 것. 이렇게 하면 STW 시간이 극적으로 줄어든다.

CMS의 Old GC는 4단계로 진행되고 그중 마킹의 큰 부분과 sweep 단계가 concurrent로 동작한다.

CMS Old GC의 단계

  1. Initial Mark — STW. GC root에서 직접 도달 가능한 객체만 마킹. 매우 짧음.
  2. Concurrent Mark — application과 함께 도는 단계. root에서 시작해 모든 reachable 객체를 마킹.
  3. Remark — STW. concurrent mark 도중 변경된 참조를 보정. 짧은 시간.
  4. Concurrent Sweep — application과 함께 도는 단계. 마킹되지 않은 객체를 free list에 등록.

STW 시간은 1단계와 3단계뿐. 둘 다 매우 짧아 사용자가 거의 느끼지 못한다. 전체 GC 시간은 Parallel보다 더 걸리지만, application이 그 동안 돌고 있으니 latency 관점에서는 큰 진전.

CMS의 한계

좋은 아이디어였지만 CMS는 결국 Java 9에서 deprecate되고 Java 14에서 제거된다. 이유는 여러 가지.

  • 단편화 — Mark & Sweep 기반이라 1편에서 본 단편화 문제가 그대로 남는다. 결국 fallback으로 Full GC가 필요한데 이건 Serial이라 매우 길다.
  • Concurrent Mode Failure — concurrent sweep이 끝나기 전에 Old가 가득 차면 Full GC로 떨어짐. 이게 발생하면 수 초 이상의 STW.
  • Floating Garbage — concurrent mark 도중 죽은 객체는 다음 GC를 기다려야 함. 메모리 효율 손해.
  • 구현 복잡도 — 코드가 복잡해 유지보수 부담이 컸고, G1의 등장으로 자연스러운 후계 구도가 만들어짐.

G1 — Region 기반의 새 출발

Garbage-First Collector. Java 7에서 도입돼 Java 9부터 server JVM 기본 GC. 이름의 "Garbage-First"는 garbage가 가장 많은 region을 우선 청소한다는 전략에서 나왔다.

가장 큰 변화는 Heap의 구조 자체. Young/Old를 통째 한 덩어리로 두던 기존 모델과 달리, Heap을 균일한 크기의 region 수백~수천 개로 잘게 나눈다 (기본 region 크기는 Heap 크기에 따라 1MB~32MB). 각 region은 그때그때 Young (Eden 또는 Survivor), Old, 또는 Humongous(거대 객체용) 중 하나의 역할을 맡는다.

왜 Region인가

Region 단위로 잘게 쪼개면 부분 청소가 가능해진다. Heap 전체를 한 번에 청소하지 않고 garbage가 가장 많은 region 몇 개만 골라 청소하면 한 번의 GC가 짧게 끝난다. 이게 "Garbage-First" 이름의 출처.

또한 region이 작은 단위라 evacuation(살아있는 객체를 다른 region으로 복사)이 빠르고, 이 과정에서 자연스럽게 단편화도 해소된다 — Mark-Compact의 효과를 region 단위로 얻는 셈.

G1의 GC 단계

기본 골격은 CMS와 비슷하다 (concurrent 마킹 + STW 단계 혼합). 하지만 청소 대상을 region으로 한정해 STW를 예측 가능한 짧은 시간으로 유지한다.

  1. Young GC — STW. Young region(Eden + Survivor)을 청소. 살아남은 객체는 빈 Survivor 또는 Old region으로 복사.
  2. Concurrent Marking — application과 함께 도는 단계. 전체 Heap에서 살아있는 객체를 마킹.
  3. Mixed GC — STW. Young region + garbage 비율이 높은 Old region 일부를 동시에 청소. 살아있는 객체를 다른 region으로 evacuate.

Mixed GC가 G1의 핵심 아이디어. Old를 한 번에 다 청소하지 않고 매 GC마다 가장 garbage 비율이 높은 region 몇 개만 골라 처리. 한 번의 GC 시간을 작게 유지하면서 점진적으로 Old를 정리한다.

Pause Time Goal

G1의 또 다른 차별점은 사용자가 STW 목표 시간을 명시할 수 있다는 것. 

java -XX:+UseG1GC -XX:MaxGCPauseMillis=200 MyApp

위 옵션은 한 번의 GC가 200ms 이내에 끝나도록 G1이 알아서 청소할 region 수를 조절한다. 물리적으로 보장되지는 않지만(목표일 뿐), G1은 통계를 학습해 목표에 근접하도록 동작한다. 기존 GC들은 "이번 GC가 얼마나 걸릴지"가 Heap 크기와 객체 수에 좌우됐다면, G1은 시간 예산 안에서 동작하는 GC.

Remembered Set과 Card Table

Region 단위로 부분 청소하려면 한 가지 어려움이 생긴다. Region A의 GC를 하려면 다른 region들에서 region A의 객체를 가리키는 참조를 모두 알아야 한다. 그렇지 않으면 살아있는 객체를 죽은 것으로 오판할 위험이 있다.

G1은 각 region마다 Remembered Set (RSet)이라는 자료구조를 두고 "이 region의 객체를 가리키는 외부 참조"를 추적한다. 참조가 새로 만들어지면 write barrier가 발동해 RSet을 갱신. 이 비용이 G1의 throughput overhead 중 가장 큰 부분이며, application 코드의 모든 참조 쓰기에 약간의 추가 비용을 부과한다.

활성화 옵션

java -XX:+UseG1GC -XX:MaxGCPauseMillis=200 -XX:G1HeapRegionSize=16m MyApp

Java 9부터 server JVM 기본 GC라 명시 안 해도 G1이 활성화된다. Heap이 4GB 이상이면 G1, 그 이하면 Parallel이 합리적인 디폴트.

면접 단골 질문

Q. CMS의 핵심 아이디어와 한계는?

핵심은 Old GC의 마킹과 sweep 단계를 application과 동시에(concurrent) 도는 것 — STW 시간을 극적으로 줄임. 하지만 Mark & Sweep 기반이라 단편화가 누적되고, concurrent mode failure 시 매우 긴 Full GC로 떨어지는 함정이 있다. Java 14에서 제거.

Q. G1의 Region 기반 설계가 가지는 의미?

Heap을 균일한 region 격자로 나눠 부분 청소를 가능하게 한다. Garbage가 가장 많은 region 몇 개만 매번 청소하므로 한 번의 GC가 짧게 끝나고, evacuation 과정에서 단편화가 자연스럽게 해소된다. CMS의 두 한계를 동시에 푼 설계.

Q. MaxGCPauseMillis는 어떤 옵션인가?

G1에 한 번의 GC가 끝나야 할 목표 시간을 알려주는 옵션. G1은 통계를 학습해 그 목표 안에서 청소할 region 수를 조절한다. 물리적 보장이 아닌 "best-effort" 목표지만 일반적으로 잘 작동한다. Heap이 매우 크거나 GC 부담이 큰 워크로드에선 목표 달성이 어려울 수 있다.

Q. Remembered Set이 왜 필요한가?

Region 단위로 부분 청소를 하려면 그 region의 객체를 가리키는 외부 참조를 모두 알아야 한다. 전체 Heap을 매번 스캔하지 않으려고 각 region이 자기를 가리키는 참조 목록을 RSet으로 유지하고, 참조 쓰기마다 write barrier로 RSet을 갱신한다. 이게 G1의 throughput overhead 중 가장 큰 부분.

한 줄 정리

CMS는 GC에 concurrent라는 개념을 처음 들여온 GC. STW 단축에 크게 기여했지만 단편화와 fallback 비용으로 좌초. G1은 그 자리를 이어받아 Heap을 region 격자로 재설계해 부분 청소를 가능하게 했고, 사용자가 STW 목표 시간을 명시할 수 있게 했다. Java 9부터 server JVM 기본이고, 대부분의 일반 워크로드에 무난한 선택.

하지만 G1도 ms 단위 STW는 여전히 존재한다. 응답 시간이 진짜 critical한 환경 — 결제, 트레이딩, 실시간 게임 — 에서는 그 정도도 부담. 그래서 STW를 거의 ms 한 자릿수로 끌어내린 다음 세대 GC가 등장한다. ZGC와 Shenandoah가 다음 편의 주제.
