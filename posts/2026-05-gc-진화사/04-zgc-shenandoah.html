G1로도 부족한 영역

G1은 대부분의 워크로드에서 충분히 좋다. 그러나 한 번의 STW가 수십~수백 ms 단위로 발생할 수 있고, Heap 크기가 클수록 그 시간도 비례해서 늘어난다. 평범한 웹 서버는 이 정도면 사용자가 거의 못 느끼지만, 실시간 트레이딩, 결제 게이트웨이, 게임 서버, 큰 캐시 같은 워크로드에서는 그 ms도 부담스럽다.

그래서 다음 세대 GC가 노린 목표는 한 가지다. Heap 크기와 관계없이 STW를 ms 한 자릿수로 일정하게 유지. 이 목표를 달성한 두 GC가 ZGC와 Shenandoah.

ZGC — Oracle의 답안

Z Garbage Collector. Java 11에서 experimental로 도입돼 Java 15에서 production-ready 선언. 이름의 "Z"는 정해진 의미가 없다고 공식 자료에 나와있다 (Z 다음의 무언가를 암시하는 듯).

핵심 아이디어 — Colored Pointer

ZGC의 가장 독창적인 부분. 64bit 주소 공간 중 일부 비트를 "메타데이터"로 활용한다. 객체의 실제 주소를 위한 비트와 GC 상태 표시용 메타데이터 비트가 한 포인터 안에 함께 인코딩된다. 메타데이터 비트는 Marked0, Marked1, Remapped, Finalizable 같은 GC 단계 상태를 표현하고, 이 비트들을 합쳐 "color"라고 부른다.

왜 색을 칠하나. GC가 어떤 객체를 옮기거나 마킹할 때 그 정보를 객체 자체나 별도 자료구조에 기록하는 대신 그 객체를 가리키는 포인터에 색을 칠한다. 포인터를 따라가는 모든 코드가 그 색을 보고 GC 진행 상태에 따라 반응할 수 있게 된다.

Load Barrier

Colored Pointer를 활용하기 위한 메커니즘. 모든 객체 참조 읽기에 작은 검사 코드(load barrier)가 삽입된다. 참조를 읽을 때마다 그 포인터의 색을 보고 GC가 어떤 단계인지 확인하고, 필요하면 즉석에서 보정 작업을 수행한다.

예를 들어 GC가 객체 A를 다른 위치로 옮기는 중에 application 스레드가 A를 가리키는 참조를 읽으려 한다면, load barrier가 색을 보고 "이 참조는 옛 주소를 가리키고 있다"고 판단해 새 주소로 자동 갱신한다. application 스레드는 GC 진행 상황을 의식하지 않고 코드를 진행할 수 있다.

이 덕분에 ZGC의 거의 모든 작업이 application과 함께(concurrent) 도는 것이 가능해진다. STW가 필요한 단계는 GC root 스캔뿐이고, 그것도 millisecond 한 자릿수로 끝난다.

ZGC의 단계

  1. Pause Mark Start — STW. GC root에서 직접 도달 가능한 객체만 마킹. 매우 짧음 (~1ms).
  2. Concurrent Mark/Remap — application과 동시. 전체 객체 그래프를 마킹하고, 옮겨진 객체의 참조를 갱신.
  3. Pause Mark End — STW. 마킹 마무리. 매우 짧음.
  4. Concurrent Prepare for Relocation — application과 동시. 어느 region을 비울지 결정.
  5. Pause Relocate Start — STW. 재배치 시작 신호. 매우 짧음.
  6. Concurrent Relocate — application과 동시. 살아있는 객체를 새 region으로 옮김. Load barrier가 동시 접근을 처리.

STW는 세 차례뿐이고 모두 root scan만 하므로 객체 수와 무관하게 짧다. 이게 ZGC가 자랑하는 "Heap 크기와 관계없이 ms 단위 STW"의 비결.

활성화 옵션

java -XX:+UseZGC MyApp

Generational ZGC

초기 ZGC는 Young/Old 구분 없이 단일 generation으로 동작했다. 이는 구현 단순성과 ms 단위 STW 보장에는 좋았지만, 처리량 면에서 G1보다 다소 떨어졌다. Java 21에서 Generational ZGC가 도입되어 Young/Old 구분을 다시 들여왔다. 

java -XX:+UseZGC -XX:+ZGenerational MyApp

처리량이 개선되면서도 ms 단위 STW를 유지한다. Java 24에서는 non-generational 모드가 제거되어(JEP 490), Generational ZGC가 ZGC의 유일한 동작이 된다.

Shenandoah — Red Hat의 답안

Red Hat이 OpenJDK에 기여한 GC. 2014년 시작돼 OpenJDK 12에서 production-ready. ZGC와 비슷한 시기에 비슷한 목표를 추구한 GC이지만 다른 메커니즘으로 접근한다.

핵심 아이디어 — Brooks Pointer (Forwarding Pointer)

Shenandoah의 무기는 모든 객체에 추가된 작은 forwarding pointer. 모든 객체 헤더에 "이 객체의 현재 위치"를 가리키는 포인터가 한 자리 마련된다. 평소엔 자기 자신을 가리키지만, 객체가 옮겨지면 새 위치를 가리키도록 갱신된다.

모든 객체 접근은 이 forwarding pointer를 한 번 거쳐 이뤄진다. GC가 객체를 옮기는 도중에 application이 그 객체를 읽으려 하면 forwarding pointer가 새 위치로 가이드해주는 식. 이 비용 덕에 모든 작업이 concurrent로 동작 가능해진다.

활성화 옵션

java -XX:+UseShenandoahGC MyApp

둘은 매우 비슷한 목표를 비슷한 결과로 달성하지만 메커니즘이 다르다. ZGC는 포인터에 메타데이터를 심는 영리한 트릭으로, Shenandoah는 객체에 forwarding pointer를 두는 더 직관적인 방식으로 같은 목표에 도달한다.

어느 쪽을 쓸지는 환경에 따른다. Oracle JDK라면 ZGC가 더 친숙하고, OpenJDK 위주의 Linux 환경이면 Shenandoah도 좋은 선택. 어떤 GC도 STW를 거의 사라진 수준으로 만든다는 점에선 동일.

"Sub-millisecond GC"의 새 정의

Java 21의 ZGC는 STW를 평균 1ms 이하로 유지한다. Heap이 1GB든 1TB든 STW 시간은 거의 변하지 않는다 — 이게 가장 큰 진화점. Heap 크기에 비례해 GC 시간이 늘던 G1까지의 패러다임을 깬 것.

그럼 왜 모두 ZGC를 쓰지 않는가

Latency를 위해 약간의 throughput을 내준다. ZGC와 Shenandoah는 G1 대비 ~5~15% 정도의 처리량 손해를 본다. 모든 참조 읽기에 load barrier 또는 forwarding pointer 우회 비용이 있기 때문.

그래서 선택은 워크로드 특성에 따른다. 처리량이 우선인 배치 작업 — 처리량 GC (Parallel). 균형이 필요한 일반 웹 서버 — G1. Latency가 critical한 실시간 시스템 — ZGC 또는 Shenandoah. 이게 모던 GC 선택의 큰 그림.

면접 단골 질문

Q. ZGC의 핵심 메커니즘은?

Colored Pointer와 Load Barrier. 64bit 주소 공간의 일부 비트를 GC 메타데이터(색)로 활용해 포인터 자체에 GC 진행 상태를 표시한다. 모든 객체 참조 읽기에 삽입된 load barrier가 그 색을 보고 필요한 보정 작업을 수행. 덕분에 거의 모든 GC 작업이 application과 동시에 진행된다.

Q. ZGC와 Shenandoah는 어떤 차이?

목표는 같다 — STW를 Heap 크기와 무관하게 ms 한 자릿수로. 메커니즘이 다르다. ZGC는 포인터에 메타데이터를 심고, Shenandoah는 모든 객체에 forwarding pointer를 두어 객체 이동을 처리한다. 성능과 결과는 거의 비슷. 운영 환경(JDK 종류, OS)에 따라 더 친숙한 쪽을 선택한다.

Q. 왜 모든 워크로드에 ZGC를 안 쓰나?

처리량 손해 때문. ZGC는 모든 참조 읽기에 load barrier가 들어가므로 G1 대비 5-15% 처리량 감소가 있다. Latency가 critical하지 않은 워크로드(배치, 처리량 위주 서비스)에서는 그 손해가 아쉽다. 균형 잡힌 일반 웹 서비스에는 G1이 여전히 무난한 선택.

Q. ZGC가 Heap 크기에 거의 영향받지 않는 이유?

STW가 필요한 단계가 GC root scan뿐이고 그건 객체 수가 아닌 root 수에 비례한다. Heap이 커도 root 수는 비슷하니 STW 시간이 거의 일정. 마킹과 재배치는 모두 concurrent라 application 응답 시간에 영향이 미미하다.

한 줄 정리

ZGC와 Shenandoah는 STW를 사실상 사라진 수준(ms 한 자릿수)으로 끌어내린 GC. ZGC는 포인터에 색을 칠하는 영리한 트릭으로, Shenandoah는 forwarding pointer로 같은 목표에 도달한다. 처리량 ~10% 손해라는 비용을 받아들이면 Heap 크기와 관계없이 일정한 짧은 STW를 얻는다. 실시간 응답이 critical한 워크로드의 표준 선택지.

여기까지가 GC 알고리즘의 진화. 마지막 편은 실전 — 어떤 GC를 언제 쓰고, 어떻게 모니터링하고, 어떤 함정을 피할지.
