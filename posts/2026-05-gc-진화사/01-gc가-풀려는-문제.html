GC가 풀려는 문제

어떤 객체를 살리고 어떤 객체를 죽일지 정하는 일. 그리고 죽은 자리를 어떻게 다시 쓸 만하게 만들지의 선택. 모든 GC 알고리즘이 이 두 질문에 답한다.

왜 GC인가

C나 C++의 세계에서 메모리 관리는 개발자의 책임이다. malloc으로 잡은 메모리는 free로 직접 풀어야 하고, 이걸 잊으면 메모리 누수, 두 번 풀면 use-after-free. 큰 코드베이스에서 누가 언제 객체를 마지막으로 쓰는지 추적하는 일은 일종의 정신 노동이고 C 시절의 보안 취약점 상당수가 여기서 나왔다.

GC는 이 책임을 런타임이 떠안겠다는 결정이다. 개발자는 new로 객체를 만들기만 하고, 누가 더 이상 그 객체를 참조하지 않게 되면 런타임이 알아서 회수한다. 자바, C#, Go, Python 등 거의 모든 모던 언어의 표준 모델.

대신 두 가지 비용을 치른다. 회수 작업이 일어나는 동안 발생하는 일시적 멈춤 (pause time), 그리고 항상 살아있는 객체와 죽은 객체를 구별해야 하는 추적 비용 (overhead). GC 알고리즘의 진화는 이 두 비용을 어떻게 줄일 것인가에 대한 30년의 답안지다.

"살아있는 객체"의 정의 — Reachability

누가 살았고 누가 죽었는지 어떻게 판단하나. 가장 단순한 답은 "참조하는 사람이 한 명도 없는 객체는 죽었다"이지만, 모든 모던 GC는 이보다 한 단계 더 나아가 도달 가능성(reachability)을 본다.

출발점은 GC roots. 자바에서 GC root에 해당하는 것은 다음 네 종류다.

  • 실행 중인 모든 스레드의 JVM Stack 안 로컬 변수와 매개변수
  • 모든 클래스의 static 필드
  • JNI를 통해 native 코드가 들고 있는 참조
  • 현재 동기화 락을 잡고 있는 객체 (synchronized 모니터)

GC는 이 root들을 출발점으로 객체 그래프를 탐색해 "도달 가능한" 객체를 모두 살아있는 것으로 간주한다. 한 번도 도달되지 않은 객체는 죽었다고 판단해 회수. 참조 카운트만 보면 안 되는 이유는 사이클(cycle) 때문이다 — A가 B를 참조하고 B가 A를 참조하면 외부 참조가 없어도 둘 다 카운트가 1이라 죽지 않는다. Reachability 기반은 이 함정을 자연스럽게 푼다.

Tracing GC의 두 단계 — Mark & Sweep

가장 기초가 되는 GC 알고리즘. 1960년 John McCarthy가 LISP을 위해 처음 제안했고, 이후 거의 모든 GC가 이 골격 위에서 변형된다.

Mark — 살아있는 것에 표시

GC root에서 출발해 도달 가능한 모든 객체를 그래프 탐색(BFS 또는 DFS)으로 방문하며 각 객체에 "살아있음" 비트를 기록한다. 객체 헤더의 Mark Word(synchronized 시리즈에서 본 그것)에 GC 마킹 비트가 한 자리 마련되어 있다.

Sweep — 표시되지 않은 것 제거

Heap 전체를 처음부터 끝까지 훑으며 마킹되지 않은 객체의 메모리를 회수해 free list에 등록. 마킹된 객체의 비트는 다음 GC를 위해 초기화된다.

Mark & Sweep의 한계 — 단편화

살아있는 객체와 죽은 객체가 뒤섞여 있다가 죽은 객체만 제거되면 Heap이 마치 빈 자리가 군데군데 뚫린 치즈처럼 된다 — 이게 메모리 단편화(fragmentation). 전체 빈 공간의 합은 충분한데 연속된 큰 공간이 없어 큰 객체 할당이 실패할 수 있다.

Mark-Compact — 단편화의 해결

Sweep 단계 대신 살아있는 객체를 한쪽 끝으로 모아버리는 방식. 빈 자리는 자연스럽게 다른 한쪽에 큰 덩어리로 남고, 다음 객체 할당은 그 끝부터 차례로 채우면 된다.

단점은 객체를 실제로 옮겨야 한다는 것. 옮기는 비용 + 옮긴 객체를 가리키는 모든 참조를 갱신하는 비용이 Mark & Sweep보다 무겁다. Old Generation의 GC가 보통 이 알고리즘을 쓴다 — Old는 자주 일어나지 않으니 한 번 일어날 때 깊게 정리하는 편이 낫기 때문.

Copying — 단편화 없이 빠르게

공간을 둘로 나눠 절반(From space)에서 살아있는 객체만 다른 절반(To space)으로 통째로 복사하고, From 전체를 한 번에 비우는 방식. 살아있는 객체만 만지므로 Mark & Sweep보다 빠르고, 복사 후엔 단편화도 없다.

하지만 Heap의 절반은 항상 비어있어야 하므로 메모리 효율이 50%. Young Generation의 Eden + Survivor 구조가 정확히 이 알고리즘을 변형한 것. Eden + 사용 중인 Survivor에서 살아남은 객체를 빈 다른 Survivor로 복사하고, 나머지는 통째로 비운다. "대부분의 객체는 곧 죽는다"는 가설이 맞을 때 Copying은 매우 효율적이다.

세 알고리즘의 비교

알고리즘 장점 단점 주요 사용처
Mark & Sweep 단순. 객체 이동 없음. 단편화 발생. 오래된 GC, CMS의 Old GC
Mark-Compact 단편화 없음. 객체 이동 + 참조 갱신 비용. 대부분의 Old GC (Serial, Parallel, G1 mixed)
Copying 빠름. 단편화 없음. 메모리 효율 50%. Young GC (Eden + Survivor)

왜 Stop-the-World가 필요한가

위의 알고리즘들이 정확히 동작하려면 GC 도중 객체 그래프가 변하지 않아야 한다. GC 스레드가 마킹 중인데 다른 스레드가 새 참조를 만들거나 기존 참조를 끊어버리면 결과가 깨진다. 그래서 가장 안전한 방법은 GC 동작 중 모든 application 스레드를 잠시 멈추는 것 — Stop-the-World (STW).

STW가 짧으면 사용자가 못 느끼지만, Heap이 크고 객체가 많으면 수백 ms~수 초까지 갈 수 있다. 웹 서버에서 갑자기 응답이 멈추는 현상의 흔한 원인. 현대 GC의 진화는 결국 "이 STW를 어떻게 줄이거나 없앨 것인가"의 답안.

Serial과 Parallel은 STW에 정직하게 의존하고, CMS와 G1은 일부 단계만 application 스레드와 함께(concurrent) 진행한다. ZGC와 Shenandoah는 거의 모든 단계를 concurrent로 만들어 사실상 사라진 STW에 도달한다. 다음 편들에서 한 단계씩 본다.

면접 단골 질문

Q. GC는 살아있는 객체를 어떻게 판별하나?

참조 카운트가 아닌 도달 가능성(reachability)을 본다. GC root(스택 로컬, static 필드, JNI 참조, 락 보유 객체)에서 출발해 그래프 탐색으로 도달 가능한 객체를 살아있는 것으로 간주. 참조 카운트만 보면 사이클을 이루는 객체들이 외부 참조 없이도 죽지 않는 함정에 걸린다.

Q. Mark & Sweep의 한계는?

단편화. 살아있는 객체와 죽은 객체가 뒤섞인 상태에서 죽은 것만 제거되면 Heap이 군데군데 빈 자리로 깨진다. 자유 공간의 합은 충분한데 연속된 큰 공간이 없어 큰 객체 할당이 실패할 수 있다. 이를 해결하려고 등장한 것이 Mark-Compact와 Copying.

Q. Young GC가 Copying인 이유?

Young은 "대부분의 객체가 곧 죽는다"는 가설이 강하게 성립하는 영역. Copying은 살아있는 객체만 만지므로 죽은 객체가 많을수록 빠르다. 단편화 없이 깔끔하게 정리되는 것도 장점. 메모리 효율 50% 단점은 Young 영역이 작은 비중(전체 Heap의 1/3)이라 큰 부담은 아니다.

Q. Stop-the-World가 왜 필요한가?

GC 알고리즘이 정확히 동작하려면 객체 그래프가 변하지 않아야 한다. GC 도중 application 스레드가 참조를 바꾸면 마킹 결과가 깨질 수 있어, 가장 안전하고 단순한 방법으로 모든 application 스레드를 일시 정지시키는 것. 현대 GC의 진화는 이 STW를 줄이거나 없애는 방향이다.

한 줄 정리

GC는 두 가지 질문에 답한다. "어떤 객체가 살아있나" 와 "죽은 자리를 어떻게 다시 쓸 만하게 만드나". 첫 질문은 GC root에서 출발하는 도달 가능성으로, 두 번째 질문은 Mark & Sweep / Mark-Compact / Copying 세 알고리즘의 변형으로 해결된다. 그 과정에서 발생하는 Stop-the-World가 실무 GC 튜닝의 핵심 비용.

다음 편은 가장 오래된 두 GC — Serial과 Parallel. STW에 정직하게 의존하면서도 멀티코어를 활용하기 시작한 단계.
