핫 키와 LongAdder, False Sharing

ConcurrentHashMap이 만능이 아닌 자리. 핫 키 시나리오에서 35배 차이가 나는 이유, 그리고 그 아래 하드웨어 레벨 함정까지.

핫 키 시나리오 — 한 키에 트래픽 몰림

페이지 방문 카운터를 만든다고 해볼게요. 3편에서 본 merge 패턴이에요. 

private final ConcurrentHashMap<String, Long> pageViews = new ConcurrentHashMap<>();

public void trackVisit(String pageUrl) {
    pageViews.merge(pageUrl, 1L, Long::sum);
}

단순하고 정확해요. 그런데 한 페이지(예: /home)에 트래픽이 몰리면 문제가 생겨요. 그 페이지의 키를 다루는 모든 스레드가 같은 버킷의 락을 다투게 되거든요.

2편에서 본 ConcurrentHashMap의 비밀은 "버킷 단위 락"이었어요. 다른 버킷은 동시 처리 가능. 그런데 같은 버킷, 같은 키면 결국 한 번에 한 스레드만 통과해요. 이게 핫 키 직렬화의 본질이에요.

실측 — 16 스레드의 한 키 동시 갱신

이 차이가 얼마나 큰지 직접 측정해봤어요. 16 스레드가 각각 5백만번 increment 하는 시나리오예요.

패턴처리 시간처리량 (ops/sec)상대 속도
CHM.merge(Long::sum) 3,492 ms 약 22.9M 1.0x (기준)
CHM<K, LongAdder>.increment() 98 ms 약 816M 35.6x

같은 작업인데 35배 차이. 이 격차가 어디서 오는지가 이 편의 핵심이에요.

두 패턴의 동작 차이

merge — 버킷 락 안에서 read-modify-write

merge 호출 시 ConcurrentHashMap 내부 동작을 펼쳐보면 이래요. 

synchronized (f) {  // f = 버킷 head
    Long oldVal = node.val;
    Long newVal = remappingFunction.apply(oldVal, value);  // Long::sum
    node.val = newVal;
}

16 스레드가 같은 버킷의 락을 차례로 잡고 통과해요. 1000개 요청이면 1000번 직렬화. 여기에 추가 비용이 두 가지 더 있어요.

  • Boxing: Long은 immutable이라 Long::sum 호출마다 새 Long 객체 할당. GC 압박
  • 버킷 lookup도 락 안에서: 락을 잡은 채로 체인 traverse

CHM<K, LongAdder> — 락 없는 lookup + 분산 increment

private final ConcurrentHashMap<String, LongAdder> counts = new ConcurrentHashMap<>();

public void increment(String key) {
    counts.computeIfAbsent(key, k -> new LongAdder()).increment();
}

핵심 통찰. computeIfAbsent는 키가 이미 존재하면 락을 안 잡아요. ConcurrentHashMap 소스의 fast-path를 보면 명확해요. 

public V computeIfAbsent(K key, Function<...> mappingFunction) {
    int h = spread(key.hashCode());
    for (Node<K,V>[] tab = table;;) {
        // ...
        else if (f.hash >= 0 && f.key.equals(key) && f.val != null)
            return f.val;  // ★ 키 매칭되면 락 없이 즉시 반환
        else {
            synchronized (f) { ... }  // 키 없거나 충돌 시에만
        }
    }
}

이미 등록된 LongAdder를 가져오는 건 tabAt의 volatile read 한 번이에요. 락 없음. 그 다음 increment()는 ConcurrentHashMap과 무관한 별도 영역. LongAdder 자체 메커니즘으로 분산 처리돼요.

두 단계로 분리된 효과

1000 스레드가 한 키 /home으로 몰리는 시나리오에서 두 패턴이 어떻게 다른지 펼쳐볼게요.

단계 A — LongAdder ref 가져오기

모든 스레드가 ConcurrentHashMap에서 /home 키의 LongAdder 참조를 가져와요. tabAt의 volatile read만 일어나요. 락 없음.

여러 스레드가 같은 캐시 라인을 동시에 읽는 건 MESI 프로토콜에서 Shared 상태로 합법적이에요. 누가 쓰지 않는 한 invalidate가 안 일어나요. 1000 스레드가 같은 라인을 읽어도 충돌 없음.

단계 B — 분산된 셀에 CAS

그 다음 increment()는 LongAdder 내부의 cell 배열에 분산되어 처리돼요. 

T1 (probe=A) ──→ cells[A & mask] 에 CAS
T2 (probe=B) ──→ cells[B & mask] 에 CAS
T3 (probe=C) ──→ cells[C & mask] 에 CAS
   ⋮
T1000 (probe=...) ──→ 분산된 cell에 CAS

cells 배열 크기가 16개면 1000 스레드가 16개 셀에 분산 → 16-way 병렬 카운팅. 한 cell에 몰리는 충돌만 직렬화. 전체 직렬화 대비 16배 가까운 처리량.

LongAdder의 내부 — Striped64

LongAdder가 어떻게 분산 처리하는지 그 내부를 봐요. ConcurrentHashMap도 자기 size 카운터에 같은 패턴을 인라인으로 구현하고 있어요. 둘 다 Striped64라는 공통 조상에서 파생.

핵심 필드

private transient volatile long baseCount;            // 경합 없을 때 쓰는 기본 카운터
private transient volatile CounterCell[] counterCells; // 경합 시 분산 셀

@jdk.internal.vm.annotation.Contended
static final class CounterCell {
    volatile long value;
}

baseCount는 단일 카운터. 경합 없으면 여기에만 CAS. counterCells는 cell 배열. 경합이 발생하면 그때서야 만들어져요. 적응형(adaptive) 시작 패턴.

addCount의 동작

private final void addCount(long x, int check) {
    CounterCell[] as; long b, s;
    // 1) baseCount에 CAS 시도 (경합 없으면 성공)
    if ((as = counterCells) != null ||
        !U.compareAndSetLong(this, BASECOUNT, b = baseCount, s = b + x)) {
        // 2) 실패 = 경합 → 셀 사용
        CounterCell a; long v; int m;
        boolean uncontended = true;
        if (as == null || (m = as.length - 1) < 0 ||
            // 3) 스레드별 probe로 셀 선택
            (a = as[ThreadLocalRandom.getProbe() & m]) == null ||
            !(uncontended = U.compareAndSetLong(a, CELLVALUE, v = a.value, v + x))) {
            // 4) 셀도 경합 → 풀버전 (셀 배열 확장 등)
            fullAddCount(x, uncontended);
            return;
        }
    }
}

핵심 흐름이 4단계.

  1. baseCount에 CAS 시도. 경합 없으면 한 번에 끝
  2. 실패하면 cell 배열로 전환
  3. 스레드별 probe로 cell 선택. ThreadLocalRandom.getProbe()가 스레드마다 다른 값 반환
  4. cell도 경합이면 fullAddCount로 cell 확장 등 더 비싼 처리

경합이 없는 평상시엔 baseCount 한 번의 CAS로 끝나요. 추가 비용 0. 경합이 시작되면 그때 분산 시스템이 자라나는 식. 매우 영리한 디자인이에요.

측정 — 단일 카운터에서도 큰 차이

핫 키 시나리오가 아니라 그냥 단일 카운터 16스레드 동시 increment에서도 차이가 분명해요.

패턴처리 시간처리량 (ops/sec)
AtomicLong.incrementAndGet() 1,407 ms 약 56.9M
LongAdder.increment() 109 ms 약 734M

LongAdder가 약 12.9배 빨라요. 단일 메모리 위치에 모든 스레드가 CAS 시도하는 AtomicLong은 충돌이 누적되거든요. 왜 단일 위치 CAS가 그렇게 비싼가? 다음 절의 False Sharing이 큰 부분이에요.

False Sharing — 하드웨어 레벨 함정

AtomicLong의 본질적 비용은 CAS 자체가 아니라 그 아래의 캐시 동작에 있어요.

1단계 — CPU는 캐시 라인 단위로 동작

메인 메모리는 CPU 입장에서 매우 느려요(수백 사이클). CPU 안에 캐시(L1/L2/L3)를 둬서 자주 쓰는 메모리를 빠르게 접근.

중요한 건 캐시가 1바이트 단위가 아니라 "캐시 라인" 단위로 동작한다는 거예요. 대부분 x86 CPU에서 64바이트. 한 바이트만 필요해도 64바이트 통째로 캐시에 가져와요. "이 근처도 곧 쓸 거잖아"라는 locality 가정.

2단계 — 멀티코어와 MESI

각 코어가 자기만의 L1 캐시를 가져요. 한 코어가 어떤 캐시 라인을 수정하면 다른 코어가 가진 같은 라인을 무효화(invalidate)해야 해요. 이게 MESI 프로토콜(cache coherence)이에요. 정확성을 위해 필수.

비용이 커요. 다음 접근에서 캐시 미스 → 다른 코어 캐시나 RAM에서 다시 가져와야 해요.

3단계 — False Sharing의 등장

단순한 CounterCell이 있다고 해볼게요. 

static final class CounterCell {
    volatile long value;  // 8 bytes
}
CounterCell[] cells = new CounterCell[4];

CounterCell 객체는 메모리 레이아웃상 약 24바이트(헤더 16 + long 8). 4개를 연달아 만들면 메모리에 이렇게 배치돼요.

왜 "False"인가요

T1과 T2가 진짜로 데이터를 공유하는 게 아니에요. cell0과 cell1은 완전히 별개 데이터. 그런데 하드웨어 입장에선 같은 캐시 라인이라 공유처럼 보여요. 한 코어가 자기 cell에 쓸 때마다 다른 코어의 캐시가 무효화되어 핑퐁이 발생하는 거예요.

AtomicLong 한 카운터를 16스레드가 다투면 핑퐁의 강도가 16배. 모든 increment마다 다른 코어들의 캐시 무효화. 이게 측정상 12.9배 차이의 큰 부분이에요.

해결책 — Padding과 @Contended

옛날 방식 — 손으로 padding

class PaddedCell {
    volatile long value;
    long p1, p2, p3, p4, p5, p6, p7;  // 56바이트 패딩
}

더미 필드로 64바이트 이상 만들어 cell마다 자기 캐시 라인 독점. 단순하지만 단점이 있어요. JIT 컴파일러가 "안 쓰는 필드네?" 하고 dead code elimination 가능. 객체 헤더의 false sharing은 못 막음.

Java 8+ 방식 — @Contended

@jdk.internal.vm.annotation.Contended
static final class CounterCell {
    volatile long value;
}

JVM에게 "이 필드/클래스는 cache line bouncing 위험이 있으니 앞뒤로 충분한 패딩을 자동으로 끼워서 자기만의 캐시 라인을 독점하게 해줘"라고 지시.

처리 후 메모리 레이아웃이 이렇게 바뀌어요. 

[ padding ][ cell0 value ][ padding ] [ padding ][ cell1 value ][ padding ]
└─── 캐시 라인 0 (cell0 독점) ───┘    └─── 캐시 라인 1 (cell1 독점) ────┘

각 cell이 자기만의 캐시 라인 차지. False sharing 해소. JIT이 padding을 제거하지도 않고, 객체 헤더 영역도 보호돼요.

실무 사용 시 주의

  • jdk.internal 패키지라 일반 사용자 코드에서는 모듈 시스템에 막힘
  • -XX:-RestrictContended JVM 옵션으로 풀어줘야 함
  • 일반 코드에선 직접 padding 박거나 JCTools 같은 라이브러리의 PaddedAtomicLong 사용

측정 결과 정리

이 모든 메커니즘이 실측에 어떻게 나타나는지 정리해볼게요.

시나리오패턴 1패턴 2차이
단일 카운터 (16스레드) AtomicLong: 56.9M ops/s LongAdder: 734M ops/s 12.9x
핫 키 (16스레드 한 키) CHM.merge: 22.9M ops/s CHM<K, LongAdder>: 816M ops/s 35.6x
분산 키 (16스레드 16키) CHM.merge: 168M ops/s CHM<K, LongAdder>: 1,081M ops/s 6.4x

핫 키 시나리오에서 차이가 가장 극명해요. 이건 두 효과의 곱이에요.

  • 버킷 락 직렬화 회피 (computeIfAbsent fast-path)
  • cell 분산으로 false sharing 회피

분산 키여도 6.4배 차이. 이유는 단일 cell에서도 LongAdder가 AtomicLong보다 빠르거든요(false sharing 방지 + cell 확장).

합성 원칙 — 책임 분리

이 시리즈가 말하려는 더 큰 통찰을 정리하면 이래요. "ConcurrentHashMap이 만능이 아니라, 적절히 합성(compose)해야 진가가 나온다"는 거예요.

한 줄 요약

ConcurrentHashMap은 버킷 단위 락이라 한 키에 부하 몰리면 직렬화돼요. 그래서 ConcurrentHashMap 자체에서 카운팅하는 게 아니라, ConcurrentHashMap은 객체 lookup만 하고 그 객체(LongAdder)가 카운팅을 책임지게 분리해요.

책임 분리

레이어책임경합 처리
ConcurrentHashMap "이 키의 LongAdder ref 찾기" 락 없는 fast-path (computeIfAbsent)
LongAdder "+1" cell striping으로 분산 (자체 메커니즘)

일반화 가능한 원칙

이 패턴이 분산 시스템 전반에 적용되는 큰 원칙이에요.

동시성 자료구조를 합성할 때, 각 레이어가 자기 책임만 지면 락 경합이 곱셈이 아니라 덧셈처럼 동작해요.

비슷한 합성 사례들이에요.

  • ConcurrentLinkedQueue<AtomicReference<Foo>> — 동시 큐 안에 동시 객체
  • ConcurrentHashMap<String, ConcurrentLinkedQueue<Event>> — 동시 맵 안에 동시 큐
  • Cache<Key, LongAdder> — 캐시 안에 카운터

같은 사고방식의 다른 예

소프트웨어 설계 전반에 같은 사고방식이 보여요.

패턴분리한 책임
Outbox Pattern DB 트랜잭션과 메시지 발송 분리
CQRS 읽기 모델과 쓰기 모델 분리
Backpressure (WebFlux) 생산 속도와 소비 속도 분리
Circuit Breaker 요청 발송과 장애 감지 분리

전부 단일 컴포넌트가 짊어진 여러 책임을 분리해서, 각 책임에 가장 적합한 메커니즘에 위임하는 거예요.

실무 가이드

핫 키 의심되면 LongAdder 패턴

페이지 방문 카운터, API 호출 통계, 글로벌 메트릭 같이 한 키에 트래픽 집중되는 자리는 처음부터 CHM<K, LongAdder>. Micrometer 같은 메트릭 라이브러리도 모두 이 방식이에요.

키 많고 분산되면 merge로 충분

키가 수만 개고 키별 빈도 낮은 자리는 merge가 메모리 효율적. LongAdder는 cell 배열 때문에 cell당 메모리 부담이 있어요.

둘 다인 경우

실무에서는 보통 LongAdder 패턴으로 통일해도 무방. 메모리 손해는 일반적으로 무시 가능한 수준. 단, 키 수가 매우 많거나 메모리가 critical한 환경이면 측정 필요.

흔한 실수

실수 1 — putIfAbsent로 LongAdder 등록

// 매우 나쁨 — 호출마다 무조건 LongAdder 생성, GC 폭탄
LongAdder adder = new LongAdder();
counts.putIfAbsent(key, adder);
counts.get(key).increment();

반드시 computeIfAbsent를 써요. 람다는 키 없을 때만 호출되니 lazy 생성. putIfAbsent는 매번 LongAdder 인스턴스를 만들어 인자로 넘기니 GC 압박이 누적돼요.

실수 2 — merge 람다에 무거운 로직

// 매우 나쁨 — 람다가 버킷 락 잡은 채로 실행됨
pageViews.merge(pageUrl, 1L, (oldV, newV) -> {
    log.info("incrementing...");  // I/O를 락 안에서!
    Thread.sleep(10);
    return oldV + newV;
});

merge의 람다는 버킷 락 안에서 실행돼요. 무거운 로직이나 I/O를 람다에 넣으면 다른 모든 스레드가 그 락에서 대기. Long::sum 같은 순수 함수, 빠른 연산만 두는 게 원칙이에요. 사이드 이펙트 절대 금지.

면접 단골 질문

Q. ConcurrentHashMap이 왜 핫 키에 약한가요?

ConcurrentHashMap은 버킷 단위 락이에요. 다른 버킷은 동시 처리되지만 같은 버킷, 같은 키를 다루는 작업은 결국 한 락에서 직렬화돼요. 한 키에 트래픽 1000개가 몰리면 1000번 직렬화. 락 안에서의 read-modify-write 비용도 누적돼요. 이게 merge 같은 in-place 갱신 패턴의 본질적 한계예요.

Q. CHM<K, LongAdder>가 왜 그렇게 빠른가요?

두 가지가 결합돼요. 첫째, computeIfAbsent는 키 존재 시 fast-path로 락 없이 LongAdder 참조 반환. 핫 키여도 lookup이 동시 처리. 둘째, LongAdder는 내부적으로 cell 배열에 분산 카운팅. 16스레드면 16개 cell에 분산되어 직렬화 안 됨. 여기에 @Contended로 false sharing까지 막아요. 합쳐서 35배 차이.

Q. False Sharing이 뭔가요?

서로 다른 데이터를 만지는데 같은 캐시 라인 안에 있어서, 한 스레드의 쓰기가 다른 스레드의 캐시를 무효화시키는 현상이에요. MESI 프로토콜이 캐시 일관성을 위해 invalidate를 강제하는데, 진짜 공유가 아닌데 발생하니 "false". 단순 CAS도 가까운 데이터를 만지는 다른 스레드 때문에 캐시 미스 누적되어 처리량 떨어져요. @Contended로 cell마다 자기 캐시 라인 독점하게 해서 막아요.

Q. AtomicLong과 LongAdder는 언제 어느 걸 쓰나요?

경합이 적고 정확한 현재 값이 자주 필요하면 AtomicLong이 좋아요. 단일 메모리에서 sum 비용 0. 경합이 심하고 sum은 가끔만 필요한 카운터라면 LongAdder. 분산 갱신으로 처리량 매우 높지만 sum이 모든 cell 순회라 약간 비싸요. 메트릭, 통계, 카운터 같은 자리는 거의 항상 LongAdder가 답이에요.

한 줄 정리

ConcurrentHashMap은 만능이 아니에요. 핫 키에서는 버킷 락 직렬화로 성능이 크게 떨어져요. 답은 책임 분리 — ConcurrentHashMap은 LongAdder 객체 lookup만 하고, 카운팅은 LongAdder가 cell striping으로 분산 처리. 이 합성으로 35배 차이가 나는 이유가 락 회피 + false sharing 회피의 곱셈 효과예요. 분산 시스템 설계 전반에 적용되는 "각 레이어가 자기 책임만"이라는 원칙이 여기에서 가장 잘 보여요.

ConcurrentHashMap 시리즈는 여기까지예요. 자료구조 한 클래스 안에 소프트웨어 동시성 → 메모리 모델 → CPU 캐시 아키텍처가 모두 녹아있는 게 보였길 바라요.
