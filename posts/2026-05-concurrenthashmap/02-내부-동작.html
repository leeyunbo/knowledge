Java 8 내부 동작

fine-grained locking과 CAS가 어떻게 결합되는지, 그리고 resize는 어떻게 동시성 안전하게 처리되는지 들여다봐요.

전체 구조

Java 8의 ConcurrentHashMap은 사실 HashMap과 매우 닮았어요. 내부 자료구조도 거의 같아요.

  • 버킷 배열 (Node[] table)
  • 각 버킷은 LinkedList 또는 Red-Black Tree (충돌이 8개 넘으면 트리화, HashMap과 같은 정책)
  • 해시 함수와 버킷 인덱스 계산도 동일

다른 점은 동시성 처리에 집중돼 있어요. 같은 자료구조 위에 어떻게 동시성을 입혔는지가 핵심이에요.

put의 흐름

put(key, value) 호출이 들어왔을 때 내부에서 일어나는 일을 단계별로 따라가볼게요.

  1. 해시 계산해서 버킷 인덱스 결정
  2. 그 버킷이 비어있는지 확인 (table[i] == null)
  3. 비어있으면 CAS로 새 노드를 시도. 성공하면 끝
  4. 비어있지 않으면 그 버킷의 첫 노드에 synchronized 적용
  5. 락 안에서 LinkedList 또는 Tree 순회하며 키 검색
  6. 같은 키가 있으면 value 갱신, 없으면 새 노드 추가
  7. 락 해제
  8. 크기 갱신, 필요하면 treeify 또는 resize

코드로 보는 핵심 부분

final V putVal(K key, V value, boolean onlyIfAbsent) {
    int hash = spread(key.hashCode());
    Node<K,V>[] tab = table;

    for (;;) {
        Node<K,V> f = tabAt(tab, i = (n - 1) & hash);

        if (f == null) {
            // 빈 버킷: CAS 시도
            if (casTabAt(tab, i, null, new Node<>(hash, key, value, null))) {
                break;   // 락 없이 성공
            }
        } else {
            // 비어있지 않음: 첫 노드에 synchronized
            synchronized (f) {
                if (tabAt(tab, i) == f) {   // double-check
                    // LinkedList 또는 Tree 순회
                    // ...
                }
            }
        }
    }
}

왜 빈 버킷에는 CAS, 아니면 synchronized?

빈 버킷은 첫 노드를 만드는 거라 한 줄짜리 작업이에요. CAS 한 번이면 충분해요. 이 경우는 락 자체가 필요 없는 거죠.

비어있지 않으면 LinkedList 또는 Tree를 순회하며 같은 키가 있는지 검사해야 해요. 이런 여러 단계 작업은 CAS만으로 처리하기 어려워요. 그래서 짧게 synchronized로 보호해요. 단, 락의 대상이 첫 노드이기 때문에 다른 버킷의 작업은 영향 받지 않아요.

get은 어떻게 락 없이 안전한가요

가장 신기한 부분이에요. get은 락 자체가 없어요. 그런데도 동시성 안전해요. 어떻게 가능한지 이해하려면 Node의 정의를 봐야 해요. 

static class Node<K,V> {
    final int hash;
    final K key;
    volatile V val;          // ★ volatile
    volatile Node<K,V> next; // ★ volatile

    Node(int hash, K key, V val, Node<K,V> next) {
        this.hash = hash;
        this.key = key;
        this.val = val;
        this.next = next;
    }
}

volatile의 의미

val과 next가 volatile이라는 게 핵심이에요. 이 키워드 덕분에 두 가지가 보장돼요.

  • 가시성: 한 스레드가 쓴 값을 다른 스레드가 즉시 볼 수 있어요
  • 순서: 컴파일러가 이 필드와 관련된 명령어를 함부로 재정렬하지 못해요

그래서 read 스레드는 락 없이도 정확한 최신 값을 볼 수 있어요. 쓰기 스레드가 새 노드를 만들고 next 링크를 연결하면, read 스레드는 자연스럽게 그 변화를 감지해요.

읽는 도중 누군가 쓰면?

read 스레드가 LinkedList를 순회하는 도중에 다른 스레드가 노드를 추가/삭제하면 어떻게 될까요? 답은 "둘 중 한 가지를 본다"예요. 변경 전 상태나 변경 후 상태 중 하나를 보지, 깨진 중간 상태를 보지는 않아요. 이게 weak consistency라고 불리는 약속이에요.

이런 약한 일관성이 멀티스레드 환경에서 락 없이 read를 가능하게 해주는 핵심 디자인이에요. 정확한 시점의 스냅샷이 필요한 게 아니라면 충분한 보장이에요.

Treeify — HashMap과 같은 정책

한 버킷의 노드가 8개를 넘으면 LinkedList가 Red-Black Tree로 변환돼요. HashMap 시리즈에서 본 그 메커니즘과 같아요. 다른 점은 변환 자체도 동시성 안전하게 처리된다는 거예요.

treeify가 일어나는 동안에는 그 버킷의 첫 노드에 synchronized가 걸려요. 다른 스레드는 그 버킷에서 잠시 기다려야 하지만, 다른 버킷의 작업은 영향 받지 않아요.

Resize — 가장 어려운 부분

ConcurrentHashMap의 resize는 동시성 처리의 정점이에요. 전체 Map을 새 크기로 옮겨야 하는데, 이걸 락 잡고 한 번에 하면 너무 느려져요.

여러 스레드가 협력

Java 8 ConcurrentHashMap은 resize 작업을 여러 스레드가 협력해서 처리해요.

  • 한 스레드가 resize 시작을 결정하면 새 테이블을 할당
  • 옮겨야 할 버킷을 작업 단위로 분할
  • 다른 스레드가 put/get 요청하면, 그 작업을 처리하면서 동시에 resize 작업도 일부 도와줘요
  • 모든 버킷이 옮겨지면 새 테이블이 활성화됨

마치 줄 서서 도와주는 것처럼, 모든 스레드가 자기 작업하면서 resize에 기여해요. 한 스레드가 resize 전체를 부담하지 않으니 응답 시간이 일정하게 유지돼요.

ForwardingNode

resize 도중 이미 옮겨진 버킷에는 ForwardingNode라는 특별한 노드가 들어가요. 이 노드를 만난 스레드는 "여기는 새 테이블로 옮겨졌네"라고 알아채고, 새 테이블에서 작업을 진행해요. 

// resize 도중에 read를 시도하면
Node<K,V> e = tabAt(tab, i);
if (e instanceof ForwardingNode) {
    // 새 테이블로 redirect
    tab = ((ForwardingNode<K,V>)e).nextTable;
    // 새 테이블에서 다시 시도
}

이 패턴이 read와 resize가 동시에 일어나도 충돌하지 않게 만들어줘요. read 스레드는 ForwardingNode를 보면 새 테이블로 자동 이동, write 스레드는 일단 resize 돕고 자기 작업.

size 카운터의 미묘함

size() 메서드도 흥미로운 자리예요. 모든 키 개수를 정확히 세려면 전체 Map을 락 걸고 카운트해야 하는데, 그건 너무 느려요. 그래서 ConcurrentHashMap은 LongAdder 패턴을 사용해요.

  • 여러 cell에 카운트가 분산돼 있어요
  • 각 스레드가 자기 가까운 cell에 +1 또는 -1을 기록
  • size() 호출 시 모든 cell을 합산

단점은 size 결과가 정확한 시점의 값이 아닐 수 있다는 거예요. 호출 도중에 다른 스레드가 put/remove를 하면 그 변경을 반영할지는 보장되지 않아요. 이래서 size()를 정확한 정수로 신뢰하면 안 돼요. 대략적인 값으로 봐야 해요.

compute 류 메서드의 원자성

Java 8에서 추가된 compute, computeIfAbsent, merge 같은 메서드는 내부적으로 같은 락 메커니즘을 활용해서 원자적 작업을 보장해요. 

map.compute("counter", (k, v) -> v == null ? 1 : v + 1);

이 한 줄이 원자적으로 실행돼요. get → +1 → put 세 단계가 분리되지 않아요. 그래서 멀티스레드 카운터에 매우 적합해요. 다음 편에서 이런 패턴들을 자세히 봐요.

HashMap과의 핵심 차이 정리

측면HashMapConcurrentHashMap
Node 필드 일반 필드 val/next는 volatile
put 락 없음 (안전 X) 빈 버킷 CAS, 아니면 buc-level synchronized
get 락 없음 락 없음 (volatile 기반)
resize 단일 스레드 여러 스레드 협력

왜 null이 금지되었나요

ConcurrentHashMap은 null key와 null value를 둘 다 허용하지 않아요. 이유는 map.get(key)가 null을 반환했을 때 두 가지 의미가 모순되기 때문이에요.

  • "키가 없다"
  • "키는 있지만 value가 null이다"

단일 스레드 HashMap은 containsKey로 둘을 구분할 수 있지만, 멀티스레드에서는 get 결과와 containsKey 결과 사이에 다른 스레드가 끼어들 수 있어서 모호해져요. 그래서 null 자체를 허용하지 않는 게 더 안전한 디자인이에요.

면접 단골 질문

Q. ConcurrentHashMap의 put이 어떻게 동작하나요?

버킷 인덱스를 계산한 뒤, 그 버킷이 비어있으면 CAS로 첫 노드를 시도해요. 성공하면 락 없이 끝나요. 비어있지 않으면 그 버킷의 첫 노드에 synchronized를 걸고 LinkedList나 Tree를 순회하며 키 검색. 락의 영역이 한 버킷에 한정되니 다른 버킷 작업과 경합이 없어요.

Q. get이 락 없이 어떻게 안전한가요?

내부 Node의 val과 next 필드가 volatile이에요. 한 스레드가 쓴 값을 다른 스레드가 즉시 볼 수 있게 가시성이 보장되고, 컴파일러도 함부로 재정렬을 못 해요. read 도중 다른 스레드가 변경하더라도 변경 전 상태나 변경 후 상태 중 하나를 보지, 깨진 중간 상태는 안 봐요.

Q. ConcurrentHashMap이 null을 금지하는 이유는요?

멀티스레드 환경에서 get이 null을 반환했을 때 "키가 없다"인지 "value가 null이다"인지 구분이 모호해져요. 단일 스레드 HashMap은 containsKey로 구분 가능하지만, 멀티스레드는 두 호출 사이 다른 스레드가 끼어들 수 있어요. 이런 모호성을 피하기 위해 null 자체를 허용하지 않아요.

Q. resize가 동시성 안전한 비결?

여러 스레드가 협력해서 처리해요. 한 스레드가 resize를 시작하면 작업을 작은 단위로 나누고, 다른 스레드가 put/get 요청을 하면서 자기 작업과 함께 resize 작업도 도와줘요. 이미 옮겨진 버킷에는 ForwardingNode가 들어가서 read 스레드는 자동으로 새 테이블로 redirect돼요.

한 줄 정리

Java 8 ConcurrentHashMap은 락의 단위를 버킷으로 매우 작게 가져가요. 빈 버킷은 CAS, 비어있지 않으면 첫 노드에 synchronized. read는 volatile 덕에 락 자체가 없어요. resize는 여러 스레드가 협력해서 분산 처리하고, ForwardingNode로 read 스레드를 안내해요. fine-grained locking과 CAS, volatile, weak consistency가 어우러진 정교한 디자인이에요.

마지막 편에서는 이 강력한 도구를 어떻게 잘 쓰는지, 그리고 어떤 함정이 있는지 봐요.
