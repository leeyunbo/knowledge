ConcurrentHashMap의 정체와 진화

멀티스레드 환경에서 가장 자주 쓰이는 Map. HashMap, Hashtable과 어떻게 다른지부터 시작해볼게요.

출발점: 세 Map의 비교

자바에서 Map을 멀티스레드 환경에 쓰려고 하면 세 가지 선택지가 떠올라요. HashMap, Hashtable, 그리고 ConcurrentHashMap이에요. 이름은 비슷하지만 동시성 처리 방식이 완전히 달라요.

HashMap이 멀티스레드에서 깨지는 이유

HashMap은 동시성 안전을 보장하지 않아요. 여러 스레드가 동시에 put/remove를 호출하면 다음 같은 문제가 생길 수 있어요.

  • 두 스레드가 동시에 같은 버킷에 쓰면 한 쪽 데이터가 사라질 수 있어요
  • resize가 동시에 일어나면 내부 자료구조가 깨져요
  • Java 7까지는 더 무서운 일이 있었는데, resize 도중 LinkedList가 순환 참조를 만들어 무한 루프가 발생했어요

단일 스레드 환경에서는 빠르고 좋지만, 동시성이 필요하다면 절대 그냥 쓰면 안 돼요. 여러 스레드가 read만 한다 해도 다른 스레드가 한 번이라도 put하면 모든 스레드의 read가 의도와 다르게 동작할 수 있어요.

Hashtable의 단순한 해결책

Java 1.0 시절의 Hashtable은 가장 단순한 방법으로 동시성을 풀었어요. 모든 메서드에 synchronized를 붙이는 거예요. 

public class Hashtable<K,V> {
    public synchronized V get(Object key) { ... }
    public synchronized V put(K key, V value) { ... }
    public synchronized V remove(Object key) { ... }
    // 모든 메서드에 synchronized
}

확실하게 안전해요. 그런데 비용이 너무 커요. 한 스레드가 put을 하는 동안 다른 스레드는 get조차 못 해요. 멀티코어 시대의 처리량을 살리지 못하는 구조예요.

그래서 Hashtable은 현재 레거시로 분류돼요. 새 코드에서 쓸 일은 거의 없고, 멀티스레드가 필요하면 ConcurrentHashMap을 쓰면 돼요.

ConcurrentHashMap의 등장

Java 5에서 등장한 ConcurrentHashMap은 한 가지 핵심 아이디어를 가져요. 전체 Map에 락을 걸지 말고, 일부 영역에만 걸자는 거예요.

왜 이게 의미가 있을까요? 두 스레드가 다른 키에 접근한다면 사실 충돌할 일이 없거든요. 그런데 Hashtable은 어차피 전체 락을 걸어서, 무관한 키들끼리도 서로를 기다려요. ConcurrentHashMap은 이걸 고치는 데 집중했어요.

Java 7까지: Segment Locking

Java 5 ~ 7의 ConcurrentHashMap은 Map을 Segment라는 작은 영역으로 나눴어요. 기본 16개. 각 Segment가 자기만의 락을 갖고, 한 Segment 안의 작업만 그 락으로 보호돼요.

왜 16개?

기본값이 16이었던 이유는 단순해요. 너무 적으면 락 경합이 심해지고, 너무 많으면 메모리 오버헤드가 커요. 16이 합리적인 균형점이었어요. 생성자에서 concurrencyLevel로 조정할 수도 있었어요.

한계

Segment Locking은 의미 있는 진전이었지만 완벽하지 않았어요.

  • 같은 Segment에 들어가는 다른 키들끼리는 여전히 락 경합이 있었어요
  • Segment 자체가 메모리 오버헤드를 만들었어요. 키가 적은 Map이라도 16개 Segment 구조 유지
  • 모든 작업이 락 기반이라 read도 가끔 영향을 받았어요

Java 8의 큰 변화

Java 8에서 ConcurrentHashMap은 거의 다시 만들어졌어요. 핵심 변화는 두 가지예요.

변화 1: Segment를 버렸어요

Segment 추상화를 없애고, HashMap처럼 단일 배열 구조로 돌아왔어요. 대신 락의 단위를 더 작게 만들었어요. 버킷 단위로요.

변화 2: 락 + CAS의 조합

쓰기 작업에 따라 두 가지 방식을 골라 써요.

  • 버킷이 비어있으면: CAS로 첫 노드를 시도. 성공하면 락 자체가 필요 없어요
  • 버킷이 비어있지 않으면: 그 버킷의 첫 노드에 synchronized 적용. 다른 버킷은 영향 없음

결과적으로 락의 영역이 Segment 단위에서 버킷 단위로 작아졌어요. Segment 16개에서 버킷 수십~수백 개로 갔으니, 락 경합 가능성이 훨씬 줄어든 거죠.

읽기는 락 없음

가장 큰 진전은 read였어요. get 같은 읽기 작업에는 락이 전혀 없어요. 내부 노드의 val과 next 필드가 volatile로 선언돼 있어서 가시성이 보장되거든요. 이 덕분에 읽기 작업은 사실상 동시성 비용이 0에 가까워졌어요.

그럼 항상 ConcurrentHashMap을 쓰면 되나요?

멀티스레드 환경이라면 거의 그래요. 하지만 단일 스레드라면 HashMap이 살짝 더 빨라요. ConcurrentHashMap은 동시성을 위한 추가 비용 (volatile 접근, CAS 시도)이 있거든요. 경합이 없는 환경에서는 그 비용이 의미 없는 오버헤드가 될 수 있어요.

그래도 차이는 크지 않아요. 의심스럽다면 ConcurrentHashMap을 기본 선택으로 가도 안전해요. 특히 Spring Bean 같이 여러 스레드가 같은 객체를 공유하는 환경이면 ConcurrentHashMap이 답이에요.

면접 단골 질문

Q. HashMap을 멀티스레드에서 그냥 쓰면 안 되나요?

안 돼요. 동시 put/remove에서 데이터가 사라지거나, resize 도중 자료구조가 깨질 수 있어요. Java 7까지는 resize 중 LinkedList가 순환 참조를 만들어 무한 루프가 발생하는 무서운 버그도 있었어요. 멀티스레드 환경에서 Map이 필요하면 ConcurrentHashMap을 쓰는 게 정답이에요.

Q. Hashtable과 ConcurrentHashMap의 차이는요?

Hashtable은 모든 메서드에 synchronized를 붙여 전체 락을 걸어요. 한 스레드가 작업하는 동안 다른 모든 스레드가 대기해요. ConcurrentHashMap은 락의 영역을 매우 작게 가져가요. Java 8부터는 버킷 단위 락 + CAS 조합으로, 서로 다른 버킷의 작업은 동시 진행이 가능해요. 처리량 차이가 매우 커요.

Q. Java 7과 Java 8의 ConcurrentHashMap이 다른가요?

많이 달라요. Java 7은 Segment 16개로 Map을 나눠서 각 Segment에 락을 걸었어요. Java 8은 Segment 추상화를 없애고 HashMap처럼 단일 배열 구조로 돌아온 뒤, 락의 단위를 버킷으로 더 작게 만들었어요. 빈 버킷에는 CAS, 비어있지 않으면 그 버킷의 첫 노드에 synchronized. 읽기는 락이 아예 없고요.

Q. ConcurrentHashMap의 read는 락이 없는데 어떻게 안전한가요?

내부 Node의 val과 next 필드가 volatile로 선언돼 있어서 가시성이 보장돼요. 한 스레드가 쓴 값은 다른 스레드가 즉시 볼 수 있어요. 그래서 read는 락 없이도 정확한 값을 읽을 수 있어요.

한 줄 정리

ConcurrentHashMap은 멀티스레드용 Map의 표준 답이에요. Hashtable처럼 전체 락을 걸지 않고, 락의 영역을 매우 작게 잡아서 동시성을 살려요. Java 7의 Segment 16조각에서 Java 8의 버킷 단위 + CAS로 진화하면서 거의 lock-free read에 가까워졌어요.

다음 편에서는 Java 8의 내부 구조를 더 자세히 들여다봐요. 버킷 단위 락이 정확히 어떻게 동작하는지, CAS와 어떻게 결합되는지요.
