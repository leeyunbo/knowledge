객체 헤더가 어디에 있나요

1편에서 "모든 자바 객체는 모니터 락을 하나씩 가진다"고 했어요. 그게 어디에 어떻게 저장되는지 봐요. 모든 객체는 메모리에 다음 구조로 저장돼요.

모든 객체는 헤더 + 필드 + 패딩으로 구성돼요. 헤더 안의 Mark Word가 락 정보를 저장하는 자리예요. 크기는 64bit JVM에서 8바이트, 32bit에서 4바이트.

이 헤더는 작은 객체일수록 부담이 커요. 빈 객체도 16바이트 정도 차지. 그래서 객체를 너무 많이 만들면 헤더만으로 메모리가 부족해질 수 있어요.

Mark Word의 다중 의미

Mark Word는 한 워드(8바이트)지만 여러 용도로 쓰여요. 객체 상태에 따라 그 안의 비트가 다른 의미로 해석돼요.

객체 상태Mark Word 내용마지막 비트
No Lock (일반) identity hashCode + age + ... 01
Biased Lock 점유 스레드 ID + epoch + age + ... 101
Lightweight Lock 스레드 스택의 Lock Record 포인터 00
Heavyweight Lock ObjectMonitor 포인터 10
GC Marked GC 마킹 정보 11

같은 메모리 위치가 객체 상태에 따라 다른 의미. JVM이 마지막 비트 패턴을 보고 현재 상태를 식별해요. 메모리를 절약하기 위한 영리한 트릭이에요.

왜 락에 단계가 있나요

가장 단순한 락 구현은 OS의 mutex를 그대로 쓰는 거예요. 시스템 콜로 락을 잡고 풀고. 하지만 비싸요.

  • 매 락 획득에 시스템 콜 (커널 모드 진입)
  • 경합 시 스레드 suspend → 컨텍스트 스위칭
  • 한 번에 수 마이크로초 비용

그런데 자바 코드의 많은 synchronized는 실제 경합이 거의 없어요. 단일 스레드만 그 코드를 실행하거나, 한 스레드가 오래 점유하는 패턴. 이런 경우에 매번 OS mutex를 호출하는 건 큰 낭비예요.

그래서 자바 6 (2006)에서 락 단계화가 도입됐어요. 경합 정도에 맞는 가장 가벼운 메커니즘을 골라 쓰자는 아이디어.

4단계 락 진화

락은 다음 순서로 무거워져요. 가벼운 단계로 시작하고, 경합이 심해지면 한 단계씩 올라가요.

  1. No Lock: 누구도 잡지 않은 상태
  2. Biased Lock (편향): 한 스레드만 점유 중. 거의 무비용
  3. Lightweight Lock (경량): 가벼운 경합. CAS로 처리
  4. Heavyweight Lock (중량): 심한 경합. OS mutex 사용

하나씩 자세히 봐요.

1. Biased Lock — 편향 락

핵심 아이디어. "어차피 한 스레드만 쓰는 락이 대부분"이라는 관찰. StringBuilder, ArrayList 같은 단일 스레드 객체가 그렇거든요.

동작

처음 어떤 스레드가 락을 잡으면 Mark Word에 그 스레드 ID를 기록. 락 비트도 101로 변경. 같은 스레드가 다시 락을 잡으려 하면 Mark Word의 ID가 자기 ID와 일치하는지 확인. 일치하면 그냥 통과. CAS도 안 함.

비용이 거의 0. 락 획득과 해제가 단순한 비교 한 번.

편향 깨짐 (Revoke)

다른 스레드가 같은 락을 시도하면 편향이 깨져요. JVM이 짧은 stop-the-world를 발생시켜 안전한 상태에서 Lightweight Lock으로 전환. 이 revoke 비용이 의외로 커요.

Java 15+에서의 deprecate

처음엔 좋은 최적화였지만 Java 15에서 deprecate됐어요(JEP 374). 이유가 여러 가지.

  • revoke의 짧은 stop-the-world 비용이 누적되면 부담
  • 모던 자바 코드는 ConcurrentHashMap 같은 동시성 컬렉션이 많아져 단일 스레드 가정이 자주 깨짐
  • JVM 내부 코드 복잡도 부담
  • 다른 최적화(escape analysis 등)로 이득이 줄어듦

Java 15+에선 기본 비활성. 활성화하려면 -XX:+UseBiasedLocking 옵션 필요. Java 18부터는 더 깊이 제거 진행 중. 이 글을 쓰는 시점(Java 21)에선 사실상 사라진 것으로 봐도 돼요.

2. Lightweight Lock — 경량 락

경합이 짧을 거라 예상되는 자리. OS mutex 안 쓰고 CAS로 락을 잡고 풉니다.

동작

  1. 락 잡는 스레드의 스택에 Lock Record라는 작은 공간 할당
  2. 객체의 Mark Word를 그 Lock Record에 백업
  3. CAS로 Mark Word를 Lock Record 포인터로 교체
  4. 성공이면 락 획득. 실패면 다른 스레드가 이미 잡고 있다는 뜻

해제는 반대로. CAS로 Mark Word를 백업해둔 원래 값으로 복원. 한 번의 CAS로 끝나는 매우 가벼운 락이에요.

경합 시 spin

CAS가 실패해도 즉시 OS mutex로 가지 않고, 잠깐 spin(busy-wait)을 해요. 경합이 매우 짧으면 spin이 컨텍스트 스위칭보다 싸거든요.

JVM의 Adaptive Spinning이 영리해요. 과거에 그 락에서 spin이 성공했던 이력을 추적해서, 성공 가능성이 높으면 더 길게 spin. 실패가 누적되면 spin 안 하고 즉시 Heavyweight으로 전환.

3. Heavyweight Lock — 중량 락

경합이 정말 심한 자리. 더 spin하느니 OS에 맡기는 게 효율적인 시점.

ObjectMonitor

Heavyweight Lock으로 전환되면 JVM이 ObjectMonitor라는 자료구조를 만들어요. 그 안에 다음 정보가 들어가요.

  • _owner: 현재 락 보유 스레드
  • _EntryList: 락 대기 중인 스레드 큐
  • _WaitSet: wait()로 대기 중인 스레드
  • _recursions: 재진입 카운트

동작

  1. CAS로 _owner를 자기 스레드로 설정 시도
  2. 실패하면 _EntryList에 자기를 등록
  3. OS mutex로 suspend (block 상태)
  4. 다른 스레드가 락을 풀면 OS가 깨워줌

시스템 콜 + 컨텍스트 스위칭 비용이 들어가요. 한 번에 수 마이크로초. 단, 대기 시 CPU를 안 쓰니 spin과 다르게 절약 효과는 있어요.

비용 측정 — 실제 얼마나 차이나는가

이 4단계가 실측에 어떻게 나타나는지 직접 측정해봤어요. 카운터 한 개를 락으로 보호하면서 5백만 번 increment. 스레드 수를 늘리면서 경합 정도를 변화시켰어요. (Java 21, M-series Mac)

단일 스레드 — 경합 없는 baseline

패턴처리 시간처리량 (ops/s)락 없음 대비
락 없음 1 ms 5,000M 1.0x (기준)
synchronized 12 ms 417M 12x
ReentrantLock 25 ms 200M 25x

경합 없는 단일 스레드에서도 락은 12배 정도 비용이에요. 5백만 번 시도면 미세한 차이가 누적. 그래도 synchronized가 ReentrantLock보다 2배 가까이 빠르네요. JVM의 lock 단계화 최적화 덕분.

경합 점진 증가

스레드 수synchronizedReentrantLock관찰
1 스레드 417M ops/s 200M ops/s synchronized 우세
2 스레드 43M ops/s 35M ops/s synchronized 약간 우세
4 스레드 32M ops/s 134M ops/s ReentrantLock 우세
16 스레드 148M ops/s 134M ops/s 비슷

몇 가지 흥미로운 관찰이 보여요.

  • 단일 스레드에서는 synchronized가 2배 빠름 (lightweight CAS의 효율)
  • 2 스레드 가벼운 경합도 synchronized 우세
  • 4 스레드에서 갑자기 ReentrantLock이 4배 빠름. 이 자리는 synchronized의 spin 비용이 누적되는 영역
  • 16 스레드 심한 경합에선 다시 비슷. 둘 다 결국 OS mutex 기반 처리

중요한 건 단순 비교가 어렵다는 점이에요. 경합 정도와 패턴에 따라 답이 달라요. 일반론으로 "X가 더 빠르다"고 말하기 힘들어요.

1 스레드에서 락이 12배 비싸다는 의미

무서운 숫자처럼 보이지만 절대값을 보면 다른 그림이에요. 5백만 번 increment에 12ms. 한 번 락 획득 + 해제에 약 2.4 nanosecond. 매우 빠른 거죠.

실무에서 synchronized 비용이 문제가 되는 자리는 경합이 심한 핫 키 또는 매우 짧은 임계 영역의 반복 정도예요. 일반 비즈니스 로직은 락 비용이 무시 가능한 수준.

전체 진화 흐름

실무 영향 — 어떻게 쓰면 좋은가요

이 진화 메커니즘이 실무 코드에 주는 함의를 정리해볼게요.

1. 임계 영역을 짧게

락 안에서 I/O, 외부 호출, 큰 DB 쿼리 같은 무거운 작업 금지. 임계 영역이 길수록 다른 스레드 대기가 누적되고, Heavyweight으로 빨리 승급해요. 

// 안 좋음
synchronized (lock) {
    User user = userRepository.findById(id);   // DB 조회 (수 ms)
    user.update(data);
    userRepository.save(user);
}

// 좋음
User user = userRepository.findById(id);      // 락 밖에서
user.update(data);
synchronized (lock) {
    state.put(user.getId(), user);             // 락 안은 메모리 작업만
}
userRepository.save(user);                     // 락 밖에서

2. 락 단위를 작게

하나의 큰 락보다 여러 개의 작은 락이 좋아요. ConcurrentHashMap이 버킷 단위 락(bin-level locking)으로 동시성을 살린 게 같은 원리. 여러 자원을 보호한다면 자원별 락 분리 검토.

3. 락 자체를 줄이기

가능하면 락 없이 처리하는 패턴 검토.

  • 불변 객체 — 동기화 불필요
  • ThreadLocal — 스레드별 격리로 공유 자체 회피
  • Atomic 클래스 — CAS 기반, 락 없음
  • ConcurrentHashMap, BlockingQueue — 자료구조가 동시성 처리

4. 측정 후 결정

synchronized vs ReentrantLock 같은 선택은 일반론으로 답하기 어려워요. 위 벤치마크에서도 4스레드와 16스레드의 결과가 달랐듯이. 실제 워크로드 패턴으로 측정한 뒤 결정하는 게 안전해요.

VM 옵션으로 락 관찰하기

JVM의 락 동작을 실제로 관찰할 수 있는 옵션이 있어요. 디버깅 시 유용해요.

옵션의미
-XX:+UseBiasedLocking Biased Lock 활성 (Java 15+ 기본 비활성)
-XX:BiasedLockingStartupDelay=0 Biased Lock 시작 지연 제거
-XX:+PrintBiasedLockingStatistics Biased Lock 통계 출력
-XX:+PrintCompilation JIT 컴파일 진행 로그

면접 단골 질문

Q. synchronized의 락 정보는 어디에 저장되나요?

객체 헤더의 Mark Word에 저장돼요. 64bit JVM에서 8바이트 슬롯이고, 객체 상태에 따라 다른 의미로 해석돼요. No Lock일 땐 hashCode, Biased일 땐 스레드 ID, Lightweight일 땐 Lock Record 포인터, Heavyweight일 땐 ObjectMonitor 포인터. 마지막 비트 패턴으로 현재 상태를 식별해요.

Q. 4단계 락의 차이는요?

비용이 점점 커지는 단계예요. Biased는 한 스레드 점유 시 거의 무비용 (Java 15+에서 deprecate). Lightweight는 가벼운 경합을 CAS로 처리. Heavyweight는 OS mutex로 진짜 경합 처리. 컨텍스트 스위칭 발생. JVM이 경합 상황에 따라 자동으로 단계 상승. 대부분 락은 Lightweight에서 끝나요.

Q. Java 15에서 Biased Lock이 deprecate된 이유는요?

revoke의 stop-the-world 비용이 누적되면 부담이고, 모던 자바 코드는 ConcurrentHashMap 같은 동시성 컬렉션이 보편화되어 단일 스레드 가정이 자주 깨져요. 또 JVM 내부 코드 복잡도와 다른 최적화로 인해 이득이 줄어든 것도 이유. 현재(Java 21)에는 사실상 사라진 것으로 봐도 돼요.

Q. 임계 영역을 짧게 유지해야 하는 이유는요?

락 보유 시간이 길수록 다른 스레드 대기가 누적되어 처리량이 떨어져요. 락이 빨리 Heavyweight으로 승급되어 OS mutex 비용도 누적. 또 락 안에서 외부 호출하다가 응답 안 오면 락이 영원히 안 풀리는 위험도 있어요. 락 안은 메모리 작업만, 무거운 작업은 락 밖에서 처리하는 게 원칙이에요.

한 줄 정리

synchronized의 락 정보는 객체 헤더의 Mark Word에 압축되어 저장돼요. 경합 정도에 따라 No Lock → Biased → Lightweight → Heavyweight 4단계로 자동 진화. 대부분 락은 Lightweight에서 끝나요. Java 15+에서 Biased는 deprecate되어 사실상 3단계예요. 실무에서는 임계 영역을 짧게 유지하고, 경합이 심하면 락 단위를 작게 분리하는 게 핵심 원칙이에요.

다음 편에서는 synchronized의 다른 면 — 메모리 가시성과 happens-before 관계로 들어가요. 락이 단순한 mutex 이상의 역할을 한다는 게 보일 거예요.
