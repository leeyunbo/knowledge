객체 헤더의 구조

HotSpot JVM의 객체는 메모리에 다음 구조로 저장:

  ┌─────────────────────────────┐
  │ Object Header               │
  │  - Mark Word    (8 bytes)   │  ← ★ 락 정보가 여기
  │  - Klass Pointer (4-8 bytes)│  ← 클래스 메타데이터
  ├─────────────────────────────┤
  │ Instance Fields             │
  │  - 필드 1                    │
  │  - 필드 2                    │
  │  ...                        │
  ├─────────────────────────────┤
  │ Padding (8-byte 정렬)        │
  └─────────────────────────────┘

총 헤더 크기: 12 또는 16 bytes (압축 옵션, JVM 설정에 따라)
모든 객체가 이 헤더를 가짐 (작은 객체일수록 헤더 비중 큼)

Mark Word의 다목적성

Mark Word는 64비트 (64bit JVM 기준)
하나의 메모리 슬롯이지만 여러 상태에서 다른 의미로 사용됨:

상태             Mark Word의 비트 활용 (64bit JVM, 개념적)
─────────────────────────────────────────────────────────────
No Lock          | hashCode (31bits) | age | unused | 0 01 |   ← 일반
Biased Lock      | thread ID | epoch | age | 1 01 |              ← 특정 스레드 점유
Lightweight Lock | pointer to Lock Record (스택 포인터)            ← 스핀
Heavyweight Lock | pointer to ObjectMonitor                        ← OS 락
GC Marked        | GC 마킹 정보                                    ← GC 중

→ 같은 메모리 위치가 객체 상태에 따라 다른 의미
→ 마지막 비트 패턴으로 현재 상태 식별

Mark Word는 메모리 절약을 위해 한 워드를 여러 용도로 쓴다. 락 상태에 따라 비트 패턴이 달라지고, JVM이 그 패턴을 보고 분기.

왜 락에 단계가 있나 — 비용의 문제

Heavyweight Lock (옛날 synchronized):
  락 획득 = OS 커널 호출 (mutex 시스템 콜)
  락 대기 = 스레드를 suspend, 컨텍스트 스위칭
  → 한 번의 락 획득에 수 마이크로초

문제:
  많은 코드가 synchronized를 쓰지만 실제로 경합 없음
  - 단일 스레드만 그 코드 실행
  - 또는 한 스레드가 오랫동안 점유

이런 케이스에 매번 OS 락을 잡는 건 낭비
→ "경합이 없거나 적을 때는 가볍게, 경합이 심할 때만 무겁게"
→ 락의 단계화 (Java 6, 2006)

락 진화 단계

1. No Lock (락 없음)
   → 누구도 안 잡고 있음

2. Biased Lock (편향 락)
   → 한 스레드가 단독으로 사용 중
   → 락 획득 비용 거의 0

3. Lightweight Lock (경량 락)
   → 다른 스레드가 락 획득 시도 (편향 깨짐)
   → CAS로 빠르게 락 시도, 실패하면 잠깐 스핀

4. Heavyweight Lock (중량 락)
   → 경합이 지속됨 → OS 락으로 승급
   → 스레드 suspend, 컨텍스트 스위칭

진화 방향: 1 → 2 → 3 → 4
역방향(de-bias)도 일부 가능하지만 비용이 더 듦

1. Biased Lock — 편향 락

아이디어: "어차피 한 스레드만 쓰는 락이 대부분"

처음 락 획득:
  Mark Word에 "이 스레드가 점유" 기록 (Thread ID 저장)
  락 비트 = 101 (bias 패턴)

같은 스레드가 다시 락 획득:
  Mark Word의 Thread ID와 자기 ID 비교 (한 번의 비교)
  같으면 그냥 통과 — CAS도 안 함
  → 거의 비용 없음

다른 스레드가 락 시도:
  편향 깨짐 (revoke biased lock)
  → 일종의 stop-the-world 짧게 발생
  → Lightweight Lock으로 승급

Biased Lock의 문제와 폐지

왜 좋았나:
  단일 스레드 락 획득 비용을 사실상 0으로
  StringBuilder, ArrayList 등 단일 스레드 사용에 큰 이득
  레거시 자바 코드의 "방어적 synchronized"에 효과적

왜 폐기되었나 (JEP 374, Java 15에서 deprecate, Java 18에서 제거 검토):
  1. revoke 비용이 큼 — 짧은 stop-the-world
  2. 모던 JVM의 다른 최적화로 이득 줄어듦
  3. 코드 복잡도 — JVM 내부 유지보수 부담
  4. ConcurrentHashMap 등 동시성 컬렉션 보편화로 단일 스레드 가정이 깨지는 경우 많아짐

  → Java 15+: 기본 비활성화 (-XX:+UseBiasedLocking 옵션으로 활성화 가능)
  → Java 21+: 더 깊은 제거 진행

현재 추세:
  Lightweight Lock과 Heavyweight Lock 두 단계 위주
  Biased Lock은 레거시 환경에만 의미

2. Lightweight Lock — 경량 락

아이디어: "경합이 짧으면 OS 락 안 쓰고 CAS로 처리"

획득:
  1. 스레드의 스택에 Lock Record 공간 할당
  2. 객체의 Mark Word를 Lock Record에 백업
  3. CAS로 Mark Word를 Lock Record 포인터로 교체
     - 성공: 락 획득 완료
     - 실패: 다른 스레드가 이미 점유 → Heavyweight 승급 또는 스핀

해제:
  1. CAS로 Mark Word를 원래 값(백업)으로 복원
     - 성공: 정상 해제
     - 실패: 누군가 Heavyweight으로 승급 → 별도 처리

특징:
  락 획득/해제가 CAS 한 번
  성공하면 매우 빠름 (< 100 nanosec)
  단, 다른 스레드와 경합 시 효율 떨어짐

스핀 락 (Spin Lock) — Lightweight의 보조

경합이 잠깐일 거라 예상되면:
  CAS 실패 시 즉시 OS 락으로 가지 않고
  잠깐 동안 (수 사이클) busy-wait하며 다시 CAS 시도
  → 컨텍스트 스위칭 비용보다 싸면 이득

JVM의 Adaptive Spinning:
  과거에 그 락에서 스핀이 성공했는지 추적
  성공 이력 있으면 다음에도 스핀 시도
  실패 누적이면 스핀 안 하고 즉시 Heavyweight

3. Heavyweight Lock — 중량 락

아이디어: "경합이 진짜 심함, OS에 맡기자"

ObjectMonitor 구조 (HotSpot 내부):
  - _owner: 현재 락 보유 스레드
  - _EntryList: 락 대기 중인 스레드 큐
  - _WaitSet: wait()로 대기 중인 스레드
  - _recursions: 재진입 카운트

획득:
  CAS로 _owner를 자기 스레드로 설정 시도
  실패 시:
    → _EntryList에 자기 자신 등록
    → OS의 mutex로 suspend (block)
    → 다른 스레드가 release하면 OS가 깨워줌

해제:
  _owner를 null로
  _EntryList에서 한 스레드 깨움 (선택은 unfair, OS 의존)

특징:
  안정적 (어떤 경합 상황에도 작동)
  비용 큼 (시스템 콜 + 컨텍스트 스위칭)
  대기 시 CPU 사용 안 함 (block 상태)

전체 진화 그림

새 객체 생성:
  Mark Word: No Lock 상태

스레드 A가 처음 synchronized 진입:
  → Biased Lock으로 변환 (Thread A의 ID 기록)
  → A가 다시 진입해도 거의 무비용

스레드 B가 같은 락 진입 시도:
  → Biased 해제 (revoke) → Lightweight Lock으로
  → B와 A 모두 CAS 기반으로 락 시도

경합 지속:
  → CAS 반복 실패 / 스핀 한계 도달
  → Heavyweight Lock으로 승급
  → ObjectMonitor 사용, OS 큐로

시간 흘러 경합 사라짐:
  → 다음 GC cycle에 락 상태 재평가 가능 (deflation)
  → No Lock으로 복귀 가능

핵심:
  대부분 락은 Lightweight 또는 Biased에서 끝남
  Heavyweight까지 가는 건 진짜 경합 심한 락만

측정 — 단계별 비용

대략적 비용 비교 (현대 CPU, 단일 락 획득 한 번):

No Lock:                 0 ns
Biased Lock:             ~5 ns   (Thread ID 비교만)
Lightweight Lock (성공): ~20-50 ns (CAS 한 번)
Lightweight Lock (스핀): ~100-500 ns
Heavyweight Lock:        ~1000+ ns (시스템 콜)

→ 같은 synchronized 키워드라도 상황에 따라 100~1000배 비용 차이

실무 영향 — 어떻게 락을 짧게 유지하는가

락 진화 단계는 대부분 JVM이 알아서 함.
개발자가 신경 쓸 것:

1. 임계 영역을 짧게
   - 락 안에서 I/O 호출 X
   - 락 안에서 외부 메서드 호출 최소화 (Lock 외부에서 인자 다 준비)

2. 락 단위를 작게
   - 큰 객체 통째로 잡기보다 필요한 부분만
   - "Stripe Lock" 패턴 (ConcurrentHashMap이 사용)

3. 락 경합 자체를 줄이기
   - ThreadLocal로 스레드별 격리
   - 불변 객체 사용으로 동기화 불필요
   - CAS 기반 자료구조 (Atomic, ConcurrentMap)

4. 스레드별 워크로드 분산
   - 같은 락에 많은 스레드가 몰리지 않도록 구조 설계

면접 단골 질문

Q. synchronized의 락 정보는 어디에 저장되나?

객체 헤더의 Mark Word에 저장. 64비트 슬롯 하나가 락 상태에 따라 다른 의미로 쓰임 — No Lock일 땐 hashCode 등, Biased일 땐 Thread ID, Lightweight일 땐 Lock Record 포인터, Heavyweight일 땐 ObjectMonitor 포인터.

Q. Biased / Lightweight / Heavyweight Lock의 차이는?

비용 순으로 단계화. Biased는 한 스레드 점유 시 거의 무비용, Lightweight는 CAS로 짧은 경합 처리, Heavyweight는 OS mutex로 무거운 경합 처리. JVM이 경합 상황 따라 자동으로 단계 상승.

Q. Java 15에서 Biased Lock이 왜 deprecate되었나?

revoke 비용(짧은 stop-the-world), 코드 복잡도 부담, 모던 자바의 동시성 컬렉션 보편화로 이득이 줄어듦. 단일 스레드 가정이 깨지는 케이스가 많아져서 비용 대비 효과가 줄었다는 판단.

Q. 임계 영역을 어떻게 빨리 만드나?

락 안에서 I/O / 외부 호출 안 하기, 락 단위 작게(필드 단위), 락 자체를 줄이기(불변 객체, ThreadLocal, CAS 기반 자료구조). JVM의 락 진화는 자동이지만 임계 영역의 길이는 개발자 책임.

한 줄 정리

객체 헤더의 Mark Word에 락 정보가 다목적으로 저장.
synchronized는 4단계 락 진화: No Lock → Biased → Lightweight → Heavyweight.

진화 의미:
  대부분 락은 Lightweight 또는 Biased에서 끝남 — 매우 빠름
  진짜 경합 심한 락만 Heavyweight (OS mutex) — 비싼 처리

Java 15+에서 Biased Lock은 기본 비활성화 (deprecate).

다음 편: synchronized가 단순 mutex가 아니라 메모리 가시성까지 보장하는 이유 — JMM과 happens-before.
