메모리 가시성과 happens-before

synchronized는 단순한 mutex가 아니에요. CPU 캐시와 컴파일러 재정렬을 다스리는 메모리 도구이기도 해요. 그 다른 면을 봐요.

가시성 문제 — mutex만으로는 부족해요

한 가지 시나리오로 시작해볼게요. 한 스레드가 다른 스레드를 멈추게 하는 단순한 코드예요. 

class Worker {
    boolean running = true;

    void run() {
        while (running) {
            // 작업
        }
    }

    void stop() {
        running = false;
    }
}

기대는 단순해요. 한 스레드가 worker.run()을 실행 중이고, 다른 스레드가 worker.stop()을 호출하면 멈춤. 그런데 실제로 돌리면 worker가 영원히 멈추지 않을 수 있어요. mutex(상호 배제) 문제가 아니라 메모리 가시성 문제예요.

왜 가시성 문제가 생기나요

현대 CPU의 메모리 모델이 단순하지 않아요. 두 가지 요인이 가시성을 깨요.

요인 1 — CPU 캐시

각 코어가 자기만의 캐시(L1, L2)를 가져요. 메모리 쓰기는 일단 캐시에 머물고, 나중에 메인 메모리로 flush. 그 사이에 다른 코어는 자기 캐시의 옛 값을 계속 봐요.

요인 2 — 컴파일러 재정렬

JIT 컴파일러는 성능을 위해 코드를 재정렬해요. 단일 스레드 의미만 보존하면 자유롭게 가능. 

// 원본 코드
while (running) {
    // 작업
}

// JIT 최적화 후 (가상 변환)
boolean cached = running;
while (cached) {
    // 작업 (running을 다시 안 읽음)
}

JIT가 "running이 루프 안에서 안 바뀌니 한 번만 읽고 캐시하자"라고 판단하면, 메모리가 갱신되어도 그 변수는 영원히 옛 값. 단일 스레드 의미는 보존되지만 멀티스레드에선 깨져요.

그래서 멀티스레드 코드는 원자성(atomicity) + 가시성(visibility) + 순서(ordering) 셋을 모두 다뤄야 안전해요. synchronized는 이 셋을 모두 보장해요.

JMM — Java Memory Model

자바가 다양한 CPU 아키텍처에서 일관된 동작을 약속하기 위해 정의한 메모리 모델이에요. JLS(Java Language Specification) 17장에 명세되어 있어요.

JMM이 답하려는 질문은 단순해요. "어떤 쓰기가 어떤 읽기에서 보이는가". 이걸 형식적으로 표현하기 위한 도구가 happens-before 관계예요.

happens-before 관계

A happens-before B라고 하면 두 가지가 동시에 성립해요.

  • 가시성: A의 모든 메모리 효과가 B에서 보임
  • 순서: A는 B보다 먼저 일어난 것으로 간주됨

중요한 건 단순한 시간적 선후가 아니라는 거예요. 물리적 시계로 A가 먼저 일어났더라도 happens-before 관계가 없으면 B에서 A의 결과가 안 보일 수 있어요. 반대로 happens-before 관계가 성립하면 어떤 환경에서도 가시성과 순서가 보장돼요.

happens-before가 성립하는 6가지 규칙

JLS 17.4.5가 정의하는 핵심 규칙들이에요.

1. Program Order (프로그램 순서)

같은 스레드 안에서 코드 순서대로 happens-before. 가장 기본적인 보장이에요. 

// 같은 스레드에서
x = 1;        // ①
y = 2;        // ②
// ① happens-before ②

2. Monitor Lock (모니터 락)

한 모니터의 unlock은 그 모니터의 다음 lock보다 happens-before. synchronized가 가시성을 보장하는 근거가 이 규칙이에요. 

// Thread A
synchronized (lock) {
    x = 1;
}   // unlock — A가 쓴 모든 변경이 메모리에 flush

// Thread B
synchronized (lock) {   // lock — 메모리에서 새로 읽음
    int v = x;          // A의 x = 1이 보장됨
}

synchronized가 단순한 mutex 이상으로 동작하는 이유가 여기예요. 락을 잡고 푸는 행위 자체에 메모리 가시성이 묶여 있어요.

3. Volatile Variable (volatile 변수)

volatile 변수의 write는 그 변수의 다음 read보다 happens-before. 그래서 위의 worker 시나리오는 volatile boolean running으로 풀려요.

4. Thread Start (스레드 시작)

Thread.start()를 호출한 스레드의 모든 동작은 새 스레드의 모든 동작보다 happens-before. 그래서 새 스레드가 부모의 변수를 별도 동기화 없이 볼 수 있어요. 

data = "ready";              // ①
new Thread(() -> {
    System.out.println(data); // ② "ready" 보장
}).start();

5. Thread Join (스레드 종료 대기)

한 스레드의 모든 동작은 다른 스레드의 그 스레드에 대한 join() 반환 이후 동작보다 happens-before. 

Thread t = new Thread(() -> {
    result = compute();
});
t.start();
t.join();
System.out.println(result);   // 자식 스레드의 결과 보장

6. Transitivity (전이성)

A happens-before B이고 B happens-before C면 A happens-before C. 위 규칙들을 조합해 더 복잡한 관계를 정당화해요.

synchronized의 진짜 힘 — 일반 변수도 보장

synchronized의 가시성 보장은 락 변수에만 한정되지 않아요. 락 안에서 만진 모든 일반 변수의 가시성까지 보장해요. Program Order + Monitor Lock + Transitivity의 결합이에요. 

// Thread A
data = computeData();      // ① 일반 변수 쓰기
synchronized (lock) {
    state = "ready";       // ② 락 안의 쓰기
}                          // ③ unlock

// Thread B
synchronized (lock) {      // ④ lock
    if ("ready".equals(state)) {
        use(data);          // ⑤ A가 ①에서 쓴 data가 보장됨
    }
}

관계를 따라가면 ① → ② → ③ → ④ → ⑤. 전이성으로 ① happens-before ⑤가 성립. A가 락 잡기 전에 쓴 일반 변수까지 B에서 안전하게 볼 수 있어요.

synchronized가 보장하는 3가지

synchronized가 단순한 mutex가 아니라 다음 셋을 모두 보장해요.

1. 원자성 (Atomicity)

임계 영역의 코드는 한 스레드만 실행. count++ 같은 read-modify-write가 인터럽트되지 않음. 1편의 race condition을 풀어주는 부분이에요.

2. 가시성 (Visibility)

락 진입 시 다른 스레드가 unlock으로 flush한 변경사항이 보임. 캐시 무효화 → 메인 메모리에서 다시 읽음. 락 해제 시 임계 영역 안 모든 변경이 메인 메모리로 flush.

3. 순서 (Ordering)

임계 영역의 코드 순서가 보장됨. 컴파일러나 CPU가 임계 영역 안의 코드를 락 밖으로 옮길 수 없어요. "락 안의 동작"과 "락 밖의 동작" 사이에 메모리 배리어가 박혀요.

메모리 배리어 (Memory Barrier)

synchronized의 가시성/순서 보장은 결국 CPU 명령어 수준의 메모리 배리어로 구현돼요. JVM이 monitorenter/monitorexit 시점에 자동으로 삽입.

이벤트배리어 효과
monitorenter (락 획득) Acquire 배리어. 락 밖 코드를 안으로 못 옮기게 + 캐시 무효화
monitorexit (락 해제) Release 배리어. 락 안 코드를 밖으로 못 옮기게 + 메인 메모리 flush

x86 CPU는 강한 메모리 모델이라 자동으로 보장되는 부분이 많아요. ARM 같은 약한 모델에서는 명시적 dmb 같은 명령어가 삽입돼요. JMM이 이런 CPU 차이를 추상화해서 자바 개발자는 happens-before만 의식하면 되는 거예요.

volatile과 synchronized의 비교

비슷해 보이지만 보장 범위가 달라요.

측면volatilesynchronized
원자성 X (단순 read/write만) O (임계 영역 전체)
가시성 O O
순서 O O
비용 매우 가벼움 (배리어 1번) 락 + 배리어
여러 변수 묶음 X O
적합한 자리 boolean flag, 단일 변수 read/write 복합 연산, 여러 변수 보호

volatile이 부족한 자리

volatile int count = 0;

void increment() {
    count++;   // race condition. volatile은 원자성 보장 안 함
}

count++는 read-modify-write라서 volatile로는 안전 못 해요. 가시성은 보장되지만 원자성이 빠져요. 이런 경우는 AtomicInteger 또는 synchronized로 가야 해요.

volatile로 충분한 자리

// 원래 worker 시나리오
class Worker {
    private volatile boolean running = true;   // ← volatile 추가

    void run() {
        while (running) { /* 작업 */ }
    }

    void stop() {
        running = false;
    }
}

단순 boolean flag라 read/write가 원자적. 가시성만 추가하면 됨. 이런 경우는 synchronized보다 volatile이 가볍고 의도가 명확해요.

Double-Checked Locking — 고전 함정

싱글턴을 lazy하게 만들면서 락 비용을 최소화하려는 패턴. 1990년대부터 유명한데 잘못 구현하면 깨져요.

Java 5 이전 — 깨진 구현

class Singleton {
    private static Singleton instance;

    public static Singleton getInstance() {
        if (instance == null) {
            synchronized (Singleton.class) {
                if (instance == null) {
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}

의도는 명확해요. 첫 호출만 락 잡고, 이후엔 락 없이 빠르게 read. 그런데 Java 5 이전에는 이 코드가 깨졌어요. 객체 생성 과정의 재정렬 때문.

객체 생성의 분해

instance = new Singleton()은 단일 연산이 아니에요. 세 단계로 분해돼요.

  1. 메모리 할당
  2. 생성자 호출 (필드 초기화)
  3. instance 변수에 참조 대입

컴파일러가 1 → 3 → 2 순서로 재정렬할 수 있어요. 이때 다른 스레드가 첫 번째 if (instance == null) 검사에서 참조는 있지만 생성자가 끝나지 않은 객체를 보게 돼요. 반쯤 만들어진 객체 사용 → 미정의 동작.

Java 5+ 해결 — volatile

class Singleton {
    private static volatile Singleton instance;   // ← volatile 추가

    public static Singleton getInstance() {
        if (instance == null) {
            synchronized (Singleton.class) {
                if (instance == null) {
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}

한 글자 추가. instance에 대한 쓰기가 volatile write가 되고, 그 이전의 모든 작업(생성자 안의 필드 초기화)이 다른 스레드의 volatile read에서 모두 보여요. 재정렬도 차단되니 반쯤 만들어진 객체를 보는 일이 사라져요.

더 단순한 대안 — 정적 내부 클래스

class Singleton {
    private Singleton() {}

    private static class Holder {
        private static final Singleton INSTANCE = new Singleton();
    }

    public static Singleton getInstance() {
        return Holder.INSTANCE;
    }
}

JVM의 클래스 로딩 메커니즘이 thread-safe해요. Holder 클래스는 getInstance()가 처음 호출될 때만 로드되고 INSTANCE가 초기화돼요. DCL의 미묘한 함정 없이 같은 lazy 초기화 + thread-safety. 새 코드라면 이쪽이 권장돼요.

final 필드의 가시성 — 짚어둘 만한 디테일

한 가지 자주 잊히는 부분. final 필드는 생성자 안에서 쓴 값이 별도 동기화 없이 다른 스레드에 안전하게 보여요. immutable 객체를 안전하게 공유할 수 있는 보장이에요. 

class Config {
    final String url;
    final int timeout;

    Config(String url, int timeout) {
        this.url = url;
        this.timeout = timeout;
    }
}

// Thread A
Config c = new Config("https://...", 5000);
sharedRef = c;   // 다른 스레드와 공유

// Thread B
if (sharedRef != null) {
    System.out.println(sharedRef.url);   // 안전. 쓰레기 값 안 봄
}

단, 한 가지 함정이 있어요. 생성자 안에서 this가 외부로 escape하면 이 보장이 깨져요. 

class Listener {
    final String name;

    Listener(String name, EventBus bus) {
        bus.register(this);   // ★ 위험. 생성자 안에서 this escape
        this.name = name;
    }
}

다른 스레드가 EventBus를 통해 이 객체에 접근할 때 name이 아직 null일 수 있어요. final 보장이 무너져요. 생성자 안에서 자기를 다른 객체에 등록하는 패턴은 피해야 해요.

Sequential Consistency가 아닌 이유

가끔 받는 질문. "JMM이 모든 스레드가 같은 명령어 순서를 보게 하면 안 되나요?" 이론적으로는 sequential consistency라고 부르는 더 강한 모델이에요. 그런데 자바는 이걸 채택하지 않았어요.

이유는 성능. sequential consistency를 보장하려면 CPU와 컴파일러의 최적화 자유를 크게 제약해야 하고, 매 메모리 접근에 비싼 배리어가 필요해요. 현실 워크로드의 99%는 그런 강한 보장이 필요 없어요.

JMM은 더 약한 모델 — happens-before 관계로 명시된 부분만 보장. 개발자가 동기화 도구(synchronized, volatile)를 적절히 쓰면 정확성 보장. 그 외 부분은 CPU와 컴파일러에 자유를 주는 거래예요.

단, 이 약한 모델 때문에 멀티스레드 코드는 명시적인 동기화가 필수예요. 그렇지 않으면 어떤 결과가 나올지 보장 안 돼요. 데이터 레이스(data race)라 불리는 상태.

실무 가이드

1. 공유 변수에는 항상 동기화

여러 스레드가 접근하는 변수에는 반드시 synchronized, volatile, Atomic 중 하나로 동기화. 그렇지 않으면 어떤 결과가 나올지 보장 안 돼요. "내 코드에서는 잘 되는데 운영에서 가끔 깨진다"는 거의 모두 이 누락이 원인.

2. immutable이 가장 안전

공유 객체를 immutable로 만들면 동기화 자체가 필요 없어요. final 필드 + 생성자에서만 초기화 + setter 없음. 가능하면 mutable 공유를 피하는 게 가장 좋은 방법.

3. happens-before 머릿속에 그리기

멀티스레드 코드를 짤 때 "여기 쓴 값이 저기서 보일 수 있나?"를 happens-before 관계로 검증하는 습관. synchronized, volatile, Thread.start, Thread.join이 다리를 놓는 도구예요. 다리가 없으면 가시성 보장 없음.

4. 도구 선택 우선순위

  1. 가능하면 immutable로 (동기화 불필요)
  2. 단일 변수 read/write만 → volatile
  3. 단일 변수 read-modify-write → Atomic
  4. 여러 변수 묶음 또는 복합 연산 → synchronized
  5. 정교한 락 기능 필요 → ReentrantLock
  6. 고수준 자료구조로 충분 → ConcurrentHashMap, BlockingQueue 등

면접 단골 질문

Q. synchronized가 보장하는 것은요?

세 가지예요. 원자성(임계 영역의 한 스레드만 실행), 가시성(락 진입 시 다른 스레드의 변경 보임), 순서(임계 영역 코드가 락 밖으로 재정렬 안 됨). 단순한 mutex 이상의 보장이에요. JMM의 happens-before 관계 중 Monitor Lock 규칙이 이걸 형식적으로 정의해요.

Q. happens-before가 뭔가요?

JMM의 핵심 개념이에요. "A happens-before B"는 A의 결과가 B에서 보이는 것이 보장된다는 형식적 관계예요. 단순한 시간적 선후가 아니라 보장된 가시성과 순서를 의미. Program Order, Monitor Lock, Volatile, Thread Start/Join, Transitivity 6가지 규칙으로 이 관계를 만들 수 있어요.

Q. volatile과 synchronized는 어떻게 다른가요?

volatile은 가시성과 순서만 보장하고 원자성은 X. 단순 read/write에만 안전. count++ 같은 복합 연산은 깨져요. synchronized는 셋 다 보장. 임계 영역 전체가 atomic하고, 여러 변수의 일관성도 보장. 단순 boolean flag면 volatile, 복합 연산이나 여러 변수면 synchronized 또는 Atomic이에요.

Q. Double-Checked Locking이 왜 깨졌나요?

객체 생성이 단일 연산이 아니라 [메모리 할당 → 생성자 호출 → 참조 대입] 세 단계로 분해되고, 이게 재정렬되면 다른 스레드가 반쯤 만들어진 객체를 볼 수 있어요. Java 5+에서 instance 필드에 volatile을 붙여 재정렬을 막아서 풀어요. 더 단순한 대안은 정적 내부 클래스(Holder pattern)로, JVM의 클래스 로딩 메커니즘이 thread-safe라 자연스럽게 lazy + 안전.

한 줄 정리

synchronized는 mutex 이상이에요. 원자성 + 가시성 + 순서를 모두 보장. 가시성은 JMM의 Monitor Lock 규칙으로 정의되고, 락 안에서 만진 모든 변수의 가시성이 다른 스레드에 전파돼요. 단순 flag는 volatile, 복합 연산은 synchronized나 Atomic. immutable이 가능하면 동기화 자체가 필요 없어 가장 좋아요.

synchronized 시리즈는 여기까지예요. 한 키워드 뒤에 모니터 락, Mark Word, 락 진화 4단계, JMM과 happens-before, 메모리 배리어가 다 들어있는 게 보였길 바라요.
