풀려는 문제 — Race Condition

가장 단순한 카운터 코드부터 시작해볼게요. 여러 스레드가 같은 카운터를 증가시키는 시나리오예요. 

class Counter {
    private int count = 0;

    public void increment() {
        count++;
    }
}

코드는 한 줄짜리지만 count++가 단일 연산이 아니에요. 자바 바이트코드 수준에서 세 단계로 분해돼요.

  1. load: 메모리에서 현재 count 값 읽기
  2. compute: +1 계산
  3. store: 새 값을 메모리에 쓰기

여러 스레드가 동시에 호출하면 이 세 단계 사이에 다른 스레드가 끼어들 수 있어요. 두 스레드가 같은 시점에 0을 읽고, 각자 1을 만들어 쓰면 결과는 1. 한 번의 증가가 사라지는 거예요.

실제로 깨지는 동작

이게 추상적이지 않은 진짜 문제인지 보여주는 짧은 데모예요. 1000 스레드가 각각 1000번 increment 한다고 해볼게요. 기대값은 1,000,000. 

Counter c = new Counter();
ExecutorService pool = Executors.newFixedThreadPool(1000);
CountDownLatch latch = new CountDownLatch(1000);

for (int i = 0; i < 1000; i++) {
    pool.submit(() -> {
        for (int j = 0; j < 1000; j++) c.increment();
        latch.countDown();
    });
}
latch.await();
System.out.println(c.getCount());   // 매번 다른 값. 보통 70만~80만대

돌릴 때마다 결과가 다르게 나와요. 1,000,000이 나오는 일은 거의 없어요. 이걸 race condition(경쟁 상태)이라 부르고, count++가 일어나는 코드를 임계 영역(critical section)이라고 해요. synchronized는 이 문제를 막는 가장 기본적인 도구예요.

synchronized의 두 가지 사용법

방법 1 — 메서드에 붙이기

public synchronized void increment() {
    count++;
}

가장 단순한 형태. 메서드 진입 시 this의 모니터 락을 획득하고, 종료 시 해제해요. 같은 인스턴스의 다른 synchronized 메서드를 다른 스레드가 호출하려 하면 그 락에서 대기.

static 메서드에 붙이면 this가 없으니 클래스 객체(Class)의 락을 사용해요. 

public static synchronized void doSomething() {
    // Counter.class의 모니터 락 획득
}

방법 2 — 블록에 붙이기

private final Object lock = new Object();

public void increment() {
    synchronized (lock) {
        count++;
    }
}

명시적으로 락 객체를 지정하는 방식. 임계 영역을 좁게 잡을 수 있고, 락 객체를 분리해 다른 락과 독립 운용 가능해요. 더 유연하고 권장되는 형태예요.

왜 블록이 더 권장되나요

  • 임계 영역 최소화: 메서드 일부만 보호. 락 보유 시간이 짧을수록 처리량이 높아요
  • 외부 노출 회피: this는 외부에서도 접근 가능. 누군가 synchronized(myInstance)로 락을 잡으면 의도치 않은 경합 발생
  • 전용 락 객체: private final Object lock으로 외부에서 접근 불가능한 락 사용 권장
  • 여러 락 분리 가능: 한 클래스 안에서 다른 자원을 다른 락으로 보호 가능

모니터 락 — 모든 객체에 내장된 mutex

synchronized의 핵심 메커니즘은 모니터 락(monitor lock)이에요. 자바의 모든 객체는 본질적으로 모니터를 하나씩 가지고 있어요.

모니터는 1973년 Per Brinch Hansen과 Tony Hoare가 제안한 동시성 추상화예요. 두 부분으로 구성돼요.

  • Mutex (상호 배제): 한 번에 한 스레드만 진입 가능
  • Condition Variable: wait/notify로 조건 대기 (별도 주제)

자바는 이 모니터 추상화를 모든 객체에 직접 통합했어요. 그래서 어느 객체든 synchronized의 락 객체로 사용 가능. 별도의 락 객체 클래스가 필요 없어요.

이 모니터 락이 객체의 어디에 어떻게 저장되는지는 다음 편의 주제예요. 객체 헤더의 Mark Word라는 자리에 압축되어 들어가요.

JVM 바이트코드로 보는 synchronized

synchronized 블록이 JVM 바이트코드 수준에서 어떻게 표현되는지 보면 메커니즘이 더 분명해져요. 

synchronized (lock) {
    count++;
}

이 코드를 컴파일하면 다음 바이트코드가 나와요. 

aload_1               // lock 객체 스택에 로드
monitorenter          // 락 획득
// count++ 코드
aload_1
monitorexit           // 락 해제

JVM 명령어 두 개(monitorenter, monitorexit)가 락 획득과 해제를 처리해요. 예외 발생 시에도 monitorexit가 호출되도록 try-finally 같은 핸들러가 자동으로 추가돼요.

synchronized 메서드의 경우는 약간 달라요. 메서드 자체에 ACC_SYNCHRONIZED 플래그만 표시되고, JVM이 메서드 진입/종료 시 자동으로 락을 처리해요. 명시적인 monitorenter/monitorexit 명령어는 안 들어가지만 효과는 동일해요.

재진입성 (Reentrancy)

중요한 성질 하나. 자바의 모니터 락은 재진입 가능해요. 같은 스레드가 이미 가지고 있는 락을 다시 잡아도 통과돼요. 

public synchronized void outer() {
    inner();   // 같은 락(this)을 다시 잡아야 하지만 같은 스레드라 통과
}

public synchronized void inner() {
    // 작업
}

재진입성이 없으면 어떻게 될까요? outer가 this 락을 잡고 들어왔는데, inner도 같은 락을 잡으려 하면 자기가 자기를 막는 상황. 영원히 대기하는 데드락이 발생해요.

그래서 모니터 락은 진입 카운트를 내부적으로 유지해요. 같은 스레드가 N번 잡으면 카운트가 N. 같은 횟수만큼 풀어야 락이 진짜 해제돼요. ReentrantLock의 이름도 같은 이유예요.

락의 단위 — 무엇을 보호하나요

synchronized는 객체 단위로 락을 잡아요. 같은 객체의 synchronized 메서드들은 서로 직렬화되지만, 다른 객체는 독립적이에요. 

Counter c1 = new Counter();
Counter c2 = new Counter();

// 스레드 A: c1.increment()
// 스레드 B: c2.increment()  → 동시 실행 가능 (다른 객체, 다른 락)

// 스레드 A: c1.increment()
// 스레드 B: c1.decrement()  → 직렬화 (같은 'this' 락)

흔한 실수 — 잘못된 락 단위

같은 데이터를 보호하는데 다른 락을 쓰면 동시성 보장이 깨져요. 

// 잘못된 패턴
class Counter {
    private final Object lockA = new Object();
    private final Object lockB = new Object();
    private int count = 0;

    public void increment() {
        synchronized (lockA) { count++; }
    }

    public void decrement() {
        synchronized (lockB) { count--; }
    }
}

increment와 decrement가 다른 락이라 동시 진입 가능. count가 깨질 수 있어요. 한 데이터를 보호하는 모든 임계 영역은 같은 락으로 보호해야 해요. 기본 원칙이에요.

여러 락으로 분리하는 패턴

반대로 정말 다른 자원이라면 다른 락으로 분리하는 게 처리량에 좋아요. 

class TwoCounters {
    private final Object readerLock = new Object();
    private final Object writerLock = new Object();
    private int reads = 0;
    private int writes = 0;

    public void recordRead() {
        synchronized (readerLock) { reads++; }
    }

    public void recordWrite() {
        synchronized (writerLock) { writes++; }
    }
}

read 카운터와 write 카운터를 다른 락으로 두면 두 스레드가 동시에 각각 갱신 가능. ConcurrentHashMap의 버킷 단위 락(bin-level locking)도 같은 사고방식의 확장이에요.

synchronized vs ReentrantLock

자바 5에서 도입된 java.util.concurrent.locks.ReentrantLock은 더 정교한 락 도구예요. synchronized와 어떻게 다른지 정리해볼게요.

측면synchronizedReentrantLock
형태 키워드, 자동 해제 명시적 lock/unlock 호출
JVM 최적화 O (biased/lightweight 등) 제한적
tryLock X O (timeout 가능)
인터럽트 가능 락 대기 X O (lockInterruptibly)
공정성(fair) 모드 X O (생성자 옵션)
Condition 1개 (wait/notify) 여러 개 가능 (newCondition)
실수 위험 낮음 (자동 해제) 높음 (try-finally 필수)

각각 어떤 자리에 어울리나요

단순한 임계 영역이면 synchronized가 좋아요. 코드 간결하고 자동 해제, JVM이 알아서 최적화해요. 타임아웃, 인터럽트 가능 대기, 공정성 같은 정교한 기능이 필요하면 ReentrantLock. 단, ReentrantLock은 try-finally로 unlock을 반드시 호출해야 해서 실수 위험이 있어요. 

// ReentrantLock 표준 패턴
ReentrantLock lock = new ReentrantLock();
lock.lock();
try {
    // 작업
} finally {
    lock.unlock();   // 반드시 호출
}

java.util.concurrent와의 관계

synchronized는 자바의 가장 오래된 동시성 도구예요(자바 1.0). j.u.c 패키지의 거의 모든 락 도구가 synchronized 시대의 한계를 풀려는 시도예요.

  • ReentrantLock: synchronized + tryLock/timeout/공정성
  • ReadWriteLock: 읽기는 동시에, 쓰기는 단독
  • StampedLock: optimistic read 추가
  • AtomicXXX: 단일 변수 락 없이 CAS로
  • ConcurrentHashMap: 자료구조 자체가 동시성

이런 도구들이 등장한 뒤로 synchronized 사용 빈도가 줄었지만, 여전히 가장 단순한 임계 영역에는 표준 도구예요. JVM이 워낙 최적화가 잘 되어 있어 일반 워크로드에서는 ReentrantLock과 성능 차이가 거의 없어요.

흔한 함정 — 어떤 객체로 락 잡을까

함정 1 — String literal로 락

// 매우 위험
synchronized ("LOCK") {
    // ...
}

String literal은 String pool에서 공유돼요. 다른 코드가 같은 문자열로 락 잡으면 의도치 않게 같은 락 공유. 전혀 무관한 코드가 서로 막아버리는 사고 발생.

함정 2 — Integer/Boolean 박싱 객체

// 위험
private Integer counter = 0;

synchronized (counter) {
    counter++;   // counter 참조가 바뀜
    // 다른 스레드는 옛날 Integer로 락 잡고 있을 수 있음
}

counter++ 결과 새 Integer 객체가 생성되어 변수 참조가 바뀌어요. 다음 스레드는 새 객체로 락을 잡으니 보호가 안 돼요. 또 작은 Integer는 캐시되어 공유될 위험도 있어요.

함정 3 — 변경되는 필드로 락

// 위험
class Container {
    private List<String> data = new ArrayList<>();

    public void operation() {
        synchronized (data) {
            // ...
        }
    }

    public void replace() {
        data = new ArrayList<>();   // 락 객체가 바뀜
    }
}

data를 락으로 쓰는데 그 참조가 바뀔 수 있으면 의미 없어요. 락은 final 필드로 두는 게 원칙.

권장 패턴 — private final Object

class SafeCounter {
    private final Object lock = new Object();   // ← 권장
    private int count = 0;

    public void increment() {
        synchronized (lock) {
            count++;
        }
    }
}

private final Object 패턴이 가장 안전해요. 외부 노출 없음, 변경 불가, 의도가 명확.

면접 단골 질문

Q. synchronized는 어떻게 동작하나요?

모든 자바 객체에 내장된 모니터 락을 사용해요. 메서드 또는 블록에 붙이면 진입 시 락 획득, 종료 시 해제. JVM 바이트코드 수준에서 monitorenter/monitorexit 명령어로 구현돼요. 같은 락에 대한 임계 영역들은 직렬화되어 race condition을 막아요.

Q. synchronized 메서드와 블록의 차이는요?

메서드는 this(static이면 클래스 객체) 락을 자동 사용, 메서드 전체가 임계 영역이에요. 블록은 명시한 락 객체로 좁은 영역만 보호. 블록이 더 유연하고 권장돼요. private final Object를 락으로 쓰면 외부 노출 없이 안전하게 사용 가능.

Q. 재진입성이 뭔가요?

같은 스레드가 이미 잡고 있는 락을 다시 잡을 수 있는 성질이에요. 자바 모니터 락은 기본 재진입 가능. 진입 카운트를 유지해서 같은 횟수만큼 풀어야 해제돼요. 재진입 안 되면 자기가 자기를 막아 데드락 발생. ReentrantLock도 같은 이유로 재진입 보장.

Q. synchronized로 String literal에 락 잡으면 안 되나요?

매우 위험해요. String literal은 String pool에서 공유되어 다른 무관한 코드가 같은 문자열로 락 잡으면 충돌. 전역 락처럼 동작해서 처리량 폭락. Integer 같은 작은 박싱 객체도 캐시 공유로 비슷한 위험. 항상 private final Object로 전용 락 객체를 만들어 쓰는 게 안전해요.

한 줄 정리

synchronized는 자바의 가장 기본적인 임계 영역 도구예요. 모든 객체에 내장된 모니터 락을 사용해 한 번에 한 스레드만 진입 보장. 블록 형태에 private final Object 락이 권장 패턴이에요. 재진입 가능하고, JVM이 최적화를 잘 해줘서 일반 워크로드에 충분. 정교한 기능(timeout, 공정성)이 필요하면 ReentrantLock을 검토.

다음 편에서는 그 모니터 락이 객체의 어디에 어떻게 저장되는지, 어떻게 진화해왔는지 들어가요. Mark Word, biased lock, lightweight lock, heavyweight lock의 4단계 메커니즘이에요.
