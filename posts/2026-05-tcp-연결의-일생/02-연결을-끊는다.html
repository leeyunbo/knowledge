연결을 끊는 데 왜 4번이나 걸리나

만들 땐 3번, 끊을 땐 4번. 그 차이가 어디서 오는지. 그리고 끊는 도중에 멈춰버리는 CLOSE_WAIT의 정체.

Series
TCP 연결의 일생
  1. TCP 연결을 만든다는 것
  2. 연결을 끊는 데 왜 4번이나 걸리나
  3. TIME_WAIT가 ephemeral port를 잡아먹는다

만들 땐 3번이었는데

앞 편에서 TCP 연결은 3-way handshake로 만들어진다고 봤다. SYN, SYN-ACK, ACK 세 패킷이 오가면 끝이다. 그런데 끊을 땐 패킷이 4번 오간다. 왜 한 번이 더 늘어났을까.

답은 TCP가 전이중(full-duplex) 통신이라는 데 있다. 연결 한 개에 송신 채널과 수신 채널이 따로 있다. 그래서 끊을 때도 두 채널을 각각 닫아야 한다. 한 쪽이 "나는 더 안 보낼게"라고 해도, 다른 쪽은 아직 보낼 게 남아있을 수 있다.

4-way handshake 분해 — RFC 9293

TCP 종료 절차를 RFC 9293은 이렇게 정의한다. A가 먼저 끊는다고 하자. 

[A]                                   [B]
 │ ── FIN ──────────────────────▶      │   A: "내 송신 끝났어"
 │ ◀── ACK ─────────────────────       │   B: "알겠어"
 │                                     │
 │   ... B는 아직 보낼 게 남았으면         │
 │       이 동안 계속 A에게 보낸다         │
 │                                     │
 │ ◀── FIN ─────────────────────       │   B: "이제 내 송신도 끝났어"
 │ ── ACK ──────────────────────▶      │   A: "알겠어"

A의 FIN으로 A→B 방향 채널이 닫힌다. 하지만 B→A 방향은 아직 살아있다. B가 자기 일을 다 마친 다음에야 자기 FIN을 보낸다. 이렇게 양방향이 독립적으로 종료되니 패킷이 4번 필요하다.

3-way handshake에서는 ACK와 SYN을 한 패킷에 묶을 수 있어서 3번이었다. 종료 시에는 B의 ACK와 FIN 사이에 시간 간격이 있을 수 있어서 하나로 묶을 수가 없다. B가 보낼 데이터가 남아있을 수 있기 때문이다.

half-close — 한 방향만 닫는 진짜 사례

이론으로만 들리지만 half-close는 실제로 자주 쓰인다. 대표 사례가 SSH의 파일 전송이다. 

cat large_file | ssh remote "sha256sum"

로컬에서 파일을 SSH로 흘려보내고, 원격에서 해시를 계산해 받는 명령이다. 로컬은 파일을 다 보내고 나면 송신 채널을 닫는다(FIN). 원격은 그제서야 입력이 끝난 걸 알고 해시 결과를 출력한다. 그 해시가 다시 로컬로 흘러와야 하니까 수신 채널은 살아있어야 한다.

이런 패턴을 지원하려면 양방향을 따로 닫을 수 있어야 한다. 그래서 4-way가 필요하다.

TCP 상태 머신 — 끊는 동안 어디 머무는가

종료 절차에서 양쪽은 각각 다른 상태를 거친다. 먼저 끊는 쪽(active close)과 받는 쪽(passive close)이 서로 다르다. 

Active close (먼저 FIN 보낸 쪽)
  ESTABLISHED ──FIN 보냄──▶ FIN_WAIT_1
  FIN_WAIT_1  ──ACK 받음──▶ FIN_WAIT_2
  FIN_WAIT_2  ──FIN 받음──▶ TIME_WAIT
  TIME_WAIT   ──ACK 보냄, 60초 대기──▶ CLOSED

Passive close (FIN 받은 쪽)
  ESTABLISHED ──FIN 받음──▶ CLOSE_WAIT
  CLOSE_WAIT  ──애플리케이션이 close() 호출, FIN 보냄──▶ LAST_ACK
  LAST_ACK    ──ACK 받음──▶ CLOSED

Active close 쪽이 마지막에 들르는 TIME_WAIT가 60초나 머무는 이유, 그리고 그게 왜 외부 API 호출 많은 클라이언트에게 골치 아픈지는 다음 편에서 다룬다. 이 편에서 짚을 건 그 사촌 격인 CLOSE_WAIT이다.

CLOSE_WAIT — 끝내야 하는데 안 끝내는 상태

CLOSE_WAIT는 passive close 쪽에 생긴다. 상대가 FIN을 보냈고, 우리 OS는 그걸 받아서 ACK까지 잘 보냈다. 여기까지가 CLOSE_WAIT 진입. 이 상태에서 빠져나가려면 우리 애플리케이션이 close()를 호출해줘야 한다. 

[Server: Kakao]                       [Client: 우리 GW]
   │ ── FIN ──────────────────▶          │   "더 안 보낼 거야"
   │ ◀── ACK ─────────────────           │   OS가 자동 응답
   │                                      │   상태: CLOSE_WAIT
   │                                      │
   │   ↑ 여기서 멈춰있는 connection들       │
   │     OS 입장에선 "애플리케이션이         │
   │     close() 부르길 기다리는 중"        │

OS는 "FIN 받았으니 너도 close() 좀 불러"라고 기다리는 셈이다. 하지만 우리 코드가 close()를 안 부르면 CLOSE_WAIT는 영원히 풀리지 않는다. 그래서 CLOSE_WAIT가 쌓인다는 건 거의 항상 애플리케이션 버그 신호다.

왜 close()를 빼먹게 되나

가장 흔한 패턴은 예외 처리. 

// 잘못된 패턴
Socket socket = new Socket(host, port);
InputStream in = socket.getInputStream();
process(in);              // 여기서 예외 터지면
socket.close();           // 이 줄까지 안 옴 → CLOSE_WAIT 발생

process()에서 예외가 터지면 socket.close()는 실행 안 되고, 이 socket은 CLOSE_WAIT로 남는다. 요청 1건이 1개의 leak. 트래픽 많으면 시간 지나면서 누적된다.

해법은 try-with-resources나 finally 블록. 

try (Socket socket = new Socket(host, port);
     InputStream in = socket.getInputStream()) {
    process(in);
}   // 예외 터져도 close() 자동 호출

또 한 패턴은 connection pool 라이브러리가 잘못 작성된 경우. 상대가 FIN을 보내서 끊었는데 풀 매니저가 그 socket을 다시 풀에 반납해버리고, 반납된 socket은 close() 호출 없이 그냥 풀에 누워있는 경우다. Apache HttpClient5 같은 성숙한 라이브러리는 자체적으로 idle eviction과 stale connection 검증을 가지고 있어 이 문제를 줄인다.

증상은 file descriptor 고갈

CLOSE_WAIT 하나가 file descriptor 하나를 점유한다. Linux는 프로세스당 file descriptor 상한이 있고, 보통 기본값이 1024나 4096이다. 

$ ulimit -n
4096

CLOSE_WAIT가 수천 개 누적되면 새 socket(또는 파일) 못 연다. 증상은 갑작스런 "Too many open files" 에러. 처음엔 멀쩡하다가 며칠 운영 후 터지는 게 특징이다. 누수니까.

진단 — 우리 서버에 CLOSE_WAIT 얼마나 쌓였나

$ netstat -an | awk '/^tcp/ {print $6}' | sort | uniq -c
   3 CLOSE_WAIT
  18 ESTABLISHED
   2 LISTEN
 152 TIME_WAIT

ESTABLISHED와 비슷한 수의 CLOSE_WAIT면 즉시 사라지는 일시 상태일 수 있다. 하지만 ESTABLISHED보다 CLOSE_WAIT가 더 많거나, 시간이 지나도 줄지 않으면 그건 leak이다. 

$ ss -tan state close-wait

이 명령으로 CLOSE_WAIT인 socket과 그 상대 주소를 다 볼 수 있다. 어느 외부 서비스와의 connection이 새고 있는지 추적 가능하다.

정리

연결을 끊는 데 4번이 필요한 이유는 단순하다. TCP는 양방향이고, 양방향을 따로 닫아야 하니까. 이 4번 중 어느 단계에서든 양쪽이 다른 속도로 움직일 수 있다.

그중 가장 위험한 단계가 CLOSE_WAIT다. 상대는 끊자고 했는데 우리가 close() 호출을 빼먹으면 그 socket은 영원히 시스템 자원을 잡고 있다. try-with-resources를 습관처럼 쓰는 이유가 여기 있다.

그런데 정작 정상 종료한 쪽도 60초 동안 빠져나가지 못한다. TIME_WAIT다. 다음 편에서 그 60초의 정체와, 왜 그게 외부 API 호출 많은 클라이언트의 ephemeral port를 갉아먹는지 본다.
