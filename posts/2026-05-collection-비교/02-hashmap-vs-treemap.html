Map의 세 구현

자바의 Map 인터페이스에는 자주 쓰는 구현이 세 가지 있어요. 내부 자료구조와 순서 보장 방식이 달라요.

구현내부 구조순서주요 시간 복잡도
HashMap해시 테이블 (배열 + 버킷)없음평균 O(1)
LinkedHashMap해시 테이블 + 이중 연결 리스트삽입 순서 (또는 접근 순서)평균 O(1)
TreeMapRed-Black Tree키 정렬 순서O(log n)

HashMap, 기본값

해시 기반이라 평균 O(1)로 빠르고 메모리 효율도 좋아요. 자세한 내부는 별도 시리즈에서 다뤘어요(HashMap 내부 시리즈 참조). 여기선 다른 구현과의 비교만 해요.

HashMap의 특성

  • 빠름: 키 해시로 버킷을 바로 찾아요.
  • 순서 없음: iteration 순서가 보장되지 않아요. JVM 버전·해시 분포에 따라 달라요.
  • null 허용: 키 1개, 값 여러 개 null 가능.
  • 스레드 안전 아님: 동시성 필요하면 ConcurrentHashMap.

실무에서 쓰는 자리

"키-값 매핑이 필요하다"는 거의 모든 자리예요. 캐시·인덱스·사전 같은 일반 용도면 HashMap이 기본이에요.

LinkedHashMap, 순서가 필요할 때

HashMap에 이중 연결 리스트를 더한 구조예요. 각 엔트리가 해시 버킷 안에 있으면서, 동시에 입력 순서대로 prev/next로 연결돼 있어요. 

// LinkedHashMap의 엔트리 (단순화)
static class Entry<K, V> extends HashMap.Node<K, V> {
    Entry<K, V> before, after;  // 입력 순서 연결
}

두 가지 순서 모드

  • 삽입 순서 (insertion-order): 기본값. 넣은 순서대로 순회해요.
  • 접근 순서 (access-order): 생성자에 accessOrder=true. get·put할 때마다 끝으로 이동. LRU 캐시의 토대예요.
// 간단한 LRU 캐시
class LRUCache<K, V> extends LinkedHashMap<K, V> {
    private final int capacity;

    public LRUCache(int capacity) {
        super(16, 0.75f, true);  // accessOrder = true
        this.capacity = capacity;
    }

    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > capacity;
    }
}

removeEldestEntry를 오버라이드하면 자동으로 오래된 항목을 제거해요. 50줄 미만의 LRU 캐시가 만들어져요.

오버헤드

HashMap보다 엔트리당 8~16바이트 더 써요 (before/after 참조). 순회는 오히려 더 빠를 수 있어요. 버킷을 다 훑지 않고 연결 리스트만 따라가요.

TreeMap, 정렬이 필요할 때

Red-Black Tree 기반이에요. 키가 항상 정렬돼 있어서 O(log n)에 모든 연산이 끝나요. Comparator 또는 키의 Comparable로 정렬 기준을 정해요. 

TreeMap<Integer, String> scores = new TreeMap<>();
scores.put(95, "Alice");
scores.put(72, "Bob");
scores.put(88, "Charlie");

// 정렬된 순서로 순회
for (var entry : scores.entrySet()) {
    System.out.println(entry);  // 72=Bob, 88=Charlie, 95=Alice
}

NavigableMap의 강력함

TreeMap은 NavigableMap 인터페이스를 구현해요. "X 이하의 가장 큰 키", "범위 [a, b]의 모든 엔트리" 같은 쿼리를 O(log n)으로 답해요.

메소드의미
floorKey(k)k 이하 가장 큰 키
ceilingKey(k)k 이상 가장 작은 키
higherKey(k)k 초과 가장 작은 키
lowerKey(k)k 미만 가장 큰 키
subMap(from, to)[from, to) 부분 맵
headMap(k) / tailMap(k)k 미만 / k 이상 부분 맵

잘 맞는 자리

  • 범위 쿼리: "100원~500원 구간의 상품" 같은 자리.
  • 가격 시간표: 시간을 키로 두고 floorKey로 "그 시각에 적용된 가격"을 찾는 패턴.
  • 이벤트 스케줄링: 다음 만료 시간을 O(log n)에 찾기.

세 구현 비교 정리

비교HashMapLinkedHashMapTreeMap
get/putO(1)O(1)O(log n)
순서없음삽입/접근키 정렬
null 키 허용1개1개안 됨 (Comparator 없으면)
메모리가장 적음중간가장 많음 (트리 노드)
범위 쿼리XXO(log n)
일반 용도기본 선택순서 필요정렬·범위 필요

의사결정 흐름

  1. 키 순서가 필요해요? → No면 HashMap.
  2. 삽입 순서나 LRU만 필요? → LinkedHashMap.
  3. 키 정렬·범위 쿼리가 필요? → TreeMap.
  4. 스레드 안전이 필요? → ConcurrentHashMap(순서 무관) 또는 ConcurrentSkipListMap(정렬 필요).

실무에서 자주 보는 실수

키의 hashCode·equals 미구현

HashMap·LinkedHashMap의 키는 hashCode와 equals를 일관되게 구현해야 해요. 그렇지 않으면 put한 키를 get으로 못 찾는 사고가 나요. equals/hashCode 계약 시리즈에서 자세히 다뤘어요.

TreeMap 키의 Comparable 누락

TreeMap에 Comparable이 아닌 객체를 키로 넣으면 ClassCastException이 떠요. Comparator를 생성자에 넘기지 않으면요. Comparable을 구현하거나, Comparator를 같이 줘야 해요.

HashMap의 순서 가정

"HashMap의 순서는 입력 순서다"라고 가정하는 코드를 가끔 봐요. JVM 버전이 바뀌면 깨져요. 순서가 필요하면 LinkedHashMap을 명시적으로 써야 해요.

면접에서 자주 나오는 자리

  • "HashMap과 TreeMap 차이?": 해시 vs 트리예요. HashMap은 O(1)에 빠르지만 순서가 없어요. TreeMap은 O(log n)이지만 정렬이 보장돼요.
  • "LinkedHashMap의 LRU 구현?": accessOrder=true와 removeEldestEntry 오버라이드면 끝이에요. 50줄 미만.
  • "범위 쿼리가 필요해요": TreeMap의 subMap·floorKey·ceilingKey를 써요. ConcurrentSkipListMap은 동시성까지 보장해요.
  • "HashMap의 순서가 보장돼요?": 아니요. 입력 순서·자연 순서 다 보장되지 않아요. 순서가 필요하면 LinkedHashMap·TreeMap이에요.
