두 구현의 출발

자바의 List 인터페이스를 구현한 대표 두 클래스예요. 인터페이스가 같으니 API는 거의 같지만, 내부 자료구조가 완전히 달라요. ArrayList는 배열 기반, LinkedList는 이중 연결 리스트 기반이에요. 

List<String> a = new ArrayList<>();
List<String> b = new LinkedList<>();

a.add("x");
b.add("x");

코드만 보면 똑같지만, 안에서 일어나는 일은 전혀 달라요. 어디에 어떤 비용이 드는지가 갈려요.

ArrayList의 내부

내부적으로 Object[]를 가지고 있어요. 기본 용량은 10. 가득 차면 1.5배로 늘려 새 배열에 복사해요. 

// ArrayList 내부 (단순화)
transient Object[] elementData;
private int size;

public boolean add(E e) {
    if (size == elementData.length) {
        grow();  // 1.5배로 새 배열 복사
    }
    elementData[size++] = e;
    return true;
}

접근 패턴

  • 인덱스 접근 (get/set): O(1). 배열 인덱스 한 번이에요.
  • 끝에 추가 (add): amortized O(1). 가끔 grow 비용을 평균해서 그래요.
  • 중간 삽입/삭제: O(n). 뒤의 모든 원소를 한 칸씩 옮겨야 해요.
  • 탐색: O(n). 순차 비교예요.

LinkedList의 내부

이중 연결 리스트예요. 각 노드가 값과 prev/next 포인터를 가져요. 

// LinkedList 내부 (단순화)
private static class Node<E> {
    E item;
    Node<E> next;
    Node<E> prev;
}

transient Node<E> first;
transient Node<E> last;
transient int size;

접근 패턴

  • 인덱스 접근 (get/set): O(n). head나 tail에서부터 노드를 따라 가요. 자바 구현은 인덱스가 size/2보다 크면 tail에서 시작해요.
  • 양 끝 추가/삭제: O(1). first/last 참조만 바꾸면 돼요.
  • 이미 알고 있는 노드의 삽입/삭제: O(1). 포인터 두 개만 바꿔요.
  • 인덱스로 중간 삽입/삭제: O(n). 노드를 찾는 비용이 있어요.

표만 보면 LinkedList가 add(0)·deque 연산에서 유리해 보여요. 실무에서 정말 그럴까가 다음 주제예요.

실제 성능은 거의 항상 ArrayList

Big-O가 같다고 실제 속도가 같진 않아요. 상수 항과 캐시 효과가 결정적이에요.

1. 메모리 지역성 (locality)

ArrayList는 연속된 메모리예요. CPU 캐시 라인이 한 번에 여러 원소를 읽어요. LinkedList는 노드가 힙 여기저기에 흩어져 있어서 매번 캐시 미스가 나요. 순회 속도가 5~10배까지 차이 나기도 해요.

2. 노드 오버헤드

LinkedList의 노드는 값 외에 prev/next 참조 2개와 객체 헤더가 붙어요. 한 원소당 32~40바이트 추가예요. ArrayList는 원소 참조만 있어요. 메모리 효율 차이가 커요.

3. add(0)도 LinkedList가 항상 빠르진 않아요

add(0)은 LinkedList가 O(1), ArrayList가 O(n)이에요. 그런데 ArrayList의 O(n)은 단순 메모리 복사(System.arraycopy)예요. CPU의 SIMD·캐시 친화 명령으로 빠르게 끝나요. LinkedList의 O(1)은 노드 객체 할당과 포인터 갱신이에요. 작은 리스트면 ArrayList가 더 빠른 경우가 잦아요.

4. Joshua Bloch의 권고

자바 자료구조 설계자 Joshua Bloch와 Doug Lea도 "LinkedList를 거의 쓰지 마세요. ArrayList 또는 ArrayDeque를 쓰세요."라고 말해요. 실제 자바 표준 라이브러리도 LinkedList를 거의 안 써요.

그럼 LinkedList는 언제 써요

현실적으로 거의 안 써요. 큐·덱이 필요하면 ArrayDeque가 거의 모든 상황에서 LinkedList보다 빨라요.

  • Deque(양방향 큐) 용도: ArrayDeque가 더 좋아요. 연속 메모리에 양 끝을 다루는 구조라 캐시 친화적이에요.
  • Queue 용도: ArrayDeque(단일 스레드) 또는 ArrayBlockingQueue/LinkedBlockingQueue(동시성)예요.
  • List 인터페이스가 필요한데 양 끝 연산이 많은 경우: 거의 없어요. 보통 ArrayList로도 충분해요.

벤치마크의 함정

"LinkedList가 빠르다"는 결과가 나오는 벤치마크는 보통 두 가지 문제가 있어요.

  1. JIT 워밍업 무시: JIT가 ArrayList의 hot loop을 최적화하기 전 측정.
  2. 인덱스 접근을 LinkedList iterator로 대신함: get(i)로 측정하면 LinkedList가 O(n²)로 폭망. 반면 Iterator로 측정하면 차이가 작아 보임. 자리에 따라 결론이 달라져요.

JMH로 워밍업을 충분히 하고, 실제 사용 패턴을 따라 측정해야 진짜 결과가 나와요.

면접에서 자주 나오는 자리

  • "ArrayList와 LinkedList 차이?": 배열 기반 vs 이중 연결 리스트요. 시간 복잡도가 다른데 실제 성능은 캐시 효과로 ArrayList가 거의 항상 빨라요.
  • "LinkedList는 왜 안 써요?": 노드 객체 오버헤드와 캐시 미스 때문에요. Deque가 필요하면 ArrayDeque가 더 빨라요.
  • "ArrayList의 초기 용량은?": 10이에요. 크기를 미리 알면 new ArrayList<>(initialCapacity)로 grow 비용을 아껴요.
  • "add(0)은 어느 게 빨라요?": Big-O는 LinkedList가 O(1)이지만 작은 리스트엔 ArrayList의 System.arraycopy가 더 빠를 수 있어요.
