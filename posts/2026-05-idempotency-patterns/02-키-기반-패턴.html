비멱등을 멱등으로 만드는 핵심

POST 같은 자연 비멱등을 멱등하게 만드는 발상은 단순해요. "이미 처리한 요청인지 식별할 수 있는 키"를 만들어서, 같은 키면 새로 처리하지 않고 이전 결과를 돌려줘요. 이 키를 어디에 두느냐, 누가 발급하느냐가 패턴의 차이예요.

세 가지 자리가 있어요. HTTP 레벨의 Idempotency Key, 메시지 큐의 dedup ID, DB의 unique constraint. 어디서 막아야 가장 효율적이고 안전한지가 설계 결정이에요.

패턴 1: Idempotency Key (HTTP 헤더)

클라이언트가 요청마다 UUID를 만들어 헤더로 보내요. 서버는 이 키를 저장하고, 같은 키가 다시 오면 이전 결과를 돌려줘요. Stripe·Square·Adyen 같은 결제 회사들이 표준으로 채택했어요. 

POST /payments
Idempotency-Key: 8e1b2c3d-4f5a-6b7c-8d9e-0f1a2b3c4d5e
Content-Type: application/json

{"amount": 10000, "card_id": "..."}

서버 처리 흐름

  1. 요청에서 Idempotency-Key를 추출해요.
  2. 저장소(Redis 또는 DB)에서 키를 조회해요.
  3. 존재하면 저장된 응답을 그대로 돌려주고, 처리는 하지 않아요.
  4. 없으면 키를 "처리 중"으로 마킹하고 본 작업을 실행해요.
  5. 결과를 키에 함께 저장하고, 다음 요청에서 재사용해요.

저장 형태

CREATE TABLE idempotency_keys (
    key VARCHAR(64) PRIMARY KEY,
    request_hash VARCHAR(64) NOT NULL,
    response_status INT,
    response_body TEXT,
    status VARCHAR(20),  -- 'pending' | 'completed'
    created_at TIMESTAMP DEFAULT NOW(),
    expires_at TIMESTAMP
);

request_hash를 같이 저장하면 "같은 키로 다른 요청"이 왔을 때 거부할 수 있어요. 키만 같고 본문이 다르면 409 Conflict를 줘요.

TTL과 정리

키를 영원히 저장하면 테이블이 무한정 커져요. 보통 24시간에서 7일 정도로 TTL을 잡아요. 결제는 보통 24시간이면 충분해요. 그 이후의 재시도는 비즈니스 로직에서 별도로 다뤄요.

패턴 2: 메시지 Dedup ID

메시지 큐는 at-least-once를 기본으로 제공해요. 같은 메시지가 두 번 도착할 수 있다는 거예요. 컨슈머가 멱등하지 않으면 같은 작업이 중복돼요.

Kafka의 Producer Idempotence

Kafka는 producer 수준에서 멱등을 제공해요. enable.idempotence=true로 설정하면 producer가 PID(producer ID)와 시퀀스 번호를 붙여서, 같은 메시지가 두 번 들어오는 걸 브로커가 막아요. 

enable.idempotence=true
acks=all
retries=Integer.MAX_VALUE
max.in.flight.requests.per.connection=5

단, 이건 producer-broker 사이만 보장해요. 컨슈머가 메시지를 받고 처리하다가 죽으면 다시 받아요. 컨슈머 수준 멱등은 별도로 처리해야 해요.

컨슈머 측 dedup

각 메시지에 고유 ID를 붙이고(보통 producer가 부여), 컨슈머가 처리한 메시지 ID를 저장소에 기록해요. 같은 ID가 또 오면 무시해요. 

@KafkaListener(topics = "orders")
public void consume(OrderEvent event) {
    String messageId = event.getMessageId();

    if (processedRepository.exists(messageId)) {
        return;
    }

    processOrder(event);
    processedRepository.save(messageId);
}

주의. processOrder와 processedRepository.save가 같은 트랜잭션 안에서 일어나야 해요. 안 그러면 처리는 했는데 저장에 실패하는 자리가 생겨요.

패턴 3: DB Unique Constraint

가장 안전한 방어선이에요. 애플리케이션 레벨에서 막지 못해도, DB가 마지막 보루로 막아 줘요. 

CREATE TABLE orders (
    id BIGSERIAL PRIMARY KEY,
    request_id VARCHAR(64) NOT NULL UNIQUE,
    user_id BIGINT NOT NULL,
    amount DECIMAL(10,2),
    created_at TIMESTAMP DEFAULT NOW()
);

같은 request_id로 두 번째 INSERT가 들어오면 DB가 거부해요. 23505(PostgreSQL) 같은 unique violation 에러로 잡아내고, "이미 처리된 요청"으로 변환해서 응답해요.

ON CONFLICT 패턴 (PostgreSQL)

INSERT INTO orders (request_id, user_id, amount)
VALUES (?, ?, ?)
ON CONFLICT (request_id) DO NOTHING
RETURNING id;

INSERT가 충돌하면 아무것도 안 해요. RETURNING이 비어 있으면 "이미 있다"는 신호예요. 멱등 처리를 한 쿼리로 압축할 수 있어요.

INSERT ... ON DUPLICATE KEY (MySQL)

INSERT INTO orders (request_id, user_id, amount)
VALUES (?, ?, ?)
ON DUPLICATE KEY UPDATE id=id;

MySQL은 ON DUPLICATE KEY로 비슷한 패턴을 만들어요. RETURNING이 없으니 별도 SELECT가 필요할 수 있어요.

세 패턴의 비교

패턴위치장점단점
Idempotency KeyHTTP 레벨클라이언트가 명시적, 재시도 안전저장소 운영 필요, 클라이언트 협조 필요
메시지 Dedup ID큐 컨슈머at-least-once 보완처리/저장 트랜잭션 정합성
DB Unique ConstraintDB 레벨마지막 안전망비즈니스 키 설계 필요, 에러 처리 까다로움

여러 패턴을 같이 써요

실무에서는 한 패턴만 쓰지 않아요. 단계별 방어를 쌓아요.

  1. HTTP 레벨: Idempotency-Key 헤더로 1차로 막아요.
  2. 애플리케이션 레벨: 비즈니스 로직에서 중복을 검사해요 (이미 결제된 주문인지).
  3. DB 레벨: Unique constraint로 최후 방어선이에요.

각 레이어가 독립적으로 동작해요. 한 레이어가 뚫려도 다음 레이어가 잡아 줘요. Defense in depth.

키 발급은 누가 하나

Idempotency Key를 누가 만드느냐가 중요해요. 보통 클라이언트가 만들어야 멱등의 의미가 살아요.

  • 클라이언트가 만들어요: UUID v4를 요청 직전에 생성해요. 재시도해도 같은 키를 써야 해요. 이게 표준이에요.
  • 서버가 만들어요: 의미가 없어요. 매번 새 키를 받으면 멱등이 안 돼요.
  • 비즈니스 키를 써요: order_id 같은 자연 키가 있으면 그걸 써요. 단, 클라이언트가 항상 같은 값을 보낼 수 있어야 해요.

면접에서 자주 나오는 자리

  • "Idempotency Key는 누가 만들어요?": 클라이언트요. 재시도해도 같은 키여야 멱등이 돼요.
  • "키 저장은 어디에?": Redis 또는 DB. 결제는 보통 DB(영속성). 일반 API는 Redis(속도).
  • "TTL은 얼마로?": 보통 24시간~7일. 비즈니스 재시도 패턴에 맞춰요.
  • "Kafka는 정말 exactly-once인가요?": producer 수준은 idempotent, end-to-end는 transactional API + 컨슈머 측 dedup가 필요해요.
  • "DB unique constraint와 Idempotency-Key 헤더 둘 다 필요해요?": 네. 다른 레이어예요. 헤더로 빠르게 막고, 새는 케이스를 DB가 잡아요.

다음 편

키만으로 막을 수 없는 경우가 있어요. 동시에 들어온 두 요청, 상태가 변하는 객체(주문 상태), 외부 시스템과의 정합성이 그런 자리예요. 다음 편에서는 쓰기 경합을 어떻게 방어하는지 살펴봐요. 낙관적 락, 비관적 락, 상태 머신, 보상 트랜잭션의 idempotent step 같은 패턴이에요.
