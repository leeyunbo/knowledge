왜 멱등성을 신경 써야 하나요

분산 시스템에서는 같은 요청이 두 번 도착하는 일이 흔해요. 네트워크 타임아웃 후 클라이언트 재시도, 메시지 큐의 at-least-once 보장, LB가 재라우팅하는 경우 등이에요. 한 번 처리할 작업이 두세 번 처리되면 결제는 중복으로 빠지고, 재고는 음수가 되고, 사용자는 "주문 두 번 됐어요"를 외쳐요.

멱등성(idempotency)은 이 문제를 해결하는 가장 근본적인 무기예요. 같은 요청을 N번 보내도 결과가 한 번 보낸 것과 같으면 멱등이에요. 멱등하면 재시도가 안전해지고, 재시도가 안전하면 시스템 전체의 신뢰성이 올라가요.

Safe vs Idempotent

HTTP 스펙은 두 개념을 명확히 나눠요. 비슷해 보이지만 다른 속성이에요.

속성의미예시
Safe서버 상태를 바꾸지 않음GET, HEAD, OPTIONS
IdempotentN번 호출해도 결과가 1번과 같음GET, PUT, DELETE
Non-idempotent호출할 때마다 다른 결과POST, PATCH

Safe는 멱등의 부분집합이에요. 상태를 바꾸지 않으니 당연히 N번 호출해도 같아요. 반대로 멱등은 safe보다 넓어요. 상태는 바꾸지만, 바꾸는 결과가 항상 같으면 멱등이에요.

같은 호출 다른 결과

주의할 점이 있어요. 멱등성은 "같은 요청"의 결과가 같다는 거지, "같은 응답"이라는 뜻은 아니에요. 두 번째 DELETE는 404를 줄 수도 있어요. 첫 번째 호출에서 이미 지웠으니까요. 그래도 서버 상태는 같아서 멱등이에요.

HTTP 메소드별 자연 멱등성

GET (자연 Safe + Idempotent)

데이터를 읽기만 해요. 서버 상태를 바꾸지 않아요. 다만 GET이 카운터를 증가시키거나 로그를 남기면 엄밀히는 safe가 아닐 수 있어요. 그래도 응답이 같으면 클라이언트 입장에서는 safe로 취급해요.

PUT (자연 멱등)

리소스를 특정 상태로 "덮어쓰기"예요. PUT /users/42에 같은 본문을 N번 보내도, 42번 유저는 같은 상태로 끝나요. 멱등성이 디자인에 내장돼 있어요. 

PUT /users/42
{"name": "alice", "age": 30}

이걸 10번 호출해도 alice/30이에요. 자연 멱등이에요.

DELETE (자연 멱등)

"지운다"는 결과가 한 번이면 N번이든 같아요. 두 번째 DELETE는 404를 받을 수도 있지만 서버 상태는 같아요. 클라이언트가 받는 응답 코드만 다를 뿐 부작용은 없어요.

POST (자연 비멱등)

"새 리소스 생성"이에요. N번 호출하면 N개가 생겨요. POST /orders를 두 번 호출하면 주문이 두 개 만들어져요. 자연스럽게 비멱등이라 별도로 멱등화를 해야 해요.

PATCH (보통 비멱등, 예외 있음)

부분 업데이트라 비멱등이 일반적이에요. {"age": 30}은 멱등이지만, {"age_increment": 1} 같은 증감 연산은 호출할 때마다 결과가 달라져요. 같은 PATCH도 의미에 따라 달라요.

실무에서 비멱등이 되는 자리

설계 의도로 멱등이라도, 구현이 비멱등을 만드는 경우가 있어요.

GET이 비멱등이 되는 경우

  • 조회 카운트 증가: GET /posts/42가 view_count를 1 올려요. 서버 상태가 변해요.
  • 토큰 발급: 호출할 때마다 다른 토큰을 발급하면 응답이 매번 달라요.

PUT이 비멱등이 되는 경우

  • created_at 같은 자동 필드: PUT 안에 들어 있으면 매번 갱신돼서 응답이 달라요.
  • 증감 연산: PUT으로 "잔액에 +100" 같은 의미를 넣으면 비멱등이에요.

DELETE가 부작용 있는 경우

  • cascading delete + 외부 호출: 삭제할 때 외부 시스템에 알림을 보낸다면, 두 번째 DELETE는 알림을 보내지 않아야 해요. 안 그러면 비멱등이에요.

의도된 멱등성과 구현된 멱등성이 다를 수 있어요. 코드를 봐야 정확히 알 수 있어요.

멱등성과 일관성

두 개념을 자주 헷갈려요. 다른 거예요.

개념의미
멱등성 (Idempotency)같은 작업을 N번 해도 결과가 1번과 같음
일관성 (Consistency)모든 읽기가 가장 최근 쓰기를 봄

멱등이라도 일관성이 깨질 수 있어요. PUT을 한 번 했는데, 복제 지연 때문에 어떤 노드는 새 값을, 어떤 노드는 옛 값을 줄 수 있어요. 그래도 PUT 자체는 멱등이에요.

반대로 일관성이 강해도 비멱등일 수 있어요. POST가 일관되게 매번 다른 새 리소스를 만들어요.

면접에서 자주 나오는 자리

  • "GET이 idempotent인가요 safe인가요?": 둘 다예요. Safe는 멱등의 부분집합이에요.
  • "DELETE를 두 번 호출하면?": 첫 번째에 지우고, 두 번째는 보통 404예요. 서버 상태가 같아서 멱등이에요. 응답 코드만 다를 뿐이에요.
  • "PUT과 POST 차이?": PUT은 리소스를 특정 상태로 만들어요 (멱등). POST는 새 리소스를 만들어요 (비멱등).
  • "PATCH는 멱등인가요?": 의미에 따라 달라요. 절대값 설정이면 멱등, 증감 연산이면 비멱등이에요.

다음 편

자연 멱등이 안 되는 작업, 특히 POST 계열을 어떻게 멱등하게 만드는지가 다음 주제예요. Idempotency Key, DB unique constraint, 메시지 큐의 dedup 키 같은 패턴을 정리해요.
