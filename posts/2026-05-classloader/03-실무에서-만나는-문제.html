ClassLoader 누수 (Classloader Leak)

WAS에서 가장 흔히 만나는 메모리 사고예요. 애플리케이션을 hot redeploy 하면 옛 WebappClassLoader가 회수돼야 하는데, 어딘가 한 곳에 참조가 남아서 회수되지 않아요. 그 안의 모든 클래스와 그 클래스의 static 필드 전부가 메모리에 남아요. OutOfMemoryError: Metaspace로 직진해요.

누수의 흔한 원인

  • ThreadLocal: 스레드풀의 스레드가 옛 ClassLoader의 클래스를 ThreadLocal에 담아 두면, 스레드가 죽지 않는 한 회수가 안 돼요.
  • JDBC DriverManager: DriverManager.registerDriver로 등록한 드라이버가 시스템 ClassLoader에 캐시돼 있으면, 그 드라이버 클래스의 ClassLoader 전체가 같이 살아 있어요.
  • ShutdownHook: Runtime.addShutdownHook으로 등록한 훅도 JVM 전역에 잡혀서 ClassLoader 회수를 막아요.
  • 로그 라이브러리: Log4j, Logback 같은 라이브러리가 static 필드로 컨텍스트를 잡고 있어요.
  • 스레드: 살아 있는 스레드의 contextClassLoader가 옛 ClassLoader면 똑같이 잡혀요.

전형적인 함정 예시

// webapp의 어딘가
public class CacheHolder {
    private static final Map<String, Object> CACHE = new HashMap<>();

    static {
        // 외부 스레드풀에 작업 등록
        EXTERNAL_POOL.submit(() -> {
            // 이 람다는 옛 ClassLoader에 묶여 있어요
            Thread.sleep(60_000);
            CACHE.put("key", new MyClass());
        });
    }
}

외부 스레드풀이 작업을 60초 잡고 있는 동안 redeploy가 일어나면, 그 스레드가 살아 있어서 옛 ClassLoader가 회수되지 않아요. 60초 안에 redeploy를 한 번 더 하면 또 누수가 쌓여요.

예방 패턴

  • ServletContextListener의 contextDestroyed에서 정리 코드를 실행해요.
  • ThreadLocal.remove()를 명시적으로 호출해요. 스레드풀을 쓰면 필수예요.
  • DriverManager.deregisterDriver()로 드라이버를 해제해요.
  • 외부 스레드풀에 webapp 클래스를 직접 넘기지 않아요.

ClassCastException: A cannot be cast to A

1편에서 본 "같은 이름 다른 ClassLoader" 문제가 실제로 던지는 에러예요. 보면 황당해요. "Foo가 Foo로 캐스팅 안 된대요"라고 트래픽 한가운데서 알람이 와요.

전형적 시나리오: 플러그인

// 메인 앱과 플러그인 둘 다 Plugin 인터페이스를 가진 jar를 포함했을 때
URLClassLoader pluginLoader = new URLClassLoader(
    new URL[]{ pluginJar, commonJar }  // 둘 다 들어 있음
);

Class<?> cls = pluginLoader.loadClass("com.example.MyPlugin");
Plugin plugin = (Plugin) cls.getDeclaredConstructor().newInstance();
// ClassCastException: MyPlugin cannot be cast to Plugin

메인 앱의 Plugin과 플러그인 ClassLoader의 Plugin이 서로 다른 클래스로 인식돼요. 둘 다 같은 이름이지만 로더가 다르니까요.

해결 패턴

  1. 공통 인터페이스(Plugin)는 부모 ClassLoader에만 두고, 플러그인 jar에선 빼요.
  2. 플러그인 ClassLoader가 그 인터페이스를 찾을 때 부모로 위임하도록 해요.
  3. 플러그인 jar 안에 같은 인터페이스가 또 들어가지 않게 빌드 설정을 잘 잡아요.

NoClassDefFoundError vs ClassNotFoundException

비슷해 보이지만 다른 에러예요. 발생 시점과 원인이 달라요.

비교ClassNotFoundExceptionNoClassDefFoundError
타입Checked ExceptionError (회복 불가)
발생 시점명시적 클래스 로드 시도 시이미 로드된 클래스를 쓰는데 실패할 때
전형적 원인Class.forName, loadClass 호출 시 클래스 없음컴파일은 됐는데 런타임에 의존 클래스가 사라짐

ClassNotFoundException 예시

try {
    Class<?> cls = Class.forName("com.example.Missing");
} catch (ClassNotFoundException e) {
    // 명시적으로 잡을 수 있어요
}

NoClassDefFoundError 예시

// 컴파일 시 com.example.Foo가 classpath에 있었음
public class A {
    private Foo foo;  // 컴파일 OK
}

// 런타임에 Foo가 빠진 jar로 실행하면
new A();
// NoClassDefFoundError: com/example/Foo

static 블록 실행 중 예외가 터지면 그 클래스는 다음번에 쓸 때부터 NoClassDefFoundError를 던져요. "예전에 한 번 초기화에 실패했다"는 신호예요. 진짜 원인은 첫 번째 시도 때의 예외이고, 그건 다른 스택트레이스에 묻혀 있을 수 있어요.

Spring Boot의 ClassLoader 구조

Spring Boot의 fat jar는 표준 jar와 구조가 달라요. BOOT-INF/lib/*.jar로 의존성이 들어 있고, BOOT-INF/classes/에 우리 코드가 있어요. 

app.jar
├── META-INF/
├── org/springframework/boot/loader/   # 부트스트랩 로더
├── BOOT-INF/
│   ├── classes/                       # 우리 코드
│   └── lib/                           # 의존 jar들 (jar 안의 jar)
└── ...

왜 자체 ClassLoader가 필요한가요

표준 자바 도구는 jar 안의 jar를 클래스 경로로 인정하지 않아요. Spring Boot는 LaunchedURLClassLoader를 자체 구현해서 이 구조를 처리해요. java -jar app.jar로 실행하면 사실은 부트스트랩 로더가 먼저 동작해서, LaunchedURLClassLoader로 우리 앱을 다시 로드해요.

실무에서 부딪치는 자리

  • 리소스 위치: getResource가 돌려주는 URL이 jar:file:.../app.jar!/BOOT-INF/classes/foo.txt 같은 중첩 형식이에요. 외부 도구가 이걸 못 읽으면 곤란해져요.
  • 외부 모니터링 에이전트: javaagent로 붙는 도구가 LaunchedURLClassLoader가 로드한 클래스에 접근할 때 인스트루먼트 누락이 생길 수 있어요.

실무 진단 도구

JVM 옵션

  • -verbose:class: 모든 클래스 로딩 로그. 어디서 어떤 ClassLoader가 무엇을 로드하는지 다 볼 수 있어요.
  • -XX:+TraceClassLoading: 같은 정보를 다른 형식으로 보여줘요.
  • -XX:+TraceClassUnloading: 언로드되는 클래스를 추적해요.

힙 덤프 분석

ClassLoader 누수는 힙 덤프로 잡아요. Eclipse MAT의 Leak Suspects나 Path to GC Roots로 옛 WebappClassLoader가 누구에게 잡혀 있는지 추적해요.

jcmd

jcmd <pid> VM.classloaders   # 모든 ClassLoader 목록
jcmd <pid> GC.class_stats    # 클래스별 메모리

면접에서 자주 나오는 자리

  • "ClassLoader 누수가 뭐예요?": WAS 핫 리디플로이 후에도 옛 ClassLoader가 메모리에 남는 현상이에요. ThreadLocal·JDBC 드라이버·스레드가 주요 원인이에요.
  • "ClassNotFoundException vs NoClassDefFoundError?": 전자는 명시적 로딩 시 클래스가 없을 때, 후자는 이미 로드됐어야 할 클래스가 런타임에 없을 때예요. 후자는 회복 불가 에러예요.
  • "Spring Boot가 자체 ClassLoader를 쓰는 이유?": fat jar 안의 jar를 로드하기 위해서요. 표준 자바 도구는 중첩 jar를 못 읽어요.
  • "같은 클래스에 ClassCastException이 떠요": 두 ClassLoader가 같은 이름의 클래스를 따로 로드했어요. 보통 플러그인이나 WAS 격리 환경에서 발생해요.
  • "ClassLoader 누수 진단?": 힙 덤프 후 MAT으로 옛 WebappClassLoader의 GC root path를 추적해요. ThreadLocal·DriverManager·ShutdownHook이 단골이에요.

시리즈 마무리

1편에서 부모 위임 모델과 3계층 ClassLoader 구조, 클래스 식별이 "이름 + 로더"라는 사실을 봤어요. 2편에서 URLClassLoader, 사용자 정의 ClassLoader, Tomcat과 Spring Boot의 자체 로더, 모듈 시스템과의 관계를 정리했고요. 3편에서는 ClassLoader 누수·ClassCastException·NoClassDefFoundError 같은 실무 사고를 같은 뿌리에서 풀었어요.

핵심은 단순해요. ClassLoader는 클래스의 신원증명서예요. 어느 로더가 로드했느냐가 클래스의 정체성을 정해요. 메모리 누수, 캐스트 실패, 리디플로이 OOM은 다 이 정체성이 꼬일 때 일어나요.
