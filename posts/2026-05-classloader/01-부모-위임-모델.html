클래스 로딩이 푸는 문제

자바에서 new Foo()를 처음 호출하는 순간을 생각해 봐요. JVM은 어딘가에서 Foo.class 바이트코드를 찾아 메모리에 올려야 해요. "어디서 찾을 것인가", "찾은 걸 누가 책임지고 관리할 것인가"가 클래스 로딩의 문제예요.

단순히 클래스파일을 메모리에 올리는 게 아니에요. 같은 이름의 클래스가 여러 jar에 있으면 어느 걸 쓸지, 다른 모듈에서 같은 이름 클래스를 새로 로드하면 같은 클래스인지 다른 클래스인지, 클래스를 언로드해 메모리에서 빼낼 수 있는지가 다 클래스 로더의 책임이에요.

3계층 ClassLoader 구조

자바 9 이전엔 Bootstrap → Extension → Application 3계층이었어요. 9부터 모듈 시스템이 들어오면서 Extension이 Platform으로 바뀌었어요. 역할은 비슷해요.

계층로더책임
1Bootstrapjava.base 모듈 (java.lang.*, java.util.* 등)
2Platformjava.sql, java.xml 등 표준 라이브러리 (java 9+)
3Application (System)classpath의 사용자 클래스

Bootstrap ClassLoader

JVM의 일부예요. 네이티브 코드로 구현돼서 자바 코드로는 객체 참조를 얻을 수 없어요. String.class.getClassLoader()가 null을 돌려주는 이유예요. 핵심 자바 클래스들을 책임져요.

Platform ClassLoader (자바 9+)

java.sql, java.xml, java.naming 같은 표준 모듈을 로드해요. 자바 8까지는 Extension ClassLoader였고, ext 디렉토리의 jar를 로드했어요. 모듈 시스템 도입 이후 역할이 깔끔해졌어요.

Application ClassLoader

실제 우리가 쓰는 로더예요. -classpath나 -cp로 지정한 위치, 메인 메소드와 우리 코드의 모든 클래스를 로드해요. ClassLoader.getSystemClassLoader()로 얻을 수 있어요.

부모 위임 모델 (Parent Delegation)

클래스 로딩의 가장 중요한 규칙이에요. 클래스 로더가 클래스를 로드하기 전에, 먼저 부모 로더에게 "이 클래스 너가 로드할 수 있어?"를 물어요. 부모가 못 하면 자기가 해요.

왜 부모에게 먼저 위임하나요

두 가지 이유가 있어요. 첫째는 보안이에요. 누군가 java.lang.String 클래스를 만들어 classpath에 넣어도, Application ClassLoader가 위임하는 Bootstrap이 진짜 String을 먼저 로드해 줘요. 우리가 만든 가짜 String은 절대 로드되지 않아요. 핵심 클래스가 오염되지 않게 하는 안전장치예요.

둘째는 유일성이에요. 같은 클래스가 한 JVM에 두 번 로드되면 안 돼요. 위임 모델로 항상 가장 위쪽 로더가 먼저 처리해서, 한 클래스에 한 로더만 매핑돼요.

클래스의 식별: 이름 + 로더

JVM이 두 클래스가 같은지 판단할 때는 (클래스 풀네임 + 로딩한 ClassLoader)를 같이 봐요. 이름이 같아도 다른 로더가 로드했으면 다른 클래스예요. 

// 두 로더가 같은 클래스를 따로 로드한다면
Class<?> a = loaderA.loadClass("com.example.Foo");
Class<?> b = loaderB.loadClass("com.example.Foo");

System.out.println(a == b);  // false
// JVM 입장에선 서로 다른 클래스

ClassCastException: com.example.Foo cannot be cast to com.example.Foo 같은 황당한 에러는 보통 이 자리에서 와요. 같은 이름이지만 다른 로더가 로드한 두 클래스가 만나서요.

3단계 로딩 과정

클래스 로딩은 한 번에 끝나지 않아요. JVM은 세 단계로 나눠 처리해요.

1. Loading

바이트코드를 찾아 메모리에 적재해요. .class 파일을 읽어서 Class 객체를 만들어요. 이 시점에 ClassLoader의 defineClass가 호출돼요.

2. Linking (Verification → Preparation → Resolution)

  • Verification: 바이트코드가 안전한지 검증해요. 스택 오버플로우, 잘못된 타입 캐스팅 같은 게 없는지 봐요.
  • Preparation: static 필드를 기본값(0, null, false)으로 초기화해요. 코드의 초기화 값은 아직 적용 안 돼요.
  • Resolution: 심볼릭 레퍼런스를 실제 메모리 주소로 변환해요. 지연될 수 있어요.

3. Initialization

static 블록을 실행하고, static 필드에 실제 값을 대입해요. 클래스가 처음 능동적으로 사용될 때(new, static 호출, Class.forName 등) 일어나요. JVM이 thread-safe 하게 한 번만 실행하도록 보장해요.

능동 사용 vs 수동 사용

Initialization은 "능동 사용"일 때만 일어나요. 클래스를 참조만 한다고 다 일어나지 않아요.

능동 사용 (Initialization 발생)수동 사용 (Loading만)
new Foo()Foo.class 참조
Foo.staticMethod()final 상수 접근 (Foo.CONST)
static 필드 read/write배열 선언 (Foo[] arr)
Class.forName("Foo")자식 클래스의 static 호출

특히 final 상수는 컴파일 타임에 인라인돼서 클래스 로딩 자체가 안 일어날 수 있어요. Foo.CONST를 썼는데 Foo의 static 블록이 실행되지 않는다면 이 자리예요.

면접에서 자주 나오는 자리

  • "부모 위임 모델이 뭐예요?": 클래스를 로드하기 전에 부모 로더에게 먼저 위임하고, 부모가 못 찾으면 자기가 로드하는 모델이에요. 보안과 유일성을 보장해요.
  • "왜 부모에 먼저 위임?": 핵심 클래스가 오염되지 않게 하기 위해서요. 누가 java.lang.String을 만들어도 진짜 String이 먼저 로드돼요.
  • "같은 클래스 다른 로더면?": JVM 입장에서는 서로 다른 클래스예요. 캐스팅하면 ClassCastException이 나요.
  • "Initialization은 언제 일어나요?": 능동 사용 시점이에요. new, static 메소드 호출, Class.forName 같은 시점이고, final 상수 접근은 안 일어날 수 있어요.
