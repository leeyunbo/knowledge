왜 직접 만드나요

Application ClassLoader가 classpath의 클래스를 다 로드해 주는데, 굳이 ClassLoader를 만드는 자리가 있어요. 보통 이런 요구예요.

  • 동적 로딩: 실행 중에 jar 파일을 새로 받아서 클래스를 불러와요. 플러그인 시스템 같은 자리예요.
  • 격리: 같은 이름의 클래스가 두 버전 필요해요. WAS의 webapp 격리, 마이크로 모듈 시스템이 그래요.
  • 변환: 클래스 바이트코드를 로딩 시점에 수정해요. AOP 프레임워크나 코드 instrument 도구가 써요.
  • 네트워크 로딩: classpath가 아닌 자리(원격 서버, DB)에서 바이트코드를 가져와요.

URLClassLoader로 동적 로딩

가장 쉬운 방법이에요. URL 배열만 주면 그 위치의 jar에서 클래스를 가져와요. 

URL jarUrl = new URL("file:///path/to/plugin.jar");
URLClassLoader loader = new URLClassLoader(
    new URL[]{ jarUrl },
    getClass().getClassLoader()  // 부모 로더
);

Class<?> cls = loader.loadClass("com.plugin.MyPlugin");
Object instance = cls.getDeclaredConstructor().newInstance();

두 번째 인자가 부모 로더예요. 이 부모는 부모 위임 모델로 먼저 클래스 검색을 시도해요. 직접 명시하지 않으면 시스템 ClassLoader가 부모예요.

플러그인 패턴

플러그인이 공통 인터페이스(예: Plugin)를 구현했다고 약속하면, 동적으로 로드해 호출할 수 있어요. 

public interface Plugin {
    void execute();
}

// 메인 앱
URLClassLoader loader = new URLClassLoader(
    new URL[]{ new URL("file:///plugins/plugin.jar") }
);

Class<?> cls = loader.loadClass("com.example.MyPlugin");
Plugin plugin = (Plugin) cls.getDeclaredConstructor().newInstance();
plugin.execute();

주의 자리가 있어요. Plugin 인터페이스는 메인 앱과 플러그인 모두 같은 ClassLoader가 로드한 거여야 해요. 그렇지 않으면 1편의 ClassCastException이 발생해요.

ClassLoader 직접 구현

더 세밀한 제어가 필요하면 ClassLoader를 상속해요. 보통 findClass만 오버라이드해요. 

public class MyClassLoader extends ClassLoader {
    public MyClassLoader(ClassLoader parent) {
        super(parent);
    }

    @Override
    protected Class<?> findClass(String name) throws ClassNotFoundException {
        byte[] bytecode = loadBytecode(name);
        return defineClass(name, bytecode, 0, bytecode.length);
    }

    private byte[] loadBytecode(String name) {
        // 파일·네트워크·DB 등에서 바이트코드 가져오기
        ...
    }
}

왜 loadClass가 아니라 findClass인가요

loadClass는 ClassLoader의 표준 진입점이에요. 부모 위임을 먼저 수행하고, 부모가 못 찾으면 findClass를 호출해요. 우리가 직접 클래스를 찾는 로직은 findClass에 넣고, 부모 위임 처리는 부모 클래스의 loadClass에 맡기는 게 정석이에요. 

// ClassLoader.loadClass의 기본 구현 (단순화)
protected Class<?> loadClass(String name, boolean resolve)
        throws ClassNotFoundException {
    Class<?> c = findLoadedClass(name);  // 이미 로드돼 있는지
    if (c == null) {
        try {
            if (parent != null) {
                c = parent.loadClass(name, false);  // 부모에 위임
            } else {
                c = findBootstrapClassOrNull(name);
            }
        } catch (ClassNotFoundException e) {
            // 부모도 못 찾으면 직접 찾기
        }
        if (c == null) {
            c = findClass(name);
        }
    }
    if (resolve) resolveClass(c);
    return c;
}

부모 위임을 깨야 하는 자리

WAS나 OSGi처럼 격리가 필요한 환경에서는 의도적으로 부모 위임을 깨요. Tomcat의 WebappClassLoader가 대표적이에요.

Tomcat의 child-first 전략

일반적인 부모 위임은 "부모 먼저, 자식 나중에"예요. Tomcat은 webapp의 클래스 격리를 위해 반대로 동작해요.

  1. 먼저 자기 자신(WebappClassLoader)이 찾아봐요.
  2. 없으면 부모(Common ClassLoader)에 위임해요.
  3. 예외: java.* 같은 핵심 패키지는 무조건 부모에 위임. 보안 때문이에요.

왜 이렇게 해요? webapp이 자기 jar에 들어 있는 라이브러리를 우선 쓰게 하기 위해서예요. 컨테이너에 들어 있는 라이브러리 버전과 webapp이 원하는 버전이 다를 수 있어요. webapp이 자기 버전을 쓰면 격리가 가능해요.

Spring Boot의 LaunchedURLClassLoader

Spring Boot의 fat jar는 내부에 BOOT-INF/lib/*.jar로 라이브러리가 들어 있어요. 표준 ClassLoader는 jar 안의 jar를 못 읽어요. Spring Boot가 자체 ClassLoader로 이걸 해결해요.

모듈 시스템(JPMS)과 ClassLoader

자바 9의 모듈 시스템(JPMS)이 들어오면서 ClassLoader 구조가 좀 정리됐어요. 클래스 로더는 그대로지만, 그 위에 "모듈 레이어"가 생겼어요.

주요 변화

  • Extension → Platform: 8까지 있던 Extension ClassLoader가 사라지고 Platform ClassLoader가 등장했어요.
  • 모듈 경계: 같은 클래스 로더가 로드한 클래스라도 다른 모듈이면 접근이 제한돼요. requires·exports로 명시해야 해요.
  • 분할 패키지 금지: 같은 패키지를 두 모듈이 못 가져요. classpath 시절의 흔한 충돌이 사라졌어요.

ModuleLayer

같은 ClassLoader 위에 여러 ModuleLayer를 둬서 모듈을 격리해요. 동적으로 모듈을 추가·제거할 수 있어요. 플러그인 시스템을 만든다면 옛 URLClassLoader 대신 ModuleLayer를 쓰는 게 자바 9+ 시대 정석이에요. 

// 자바 9+ 모듈 동적 로딩 (단순화)
Path pluginPath = Path.of("/plugins");
ModuleFinder finder = ModuleFinder.of(pluginPath);
Configuration parent = ModuleLayer.boot().configuration();
Configuration cf = parent.resolve(finder, ModuleFinder.of(),
    Set.of("com.plugin"));

ModuleLayer layer = ModuleLayer.boot()
    .defineModulesWithOneLoader(cf, ClassLoader.getSystemClassLoader());

Class<?> cls = layer.findLoader("com.plugin")
    .loadClass("com.plugin.MyPlugin");

ClassLoader와 메모리

ClassLoader는 자기가 로드한 클래스를 GC가 회수하지 못하게 잡고 있어요. 클래스를 언로드하려면 그 ClassLoader를 회수해야 해요.

Class·ClassLoader·Instance의 참조 관계

  • 인스턴스가 Class 객체를 참조하고, Class 객체가 ClassLoader를 참조해요.
  • ClassLoader는 자기가 로드한 모든 Class 객체를 참조해요.

ClassLoader가 살아 있으면 그 안의 클래스 전체가 살아 있어요. 특정 인스턴스 하나만 남아 있어도 전체 클래스 그룹이 GC 대상이 아니에요. 다음 편에서 이게 어떤 문제를 일으키는지 자세히 봐요.

면접에서 자주 나오는 자리

  • "URLClassLoader는 언제 써요?": 실행 중에 jar를 동적으로 로드할 때요. 플러그인 패턴이 대표적이에요.
  • "ClassLoader를 직접 구현할 때 뭘 오버라이드?": 보통 findClass만 오버라이드해요. 부모 위임 로직은 ClassLoader.loadClass가 알아서 해 줘요.
  • "Tomcat의 ClassLoader는 왜 child-first?": webapp이 자기가 가진 라이브러리 버전을 우선 쓰게 하기 위해서요. 컨테이너 라이브러리와의 충돌을 막아요.
  • "자바 9의 모듈 시스템이 ClassLoader에 미친 영향?": ModuleLayer 개념이 추가됐어요. 같은 ClassLoader 위에서도 모듈로 격리할 수 있어요. Extension이 Platform으로 바뀐 것도 그 일환이에요.
