비동기 I/O의 모든 것 — select부터 DPDK까지

네트워크 · IO 이벤트 모델 · 2026-03-27

✦
핵심 요약
비동기 I/O의 핵심은 OS 커널의 I/O 이벤트 감시 기능(epoll/kqueue)을 이용해, 스레드가 I/O 완료를 기다리지 않고 "준비되면 알려줘"라고 등록한 뒤 다른 일을 하는 것이다.

동기 모델에서는 스레드 1개 = 커넥션 1개이므로, 동시 접속 10,000개면 스레드 10,000개가 필요하다. 비동기 모델에서는 이벤트루프 스레드 몇 개가 수만 커넥션을 처리한다.

◈
동기(블로킹) vs 비동기(논블로킹)

동기 — 기다린다

스레드: "카카오야 데이터 줘"
스레드: zzz... (sleep 상태, CPU 안 씀, 근데 스레드 하나 점유)
스레드: "왔다!" → 처리

비동기 — 등록하고 넘어간다

이벤트루프: "OS야, 이 소켓에 데이터 오면 알려줘" (epoll/kqueue에 등록)
이벤트루프: 다른 소켓 처리하러 감
            ...
OS: "야 데이터 왔어" (이벤트 알림)
이벤트루프: "ㅇㅋ" → 콜백 실행

OS 스레드한테 넘기는 게 아니라, OS 커널의 I/O 이벤트 감시 기능을 쓰는 것이다.

OS이벤트 감시 시스템 콜
Linuxepoll
macOS / BSDkqueue
WindowsIOCP
◈
역사: select의 한계 (1983) 
// select (1983년, BSD)
fd_set readfds;
FD_SET(socket1, &readfds);
FD_SET(socket2, &readfds);
FD_SET(socket3, &readfds);

select(maxfd, &readfds, NULL, NULL, timeout);

// 누가 준비됐는지 전부 순회해야 함
for (int i = 0; i < maxfd; i++) {
    if (FD_ISSET(i, &readfds)) { ... }
}
문제점:
  • 매 호출마다 감시할 소켓 목록을 커널에 복사
  • 결과도 전체를 순회해야 준비된 걸 찾음 → O(n)
  • 소켓 1,024개 제한 (FD_SETSIZE)
  • 소켓 10,000개면 매번 10,000개 순회

이걸 해결하려고 나온 게 epoll과 kqueue이다.

◉
epoll (Linux, 2002)

3단계 API

// 1. epoll 인스턴스 생성 (커널에 감시 목록 공간 만듦)
int epfd = epoll_create(1);

// 2. 소켓 등록 (한 번만 하면 됨)
struct epoll_event ev;
ev.events = EPOLLIN;          // 읽기 가능할 때 알려줘
ev.data.fd = client_socket;
epoll_ctl(epfd, EPOLL_CTL_ADD, client_socket, &ev);

// 3. 대기 (준비된 것만 리턴)
struct epoll_event events[MAX_EVENTS];
int nready = epoll_wait(epfd, events, MAX_EVENTS, timeout);

for (int i = 0; i < nready; i++) {
    // 준비된 소켓만 순회 → O(준비된 수)
    handle(events[i].data.fd);
}
핵심 차이:
select: 소켓 10,000개 중 3개 준비 → 10,000개 순회
epoll: 소켓 10,000개 중 3개 준비 → 3개만 리턴

두 가지 트리거 모드

모드동작특징
Level Triggered (기본)데이터가 있는 동안 계속 알림안전하지만 알림이 반복됨
Edge Triggered (EPOLLET)상태가 변할 때 딱 한 번만 알림더 효율적, 한번에 다 읽어야 함. Netty가 사용
                데이터 도착
                    ↓
Level Triggered:  알림! 알림! 알림! (읽을 때까지 반복)
Edge Triggered:   알림!              (한 번만, 안 읽으면 끝)
◉
kqueue (macOS/BSD, 2000) 
// 1. kqueue 인스턴스 생성
int kq = kqueue();

// 2. 이벤트 등록
struct kevent change;
EV_SET(&change, client_socket, EVFILT_READ, EV_ADD, 0, 0, NULL);

// 3. 대기 (준비된 것만 리턴)
struct kevent events[MAX_EVENTS];
int nready = kevent(kq, &change, 1, events, MAX_EVENTS, timeout);

for (int i = 0; i < nready; i++) {
    handle(events[i].ident);
}

epoll과 거의 같은 개념이지만 차이가 있다:

epoll (Linux)kqueue (macOS/BSD)
API등록/대기 별도 함수
(epoll_ctl / epoll_wait)		하나의 함수로 등록+대기 동시
(kevent)
감시 대상소켓(fd)만소켓, 파일, 프로세스, 시그널, 타이머 전부
필터EPOLLIN, EPOLLOUT 정도EVFILT_READ, WRITE, PROC, TIMER...
범용성소켓에 특화더 범용적
◆
실제 동작 흐름 (Netty 이벤트루프)

Netty가 하는 일은 이 epoll 루프를 감싸서 Java에서 쓰기 편하게 만든 것이다.

// 이벤트루프가 하는 일 (스레드 1개)
while (true) {
    events = epoll_wait();     // 커널에게 "준비된 거 있어?"

    // 10,000 커넥션 중 5개만 데이터 왔으면 → 5개만 리턴
    for (event : events) {
        if (READ 이벤트)  → 데이터 읽고 → 핸들러 체인 실행
        if (WRITE 이벤트) → 버퍼에 있던 데이터 전송
    }
}
◉
io_uring (Linux 5.1, 2019)

epoll도 매 I/O 작업마다 시스템 콜이 필요하다. io_uring은 유저-커널 공유 링 버퍼로 이 오버헤드를 제거했다.

epoll의 문제

유저 공간                    커널 공간
─────────                   ─────────
epoll_wait() ──시스템콜──→  준비된 소켓 확인
             ←──결과 복사──
read()       ──시스템콜──→  데이터 읽기
             ←──데이터 복사──
write()      ──시스템콜──→  데이터 쓰기
             ←──결과 복사──

매번 시스템 콜 = 유저↔커널 컨텍스트 스위칭 비용

io_uring의 해결

유저 공간과 커널이 공유하는 링 버퍼 2개를 만듦

[Submission Queue (SQ)]  유저 → 커널 (요청)
[Completion Queue (CQ)]  커널 → 유저 (결과)

유저 공간                    커널 공간
─────────                   ─────────
SQ에 작업 넣기 ──────────→  (공유 메모리, 시스템콜 없음)
  "소켓A 읽어줘"
  "소켓B에 써줘"
  "파일C 열어줘"

io_uring_enter() ─1번만──→  "SQ에 있는 거 처리해줘"

CQ에서 결과 읽기 ←────────  (공유 메모리, 시스템콜 없음)
  "소켓A 데이터 여기"
  "소켓B 쓰기 완료"
  "파일C 열기 완료"
epoll: 작업 1개 = 시스템콜 1번
io_uring: 작업 100개 = 시스템콜 1번 (또는 폴링 모드에서 0번)

핵심:

  • 배치 처리 — 여러 I/O 요청을 한번에 제출
  • Zero-copy — 링 버퍼가 공유 메모리라 복사 없음
  • 시스템콜 최소화 — 폴링 모드에서는 시스템콜 0번도 가능
◉
DPDK — 커널을 아예 우회

DPDK(Data Plane Development Kit)는 더 급진적이다. 커널 네트워크 스택을 완전히 우회한다.

일반적인 패킷 흐름

NIC(랜카드) → 커널 네트워크 스택 → 소켓 → 유저 애플리케이션
              ├ 인터럽트 처리
              ├ 프로토콜 파싱 (TCP/IP)
              ├ 방화벽 (iptables)
              ├ 버퍼 복사
              └ 컨텍스트 스위칭

              패킷당 수 μs 소요

DPDK

NIC(랜카드) → 유저 애플리케이션 (커널 완전 우회)
              ├ NIC 드라이버를 유저 공간에서 직접 제어
              ├ 패킷을 유저 메모리에 직접 DMA
              ├ CPU 코어를 전용으로 할당 (poll 모드)
              └ 인터럽트 없음, 컨텍스트 스위칭 없음

              패킷당 ~0.1μs (100배 빠름)
대가:
  • CPU 코어를 100% 점유 (poll loop)
  • 커널 네트워크 스택 못 씀 (TCP/IP 직접 구현)
  • 해당 NIC는 OS에서 안 보임 (ping도 안 됨)
  • 일반 소켓 API(connect, read, write) 못 씀

언제 비동기(WebFlux/Netty)가 필요한가?
핵심 기준: "동시에 열려있는 커넥션이 스레드 수로 감당 안 될 만큼 많은가?"

비동기가 빛나는 경우

서비스이유
API Gateway사용자 수만 명의 요청을 받아서 뒤로 라우팅. 자기는 넘기기만.
채팅/알림 서버WebSocket 수만 커넥션 유지. 대부분 idle.
스트리밍 서비스SSE로 수만 클라이언트에 실시간 피드.
BFF여러 마이크로서비스 호출 후 조합. I/O 대기가 대부분.

공통점: CPU 연산은 거의 없고, I/O 대기가 대부분이며, 동시 접속 수가 매우 많음.

비동기가 과한 경우

서비스이유
내부 워커 (Consumer → 외부 API)동시 커넥션 수가 적고 제어 가능. 스레드 100~200개로 충분.
배치 서버순차 처리가 주. 동시성 필요 없음.
CPU 집약 서비스I/O가 아니라 연산이 병목. 비동기가 도움 안 됨.
브라우저든 앱이든 IoT든 서버든, 상대가 누구냐가 아니라 동시에 몇 개가 붙어있느냐가 기준이다.

Netty vs WebFlux

Netty는 네트워크 프레임워크이고, WebFlux는 웹 애플리케이션 프레임워크이다.

Netty만 쓰면 HTTP 파싱, URL 라우팅, JSON 직렬화, 인증, 예외 처리를 전부 직접 구현해야 한다. WebFlux는 그걸 Spring 방식으로 제공한다.

// Netty 직접 사용 — 전부 수동
ServerBootstrap b = new ServerBootstrap();
b.group(bossGroup, workerGroup)
 .childHandler(new ChannelInitializer<SocketChannel>() {
     protected void initChannel(SocketChannel ch) {
         ch.pipeline().addLast(new HttpRequestDecoder());
         ch.pipeline().addLast(new MyHandler()); // 직접 구현
     }
 });

// WebFlux — Spring이 다 해줌
@GetMapping("/users/{id}")
public Mono<User> getUser(@PathVariable String id) {
    return userRepository.findById(id);
}
관계:
Tomcat = 네트워크 엔진 → Spring MVC = 웹 프레임워크
Netty = 네트워크 엔진 → WebFlux = 웹 프레임워크

C10K → C10M 문제 
C10K (1999년 문제): 동시 접속 10,000개를 어떻게 처리?
→ select/poll은 O(n)이라 느림
→ epoll/kqueue로 해결 → O(준비된 수)

C10M (현재 목표): 동시 접속 10,000,000개
→ epoll도 커널-유저 공간 복사 비용 있음
→ io_uring, DPDK 등으로 해결 중
