비관적 락과 IN_PROGRESS 패턴

설계 스터디 · 락과 동시성 제어 · 2026-03-25

✦
핵심 답변
외부 API 호출이 포함된 트랜잭션에서 락을 잡으면 안 된다. IN_PROGRESS 상태로 선점하고 락을 해제한 뒤 외부 호출, 결과에 따라 완료/롤백하는 3단계 패턴을 쓴다.
◈
비관적 락 vs 낙관적 락 
// 비관적 락 — DB 수준에서 row 잠금 (SELECT ... FOR UPDATE)
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT p FROM Payment p WHERE p.id = :id")
Optional<Payment> findByIdWithLock(@Param("id") Long id);

// 낙관적 락 — 커밋 시점에 버전 충돌 감지
@Version
private Long version;  // UPDATE ... WHERE version = ?
비관적 락낙관적 락
방식조회 시점에 row 잠금커밋 시점에 충돌 감지
충돌 시대기OptimisticLockException
적합충돌이 잦을 때 (결제 취소)충돌이 드물 때 (일반 수정)
단점대기 시간, 데드락 가능재시도 로직 필요

트랜잭션이 커밋/롤백될 때 비관적 락이 해제된다.

◉
왜 락 잡고 외부 API 호출하면 안 되는가 
// ❌ 나쁜 패턴 — 락 잡은 상태에서 외부 API 호출
@Transactional
public void cancelPayment(Long paymentId, ...) {
    Payment payment = repository.findByIdWithLock(paymentId);  // 🔒 락 시작
    검증...
    cardApiClient.cancel(...);  // 50~150ms 대기 (이 동안 다른 요청 전부 블로킹!)
    payment.cancel(...);
}  // 커밋 → 🔓 락 해제

외부 API가 느려지면(타임아웃 등) 같은 row에 접근하는 모든 요청이 줄줄이 대기한다. 치명적.

◆
해결: 3단계 패턴 (Saga) 
// PaymentService — 오케스트레이터 (@Transactional 없음)
public Payment cancelPayment(Long paymentId, BigDecimal cancelAmount, String cancelReason) {
    // 1단계: 트랜잭션 1 — 락 + 선점
    String approvalNumber = transitionService.startCancel(paymentId, cancelAmount);

    try {
        // 2단계: 락 없이 외부 API + 결과 저장
        cardApiService.cancel(paymentId, approvalNumber, cancelAmount);
    } catch (CardApiClient.CardApiException e) {
        // 3b: 실패 → 롤백
        transitionService.rollbackCancel(paymentId);
        throw new CardApiFailedException(e.getMessage());
    }

    // 3a: 성공 → 완료
    return transitionService.completeCancel(paymentId, cancelAmount, cancelReason);
}
◉
동시 취소 요청 시나리오 
Thread A: startCancel(30000)
  → findByIdWithLock 🔒
  → status = APPROVED ✅
  → status = CANCEL_IN_PROGRESS → 커밋 → 🔓

Thread B: startCancel(30000)
  → findByIdWithLock 🔒 (A 커밋 후 진입)
  → status = CANCEL_IN_PROGRESS ≠ APPROVED ❌ → 예외!

IN_PROGRESS 상태가 다른 요청을 자연스럽게 차단한다.
