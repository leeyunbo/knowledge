Spring Data JPA existsBy 쿼리에서 LEFT JOIN이 발생하는 이유

설계 · JPA 실전 패턴 · 2026-04-13

✦
핵심 답변
Spring Data JPA의 쿼리 메서드 파서는 existsByUserIdAndCouponId에서 user와 coupon을 엔티티 연관관계(객체 그래프)로 해석하기 때문에, FK 컬럼이 이미 같은 테이블에 있음에도 불구하고 연관 테이블로 JOIN하여 id를 조회한다.

예를 들어 CouponIssue 엔티티에 @ManyToOne User user가 있으면, JPA는 "user → User 엔티티로 이동 → id 접근"이라는 객체 탐색 경로를 생성하고, 이를 SQL로 번역할 때 LEFT JOIN users가 붙게 된다.

◈
알아야 할 배경 개념

1. Spring Data JPA 쿼리 메서드 파싱

Spring Data JPA는 메서드 이름에서 쿼리를 자동 생성한다. 이때 엔티티의 프로퍼티 경로를 기준으로 파싱한다.

// Repository 메서드
boolean existsByUserIdAndCouponId(Long userId, Long couponId);

// Spring Data JPA의 파싱 과정
// "User" → CouponIssue.user (엔티티 프로퍼티)
// "Id"   → User.id (연관 엔티티의 id)
// "Coupon" → CouponIssue.coupon (엔티티 프로퍼티)
// "Id"    → Coupon.id (연관 엔티티의 id)

2. JPA의 세계관: 테이블이 아니라 객체

JPA(Hibernate)는 객체 관계 매핑(ORM)이다. SQL을 직접 다루는 게 아니라 엔티티 객체 그래프를 탐색해서 쿼리를 만든다. 따라서 user.id에 접근하려면 user 엔티티를 먼저 거쳐야 한다고 판단한다.

3. FK 컬럼 vs 엔티티 참조

테이블 관점에서 coupon_issue.user_id는 이미 FK 컬럼으로 존재한다. JOIN 없이도 값을 알 수 있다. 하지만 JPA는 이를 "컬럼"이 아니라 "엔티티 참조의 id"로 인식한다.

// 테이블 관점 (컬럼)
coupon_issue.user_id    ← 이미 여기 있음, JOIN 불필요

// JPA 관점 (객체 그래프)
CouponIssue.user → User.id  ← User 엔티티로 이동해야 id 접근 가능

실제 생성되는 SQL 비교

❌ 자동 생성 쿼리 (LEFT JOIN 발생)

-- existsByUserIdAndCouponId가 생성하는 SQL
SELECT COUNT(*) > 0
FROM coupon_issue ci
LEFT JOIN users u ON ci.user_id = u.id        -- 불필요한 JOIN
LEFT JOIN coupons c ON ci.coupon_id = c.id     -- 불필요한 JOIN
WHERE u.id = ? AND c.id = ?

✅ 직접 작성한 JPQL (JOIN 없음)

-- @Query로 직접 작성하면
@Query("SELECT COUNT(ci) > 0 FROM CouponIssue ci " +
       "WHERE ci.user.id = :userId AND ci.coupon.id = :couponId")

-- 생성되는 SQL
SELECT COUNT(*) > 0
FROM coupon_issue ci
WHERE ci.user_id = ? AND ci.coupon_id = ?      -- FK 컬럼 직접 참조

JPQL에서 ci.user.id라고 쓰면 Hibernate는 FK 컬럼이 이미 같은 테이블에 있다는 것을 알고 JOIN을 생략하는 최적화를 적용한다. 하지만 Spring Data JPA의 메서드 이름 파서는 이 최적화를 하지 않는다.

또 다른 해결법: Native Query

@Query(value = "SELECT EXISTS(" +
       "SELECT 1 FROM coupon_issue " +
       "WHERE user_id = :userId AND coupon_id = :couponId)",
       nativeQuery = true)
boolean existsByUserIdAndCouponIdNative(
    @Param("userId") Long userId,
    @Param("couponId") Long couponId);

Native Query는 SQL을 직접 쓰기 때문에 JPA의 객체 그래프 탐색을 완전히 우회한다. EXISTS + SELECT 1은 COUNT(*) > 0보다 성능이 좋다 — 첫 번째 매칭 행을 찾으면 즉시 반환하기 때문.

성능 차이가 중요한 이유

단일 요청에서는 LEFT JOIN의 비용이 미미하다. 하지만 쿠폰 발급처럼 동시 요청이 많은 상황에서는 이야기가 다르다.

  • LEFT JOIN → DB가 3개 테이블을 읽음 → 실행 시간 증가
  • 실행 시간 증가 → 커넥션 점유 시간 증가
  • 커넥션 점유 증가 → 풀 고갈 → connection timeout
  • 200 스레드 환경에서 쿼리 하나 30ms 줄이면 → 전체 처리량 수십% 향상

왜 Hibernate가 메서드 파서에서 최적화 안 하나?

JPQL의 ci.user.id 최적화는 Hibernate ORM 레벨에서 처리하는 것이고, 메서드 이름 파싱은 Spring Data JPA 레벨에서 처리하는 것이다. 두 레이어가 다르기 때문에 Spring Data가 생성한 쿼리 구조에 Hibernate의 FK 최적화가 적용되지 않는 것이다.
