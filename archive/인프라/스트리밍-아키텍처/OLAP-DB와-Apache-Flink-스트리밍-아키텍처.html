핵심 답변
OLAP DB는 대용량 집계 분석에 특화된 컬럼형 DB고, Apache Flink는 실시간 스트림을 변환·집계하는 엔진이다.
Kafka → Flink → OLAP DB는 실시간 분석 파이프라인의 표준 패턴이다.

서비스에서 발생하는 수많은 이벤트(클릭, 결제, 로그)를 실시간으로 집계해서 대시보드에 보여주려면 이 세 가지가 필요하다. MySQL 같은 OLTP DB는 트랜잭션 처리엔 강하지만, "지난 1시간 동안 국가별 결제 건수"처럼 대규모 집계 쿼리는 매우 느리다. OLAP DB는 이런 집계 쿼리를 초 단위로 처리하도록 설계되어 있다.

◈
OLAP DB란?

OLAP vs OLTP

OLTP(Online Transaction Processing)은 MySQL, PostgreSQL처럼 빠른 단건 읽기/쓰기에 최적화된 DB다. 반면 OLAP(Online Analytical Processing)은 수억 건의 데이터를 집계·분석하는 쿼리에 최적화되어 있다.

특성OLTPOLAP
목적트랜잭션 처리 (읽기/쓰기)분석 · 집계
쿼리 패턴단건 조회, 수정SUM, COUNT, GROUP BY 등 집계
스토리지Row-oriented (행 단위 저장)Column-oriented (컬럼 단위 저장)
최적화쓰기 성능, 트랜잭션읽기 성능, 압축, 집계 속도
대표 제품MySQL, PostgreSQL, OracleClickHouse, Druid, Pinot, StarRocks

왜 컬럼형 저장이 빠른가?

OLAP DB의 핵심은 컬럼 지향 스토리지(Columnar Storage)다. 예를 들어 "결제 금액의 합계"를 구할 때 OLTP는 모든 행을 읽고 금액 컬럼만 추출하지만, OLAP는 금액 컬럼 데이터만 연속으로 저장되어 있어서 해당 블록만 읽으면 된다. 게다가 같은 타입 데이터가 연속으로 있으면 압축률이 매우 높아져 I/O 자체가 줄어든다.

대표 OLAP DB 비교

  • ClickHouse — 초고속 컬럼형 DB. 초당 수억 행 집계. 실시간 분석 최강자. Kafka 직접 연동 지원.
  • Apache Druid — 실시간 스트리밍 인제스트 + OLAP. Kafka Consumer 내장. 시계열 분석에 강함.
  • Apache Pinot — LinkedIn이 개발한 실시간 분산 OLAP. 초저지연 쿼리.
  • StarRocks / Apache Doris — MySQL 프로토콜 호환 OLAP. 국내 기업에서 많이 채택.
  • Snowflake / BigQuery — 클라우드 기반 Data Warehouse. 관리형 서비스.

Apache Flink란?

Apache Flink는 분산 스트림 처리 엔진(Stream Processing Engine)이다. Kafka에서 들어오는 무한한 이벤트 스트림을 실시간으로 변환·집계·조인하는 역할을 한다.

핵심 개념

  • DataStream API — 스트림 데이터를 처리하는 핵심 API. map/filter/keyBy/window 등으로 파이프라인 구성.
  • Source / Sink — 데이터 입출력 커넥터. Kafka Source → 처리 → ClickHouse Sink.
  • Window — 무한 스트림을 시간 기반으로 묶어서 처리하는 단위.
    • Tumbling Window: 겹치지 않는 고정 구간 (매 10분)
    • Sliding Window: 슬라이딩 구간 (10분 크기, 1분마다 갱신)
    • Session Window: 이벤트 비활성 구간으로 자동 분리
  • Watermark — 네트워크 지연으로 늦게 도착한 이벤트를 처리하기 위한 이벤트 타임 기준선. "이 시간 이전 이벤트는 다 도착했다고 간주"
  • Stateful Processing — 이전 이벤트 상태를 기억하며 처리. 예: 사용자별 누적 금액 계산.
  • Checkpoint / Savepoint — 장애 발생 시 정확히 어디까지 처리했는지 저장. 재시작해도 중복/유실 없음.
  • Exactly-Once Semantics — Kafka + Flink + 트랜잭셔널 Sink 조합으로 정확히 한 번만 처리 보장.

Kafka → Flink → OLAP DB — 왜 이 조합인가?

이 아키텍처는 Lambda Architecture나 Kappa Architecture의 실시간 레이어를 구현하는 표준 패턴이다. 각 컴포넌트가 담당하는 역할이 명확하게 분리된다.

각 컴포넌트의 역할

  • Kafka (버퍼 + 내구성) — 이벤트를 디스크에 보관하므로 Flink가 장애나 재시작해도 다시 읽을 수 있다. 이벤트 유실 없음. Consumer가 느려도 압박이 Producer에 전달되지 않는다.
  • Flink (변환 + 집계) — 원시 이벤트를 OLAP에 넣기 좋은 형태로 변환한다. 예: JSON 파싱, 컬럼 추출, 집계(Window), 여러 스트림 조인, 이상값 필터링. OLAP DB에 직접 쿼리 부하를 주지 않고 미리 가공.
  • OLAP DB (고속 집계 제공) — 가공된 데이터에 대해 초고속 집계 쿼리를 제공한다. 수억 건 데이터도 초 단위 응답. 대시보드와 직접 연결.

실제 사용 사례

  • 실시간 결제 대시보드 — 결제 이벤트 → Kafka → Flink(국가/금액 집계) → ClickHouse → Grafana
  • 사용자 행동 분석 — 클릭/뷰 이벤트 → Kafka → Flink(세션 분석) → Druid → 분석 툴
  • 이상 탐지(Fraud Detection) — 거래 이벤트 → Kafka → Flink(패턴 감지, CEP) → Alert 또는 OLAP
  • 실시간 재고/주문 현황 — 주문 이벤트 → Kafka → Flink(집계) → Pinot → 운영 대시보드
  • 광고 클릭 집계 — 광고 클릭 → Kafka → Flink(Campaign별 집계) → StarRocks → 광고주 리포트

Druid처럼 Kafka를 직접 연동하는 경우도 있다

Apache Druid, Apache Pinot은 Kafka Consumer를 내장하고 있어서 Flink 없이 Kafka → OLAP DB 직접 연결도 가능하다. 하지만 복잡한 변환/조인/이상 탐지가 필요하면 Flink를 중간에 넣는다. 단순 집계라면 Kafka → OLAP DB 직접 연결이 더 단순하다.

어떤 OLAP DB를 선택하나?

  • ClickHouse — 빠른 집계가 최우선. 운영이 단순. Flink와 조합 매우 흔함.
  • Apache Druid — Kafka 직접 인제스트 + 시계열 분석. 별도 Flink 없이도 가능.
  • StarRocks — MySQL 문법 호환. 팀이 SQL에 익숙할 때. 국내 스타트업 채택 증가.
  • Snowflake/BigQuery — 관리 부담 없는 클라우드 환경. 실시간보다 준실시간(분 단위) 수준.
◆
시각화 — 실시간 데이터 파이프라인

Kafka는 이벤트를 안전하게 보관하는 버퍼, Flink는 중간에서 변환·집계하는 엔진, OLAP DB는 대시보드가 빠르게 쿼리할 수 있는 저장소 역할을 한다. 각 컴포넌트가 실패해도 재처리(Kafka offset 되감기 + Flink Checkpoint)로 데이터 유실 없이 복구 가능하다.
