Elasticsearch 핵심 개념 정리

Elasticsearch · 기본개념 · 2025-03-25

◈
ES 내부 저장 구조
핵심: 인덱스 → 샤드 → 세그먼트 → 파일들
구성 요소 설명 특징
인덱스 데이터를 담는 논리적 단위 RDB의 테이블과 유사. 우리가 이름을 정함
샤드 인덱스를 물리적으로 분할한 조각 병렬 처리 가능. 권장 크기: 10~50GB
세그먼트 실제 데이터가 저장되는 파일 단위 불변(immutable). refresh 시 생성됨
레플리카 Primary 샤드의 복제본 장애 대비. 저장 공간 2배

세그먼트 파일 구조

각 세그먼트마다 아래 파일들이 생성됨 (번호: _0, _1, _2, ...)

파일 용도 설명
_0.fdt 원본 데이터 _source 필드 (저장된 JSON 원본)
_0.tim / .tip 역인덱스 단어 → 문서 매핑 (검색용)
_0.dvd / .dvm Doc Values 정렬/집계용 컬럼 데이터
_0.si / .fnm 메타데이터 세그먼트 정보, 필드명/타입 정보
실제 디스크 사용량: 원본 JSON + 역인덱스 + Doc Values + 메타데이터 = JSON의 1.5~2배
◉
역인덱스와 필드 타입
역인덱스 (Inverted Index): 단어 → 문서 목록을 미리 만들어두는 자료구조. ES가 빠른 이유!

필드 타입별 역인덱스 방식

타입 역인덱스 방식 검색 비용
keyword ⭐ 값 통째로 저장 정확히 일치만 낮음
text 형태소 분석 후 쪼갬 부분 검색 가능 높음
date 숫자로 변환 범위 검색 낮음
boolean true/false 정확히 일치 낮음
long 숫자 범위 검색 낮음
왜 keyword를 주로 사용?
partnerId, msgId, code 같은 필드는 정확히 일치 검색만 필요.
keyword는 형태소 분석 안 함 → 인덱싱 비용 낮음

인덱스 설계 포인트

인덱스 vs 역인덱스 (헷갈리는 용어!)

구분 누가 만듦 용도 예시
인덱스 우리가 설계 데이터 저장/관리 단위 alio-send-kakao-2026.03.25
역인덱스 ES가 자동 생성 빠른 검색용 자료구조 "testbizppurio" → [doc1, doc5]

날짜별 인덱스는 역인덱스(형태소)와 무관하고, 순수하게 관리 편의를 위한 설계 결정!

인덱스 템플릿 설정

설정 권장값 선정 이유
number_of_shards 2 병렬 처리 (권장: 샤드당 10~50GB)
number_of_replicas 1 (운영) / 0 (개발) 운영: 장애 대응 (저장 공간 2배)
개발: 용량 절약
refresh_interval 5s 너무 짧으면 세그먼트 과다 생성 → I/O 부하
매핑 안 하면? ES가 자동 추측(Dynamic Mapping) → 보통 text로 판단 → 불필요한 형태소 분석 발생 → 성능 저하
반드시 매핑 정의 필요!
◆
ILM과 용량 계산

ILM (Index Lifecycle Management)

인덱스의 생명주기를 자동 관리. 오래된 데이터를 자동으로 축소/삭제.

Phase 기간 액션 설명
Hot 0 ~ 7일 rollover 활발히 쓰기/읽기
Warm 7일 ~ N일 shrink, forcemerge 읽기만, 샤드 축소
Delete N일 이후 delete 인덱스 삭제

용량 계산 공식

월간 JSON 용량
  × ES 오버헤드 (1.5~2배)   ← 역인덱스 + 메타데이터
  × 레플리카 (2배)          ← replica: 1
  ÷ 보관일수/30일
  = 실제 디스크 사용량

예시 계산 (월간 3억건, JSON 300 Bytes 기준)

항목 옵션 A (2개 모듈) 옵션 B (3개 모듈)
월간 JSON 용량 ~180GB ~270GB
ES 실제 저장 (×1.5~2) ~270~360GB ~400~540GB
레플리카 포함 (×2) ~540~720GB ~800GB~1TB
보관기간별 환산:
• 7일 보관: 위 수치의 약 1/4
• 15일 보관: 위 수치의 약 1/2
• 30일 보관: 위 수치 그대로
