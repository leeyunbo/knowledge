Redis 실전 패턴 총정리

인프라 · Redis · 2026-04-07

✦
핵심 답변
Redis는 단순 캐시를 넘어 분산락 · 리더보드 · 스트림 · 속도 제한 · 클라이언트 캐싱까지 지원하는 다목적 인메모리 데이터 구조 서버다.

각 패턴은 Redis의 특정 자료구조와 명령어의 원자성을 활용한다. 단순히 "Redis에 저장한다"가 아니라 어떤 자료구조를, 왜, 어떻게 쓰는지 이해하는 것이 핵심이다.

◈
1. Redis 분산락 — SET NX PX 패턴

여러 서버 인스턴스가 동시에 같은 자원에 접근하지 못하도록 분산 환경에서 뮤텍스를 구현한다.

락 획득

# NX: 키가 없을 때만 SET (원자적)
# PX 30000: 30초 후 자동 만료 (데드락 방지)
# value는 UUID — 자신만 해제할 수 있게
SET lock:order:123 "uuid-abc-1234" NX PX 30000

락 해제 — Lua 스크립트로 원자적 처리

-- GET + DEL을 원자적으로 → 내 락만 해제
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end

왜 Lua 스크립트인가? GET 후 DEL을 따로 실행하면 내가 GET하는 사이에 다른 프로세스가 락을 재획득할 수 있다. Lua 스크립트는 Redis 서버에서 원자적으로 실행된다.

Java 구현 (Redisson 사용 권장)

// Redisson은 분산락을 완전히 추상화해줌
RLock lock = redissonClient.getLock("lock:order:" + orderId);
try {
    if (lock.tryLock(3, 30, TimeUnit.SECONDS)) {
        // critical section
    }
} finally {
    lock.unlock();
}

2. Redlock 알고리즘은 안전한가?
Redlock은 단일 Redis 장애에는 강하지만, GC pause나 네트워크 지연 시 두 프로세스가 동시에 락을 보유할 수 있다. 강한 일관성이 필요하면 ZooKeeper/etcd를 써라.

Redlock 동작 원리

독립적인 Redis 노드 N개(보통 5개)에 순차적으로 락 획득을 시도한다. 과반수(3개) 이상에서 획득 성공하고, 전체 획득 시간이 TTL보다 짧으면 락 획득으로 간주한다.

노드 1: SET lock "uuid" NX PX 10000 → OK  ✓
노드 2: SET lock "uuid" NX PX 10000 → OK  ✓
노드 3: SET lock "uuid" NX PX 10000 → OK  ✓  ← 과반수 달성
노드 4: SET lock "uuid" NX PX 10000 → FAIL
노드 5: (타임아웃)

Martin Kleppmann이 제기한 문제

  • GC pause — 프로세스 A가 락 획득 후 GC로 30초 멈춤 → 락 TTL 만료 → 프로세스 B가 락 획득 → A가 GC 끝나고 재개 → A, B 동시 critical section 진입
  • Fencing Token 부재 — 락 획득 시 단조 증가하는 토큰을 받아서 스토리지에 함께 전달해야 진정한 안전성 보장. Redlock엔 이 메커니즘이 없음.
  • 시계 불일치 — 노드들의 시스템 시계가 다르면 TTL 계산이 틀어짐.

Antirez(Redis 창시자)의 반론

Antirez는 "현실적인 GC pause는 수백 ms 수준이고 TTL을 충분히 설정하면 안전하다"고 반론했다. 하지만 Kleppmann의 핵심인 "Redlock은 분산 시스템 이론상 완전히 안전하지 않다"는 반박하지 못했다.

결론: 언제 무엇을 쓸까?

상황선택
성능 우선, 일시적 중복 허용 가능 (캐시 갱신 등)단일 Redis 분산락 (SET NX PX)
단일 Redis 장애 허용 안 됨, 중복은 허용Redlock
금융/결제 등 강한 일관성 필수ZooKeeper / etcd / DB 비관락

3. 리더보드 구현 — Sorted Set

Redis의 Sorted Set(ZSET)은 점수(score)와 함께 멤버를 저장하고, 점수 기준으로 자동 정렬한다. 시간 복잡도 O(log N)으로 대규모 리더보드에 최적이다.

# 점수 추가/업데이트
ZADD leaderboard 1500 "user:alice"
ZADD leaderboard 2300 "user:bob"
ZADD leaderboard 980  "user:charlie"

# Top 10 조회 (높은 점수 순)
ZREVRANGE leaderboard 0 9 WITHSCORES

# 내 순위 조회 (0-indexed, 높은 점수 기준)
ZREVRANK leaderboard "user:alice"   # → 1 (2등)

# 점수 증가 (원자적)
ZINCRBY leaderboard 100 "user:alice"

# 특정 점수 범위 조회
ZREVRANGEBYSCORE leaderboard 9999 1000 WITHSCORES LIMIT 0 10

주변 순위 조회 (내 위아래 N명)

# 1. 내 순위 조회
rank = ZREVRANK leaderboard "user:alice"  # 예: 49

# 2. 49-2 ~ 49+2 = 47~51위 조회
ZREVRANGE leaderboard 47 51 WITHSCORES

4. Redis Stream — 실시간 데이터 파이프라인

Redis Stream은 append-only 로그 자료구조로 Kafka처럼 메시지를 순서대로 보관하고 Consumer Group으로 분산 처리한다. Kafka보다 가볍지만 기능도 제한적이다.

# 메시지 추가 (* = 자동 ID 생성)
XADD orders * orderId 1001 amount 50000 userId alice

# 메시지 읽기 (0부터 전체)
XREAD COUNT 10 STREAMS orders 0

# 새 메시지만 블로킹 대기 (0ms = 무한 대기)
XREAD COUNT 10 BLOCK 0 STREAMS orders $

Consumer Group — 분산 처리

# 그룹 생성 ($ = 이후 새 메시지부터)
XGROUP CREATE orders payment-group $ MKSTREAM

# Consumer가 메시지 가져가기 (> = 아직 안 읽은 메시지)
XREADGROUP GROUP payment-group worker-1 COUNT 5 STREAMS orders >

# 처리 완료 ACK
XACK orders payment-group 1640000000000-0

# 처리 실패한 메시지 재처리 (PEL 확인)
XPENDING orders payment-group - + 10

Kafka vs Redis Stream

항목KafkaRedis Stream
처리량초당 수백만 메시지초당 수십만 메시지
보관디스크, 장기 보관메모리 (MAXLEN으로 제한)
Consumer Group완전 지원지원 (기능 제한)
운영 복잡도높음낮음 (Redis 이미 있으면 무료)
적합한 경우대용량, 장기 이벤트 소싱내부 서비스 간 가벼운 이벤트

5. Redis Rate Limit — 요청 속도 제한

방법 1 — Fixed Window Counter (단순, 경계 문제 있음)

# 분당 100회 제한
key = "ratelimit:userId:${minute}"
count = INCR key
if count == 1: EXPIRE key 60   # 첫 요청 시 TTL 설정
if count > 100: reject

문제: 0:59초에 100회 + 1:00초에 100회 = 1초 사이에 200회 가능.

방법 2 — Sliding Window (Sorted Set)

# 현재 시간 기준 60초 내 요청 수 계산
now = System.currentTimeMillis()
key = "ratelimit:userId"

ZADD key now now                          # 현재 요청 추가
ZREMRANGEBYSCORE key 0 (now - 60000)     # 60초 이전 항목 제거
count = ZCARD key                         # 윈도우 내 요청 수

if count > 100: reject
EXPIRE key 60                             # 키 자동 만료

정확한 슬라이딩 윈도우지만 메모리를 더 사용한다. Lua 스크립트로 원자적 처리 권장.

방법 3 — Token Bucket (Lua 스크립트)

-- 토큰 버킷: 버킷에 토큰이 있으면 소비, 없으면 거절
-- 토큰은 시간이 지남에 따라 자동 보충
local tokens = tonumber(redis.call("get", KEYS[1])) or capacity
local refill = math.floor((now - last_time) / interval) * rate
tokens = math.min(capacity, tokens + refill)
if tokens >= 1 then
    redis.call("set", KEYS[1], tokens - 1)
    return 1  -- 허용
else
    return 0  -- 거절
end

6. 클라이언트 사이드 캐싱 — Redis 6.0+
클라이언트가 읽은 키를 로컬 메모리에 캐싱하고, Redis 서버가 키 변경 시 invalidation 메시지를 보내 로컬 캐시를 무효화한다. 네트워크 왕복 없이 응답.

동작 방식

  • Tracking 모드: CLIENT TRACKING ON → 서버가 이 클라이언트가 읽은 키 목록 추적
  • 클라이언트는 읽은 값을 로컬(JVM heap 등)에 저장
  • 해당 키가 변경(SET/DEL)되면 서버가 Pub/Sub 채널로 invalidation 알림 전송
  • 클라이언트는 알림 받으면 로컬 캐시에서 해당 키 삭제
# Tracking 활성화 (RESP3 프로토콜 또는 Pub/Sub 채널 지정)
CLIENT TRACKING ON BCAST PREFIX user:   # user: 로 시작하는 키만 추적
CLIENT TRACKING ON REDIRECT 12345       # 다른 연결(ID=12345)로 invalidation 전달

장단점

일반 Redis 조회클라이언트 사이드 캐싱
속도네트워크 왕복 필요 (~1ms)로컬 메모리 직접 조회 (ns)
일관성항상 최신값invalidation 지연 가능
구현 복잡도낮음높음 (추가 연결, 캐시 관리)
적합한 경우일반적인 경우읽기가 극도로 많고 변경이 드문 경우

7. Hot Key 문제와 해결 방법
특정 키에 요청이 집중되면 해당 Redis 노드에 CPU/네트워크 병목이 생긴다. 핵심 해결책은 키 분산 또는 로컬 캐시로 Redis 호출 자체를 줄이는 것이다.

Hot Key 탐지

# Redis 4.0+, maxmemory-policy: allkeys-lfu or volatile-lfu 필요
redis-cli --hotkeys

# 또는 MONITOR로 실시간 확인 (운영환경 주의 — 성능 영향)
redis-cli MONITOR | grep "GET\|SET" | awk '{print $4}' | sort | uniq -c | sort -rn | head

해결책 1 — 키 분산 (Key Sharding)

// hot:config 대신 hot:config:0 ~ hot:config:9 로 분산
int shard = ThreadLocalRandom.current().nextInt(10);
String key = "hot:config:" + shard;
String value = redis.get(key);  // 10개 노드로 부하 분산

쓸 때는 모든 샤드에 쓰거나, 읽기 전용 데이터면 한 곳에만 쓰고 나머지는 복제한다.

해결책 2 — 로컬 캐시 (L1 Cache)

// Caffeine 로컬 캐시: 100ms TTL로 Redis 호출 최대 10분의 1로 감소
Cache<String, String> localCache = Caffeine.newBuilder()
    .expireAfterWrite(100, TimeUnit.MILLISECONDS)
    .maximumSize(1000)
    .build();

String value = localCache.get(key, k -> redis.get(k));

100ms TTL이면 초당 최대 10번만 Redis에 물어본다. 100ms 내 일관성 허용 가능하면 매우 효과적.

해결책 3 — Read Replica 활용

# Redis Cluster에서 replica에서 읽기 (기본은 master만 읽음)
# Lettuce 사용 시
ReadFrom.REPLICA_PREFERRED   # replica 우선, 없으면 master

# 단점: replica 복제 지연(replication lag)으로 약간 오래된 데이터 읽을 수 있음

해결책 4 — 데이터 구조 변경

대형 Hash나 List를 하나의 키에 몰지 말고 작게 쪼갠다. 예: user:1:profile 대신 user:1:name, user:1:email로 분리하거나, 반대로 여러 작은 키를 Hash 하나로 합쳐 키 수를 줄이는 방향 검토.

시각화 — Redis 자료구조 → 패턴 매핑

Redis 자료구조와 실전 패턴의 매핑. String의 원자적 SET NX로 분산락, Sorted Set의 자동 정렬로 리더보드, Stream으로 이벤트 파이프라인을 구현한다.
