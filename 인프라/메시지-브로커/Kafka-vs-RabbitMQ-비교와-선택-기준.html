Kafka vs RabbitMQ 비교와 선택 기준

DevOps 인프라 · 메시지 브로커 · 2026-03-26

✦
핵심 답변
Kafka는 대용량 이벤트 스트리밍, RabbitMQ는 작업 큐/라우팅에 적합하다. "얼마나 많은 메시지를 처리하는가"와 "메시지를 어떻게 소비하는가"로 선택한다.
◈
Kafka — 분산 이벤트 스트리밍 플랫폼

핵심 개념

  • Topic — 메시지가 저장되는 카테고리 (예: "payment-events")
  • Partition — Topic을 나눈 단위. 파티션 내에서 순서 보장
  • Producer — 메시지를 Topic에 쓰는 쪽
  • Consumer Group — 같은 그룹의 Consumer들이 파티션을 나눠서 소비
  • Offset — Consumer가 어디까지 읽었는지 추적하는 위치값

동작 방식

Producer → [Topic: payment-events]
              ├─ Partition 0: [msg1, msg3, msg5, ...]
              ├─ Partition 1: [msg2, msg4, msg6, ...]
              └─ Partition 2: [msg7, msg8, msg9, ...]
                    ↓
           Consumer Group A
              ├─ Consumer 1 → Partition 0
              ├─ Consumer 2 → Partition 1
              └─ Consumer 3 → Partition 2

핵심 특성

  • 메시지 보관 — 소비해도 삭제 안 함. 디스크에 보관 (retention 기간 설정)
  • 재처리 가능 — offset을 되감으면 다시 읽을 수 있음
  • 처리량 — 초당 수십만~수백만 메시지
  • 순서 보장 — 파티션 단위로 보장 (전체 Topic에서는 보장 안 됨)
  • Pull 방식 — Consumer가 직접 가져감 (속도 조절 가능)
◈
RabbitMQ — AMQP 기반 메시지 브로커

핵심 개념

  • Exchange — 메시지를 받아서 Queue로 라우팅하는 역할
  • Queue — 메시지가 대기하는 버퍼
  • Binding — Exchange와 Queue를 연결하는 규칙
  • Routing Key — 메시지를 어떤 Queue로 보낼지 결정하는 키

Exchange 타입

Direct Exchange  — routing key 정확히 일치하는 Queue로
Fanout Exchange  — 연결된 모든 Queue로 (브로드캐스트)
Topic Exchange   — 패턴 매칭 (payment.* → payment.success, payment.fail)
Headers Exchange — 헤더 기반 라우팅

동작 방식

Producer → [Exchange] → routing → [Queue 1] → Consumer A
                                  → [Queue 2] → Consumer B
                                  → [Queue 3] → Consumer C

핵심 특성

  • 메시지 삭제 — Consumer가 ACK 보내면 Queue에서 제거
  • 유연한 라우팅 — Exchange 타입으로 복잡한 라우팅 가능
  • 처리량 — 초당 수만 메시지
  • 순서 보장 — 단일 Queue 내에서 보장
  • Push 방식 — Broker가 Consumer에게 밀어줌 (prefetch로 조절)

언제 뭘 쓰는가

Kafka를 선택하는 경우

  • 선착순 쿠폰, 결제 이벤트 — 순간 트래픽 폭증, 대용량 처리
  • 이벤트 소싱 — 모든 이벤트를 기록하고 재처리해야 할 때
  • 실시간 데이터 파이프라인 — 로그 수집, 지표 집계
  • 여러 Consumer가 같은 메시지를 소비 — Consumer Group으로 독립 소비
  • 순서가 중요한 대용량 처리 — 파티션 키로 같은 사용자의 이벤트를 순서 보장

RabbitMQ를 선택하는 경우

  • 이메일/알림 발송 — 작업 큐, 실패 시 재시도
  • 복잡한 라우팅 — 조건에 따라 다른 큐로 분배
  • 요청-응답 패턴 — RPC 스타일 통신
  • 트래픽이 크지 않은 비동기 처리 — 단순하고 빠르게 구축
  • 메시지 우선순위 — Priority Queue 지원

실무 조합 예시

결제 시스템:
  결제 이벤트 발행 → Kafka (대용량, 재처리, 여러 Consumer)
  결제 완료 알림 → RabbitMQ (이메일/SMS 발송 큐)

이커머스:
  주문 이벤트 스트림 → Kafka
  재고 차감 요청 → Kafka (순서 보장 필요)
  배송 요청 → RabbitMQ (작업 큐)
