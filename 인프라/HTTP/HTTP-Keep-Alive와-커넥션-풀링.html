HTTP Keep-Alive와 커넥션 풀링

네트워크 · HTTP · 2026-03-27

✦
핵심 답변
HTTP Keep-Alive는 TCP 연결을 끊지 않고 유지하는 기능이고, 커넥션 풀링은 유지된 연결을 재사용할 수 있도록 보관하는 구조입니다. Keep-Alive만으로는 부족하고, 풀이 있어야 실제로 연결이 재사용됩니다.

HTTP는 Request/Response 모델이지만, HTTP/1.1부터 Keep-Alive가 기본으로 활성화됩니다. 이는 응답 후에도 TCP 연결을 닫지 않겠다는 의미입니다.

그러나 Java의 SimpleClientHttpRequestFactory처럼 커넥션 풀이 없는 클라이언트는 응답을 받은 뒤 연결 객체에 대한 참조가 사라져 GC가 소켓을 닫아버립니다. 서버가 Keep-Alive를 허용해도 클라이언트가 연결을 보관하지 않으면 매번 새로운 TCP 연결을 생성하게 됩니다.

커넥션 풀은 이 문제를 해결합니다. 사용한 연결을 풀에 반환(return)하고, 다음 요청 시 풀에서 빌려(borrow) 재사용합니다. 이를 통해 TCP 3-way handshake 비용을 제거하고, TIME_WAIT 소켓 폭증을 방지합니다.

TCP 3-Way Handshake

TCP 연결을 수립하려면 클라이언트-서버 간 SYN → SYN+ACK → ACK 3단계 패킷 교환이 필요합니다. 네트워크 왕복 시간(RTT)이 1ms라면, 매 요청마다 약 1.5ms의 연결 수립 비용이 추가됩니다. 2000 TPS에서는 초당 3,000ms에 달하는 누적 지연이 발생합니다.

Ephemeral Port (임시 포트)

클라이언트가 TCP 연결을 생성할 때 OS는 49152~65535 범위의 임시 포트를 할당합니다. 사용 가능한 포트는 약 16,000개입니다. 소켓이 닫혀도 TIME_WAIT 상태에서 포트를 점유하므로, 대량 연결 생성 시 포트가 고갈될 수 있습니다.

TIME_WAIT 상태

TCP 연결을 먼저 끊는 쪽(active close)은 소켓이 즉시 사라지지 않고 TIME_WAIT 상태로 60초간 유지됩니다. 이는 네트워크에 남아있을 수 있는 지연 패킷이 새 연결에 영향을 주는 것을 방지하기 위한 TCP 설계입니다.

더 깊이 파고들기

SimpleClientHttpRequestFactory는 왜 연결을 재사용하지 못하는가?

Spring의 기본 RestTemplate은 SimpleClientHttpRequestFactory를 사용합니다. 이 팩토리는 내부적으로 java.net.HttpURLConnection을 사용하며, 커넥션 풀이 없습니다.

요청-응답이 끝나면 HttpURLConnection 객체에 대한 참조가 메서드 스코프를 벗어나 사라집니다. 참조가 없어진 객체는 GC 대상이 되고, GC가 이 객체를 수거하면서 내부 소켓의 close()가 호출됩니다. 서버가 Keep-Alive를 허용하더라도 클라이언트 측에서 소켓을 닫아버리는 것입니다.

커넥션 풀링은 어떻게 동작하는가?

Apache HttpClient의 PoolingHttpClientConnectionManager는 다음과 같이 동작합니다:

  1. Borrow: 요청 시 풀에서 유휴 연결을 꺼냄 (없으면 새로 생성)
  2. Execute: 빌린 연결로 HTTP 요청/응답 수행
  3. Return: 응답이 끝나면 연결을 풀에 반환 (닫지 않음)
  4. Reuse: 다음 요청이 같은 호스트라면 반환된 연결을 재사용

풀은 연결 객체에 대한 강한 참조(strong reference)를 유지하므로 GC 대상이 되지 않습니다. 소켓은 살아있고, Keep-Alive 덕분에 서버도 연결을 유지하고 있으므로 즉시 재사용할 수 있습니다.

2000 TPS에서의 TIME_WAIT 문제

커넥션 풀 없이 2000 TPS로 외부 API를 호출하면 다음과 같은 상황이 발생합니다:

초당 2,000개 소켓 생성
× TIME_WAIT 유지 시간 60초
= 최대 120,000개 TIME_WAIT 소켓

사용 가능한 Ephemeral Port: ~16,000개
→ 포트 고갈 → java.net.BindException: Address already in use

커넥션 풀을 사용하면 소켓 수가 풀 크기(예: maxTotal=200)로 제한됩니다. 200개의 소켓을 재사용하므로 TIME_WAIT 자체가 거의 발생하지 않습니다.

PoolingHttpClientConnectionManager 설정 예시

@Bean
public RestTemplate restTemplate() {
    PoolingHttpClientConnectionManager cm =
        new PoolingHttpClientConnectionManager();
    cm.setMaxTotal(200);              // 전체 최대 커넥션 수
    cm.setDefaultMaxPerRoute(50);     // 호스트당 최대 커넥션 수

    CloseableHttpClient httpClient = HttpClients.custom()
        .setConnectionManager(cm)
        .setKeepAliveStrategy((response, context) -> 30_000) // 30초
        .build();

    HttpComponentsClientHttpRequestFactory factory =
        new HttpComponentsClientHttpRequestFactory(httpClient);
    factory.setConnectTimeout(3_000);
    factory.setReadTimeout(5_000);

    return new RestTemplate(factory);
}
