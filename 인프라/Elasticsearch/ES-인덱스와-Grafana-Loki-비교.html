ES의 인덱스와 Grafana Loki 비교

DevOps 인프라 · Elasticsearch · 2026-03-23

✦
핵심 답변
ES는 로그 본문까지 전부 인덱싱(역색인)하여 어떤 키워드든 즉시 검색할 수 있고, Loki는 본문을 인덱싱하지 않고 라벨(메타데이터)만 인덱싱하여 저장 비용을 극단적으로 줄인다.

둘 다 로그를 저장하고 검색하는 시스템이지만, 인덱싱 전략이 정반대다. 이 차이가 성능, 비용, 운영 복잡도 전부를 결정한다.

알아야 할 배경 개념

인덱스(Index)란?

데이터베이스의 테이블과 비슷한 개념이다. ES에서 인덱스 = 문서(document)의 모음이다. 로그 한 줄 한 줄이 하나의 문서(JSON)가 되어 인덱스에 저장된다.

역색인(Inverted Index)

ES의 핵심 자료구조. 책 뒤쪽의 "찾아보기"와 같다:

로그 원문:
  doc1: "user login failed from 192.168.1.1"
  doc2: "user login success from 10.0.0.1"
  doc3: "payment failed timeout"

역색인:
  "user"    → [doc1, doc2]
  "login"   → [doc1, doc2]
  "failed"  → [doc1, doc3]
  "payment" → [doc3]
  "timeout" → [doc3]

모든 단어가 어떤 문서에 있는지 미리 매핑해두므로, "failed"를 검색하면 전체 스캔 없이 즉시 doc1, doc3을 찾는다.

Shard와 Replica

하나의 인덱스는 여러 샤드(shard)로 분할된다. 각 샤드는 독립적인 Lucene 인스턴스이다. 이를 통해 데이터를 여러 노드에 분산 저장하고, 병렬로 검색할 수 있다.

  • Primary Shard — 원본 데이터를 담는 샤드
  • Replica Shard — Primary의 복제본. 노드 장애 시 데이터 보호 + 읽기 부하 분산

ES 인덱스의 내부 구조

인덱스에 문서가 들어오면 다음이 일어난다:

  1. Analyze — 텍스트를 토큰(단어)으로 분리. "user login failed" → ["user", "login", "failed"]
  2. Inverted Index 갱신 — 각 토큰이 어떤 문서에 있는지 기록
  3. Doc Values 저장 — 정렬/집계용 컬럼 지향 저장소
  4. _source 저장 — 원본 JSON을 그대로 보관 (검색 결과 반환용)

즉, 원본 + 역색인 + 컬럼 저장소를 전부 유지한다. 이래서 검색이 빠르지만 저장 공간을 많이 먹는다.

Grafana Loki는 왜 다른가?

Loki의 설계 철학: "로그 본문은 인덱싱하지 않는다"

  • 인덱싱 대상은 라벨(label)만. 예: {app="gateway", env="prod", host="aliogw03"}
  • 로그 본문은 압축된 청크(chunk)로 Object Storage(S3 등)에 저장
  • 검색 시: 라벨로 청크를 좁힌 뒤, 해당 청크를 brute-force grep

ES처럼 모든 단어를 역색인하지 않으므로, 인덱스 크기가 극적으로 작다.

핵심 비교

항목 Elasticsearch Grafana Loki
인덱싱 대상 로그 본문의 모든 단어 (Full-text) 라벨(메타데이터)만
검색 방식 역색인 → 즉시 결과 라벨로 범위 축소 → 청크 brute-force
검색 속도 매우 빠름 (어떤 키워드든) 라벨 매칭은 빠름, 본문 검색은 느림
저장 비용 원본의 1.5~2배 (역색인 + _source) 원본의 0.1~0.3배 (압축 청크)
스토리지 로컬 디스크 (SSD 권장) Object Storage (S3, GCS 등)
운영 복잡도 높음 (JVM 튜닝, 샤드 관리, ILM) 낮음 (stateless 컴포넌트)
적합한 경우 다양한 키워드로 자유롭게 검색, 집계/분석 라벨 기반 필터링 + 최근 로그 조회
메모리 요구량 높음 (JVM 힙 + OS 캐시) 낮음

실무 선택 기준

ES를 선택해야 할 때: 로그에서 임의의 키워드를 자유롭게 검색해야 할 때. 예: 특정 에러 메시지, 사용자 ID, 트랜잭션 ID 등으로 검색. 집계(aggregation)가 필요한 경우.
Loki를 선택해야 할 때: 비용이 최우선이고, "이 서버의 최근 로그 보여줘" 수준의 조회면 충분할 때. Grafana와 자연스럽게 통합. Kubernetes 환경에서 특히 강력.
◆
시각화

왼쪽 ES는 모든 단어를 역색인으로 관리해서 즉시 검색이 가능하지만 저장 비용이 크다. 오른쪽 Loki는 라벨만 인덱싱하고 본문은 압축 저장하여 비용을 극단적으로 줄이되, 본문 검색은 grep 방식으로 처리한다.
