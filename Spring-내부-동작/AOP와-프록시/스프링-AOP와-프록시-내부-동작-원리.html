스프링 AOP와 프록시 내부 동작 원리

Spring 내부 동작 · AOP와 프록시 · 2026-03-25

✦
핵심 답변
Spring AOP는 런타임 프록시로 동작한다. 대상 빈을 감싸는 프록시 객체가 메서드 호출을 가로채고, Advice(부가 로직)를 실행한 뒤 실제 타깃을 호출한다. @Transactional, @Cacheable, @Async 모두 이 프록시 메커니즘 위에서 동작하며, 프록시를 거치지 않는 self-invocation에서는 AOP가 적용되지 않는다.

프록시 구현에는 두 가지 방식이 있다. JDK Dynamic Proxy(인터페이스 기반)와 CGLIB Proxy(상속 기반). Spring Boot 2.0부터 기본값은 CGLIB이며, proxyTargetClass=true가 디폴트다.

◈
프록시 패턴 — 왜 Spring이 프록시를 쓰는가

프록시 패턴은 실제 객체에 대한 접근을 제어하는 대리 객체를 두는 디자인 패턴이다. 클라이언트는 프록시를 통해 타깃 객체에 접근하므로, 타깃 코드를 수정하지 않고도 부가 기능을 끼워 넣을 수 있다.

Spring은 이 패턴을 활용해 횡단 관심사(Cross-Cutting Concerns)를 분리한다. 트랜잭션 관리, 로깅, 보안, 캐싱 같은 공통 로직을 비즈니스 코드에서 분리해 별도 Aspect로 관리하고, 런타임에 프록시를 통해 자동으로 적용한다. 

// 클라이언트가 보는 것: 프록시 객체
// 실제 호출 흐름
Client → Proxy → [Before Advice] → Target.method() → [After Advice] → Client

Advice 타입별 실행 순서

@Around — proceed() 호출 전

    Target.method() 실행
  @AfterReturning (정상) / @AfterThrowing (예외)

@Around — proceed() 호출 후
@Aspect
@Component
public class LoggingAspect {

    @Around("execution(* com.example.service.*.*(..))")
    public Object logExecution(ProceedingJoinPoint joinPoint) throws Throwable {
        long start = System.currentTimeMillis();
        Object result = joinPoint.proceed();  // 타깃 메서드 실행
        long elapsed = System.currentTimeMillis() - start;
        log.info("{} executed in {}ms", joinPoint.getSignature(), elapsed);
        return result;
    }
}
◉
JDK Dynamic Proxy — 인터페이스 기반

Java 표준 라이브러리 java.lang.reflect.Proxy가 제공하는 프록시 메커니즘이다. 인터페이스를 구현하는 프록시 클래스를 런타임에 동적으로 생성한다.

핵심 API

// 프록시 생성
Object proxy = Proxy.newProxyInstance(
    classLoader,           // 프록시 클래스를 정의할 클래스로더
    new Class[]{ MyService.class },  // 프록시가 구현할 인터페이스 배열
    invocationHandler      // 메서드 호출을 가로챌 핸들러
);

InvocationHandler 인터페이스

public interface InvocationHandler {
    Object invoke(Object proxy, Method method, Object[] args) throws Throwable;
}

내부 동작 흐름

  1. Proxy.newProxyInstance() 호출
  2. 내부적으로 Proxy.getProxyClass()가 바이트코드를 동적 생성하여 프록시 클래스를 만듦
  3. 생성된 프록시 클래스는 java.lang.reflect.Proxy를 상속하고, 지정된 인터페이스를 구현
  4. 프록시 클래스의 생성자에 InvocationHandler를 전달하여 인스턴스 생성
  5. 프록시의 모든 메서드 호출 → InvocationHandler.invoke()로 위임
// 내부적으로 생성되는 프록시 클래스 (개념)
public class $Proxy0 extends Proxy implements MyService {
    private InvocationHandler h;

    public $Proxy0(InvocationHandler h) {
        super(h);
        this.h = h;
    }

    @Override
    public void doSomething() {
        // 모든 호출이 InvocationHandler로 위임됨
        h.invoke(this, doSomethingMethod, null);
    }
}
제약사항: 타깃 객체가 반드시 인터페이스를 구현해야 한다. 인터페이스가 없는 구체 클래스에는 JDK Dynamic Proxy를 적용할 수 없다. 또한 Proxy를 이미 상속하므로 다른 클래스를 상속할 수 없다 (Java 단일 상속).
◉
CGLIB Proxy — 상속 기반 바이트코드 조작

CGLIB(Code Generation Library)는 ASM 라이브러리를 사용해 바이트코드를 직접 조작하여 타깃 클래스의 서브클래스를 런타임에 생성한다. 인터페이스 없이도 프록시를 만들 수 있다. Spring Framework는 CGLIB를 spring-core에 내장(repackage)하고 있다.

핵심 API

Enhancer enhancer = new Enhancer();
enhancer.setSuperclass(MyServiceImpl.class);  // 타깃 클래스를 부모로 설정
enhancer.setCallback(methodInterceptor);       // 메서드 가로채기 콜백
MyServiceImpl proxy = (MyServiceImpl) enhancer.create();

MethodInterceptor 인터페이스

public interface MethodInterceptor extends Callback {
    Object intercept(Object obj, Method method, Object[] args,
                      MethodProxy proxy) throws Throwable;
}

// 사용 예시
MethodInterceptor interceptor = (obj, method, args, proxy) -> {
    System.out.println("Before: " + method.getName());
    Object result = proxy.invokeSuper(obj, args);  // 부모(타깃) 메서드 호출
    System.out.println("After: " + method.getName());
    return result;
};

내부 동작 흐름

  1. Enhancer가 타깃 클래스를 상속하는 서브클래스의 바이트코드를 ASM으로 생성
  2. 서브클래스의 모든 non-final 메서드를 오버라이드
  3. 오버라이드된 메서드에서 MethodInterceptor의 intercept()를 호출
  4. MethodProxy.invokeSuper()로 실제 부모 클래스의 원본 메서드를 호출
// CGLIB가 생성하는 서브클래스 (개념)
public class MyServiceImpl$$EnhancerByCGLIB$$a1b2c3 extends MyServiceImpl {
    private MethodInterceptor interceptor;

    @Override
    public void doSomething() {
        interceptor.intercept(
            this,
            doSomethingMethod,
            new Object[]{},
            methodProxy
        );
    }
}
제약사항:
  • final 클래스는 프록시 생성 불가 — 상속이 불가능하기 때문
  • final 메서드는 오버라이드 불가 — 해당 메서드에는 AOP가 적용되지 않음
  • private 메서드도 오버라이드 불가 — AOP 미적용
  • 프록시 인스턴스와 타깃 인스턴스, 두 개의 객체가 생성됨 (메모리 오버헤드)

ProxyFactory — Spring이 프록시 방식을 결정하는 방법

Spring AOP에서 프록시 생성의 핵심은 DefaultAopProxyFactory다. 이 클래스가 타깃 객체의 특성을 확인하고 JDK 또는 CGLIB 프록시를 선택한다.

DefaultAopProxyFactory의 판단 로직

// DefaultAopProxyFactory.createAopProxy() 내부 로직 (간략화)
public AopProxy createAopProxy(AdvisedSupport config) {
    if (config.isOptimize()
        || config.isProxyTargetClass()       // proxyTargetClass=true이면 CGLIB
        || hasNoUserSuppliedProxyInterfaces(config)) {  // 인터페이스 없으면 CGLIB

        Class<?> targetClass = config.getTargetClass();
        if (targetClass.isInterface() || Proxy.isProxyClass(targetClass)) {
            return new JdkDynamicAopProxy(config);  // 인터페이스 자체면 JDK
        }
        return new ObjenesisCglibAopProxy(config);  // CGLIB
    }
    return new JdkDynamicAopProxy(config);  // 기본: JDK
}

Spring Boot 2.0부터 CGLIB가 기본값인 이유

spring.aop.proxy-target-class=true (Spring Boot 2.0 기본값)
  • 일관성 — 인터페이스 유무에 관계없이 항상 같은 프록시 방식을 사용
  • 구체 클래스 주입 가능 — 인터페이스 없이도 타입 안전한 DI 가능. 테스트에서도 편리
  • 어노테이션 중복 제거 — JDK 프록시에서는 인터페이스에도 어노테이션을 선언해야 하는 경우가 있었음
  • 실무 편의성 — 대부분의 Spring 애플리케이션에서 인터페이스 없이 서비스 클래스를 직접 사용

Spring Boot 1.x에서는 JDK Dynamic Proxy가 기본이었으나, 2.0에서 변경되었다.

@Transactional 내부 동작 원리

@Transactional은 Spring AOP 기반으로 동작한다. 컨테이너가 빈을 생성할 때 TransactionInterceptor가 포함된 프록시를 만들고, 이 인터셉터가 트랜잭션의 시작-커밋-롤백을 제어한다.

전체 호출 흐름

1. 클라이언트가 Proxy.method() 호출
2. TransactionInterceptor.invoke() 실행
3.   → TransactionAspectSupport.invokeWithinTransaction()
4.     → TransactionAttributeSource에서 트랜잭션 메타데이터 추출
5.       (propagation, isolation, readOnly, timeout, rollbackFor 등)
6.     → PlatformTransactionManager.getTransaction() 호출
7.       → DataSourceTransactionManager.doBegin()
8.         → DataSource에서 Connection 획득
9.         → Connection.setAutoCommit(false)   // ← 핵심! DB 트랜잭션 시작
10.        → TransactionSynchronizationManager에 Connection을 ThreadLocal로 바인딩
11.    → 타깃 메서드 실행 (비즈니스 로직)
12.    → 예외 없으면: Connection.commit()
13.    → 예외 발생 시: Connection.rollback()
14.    → Connection 정리 (autoCommit 복원, 바인딩 해제)

핵심 컴포넌트 역할

컴포넌트역할
TransactionInterceptor AOP Alliance의 MethodInterceptor 구현체. 메서드 호출을 가로채서 트랜잭션 로직을 실행
TransactionAttributeSource @Transactional 어노테이션에서 트랜잭션 속성(propagation, isolation 등)을 읽어옴
PlatformTransactionManager 트랜잭션 추상화 인터페이스. getTransaction(), commit(), rollback() 세 메서드를 정의
DataSourceTransactionManager JDBC 기반 구현체. Connection을 직접 관리. doBegin()에서 setAutoCommit(false) 호출
JpaTransactionManager JPA 기반 구현체. EntityManager와 연동. 내부적으로 JDBC Connection을 관리
TransactionSynchronizationManager ThreadLocal로 현재 스레드의 트랜잭션 상태(Connection, EntityManager 등)를 관리
주의: @Transactional은 기본적으로 RuntimeException(Unchecked)에서만 롤백한다. Checked Exception에서도 롤백하려면 @Transactional(rollbackFor = Exception.class)를 명시해야 한다.

Self-Invocation 문제 — 같은 클래스 내부 호출 시 AOP 미적용

Spring AOP의 가장 대표적인 함정이다. 같은 빈의 메서드를 내부에서 this로 호출하면, 프록시를 거치지 않고 타깃 객체의 메서드를 직접 호출하므로 AOP Advice가 전혀 적용되지 않는다. 

@Service
public class OrderService {

    @Transactional
    public void createOrder() {
        // ... 주문 생성 로직
    }

    public void processOrder() {
        this.createOrder();  // ❌ this = 실제 타깃 객체 (프록시 아님)
                            //    → @Transactional이 동작하지 않음!
    }
}

왜 이런 일이 발생하는가?

외부에서 orderService.processOrder()를 호출하면 프록시가 가로채지만, processOrder() 내부에서 this.createOrder()를 호출할 때의 this는 프록시가 아닌 실제 타깃 객체를 가리킨다. 프록시는 외부에서 들어오는 호출만 가로챌 수 있고, 타깃 내부의 호출은 관여할 수 없다.

해결 방법

방법 1. 별도 빈으로 분리 (권장) — 가장 깔끔하고 Spring 공식 권장 방법 
@Service
public class OrderTransactionService {
    @Transactional
    public void createOrder() { ... }
}

@Service
public class OrderService {
    private final OrderTransactionService txService;

    public void processOrder() {
        txService.createOrder();  // ✅ 다른 빈 → 프록시를 통해 호출 → 트랜잭션 적용
    }
}
// 방법 2. 자기 자신을 주입 (비추 — 순환 참조 유발 가능)
@Service
public class OrderService {
    @Autowired
    private OrderService self;  // 프록시 객체가 주입됨

    public void processOrder() {
        self.createOrder();  // ✅ 프록시를 통해 호출
    }
}

// 방법 3. ApplicationContext에서 빈을 꺼내기 (비추 — Service Locator 안티패턴)
@Service
public class OrderService implements ApplicationContextAware {
    private ApplicationContext ctx;

    public void processOrder() {
        ctx.getBean(OrderService.class).createOrder();  // ✅ 프록시 반환
    }
}

// 방법 4. AspectJ 위빙 사용 (런타임 프록시가 아닌 컴파일/로드 타임 위빙)
// → self-invocation 문제 자체가 없음 (바이트코드에 직접 삽입되므로)
영향 범위: @Transactional 뿐 아니라 @Cacheable, @Async, @Retryable, 커스텀 AOP 등 프록시 기반의 모든 어노테이션이 self-invocation에 영향을 받는다.

적용 대상 Spring 빈만 모든 Java 객체 (POJO 포함)

AspectJ 위빙 타입 3가지

  1. Compile-Time Weaving (CTW) — ajc 컴파일러가 소스 코드 컴파일 시 Aspect를 삽입. 가장 빠름
  2. Post-Compile Weaving (Binary Weaving) — 이미 컴파일된 .class 파일이나 JAR에 Aspect를 삽입
  3. Load-Time Weaving (LTW) — ClassLoader가 클래스를 로드하는 시점에 Aspect를 삽입. -javaagent 옵션 필요
실무 권장: 대부분의 경우 Spring AOP만으로 충분하다. self-invocation이 꼭 필요하거나, 메서드 실행 외의 Join Point가 필요하거나, 극도의 성능이 요구될 때만 AspectJ를 고려한다.
◉
BeanPostProcessor에서 프록시가 생성되는 시점

Spring AOP 프록시는 AbstractAutoProxyCreator에 의해 생성된다. 이 클래스는 BeanPostProcessor를 구현하며, 빈의 초기화 라이프사이클 중에 프록시 생성 여부를 결정한다.

빈 라이프사이클에서의 프록시 생성 위치

1. Bean 정의 등록 (BeanDefinition)
2. Bean 인스턴스 생성 (createBeanInstance)
3. 의존성 주입 (populateBean)
4. 초기화 콜백 (initializeBean)
   4-1. BeanPostProcessor.postProcessBeforeInitialization()
   4-2. @PostConstruct / InitializingBean.afterPropertiesSet() / init-method
   4-3. BeanPostProcessor.postProcessAfterInitialization()
        └─ ★ AbstractAutoProxyCreator가 여기서 프록시를 생성
5. 빈 사용 준비 완료 (컨테이너에 프록시 객체가 등록됨)

AbstractAutoProxyCreator 주요 구현체

클래스역할
AnnotationAwareAspectJAutoProxyCreator @Aspect 어노테이션 기반 AOP를 처리. @EnableAspectJAutoProxy로 활성화
InfrastructureAdvisorAutoProxyCreator @Transactional 같은 Spring 인프라 Advisor를 처리
DefaultAdvisorAutoProxyCreator ApplicationContext에 등록된 모든 Advisor에 대해 자동 프록시 생성

프록시 생성 판단 과정

// AbstractAutoProxyCreator.postProcessAfterInitialization()
public Object postProcessAfterInitialization(Object bean, String beanName) {
    if (bean != null) {
        Object cacheKey = getCacheKey(bean.getClass(), beanName);
        if (!this.earlyProxyReferences.contains(cacheKey)) {
            return wrapIfNecessary(bean, beanName, cacheKey);
        }
    }
    return bean;
}

// wrapIfNecessary() 내부
1. 이 빈에 적용할 Advisor(인터셉터)가 있는지 탐색
2. Advisor가 있으면 → ProxyFactory를 생성하고 Advisor를 추가
3. ProxyFactory.getProxy() → DefaultAopProxyFactory가 JDK/CGLIB 결정
4. 프록시 객체 반환 → 컨테이너에 원본 대신 프록시가 등록됨
즉, 다른 빈이 @Autowired로 주입받는 것은 원본 객체가 아닌 프록시 객체다. 컨테이너에 프록시가 등록되므로, 외부 호출은 항상 프록시를 통과한다.
