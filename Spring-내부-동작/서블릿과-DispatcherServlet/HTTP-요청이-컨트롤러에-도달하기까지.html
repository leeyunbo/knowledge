HTTP 요청이 컨트롤러에 도달하기까지

Spring 내부 동작 · 서블릿과 DispatcherServlet · 2026-03-25

✦
핵심 답변
HTTP 요청은 Tomcat Connector(Coyote)가 소켓을 수신하고, Catalina Engine이 서블릿 컨테이너로서 Filter Chain → DispatcherServlet → HandlerMapping → HandlerAdapter → ArgumentResolver → Controller 순서로 전달한다. 응답은 역순으로 ReturnValueHandler → HttpMessageConverter → Filter → Tomcat → Client로 돌아간다.

이 전체 흐름을 이해하려면 크게 3개 계층을 알아야 한다: (1) 서블릿 컨테이너(Tomcat)가 네트워크 I/O와 스레드 관리를 담당하고, (2) 서블릿 스펙(Filter, Servlet)이 요청/응답의 전처리/후처리를 수행하며, (3) Spring MVC(DispatcherServlet)가 핸들러 매핑, 어댑터 호출, 인자 바인딩, 응답 변환을 처리한다.

◈
1. 서블릿 컨테이너 — Tomcat 내부 구조

Tomcat의 주요 컴포넌트

Tomcat은 크게 두 모듈로 나뉜다:

  • Coyote (Connector) — HTTP/1.1, HTTP/2, AJP 등 프로토콜을 처리하는 네트워크 계층. 소켓 연결 수신, 바이트 스트림 파싱, org.apache.coyote.Request 객체 생성까지 담당한다.
  • Catalina (Container) — 서블릿 스펙을 구현한 서블릿 컨테이너. Engine → Host → Context → Wrapper(Servlet) 계층 구조로 요청을 라우팅한다.

이 둘을 연결하는 것이 CoyoteAdapter다. Coyote의 저수준 Request 객체를 Servlet API의 HttpServletRequest로 변환하여 Catalina 파이프라인에 넘긴다.

Tomcat 계층 구조

// Tomcat 내부 컨테이너 계층
Server                       // 최상위. 전체 Tomcat 인스턴스
 └─ Service                  // Connector + Engine 묶음
     ├─ Connector (Coyote)   // 네트워크 I/O, 프로토콜 처리
     └─ Engine (Catalina)    // 서블릿 컨테이너 최상위
         └─ Host             // 가상 호스트 (localhost)
             └─ Context      // 하나의 웹 애플리케이션 (WAR)
                 └─ Wrapper  // 하나의 서블릿 (DispatcherServlet)

NIO Connector의 스레드 모델

Spring Boot 기본 내장 Tomcat은 NIO Connector를 사용한다. 3종류의 스레드가 협력한다:

  • Acceptor Thread — ServerSocketChannel.accept()로 새 소켓 연결을 수락한 뒤, Poller에게 전달한다. 직접 요청을 처리하지 않는다.
  • Poller Thread — java.nio.Selector를 유지하면서, 등록된 소켓 중 읽기 가능한(readable) 소켓을 감지한다. 데이터가 준비되면 Worker 스레드 풀에 작업을 넘긴다.
  • Worker Thread (Executor) — 실제 요청을 처리하는 스레드. 기본 최대 200개(maxThreads=200). 이 스레드 위에서 Filter, Servlet, Controller 코드가 실행된다.
BIO vs NIO의 핵심 차이: BIO는 Acceptor가 소켓을 바로 Worker에게 넘겨서 연결 하나당 스레드 하나를 점유했다. NIO는 Poller가 Selector로 I/O 준비 상태를 감지하므로, 연결이 유지되더라도 데이터가 없으면 스레드를 점유하지 않는다. keep-alive 연결이 많은 환경에서 NIO가 훨씬 효율적이다.

요청 수신 흐름 (Tomcat 내부)

// 1. Acceptor: 소켓 연결 수락
SocketChannel socket = serverSocket.accept();

// 2. Poller: Selector에 소켓 등록, 읽기 가능할 때까지 대기
selector.register(socket, SelectionKey.OP_READ);

// 3. Poller: 읽기 가능한 소켓 감지 → Worker 스레드에 전달
executor.execute(socketProcessor);

// 4. Worker Thread에서:
//    Coyote가 HTTP 바이트 스트림 파싱 → coyote.Request 생성
//    CoyoteAdapter.service(coyoteReq, coyoteRes)
//      → HttpServletRequest/Response로 변환
//      → Engine → Host → Context → Wrapper 파이프라인 실행

2. 서블릿 라이프사이클 — init(), service(), destroy()

서블릿은 서블릿 컨테이너(Tomcat)가 생명주기를 관리한다. 개발자가 직접 new하지 않는다.

3단계 생명주기

  • init(ServletConfig config) — 서블릿 인스턴스가 생성된 직후 단 한 번 호출된다. DB 커넥션 풀 초기화, 설정 파일 로딩 등 무거운 초기화 작업을 여기서 수행한다. loadOnStartup 값이 0 이상이면 컨테이너 시작 시 즉시 init이 호출되고, 설정하지 않으면 첫 번째 요청이 올 때 lazy하게 초기화된다.
  • service(ServletRequest, ServletResponse) — 매 요청마다 호출된다. HttpServlet의 경우 HTTP 메서드에 따라 doGet(), doPost(), doPut(), doDelete() 등으로 분기한다. 요청마다 새로운 스레드에서 호출되므로, 서블릿 인스턴스의 필드를 공유하면 동시성 문제가 발생한다.
  • destroy() — 컨테이너가 서블릿을 제거할 때 단 한 번 호출된다. 리소스 정리(DB 연결 해제, 파일 핸들 닫기 등)를 수행한다. 모든 service() 스레드가 종료되거나 타임아웃된 후에 호출된다.
면접 포인트: 서블릿은 싱글톤이다. 컨테이너는 서블릿 클래스당 인스턴스를 하나만 생성하고, 여러 스레드가 동일한 인스턴스의 service()를 동시에 호출한다. 따라서 서블릿의 인스턴스 변수는 thread-safe하지 않다. 
public class MyServlet extends HttpServlet {

    @Override
    public void init(ServletConfig config) throws ServletException {
        super.init(config);
        // 한 번만 실행: 설정 로딩, 리소스 초기화
    }

    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp) {
        // GET 요청마다 실행
    }

    @Override
    public void destroy() {
        // 컨테이너 종료 시 한 번 실행: 리소스 정리
    }
}

3. DispatcherServlet 클래스 계층과 초기화

상속 계층

javax.servlet.http.HttpServlet          // 서블릿 스펙
  └─ HttpServletBean                     // Spring: init-param → 프로퍼티 바인딩
      └─ FrameworkServlet                 // Spring: WebApplicationContext 생성
          └─ DispatcherServlet             // Spring: 전략 컴포넌트 초기화 + 요청 디스패치

각 계층의 역할

클래스init 시 역할요청 처리 시 역할
HttpServlet 서블릿 스펙의 init() 호출 service() → HTTP 메서드별 doGet/doPost 분기
HttpServletBean init()을 오버라이드하여 web.xml의 init-param을 Servlet 인스턴스 프로퍼티에 바인딩. initServletBean() 훅 호출 직접 관여하지 않음
FrameworkServlet initServletBean()에서 WebApplicationContext 생성/초기화. onRefresh() 훅 호출 service()를 오버라이드하여 PATCH 등 추가 HTTP 메서드 지원. processRequest() → doService() 호출
DispatcherServlet onRefresh()에서 initStrategies() — 9개 전략 컴포넌트 초기화 doService() → doDispatch()에서 실제 요청 디스패치

초기화 호출 순서

// 1. 서블릿 컨테이너가 init() 호출
HttpServletBean.init()
  → init-param을 BeanWrapper로 프로퍼티에 바인딩
  → initServletBean()                  // 훅 → FrameworkServlet로

// 2. FrameworkServlet에서 ApplicationContext 생성
FrameworkServlet.initServletBean()
  → initWebApplicationContext()
    → createWebApplicationContext(rootContext)
    → configureAndRefreshWebApplicationContext(wac)
    → wac.refresh()                       // Bean 생성 완료
    → onRefresh(wac)                       // 훅 → DispatcherServlet로

// 3. DispatcherServlet에서 9개 전략 초기화
DispatcherServlet.onRefresh(context)
  → initStrategies(context)
    → initMultipartResolver(context)
    → initLocaleResolver(context)
    → initThemeResolver(context)
    → initHandlerMappings(context)       // ★ URL → Handler 매핑
    → initHandlerAdapters(context)       // ★ Handler 실행 어댑터
    → initHandlerExceptionResolvers(context)
    → initRequestToViewNameTranslator(context)
    → initViewResolvers(context)
    → initFlashMapManager(context)
면접 포인트: initStrategies()는 ApplicationContext에서 해당 타입의 Bean을 찾는다. 없으면 DispatcherServlet.properties 파일에 정의된 기본 전략 클래스를 사용한다. Spring Boot의 자동 설정이 이 Bean들을 미리 등록하므로, 대부분 커스텀 설정이 적용된다.

4. WebApplicationContext — Root vs Servlet Context

Spring MVC는 2단계 ApplicationContext 계층을 가진다:

Root WebApplicationContext

  • ContextLoaderListener가 생성한다 (서블릿 컨텍스트 리스너)
  • 애플리케이션 전역에서 공유되는 Bean: Service, Repository, DataSource, 트랜잭션 매니저
  • 모든 DispatcherServlet이 공유한다

Servlet WebApplicationContext

  • 각 DispatcherServlet이 자체적으로 생성한다
  • 해당 서블릿에만 국한되는 Bean: Controller, HandlerMapping, HandlerAdapter, ViewResolver
  • Root Context의 Bean을 상속(조회 가능)하지만, 반대는 불가
// 컨텍스트 계층 구조
Root WebApplicationContext  (ContextLoaderListener)
├── Service beans
├── Repository beans
├── DataSource, TransactionManager
│
├── Servlet WebApplicationContext  (DispatcherServlet #1)
│   ├── Controllers
│   ├── HandlerMapping
│   ├── ViewResolver
│   └── → Root의 Service/Repository Bean 조회 가능
│
└── Servlet WebApplicationContext  (DispatcherServlet #2)
    └── → 별도의 Controller, 별도의 설정 가능
Spring Boot에서는? Spring Boot는 기본적으로 Root Context 없이 단일 WebApplicationContext만 사용한다. DispatcherServlet이 생성하는 Servlet Context가 모든 Bean을 담고 있다. 전통적인 WAR 배포가 아니라면 2단계 계층을 의식할 필요가 없다.

5. Filter vs Interceptor — 실행 위치와 차이
구분FilterHandlerInterceptor
스펙 Servlet 스펙 (javax.servlet.Filter) Spring MVC 프레임워크 (HandlerInterceptor)
실행 위치 DispatcherServlet 앞 (서블릿 컨테이너 레벨) DispatcherServlet 안 (HandlerMapping 이후, Controller 이전)
실행 순서 요청: Filter → DispatcherServlet
응답: DispatcherServlet → Filter		 요청: preHandle → Controller
후: postHandle → View 렌더링 → afterCompletion
접근 가능 정보 ServletRequest/Response만 (Spring Bean에 대한 접근 어려움) Handler(Controller) 정보, ModelAndView 접근 가능
주요 용도 인코딩, CORS, 보안(Spring Security), 로깅, 압축 인증/인가, 로깅, 공통 모델 데이터, 실행 시간 측정
예외 처리 Spring의 @ExceptionHandler 범위 밖 afterCompletion에서 예외 수신 가능
Spring Bean 주입 Spring Boot에서는 @Component로 등록 가능 (DelegatingFilterProxy) Spring Bean이므로 자유롭게 DI 가능
Spring Security의 Filter Chain: Spring Security는 DelegatingFilterProxy → FilterChainProxy를 통해 서블릿 Filter 레벨에서 동작한다. 따라서 Interceptor보다 먼저 실행되며, Security에서 거부된 요청은 DispatcherServlet에 도달하지 않는다.

Interceptor의 3가지 메서드

public class LoggingInterceptor implements HandlerInterceptor {

    @Override
    public boolean preHandle(HttpServletRequest req, HttpServletResponse res,
                             Object handler) {
        // Controller 호출 전. false 반환 시 요청 중단
        return true;
    }

    @Override
    public void postHandle(HttpServletRequest req, HttpServletResponse res,
                           Object handler, ModelAndView mav) {
        // Controller 실행 후, View 렌더링 전
        // @ResponseBody 사용 시 ModelAndView는 null
    }

    @Override
    public void afterCompletion(HttpServletRequest req, HttpServletResponse res,
                                Object handler, Exception ex) {
        // View 렌더링 완료 후 (항상 실행, 예외 시에도)
    }
}

6. 전체 요청 처리 흐름 — doDispatch() 상세

DispatcherServlet의 doDispatch()는 Spring MVC의 핵심이다. 단계별로 살펴보자:

Step 1: HandlerMapping — 어떤 핸들러가 처리할까?

// DispatcherServlet.getHandler()
for (HandlerMapping mapping : this.handlerMappings) {
    HandlerExecutionChain handler = mapping.getHandler(request);
    if (handler != null) return handler;
}
  • RequestMappingHandlerMapping: @RequestMapping, @GetMapping 등 어노테이션 기반 매핑. 가장 많이 사용
  • 반환값: HandlerExecutionChain = Handler(컨트롤러 메서드) + Interceptor 목록
  • 매칭 기준: URL 패턴, HTTP 메서드, 헤더, 파라미터, Content-Type, Accept 등

Step 2: HandlerAdapter — 핸들러를 어떻게 실행할까?

// DispatcherServlet.getHandlerAdapter()
for (HandlerAdapter adapter : this.handlerAdapters) {
    if (adapter.supports(handler)) return adapter;
}
  • RequestMappingHandlerAdapter: @RequestMapping 메서드를 처리하는 핵심 어댑터
  • 어댑터 패턴을 사용하는 이유: 핸들러의 형태가 다양하기 때문 (@Controller 메서드, Controller 인터페이스 구현체, HttpRequestHandler 등)
  • DispatcherServlet은 핸들러의 구체적 타입을 몰라도, HandlerAdapter를 통해 일관되게 실행할 수 있다

Step 3: ArgumentResolver — 메서드 파라미터 바인딩

RequestMappingHandlerAdapter가 컨트롤러 메서드를 호출하기 전에, 각 파라미터를 HTTP 요청에서 추출해야 한다.

// HandlerMethodArgumentResolver 인터페이스
public interface HandlerMethodArgumentResolver {
    boolean supportsParameter(MethodParameter parameter);
    Object resolveArgument(MethodParameter parameter,
                           ModelAndViewContainer mavContainer,
                           NativeWebRequest webRequest,
                           WebDataBinderFactory binderFactory);
}
어노테이션ArgumentResolver소스
@RequestParamRequestParamMethodArgumentResolver쿼리 파라미터, 폼 데이터
@PathVariablePathVariableMethodArgumentResolverURL 경로 변수
@RequestBodyRequestResponseBodyMethodProcessorHTTP Body → HttpMessageConverter 사용
@RequestHeaderRequestHeaderMethodArgumentResolverHTTP 헤더
@ModelAttributeModelAttributeMethodProcessor쿼리 파라미터 → 객체 바인딩
@AuthenticationPrincipalAuthenticationPrincipalArgumentResolverSecurityContext

Step 4: Controller 실행

ArgumentResolver가 모든 파라미터를 준비하면, 리플렉션으로 컨트롤러 메서드를 호출한다:

// InvocableHandlerMethod.invokeForRequest()
Object[] args = getMethodArgumentValues(request, mavContainer, providedArgs);
Object returnValue = doInvoke(args);  // Method.invoke() 호출

Step 5: ReturnValueHandler — 반환값 처리

// HandlerMethodReturnValueHandler 인터페이스
public interface HandlerMethodReturnValueHandler {
    boolean supportsReturnType(MethodParameter returnType);
    void handleReturnValue(Object returnValue,
                           MethodParameter returnType,
                           ModelAndViewContainer mavContainer,
                           NativeWebRequest webRequest);
}
  • @ResponseBody 또는 ResponseEntity 반환 → RequestResponseBodyMethodProcessor가 처리
  • 내부에서 HttpMessageConverter를 사용하여 Java 객체를 JSON/XML 등으로 변환
  • MappingJackson2HttpMessageConverter: Jackson ObjectMapper로 JSON 직렬화 (가장 일반적)
  • View 이름(String) 반환 → ViewNameMethodReturnValueHandler → ViewResolver에게 위임

Step 6: ViewResolver (뷰 렌더링이 필요한 경우)

REST API(@ResponseBody)에서는 ViewResolver를 거치지 않지만, 서버 사이드 렌더링(Thymeleaf, JSP) 시 동작한다:

  • ViewResolver가 뷰 이름("home")을 실제 View 객체로 변환
  • View.render()가 Model 데이터를 사용하여 HTML을 생성하고 Response에 쓴다
REST API에서의 응답 흐름: Controller return → ReturnValueHandler → HttpMessageConverter(Jackson) → Response Body에 JSON 직접 쓰기 → ViewResolver 스킵

7. doDispatch() 핵심 코드 흐름 
protected void doDispatch(HttpServletRequest request,
                           HttpServletResponse response) throws Exception {

    HandlerExecutionChain mappedHandler = null;
    ModelAndView mv = null;

    try {
        // 1. 멀티파트 요청인지 확인
        processedRequest = checkMultipart(request);

        // 2. HandlerMapping으로 Handler 조회
        mappedHandler = getHandler(processedRequest);
        if (mappedHandler == null) {
            noHandlerFound(processedRequest, response);
            return;
        }

        // 3. Handler에 맞는 HandlerAdapter 조회
        HandlerAdapter ha = getHandlerAdapter(mappedHandler.getHandler());

        // 4. Interceptor.preHandle() 실행
        if (!mappedHandler.applyPreHandle(processedRequest, response)) {
            return;  // preHandle이 false면 중단
        }

        // 5. ★ 실제 Handler(Controller) 실행
        //    내부에서 ArgumentResolver → Controller → ReturnValueHandler
        mv = ha.handle(processedRequest, response, mappedHandler.getHandler());

        // 6. Interceptor.postHandle() 실행
        mappedHandler.applyPostHandle(processedRequest, response, mv);

    } catch (Exception ex) {
        dispatchException = ex;
    }

    // 7. View 렌더링 또는 예외 처리
    processDispatchResult(processedRequest, response, mappedHandler, mv, dispatchException);
    //    → ViewResolver로 View 렌더링
    //    → Interceptor.afterCompletion() 실행
}

Q: HTTP 요청이 Controller에 도달하기까지의 과정을 설명해주세요.

모범 답변 구조:

  1. Tomcat Connector(Coyote)가 소켓으로 HTTP 요청을 수신하고, NIO Selector로 읽기 가능 여부를 감지한 뒤, Worker 스레드에서 HTTP 파싱을 수행합니다.
  2. CoyoteAdapter가 Coyote의 내부 Request를 Servlet API의 HttpServletRequest로 변환하고, Catalina 파이프라인(Engine → Host → Context)을 통해 서블릿으로 라우팅합니다.
  3. Filter Chain이 먼저 실행됩니다. 인코딩, CORS, Spring Security 등이 여기서 동작합니다.
  4. DispatcherServlet.doDispatch()가 호출되면, HandlerMapping으로 요청에 매핑된 핸들러(컨트롤러 메서드)를 찾습니다.
  5. HandlerAdapter가 해당 핸들러를 실행할 수 있는 어댑터를 선택합니다.
  6. Interceptor.preHandle()이 실행된 후, HandlerAdapter 내부에서 ArgumentResolver가 메서드 파라미터를 HTTP 요청에서 바인딩합니다.
  7. 컨트롤러 메서드가 리플렉션으로 호출됩니다.
  8. 반환값은 ReturnValueHandler가 처리하며, @ResponseBody인 경우 HttpMessageConverter(Jackson)가 JSON으로 변환하여 응답 본문에 씁니다.
추가 포인트:
  • DispatcherServlet은 서블릿 스펙의 HttpServlet을 상속한 프론트 컨트롤러 패턴의 구현이다
  • Filter는 서블릿 스펙, Interceptor는 Spring MVC 레벨이므로 실행 시점이 다르다
  • REST API에서는 ViewResolver를 거치지 않고 HttpMessageConverter가 직접 응답을 작성한다
  • @ResponseBody가 붙으면 RequestResponseBodyMethodProcessor가 ReturnValueHandler이자 ArgumentResolver 역할을 모두 수행한다
