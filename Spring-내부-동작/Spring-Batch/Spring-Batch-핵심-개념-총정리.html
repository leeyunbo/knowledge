Spring 내부 동작 · Spring Batch · 2026-04-07

✦
핵심 답변
Spring Batch는 대량 데이터를 안전하게 처리하기 위한 프레임워크다. 핵심 추상화는 Job → Step → chunk(Reader/Processor/Writer) 3단 구조이고, chunk 단위로 트랜잭션을 끊어 메모리/실패 영향 범위를 통제한다.

Job은 "한 번의 배치 작업 단위", Step은 그 안의 처리 단계, chunk는 Step 안에서 N개씩 묶어 커밋하는 트랜잭션 단위다. Reader가 1건 꺼내고, Processor가 변환/필터링하고, Writer가 chunk만큼 모인 결과를 한 번에 저장한다.

Spring Batch가 빛나는 진짜 이유는 단순히 chunk 처리만이 아니다. 실행 이력(BATCH_* 메타테이블)을 DB에 영속화해서 재시작/멱등성/모니터링까지 지원한다는 점이다. 다만 모든 기능이 모든 배치에 필요하지는 않다 — 도구의 가치는 "내 문제에 어느 부분이 필요한가"를 판단하는 데서 나온다.

◈
알아야 할 배경 개념

1. Job · Step · chunk

Job은 배치 1회 실행 단위. JobBuilder("settlementJob", jobRepository).start(step).build() 형태로 만든다. Job 이름은 그저 라벨일 뿐, 식별자 역할은 JobInstance가 한다.

Step은 Job 안의 처리 단계. 한 Job에 여러 Step을 두고 흐름을 분기시킬 수도 있다. Step 안에서는 chunk 단위로 일이 돈다.

chunk는 "N개씩 끊어서 트랜잭션 처리하라"는 의미. 1만 건을 한 번에 처리하면 메모리가 폭발하고, 9999번째에서 죽으면 전부 롤백된다. chunk 100이면 100개씩 commit이라 메모리도 안전하고 실패 영향도 그 chunk로 한정된다.

2. JobInstance vs JobExecution

JobInstance = Job 이름 + JobParameters의 조합. 같은 조합으로 실행하면 같은 JobInstance로 본다. 한 JobInstance가 한 번 성공(COMPLETED)하면 같은 조합으로 다시는 못 돌린다 (JobInstanceAlreadyCompleteException).

JobExecution은 그 JobInstance를 실제로 실행한 한 번의 이벤트. 하나의 JobInstance에 대해 실패 → 재시작 → 성공 식의 여러 JobExecution이 붙을 수 있다. execution.getStatus()로 BatchStatus를 받아 실제 성공/실패를 판별한다.

3. ItemReader · ItemProcessor · ItemWriter

Reader는 1건씩 꺼내고, Processor는 1건을 받아 1건으로 변환(또는 null로 필터링), Writer는 chunk size만큼 모인 결과를 한꺼번에 저장한다. 이 셋을 표준 인터페이스로 통일한 게 Spring Batch 구조의 핵심이다.

4. @StepScope

Reader/Processor를 빈으로 등록할 때 @StepScope를 붙이면, Step이 시작될 때 빈이 생성되어 jobParameters를 SpEL(@Value("#{jobParameters['date']}"))로 주입받을 수 있다. 일반 빈은 앱 시작 시점에 만들어지므로 Job 파라미터를 모른다.

◉
더 깊이 파고들기

JpaCursorItemReader vs JpaPagingItemReader — 메모리 안전한 두 길

대량 데이터를 한 번에 메모리에 올리면 안 된다는 건 자명하다. Spring Batch는 두 가지 방식을 제공한다.

  • JpaCursorItemReader: JDBC 커서를 이용해 결과를 1건씩 스트리밍. 쿼리 1번으로 끝나지만, 커서가 살아있는 동안 커넥션 1개를 Step 끝까지 점유한다. GROUP BY/JOIN 등 무거운 집계와 잘 어울린다.
  • JpaPagingItemReader: 페이지마다 LIMIT/OFFSET 쿼리를 새로 날리고 커넥션을 빌렸다 놓는다. 커넥션 점유는 짧지만 OFFSET이 깊어질수록 느려지고, GROUP BY 쿼리에서는 매 페이지마다 전체 GROUP BY를 다시 돌려야 해 비효율적이다.

선택은 실행 시간대(낮/새벽), 결과 row 수, GROUP BY 유무, 커넥션 풀 여유에 따라 다르다. 정답은 없고 트레이드오프 판단이다.

N+1과 LEFT JOIN 안티조인 트릭

흔한 실수: Reader는 ID 목록만 가져오고, Processor가 ID마다 SUM/exists 쿼리를 또 날리는 패턴. ID가 N개면 쿼리가 1+2N번 발생한다. "N+1"이라 부르지만 본질은 왕복 비용(round-trip)이 곱해지는 것이다.

해결책 중 가장 우아한 형태는 LEFT JOIN + WHERE right.id IS NULL 패턴이다. 대부분의 DB가 이 패턴을 Anti-Join으로 최적화해, "오른쪽에 매칭이 없는 왼쪽 row만" 한 방에 가져온다. 정산 배치에서 "이미 정산된 가맹점은 제외하고 미처리분만 처리" 같은 멱등성 보장이 자연스럽게 풀린다.

멱등성 3겹 방어

실무 배치는 보통 3겹으로 멱등성을 보장한다.

  1. Spring Batch JobInstance 차단 (1차) — 같은 (Job + Parameters) 재실행 금지
  2. 도메인 쿼리 (LEFT JOIN/exists 체크) (2차) — 이미 처리된 건은 Reader가 안 내려보냄
  3. DB Unique Constraint (3차) — 1, 2를 모두 뚫어도 INSERT 단계에서 막힘

요구사항이 "재실행 가능 + 중복 없음"이면 1차 방어선을 일부러 우회해야 한다. 흔히 쓰는 트릭이 JobParameters에 run.id = System.currentTimeMillis()를 끼워 매번 새 JobInstance를 만드는 것. 이건 멱등성을 도메인 레벨(2, 3차)에 위임한다는 명시적 결정이다.

JPQL의 함정 — new 표현식과 FQN

JPQL은 SQL이 아니다. 엔티티/필드 기반이고, Hibernate가 DB 방언으로 번역한다. 집계 결과를 DTO로 받고 싶으면 SELECT new com.example.Dto(...) 형태의 생성자 표현식을 쓰는데, 풀 패키지 경로가 필수다. JPQL은 문자열이라 Java의 import 컨텍스트를 모른다.

Spring Boot 3 + Spring Batch 5의 함정

Spring Boot 2까지는 @EnableBatchProcessing이 필요했지만, Spring Boot 3 + Spring Batch 5에서는 정반대다. 이 어노테이션을 붙이면 BatchAutoConfiguration이 비활성화되어 BATCH_* 메타테이블 초기화 빈(JobRepositoryDataSourceScriptDatabaseInitializer)이 등록되지 않는다. 결과적으로 BATCH_JOB_INSTANCE 테이블이 없다는 에러로 모든 테스트가 깨진다.

해결: Spring Boot 3에서는 @EnableBatchProcessing을 붙이지 말 것. spring-boot-starter-batch만 의존성에 있으면 자동설정이 알아서 한다.

"왜 Spring Batch를 쓰는가" — 정직한 답

하루 한 번 도는 작은 정산 배치라면 사실 손으로 짜도 된다. Spring Batch가 진짜로 빛나는 시나리오는:

  • 수시간~수일 걸리는 배치 (실패 시 재시작 필수)
  • 수천만~수억 건 처리 (메모리/페이징/트랜잭션 직접 관리하면 버그 천국)
  • 실패 row를 따로 모아 재처리 (Skip/Retry 정책)
  • 여러 서버에 분산 처리 (Partition Step)
  • Step 분기/조건부 흐름이 복잡한 ETL

반대로 작은 배치에서 쓰는 이유는 표준 구조 · 학습 자산 · 미래 확장성 · 운영 모니터링이지, "배치니까 당연히"가 아니다. 도구를 의심할 줄 아는 것이 시니어의 시작이다.

Cursor vs Paging Reader 비교

[Cursor Reader]
앱 ─── 쿼리 1번 ───→ DB
앱 ←── 1건 ──── DB    (커넥션 점유)
앱 ←── 1건 ──── DB    (커넥션 점유)
앱 ←── 1건 ──── DB    (커넥션 점유)
       ...
앱 ←── 끝 ──── DB
   (Step 끝까지 커넥션 1개 묶임)


[Paging Reader]
앱 ─── 쿼리(LIMIT 100 OFFSET 0) ───→ DB → 100건 → 반납
앱 ─── 쿼리(LIMIT 100 OFFSET 100) ──→ DB → 100건 → 반납
앱 ─── 쿼리(LIMIT 100 OFFSET 200) ──→ DB → 100건 → 반납
       ...
   (커넥션은 짧게 빌렸다 놓음, OFFSET 비용 ↑)

LEFT JOIN Anti-Join 동작

SELECT new MerchantAggregation(p.merchantId, SUM(...), ...)
FROM Payment p
LEFT JOIN Settlement s
  ON s.merchantId = p.merchantId
 AND s.settlementDate = :date
WHERE p.status = 'APPROVED'
  AND p.approvedAt BETWEEN ... AND ...
  AND s.id IS NULL          ← anti-join 트리거
GROUP BY p.merchantId
