Spring Boot 자동 설정의 내부 동작 원리

Spring 내부 동작 · Spring Boot 자동 설정 · 2026-03-25

✦
핵심 답변
Spring Boot의 자동 설정은 @EnableAutoConfiguration이 AutoConfigurationImportSelector를 통해 META-INF/spring/...AutoConfiguration.imports 파일에 나열된 설정 클래스들을 로드하고, 각 클래스에 붙은 @Conditional 계열 어노테이션으로 클래스패스 존재 여부, 기존 빈 유무, 프로퍼티 값 등을 검사한 뒤 조건을 만족하는 빈만 등록하는 메커니즘이다.

개발자가 spring-boot-starter-web만 의존성에 추가하면 Tomcat, Jackson, DispatcherServlet 등이 자동으로 구성되는 이유가 바로 이 과정 때문이다. 아래에서 SpringApplication.run() 호출 시점부터 내장 톰캣이 뜨고 요청을 받기까지의 전 과정을 추적한다.

◈
1. @SpringBootApplication 분해

@SpringBootApplication은 세 어노테이션의 합성(composed annotation)이다.

@SpringBootConfiguration   // = @Configuration의 특수화
@EnableAutoConfiguration    // 자동 설정 핵심 트리거
@ComponentScan              // 현재 패키지 + 하위 패키지 스캔
public @interface SpringBootApplication { ... }

@SpringBootConfiguration

@Configuration의 특수 버전이다. 클래스 자체가 빈 정의의 소스임을 선언한다. Spring Boot는 애플리케이션 전체에서 하나의 @SpringBootConfiguration만 존재해야 한다는 규약을 가진다. 테스트에서 @SpringBootTest가 자동으로 이 어노테이션이 붙은 클래스를 탐색하는 이유이기도 하다.

@EnableAutoConfiguration

자동 설정의 진짜 트리거다. 내부에 @Import(AutoConfigurationImportSelector.class)가 선언되어 있어, Spring의 ConfigurationClassPostProcessor가 이 Import를 처리할 때 AutoConfigurationImportSelector.getAutoConfigurationEntry()가 호출된다.

@ComponentScan

메인 클래스가 위치한 패키지를 기준으로 @Component, @Service, @Repository, @Controller 등이 붙은 클래스를 스캔하여 빈으로 등록한다. 메인 클래스를 루트 패키지에 두는 관례가 중요한 이유다.

◉
2. SpringApplication.run() 내부 흐름

SpringApplication.run(App.class, args)를 호출하면 내부에서 다음 단계를 순서대로 밟는다.

단계별 상세

1단계: SpringApplication 인스턴스 생성

  • WebApplicationType 추론: 클래스패스에 DispatcherServlet이 있으면 SERVLET, DispatcherHandler가 있으면 REACTIVE, 둘 다 없으면 NONE
  • spring.factories에서 ApplicationContextInitializer와 ApplicationListener 구현체를 로드
  • 메인 클래스(primary source)를 추론하여 저장

2단계: SpringApplicationRunListeners.starting()

  • ApplicationStartingEvent 발행. 로깅 시스템 초기화 등이 이 시점에 수행됨

3단계: Environment 준비

  • ConfigurableEnvironment 생성 (Servlet이면 ApplicationServletEnvironment)
  • 커맨드라인 인자, 시스템 프로퍼티, OS 환경 변수, application.yml/properties 등을 PropertySource로 로드
  • ApplicationEnvironmentPreparedEvent 발행 → ConfigFileApplicationListener(Boot 2.x) 또는 ConfigDataEnvironmentPostProcessor(Boot 3.x)가 설정 파일을 파싱

4단계: ApplicationContext 생성

  • SERVLET 타입이면 AnnotationConfigServletWebServerApplicationContext 인스턴스 생성
  • 이 컨텍스트가 ServletWebServerApplicationContext를 상속하므로 내장 서버 라이프사이클을 관리할 수 있다

5단계: prepareContext()

  • Environment를 컨텍스트에 설정
  • ApplicationContextInitializer.initialize() 호출
  • 메인 클래스를 BeanDefinition으로 등록 (이 클래스에 @SpringBootApplication이 붙어 있으므로 자동 설정의 시작점이 됨)

6단계: refreshContext() — 가장 핵심

  • 내부적으로 AbstractApplicationContext.refresh()를 호출
  • invokeBeanFactoryPostProcessors()에서 ConfigurationClassPostProcessor가 실행됨
  • 이때 @EnableAutoConfiguration의 @Import(AutoConfigurationImportSelector.class)가 처리되어 자동 설정 클래스들이 로드됨
  • onRefresh()에서 ServletWebServerApplicationContext.createWebServer()가 호출되어 내장 서버가 생성되고 시작됨
  • finishBeanFactoryInitialization()에서 모든 싱글턴 빈이 실제로 인스턴스화됨

7단계: Runners 실행

  • ApplicationRunner와 CommandLineRunner 구현체가 실행됨
  • ApplicationReadyEvent 발행 → 애플리케이션이 트래픽을 받을 준비 완료
◉
3. Auto-Configuration 메커니즘 상세

AutoConfigurationImportSelector의 동작

@EnableAutoConfiguration 내부의 @Import(AutoConfigurationImportSelector.class)가 핵심이다. ConfigurationClassPostProcessor가 @Import를 만나면 AutoConfigurationImportSelector를 DeferredImportSelector로서 처리한다.

DeferredImportSelector: 일반 ImportSelector와 달리, 모든 @Configuration 클래스가 처리된 뒤에 실행된다. 이 덕분에 사용자 정의 빈이 먼저 등록되고, 자동 설정은 나중에 처리되어 @ConditionalOnMissingBean이 올바르게 동작한다.

자동 설정 후보 클래스 로딩

// AutoConfigurationImportSelector 핵심 흐름 (간소화)
protected AutoConfigurationEntry getAutoConfigurationEntry(AnnotationMetadata metadata) {
    // 1. 후보 클래스 목록 로드
    List<String> configurations = getCandidateConfigurations(metadata, attributes);
    // 2. 중복 제거
    configurations = removeDuplicates(configurations);
    // 3. exclude 속성으로 명시적 제외
    Set<String> exclusions = getExclusions(metadata, attributes);
    configurations.removeAll(exclusions);
    // 4. AutoConfigurationImportFilter로 사전 필터링
    configurations = getConfigurationClassFilter().filter(configurations);
    // 5. 이벤트 발행
    fireAutoConfigurationImportEvents(configurations, exclusions);
    return new AutoConfigurationEntry(configurations, exclusions);
}

Spring Boot 2.x vs 3.x: 설정 파일 위치

버전파일 경로형식비고
Spring Boot 2.x META-INF/spring.factories EnableAutoConfiguration=클래스1,클래스2,... 모든 팩토리 로딩에 공유되는 범용 파일
Spring Boot 2.7+ 둘 다 지원 (중복 제거) 하위 호환 + 새 형식 마이그레이션 기간
Spring Boot 3.x META-INF/spring/
org.springframework.boot.autoconfigure
.AutoConfiguration.imports		 한 줄에 FQCN 하나씩 spring.factories의 자동 설정 지원 제거

Spring Boot 3.x에서 spring.factories가 완전히 사라진 것은 아니다. ApplicationContextInitializer, ApplicationListener 등 자동 설정 이외의 팩토리 로딩은 여전히 spring.factories를 사용한다. 제거된 것은 EnableAutoConfiguration 키에 대한 지원뿐이다.

사전 필터링 (AutoConfigurationImportFilter)

Spring Boot는 모든 후보 클래스를 실제로 로드하기 전에 AutoConfigurationImportFilter (예: OnClassCondition)를 통해 ASM 기반으로 바이트코드 메타데이터만 읽어서 빠르게 필터링한다. 클래스패스에 없는 라이브러리와 관련된 자동 설정은 이 단계에서 대부분 걸러져 성능에 큰 영향을 미치지 않는다.

4. @Conditional 어노테이션 패밀리

자동 설정의 핵심은 "조건부 빈 등록"이다. Spring Framework의 @Conditional을 확장한 Spring Boot 전용 어노테이션들이 이를 담당한다.

어노테이션조건대표적 사용 예
@ConditionalOnClass 지정된 클래스가 클래스패스에 존재할 때 DataSource.class가 있으면 DB 자동 설정 활성
@ConditionalOnMissingClass 지정된 클래스가 클래스패스에 없을 때 특정 라이브러리 미존재 시 폴백 구성
@ConditionalOnBean 지정된 타입의 빈이 이미 등록되어 있을 때 DataSource 빈이 있어야 JdbcTemplate 등록
@ConditionalOnMissingBean 지정된 타입의 빈이 아직 없을 때 사용자가 직접 정의 안 했으면 기본 빈 제공
@ConditionalOnProperty 특정 프로퍼티가 지정된 값을 가질 때 spring.cache.type=redis일 때만 Redis 캐시 설정
@ConditionalOnWebApplication 웹 애플리케이션(Servlet 또는 Reactive) 환경일 때 DispatcherServlet 자동 설정
@ConditionalOnNotWebApplication 웹 환경이 아닐 때 CLI/배치 전용 구성
@ConditionalOnResource 지정된 리소스 파일이 클래스패스에 존재할 때 특정 설정 파일이 있을 때만 활성화
@ConditionalOnExpression SpEL 표현식이 true일 때 복합 조건 표현
핵심 원리: @ConditionalOnClass는 ASM 바이트코드 파싱으로 평가하므로 해당 클래스가 실제로 클래스패스에 없어도 ClassNotFoundException이 발생하지 않는다. 어노테이션의 value 속성에 클래스를 직접 참조해도 안전한 이유다.

조건 평가 순서

Spring Boot는 조건을 다음 순서로 평가한다:

  1. 클래스 조건 (@ConditionalOnClass / @ConditionalOnMissingClass) — 가장 먼저, AutoConfigurationImportFilter 단계에서 사전 필터링
  2. 빈 조건 (@ConditionalOnBean / @ConditionalOnMissingBean) — ConfigurationPhase.REGISTER_BEAN 단계에서 평가
  3. 프로퍼티 조건 (@ConditionalOnProperty) — Environment 바인딩 후 평가

5. 실제 예시: DataSourceAutoConfiguration

H2 의존성만 추가하면 DataSource가 자동 생성되는 과정을 추적해보자.

// DataSourceAutoConfiguration (Spring Boot 3.x)
@AutoConfiguration(before = DataSourceInitializationAutoConfiguration.class)
@ConditionalOnClass({ DataSource.class, EmbeddedDatabaseType.class })
@ConditionalOnMissingBean(type = "io.r2dbc.spi.ConnectionFactory")
@EnableConfigurationProperties(DataSourceProperties.class)
@Import({ DataSourcePoolMetadataProvidersConfiguration.class })
public class DataSourceAutoConfiguration {

    @Configuration(proxyBeanMethods = false)
    @Conditional(EmbeddedDatabaseCondition.class)
    @ConditionalOnMissingBean({ DataSource.class, XADataSource.class })
    @Import(EmbeddedDataSourceConfiguration.class)
    static class EmbeddedDatabaseConfiguration { }

    @Configuration(proxyBeanMethods = false)
    @Conditional(PooledDataSourceCondition.class)
    @ConditionalOnMissingBean({ DataSource.class, XADataSource.class })
    @Import({ DataSourceConfiguration.Hikari.class, ... })
    static class PooledDataSourceConfiguration { }
}

조건 평가 흐름

  1. @ConditionalOnClass({DataSource.class, EmbeddedDatabaseType.class}) → javax.sql.DataSource는 JDK에 포함, EmbeddedDatabaseType은 spring-jdbc에 포함 → 통과
  2. @ConditionalOnMissingBean(type="io.r2dbc.spi.ConnectionFactory") → R2DBC가 없으므로 → 통과
  3. @EnableConfigurationProperties(DataSourceProperties.class) → spring.datasource.* 프로퍼티를 DataSourceProperties 빈에 바인딩
  4. 내부 클래스 EmbeddedDatabaseConfiguration:
    • EmbeddedDatabaseCondition → H2/HSQL/Derby 드라이버가 클래스패스에 있는지 확인
    • @ConditionalOnMissingBean(DataSource.class) → 사용자가 직접 DataSource를 정의하지 않았는지 확인
    • 둘 다 통과하면 EmbeddedDataSourceConfiguration이 임베디드 DB DataSource를 생성
사용자가 직접 DataSource 빈을 정의하면? @ConditionalOnMissingBean(DataSource.class) 조건이 실패하여 자동 설정의 DataSource는 등록되지 않는다. 사용자 빈이 항상 우선한다.

6. 내장 톰캣 구동 과정

spring-boot-starter-web을 추가하면 내장 톰캣이 자동으로 뜨는 전체 과정이다.

자동 설정 진입점

// ServletWebServerFactoryAutoConfiguration
@AutoConfiguration
@ConditionalOnClass(ServletRequest.class)
@ConditionalOnWebApplication(type = Type.SERVLET)
@EnableConfigurationProperties(ServerProperties.class)
@Import({
    ServletWebServerFactoryAutoConfiguration.BeanPostProcessorsRegistrar.class,
    ServletWebServerFactoryConfiguration.EmbeddedTomcat.class,   // Tomcat
    ServletWebServerFactoryConfiguration.EmbeddedJetty.class,    // Jetty
    ServletWebServerFactoryConfiguration.EmbeddedUndertow.class  // Undertow
})
public class ServletWebServerFactoryAutoConfiguration { ... }
// EmbeddedTomcat 내부 클래스
@Configuration(proxyBeanMethods = false)
@ConditionalOnClass({ Servlet.class, Tomcat.class, UpgradeProtocol.class })
@ConditionalOnMissingBean(value = ServletWebServerFactory.class,
                          search = SearchStrategy.CURRENT)
static class EmbeddedTomcat {
    @Bean
    TomcatServletWebServerFactory tomcatServletWebServerFactory(...) {
        // TomcatServletWebServerFactory 빈 생성
    }
}

서버 시작 타이밍

refreshContext() 과정에서 AbstractApplicationContext.refresh()의 onRefresh() 단계가 호출된다. ServletWebServerApplicationContext는 이 메서드를 오버라이드하여 createWebServer()를 호출한다. 

// ServletWebServerApplicationContext
protected void onRefresh() {
    super.onRefresh();
    try {
        createWebServer();    // 여기서 내장 서버 생성!
    } catch (Throwable ex) { ... }
}

private void createWebServer() {
    // 1. BeanFactory에서 ServletWebServerFactory 빈 조회
    ServletWebServerFactory factory = getWebServerFactory();
    // 2. factory.getWebServer()로 Tomcat 인스턴스 생성
    this.webServer = factory.getWebServer(getSelfInitializer());
    // 3. 아직 시작은 하지 않음 (paused 상태)
}

TomcatServletWebServerFactory.getWebServer() 내부

  1. new Tomcat() 인스턴스 생성
  2. Connector 설정 (기본 포트 8080, 프로토콜 HTTP/1.1)
  3. Engine → Host → Context 계층 구조 구성
  4. ServerProperties(server.port, server.servlet.context-path 등)의 값 반영
  5. TomcatWebServer 인스턴스로 감싸서 반환 (이 시점에서는 아직 start() 호출 전)

실제 Tomcat.start()는 finishRefresh() 단계에서 WebServer.start()가 호출될 때 수행된다. 이 시점에서 커넥터가 바인딩되고 HTTP 요청을 수신할 수 있게 된다.

7. @ConfigurationProperties 바인딩 메커니즘

@ConfigurationProperties는 application.yml/properties의 값을 타입-안전한 자바 빈에 자동 바인딩하는 메커니즘이다. 

@ConfigurationProperties(prefix = "server")
public class ServerProperties {
    private Integer port;                   // server.port
    private InetAddress address;             // server.address
    private final Servlet servlet = new Servlet();

    public static class Servlet {
        private String contextPath;           // server.servlet.context-path
    }
    // getter/setter ...
}

바인딩 과정

  1. @EnableConfigurationProperties(ServerProperties.class)가 선언되면 ConfigurationPropertiesBindingPostProcessor가 등록됨
  2. 이 BeanPostProcessor가 빈 초기화 시점에 Binder를 사용하여 Environment의 프로퍼티를 빈 필드에 바인딩
  3. Binder는 ConfigurationPropertySource를 통해 프로퍼티를 읽는데, 이때 Relaxed Binding 규칙이 적용됨

Relaxed Binding 규칙

프로퍼티 표기예시매핑 대상
kebab-case (권장)server.servlet.context-pathcontextPath 필드
camelCaseserver.servlet.contextPath
snake_caseserver.servlet.context_path
UPPER_CASE (환경변수)SERVER_SERVLET_CONTEXT_PATH
Spring Boot 3.x에서는 Canonical Form으로 정규화: 프로퍼티를 내부적으로 server.servlet.context-path 형태(소문자 + 하이픈)로 정규화한 뒤 비교한다. ConfigurationPropertyName 클래스가 이 정규화를 담당한다.

타입 변환

Binder는 Spring의 ConversionService를 사용하여 문자열 프로퍼티를 Integer, Duration, DataSize, InetAddress 등 다양한 타입으로 자동 변환한다. @DurationUnit, @DataSizeUnit 같은 어노테이션으로 단위를 명시할 수도 있다. 

// application.yml
server:
  port: 8443
  shutdown: graceful
  servlet:
    session:
      timeout: 30m       // → Duration.ofMinutes(30)

8. spring-boot-starter의 역할

Starter는 의존성 묶음(dependency aggregator)이자 자동 설정 트리거다. Starter 자체에는 코드가 거의 없고, pom.xml(또는 build.gradle)에 관련 라이브러리들을 전이 의존성으로 선언한다. 

// spring-boot-starter-web이 가져오는 의존성 (간소화)
spring-boot-starter-web
├── spring-boot-starter              // 코어 (logging, yaml, auto-configure)
│   ├── spring-boot-autoconfigure    // 148개+ 자동 설정 클래스 포함
│   └── spring-boot-starter-logging  // Logback + SLF4J
├── spring-web                       // RestTemplate, WebClient 등
├── spring-webmvc                    // DispatcherServlet, @Controller
├── spring-boot-starter-tomcat       // 내장 Tomcat
│   └── tomcat-embed-core
└── spring-boot-starter-json         // Jackson

Starter가 자동 설정을 트리거하는 원리

  1. spring-boot-starter-web을 추가하면 tomcat-embed-core가 클래스패스에 들어옴
  2. spring-boot-autoconfigure JAR의 .imports 파일에 ServletWebServerFactoryAutoConfiguration이 이미 등록되어 있음
  3. 해당 자동 설정의 @ConditionalOnClass(Servlet.class, Tomcat.class) 조건이 통과됨
  4. Tomcat 관련 빈들이 자동 등록 → 내장 서버가 시작됨
요약: Starter는 코드가 아니라 의존성을 클래스패스에 올리는 역할만 한다. 실제 설정 로직은 spring-boot-autoconfigure 모듈 안에 있고, @ConditionalOnClass가 클래스패스를 감지하여 활성화한다.
