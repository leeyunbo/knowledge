스프링 IoC 컨테이너와 빈 생명주기 완벽 이해

Spring 내부 동작 · IoC 컨테이너와 빈 라이프사이클 · 2026-03-25

✦
핵심 답변
스프링 IoC 컨테이너는 객체의 생성, 의존성 주입, 초기화, 소멸까지 전체 생명주기를 관리하며, BeanPostProcessor를 통해 AOP 프록시 생성 등 횡단 관심사를 빈 생명주기에 자연스럽게 끼워넣는다.

IoC(Inversion of Control)란 객체가 자신의 의존성을 직접 생성하지 않고, 외부(컨테이너)가 대신 만들어서 주입해주는 제어의 역전이다. 이를 통해 결합도가 낮아지고, 테스트가 쉬워지며, 설정 변경만으로 구현체를 교체할 수 있다.

스프링은 BeanFactory와 ApplicationContext라는 두 가지 IoC 컨테이너를 제공하고, 빈은 인스턴스화 → 의존성 주입 → Aware 콜백 → 초기화 → 사용 → 소멸이라는 정해진 생명주기를 따른다. 각 단계마다 확장 포인트가 열려 있어 프레임워크와 개발자 모두 개입할 수 있다.

◈
DI(Dependency Injection) 3가지 방식

스프링이 의존성을 주입하는 방법은 세 가지다.

1. 생성자 주입 (Constructor Injection) — 권장

@Service
public class OrderService {
    private final OrderRepository orderRepository;
    private final PaymentService paymentService;

    // 생성자가 하나면 @Autowired 생략 가능 (Spring 4.3+)
    public OrderService(OrderRepository orderRepository, PaymentService paymentService) {
        this.orderRepository = orderRepository;
        this.paymentService = paymentService;
    }
}

2. 세터 주입 (Setter Injection)

@Service
public class OrderService {
    private OrderRepository orderRepository;

    @Autowired
    public void setOrderRepository(OrderRepository orderRepository) {
        this.orderRepository = orderRepository;
    }
}

3. 필드 주입 (Field Injection)

@Service
public class OrderService {
    @Autowired
    private OrderRepository orderRepository;  // 직접 필드에 주입
}
왜 생성자 주입이 권장되는가?
  • 불변성 보장: final 필드를 사용할 수 있어 객체 생성 후 의존성이 변경되지 않는다
  • NPE 방지: 필수 의존성이 null인 채로 객체가 생성될 수 없다 (컴파일 타임 안전)
  • 테스트 용이: 순수 자바 코드로 new를 통해 의존성을 주입할 수 있어 스프링 컨텍스트 없이 테스트 가능
  • 순환 참조 조기 발견: 생성자 주입은 순환 참조 시 즉시 예외를 던져 설계 문제를 빠르게 감지
필드 주입의 문제점: 리플렉션으로 주입하므로 final을 쓸 수 없고, 스프링 없이 테스트가 어렵다. 또한 의존성이 감춰져서 클래스의 책임이 비대해져도 눈에 잘 보이지 않는다.
◈
BeanFactory vs ApplicationContext

BeanFactory는 스프링 IoC 컨테이너의 최상위 인터페이스이고, ApplicationContext는 BeanFactory를 상속하면서 엔터프라이즈에 필요한 부가 기능을 추가한 인터페이스다.

비교 항목 BeanFactory ApplicationContext
빈 로딩 전략 Lazy Loading — getBean() 호출 시 생성 Eager Loading — 컨텍스트 시작 시 모든 싱글톤 빈을 미리 생성
BeanPostProcessor 등록 수동 등록 필요 (addBeanPostProcessor()) 자동 감지 및 등록
BeanFactoryPostProcessor 수동 호출 필요 자동 감지 및 호출
국제화 (i18n) 지원 안 함 MessageSource를 통해 지원
이벤트 발행 지원 안 함 ApplicationEventPublisher로 이벤트 발행/구독
리소스 로딩 기본적인 리소스 접근만 ResourceLoader로 classpath, URL, 파일 시스템 등 통합 접근
Environment 추상화 지원 안 함 프로파일, 프로퍼티 소스 관리
빈 스코프 singleton, prototype만 singleton, prototype, request, session, application, websocket

ApplicationContext는 BeanFactory의 모든 기능을 포함하는 상위 집합(superset)이다. 실무에서는 거의 항상 ApplicationContext를 사용한다. 대표 구현체: AnnotationConfigApplicationContext, ClassPathXmlApplicationContext, GenericWebApplicationContext.

빈 생명주기 전체 흐름 (12단계)

스프링 싱글톤 빈은 다음 순서로 생명주기를 거친다. 각 단계가 어떤 역할을 하는지 정확히 이해하는 것이 중요하다.

생성 단계 (Creation Phase)

  1. Instantiation (인스턴스화)
    컨테이너가 BeanDefinition을 기반으로 빈 객체를 생성한다. 리플렉션을 사용하며, 생성자 주입이라면 이 단계에서 의존성 해결이 함께 일어난다.
  2. Populate Properties (의존성 주입)
    세터 주입, 필드 주입으로 선언된 의존성을 주입한다. AutowiredAnnotationBeanPostProcessor가 @Autowired 어노테이션을 처리한다.
  3. BeanNameAware.setBeanName()
    빈이 BeanNameAware 인터페이스를 구현했다면, 컨테이너가 빈의 이름을 알려준다.
  4. BeanFactoryAware.setBeanFactory()
    빈이 자신을 생성한 BeanFactory 참조를 받을 수 있다.
  5. ApplicationContextAware.setApplicationContext()
    빈이 ApplicationContext 참조를 받을 수 있다. (ApplicationContext 환경에서만)
  6. BeanPostProcessor.postProcessBeforeInitialization()
    등록된 모든 BeanPostProcessor의 전처리 메서드가 호출된다. @PostConstruct 처리가 여기서 일어난다 (CommonAnnotationBeanPostProcessor).
  7. @PostConstruct
    CommonAnnotationBeanPostProcessor에 의해 @PostConstruct 어노테이션이 붙은 메서드가 실행된다. JSR-250 표준이므로 스프링에 종속되지 않는다.
  8. InitializingBean.afterPropertiesSet()
    빈이 InitializingBean 인터페이스를 구현했다면 호출된다. 스프링 프레임워크에 결합되므로 @PostConstruct 사용을 더 권장한다.
  9. Custom init-method
    @Bean(initMethod = "init") 또는 XML의 init-method로 지정한 커스텀 초기화 메서드 호출.
  10. BeanPostProcessor.postProcessAfterInitialization()
    등록된 모든 BeanPostProcessor의 후처리 메서드가 호출된다. AOP 프록시 생성이 바로 이 단계에서 일어난다! AbstractAutoProxyCreator가 이 메서드에서 대상 빈을 프록시 객체로 교체한다.
10단계를 마치면 빈은 "Ready" 상태가 되어 애플리케이션에서 사용할 수 있다. 싱글톤 빈은 컨테이너가 종료될 때까지 1차 캐시(singletonObjects)에 보관된다.

소멸 단계 (Destruction Phase)

  1. @PreDestroy
    컨테이너가 종료될 때 CommonAnnotationBeanPostProcessor에 의해 호출된다. 리소스 해제, 연결 종료 등에 사용한다.
  2. DisposableBean.destroy()
    DisposableBean 인터페이스를 구현했다면 호출. 스프링 종속이라 @PreDestroy를 더 권장한다.
  3. Custom destroy-method
    @Bean(destroyMethod = "cleanup")으로 지정한 커스텀 소멸 메서드 호출.
prototype 스코프 빈은 소멸 콜백이 호출되지 않는다! 컨테이너는 prototype 빈을 생성하고 주입까지만 관리하며, 이후 라이프사이클은 클라이언트 코드의 책임이다.

BeanPostProcessor — 빈 인스턴스 가공

BeanPostProcessor는 빈 인스턴스가 생성된 후 초기화 전/후에 커스텀 로직을 실행할 수 있는 확장 포인트다. 컨테이너에 등록된 모든 BeanPostProcessor는 모든 빈에 대해 호출된다. 

public interface BeanPostProcessor {

    // 초기화 콜백(@PostConstruct 등) 실행 전에 호출
    default Object postProcessBeforeInitialization(Object bean, String beanName) {
        return bean;
    }

    // 초기화 콜백 실행 후에 호출 — AOP 프록시 생성이 여기서!
    default Object postProcessAfterInitialization(Object bean, String beanName) {
        return bean;
    }
}
핵심: AOP 프록시 생성이 postProcessAfterInitialization에서 일어난다.
AbstractAutoProxyCreator(AnnotationAwareAspectJAutoProxyCreator의 부모)가 이 메서드에서 대상 빈을 프록시로 감싸서 반환한다. 따라서 @Transactional, @Cacheable, @Async 등이 적용된 빈은 실제로 프록시 객체가 컨테이너에 등록된다.

대표적인 BeanPostProcessor 구현체들:

  • AutowiredAnnotationBeanPostProcessor — @Autowired, @Value 처리
  • CommonAnnotationBeanPostProcessor — @PostConstruct, @PreDestroy, @Resource 처리
  • AnnotationAwareAspectJAutoProxyCreator — AOP 프록시 생성
  • AsyncAnnotationBeanPostProcessor — @Async 프록시 생성
  • ScheduledAnnotationBeanPostProcessor — @Scheduled 메서드 등록
◉
BeanFactoryPostProcessor — 빈 정의(BeanDefinition) 수정

BeanFactoryPostProcessor는 빈 인스턴스가 생성되기 전에 BeanDefinition(빈 메타데이터)을 읽고 수정할 수 있는 확장 포인트다. 빈 객체가 아니라 빈 설정을 변경한다는 점이 핵심이다. 

public interface BeanFactoryPostProcessor {

    // 모든 BeanDefinition이 로드된 후, 빈 인스턴스 생성 전에 호출
    void postProcessBeanFactory(ConfigurableListableBeanFactory beanFactory);
}
비교 BeanFactoryPostProcessor BeanPostProcessor
실행 시점 빈 인스턴스 생성 전 (BeanDefinition 로드 후) 빈 인스턴스 생성 후 (초기화 전/후)
조작 대상 BeanDefinition (빈 메타데이터, 설정값) 빈 인스턴스 (실제 객체)
대표 구현체 PropertySourcesPlaceholderConfigurer (${...} 치환)
ConfigurationClassPostProcessor (@Configuration 처리)		 AutowiredAnnotationBeanPostProcessor
AbstractAutoProxyCreator (AOP)
반환값 void (BeanDefinition을 직접 수정) Object (수정된 빈 또는 프록시 반환)
주의: BeanFactoryPostProcessor 안에서 getBean()을 호출하면 해당 빈이 너무 이르게 인스턴스화되어 BeanPostProcessor 처리를 놓칠 수 있다. 이 단계에서는 BeanDefinition 조작만 하는 것이 안전하다.

@Autowired 주입 내부 동작

@Autowired는 AutowiredAnnotationBeanPostProcessor가 처리한다. 내부 과정은 다음과 같다.

  1. 메타데이터 수집 (postProcessMergedBeanDefinition)
    빈 클래스의 모든 필드와 메서드를 리플렉션으로 스캔하여 @Autowired, @Value, @Inject 어노테이션이 붙은 요소를 찾아 InjectionMetadata 객체에 수집한다.
  2. 의존성 해결 (postProcessProperties)
    수집된 InjectionMetadata의 각 요소에 대해 컨테이너에서 매칭되는 빈을 찾는다.
    • 타입 매칭: 먼저 타입으로 후보 빈을 검색
    • @Qualifier: 후보가 여러 개면 @Qualifier로 필터링
    • 이름 매칭: 그래도 여러 개면 필드/파라미터 이름과 빈 이름을 매칭
    • @Primary: @Primary가 붙은 빈을 우선 선택
  3. 주입 실행
    필드 주입은 Field.set(), 세터 주입은 Method.invoke()로 리플렉션을 통해 값을 주입한다. 
// 의존성 해결 순서 (간략화)
// 1. 타입으로 후보 검색
Map<String, Object> candidates = findAutowireCandidates(beanName, type);

// 2. 후보가 여러 개인 경우
if (candidates.size() > 1) {
    // @Primary → @Priority → 이름 매칭 순으로 결정
    result = determineAutowireCandidate(candidates, descriptor);
}

// 3. 리플렉션으로 주입
field.set(bean, result);  // 필드 주입

Component Scanning 메커니즘

@ComponentScan은 지정된 패키지를 스캔하여 스테레오타입 어노테이션이 붙은 클래스를 자동으로 BeanDefinition으로 등록하는 기능이다.

스캔 과정

  1. @ComponentScan 파싱
    ConfigurationClassPostProcessor(BeanFactoryPostProcessor 구현체)가 @Configuration 클래스의 @ComponentScan을 읽어 basePackages를 결정한다. Spring Boot의 @SpringBootApplication에는 @ComponentScan이 포함되어 있어 해당 클래스의 패키지가 기본 스캔 대상이 된다.
  2. ClassPathBeanDefinitionScanner 실행
    ClassPathBeanDefinitionScanner가 basePackages 하위의 모든 .class 파일을 읽고, 기본 필터(@Component, @Repository, @Service, @Controller)에 매칭되는 클래스를 후보로 선택한다.
  3. BeanDefinition 생성 및 등록
    후보 클래스마다 ScannedGenericBeanDefinition을 생성하고 빈 이름을 결정한 후 BeanDefinitionRegistry에 등록한다. 빈 이름은 기본적으로 클래스명의 camelCase (예: OrderService → orderService). 
// @ComponentScan이 트리거하는 내부 흐름 (간략화)
ConfigurationClassPostProcessor.postProcessBeanDefinitionRegistry()
  → ComponentScanAnnotationParser.parse()
    → ClassPathBeanDefinitionScanner.doScan(basePackages)
      → findCandidateComponents(basePackage)  // .class 파일 스캔
        → TypeFilter.match()  // @Component 여부 확인
      → registerBeanDefinition(definitionHolder, registry)
스테레오타입 어노테이션 계층: @Repository, @Service, @Controller는 모두 @Component를 메타 어노테이션으로 갖고 있다. 따라서 @Component를 감지하는 필터가 이들도 함께 잡는다.

Bean Scope 상세
Scope 설명 생성 시점 소멸 관리
singleton (기본) 컨테이너당 인스턴스 1개. 모든 요청에 같은 객체 반환 컨텍스트 시작 시 (Eager) 컨테이너가 관리 (소멸 콜백 O)
prototype 요청할 때마다 새 인스턴스 생성 getBean() 호출 시 (Lazy) 컨테이너가 관리 안 함 (소멸 콜백 X)
request HTTP 요청당 인스턴스 1개 HTTP 요청 시작 시 요청 완료 시 소멸
session HTTP 세션당 인스턴스 1개 세션 생성 시 세션 만료 시 소멸
application ServletContext당 인스턴스 1개 ServletContext 초기화 시 ServletContext 종료 시
websocket WebSocket 세션당 인스턴스 1개 WebSocket 연결 시 WebSocket 종료 시
Scope 혼합 시 주의! Singleton 빈이 Prototype 빈을 주입받으면, singleton이 생성될 때 prototype이 딱 한 번만 주입된다. 이후에는 항상 같은 prototype 인스턴스를 사용하게 된다.

해결 방법:
  • ObjectProvider<PrototypeBean> 주입 후 매번 getObject() 호출
  • @Lookup 어노테이션으로 메서드 주입
  • Scoped proxy 사용 (@Scope(proxyMode = ScopedProxyMode.TARGET_CLASS))
// Singleton에서 Prototype을 올바르게 사용하는 방법
@Service
public class OrderService {
    private final ObjectProvider<OrderContext> contextProvider;

    public OrderService(ObjectProvider<OrderContext> contextProvider) {
        this.contextProvider = contextProvider;
    }

    public void processOrder() {
        // 매번 새로운 prototype 인스턴스 획득
        OrderContext ctx = contextProvider.getObject();
    }
}

순환 참조 해결: 3단계 캐시

스프링은 싱글톤 빈의 세터/필드 주입 순환 참조를 3단계 캐시로 해결한다. 이 세 가지 캐시는 DefaultSingletonBeanRegistry에 정의되어 있다.

캐시 레벨 필드명 타입 역할
1차 캐시 singletonObjects Map<String, Object> 완전히 초기화된 싱글톤 빈. 외부에서 사용하는 최종 캐시
2차 캐시 earlySingletonObjects Map<String, Object> 아직 초기화가 끝나지 않은 "이른 참조" 객체. 순환 참조 해결 중 사용
3차 캐시 singletonFactories Map<String, ObjectFactory<?>> 빈의 이른 참조를 생성하는 팩토리. AOP 프록시가 필요한 경우 여기서 프록시를 미리 생성

순환 참조 해결 과정 (A ↔ B)

A가 B를 주입받고, B가 A를 주입받는 상황을 가정한다.

  1. A 인스턴스 생성 (생성자 호출) → 3차 캐시에 A의 ObjectFactory 등록
  2. A의 의존성 주입 단계에서 B가 필요 → B 생성 시작
  3. B 인스턴스 생성 → 3차 캐시에 B의 ObjectFactory 등록
  4. B의 의존성 주입 단계에서 A가 필요 → 3차 캐시에서 A의 ObjectFactory를 꺼내 getObject() 호출
  5. ObjectFactory가 A의 이른 참조 반환 (AOP 대상이면 프록시, 아니면 원본) → 2차 캐시로 승격, 3차 캐시에서 제거
  6. B가 A의 이른 참조를 주입받아 B 초기화 완료 → 1차 캐시로 등록
  7. A가 완성된 B를 주입받아 A 초기화 완료 → 1차 캐시로 등록, 2차 캐시에서 제거

왜 3차 캐시(singletonFactories)가 필요한가?

단순히 순환 참조만 해결하려면 2차 캐시만으로 충분하다. 하지만 AOP 프록시가 적용된 빈이 순환 참조에 연루되면 문제가 생긴다.

정상적인 경우 AOP 프록시는 BeanPostProcessor.postProcessAfterInitialization()에서 생성된다 (생명주기 10단계). 그런데 순환 참조로 인해 초기화가 끝나기 전에 다른 빈이 참조를 요구하면, 프록시가 아닌 원본 객체를 주입하게 되어 AOP가 무시되는 치명적인 버그가 발생한다.

3차 캐시의 ObjectFactory는 이 문제를 해결한다. getObject()가 호출될 때 SmartInstantiationAwareBeanPostProcessor.getEarlyBeanReference()를 통해 AOP 프록시가 필요하면 미리 프록시를 만들어서 반환한다. 프록시가 필요 없으면 원본 객체를 그대로 반환한다.

생성자 주입에서 순환 참조가 불가능한 이유:
3차 캐시에 ObjectFactory를 등록하는 시점은 인스턴스 생성(생성자 호출) 직후다. 그런데 생성자 주입은 생성자가 완료되기 전에 의존성이 필요하다. 즉, A의 생성자를 호출하려면 B가 필요한데, A 자체가 아직 만들어지지 않아서 캐시에 등록조차 되지 않은 상태다. 따라서 순환을 끊을 방법이 없어 BeanCurrentlyInCreationException이 발생한다.

해결책: 한쪽에 @Lazy를 붙여서 프록시를 주입하거나, 설계를 변경하여 순환을 제거한다. 
// 생성자 주입 순환 참조 → @Lazy로 해결
@Service
public class ServiceA {
    private final ServiceB serviceB;

    public ServiceA(@Lazy ServiceB serviceB) {
        this.serviceB = serviceB;  // 실제 객체가 아닌 Lazy 프록시 주입
    }
}
