✦
핵심 답변
엔티티 로직은 Mock할 수 없다. 서비스를 분리하면 @SpyBean으로 중간 실패를 유도할 수 있고, 결과적으로 재사용성과 테스트 용이성이 동시에 좋아진다.
◈
문제 — 엔티티는 Mock할 수 없다

이체의 원자성을 테스트하고 싶다: "A 차감 후 B 증가 실패 시 A도 롤백되는가?"

// 엔티티에 로직이 있으면 Mock 불가
@Transactional
public TransferResult transfer(...) {
    fromWallet.transferOut(amount);  // 엔티티 메서드 → Mock 안 됨
    toWallet.transferIn(amount);     // 여기를 실패시키고 싶은데...
}

JPA 엔티티는 Hibernate 프록시로 관리되기 때문에 Mockito로 Mock/Spy 처리가 안 된다.

◉
해결 — 잔액 변동을 별도 서비스로 분리 
// WalletOperationService — 잔액 변동만 책임
@Service
public class WalletOperationService {

    @Transactional
    public PointWallet withdraw(Long walletId, BigDecimal amount) {
        PointWallet wallet = findByIdWithLock(walletId);
        wallet.decrease(amount);  // 엔티티는 순수 잔액 변동만
        return wallet;
    }

    @Transactional
    public PointWallet deposit(Long walletId, BigDecimal amount) {
        PointWallet wallet = findByIdWithLock(walletId);
        wallet.increase(amount);
        return wallet;
    }
}

// PointWalletService — 비즈니스 로직 + 트랜잭션 기록
@Service
public class PointWalletService {

    private final WalletOperationService walletOps;

    @Transactional
    public PointTransaction chargePoint(...) {
        walletOps.deposit(walletId, amount);       // 재사용
        return saveTransaction(CHARGE, ...);
    }

    @Transactional
    public PointTransaction usePoint(...) {
        walletOps.withdraw(walletId, amount);      // 재사용
        return saveTransaction(USE, ...);
    }

    @Transactional
    public TransferResult transferPoint(...) {
        walletOps.withdraw(fromId, amount);        // @SpyBean으로 Mock 가능
        walletOps.deposit(toId, amount);           // @SpyBean으로 Mock 가능
        saveTransaction(TRANSFER_OUT, ...);
        saveTransaction(TRANSFER_IN, ...);
    }
}
◆
이제 원자성 테스트가 가능하다 
@SpyBean
private WalletOperationService walletOps;

@Test
void transferAtomic_depositFails_shouldRollback() {
    // given — A: 100, B: 0
    chargePoint(walletA, 100);

    // deposit(B)에서 예외 터지게
    doThrow(new RuntimeException("증가 실패"))
            .when(walletOps).deposit(eq(walletB.getId()), any());

    // when
    assertThatThrownBy(() ->
            service.transferPoint(walletA.getId(), walletB.getId(), 50, "TX-001"))
            .isInstanceOf(RuntimeException.class);

    // then — A 잔액이 100 그대로 (롤백됨)
    assertThat(getBalance(walletA)).isEqualTo(new BigDecimal("100.00"));
}

엔티티를 Mock한 게 아니라, 엔티티를 호출하는 서비스 메서드를 Mock한 것이다.

◉
테스트 때문이 아니라, 비즈니스가 그렇다

포인트 시스템의 모든 기능이 withdraw/deposit의 조합이다:

기능구성
충전deposit
사용withdraw
이체withdraw + deposit

트랜잭션 타입(CHARGE, USE, TRANSFER_OUT/IN)은 각 비즈니스 메서드가 기록하고, 잔액 변동 자체는 공통이다. 재사용이 자연스러우니 분리가 억지가 아니다.

분리 판단 기준

분리가 맞는 경우:
  → 같은 로직이 여러 비즈니스에서 재사용됨 (withdraw/deposit)
  → 분리하면 테스트도 쉬워짐 (부수 효과)

분리가 과한 경우:
  → 한 곳에서만 쓰이는 로직을 테스트 때문에 억지로 분리
  → 재사용 없이 클래스만 늘어남
◈
테스트 레이어별 역할
레이어역할예시
엔티티 단위비즈니스 규칙 검증잔액 부족 시 예외, 음수 금액 거부, 상태 전이
서비스 통합협력 흐름 검증멱등성, 동시성, 원자성, 전체 플로우
컨트롤러요청/응답 형식@Valid, HTTP 상태 코드, JSON 구조

겹치는 것처럼 보여도 검증 관점이 다르다. 엔티티 테스트는 "규칙이 맞는가", 서비스 테스트는 "흐름이 맞는가".
