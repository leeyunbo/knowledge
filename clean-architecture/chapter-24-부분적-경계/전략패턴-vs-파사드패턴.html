전략 패턴 vs 파사드 패턴 — 부분적 경계에서의 역할

Clean Architecture · Chapter 24 부분적 경계 · 2026-03-25

✦
핵심 답변
전략 패턴은 "행위를 인터페이스로 분리해서 런타임에 교체 가능"하게 만드는 것이고, 파사드 패턴은 "복잡한 내부를 단순한 인터페이스 뒤에 숨기는" 것이다. 24장에서 둘 다 완전한 아키텍처 경계 없이도 의존성을 관리하는 부분적 경계(Partial Boundary) 전략으로 등장한다.

클린 아키텍처의 완전한 경계는 비용이 크다 — 양방향 인터페이스, 독립 컴파일, 독립 배포가 필요하니까. 24장은 "지금 당장 완전한 경계를 만들 필요는 없지만, 나중에 필요할 수도 있을 때" 쓸 수 있는 3가지 부분적 경계 전략을 제시한다. 전략 패턴과 파사드 패턴은 그중 핵심이다.

◈
알아야 할 배경 개념

1. 완전한 아키텍처 경계의 비용

완전한 경계를 만들려면:

  • 양쪽 모두에 인터페이스(Boundary Interface)를 정의
  • Input/Output 데이터 구조를 별도로 생성
  • 독립적으로 컴파일 가능한 모듈(또는 jar/패키지)로 분리
  • 의존성 관리, 버전 관리, 릴리즈 관리까지 필요

이건 진짜 비싸다. 초기에는 경계가 필요할지 확신이 없는 경우가 많다. 그래서 "부분적 경계"가 등장한다.

2. 24장의 3가지 부분적 경계 전략

전략핵심 아이디어비용보호 수준
마지막 단계 건너뛰기완전한 경계를 설계하되, 별도 컴포넌트로 분리하지 않고 같은 컴포넌트에 둔다중간높음

전략 패턴 (Strategy Pattern) — 일차원 경계

24장에서 말하는 "일차원 경계"가 바로 전략 패턴의 응용이다.

핵심: 고수준 모듈이 인터페이스에 의존하고, 저수준 모듈이 그 인터페이스를 구현한다. 이렇게 하면 의존성 방향이 역전되어 고수준 정책이 저수준 세부사항에 의존하지 않게 된다. 
// 고수준 모듈 (도메인 레이어)
public interface MessageRepository {
    Message findById(Long id);
    void save(Message message);
}

// 저수준 모듈 (인프라 레이어)
public class JpaMessageRepository implements MessageRepository {
    private final JpaRepository jpaRepo;

    @Override
    public Message findById(Long id) {
        return jpaRepo.findById(id).orElseThrow();
    }
}

// 고수준 모듈의 서비스는 인터페이스만 안다
public class MessageService {
    private final MessageRepository repository; // 인터페이스!
}

왜 "일차원"인가? 완전한 경계는 양쪽 모두 인터페이스를 두지만(쌍방향), 전략 패턴은 한쪽(고수준→저수준) 방향만 인터페이스로 보호한다. 반대 방향의 보호가 없으므로 "일차원"이다.

위험: 인터페이스가 한쪽에만 있으므로, 누군가 실수로 저수준 모듈의 구현 클래스를 직접 참조하면 경계가 무너진다. "영리한 개발자나 게으른 개발자가 이 경계를 무시하고 직접 의존할 수 있다" — 밥 아저씨의 경고.

파사드 패턴 (Facade Pattern)

가장 단순한 부분적 경계. 인터페이스조차 없이, 파사드 클래스 하나가 내부 서비스들을 호출하는 메서드만 노출한다.

핵심: 클라이언트는 Facade만 알고, 내부의 복잡한 클래스들은 모른다. 하지만 의존성 역전이 없기 때문에 모든 의존성이 같은 방향으로 흐른다. 
// Facade — 클라이언트가 아는 유일한 클래스
public class NotificationFacade {
    private final EmailSender emailSender;
    private final SmsSender smsSender;
    private final PushSender pushSender;
    private final NotificationLogger logger;

    public void notify(User user, String message) {
        // 내부의 복잡한 로직을 단순한 메서드로 감춤
        if (user.prefersEmail()) emailSender.send(user, message);
        else if (user.prefersSms()) smsSender.send(user, message);
        else pushSender.send(user, message);
        logger.log(user, message);
    }
}
위험: 파사드는 의존성 역전이 전혀 없다. 클라이언트 → Facade → 내부 클래스들로 추이적 의존성(transitive dependency)이 생긴다. 내부 클래스 중 하나가 변경되면 Facade를 거쳐 클라이언트까지 재컴파일이 필요할 수 있다.

실무에서 어떻게 선택하나?

전략 패턴을 쓸 때: 나중에 구현체가 바뀔 가능성이 높거나, 테스트에서 모킹이 필요하거나, 의존성 방향을 확실히 지키고 싶을 때. 예: Repository 인터페이스, 외부 API 클라이언트 인터페이스.
파사드를 쓸 때: 경계가 필요할지 아직 불확실하고, 일단 복잡성만 감추고 싶을 때. 비용이 가장 낮으므로 "시작점"으로 적합. 예: 여러 서비스를 묶어서 하나의 API로 노출할 때.

밥 아저씨가 강조하는 핵심 메시지

"부분적 경계는 완전한 경계보다 비용이 훨씬 적지만, 퇴화하기도 쉽다. 아키텍트의 역할은 이런 경계를 감시하고, 경계가 필요해지는 시점을 놓치지 않는 것이다."

즉, 전략 패턴이든 파사드든 "지금은 부분적 경계로 충분하지만, 언제든 완전한 경계로 승격시킬 준비"를 해야 한다는 것이다. 부분적 경계는 목적지가 아니라 경유지다.

경계의 진화 경로

실무에서 경계는 보통 이런 순서로 진화한다:

// Level 0: 경계 없음
Controller → ServiceImpl → RepositoryImpl

// Level 1: 파사드 (복잡성만 감춤)
Controller → OrderFacade → ServiceA, ServiceB, ServiceC

// Level 2: 전략 패턴 (의존성 역전)
Controller → OrderService(interface) ← OrderServiceImpl

// Level 3: 완전한 경계 (독립 컴포넌트)
[api module] → OrderService(interface)
                         ↑ 구현
[impl module] → OrderServiceImpl

파사드 패턴

전략 패턴은 인터페이스가 의존성 방향을 꺾어준다. 파사드는 의존성이 직선으로 관통한다. 이 차이가 경계의 강도를 결정한다.
