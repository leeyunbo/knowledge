Docker 기반 Jenkins 구성 — Socket, 이미지, 볼륨

DevOps 인프라 · Jenkins CI/CD · 2026-03-22

✦
핵심 답변
Jenkins를 Docker로 띄우되, Docker Socket을 마운트하면 Jenkins가 호스트의 다른 컨테이너를 빌드하고 재시작할 수 있다.

Jenkins를 직접 설치하지 않고 Docker로 운영하면 환경이 격리되고 관리가 깔끔하다. 핵심은 세 가지 볼륨 마운트다:

마운트용도
/var/run/docker.sock호스트 Docker API 접근 — 다른 컨테이너 제어
jenkins_home (Named Volume)Jenkins 설정/플러그인/빌드 기록 영속화
소스 코드 디렉토리 (Bind Mount)호스트의 프로젝트 소스를 컨테이너 안에서 접근

Docker Socket이란?

Docker 데몬은 /var/run/docker.sock이라는 Unix 소켓을 통해 명령을 받는다. docker ps, docker run 등 모든 Docker CLI 명령은 결국 이 소켓을 통해 데몬에게 API 요청을 보내는 것이다.

이 소켓 파일을 다른 컨테이너에 마운트하면, 그 컨테이너 안에서도 호스트의 Docker를 조작할 수 있다. 이를 Docker-in-Docker(DinD)의 소켓 바인딩 방식이라 한다.

주의: 이건 네트워크 통신이 아니다. HTTP API를 Unix 소켓 위에서 호출하는 것이다. 컨테이너 간 네트워크 연결(공유 네트워크 등)과는 완전히 다른 개념.

왜 커스텀 Jenkins 이미지가 필요한가?

공식 jenkins/jenkins:lts 이미지에는 Docker CLI가 없다. Socket을 마운트해도 docker 명령어 자체가 없으면 쓸 수 없다.

해결법은 Dockerfile에서 Docker CLI를 설치하는 것:

FROM jenkins/jenkins:lts
USER root
RUN apt-get update && apt-get install -y docker.io
USER jenkins

중요: 컨테이너를 재생성하면 내부에 수동 설치한 것은 전부 날아간다. 따라서 docker exec로 설치하는 게 아니라 이미지 자체에 포함시켜야 한다.

docker-compose 분리 원칙

Jenkins가 앱을 재배포할 때 DB나 캐시 같은 인프라까지 영향받으면 안 된다. 따라서 compose 파일을 분리하는 것이 일반적이다:

  • docker-compose.infra.yml — DB, Redis 등 인프라. 항상 떠있음
  • docker-compose.app.yml — 앱 컨테이너만. Jenkins가 재배포하는 대상

이렇게 분리하면 Jenkins는 앱 컨테이너만 교체하고, 인프라는 무관하게 유지된다.

◆
시각화

Jenkins가 Docker Socket을 통해 호스트의 Docker 데몬에게 명령을 보내고, 데몬이 앱 컨테이너를 빌드/재시작한다. 인프라 컨테이너는 Jenkins가 건드리지 않는다.
