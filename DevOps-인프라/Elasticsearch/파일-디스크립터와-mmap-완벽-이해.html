파일 디스크립터(FD)와 mmap 완벽 이해

DevOps 인프라 · Elasticsearch · 2026-03-26

✦
핵심 답변
FD는 프로세스가 파일을 열 때 OS가 부여하는 번호표이고, mmap은 파일을 프로세스 메모리 주소에 직접 매핑해서 복사 없이 읽는 기법이다.
Elasticsearch는 세그먼트 파일을 mmap으로 열어두고 상시 유지하기 때문에, 샤드/세그먼트가 많을수록 FD를 많이 점유한다.

ES는 Java(JVM) 기반이지만, 실제 데이터(역인덱스, 원본 문서)는 JVM 힙이 아닌 OS 페이지 캐시를 통해 읽는다. 이때 핵심 메커니즘이 mmap이고, mmap을 유지하려면 파일이 열려 있어야 하므로 FD가 상시 점유된다.

◈
알아야 할 배경 개념

1. 파일 디스크립터 (File Descriptor, FD)

프로세스가 파일을 open() 시스템콜로 열면, OS 커널이 정수 번호를 하나 돌려준다. 이게 FD다.

# 모든 프로세스는 기본 3개의 FD를 가지고 시작한다
FD 0 = stdin   (표준 입력, 키보드)
FD 1 = stdout  (표준 출력, 화면)
FD 2 = stderr  (표준 에러, 화면)

# 파일을 열면 3번부터 순서대로 부여
int fd = open("segment_0.fdt", O_RDONLY);  // fd = 3
int fd = open("segment_0.tim", O_RDONLY);  // fd = 4
int fd = open("segment_1.fdt", O_RDONLY);  // fd = 5
...

FD는 커널이 관리하는 파일 테이블(open file table)의 인덱스다. 프로세스는 이 번호로 "3번 파일에서 100바이트 읽어줘"라고 커널에 요청한다.

왜 제한이 있나? FD마다 커널 메모리(구조체)를 소비한다. 무한히 열면 커널 메모리가 고갈되므로 OS가 프로세스당 상한을 건다.
ulimit -n으로 확인 가능. 기본값은 보통 1,024개.

2. 일반적인 파일 읽기 (read 시스템콜)

애플리케이션                커널                     디스크
    |                       |                        |
    |--- read(fd, buf, n) ->|                        |
    |                       |--- 디스크에서 읽음 --->|
    |                       |<-- 데이터 반환 ---------|
    |                       |                        |
    |                       |  커널 버퍼에 복사        |
    |                       |  커널 → 유저 메모리 복사 |
    |<-- buf에 데이터 -------|                        |

문제: 커널 버퍼 → 유저 메모리로 복사가 일어난다. 대용량 파일을 반복 읽으면 이 복사 비용이 크다.

3. mmap (Memory-Mapped I/O)

애플리케이션                커널                     디스크
    |                       |                        |
    |--- mmap(fd, ...) ---->|                        |
    |                       |  가상 주소 공간에        |
    |                       |  파일을 매핑 (아직 안 읽음)|
    |<-- 메모리 주소 반환 ---|                        |
    |                       |                        |
    |--- ptr[100] 접근 ---->|                        |
    |                       |  Page Fault 발생!       |
    |                       |--- 해당 페이지만 읽음 ->|
    |                       |<-- 데이터 반환 ---------|
    |                       |  페이지 캐시에 올림      |
    |<-- 데이터 즉시 접근 ---|  (복사 없음!)           |

핵심 차이: 복사가 없다. 파일 내용이 담긴 페이지 캐시를 프로세스가 직접 참조한다.

  • mmap() 호출 시점에는 실제로 디스크를 안 읽음 (lazy loading)
  • 해당 메모리 주소에 접근할 때 Page Fault가 발생하면서 OS가 디스크에서 로드
  • 한 번 로드된 페이지는 OS 페이지 캐시에 남아서 다음 접근은 메모리 속도
  • 여러 프로세스가 같은 파일을 mmap하면 같은 물리 페이지를 공유 (메모리 효율적)

4. Page Fault란?

CPU가 가상 메모리 주소에 접근했는데, 해당 페이지가 물리 메모리에 없을 때 발생하는 인터럽트다.

  • Minor Page Fault: 페이지가 이미 페이지 캐시에 있음 → 매핑만 하면 됨 (빠름)
  • Major Page Fault: 디스크에서 읽어와야 함 (느림, I/O 발생)

ES에서 자주 접근하는 세그먼트는 Minor Fault만 발생하므로 매우 빠르고, 오래된 세그먼트는 Major Fault가 발생할 수 있다. 이것이 "핫 데이터"와 "콜드 데이터"의 성능 차이 원인이기도 하다.

◉
ES에서 FD와 mmap이 작동하는 방식

ES(Lucene)의 세그먼트 파일과 mmap

ES의 검색 엔진인 Lucene은 세그먼트 파일들을 mmap으로 열어서 사용한다.

세그먼트 파일 용도 mmap 여부
.tim / .tip역인덱스 (단어 → 문서 매핑)mmap (검색마다 접근)
.fdt원본 JSON (_source)mmap
.dvd / .dvmDoc Values (정렬/집계)mmap
.si세그먼트 메타mmap
.fnm필드명, 타입 정보mmap

이 파일들을 mmap으로 열면 파일이 열린 상태로 유지된다. 닫으면 매핑이 끊기기 때문이다.

FD 사용량 계산 예시

# 세그먼트 1개당 파일 약 6~8개
# 샤드 1개에 세그먼트가 평균 3~5개

샤드 1개 = 세그먼트 4개 x 파일 7개 = FD 28개
인덱스 1개 = Primary 2 + Replica 2 = 샤드 4개 = FD 112개
날짜별 인덱스 30일 = 인덱스 30개 = FD 3,360개

+ 네트워크 소켓 (노드 간 통신, 클라이언트 연결)
+ Translog 파일
+ 기타 임시 파일

=> 기본 ulimit 1,024로는 턱없이 부족!
ES 공식 권장: ulimit -n 65535 이상 설정.
설정 안 하면 Too many open files 에러로 ES가 죽을 수 있다.

mmap은 배타적 잠금이 아니다

mmap은 "이 파일을 내 메모리 주소에 매핑해줘"라는 요청일 뿐, 파일을 독점하지 않는다.

# 동시에 가능
ES 프로세스    ── mmap ──> segment_0.fdt   (O)
다른 프로세스  ── read() ──> segment_0.fdt  (O)
또 다른 프로세스 ── mmap ──> segment_0.fdt  (O)

파일을 독점하려면 별도로 flock() 같은 파일 락을 걸어야 한다. ES가 락을 거는 건 write.lock 파일 하나뿐이고, 이건 같은 샤드를 두 프로세스가 동시에 쓰는 걸 방지하기 위한 것이다.

JVM 힙 vs OS 페이지 캐시

ES는 JVM 위에서 돌지만, 데이터 저장/검색의 핵심은 JVM 밖에서 일어난다.

저장 위치 무엇이 올라가나 관리 주체
JVM Heap 세그먼트 메타데이터, 클러스터 상태, 필드 매핑, 쿼리 캐시, 요청 버퍼 JVM GC
OS 페이지 캐시 (off-heap) 역인덱스 데이터, 원본 문서, Doc Values — mmap으로 매핑된 세그먼트 파일 전부 OS 커널
디스크 세그먼트 파일 원본 (.fdt, .tim 등) 파일시스템

그래서 ES 운영 시 JVM 힙을 전체 메모리의 50% 이하로 설정하라는 권장이 있다. 나머지 50%를 OS 페이지 캐시용으로 남겨둬야 mmap 성능이 나온다.

Warm 단계에서 shrink하면 절약되는 것

ILM Warm 단계에서 샤드를 2개 → 1개로 축소(shrink)하면:

리소스 샤드 2개 샤드 1개 (shrink 후) 영향도
FD (상시 점유)~56개~28개큰 절약
힙 메모리 (세그먼트 메타)2배1배미미
mmap 매핑 영역2배1배중간
클러스터 상태 관리마스터가 2개 추적1개 추적누적 시 큼
검색 스레드쿼리당 2개쿼리당 1개Warm은 거의 안 읽힘

핵심은 "상시 비용 vs 가끔의 이점"이다. 샤드 2개의 FD/mmap 매핑은 24시간 소비되지만, Warm 데이터는 거의 조회되지 않고 조회되어도 keyword 정확 일치로 수 ms면 끝난다.

◆
시각화

read() vs mmap 데이터 흐름

read()는 커널 버퍼 → 유저 메모리로 복사가 2번 일어나지만, mmap은 페이지 캐시를 직접 참조하므로 복사가 0번이다. 대신 mmap은 파일을 열어둔 채 유지해야 하므로 FD를 상시 점유한다.

ES에서의 메모리 계층

ES 서버의 RAM이 32GB라면, JVM 힙 16GB + 페이지 캐시 16GB가 이상적이다. 힙을 너무 크게 잡으면 mmap 성능이 떨어지고, 너무 작게 잡으면 GC가 폭주한다.

◉
read() vs mmap 비교 정리
항목 read() 시스템콜 mmap()
데이터 복사커널 → 유저 메모리 (복사 발생)직접 참조 (복사 없음)
FD 사용읽고 닫으면 반환 가능매핑 유지 = 상시 점유
캐싱OS 페이지 캐시 + 유저 버퍼OS 페이지 캐시만 (효율적)
랜덤 접근seek + read (시스콜 반복)포인터 연산 (빠름)
대용량 반복 읽기느림빠름
파일 공유프로세스별 독립 버퍼같은 물리 페이지 공유 가능
적합한 경우순차 읽기, 한 번 읽고 끝반복 랜덤 접근 (검색 엔진!)

ES(Lucene)가 mmap을 선택한 이유: 역인덱스 검색은 같은 파일의 여러 위치를 반복적으로 랜덤 접근하는 패턴이므로, mmap이 압도적으로 유리하다.

운영 시 주의사항

ulimit 설정

# 현재 FD 제한 확인
ulimit -n
# 1024  ← 기본값, ES에 부족

# /etc/security/limits.conf 에 추가
elasticsearch  -  nofile  65535

# 또는 systemd 서비스 파일에서
[Service]
LimitNOFILE=65535

현재 ES 프로세스의 FD 사용량 확인

# ES 프로세스의 열린 파일 수 확인
GET _nodes/stats/process

# 응답에서 확인할 필드
"process": {
  "open_file_descriptors": 312,    // 현재 사용 중
  "max_file_descriptors": 65535    // 최대 허용
}

vm.max_map_count 설정

mmap 매핑 영역 수에도 OS 제한이 있다.

# 현재 값 확인
sysctl vm.max_map_count
# 65530  ← 기본값

# ES 권장값 설정
sysctl -w vm.max_map_count=262144

# 영구 적용: /etc/sysctl.conf
vm.max_map_count=262144
Docker에서 ES 실행 시 이 설정을 호스트에서 해야 한다. 컨테이너 안에서는 변경 불가.
