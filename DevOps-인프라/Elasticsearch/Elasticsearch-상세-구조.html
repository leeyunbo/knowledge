Elasticsearch 상세 구조

DevOps 인프라 · Elasticsearch · 2026-03-23

✦
핵심 답변
Elasticsearch는 분산 역색인(Inverted Index) 기반 검색 엔진으로, 데이터를 여러 노드의 샤드에 분산 저장하고, 역색인 구조로 전문 검색을 밀리초 단위로 수행한다.

RDBMS가 행(row) 단위로 데이터를 저장하고 B-Tree 인덱스로 탐색하는 반면, ES는 문서(Document) 단위로 저장하고 역색인(Inverted Index)으로 탐색한다. 이 구조 차이가 "텍스트 검색"에서 압도적인 성능 차이를 만든다.

◈
알아야 할 배경 개념

1. Lucene — ES의 심장

ES는 Apache Lucene 위에 만들어진 래퍼다. Lucene이 실제 역색인 생성, 검색, 스코어링을 담당하고, ES는 그 위에 분산 처리, REST API, 클러스터 관리를 얹은 것이다.

사용자 → ES REST API → ES 분산 레이어 → Lucene (실제 검색)

2. 역색인 (Inverted Index)

일반 인덱스가 "문서 → 단어"를 매핑한다면, 역색인은 "단어 → 문서 목록"을 매핑한다.

Term (토큰)Document IDs
elasticsearchdoc_1, doc_3, doc_7
검색doc_1, doc_2, doc_5
인덱스doc_2, doc_3
분산doc_1, doc_7

"elasticsearch 분산"을 검색하면? 두 포스팅 리스트의 교집합을 구하면 끝 → doc_1, doc_7. B-Tree처럼 모든 행을 LIKE 스캔할 필요가 없다.

3. Analyzer — 텍스트를 토큰으로 분해하는 파이프라인

역색인을 만들려면 먼저 텍스트를 토큰으로 쪼개야 한다. 이 과정을 Analysis라 하며, 3단계로 구성된다:

Character Filter → Tokenizer → Token Filter
  • Character Filter: 원본 텍스트 전처리 (HTML 태그 제거, 특수문자 치환 등)
  • Tokenizer: 텍스트를 토큰으로 분리 (Standard, Nori(한국어), Whitespace 등)
  • Token Filter: 토큰 후처리 (소문자 변환, 불용어 제거, 동의어 확장 등)
// 예시: "The Quick Brown Fox!" → Standard Analyzer
Character Filter : "The Quick Brown Fox!"  → 변화 없음
Tokenizer       : ["The", "Quick", "Brown", "Fox"]
Token Filter    : ["the", "quick", "brown", "fox"]  → lowercase

한국어의 경우 Nori Analyzer를 사용하며, 형태소 분석을 통해 "검색엔진을" → ["검색", "엔진", "을"] 같이 분리한다.

2. 샤드 (Shard) — 분산의 핵심

인덱스를 만들 때 Primary Shard 수를 지정한다 (기본 1개, 생성 후 변경 불가). 문서는 hash(_id) % shard_count로 어떤 샤드에 갈지 결정된다.

  • Primary Shard: 원본 데이터를 가진 샤드. 쓰기 요청을 먼저 처리
  • Replica Shard: Primary의 복제본. 읽기 부하 분산 + 장애 시 승격
Primary Shard 수는 인덱스 생성 후 변경할 수 없다. 나중에 바꾸려면 _reindex로 새 인덱스를 만들어야 한다. 초기 설계가 중요하다.

3. 세그먼트 (Segment) — 불변 파일의 비밀

각 샤드는 내부적으로 여러 세그먼트로 구성된다. 세그먼트는 한 번 쓰면 절대 수정되지 않는 불변(immutable) 파일이다.

  • 새 문서 인덱싱 → 메모리 버퍼에 쌓임 → 주기적으로 새 세그먼트로 flush
  • 문서 수정 → 기존 문서를 삭제 표시 + 새 세그먼트에 신규 버전 작성
  • 문서 삭제 → .del 파일에 삭제 표시만 (실제 삭제는 merge 시)
왜 불변으로 만들까? 동시성 제어가 극도로 단순해진다. 락(lock) 없이 여러 스레드가 동시에 읽을 수 있고, OS 파일시스템 캐시를 최대한 활용할 수 있다.

4. Segment Merge — 가비지 컬렉션

시간이 지나면 작은 세그먼트가 쌓인다. ES는 백그라운드에서 작은 세그먼트들을 큰 세그먼트로 합병(merge)한다. 이때 삭제 표시된 문서가 실제로 제거된다.

// Merge 전
Segment_1 (100 docs, 3 deleted)
Segment_2 (50 docs, 1 deleted)
Segment_3 (30 docs, 0 deleted)

// Merge 후
Segment_merged (176 docs, 0 deleted)  ← 삭제된 4개 제거됨

5. Near Real-Time (NRT) 검색

ES는 "실시간"이 아니라 "거의 실시간(NRT)"이다:

  • 문서 인덱싱 → 메모리 버퍼에 저장
  • Refresh (기본 1초 간격) → 메모리 버퍼의 내용을 새 세그먼트로 만들어 검색 가능하게 함
  • Flush (주기적) → 세그먼트를 디스크에 영구 저장 + Translog 클리어
문서를 인덱싱하고 최대 1초 후에 검색 결과에 나타난다. 이것이 "Near Real-Time"의 의미다.

6. Translog — 장애 복구의 핵심

Refresh로 세그먼트가 만들어져도 아직 디스크에 flush되지 않았을 수 있다. 이 사이에 노드가 죽으면? Translog(Transaction Log)가 이를 방지한다.

  • 모든 인덱싱/삭제 연산은 Translog에 먼저 기록 (WAL과 동일한 개념)
  • 노드 재시작 시 Translog를 replay하여 유실된 세그먼트 복구
  • Flush 이후 Translog 삭제

8. 검색 실행 과정 (Query → Fetch)

ES의 분산 검색은 2 phase로 동작한다:

Phase 1 — Query: 모든 관련 샤드에서 매칭되는 문서 ID + 점수를 수집
Phase 2 — Fetch: 상위 N개 문서의 실제 데이터를 해당 샤드에서 가져옴 
// 예: "elasticsearch" 검색 (3 Primary Shards)

Client → Coordinating Node
           ├─→ Shard 0: 매칭 doc_id + score 반환
           ├─→ Shard 1: 매칭 doc_id + score 반환
           └─→ Shard 2: 매칭 doc_id + score 반환

Coordinating Node: 전체 결과를 score 기준 정렬, 상위 10개 선택

Coordinating Node → 해당 샤드들에서 실제 문서 데이터 fetch
           → Client에 최종 결과 반환

9. Relevance Scoring (BM25)

ES는 검색 결과의 관련성 순위를 매기기 위해 BM25 알고리즘을 사용한다 (v5.0부터, 이전은 TF-IDF).

  • TF (Term Frequency): 해당 문서에 검색어가 많이 나올수록 높은 점수
  • IDF (Inverse Document Frequency): 전체 문서에서 드물게 나타나는 단어일수록 높은 점수
  • Field Length: 짧은 필드에서 매칭되면 더 높은 점수 (제목 > 본문)

10. Mapping — 스키마 정의

RDBMS의 스키마에 해당한다. 각 필드의 데이터 타입과 분석 방법을 정의한다.

{
  "mappings": {
    "properties": {
      "title":   { "type": "text", "analyzer": "nori" },
      "status":  { "type": "keyword" },
      "price":   { "type": "integer" },
      "created": { "type": "date" }
    }
  }
}
타입역색인 여부용도
textO (Analyzer 적용)전문 검색 (match query)
keywordO (토큰화 없이 원본 그대로)정확 일치, 필터링, 집계, 정렬
integer / long / floatX (BKD tree)범위 검색, 집계
dateX (내부적으로 long)시간 범위 검색
booleanX필터링
text vs keyword를 구분하는 게 핵심이다. text는 분석(토큰화)되므로 "Hello World"로 검색하면 "hello"와 "world" 각각 매칭. keyword는 "Hello World" 전체가 하나의 토큰이므로 정확히 일치해야 매칭.
