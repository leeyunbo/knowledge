핵심 답변
결제 시스템의 4가지 핵심 패턴: 멱등성(중복 요청 안전), 상태 머신(잘못된 전이 방지), Outbox(외부 API 결과 기록), 복구 스케줄러(stuck 건 자동 복구).
◈
1. 멱등성 (Idempotency)

같은 요청을 여러 번 보내도 결과가 같아야 한다. 클라이언트가 네트워크 오류로 응답을 못 받아 재요청하는 경우를 대비.

@Transactional
public Payment createPayment(String orderId, BigDecimal amount, String cardNumber) {
    // orderId로 기존 결제가 있으면 그대로 반환
    return paymentRepository.findByOrderId(orderId)
            .orElseGet(() -> {
                Payment payment = new Payment(orderId, amount, cardNumber);
                return paymentRepository.save(payment);
            });
}

핵심: 비즈니스 키(orderId)를 unique로 잡고, 이미 존재하면 기존 것을 반환.

2. 상태 머신 (State Machine)

규칙: 엔티티 내부에서 상태 전이를 검증한다. 서비스가 아니라 엔티티가 책임진다.

public void startApprove() {
    validateStatus(PaymentStatus.READY, "승인");  // READY가 아니면 예외
    this.status = PaymentStatus.APPROVE_IN_PROGRESS;
}

public void startCancel(BigDecimal cancelAmount) {
    if (this.status != PaymentStatus.APPROVED) {  // APPROVED가 아니면 예외
        throw new IllegalStateException("취소할 수 없는 상태: " + this.status);
    }
    // 금액 검증도 엔티티에서
    ...
    this.status = PaymentStatus.CANCEL_IN_PROGRESS;
}

3. Outbox 패턴 — 외부 API 결과 기록

문제: 카드사 승인은 성공했는데 DB 반영 전에 서버가 죽으면?

startApprove() → APPROVE_IN_PROGRESS → 커밋 ✅
cardApiClient.approve() → 카드사 승인 성공 ✅
                                    → 결과를 CardApiResult에 저장 ✅ ← Outbox!
completeApprove() → 서버 죽음 💥 → DB는 APPROVE_IN_PROGRESS로 남음

해결: 외부 API 호출 결과를 별도 테이블에 즉시 저장. 래퍼 클래스(CardApiService)가 호출과 기록을 항상 함께 수행.

// CardApiService — 래퍼: API 호출 + 결과 저장이 항상 함께
public String approve(Long paymentId, String cardNumber, BigDecimal amount) {
    try {
        String approvalNumber = cardApiClient.approve(cardNumber, amount);
        cardApiResultRepository.save(CardApiResult.approveSuccess(paymentId, approvalNumber));
        return approvalNumber;
    } catch (CardApiClient.CardApiException e) {
        cardApiResultRepository.save(CardApiResult.approveFailed(paymentId, e.getMessage()));
        throw e;
    }
}

4. 복구 스케줄러

IN_PROGRESS 상태가 일정 시간(5분) 이상 유지되면 비정상으로 판단. CardApiResult를 보고 자동 복구.

@Scheduled(fixedDelay = 60_000) // 1분마다
public void recoverStuckPayments() {
    List<Payment> stuck = paymentRepository.findStuckPayments(
        List.of(APPROVE_IN_PROGRESS, CANCEL_IN_PROGRESS),
        LocalDateTime.now().minusMinutes(5));

    for (Payment payment : stuck) {
        CardApiResult result = cardApiResultRepository
            .findTopByPaymentIdOrderByCreatedAtDesc(payment.getId());

        if (result != null && result.isSuccess()) {
            complete(payment, result);  // API 성공 → 완료 처리
        } else {
            rollback(payment);          // API 실패 or 미호출 → 롤백
        }
    }
}
CardApiResult 상태복구 액션
SUCCESScomplete — API는 성공했으니 DB만 맞춰줌
FAILEDrollback — 이전 상태로 복구
없음rollback — API 호출 전에 죽은 것
◈
서비스 책임 분리 
PaymentService (오케스트레이터)
├─ PaymentTransitionService  → 상태 전이 + 락 관리
├─ CardApiService            → 외부 API 호출 + 결과 저장 (래퍼)
└─ PaymentRepository         → 생성/조회

각 서비스가 하나의 책임만 갖는다. 검증은 엔티티가, 마스킹 같은 표현 로직은 DTO가 담당.
