택시/야옹이 예시로 본 서비스의 오류

Clean Architecture · Chapter 27 크고 작은 모든 서비스들 · 2026-04-02

✦
핵심 답변
서비스를 나누면 아키텍처가 보호된다는 건 착각이다. 택시 시스템에 "야옹이 배달" 기능을 추가하면 모든 서비스가 동시에 변경된다. 컴포넌트 아키텍처를 서비스 내부에 적용하면 배포 범위는 여전히 전체지만, "기존 코드 수정"이 "새 코드 추가"로 바뀐다 — 이것이 밥 아저씨가 말하는 진짜 보호다.

27장의 핵심 메시지는 "서비스가 횡단 관심사를 막지 못하니까, 서비스에 기대지 말고 컴포넌트 설계를 제대로 해라"다. 서비스는 배포 메커니즘일 뿐이고, 아키텍처 보호는 다른 레벨의 일이다.

◈
알아야 할 배경 개념

1. 서비스에 대한 흔한 착각 두 가지

밥 아저씨는 서비스에 대한 두 가지 오해를 먼저 꼬집는다:

  • "서비스를 분리하면 결합이 분리된다" — 서비스 간에 공유 데이터나 공유 로직이 있으면 여전히 결합되어 있다. 네트워크를 사이에 둔다고 결합이 사라지는 게 아니다.
  • "서비스를 분리하면 독립 개발/배포가 가능하다" — 여러 서비스가 같은 요구사항 변경에 영향받으면 함께 수정·함께 배포해야 한다. 독립 배포는 환상이 된다.

2. 횡단 관심사(Cross-Cutting Concern)

기능이 여러 서비스를 가로질러(cross-cut) 영향을 미치는 것. 서비스를 아무리 잘게 쪼개도 횡단 관심사 앞에서는 모든 서비스가 동시에 변경된다. 이것이 택시/야옹이 예시의 핵심이다.

3. "수정"과 "추가"는 다르다

같은 "4개 서비스 전부 건드리기"라도 그 방식이 완전히 다르다:

  • 수정(modify) — 기존 코드를 열어서 if-else를 끼워넣는다. 기존 로직이 깨질 위험이 있고, 전체 회귀 테스트가 필요하다.
  • 추가(extend) — 새 파일(플러그인)을 추가한다. 기존 코드는 건드리지 않으므로 기존 로직이 깨지지 않고, 새 코드만 테스트하면 된다.

이 차이가 OCP(개방-폐쇄 원칙)의 핵심이며, 27장이 컴포넌트 아키텍처로 해결하려는 문제다.

더 깊이 파고들기

택시 통합 시스템 — 초기 설계

도시의 택시 업체들을 통합하는 시스템을 마이크로서비스로 설계한다:

서비스역할
TaxiUI고객이 택시를 요청하는 모바일 앱
TaxiFinder가까운 택시 후보를 찾아서 필터링
TaxiSelector비용·시간 등 조건에 맞는 택시를 최종 선택
TaxiDispatcher선택된 택시에 배차 명령 전달

여기까지만 보면 깔끔하다. 각 서비스가 하나의 역할을 담당하고, 독립적으로 개발·배포할 수 있을 것 같다.

"야옹이 배달" 기능 추가 — 문제 폭발

회사가 새 사업을 시작한다: "야옹이 배달(Kitten)" — 고양이를 고객에게 배달하는 서비스. 택시와 동일한 인프라를 재활용하되, 야옹이를 운반할 수 있는 차량만 필터링해야 한다.

결과: 이 단 하나의 요구사항이 모든 서비스의 기존 코드를 수정하게 만든다.
  • TaxiUI → 기존 UI 코드에 야옹이 배달 옵션 if-else 추가
  • TaxiFinder → 기존 필터 로직에 야옹이 조건 if-else 추가
  • TaxiSelector → 기존 비용 계산에 야옹이 분기 추가
  • TaxiDispatcher → 기존 배차 로직에 야옹이 명령 분기 추가

"야옹이"라는 횡단 관심사가 모든 서비스를 관통한다. 서비스를 나눴지만 독립 배포는 불가능하다 — 4개를 동시에 수정하고 동시에 배포해야 한다.

밥 아저씨의 해결책: 컴포넌트 아키텍처를 서비스 안에 넣어라

해결은 서비스를 더 쪼개는 것이 아니라, 각 서비스 내부에 컴포넌트 아키텍처를 적용하는 것이다.

예를 들어 TaxiFinder 서비스 안에:

// 추상 컴포넌트 (서비스 내부)
public interface VehicleFinder {
    List<Vehicle> findNearby(Location loc, Criteria c);
}

// 택시용 플러그인
public class TaxiVehicleFinder implements VehicleFinder { ... }

// 야옹이용 플러그인 — 기존 코드 수정 없이 추가!
public class KittenVehicleFinder implements VehicleFinder { ... }

그래서 뭐가 해결된 건데?

여기서 흔히 드는 의문: "결국 4개 서비스 전부 배포하는 건 마찬가지 아닌가?"

맞다. 배포 범위는 해결 안 됐다. 밥 아저씨가 해결하려는 건 "배포 독립성"이 아니라 "변경 안전성"이다.

컴포넌트 없음컴포넌트 있음
배포 범위4개 서비스 전부4개 서비스 전부
변경 방식기존 코드에 if-else 추가 (수정)새 플러그인 파일 추가 (확장)
기존 코드 위험기존 택시 로직이 깨질 수 있음기존 택시 로직 안 건드림
테스트 범위전체 회귀 테스트 필요새 플러그인만 테스트
OCP위반만족
배포 범위는 같지만, 변경의 위험도가 완전히 다르다. "4개 서비스를 배포한다"는 사실은 같아도, "기존 코드를 열어서 수정한다" vs "새 파일을 추가한다"는 근본적으로 다른 행위다.

27장의 진짜 결론

서비스는 횡단 관심사를 막지 못한다. 서비스에 의존하지 말고, 서비스 내부에 컴포넌트 설계를 제대로 해라. 서비스는 배포 메커니즘일 뿐이고, 아키텍처 보호는 컴포넌트 레벨에서 일어난다.
착각현실
서비스 = 아키텍처 경계서비스는 배포 경계일 뿐. 아키텍처 경계는 컴포넌트가 만든다
서비스를 나누면 결합이 줄어든다횡단 관심사 앞에서 모든 서비스가 함께 변경된다
서비스를 더 쪼개면 해결된다쪼개기가 아니라 서비스 내부에 OCP를 적용해야 한다
컴포넌트 설계가 배포 독립성을 준다배포 범위는 못 줄인다. 대신 변경 안전성(수정→추가)을 준다

컴포넌트 없이: 기존 코드 수정 (위험)

컴포넌트 적용: 새 플러그인 추가 (안전)
