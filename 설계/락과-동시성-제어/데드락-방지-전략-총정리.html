데드락 방지 전략 총정리

설계 스터디 · 락과 동시성 제어 · 2026-03-30

✦
핵심 답변
데드락은 두 트랜잭션이 서로가 잡은 락을 기다리면서 영원히 진행되지 않는 상태다. 락 순서 고정, 타임아웃, 락 범위 최소화, 낙관적 락 등으로 방지한다.
◈
데드락이 발생하는 조건 
Thread 1: A 락 🔒 → B 락 대기...
Thread 2: B 락 🔒 → A 락 대기...
→ 서로 대기 → 영원히 진행 안 됨 💥

데드락이 발생하려면 4가지 조건이 모두 충족돼야 한다:

  • 상호 배제 — 자원을 동시에 사용할 수 없음
  • 점유 대기 — 하나 잡은 채로 다른 것을 기다림
  • 비선점 — 강제로 빼앗을 수 없음
  • 순환 대기 — A→B→A 순환 구조

이 중 하나라도 깨면 데드락이 발생하지 않는다.

◉
방지 전략

1. 락 순서 고정 (순환 대기 깨기) ⭐

항상 ID가 작은 쪽을 먼저 잠근다. 가장 확실하고 많이 쓰는 방법.

// A→B 이체, B→A 이체 동시 발생 시
Long firstId = Math.min(fromId, toId);
Long secondId = Math.max(fromId, toId);

wallet1 = findByIdWithLock(firstId);   // 항상 작은 ID 먼저
wallet2 = findByIdWithLock(secondId);

// Thread 1: A(1)→B(2) → 1 먼저 🔒 → 2 🔒
// Thread 2: B(2)→A(1) → 1 먼저 🔒 (대기) → 2 🔒
// 순서가 같으니 데드락 없음

2. 락 타임아웃 (비선점 깨기)

일정 시간 내에 락을 못 잡으면 포기하고 재시도.

// JPA 힌트로 타임아웃 설정
@QueryHints(@QueryHint(name = "jakarta.persistence.lock.timeout", value = "3000"))
@Lock(LockModeType.PESSIMISTIC_WRITE)
Optional<PointWallet> findByIdWithLock(@Param("id") Long id);
// 3초 내에 락 못 잡으면 PessimisticLockException

// 또는 DB 수준 설정
SET innodb_lock_wait_timeout = 5;  -- MySQL

3. 낙관적 락 사용 (상호 배제 깨기)

비관적 락 대신 @Version으로. 락을 안 잡으니 데드락 자체가 불가능.

@Version
private Long version;

// 충돌 시 OptimisticLockException → 재시도
// 단점: 충돌이 잦으면 재시도가 많아져서 비효율

4. 락 범위 최소화 (점유 대기 줄이기)

락을 잡는 시간을 최소화해서 충돌 확률 자체를 줄인다.

// ❌ 락 잡고 외부 API 호출 (오래 잡음)
@Transactional
public void transfer() {
    lock(walletA);         // 🔒
    lock(walletB);         // 🔒
    externalApi.call();    // 느림... 이 동안 다른 요청 대기
    walletA.withdraw();
    walletB.deposit();
}   // 🔓

// ✅ Saga 패턴으로 분리 (락 구간 최소화)
startTransfer();           // 🔒 → 상태 선점 → 🔓
externalApi.call();        // 락 없음
completeTransfer();        // 🔒 → 반영 → 🔓

5. 단일 락으로 통합

여러 자원을 잠그는 대신 하나의 상위 락으로 통합.

// 여러 row를 개별 잠그는 대신
// Redis 분산 락 하나로 전체 이체 작업을 감싸기
redisLock.lock("transfer:" + Math.min(fromId, toId) + ":" + Math.max(fromId, toId));
try {
    // 이체 로직 (DB 락 없이)
} finally {
    redisLock.unlock();
}

6. 트랜잭션 분리 (점유 대기 깨기)

하나의 트랜잭션에서 여러 락을 잡지 않도록 분리.

// 하나의 트랜잭션에서 A, B 둘 다 잠그는 대신
// 트랜잭션 1: A에서 차감
// 트랜잭션 2: B에서 증가
// 실패 시 보상 트랜잭션으로 복구
// 단점: 원자성 보장이 어려워짐 (Saga 패턴 필요)
◆
전략 비교
전략깨는 조건난이도적합한 경우
락 순서 고정순환 대기쉬움이체, 다중 자원 락 (가장 정석)
락 타임아웃비선점쉬움모든 비관적 락 (보험용)
낙관적 락상호 배제쉬움충돌이 드문 경우
락 범위 최소화점유 대기중간외부 API 호출 포함 시
단일 락 통합순환 대기중간Redis 분산 환경
트랜잭션 분리점유 대기높음MSA, Saga 패턴
