JPA 양방향 매핑 — 언제 쓰고 언제 피하는가

설계 스터디 · JPA 실전 패턴 · 2026-03-30

✦
핵심 답변
기본은 단방향. 양방향은 역방향 탐색이 빈번할 때만. 안 쓰는 양방향은 복잡성만 늘린다.
◈
단방향 vs 양방향

단방향 (기본)

// PaymentCancel → Payment 방향만 탐색 가능
public class PaymentCancel {
    @ManyToOne
    @JoinColumn(name = "payment_id")
    private Payment payment;  // cancel.getPayment() ✅
}

public class Payment {
    // cancels 필드 없음 → payment.getCancels() ❌
    // 필요하면 Repository로 조회
}

양방향

public class PaymentCancel {
    @ManyToOne
    @JoinColumn(name = "payment_id")
    private Payment payment;  // cancel.getPayment() ✅ (관계의 주인)
}

public class Payment {
    @OneToMany(mappedBy = "payment")
    private List<PaymentCancel> cancels;  // payment.getCancels() ✅ (읽기 전용)
}
단방향양방향
복잡도낮음높음 (주인/비주인, 동기화)
의존 방향명확 (한쪽만)순환 의존
역방향 탐색Repository로 별도 조회객체 그래프로 바로 접근
관리 포인트적음양쪽 동기화 필요
◉
관계의 주인 (mappedBy)

양방향 매핑에서 FK를 가진 쪽이 주인이다. 주인만 DB에 반영되고, 비주인(mappedBy)은 읽기 전용.

// ✅ 올바른 설정
public class PointWallet {
    @OneToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "user_id")  // FK 보유 → 관계의 주인
    private User user;
}

public class User {
    @OneToOne(mappedBy = "user")   // 읽기 전용 → 비주인
    private PointWallet wallet;
}

// ❌ 둘 다 mappedBy → 누가 주인인지 모름 → 에러
public class PointWallet {
    @OneToOne(mappedBy = "wallet")  // 나는 비주인
    private User user;
}
public class User {
    @OneToOne(mappedBy = "user")    // 나도 비주인 → FK가 없음 → 💥
    private PointWallet wallet;
}
규칙: @JoinColumn을 가진 쪽 = 주인, mappedBy를 가진 쪽 = 비주인(읽기 전용)
◉
양방향의 함정들

1. 양쪽 동기화를 직접 해줘야 함

// 주인 쪽만 세팅하면 DB에는 반영되지만, 같은 트랜잭션에서 비주인 쪽은 null
cancel.setPayment(payment);          // DB 반영 ✅
payment.getCancels().add(cancel);    // 메모리 동기화 (안 하면 같은 트랜잭션에서 조회 시 빈 리스트)

// 편의 메서드로 양쪽 동기화
public void addCancel(PaymentCancel cancel) {
    this.cancels.add(cancel);
    cancel.setPayment(this);
}

2. 순환 참조 — JSON 직렬화 시 무한 루프

// Payment → cancels → Payment → cancels → ... 무한 루프
// 해결: DTO로 변환해서 반환 (엔티티를 직접 반환하지 않으면 문제 없음)

3. 불필요한 쿼리

// EAGER면 Payment 조회할 때마다 cancels JOIN
// LAZY면 getCancels() 접근할 때 추가 쿼리
// → 안 쓰는 양방향은 낭비
◆
판단 기준 
양방향이 필요한 경우:
  payment.getCancels()를 자주 호출 → 양방향 (+ FETCH JOIN)
  cascade로 자식 엔티티 생명주기 관리 → 양방향

단방향으로 충분한 경우:
  역방향 조회가 드묾 → cancelRepository.findByPaymentId()로 충분
  조회만 필요하고 생명주기 관리 불필요 → 단방향
