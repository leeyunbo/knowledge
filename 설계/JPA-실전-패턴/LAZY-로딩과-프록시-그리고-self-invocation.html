LAZY 로딩과 프록시, 그리고 self-invocation

설계 스터디 · JPA 실전 패턴 · 2026-03-25

✦
핵심 답변
JPA의 LAZY 로딩, @Transactional 모두 프록시로 동작한다. 프록시의 원리를 이해하면 왜 self-invocation에서 트랜잭션이 안 걸리는지, 왜 트랜잭션 밖에서 LAZY 접근하면 터지는지 전부 설명된다.
◈
LAZY vs EAGER 
@OneToMany(fetch = FetchType.LAZY)   // 기본값 — 접근할 때 SQL 실행
@OneToMany(fetch = FetchType.EAGER)  // 항상 즉시 로딩

EAGER를 안 쓰는 이유 — 결제 조회할 때마다 취소 내역이 항상 딸려 나온다. 상태 체크만 하면 되는 곳에서도 불필요한 JOIN이 발생한다.

원칙: 기본은 LAZY, 필요한 곳에서만 FETCH JOIN.

// FETCH JOIN으로 필요할 때만 한 번에 가져오기
@Query("SELECT p FROM Payment p LEFT JOIN FETCH p.cancels WHERE p.id = :id")
Optional<Payment> findByIdWithCancels(@Param("id") Long id);

// LEFT JOIN FETCH → cancels 없어도 Payment 반환
// JOIN FETCH → cancels 없으면 결과 없음
◉
프록시 동작 원리

Hibernate가 엔티티를 상속한 가짜 클래스를 런타임에 만든다.

// Hibernate가 런타임에 만드는 프록시 (개념적)
public class Payment$HibernateProxy extends Payment {
    private boolean loaded = false;

    @Override
    public List<PaymentCancel> getCancels() {
        if (!loaded) {
            // 이 시점에 SQL 실행
            loaded = true;
        }
        return super.getCancels();
    }
}

그래서 엔티티 클래스에 제약이 있다:

  • final 클래스 ❌ → 상속 못 하면 프록시 못 만듦
  • private 기본 생성자 ❌ → protected 이상이어야 인스턴스 생성 가능
  • final 메서드 ❌ → 오버라이드 못 하면 가로채기 못 함

단일 엔티티(@ManyToOne) → 엔티티 상속 프록시
컬렉션(@OneToMany) → Hibernate가 PersistentBag으로 교체

◆
@Transactional self-invocation 문제

@Transactional도 프록시로 동작한다. 외부 호출만 프록시를 타고, 내부 호출은 안 탄다.

@Service
public class PaymentService {

    @Transactional
    public void methodA() { ... }  // 트랜잭션 걸림

    public void methodB() {
        this.methodA();  // ❌ this = 진짜 객체, 프록시 아님 → 트랜잭션 무시
    }
}

// 외부에서 호출하면 프록시를 탐
paymentService.methodA();  // ✅ 프록시 → 트랜잭션 시작

해결책: 별도 빈으로 분리.

// PaymentTransitionService (별도 빈)
@Transactional
public void startCancel(...) { ... }

// PaymentService에서 호출 → 항상 프록시 탐
transitionService.startCancel(...);
◉
dirty checking과 불변 객체

JPA는 엔티티 스냅샷과 현재 필드 값을 비교해서 변경을 감지한다.

// BigDecimal은 불변 — 재할당해야 변경 감지
this.canceledAmount.add(cancelAmount);                    // ❌ 새 객체 반환, 필드 그대로
this.canceledAmount = this.canceledAmount.add(cancelAmount); // ✅ 필드 재할당 → dirty checking 감지

// 컬렉션은 별도 추적 — 내부 변경도 감지
this.cancels.add(new PaymentCancel(...));  // ✅ JPA가 감지
◈
트랜잭션 분리 시 엔티티 재조회

트랜잭션 1에서 조회한 엔티티를 트랜잭션 2에서 쓸 수 없다.

startCancel()     ← 트랜잭션 1: 조회, 상태 변경, 커밋 → 엔티티 detached
API 호출           ← 트랜잭션 없음
completeCancel()  ← 트랜잭션 2: 새 영속성 컨텍스트 → 다시 조회해야 함

JPA의 트레이드오프 — MyBatis라면 조회 없이 바로 UPDATE 가능하지만, JPA는 엔티티 기반이라 조회가 필수.
